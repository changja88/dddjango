# dddjango-web 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md` 사본이 해당 runtime에 대한 권위 있는 가이드입니다.
manifest의 homepage는 최신 온라인 문서(latest-online)를 찾는 발견 경로이며, 설치 버전의 동작 기준은
이 사본을 우선합니다. 이 가이드는 Claude Code와 Codex 설치본에서 독립적으로 읽을 수 있습니다.

## 1. 언제 쓰는가

`dddjango-web`은 기존 Django 프로젝트의 한 화면과 관련 파생 화면을 만들거나 수정합니다.
기준 시안은 **Claude Design 시안으로만 받습니다.** Claude Design 공유 URL을 주거나, 같은 시안을
Claude Design에서 내려받은 폴더를 줍니다. 공유한 시안의 배치·서체·색상·여백과 필요한 동작을
충실하게 재현합니다. 의미에 맞는 HTML과 유지보수 가능한 화면 구조, 반응형·상태별 동작은
플러그인이 설계하고 구현합니다.

실제 데이터와 연동하는 화면은 기존 API를 사용합니다. 새 API나 업무 규칙·권한·데이터 처리 기능이
필요하면 플러그인이 부족한 백엔드 결과와 범위를 설명하고 별도 `dddjango` 작업을 안내합니다.
필요한 API가 아직 없다면 `dddjango` 작업을 먼저 요청하세요. 서버와 연결하지 않고 시안의 견본 값으로 보여 주는
화면도 요청할 수 있습니다.

한 요청에는 한 화면과 그 파생 화면을 담습니다. 서로 다른 화면을 여럿 바꾸는 일이면 나눠서 요청하세요.

## 2. 바로 시작

기준 시안(Claude Design 공유 URL 또는 내려받은 폴더), 그 안에서 구현할 화면, 원하는 작업을 알려 주세요.
Claude Code에서는 `/dddjango-web:dddjango-web`으로, Codex에서는 `dddjango-web을 사용해 …`처럼
요청합니다. Claude Code에서는 명령을 요청의 맨 앞에 직접 입력합니다. 긴 문서를 붙여 넣을 때도 명령을
먼저 입력한 뒤 붙이거나, 문서는 파일 경로로 알려 주세요.

### 기본 요청

Claude Code:

```text
/dddjango-web:dddjango-web 주문 목록 화면을 시안대로 구현해 주세요.
Claude Design 공유 URL: [공유 URL]
구현 대상: 주문 목록 / 기본
```

Codex:

```text
dddjango-web을 사용해 주문 목록 화면을 시안대로 구현해 주세요.
Claude Design 공유 URL: [공유 URL]
구현 대상: 주문 목록 / 기본
```

`[공유 URL]`을 실제 Claude Design 공유 URL로 바꿔 주세요. 여러 화면이나 상태가 포함돼 있다면
이번에 구현할 화면·상태의 이름을 함께 적습니다. 시안 내용을 옮겨 적거나 요약할 필요는 없습니다.
플러그인이 받은 시안이 기준이며, 화면과 상태의 이름만 알려 주면 됩니다.

### 내려받은 시안 폴더로 요청하기

Claude Design에서 내려받은 폴더도 기준 시안으로 쓸 수 있습니다. `.dc.html` 파일과 `_ds`·`assets` 등
함께 내려받은 파일이 들어 있는 폴더를 그대로 주세요.

```text
/dddjango-web:dddjango-web 관계인 화면을 시안대로 구현해 주세요.
기준 시안: /Users/me/Downloads/서비스 웹앱 (Claude Design에서 내려받은 폴더)
구현 대상: 관계인 / 기본
```

시안 없이 시작하는 요청이나 이미지·일반 웹페이지를 기준 시안으로 삼는 요청은 이 가이드의 시작
방식에 포함하지 않습니다. 먼저 Claude Design 시안을 준비한 뒤 요청하세요.

### 시안에 접근할 수 없을 때

```text
dddjango-web을 사용해 회원가입 화면을 만들어 주세요.
Claude Design 공유 URL: [공유 URL]
구현 대상: 회원가입 / 기본
접근 문제: 공유 URL을 열면 권한이 없다고 표시됩니다.
```

접근 문제를 알리고 공유 설정을 확인하거나, 같은 시안을 내려받은 폴더를 주세요. 로그인이 필요하면
요청 전에 에이전트가 쓰는 브라우저에서 Claude Design에 로그인해 둡니다. 접근을 해소한 시안을 구현 기준으로 사용합니다.
API 위치를 모르거나 필요한 상태·폭을 아직 정하지 못했어도 요청할 수 있습니다.
플러그인이 프로젝트에서 확인할 수 있는 사실을 조사하고, 사용자가 결정할 부분을 질문합니다.

기준 시안과 구현 대상을 전달한 뒤, 아래 항목 중 이미 알고 있거나 정한 내용만 덧붙이면 됩니다.
추가 항목을 모두 채울 필요는 없습니다.

| 묶음 | 알려 주면 좋은 내용 |
|---|---|
| 화면 | 만들거나 바꿀 화면과 원하는 변화, 유지할 부분과 이번 범위에서 제외할 부분 |
| 필수 상태·폭·동작 | 이미 정한 화면 상태, 필요한 화면 폭, 클릭·입력·스크롤 뒤 기대하는 결과 |
| 의도적인 차이 | 사용자가 직접 시안과 다르게 만들기로 정한 부분과 그 결과. 정하지 않았으면 비워 두세요. 기본은 시안 그대로입니다 |
| 데이터 연동 의도 | 실제 데이터로 동작할지, 서버와 연결하지 않고 시안의 견본 값으로 보여 줄 화면인지 등 정해진 범위 |

## 3. 알려 주면 좋은 제품 정보

시안만으로 알기 어렵거나 이미 정해진 결과가 있을 때 다음처럼 보충할 수 있습니다.

- 정확한 디자인 대상: “공유 URL의 ‘주문 목록 / 기본’ 화면을 기준으로 합니다.”
  다른 상태의 시안도 함께 쓴다면 해당 시안과 화면 이름으로 기준을 지정합니다.
- 상태별 결과: “검색 결과가 없으면 필터 초기화 버튼을 보여 주세요.” 또는
  “조회에 실패하면 기존 목록을 유지하고 재시도할 수 있어야 합니다.”
  긴 제목이나 이미지가 없는 주문에서 보존해야 할 표시도 정해져 있다면 함께 말할 수 있습니다.
- 눌러야 보이는 상태: “지역 드롭다운을 연 상태와 삭제 확인 창도 시안대로 맞춰 주세요.”
  시안에서 조작해야 나타나는 상태도 맞춰야 한다면 그 상태를 이름으로 알려 주세요.
- 반응형과 동작: “390px에서는 목록을 한 열로 보여 주고 필터를 접을 수 있어야 합니다.”
  “스크롤 중에도 주문 합계가 화면 하단에 보여야 합니다”처럼 화면에서 기대하는 변화를 설명합니다.
  꼭 필요한 움직임이 있다면 어떤 행동 뒤에 무엇이 어떻게 변하는지 알려 주세요.
- 브라우저 안의 UI 동작: “비밀번호 표시 버튼을 누르면 입력값을 볼 수 있고, 다시 누르면 숨깁니다.”
  “선택한 이미지는 업로드 전에 미리 볼 수 있고, 선택을 지우면 미리보기도 사라집니다”처럼
  필요한 동작과 그 뒤의 결과를 설명합니다. 정해진 키보드·포커스 동작이나 실패 안내도 덧붙일 수 있습니다.
- 의도적인 차이와 보존: “시안에 없는 배송 안내를 주문 금액 아래에 추가하고,
  기존 주문 상세 진입 동작은 유지해 주세요.” 사용자가 직접 정한 차이만 적습니다. 시안이 정한
  컴포넌트 종류를 기본 요소로 바꾸는 것(예: 시안의 드롭다운을 기본 선택 상자로)은 차이로 받지 않습니다.

이 예시는 제품 결과를 설명하는 단서입니다. 필요한 상태와 폭을 모두 미리 열거하거나,
아직 정하지 않은 결과를 추측해서 보충할 필요는 없습니다.

## 4. 플러그인이 하는 일과 요청에 적지 않을 것

플러그인은 요청과 기존 프로젝트를 바탕으로 다음 작업을 맡습니다.

- 시안 조사: 기준 시안의 접근 가능성과 지정한 화면을 확인하고,
  사용할 수 있는 읽기·추출·비교 방법을 판단합니다. 구현 기준으로 쓸 시안을 보존하고,
  필요한 디자인 정보와 이미지·폰트를 조사해 활용합니다.
- 화면 상태와 검증 계획: 시안과 요구에서 필요한 상태·폭·동작을 정리하고,
  이를 재현하고 확인할 방법을 구성합니다.
- API 조사: 실제 데이터 연동에 사용할 API 계약을 확인해 요청·응답과 화면 요구를 대조합니다.
  필요한 계약이 없거나 자료가 서로 다르면 부족한 결과와 결정할 부분을 설명합니다.
- 화면 구조와 구현: 의미에 맞는 HTML과 유지보수 가능한 CSS를 작성합니다.
  Django가 서버 데이터와 업무 판정을 맡고, HTMX가 서버 요청과 화면 일부의 교체를 맡습니다.
  브라우저 안의 임시 UI 동작에는 필요한 경우 JavaScript를 사용합니다.
  HTML·CSS만으로 충분한 동작은 그대로 구현하며, 업무 권한·금액·저장 여부의 최종 판정은 서버에 둡니다.
- 검토와 확인: 작업에 맞는 agent·skill, 코드 검토와 검증 방법을 선택합니다.
  필요한 UI 동작은 반복 조작·키보드·실패 상태와 화면 일부가 교체된 뒤의 동작까지 확인하고,
  실제 실행 결과와 미확인 부분을 구분해 정리합니다.

조사만으로 정할 수 없는 제품 선택은 질문하고, 필요한 승인은 플러그인이 안내합니다. 새 화면을 만들거나
기존 영역을 건드리면 이 화면을 어느 영역에 둘지 묻습니다. 정하지 않았으면 맡길 수 있습니다.
사용자가 정해 요청에 적은 구체적인 결정은 기록해 다시 묻지 않습니다.
실제 API와 연결할 부분은 사용할 수 있는 계약이 준비되어야 구현할 수 있습니다.
새로운 데이터 조회·변경이나 업무상 권한 같은 백엔드 기능이 필요하면 별도 작업 범위를 안내하며,
API를 어떤 도구로 만들었는지는 관계없습니다.

화면 설계와 구현은 플러그인이 합니다. 요청에 다음을 적으면 시안 재현과 플러그인의 규칙 검사를
가로막습니다. 원하는 것이 있으면 화면에서 보이는 결과로 적어 주세요.

- 파일 경로·줄 번호, 템플릿·컴포넌트 분해, CSS 클래스·JS 이벤트, 사용할 라이브러리
- 수정해도 되는 파일이나 건드리면 안 되는 경로의 목록
- “이 화면을 본떠라” 같은 선례 지정. 참고할 화면이 있으면 위치만 알려 주세요.
- 시안 내용을 옮겨 적거나 요약한 수치·문구·비율. 시안이 기준입니다.
- 사용자가 정하지 않은 “의도적인 차이”
- 진행 방식, 시안을 다시 받는 절차, 검사나 승인 단계를 줄이거나 건너뛰라는 지시

기준 시안과 다르게 정하고 싶은 부분은 요청에 적기보다 먼저 시안을 고쳐 주세요. 사용자가 직접 정한
차이는 “의도적인 차이”로 적을 수 있습니다.

## 5. 있으면 함께 주기

알고 있는 위치나 이미 가진 자료가 있을 때만 함께 주면 조사를 빠르게 할 수 있습니다.

- 추가 시안: 다른 상태·폭의 기준도 Claude Design 시안(공유 URL 또는 내려받은 폴더)과 그 안의
  화면 이름으로 지정합니다.
- 동작 보조 자료: 기준 시안의 클릭이나 스크롤 동작을 설명하는 영상이나 관찰 내용.
- 별도 이미지·폰트: 따로 전달해야 하는 원본 파일이나 위치, 이미 알고 있는 사용·접근 제약.
- 대표 데이터: 긴 제목, 빈 목록, 이미지가 없는 항목, 권한에 따라 달라지는 표시 등의 예.
- API 문서: 실제 데이터 연동은 OpenAPI 문서(URL 또는 파일)로 확인되는 API를 기준으로 합니다.
  위치를 알면 함께 주세요. 없으면 플러그인이 묻고, 끝내 없으면 서버와 연결하지 않는 견본 값 화면으로
  할지 정합니다.
- 관련 자료 위치: 기존 화면이나 코드, 이미 확보한 응답 예시.
- 실행 환경: 이미 띄운 개발 서버 주소, 사용할 Python·가상환경, 쓰면 안 되는 포트.
- 지켜야 할 환경 조건: 개발 DB를 쓰면 안 된다거나 실제 외부 호출을 하면 안 된다는 조건과 그 이유.
- 외부 접근 사실: 시안이나 API에 로그인·조직 권한이 필요한지, 링크가 만료되었는지 등
  플러그인이 프로젝트 안에서 알 수 없는 조건.
- 동시 작업: 같은 화면이나 공용 파일을 동시에 고치는 다른 작업이 있다는 사실.

자료는 알고 있는 위치만 전달해도 됩니다. 자료의 내용과 이번 화면에 필요한 정보는 플러그인이
조사하고, 추가 접근이나 별도 자료가 꼭 필요하면 구체적으로 묻습니다.

시안 확인과 화면 검증에는 에이전트가 쓸 수 있는 브라우저가 필요합니다. 브라우저가 없으면 시안 준비
단계에서 멈추고 필요한 조건을 알립니다. 구현한 화면을 확인하지 못한 범위는 미확인으로 보고합니다.

## 6. 수정하거나 이어서 요청하기

바꿀 화면 결과와 보존할 부분을 알려 주세요. 중단한 작업이라면 이전 작업을 이어간다는 사실을
덧붙이면 됩니다.

```text
dddjango-web을 사용해 이전 주문 목록 화면 작업을 이어 주세요.
기준 시안: 이전 작업의 Claude Design 공유 URL과 구현 대상 그대로 사용
빈 목록 안내를 ‘조건에 맞는 주문이 없습니다’로 바꾸고 필터 초기화 버튼을 추가해 주세요.
기본 목록과 오류 안내, 주문 상세로 이동하는 동작은 유지해 주세요.
```

이어서 요청할 때는 이전에 전달한 기준 시안과 구현 대상을 그대로 사용하는지 알려 주세요.
기준 시안이 바뀌었다면 새 시안과 대상 화면을 전달합니다. 같은 공유 URL에서 시안을 고쳤다면
“시안이 바뀌었다”고 알려 주세요. 플러그인은 바뀐 시안을 스스로 감지하지 않습니다.
‘(임시)’ 문안이나 아직 정하지 않은 칸이 있는 시안은 확정한 뒤 요청하세요. 작업 중에 시안을 고치면
시안을 다시 받아 구현과 다시 대조해야 합니다.
API 자료나 이전 작업 위치를 알고 있다면 함께 줄 수 있습니다.
대화 밖에서 디자인이나 API가 바뀌었다면 알고 있는 변경 사실을 알려 주세요.
플러그인이 기존 기록과 현재 자료를 조사해 다음 작업을 정합니다.

화면의 모양과 동작을 유지하면서 코드를 정리해 달라고 요청할 수도 있습니다.

```text
dddjango-web을 사용해 주문 목록의 동작은 유지하면서 코드를 수정하기 쉽게 정리해 줘.
모양은 기준 시안을 따라 줘.
Claude Design 공유 URL: [공유 URL]
구현 대상: 주문 목록 / 기본
```

모양의 기준은 현재 화면이 아니라 기준 시안입니다. 기준 시안과 현재 화면이 다른 곳은 유지할지 묻고,
시안이 정한 컴포넌트 종류는 시안대로 맞춥니다. 그래서 현재 화면의 모양이 일부 바뀔 수 있습니다.

## 7. 다른 세션에 맡겨 요청할 때

다른 에이전트나 세션이 사용자를 대신해 요청을 쓰고 진행 중 질문에 답하도록 맡길 수 있습니다.
이때도 결정은 사용자가 합니다.

- 요청에는 기준 시안과 구현할 화면·상태의 이름, 사용자가 이미 정한 결과만 담습니다. 각 결정에는
  사용자가 말한 원문과 시각을 함께 적습니다. 사용자가 정하지 않은 것은 비워 둡니다.
- 시안을 조사해 내용을 옮겨 적거나 요약하지 않습니다. 플러그인이 받은 시안이 기준입니다. 조사로 찾은
  코드 사실이나 위험은 위치와 함께 사실로 적고, 어떻게 할지는 정하지 않습니다.
- 대신 답하는 쪽은 플러그인이 제시한 결과를 확인해 진행을 승인하고, 사용자가 정한 결정을 전달할 수
  있습니다. 시안과 다르게 만드는 결정, 선택지가 갈리는 설계 결정, 화면을 둘 영역처럼 사용자가 정하지
  않은 선택은 대신 승인하지 않습니다. 시안에 없는 상태나 결과가 필요하면 사용자에게 올려 시안을
  보강하거나 결정을 받습니다.
- 4장의 “요청에 적지 않을 것”은 맡긴 요청에도 그대로 적용됩니다. 긴 요청 문서를 쓰더라도 파일 경로·
  구조·선례·시안 전사·사용자가 정하지 않은 차이를 넣지 않습니다.
- 작업이 끝나면 맡은 쪽은 실제 화면이 기준 시안과 같게 그려졌는지 최종 확인해 사용자에게 알립니다.

## 8. 완료 보고 읽기

완료 보고에는 구현한 화면과 동작, 확인한 상태·폭, 실행한 검증, 남은 차이와 미확인 부분이 담깁니다.
자동 검사·측정의 결과와 실제 화면에서 확인한 범위는 구분해서 설명합니다.
UI 동작이 포함됐다면 반복 조작·키보드·화면 일부 교체·실패 상황 중 무엇을 실제로 확인했는지도
보고에서 확인할 수 있습니다.

자동 검사 통과만으로 전체 화면과 움직임의 시각적 일치가 보장되지는 않습니다.
시안 충실 재현 완료는 요구한 화면·단계·상태·폭의 증거 검사와 독립 시각 검토를 모두 통과해야 합니다.
미검증 수락은 미확인 상태를 그대로 남기는 결정이며 검증 완료를 뜻하지 않습니다.
실제 API 이미지·영상이 필요한 경우 지정 환경의 응답과 브라우저 로드·재생을 확인하며, 접근 실패를 샘플로 대체하지 않습니다.
최종 시각적 수용은 보고된 확인 범위와 남은 차이, 실제 화면을 함께 보고 판단합니다.
원하는 화면 결과와 다른 부분은 그 차이를 중심으로 피드백하면 됩니다.
