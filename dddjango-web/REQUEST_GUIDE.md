# dddjango-web 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md` 사본이 해당 runtime에 대한 권위 있는 가이드입니다.
manifest의 homepage는 최신 온라인 문서(latest-online)를 찾는 발견 경로이며, 설치 버전의 동작 기준은
이 사본을 우선합니다. 이 가이드는 Claude Code와 Codex 설치본에서 독립적으로 읽을 수 있습니다.

## 1. 언제 쓰는가

`dddjango-web`은 기존 Django 프로젝트의 한 화면과 관련 파생 화면을 만들거나 수정합니다.
기준 시안이 있으면 배치·서체·색상·여백과 필요한 동작을 충실하게 재현하고, 시안이 없으면
원하는 결과와 기존 프로젝트의 스타일에 맞는 화면을 제안합니다. 의미에 맞는 HTML과 유지보수 가능한
화면 구조, 반응형·상태별 동작은 플러그인이 설계하고 구현합니다.

실제 데이터와 연동하는 화면은 기존 API를 사용합니다. 새 API나 업무 규칙·권한·데이터 처리 기능이
필요하면 플러그인이 부족한 백엔드 결과와 범위를 설명하고 별도 `dddjango` 작업을 안내합니다.
예시 데이터로 보여 줄 화면도 요청할 수 있습니다.

## 2. 바로 시작

한 화면과 원하는 변화만으로 시작할 수 있습니다. Claude Code에서는 `/dddjango-web`으로,
Codex에서는 `dddjango-web을 사용해 …`처럼 요청합니다. 같은 요청 내용을 두 환경에서 사용할 수 있습니다.

### 시안이 있을 때

Claude Code:

```text
/dddjango-web "첨부한 orders.png의 주문 목록 기본 화면을 구현해 주세요."
```

Codex:

```text
dddjango-web을 사용해 첨부한 orders.png의 주문 목록 기본 화면을 구현해 주세요.
```

스크린샷 한 장도 기준 시안으로 사용할 수 있습니다. 디자인 파일이나 웹페이지에 여러 화면이 있다면
그중 구현할 화면·프레임·페이지를 알려 주세요.

### 시안이 없을 때

```text
dddjango-web을 사용해 주문 상태별로 주문을 찾아볼 수 있는 목록 화면을 만들어 주세요.
시안은 없습니다.
```

플러그인이 기존 화면과 스타일을 살펴보고 필요한 화면 구성을 제안합니다.

### 시안에 접근할 수 없을 때

```text
dddjango-web을 사용해 회원가입 화면을 만들어 주세요.
공유받은 ‘회원가입 / 기본’ 시안이 있지만 현재 링크에 접근할 수 없습니다.
```

플러그인이 필요한 접근 방법이나 대체 자료, 원하는 화면 결과를 구체적으로 묻습니다.
API 위치를 모르거나 필요한 상태·폭을 아직 정하지 못했어도 시작할 수 있습니다.
플러그인이 프로젝트에서 확인할 수 있는 사실을 조사하고, 사용자가 결정할 부분을 질문합니다.

요청을 더 설명하고 싶다면 아래 다섯 묶음 중 이미 알고 있거나 정한 내용만 덧붙이면 됩니다.
모든 항목을 채울 필요는 없습니다.

| 묶음 | 알려 주면 좋은 내용 |
|---|---|
| 화면 | 만들거나 바꿀 화면과 원하는 변화, 유지할 부분과 이번 범위에서 제외할 부분 |
| 기준 시안과 정확한 대상 | 시안이 있다면 그 위치와 구현할 화면·프레임·페이지. 시안 없음이나 접근 불가도 그대로 전달 |
| 필수 상태·폭·동작 | 이미 정한 화면 상태, 필요한 화면 폭, 클릭·입력·스크롤 뒤 기대하는 결과 |
| 의도적인 차이 | 시안과 다르게 만들기로 정한 부분이 있다면 그 결과 |
| 데이터 연동 의도 | 실제 데이터로 동작할지, 예시 데이터로 보여 줄 화면인지 등 정해진 범위 |

## 3. 알려 주면 좋은 제품 정보

시안만으로 알기 어렵거나 이미 정해진 결과가 있을 때 다음처럼 보충할 수 있습니다.

- 정확한 디자인 대상: “디자인 파일의 ‘주문 목록 / 기본’ 화면을 기준으로 합니다.”
  여러 시안을 함께 쓴다면 “빈 목록 안내는 ‘주문 목록 / 검색 결과 없음’ 화면을 따릅니다”처럼
  이미 정한 기준을 알려 주세요.
- 상태별 결과: “검색 결과가 없으면 필터 초기화 버튼을 보여 주세요.” 또는
  “조회에 실패하면 기존 목록을 유지하고 재시도할 수 있어야 합니다.”
  긴 제목이나 이미지가 없는 주문에서 보존해야 할 표시도 정해져 있다면 함께 말할 수 있습니다.
- 반응형과 동작: “390px에서는 목록을 한 열로 보여 주고 필터를 접을 수 있어야 합니다.”
  “스크롤 중에도 주문 합계가 화면 하단에 보여야 합니다”처럼 화면에서 기대하는 변화를 설명합니다.
  꼭 필요한 움직임이 있다면 어떤 행동 뒤에 무엇이 어떻게 변하는지 알려 주세요.
- 의도적인 차이와 보존: “시안에 없는 배송 안내를 주문 금액 아래에 추가하고,
  기존 주문 상세 진입 동작은 유지해 주세요.”

이 예시는 제품 결과를 설명하는 단서입니다. 필요한 상태와 폭을 모두 미리 열거하거나,
아직 정하지 않은 결과를 추측해서 보충할 필요는 없습니다.

## 4. 플러그인이 하는 일

플러그인은 요청과 기존 프로젝트를 바탕으로 다음 작업을 맡습니다.

- 시안 조사: 자료의 접근 가능성과 사용할 수 있는 읽기·추출·비교 방법을 판단합니다.
  구현 기준으로 쓸 시안을 보존하고, 필요한 디자인 정보와 이미지·폰트를 조사해 활용합니다.
- 화면 상태와 검증 계획: 시안과 요구에서 필요한 상태·폭·동작을 정리하고,
  이를 재현하고 확인할 방법을 구성합니다.
- API 조사: 실제 데이터 연동에 사용할 API 계약을 찾아 요청·응답과 화면 요구를 대조합니다.
  필요한 계약이 없거나 자료가 서로 다르면 부족한 결과와 결정할 부분을 설명합니다.
- 화면 구조와 구현: 의미에 맞는 HTML과 유지보수 가능한 CSS를 작성하고,
  MVVM과 HTMX에 맞게 데이터·상태·화면의 구조를 설계합니다.
  시안의 시각적 의도와 반응형·상태별 동작을 이 구조 안에서 구현합니다.
- 검토와 확인: 작업에 맞는 agent·skill, 코드 검토와 검증 방법을 선택하고 실행 결과를 정리합니다.

조사만으로 정할 수 없는 제품 선택은 질문하고, 필요한 승인은 플러그인이 안내합니다.
실제 API와 연결할 부분은 사용할 수 있는 계약이 준비되어야 구현할 수 있습니다.
새로운 데이터 조회·변경이나 업무상 권한 같은 백엔드 기능이 필요하면 별도 작업 범위를 안내하며,
API를 어떤 도구로 만들었는지는 관계없습니다.

## 5. 있으면 함께 주기

알고 있는 위치나 이미 가진 자료가 있을 때만 함께 주면 조사를 빠르게 할 수 있습니다.

- 추가 시안과 동작 자료: 다른 상태·폭의 시안, 참고 화면, 클릭이나 스크롤 동작을 보여 주는 영상.
- 별도 이미지·폰트: 따로 전달해야 하는 원본 파일이나 위치, 이미 알고 있는 사용·접근 제약.
- 대표 데이터: 긴 제목, 빈 목록, 이미지가 없는 항목, 권한에 따라 달라지는 표시 등의 예.
- 관련 자료 위치: 기존 화면이나 코드, API 문서·OpenAPI, 이미 확보한 응답 예시.
- 외부 접근 사실: 시안이나 API에 로그인·조직 권한이 필요한지, 링크가 만료되었는지 등
  플러그인이 프로젝트 안에서 알 수 없는 조건.

자료는 알고 있는 위치만 전달해도 됩니다. 자료의 내용과 이번 화면에 필요한 정보는 플러그인이
조사하고, 추가 접근이나 별도 자료가 꼭 필요하면 구체적으로 묻습니다.

## 6. 수정하거나 이어서 요청하기

바꿀 화면 결과와 보존할 부분을 알려 주세요. 중단한 작업이라면 이전 작업을 이어간다는 사실을
덧붙이면 됩니다.

```text
dddjango-web을 사용해 이전 주문 목록 화면 작업을 이어 주세요.
빈 목록 안내를 ‘조건에 맞는 주문이 없습니다’로 바꾸고 필터 초기화 버튼을 추가해 주세요.
기본 목록과 오류 안내, 주문 상세로 이동하는 동작은 유지해 주세요.
```

새 시안·API의 위치나 이전 작업 위치를 알고 있다면 함께 줄 수 있습니다.
대화 밖에서 디자인이나 API가 바뀌었다면 알고 있는 변경 사실을 알려 주세요.
플러그인이 기존 기록과 현재 자료를 조사해 다음 작업을 정합니다.

## 7. 완료 보고 읽기

완료 보고에는 구현한 화면과 동작, 확인한 상태·폭, 실행한 검증, 남은 차이와 미확인 부분이 담깁니다.
자동 검사·측정의 결과와 실제 화면에서 확인한 범위는 구분해서 설명합니다.

자동 검사 통과만으로 전체 화면과 움직임의 시각적 일치가 보장되지는 않습니다.
최종 시각적 수용은 보고된 확인 범위와 남은 차이, 실제 화면을 함께 보고 판단합니다.
원하는 화면 결과와 다른 부분은 그 차이를 중심으로 피드백하면 됩니다.
