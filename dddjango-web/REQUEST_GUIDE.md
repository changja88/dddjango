# dddjango-web 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md` 사본이 해당 runtime에 대한 권위 있는 가이드입니다.
manifest의 homepage는 최신 온라인 문서(latest-online)를 찾는 발견 경로이며, 설치 버전의 동작 기준은
이 사본을 우선합니다. 이 가이드는 Claude Code와 Codex 설치본에서 독립적으로 읽을 수 있습니다.

## 1. 언제 쓰는가

`dddjango-web`은 기존 Django 프로젝트에서 한 화면과 관련 파생 화면의 **web 표현계층**을 만듭니다.
좋은 요청은 시안의 정확한 대상, 상태별 결과, 실제 API 계약, 사람이 비교할 완료 기준을 제공합니다.
시각 결과를 충실하게 재현하면서 유지보수 가능한 화면 코드는 플러그인이 설계하도록 맡깁니다.

필요한 endpoint가 없거나 인증·권한·업무 규칙·데이터 변경 같은 backend 기능이 필요하면
`dddjango` 작업이 먼저입니다. web 플러그인은 backend 기능을 구현하지 않으며, 실제 URL+JSON 계약을
소비합니다. API를 만든 도구가 반드시 `dddjango`일 필요는 없습니다.
서버 데이터와 연동하지 않을 화면은 범위를 합의해 정적 화면 한정(`static_only`)으로 요청할 수 있습니다.
시안 없음과 API 없음은 별개의 조건입니다.

완료를 말할 때는 다음 세 가지를 구분합니다.

| 결과 | 사용할 수 있는 조건 |
|---|---|
| 구현 완료 | 승인한 코드 슬라이스와 결정적 구조 검증이 끝남 |
| 자동 측정 완료 | 지정한 한 쌍의 화면 상태·viewport에 지원되는 측정축을 실행함. diff 유무는 별도 기재 |
| 시각 수용 완료 | 승인한 `state × viewport` 행렬의 전체 스크롤과 동작을 사람이 디자인 증거·승인 기준과 대조해 수용함 |

필수 행렬의 검수가 남으면 **충실도 미검증** 또는 **조건부 인계**로 남기고 미검수 행·이유·검수자를
적습니다. 구현 완료나 자동 결과 green만으로 시각 수용 완료라고 하지 않습니다.

## 2. 가장 빠른 시작

기존 Django 프로젝트에서 시작하고, 아래 문장 뒤에 최소 요청 또는 권장 요청서를 붙입니다.

Claude Code:

```text
/dddjango-web "회원의 주문 목록 화면을 만들어 주세요. 아래 시안·상태·API 계약을 기준으로 진행해 주세요." https://api.example.test/openapi.json
```

Codex:

```text
dddjango-web으로 기존 Django 프로젝트의 주문 목록 화면을 만들어 주세요.
아래 시안 정본·viewport·상태·실물 API 계약을 기준으로 진행해 주세요.
```

예시 주소는 실제 접근 가능한 계약 주소로 바꿉니다. 로컬 OpenAPI JSON 파일은 요청 본문에 경로를 적습니다.
최소 요청은 시작점입니다. G0의 확인 질문과 검사, G1·G2 승인은 계속 필요합니다.

## 3. 30초 최소 요청

아는 항목부터 한 문단에 채워 붙여 넣으세요. 모르는 칸을 추측하지 말고 `미확정`으로 남기면 됩니다.

```text
dddjango-web으로 [정확한 화면·신규/수정·범위]를 작업해 주세요. 디자인 정본은 [종류·URL/파일·exact screen/frame/route]이고 [접근 가능 여부]입니다. 증거는 [자동 동결·추출 대상 .dc.html/참조 HTML 또는 수동 screenshot/image-only]입니다. 검수 환경은 [OS·브라우저·viewport 폭×높이 또는 반응형 증거]이며 필수 상태·interaction은 [목록]입니다. asset/font 출처는 [위치 또는 미확정], API는 [OpenAPI 3.x JSON 위치 또는 static_only/미확정]입니다. 허용할 시안 차이는 [차이·이유 또는 없음]이고, 최종 전체 스크롤·상태·폭 비교는 [검수자·원본/구현 접근 가능 여부]가 수행합니다. 범위 밖은 [항목], 미확정은 [항목]입니다.
```

핵심 항목이 서로 충돌할 수 있으면 아래 라벨을 씁니다. 모든 줄에 붙일 필요는 없습니다.

| 라벨 | 적을 내용 |
|---|---|
| 사실 | 현재 화면·계약·데이터에서 확인한 내용 |
| 필수 제약 | 반드시 지켜야 할 시각·동작·호환 조건 |
| 선호 | 이유가 있으면 다른 선택을 제안해도 되는 방향 |
| 미확정 | 아직 확인하지 못했고 추측해서는 안 되는 내용 |

예: `사실: 모바일 시안은 없다. 필수 제약: 390px에서 가로 스크롤 없이 주문을 조회해야 한다.
선호: 필터는 접어서 표시한다. 미확정: 모바일 필터의 승인 디자인.`

## 4. 디자인 정본과 정확한 대상

파일이나 URL만 주면 어느 화면을 기준으로 삼을지 달라질 수 있습니다. **exact screen·frame·route**,
선택한 버전이나 날짜, 대상 viewport와 상태를 함께 지정하세요. 여러 증거가 있으면 우선순위를 적습니다.
예를 들어 “기본 레이아웃은 9월 4일 frame A, 오류 상태는 frame B, live 페이지는 hover 참고”처럼
각 증거가 담당하는 범위를 구분합니다. screenshot과 live 화면이 다르면 어느 쪽을 따를지 정합니다.

자동 동결·추출과 render audit(브라우저 렌더 실측 비교)는 서로 다른 능력입니다.

| 디자인 출처 | 동결·추출에 사용할 수 있는 것 | 원본 render audit |
|---|---|---|
| Claude Design `.dc.html` bundle | DesignSync가 가용하면 파일을 확보하고 token/meta/image·동봉 render PNG를 활용 | 불가. `.dc.html` 원본은 브라우저 audit 대상이 아님 |
| live reference page | 접근 가능한 참조 HTML/token/image | 실행자·브라우저 접근·실행 조건이 맞을 때 가능 |
| local/static reference HTML | 읽을 수 있는 HTML/token/image | 브라우저에서 원본을 실행하고 필요한 리소스를 불러올 수 있는지 별도 확인 |
| screenshot/image-only | 수동 시각 증거. 현재 자동 동결·token 추출·render audit의 일급 채널이 아님 | 이미지 자체는 불가 |
| no-design: 애초에 화면 시안 없음 | 사용할 디자인 토큰·요구 결과를 확인하고 자체 설계 | 대조할 원본이 없어 해당 없음 |

이미지만 제출했어도 따로 열 수 있는 실서비스 원본이 있다면 그 URL과 접근 조건을 알려 주세요.
원본의 브라우저 열람이 성립하면 그 원본에 대한 실측 채널을 확인합니다. 이미지 한 장 자체가
자동 채널로 바뀌는 것은 아닙니다.

**시안이 있지만 접근할 수 없는 경우를 no-design으로 바꾸지 마세요.** 로그인·권한·만료·로컬 실행 실패 등
원인을 적고, 접근 가능한 사본이나 수동 증거를 준비할지, 어느 범위까지 조건부 인계할지 G0에서 정합니다.
비밀번호·토큰·쿠키를 요청서에 붙이지 말고 접근 권한이 있는 검수자와 인증 준비 방식을 적습니다.

render audit는 사용자 실행이 우선입니다. 세션의 대행은 실행 채널, 명시 동의, 비인증 공개 페이지 확인,
목표·구현의 같은 실행자·창폭 등 런타임 조건이 맞아야 합니다. 인증 뒤 화면은 사용자 측 실측을 준비하고,
실측이 불가능하면 사유를 기록합니다. G0에서 제공받은 스니펫으로 측정한 JSON을 파일로 전달할 수 있습니다.

## 5. 권장 요청서

복잡한 화면에는 아래 양식을 사용하세요. 관련 없는 항목은 `해당 없음`, 모르는 항목은 `미확정`으로 둡니다.
DOM/CSS나 내부 view model 설계를 채우는 양식은 아닙니다.

```text
[화면]
화면명 / 신규·수정 / route / 진입·이탈·navigation / 범위 포함·제외

[디자인 정본]
종류·위치 / exact screen·frame·route / 버전·날짜 / 접근 가능 여부
자동·수동 증거 구분 / 증거 우선순위 / 의도적 차이와 이유

[검수 환경과 반응형]
OS / browser·version / viewport width×height / zoom / DPR
locale / theme / reduced-motion / 폭별 기대 동작·근거

[상태표]
상태명 / 진입 조건 / 표시 내용 / 가능한 행동 / 디자인·API 계약 근거

[상태 재현]
full URL(query/hash 포함) / role·인증 준비 방식(비밀정보 제외)
fixture·seed·record / loading·error 유발 방법 / font·data ready 조건

[interaction과 부분 갱신]
필수·선호 / trigger / 전→후 결과 / duration·easing·반복
scroll container / pinned anchor / 허용 근사 / 관찰하지 못한 항목

[asset·font·motion]
원본 위치·라이선스 / font family·weight / fallback 허용 여부
animation·transition·감속 / 긴 제목·빈 목록·null image 등 대표 데이터

[API 계약]
OpenAPI 3.x JSON URL·로컬 파일 / servers / endpoint·method / auth·role
request / success·empty·error / null·긴 문자열·권한별 응답

[기존 화면·작업]
기존 화면 경로·보존할 동작 / 기존 .dddjango-web 작업 폴더 / 마지막 승인
승인 후 디자인·API·코드 변경 / 완료 slice의 영향 후보

[완료 확인]
state × viewport × design evidence × 재현 절차 × 검수자 × 자동·육안 완료 행렬
필수 행 / 허용된 차이 / 미검수 행의 조건부 인계 기준
```

## 6. 상태·반응형·interaction을 재현 가능하게 쓰기

desktop 한 장으로 mobile, loading, empty, error, modal, hover, focus, sticky를 추측하게 하지 마세요.
필요한 상태와 폭을 먼저 정하고, 증거가 없는 행은 미확정으로 둡니다. desktop만 작업한다면 다른 폭은
이번 범위 밖이라고 명시합니다. “모바일도 자연스럽게” 대신 “390px에서 필터를 접고 목록을 한 열로,
표 가로 스크롤은 허용하지 않음”처럼 관찰할 결과를 적습니다.

상태표 예시:

| 상태 | 진입 조건·표시 내용 | 가능한 행동 | 근거 |
|---|---|---|---|
| 기본 | 회원 주문 12건·긴 제목 1건·이미지 null 1건 | 필터 적용·상세 진입 | frame A, 조회 API |
| empty | 해당 필터의 결과 0건·빈 목록 안내 | 필터 초기화 | frame B, 빈 응답 계약 |
| loading | 응답 대기 중·로딩 표시 | 중복 제출의 허용 여부 명시 | 모션 요구·승인 상태 |
| error | 조회 실패·합의한 오류 안내 | 재시도 | frame C, 오류 응답 계약 |

상태 재현 절차도 함께 적습니다. 예: “검수용 회원 role로 로그인 → seed `orders-long-title` 적용 →
`https://preview.example.test/orders/?status=paid#list` 진입 → 로딩 종료와 font 적용 확인 후 비교.”
loading과 error는 어느 개발 환경의 지연·오류 fixture로 유발할지 알려 주세요.
실제 서비스 데이터를 임의 변경해야 하는 절차는 검수 준비 방식으로 합의해야 합니다.

행렬은 상태표와 연결해 필요한 행만 작성합니다. 아래는 형식 예시이며 필요한 다른 상태·폭은 추가합니다.

| state | viewport | design evidence | 재현 절차 | 검수자 | 자동 측정 완료 | 육안 완료 |
|---|---|---|---|---|---|---|
| 기본 | 1440×900 | frame A·참조 HTML | 회원 role·seed A·font/data ready | 담당자 A | 미실행 | 미검수 |
| empty | 390×844 | frame B·수동 PNG | 회원 role·빈 fixture·동일 ready | 담당자 A | 원본 audit 불가 | 미검수 |
| error | 390×844 | frame C·수동 PNG | 오류 fixture·재시도 전후 | 담당자 B | 원본 audit 불가 | 미검수 |

자동 측정을 하지 못하는 행도 육안 검수 대상이 될 수 있습니다. 반대로 자동 측정이 끝난 행도
육안 확인은 별도로 남깁니다. 필수 행마다 전체 스크롤과 해당 동작의 비교 여부를 기록합니다.

## 7. asset·font·motion·고정 요소 준비

이미지 원본 경로·파일과 사용 권한, font family·weight·라이선스·접근 경로를 알려 주세요.
같은 문구라도 폰트 로딩 실패나 긴 제목으로 줄바꿈과 높이가 달라집니다. 대표 데이터는 평균적인 예 외에
긴 문자열, 빈 목록, null image, 권한별 차이를 포함하고 fallback 허용 여부를 정합니다.

이미지 수집이 모든 자산을 확보한다고 가정하지 마세요. CSS background, `srcset`, 동적으로 주입되는 asset은
누락될 수 있으므로 원본 파일과 화면 내 쓰임을 별도로 알려 주는 편이 좋습니다.

모션은 “부드럽게” 대신 trigger, 변화 전→후, duration·easing·반복 여부, reduced-motion에서의 결과를
적습니다. 실측하지 못한 수치는 `근사`로 표시하고 허용 범위를 합의합니다.
`동작 없음(확인)`과 `관찰하지 못함`은 구분하세요. 정적 시안이나 PNG는 실제 모션의 비교 상대가
될 수 없으므로, 요구·관찰에서 채택한 모션은 G1 명세의 처분 표를 기준으로 검수합니다.

고정 헤더·하단 바는 무엇에 고정되는지(pinned anchor), 어느 scroll container를 따라야 하는지,
스크롤 중간과 끝에서의 기대 결과를 적습니다. gesture·parallax처럼 custom JS가 필요한 동작은
지원 한계·범위 조정 대상입니다. 원하는 결과와 허용 근사를 먼저 제시하고 G1에서 처리 방식을 확인합니다.

## 8. 실제 API 계약과 backend handoff

OpenAPI 입력은 **비대화형 fetch가 가능한 OpenAPI 3.x JSON URL 또는 로컬 파일**입니다.
YAML·Swagger 2.0은 사전에 OpenAPI 3.x JSON으로 변환하세요. API 문서 웹페이지 주소와 JSON 원문 주소를
구별하고, 사용할 servers·method·exact path·auth·role을 적습니다.
문서와 실제 응답이 일치하는지는 자동 증명되지 않습니다. 알려진 차이나 확인한 응답 예를 함께 제공합니다.

화면에 필요한 endpoint 부재, OpenAPI·실제 응답·승인 상태 사이의 충돌, backend 업무 규칙 부족이 있으면
해당 부분을 `dddjango`로 먼저 요청하세요. 필요한 request와 success·empty·error 결과를 넘기고,
없는 API를 가정해 web 구현을 진행하지 않도록 범위를 정합니다.

project wiring은 Django가 화면을 찾고 제공하도록 route/template/static 설정이나 필요한 vendor 자산을
연결하는 최소 작업입니다. 런타임의 G0 승인 범위에서 처리합니다.
모델·서비스·API·업무상 인증/권한 규칙을 만드는 backend feature와는 다릅니다.

backend 완료 후에는 단순히 “이어서 해줘”보다 다음 정보를 전달하세요.

```text
dddjango-web 기존 작업을 재개해 주세요.
작업 폴더: .dddjango-web/<날짜>-<화면-slug>/ (기존 build-state.json 포함)
마지막 승인: [게이트·승인 내용]
이전 OpenAPI: [동결본 위치] / 신규 OpenAPI 3.x JSON: [URL·파일]
변경 method/path/shape: [요청·성공·오류·권한 응답의 차이]
완료 slice 영향 후보: [데이터 변환·상태·UI 등 아는 범위]
G0 refreeze(재동결) → 계약·설계 변경 시 G1′ 재승인 → contract 재절단 →
영향 data/UI slice 명시 재개봉 순서로 변경을 확인해 주세요.
```

같은 작업 폴더와 `build-state.json`을 알려 주세요. 단순 resume가 계약의 stale 상태를 자동 감지하거나
완료 slice를 자동으로 올바르게 재개봉한다고 기대하지 마세요. 이전·신규 계약 차이와 영향 범위를
명시하고, 무관한 완료 slice와 이번에 다시 열 slice를 확인합니다.

## 9. 플러그인에 맡길 결정

요청자는 화면에서 보이고 일어나는 결과, 보존할 계약, 필수 제약을 정합니다.
DOM·HTML tag·CSS selector·Grid/Flex, view/view_model/state의 클래스·필드,
component 분해·HTMX attribute·partial 구조, design token 이름·파일 배치는 플러그인이 설계합니다.
기술 선택이 실제 필수 제약이면 이유와 관찰 가능한 완료 기준을 적고, 단순 선호이면 `선호`로 둡니다.

**원본 HTML/CSS 직수입은 설계 선택지가 아니라 금지입니다.**
시안의 토큰·이미지를 활용하고 템플릿은 web 규율에 맞게 재구축합니다.
시안 마크업·클래스·인라인 스타일을 복사하라는 지시는 충실도와 코드 품질을 함께 지키는 요청으로 바꿉니다.

## 10. G0·G1·G2에서 확인할 것

| 게이트 | 사용자가 확인할 내용 |
|---|---|
| G0: 범위·증거 | 신규/수정/trivial 모드, 화면 배치, 기존 작업 폴더, 선행 위반·부채와 배선 검사 결과, 디자인·API 출처와 접근 가능성, 필수 상태·폭, 미확정 범위 |
| G1: 설계 | 시각·상태·실패 결과와 실제 계약, 디자인 증거 우선순위·허용 차이, 모션 처분·지원 한계, 재현·검수 기준. 내부 이름보다 요구가 정확히 반영됐는지 확인 |
| G2: 구현·검증·육안 | 승인 범위와 실제 화면, 결정적 검사·감수 결과, 실측 diff와 미실행 사유, 상태×viewport별 육안 결과·남은 조건 |

필요한 승인을 확인한 뒤 해당 단계가 진행됩니다. 구조 검사가 통과해도 설계 의미나 시각 결과가
맞는지 확인하는 책임은 남습니다. web 플러그인은 browser·functional·accessibility 자동 테스트를
새로 작성하지 않으므로, 재현 가능한 육안 절차와 실제 동작 확인이 필요합니다.

G2에서는 개발 서버를 열고 승인한 증거와 구현을 나란히 비교하세요.

- 승인한 폭·상태마다 **전체 스크롤**을 확인합니다. 첫 화면뿐 아니라 하단까지 요소 누락·잘림을 봅니다.
- typography·color·spacing·layout을 확인합니다. 서체·웨이트·줄바꿈·줄간·블록 간격이 애매하면
  개발자도구로 높이와 간격을 실측합니다.
- hover·focus·loading·swap을 실제로 발생시켜 전후 상태와 부분 갱신을 봅니다.
- 채택한 motion과 reduced-motion 결과를 확인하고, pinned 요소는 스크롤 **중간에도** 유지되는지 봅니다.
- 허용된 차이와 새로 발견한 차이를 구분하고, 필수 미검수 행은 충실도 미검증 또는 조건부 인계로 남깁니다.

## 11. 기존 화면 수정·trivial 수정·중단 후 재개

기존 화면은 바꿀 부분과 보존할 동작, 화면·파일 경로, 기존 작업 폴더와 마지막 승인을 알려 주세요.
설계 변경이 없고 재사용 폴더에 승인된 `design-spec.md`가 있는 순수 구현 수정이면 G1′을 생략할 수 있습니다.
승인 명세가 없는 기존 화면은 설계 변경이 없더라도 G1′이 필요합니다. 판단은 G0에서 확인합니다.

trivial 수정은 **신규 파일 0 + 비구조 diff**인 문구·토큰 값·이미지 교체 등으로 한정합니다.
모드와 근거를 한 번 승인하고 직접 편집·touched 백스톱·Django check 후 보고하는 경로이며,
별도 산출물 폴더·build-state나 G2를 만들지 않습니다.
view 시그니처·state 모양·route를 바꾸게 되면 수정 모드로 승격합니다.
모션 duration·토큰 값 교체도 trivial일 수 있지만 실측을 촉발하지 않으며, 기존 모션 처분 표와
어긋날 수 있다는 고지를 확인하고 실제 동작을 검수하세요.

중단 후 재개는 기존 `.dddjango-web/<날짜>-<화면-slug>/`와 `build-state.json`, 마지막 승인,
그 뒤 바뀐 코드·디자인·API를 함께 전달합니다. 완료 slice를 새 작업으로 다시 만들게 하지 마세요.
디자인이나 계약이 바뀌었다면 재동결 필요성을 알리고, API 변경은 앞 절의 handoff 흐름을 따릅니다.

## 13. 자동 검증이 증명하는 범위

render audit의 결과는 측정축에 한정됩니다. 아래에서 “미수집·수동”은 수집되지 않았거나,
일부 값이 JSON에 있어도 comparator가 비교·판정하지 않아 사람이 확인해야 하는 항목을 포함합니다.

| 종류 | 실제 의미와 예 |
|---|---|
| DIFF / exit 2 | 조인된 text의 font size·effective weight·line height·alignment·color, center-x 비율, 수직 순서, column width, pinned 인벤토리 소실 등 일부 축의 차이 |
| warn/info | viewport 폭 mismatch는 warn-only, 한쪽에만 있어 미조인된 text는 INFO. 미조인은 비차단이며 성공 exit를 막지 않을 수 있음. 측정 버전·커버리지 경고도 확인 필요 |
| 수집만 | font family, motion count·인벤토리 등. 수집이나 계수 요약이 동일성 판정은 아님 |
| 미수집·수동 | viewport 높이 비교, 정확한 y 간격·block size, image/background, border/radius/shadow/opacity, 실제 animation·motion, 정확한 pinned anchor·세부 위치 |

comparator의 **DIFF / exit 2는 G2의 1급 판단 자료이며 구조 백스톱처럼 자동 차단하는 결과가 아닙니다.**
의도한 차이는 근거와 함께 수용할 수 있고, 명세 위반은 반송 근거가 됩니다.
구조 백스톱의 blocker는 게이트를 막습니다. 같은 숫자 exit 2라도 두 도구의 의미는 다릅니다.
render comparator의 exit 1은 사용법·파싱·스키마 등의 오류로, 통과가 아닌 미실행으로 기록합니다.

한 번의 비교는 **현재 DOM의 단일 상태·단일 viewport pair**입니다.
수집 상한은 **text 200·pinned 20**이며 전체 화면의 모든 요소를 보장하지 않습니다.
pinned는 일부 스크롤 지점 샘플의 인벤토리로 비교하므로 정확한 고정 anchor나 실제 스크롤 동작은
육안 확인이 필요합니다. 목표·구현은 같은 실행자·브라우저·창폭에서 측정하고 차이가 있으면 기록합니다.

실측 JSON의 URL에서는 query/hash가 제거됩니다. 상태 재현을 위해 full URL을 별도로 남겨야 합니다.
lazy loading이나 스크롤에 따라 생기는 상태는 완전히 포착되지 않을 수 있습니다.
font family가 수집돼도 폰트 동일성은 비교하지 않고, 높이·정확한 간격·이미지·실제 모션도 자동으로
입증하지 않습니다. 별도 모션 처분 검사는 명세와 코드의 정적 대응을 점검하며 실행된 animation의
시각 동일성을 증명하지 않습니다.

완료 보고에서는 실행한 검사·실측 결과, diff·warn과 미실행 사유, 육안 검수 범위와 미검수 행을
구분해서 받으세요. 자동 결과 green을 시각 완료와 동일시하지 않고, 접근 권한이 있는 검수자가
필수 행렬을 대조한 뒤에만 시각 수용 완료라고 기록합니다.
