# dddjango-web 작업 요청 가이드

## 1. 새 화면

```text
/dddjango-web:dddjango-web "
1. 필요한 화면
   1) <어떤 화면에서 무엇을 할 수 있어야 하는지>
   2) …
2. 시안
   1) <Claude Design 화면 주소 또는 내려받은 시안 폴더 경로 · 화면 이름>
3. 특별 기술 요청 사항
   1) <사용자가 직접 정한 기술 조건>
" <OpenAPI 문서 위치>
```

- Codex에서는 첫머리를 `dddjango-web을 사용해`로, 리팩토링(3장)은 `$dddjango-web-refactor`로 바꿉니다.
- **1번**은 화면 하나(또는 화면에서 되어야 할 일 하나)를 한 항목으로 적습니다. 서로 관계없는 화면은 요청을 나눕니다.
  - 누르거나 입력한 뒤 꼭 보여야 할 결과는 정한 만큼 모두 적습니다. 적지 않은 결과는 플러그인이 시안과 API 문서를
    보고 정해 설계 승인 때 보여 주고, 스스로 정할 수 없는 것만 묻습니다.
  - 이번에 하지 않을 것은 `제외: …` 항목으로 적습니다.
- **2번** 시안은 꼭 적습니다. 시안의 문구 · 색 · 크기를 글로 옮겨 적지 않고 위치만 줍니다.
  - Claude Code: Claude Design 화면 주소(끝에 `?file=<화면 파일>.dc.html`이 붙은 주소), 또는 Claude Design에서
    내려받은 시안 폴더의 경로와 화면 이름.
  - Codex: Claude Design 주소를 열지 못합니다. 내려받은 시안 폴더의 경로와 화면 이름을 적습니다.
  - 내려받은 폴더는 이름과 구조를 바꾸지 않고 그대로 줍니다. 화면 이름은 화면 파일 이름 그대로(`OrderList`) 적습니다.
  - 저장된 시안과 다른 프로젝트나 폴더를 줄 때는 «디자인 출처 변경»이라고 적습니다.
- **3번**은 사용자가 직접 정한 기술 조건과, 플러그인이 스스로 알 수 없는 사실(환경 · 다른 작업)만 적습니다.
  없으면 비웁니다.
  - 예: 꼭 써야 하는 API · 자동 새로고침처럼 따로 원하는 동작 · 아래 탭 막대는 그대로 두고 가운데 화면만 바뀌게 ·
    어느 제품의 화면인지(제품이 여럿일 때) · API 문서에 없는 서버 동작 · 커밋 · push 규칙 · 같은 파일을 함께 고치는
    다른 작업 · 이 요청보다 먼저 끝나야 하는 작업.
  - 시안과 달라야 하는 곳은 사용자가 직접 정한 것만, 항목마다 `시안과 다름: …`으로 밝혀 적습니다.
  - 외부 JavaScript는 공식 플랫폼 SDK만 쓸 수 있습니다.
  - 다른 세션이 대신 쓰는 요청이면 첫 항목에 «대신 쓴 요청»이라고 밝히고, 사용자가 정한 미룸 · 승인에는 그 말이
    적힌 기록의 절대 경로 `파일:줄`과 시각을 붙입니다.
- 닫는 따옴표 뒤에는 이 프로젝트 API의 OpenAPI 3 JSON 문서 위치를 붙입니다 — 프로젝트 안 경로(`/api/openapi.json`) ·
  파일 경로 · `http(s)://` 주소 가운데 하나. 한 번 주면 저장되어 다음 요청부터는 빼도 됩니다. 파일 경로에 공백이
  있으면 큰따옴표로 감쌉니다.
- 백엔드(API · 모델)는 고치지 않습니다. 필요한 API가 없으면 `dddjango`로 따로 요청합니다.

**좋은 예**

```text
/dddjango-web:dddjango-web "
1. 필요한 화면
   1) 주문 목록 화면. 주문을 누르면 주문 상세 화면으로 간다.
   2) 주문 상세 화면. 배송 시작 전이면 취소 단추가 보인다.
2. 시안
   1) <Claude Design 프로젝트 주소>?file=OrderList.dc.html
   2) <Claude Design 프로젝트 주소>?file=OrderDetail.dc.html
3. 특별 기술 요청 사항
   1) 주문 취소는 이번에 화면만 만들고 실제 취소 API는 다음 요청에서 붙인다.
" /api/openapi.json
```

내려받은 시안을 쓸 때(Codex는 늘 이 꼴)는 2번을 이렇게 적습니다.

```text
2. 시안
   1) /Users/me/Downloads/쇼핑몰 웹 시안 · 화면: OrderList
   2) /Users/me/Downloads/쇼핑몰 웹 시안 · 화면: OrderDetail
```

**나쁜 예 — 실제 요청에서(이름은 바꿈)**

```text
## 4. 의도적인 차이(확정 처분 — 묻지 않는다 · 편차표에 적고 G2 에서 사용자 승인)
| 배지 셈 | 내림(시안 Math.round) | 발주자 → 사용자 알림 05:22 · 이의 0 · 할인율을 부풀리지 않는다 |
| 카드 B 제목 | 지금 web 글 유지 | 시안 글 = 상품 이름 틀 · 문안 창작 0 |
```

- 이렇게 적습니다: 2번에 시안 위치만 줍니다. 시안과 달라야 하는 곳은 사용자가 직접 정한 것만 3번에 적습니다.

## 2. 만든 화면 고치기 · 이어서 하기

```text
/dddjango-web:dddjango-web "<고칠 화면>을 고쳐 줘.
1. 바꿀 동작
   1) 지금: <지금 모습이나 결과> → 바뀐 뒤: <원하는 모습이나 결과>
2. 시안
   1) <바뀐 시안의 주소나 폴더 경로 · 화면 이름> · 디자인 다시 적용
3. 특별 기술 요청 사항
   1) …
"
```

- 시안이 바뀌었을 때만 2번에 «디자인 다시 적용»이라고 분명히 적습니다. 플러그인은 시안이 바뀐 것을 스스로
  알아채지 않습니다. 시안은 그대로인데 화면이 시안과 다를 때는 «시안 그대로»라고 적습니다.
- 꼭 지켜야 할 기존 동작은 1번에 `유지: …`, 이번에 하지 않을 것은 `제외: …` 항목으로 적습니다.
- 끝나지 않은 이전 작업이 있으면 플러그인이 이어서 할지 새로 할지 묻습니다. 세션이 끊겼으면 같은 명령으로
  다시 부르고 «이어서»를 고르면 멈춘 곳부터 이어 갑니다. «이어서»는 같은 요청을 다시 할 때만 고르고, 바꿀 동작이
  더해졌으면 «새로»를 고릅니다.

**좋은 예**

```text
/dddjango-web:dddjango-web "주문 목록 화면을 고쳐 줘.
1. 바꿀 동작
   1) 지금: 모든 주문이 한 줄로 이어 나온다 → 바뀐 뒤: 상태별 탭(전체 · 배송 중 · 완료)으로 걸러 볼 수 있다.
   2) 유지: 주문을 누르면 주문 상세 화면으로 간다.
2. 시안
   1) <Claude Design 프로젝트 주소>?file=OrderList.dc.html · 디자인 다시 적용
3. 특별 기술 요청 사항
"
```

**나쁜 예 — 실제 요청에서(이름은 바꿈)**

```text
- 현행 코드(수정 후보): web/member/login/view/login.html · web/static/css/login.css · web/static/css/components.css(이 블록만:
  .primary-button* 12~80행 · .outline-button* 164~186 · .icon-button* 189~220 · .input-field* 223~300 — 다른 블록 무변)
- 테스트: tests/web/member/login/test_login_view.py(7) · test_login_view_model.py(9) … 그 단언을 갱신·추가한다.
- 알고 있는 사실: … check_design_evidence.py --phase inputs exit 2 를 하드 블록으로 취급하지 않는다
```

- 이렇게 적습니다: 고칠 파일 · 줄 범위 · 테스트 · 검사를 넘기라는 말은 빼고, 사용자가 말한 범위(«배경은 건들지 말고,
  입력 컴포넌트·간격·버튼만»)를 결과와 `유지:`로 적습니다.

```text
/dddjango-web:dddjango-web "로그인 화면을 고쳐 줘.
1. 바꿀 동작
   1) 지금: 입력 칸 · 간격 · 단추가 시안과 다르다 → 바뀐 뒤: 시안과 같다.
   2) 유지: 배경.
2. 시안
   1) <Claude Design 프로젝트 주소>?file=로그인.dc.html · 시안 그대로
3. 특별 기술 요청 사항
"
```

## 3. 기존 코드 정리 — 리팩토링

화면 동작은 그대로 두고 기존 화면 코드만 표준에 맞추고 싶을 때 씁니다. 시안은 적지 않습니다.

```text
/dddjango-web:refactor <대상 단위> <지금 불편한 점(있으면)>
```

- 대상 단위는 하나씩 부릅니다 — 업무 묶음 하나(`web/application/order`) · 정적 파일 칸 하나(`web/static/images` —
  공식 SDK 사본 `web/static/vendor`는 대상이 아닙니다) · `web/root` · `web/common` · `web/design_system` · 옛 배치의
  최상위 폴더 하나.
- 페이지 주소 · 화면 결과 · 화면이 쓰는 API는 바꾸지 않습니다. 새 화면이나 새 동작이 필요하면 1장으로 따로 요청합니다.
- 다른 세션이 대신 부르느라 이 입구를 직접 부를 수 없으면, `/dddjango-web:dddjango-web`에 첫 줄을
  `리팩토링 모드(입구 /dddjango-web:refactor) · 대상: <대상 단위> <불편한 점>`으로 적어 보냅니다(Codex는 입구 이름이
  `$dddjango-web-refactor`).

**좋은 예**

```text
/dddjango-web:refactor web/application/order 화면마다 같은 판정이 반복돼서 고칠 때 여러 곳을 고쳐야 해.
```

## 4. 적지 않는 것

세 칸 밖의 내용은 적지 않습니다. 특히 아래는 플러그인의 설계를 묶어 버립니다.

- 진행 방식(전체 · 수정 · 작은 수정) · 단계 건너뛰기 · 단계를 미리 승인해 두기
- 층 · 폴더 · 파일 · 클래스의 이름과 위치, 화면 쪼개기, ViewModel · State 모양, 세션이나 공유 상태를 쓸지
- API를 묶는 방식 · 오류 처리 모양, 쓸 라이브러리와 버전(사용자가 정한 것은 3번에)
- 시안의 문구 · 색 · 크기를 글로 옮겨 적기, 시안 HTML을 그대로 옮기라는 말
- 테스트 명령 · 개수 · 통과 조건
- 백엔드 수정
- 사용자가 정하지 않은 기존 코드 정리 미룸, 살펴볼 범위를 좁히라는 말
- 조사한 코드 목록, 요청 문서의 판 이력, 진행 절차 설명

기존 코드 정리를 먼저 할지, 외부 JavaScript 도구를 쓸지, 기능을 어느 업무 묶음에 둘지 같은 결정은 플러그인이
조사 결과를 보여 주고 묻습니다. 이미 정했으면 3번에 적습니다.
