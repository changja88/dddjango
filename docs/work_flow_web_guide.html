간소화 DDD + MVVM 으로 화면을 짓는 웹 빌더의 협력 구조

Coordinator 가 진행을 맡고, 에이전트 7개가 명세 · 리뷰 · 코드 · 감수를 나눠 소유합니다. 새 화면은 범위(G0) → 설계(G1) → 구현(G2) 세 단계마다 사용자 승인을 받고 넘어갑니다. 2.1.0 에서는 기존 코드 정리(빚) · 외부 JS 승인 절차 · 리팩토링 입구가 새 구조에 맞춰 돌아왔습니다.

2.1.0dddjango-web 2.1.0 의 Coordinator · 에이전트 7 · 스킬 12 · REQUEST_GUIDE.md 를 기준으로 그렸습니다. 1.x 의 구조(화면 영역 · client · 에이전트 4 · 스킬 5)는 2.0.0 에서 dddart 판 구조로 바뀌었습니다.

작업은 이렇게 전달됩니다

선은 산출물이 전달되는 순서입니다. 호출 · 입력 전달 · 반송은 모두 Coordinator 가 중계하고, G0 · G1 · G2 는 사용자가 승인합니다. 위 줄이 범위와 설계, 아래 줄이 구현과 마무리입니다.

요청에서 끝까지 — 사용자가 보는 순서

요청에는 세 가지만 주면 됩니다. 나머지는 플러그인이 프로젝트를 조사하고, 사람이 정해야 하는 것만 묻습니다(근거: dddjango-web/REQUEST_GUIDE.md).

00 · 요청

세 가지를 준다

① 만들 기능(결과로) ② OpenAPI 문서 위치 — 이 프로젝트 안 경로(/api/openapi.json, 추천) · 파일 경로 · 웹 주소 ③ 디자인 — Claude Design 화면 주소 또는 내려받은 시안 폴더(없으면 이미지 · 자체 설계).

01 · G0 범위

범위와 출발 점검

정리한 범위 · 진행 방식과 근거 · Django 연결 점검 결과 · API 와 디자인 출처를 봅니다. 시안이면 «이 화면이 맞나요?»를 묻고, 손댈 파일 쪽 기존 위반(빚)이 있으면 정리할지 묻습니다.

02 · G1 설계

설계 승인

설계 문서 경로와 요지, 기본으로 빼 둔 항목, 설계가 혼자 못 정한 선택지, 가정한 API 목록을 확인합니다. 외부 JS(공식 SDK)가 필요하면 따로 한 문항으로 묻습니다. 승인한 설계가 코드의 유일한 근거가 됩니다.

03 · G2 구현

직접 띄워 확인

화면 동작 목록(위험 항목 별표) · 시안(또는 토큰)과의 비교 · 빚 한 줄을 봅니다. python manage.py runserver 로 직접 띄워 브라우저에서 확인한 뒤 승인합니다. API 를 가정했으면 첫 줄기 직후 한 번 더 묻습니다.

04 · 끝

검증 보고 · 한 묶음

실제로 돌린 검증만 보고합니다. 깨끗한 상태에서 시작했으면 작업 중 커밋을 스테이징된 미커밋 한 묶음으로 모아 둡니다 — git diff --staged 로 보고 직접 커밋합니다.

요청에 적지 않을 것: 진행 방식 · 폴더 · 파일 · 클래스 이름 · 화면 쪼개기 · 라이브러리 · 테스트 명령 · 단계 미리 승인 · 빚 정리 미루기 — 플러그인 단계가 정하고 게이트에서 확인받습니다. 한 번 준 API 위치와 시안 출처는 .dddjango-web/config.json 에 남아 다음 요청에서 다시 묻지 않습니다.

역할마다 입력과 산출물의 주인이 있습니다

Coordinator — 진행의 주인
요청을 받아 진행 방식을 가르고, Django 연결 설정을 점검해 승인받은 줄만 넣고, OpenAPI 문서와 시안을 동결합니다(시안 토큰 · 이미지 · 계약은 스크립트로 기계 절단 — 사람이 손으로 베끼지 않습니다). 빚 스캔 · 게이트 · 에이전트 호출 · 슬라이스 도출 · 백스톱 · 전수 테스트 · 반송 · 최종 보고 · 미커밋 합치기를 맡습니다. 직접 쓰는 것은 스코프 메모 · 동결 스냅샷 · 연결 설정 · build-state.json · 빚 기록 · 공식 SDK 설치(격리 커밋)뿐이고, 명세는 설계자에게, 코드는 구현자에게 맡깁니다.

AGENT 01 · PHASE 1

화면 설계자

design-architect-web

입력: 승인된 스코프 메모 · 동결 OpenAPI · 시안(design-ref) · 디자인 토큰 · 이미지 매니페스트 · (있으면) BC 배치 · area 판정 · 빚 정리 목록.

산출: 통합 설계 명세 design-spec.md 하나 — 도메인 · 화면 · 상태 · 데이터 네 관점, 외부 관찰 가능 행위 목록, 판정 소유 라벨, 계약 위험 표기, 파일 목록 · 구조 결정, (빚 정리가 있으면) ## 슬라이스 0 절, (필요하면) SDK 사용 표. 리뷰 노트를 반영 · 중재하는 유일한 명세 작성자이고 코드는 쓰지 않습니다.

AGENT 02~05 · PHASE 1

설계 리뷰어 넷

design-review-{ddd,ui,state,data}-web

  • ddd — 애그리거트 경계 · 판정 소유 · BC 배치 · 교차 BC 채널
  • ui — 화면 분해 · design_system 재사용 · 내비게이션 · view 수동성 · 시안 대조
  • state — SharedState 채택 · 갱신 채널 · 수명 · 일회성 이벤트 · State 계약
  • data — 서버 계약 대조 · Either 계약 · DataSource 분해 · 공식 SDK

산출: 축별 리뷰 노트. 서로의 노트를 보지 않고(편향 방지), 관심사가 없으면 «해당 없음 + 근거 한 줄»을 반드시 냅니다. 명세 · 코드는 고치지 않습니다.

AGENT 06 · PHASE 2

화면 구현자

coder-web

입력: 승인 명세 · 이번 슬라이스 · server-contract.json(또는 가정 계약 절) · 시안 · 이미지 매니페스트 · check 베이스라인 · test_command · htmx 경로.

산출: 코드 + 행위 검증 테스트(web_test/). 아래층부터(domain → infra → application → presentation → 배선) 쌓고, 층마다 py_compile · manage.py check 를 실제로 돌려 베이스라인 대비 신규 0, 테스트가 생기면 test_command 전수 통과까지 확인합니다. 명세에 없는 구조 결정 · 층 밖 파일 수정 · 기존 판정 복제를 만나면 멈추고 보고합니다.

AGENT 07 · PHASE 2

규율 감수자

discipline-reviewer-web

입력: 코드 · 명세 · 슬라이스 계획 · 지금 끝난 슬라이스(=감사 범위 — «아직 안 만든 것»과 «누락»을 가른다).

산출: 감수 리포트(blocker → important → nit). 행위↔코드 대조 · 판정 소유(빈혈) · 에러 2채널 · view 수동성 · 클린코드 · 백스톱이 못 보는 구조 · 명명의 의미 변종 · 테스트 FORM · 슬라이스 0 대조 · 공식 SDK 소비를 봅니다. 코드는 고치지 않고, 반영은 구현자 몫입니다.

규율 감수자는 Phase 1 에서 명세 단순성만 보는 경량 점검으로도 불립니다 — 명세에 슬라이스 0 절이 있으면 생략할 수 없습니다. 리팩토링 입구에서는 리뷰어 넷과 규율 감수자가 «단위 점검(UNIT_AUDIT)» 모드로, 설계자가 «의미 항목 판정» 모드로 불립니다.

기존 코드 정리(빚) 2.1.0 — 면제가 아니라 아직 안 갚은 빚

백스톱 게이트는 이번 작업이 들인 위반만 잡습니다. 기존 코드의 위반은 G0 에서 따로 드러내고, 이번 요청이 손대는 파일과 그 파일을 부르는 곳의 것만 묻습니다. 범위 밖 빚은 기록에만 남고 다음 요청의 스캔이 다시 냅니다.

01 · G0 빚 스캔

찾고 묻는다

backstop.py --debt-scan 이 web/ 전체를 훑어 debt-g0.json 으로 얼립니다. 범위에 빚이 있으면 G0 보고 전에 «지금 정리하고 시작(권장) / 이번에는 미룸(사유와 결정 출처) / 리팩토링 입구로 따로(이 요청은 멈춤 — 여러 단위에 걸칠 때만)»을 묻습니다. 이번 결과를 해치는 위반은 미룰 수 없습니다.

02 · G1 명세

정리 계획을 명세에

설계자가 명세에 ## 슬라이스 0 절을 씁니다 — 옮길 파일(경로:) · 바꿀 이름(이름:) · 함께 고칠 참조. 동작 그대로 정리할 수 없는 항목이 드러나면 빼고 멈춰 묻습니다. 규율 감수자의 경량 점검이 필수입니다.

03 · 슬라이스 0

기능보다 먼저

구현자가 기능 슬라이스 앞에서 동작 그대로 정리합니다. 끝 green 다섯 — ① check 신규 0 ② 정리하기로 한 빚 잔존 0 ③ 옮긴 경로의 옛 참조 0 ④ web/ 밖 테스트 변경은 경로 · 이름 치환뿐 ⑤ 정리 앞뒤 기존 테스트의 새 실패 0.

04 · G2 빚 잔존

남았는지 다시 센다

backstop.py --debt-residual 이 같은 방식으로 다시 스캔해 «지금 정리»로 고른 빚이 사라졌는지 셉니다. 남았으면 G2 를 내지 않고 슬라이스 0 을 다시 엽니다. G2 보고에 빚 한 줄(잔존 · 미룬 수 · G0 에 없던 키)이 붙습니다.

«미룸»은 사용자 본인의 답이나 사용자 원문(파일:행 · 시각)이 있어야 받습니다. 발주 · 다른 세션의 판단 · 일정 발화 · 일반 방침은 출처가 아닙니다. 표준 트리 밖 옛 배치 파일(1.x 의 <screen_area>/·client/·base/ 류)은 파일마다 ST0 빚으로 나오고, 정리하면 새 트리의 자리 · 이름으로 옮겨집니다.

외부 JS 승인 2.1.0 — 플랫폼 공식 SDK 만, 따로 묻고 등재한다

web 이 들이는 외부 JavaScript 는 플랫폼 운영자가 자기 서비스 API 를 부르라고 직접 배포하는 브라우저 SDK(카카오 SDK 류) 하나뿐입니다. 차트 · UI 프레임워크 · 유틸 같은 일반 라이브러리는 후보가 아니고, 그런 결과는 서버가 만드는 설계 · 평범한 링크 · native 로 냅니다.

PHASE 1

설계와 후보 사실

설계자가 명세에 SDK 사용 표(쓰는 기능 묶음 · 부르는 기능 JS · 로드 위치 · 공개 설정 이름 · 실패 동작 · 검증 행위)를 둡니다. Coordinator 는 sdk_vendor.py candidate 로 운영자 원본 · 문서를 직접 받아 인용 · 무결성 · 지문 · 라이선스 사실을 모으고, 데이터 리뷰어가 «공식 SDK» 항목을 봅니다.

G1

설계 승인과 따로 한 문항

새 채택 · 판 올림 · 범위 넓힘 · 기존 등록은 명세 승인과 따로 쉬운 말 한 문항으로 묻습니다 — «승인 / 기각 — 이 도구 없이 다시 설계». 출처는 본인 직접 답 또는 커밋된 사용자 원문뿐이라 대리할 수 없습니다. 기각하면 그 SDK 없이 다시 설계합니다.

PHASE 2 · G2

격리 커밋과 경계 확인

승인된 SDK 는 sdk_vendor.py install → verify 뒤 목록 · 사본만 담은 chore(web-sdk): 격리 커밋으로 들어옵니다(web/sdk_registry.json · web/static/vendor/<id>/). G2 전에는 운영자 호스트를 막은 브라우저에서 호출 경계를 기록 대조합니다 — 실제 발송은 0, 실제 왕복은 등록 도메인에서 사용자가 확인합니다.

공개 키는 settings 값만 출처입니다(키 값은 요청에 적지 않습니다). 승인한 도구는 같은 기능 묶음이면 다음 요청에서 다시 묻지 않습니다. 등재 목록 · 사본은 백스톱 WV 13종이 게이트와 무관하게 늘 검사합니다.

리팩토링 입구 2.1.0 — 단위 하나를 동작 그대로 정리

/dddjango-web:refactor <단위> [불편한 점] — 단위는 업무 묶음 하나(web/application/order) · 정적 칸 하나(web/static/images) · web/root · web/common · web/design_system · 옛 배치 최상위 폴더 하나 가운데 하나입니다(Codex 는 $dddjango-web-refactor). 페이지 주소 · 화면 결과 · 화면이 쓰는 API 는 그대로 두고, 기존 테스트를 정리 앞뒤로 돌려 새로 깨진 것이 없는지 봅니다.

대상 단위를 정확히 하나 읽고, refactor-<단위> 폴더를 정합니다. 새 동작을 요구하면 기능 요청으로 안내하고 멈춥니다.

검사기 빚

R2 · R2′

의미 점검

도구가 범위 · 조각 · 파견 표(plan.md)를 만들고, 조각마다 리뷰어 다섯(4축 + 규율)이 단위 점검 모드로 봅니다. 인용이 맞는지 도구가 다시 확인합니다.

R3

판정

설계자가 항목마다 채택 · 병합 · 제외 · 오탐 · 사용자 판단 · 별도 요청으로 판정하고, 도구가 근거를 대조해 확정 표(verdict-final.md)를 씁니다.

G0 → G2

슬라이스 0 만

G0 에서 항목마다 정리할지 묻고(사용자 판단 항목은 대리 답 불가), 슬라이스 0 명세 → G1 → 슬라이스 0 구현 → G2(남은 항목 수 · 영향 화면 전후 대조) → 마무리.

API 계약 · 다른 단위 본문 · web/ 밖 비테스트 파일을 바꿔야 하는 항목은 «별도 요청»으로 빠집니다(API 는 /dddjango). Django 연결 설정 미비는 보고만 하고 적용하지 않습니다 — 설정 변경은 동작 변경이기 때문입니다.
