1

본질과 의미 스펙트럼

핵심

역량 질문 — 내 프로젝트에 필요한 것이 스펙트럼의 어느 단계인지, 그 위 단계로 안 가는 이유를 말할 수 있는가? 나아가: 각 단계에서 기계가 새로 할 수 있게 되는 일을 한 줄씩 말하고, 실제 고장 하나를 «단계 부재의 증상»으로 진단할 수 있는가?

1.1 정의 해부 — 세 단어가 각각 일한다

Gruber(1993)의 고전 정의 «개념화의 명시적 명세(explicit specification of a conceptualization)»는 수사가 아니라 세 단어 각각이 독립된 요건이다.

개념화 (conceptualization)
세계를 어떤 개념·관계로 볼 것인가에 대한 추상 모델. 형식화 이전에 이미 팀의 머릿속과 관행에 존재한다. 예: dddjango의 «판정에는 소유자가 있고, 소유가 구조를 정한다»는 세계관은 그 자체로 개념화다.
명시적 (explicit)
암묵을 밖으로 꺼낸다. 산문 문서화도 명시화지만 — 산문은 사람에게만 명시적이다. 16,069행의 references 본문이 정확히 이 상태: 명시됐으나 기계는 못 읽는다.
명세 (specification)
기계가 소비할 수 있는 형태로, 그리고 공유된 합의로. 한 사람의 정리 노트가 아니라 모든 소비자(사람·에이전트·검사기)가 같은 뜻으로 읽는 계약이어야 한다.

따라서 온톨로지의 본체는 OWL 같은 표기법이 아니라 «합의를 기계가 읽는 형태로 옮기는 일»이다. 표기법은 그 일의 규격 부품일 뿐이고, 부품은 바꿔 낄 수 있다.

1.2 스펙트럼 6단계 — 얻는 능력과 남는 한계

각 단계는 아래 단계를 포함한다. 단계의 정체는 «기계가 새로 할 수 있게 되는 것»과 «여전히 못 하는 것»의 쌍으로 기억하는 것이 실전적이다 — 못 하는 것이 곧 다음 단계로 올라갈 이유이고, 그 능력이 필요 없다면 멈출 이유다.

러닝 예제누구나 아는 규칙 하나로 6단계를 오른다 — «출장비가 10만 원을 넘으면 영수증을 첨부한다. 단, 법인카드 사용분은 생략 가능»(사내 규정집 §3). 고장 상황: 영수증 없는 정산이 조용히 통과됐는데 아무도 몰랐다. 카드마다 «이 단계였다면 그 위반을 잡았을까?»를 판정한다 — 이 감각이 1.4 «고장 질문»의 실체다. 각 카드 마지막 «대응» 행이 같은 구조의 dddjango 실제 사건(감사가 조용히 생략됐던 일)으로 잇는다. 자리바꿈은 이렇다: 규정집 §3 = 규칙 코퍼스 · 정산 시스템 = 백스톱 · 정산 건 = 파이프라인 산출물(명세·판정·transcript) — 예제의 온톨로지는 회사 업무에 씌워져 있지만, dddjango에선 파이프라인 운영 자체에 씌운다(4.2 «어느 층» 참조).

④ 시소러스 thesaurus

추가계층 밖 연관 관계 — related·broader/narrower·동의어 연결 (SKOS가 딱 이 수준).
가능참조망 추적 — «이 규정의 재진술 전부», «이 조항을 인용하는 문서 전부».
불가관계에 의미 제약이 없다 — 연결이 «있다»는 보여도, «있어야 할 연결이 없다»(소유자 부재 같은 위반)는 정의조차 못 한다.
# 관계망 — 규정 하나가 사는 여러 문서를 잇는다
R-출장비-영수증 ─ 정본 ──→ 규정집 §3
               ─ 재진술 → 온보딩 문서 · 정산 안내 메일
               ─ 관련 ──→ 법인카드 규정
질의: «재진술 전부» → 규정집만 고치고 온보딩 문서는
      안 고친 «표류» 검출
검출△ 문서 표류(재진술 불일치·깨진 인용)는 잡지만, 실행 시 위반은 여전히 못 본다.
대응anchor lint — 스킬 §인용 255건의 실재를 기계 검증하는 도구 — 가 이 층의 실물이다.

⑤ 온톨로지 ontology

목적합의를 기계가 집행하는 계약으로 만든다 — «반드시 이래야 한다»가 문서의 당부가 아니라 위반이 반려되는 제약이 된다.
추가관계의 의미론(도메인·치역·카디널리티) + 공리·제약(반드시 참이어야 하는 것).
가능제약 위반 검증(«모든 규정은 검증 수단 필수»), 일관성 검사, 검증 수단을 규칙 레코드에서 파생·대조. 중량이면 추론까지.
불가선언 층까지다 — 규정이 잘 정의됐는지는 보장하나, 실제 정산이 규정대로였는지는 실행 데이터 없이 모른다.
# 규칙 레코드 + 제약 — 산문 규정의 뼈대만 형식화
# R- 는 규칙(Rule) ID 관례 — 유형이 한눈에 보이고, 개념(출장비)과
# 규칙(R-…)의 이름 충돌을 막는다. DR-68의 DR, Wikidata의 Q/P와 같은 습관.
rule: R-출장비-영수증
trigger:    출장비 > 100,000원
obligation: 영수증 첨부
exception:  법인카드 사용분
owner:      재무팀                # 제약: 정확히 1
verify:     정산 시스템 필수 필드   # 제약: 없으면 반려
검출✓(구조로) «verify 없는 규정»이 기계에 반려되므로, 위반을 드러낼 «필수 필드»가 구조적으로 강제된다.
대응파이프라인 게이트 배너에 «슬라이스 감사» 상시 필드를 만든 처방이 정확히 이것 — 손으로 만든 처방이 제약 1줄이 된다.

⑥ 지식 그래프 knowledge graph

목적지식을 질의 가능한 자산으로 만든다 — 물음이 생길 때마다 문서를 뒤지는 대신, 데이터에 묻고 전수 답을 받는다.
추가스키마(온톨로지) + 인스턴스 전량 — 규정만이 아니라 정산 건 하나하나까지 올린, 질의 가능한 실물.
가능임의 전수 질의 — 준수 감사의 자동화. 사람이 서류를 뒤지던 일이 질의 한 줄이 된다.
불가그래프에 올리지 않은 것은 못 본다 — 구축 품질이 병목이고(주제 7의 GraphRAG 한계), 산문의 뉘앙스·판단 기준은 끝까지 그래프 밖에 남는다. 스펙트럼의 끝은 전지(全知)가 아니다.
# 질의 — 감사가 질의 한 줄이 된다
? 이번 달 R-출장비-영수증 위반
→ 3/12 김OO 정산: 120,000원 · 영수증 없음
  · 법인카드 아님  ⇒ 위반
? verify 없는 규정 전부
→ 0건이어야 정상
검출✓(실행까지) 정산 인스턴스가 올라가 있으면 영수증 누락이 질의 결과로 직접 나온다.
대응웨이브 1에서 수 시간 걸린 수동 스킬-사용 감사가 질의 한 줄이 되는 것 — Phase 0 센서스의 종착 형태다.

1.3 경량 vs 중량 — ⑤ 안의 갈림길

⑤에 도달해도 갈림길이 하나 더 있다. 경량(lightweight): 계층·관계·제약 검증까지 — «데이터가 정한 모양대로인가»를 폐쇄 세계(CWA)로 검사한다. 중량(heavyweight): 기술논리 공리와 자동 추론까지 — 명시 안 된 사실을 개방 세계(OWA)에서 도출한다.

중량이 정당화되려면 두 조건이 모두 필요하다: ① 명시 안 된 사실의 도출이 실제로 필요하고(자동 분류·상속 추론) ② 도메인이 논리로 잘 닫힌다. 실무 도입의 대다수는 경량에서 멈추는 것이 옳으며, 온톨로지 실패담의 상당수는 경량으로 충분한 곳에 중량을 들인 경우다.

1.4 내 위치 고르기 — 적용 수준의 결정 절차

단계는 목표가 아니라 비용-편익의 균형점이다. 위로 갈수록 검증력·질의력이 늘고, 작성·유지·합의 비용도 는다. 위치는 네 가지 질문으로 판정한다:

  1. 소비자 질문 — 그 형식을 읽을 기계(검사기·생성기·질의)가 있는가, 만들 계획인가? 없으면 그 단계는 죽은 문서다(주제 8의 제1 교훈). 소비자가 끌 수 있는 단계까지만 올린다.
  2. 고장 질문 — 지금 실제로 겪는 고장이 어느 단계의 부재 증상인가? 표기 흔들림 → ②, 분류·집계 불능 → ③, 관계 추적 불능 → ④, 제약 위반 미검출 → ⑤, 전수 질의 불능 → ⑥. 고장이 가리키는 단계보다 위로 가는 것은 투기다.
  3. 변경 질문 — 개정 빈도 × 참조 수. 자주 바뀌고 참조가 많을수록 상위 단계의 이득이 커진다 — 참조 깨짐·표류가 바로 상위 단계가 갚아주는 빚이기 때문이다.
  4. 합의 질문 — 어휘와 의미에 대한 합의가 먼저 있는가? 형식은 합의를 기록할 뿐 대신 만들어주지 않는다. 합의 없는 형식화가 죽은 온톨로지의 최다 사인이다.

오해 교정 — «온톨로지 도입 = OWL·트리플 스토어 도입»이 아니다. 본질은 단계 선택이고, YAML 레지스트리 + 자체 lint로 구현해도 ⑤단계의 온톨로지적 실천이다.

부위별 처방 — 한 시스템이 한 단계에 있을 필요도 없다. dddjango를 예로 들면: 참조(앵커) 축은 anchor lint로 이미 ⑤급 검증이 있고, 용어 축은 ② 미달(목록 미확정), 분류 축은 ③ 부재다. 축마다 고장이 가리키는 단계로 각각 올리는 것이 정상 처방이며, 전면 격상은 과형식화의 지름길이다.

이 절이 곧 «적용 수준» 결정의 알고리즘이다. 나중의 Phase 0 센서스는 네 질문 중 «고장 질문»을 정량화하는 도구 — 축별(용어·참조·분류·제약) 현재 단계와 고장 밀도를 재서, 축마다 목표 단계를 따로 정하게 된다.

핵심

역량 질문 — 규칙 하나를 클래스·관계·공리·인스턴스로 분해할 수 있고, 검증에 폐쇄 세계 가정이 왜 필요한지 설명할 수 있는가?

빌딩 블록
클래스(개념 유형) · 인스턴스(개별자) · 속성/관계(is-a 계층, part-of, 도메인 고유 관계) · 공리/제약(반드시 참이어야 하는 것) · 안정 식별자(IRI — 이름이 아니라 주소).
is-a와 part-of를 섞지 않기
초심자 오류 1위. 계층(상속)과 구성(부분)은 다른 관계이고 섞으면 추론이 오염된다.
세계관 가정
개방 세계 가정(OWA): 안 적힌 것은 «거짓»이 아니라 «모름» — OWL 추론의 기본. 폐쇄 세계 가정(CWA): 안 적힌 것은 위반 — 검증·lint가 원하는 것. 고유 이름 가정(UNA) 유무도 같은 축. 이 구분을 모르면 «OWL로 검증»이라는 잘못된 설계를 하게 된다.
역량 질문(competency questions)
«이 온톨로지가 답할 수 있어야 하는 질문 목록»으로 범위를 정하는 기법. 온톨로지의 요구사항 명세다.
결정적 백스톱 27종은 전부 CWA 검사기다. «검증은 CWA, 지식 표현은 OWA»라는 구분이 잡히면, 도입할 것이 OWL 추론기가 아니라 SHACL류 제약 검증임이 자명해진다.

표준 기술 스택

채택 판단용

역량 질문 — 각 부품이 «무엇을 주는 대가로 무엇을 요구하는지» 한 줄씩 말할 수 있는가? 특히: RDFS의 domain/range가 검증이 아닌 이유와 OWL 카디널리티로 «owner 필수»를 집행할 수 없는 이유를 설명할 수 있는가?

이 절의 위치 — 주제 1이 «어느 단계까지 형식화할까»를 정하는 지도라면, 이 절은 그 지도의 각 지점을 구현하는 표준 부품 카탈로그(W3C 표준 계열)다. 만드는 절차(방법론)는 주제 5의 몫이고, 표준 대신 자체 구현으로 같은 단계를 구현하는 길은 3.2가 다룬다. 단계↔부품 대응부터:

공통 기반RDF + IRI — 모든 부품이 딛는 데이터 모델(트리플)
① 용어집표준 부품 불요 — 산문 정의로 충분
② 통제 어휘SKOS (prefLabel·hiddenLabel)
③ 택소노미RDFS (subClassOf) · 가볍게는 SKOS (broader/narrower)

⑥ 지식 그래프RDF 인스턴스 + SPARQL (질의) + 트리플 스토어 (저장)

3.1 스택의 지도 — 부품별 목적과 함정

외울 필요 없다 — 각 부품의 목적과 함정만 잡으면 된다. 부품은 바꿔 낄 수 있다는 것(1.1)이 이 절의 전제다. 러닝 예제(R-출장비-영수증)가 각 부품에서 어떤 모습이 되는지 계속 따라간다.

RDF Resource Description Framework(자원 기술 프레임워크) · 모든 부품이 딛는 데이터 모델

목적모든 지식을 하나의 만능 원자(트리플)로 표현하는 데이터 모델. 아래 네 소절이 RDF의 전부다 — ⓐ 원자 ⓑ 주소 ⓒ 표기 ⓓ 작성 순서.
ⓐ 트리플 — 지식의 원자

«주어–서술어–목적어» 3칸으로 된 최소 문장 하나가 트리플이다. 어떤 지식이든 더 쪼갤 수 없는 사실 단위까지 부수면 전부 이 꼴이 되고, 트리플이 모이면 그래프가 된다 — 주어·목적어가 점, 서술어가 화살표. RDFS·OWL·SHACL·SPARQL 전부가 이 원자 위에서 동작한다.

예제 ⓐ — 자연어 문장 2개를 트리플로 분해
"출장비 규정의 소유자는 재무팀이다"
→ (R-출장비-영수증) ─ 소유자 ──→ (재무팀)

"출장비는 경비의 일종이다"
→ (출장비) ─ 일종(is-a) ──→ (경비)
ⓑ IRI와 접두어 — 각 칸에는 이름이 아니라 주소를 쓴다

주어·서술어 칸에는 전역 주소 IRI를 쓴다 — «안정 ID»의 표준형. 목적어 칸에는 IRI 또는 리터럴(문자열·숫자·날짜 같은 값)이 온다: 목적어가 IRI면 다른 점으로 가는 화살표(관계), 리터럴이면 그 점에 매달린 값(속성값)이다. 매번 전체 주소를 쓸 수 없으니 접두어(prefix)로 줄인다. ex:는 example의 준말(예제용 관례)이고 rdf:·rdfs:·skos:·sh:는 각자 W3C 네임스페이스의 접두어다. 실전에선 ex: 자리에 자기 프로젝트 네임스페이스가 들어가고, 빈 접두어(:출장비)나 JSON-LD의 @context로 노이즈를 줄인다 — 접두어가 진짜 필요해지는 순간은 외부 어휘와 섞일 때다(모듈 네임스페이스 원리).

예제 ⓑ — 접두어 선언과 축약의 관계
@prefix ex: <http://example.org/> .   # 선언은 파일 맨 위 한 번

ex:출장비    # = <http://example.org/출장비> 의 축약
ⓒ 모델과 표기의 분리 — Turtle은 철자법이다

그래프는 점·화살표라는 추상 데이터라서, 파일로 적으려면 표기법(직렬화)이 필요하다. 같은 그래프를 여러 문법으로 적을 수 있고 셋 다 기계가 읽는다 — 차이는 최적화 대상뿐이다: Turtle=사람 손, N-Triples=단순 도구(행 단위 처리·대용량 덤프), JSON-LD=JSON 생태계(schema.org가 이 모습). Turtle 문법은 셋이 전부다: 트리플은 주어 서술어 목적어 . / 같은 주어는 ;로 잇기 / a는 «~의 유형은»(rdf:type)의 준말. 층 판별법: «모든 사실은 3칸»·«칸에는 IRI»는 RDF의 규칙, «끝에 .»·«;로 잇기»는 Turtle의 규칙.

예제 ⓒ — 같은 트리플 하나를 세 문법으로 (읽는 순간 문법은 벗겨지고 같은 그래프만 남는다)
① Turtle     ex:R-출장비-영수증 ex:owner ex:재무팀 .

② N-Triples  <http://example.org/R-출장비-영수증>
             <http://example.org/owner> <http://example.org/재무팀> .

③ JSON-LD    { "@id": "ex:R-출장비-영수증",
               "ex:owner": {"@id": "ex:재무팀"} }
ⓓ 작성 순서 — 스키마 먼저, 데이터 다음

용어(스키마)를 먼저 선언하고 그 용어로 사실(데이터)을 적는 순서가 읽기 좋다. 단, DB와 달리 선언은 의무가 아니다 — 선언 없이 데이터부터 적어도 동작한다(schemaless). 이 유연함이 병합-공짜의 원천이자 위험이고, 그 관리가 RDFS(계층)·SHACL(검증)의 몫이다.

예제 ⓓ — 러닝 예제의 스키마 선언과 데이터 작성 (Turtle 표기)
# 1) 스키마: 용어 선언 (Class·Property 어휘는 다음 카드 RDFS의 것)
ex:규정    a rdfs:Class .    # «규정»이라는 유형이 있다
ex:trigger a rdf:Property .  # 규정이 가질 속성들
ex:owner   a rdf:Property .
ex:verify  a rdf:Property .

# 2) 데이터: 위 용어로 적은 사실
#    = 같은 주어의 트리플 4개를 ; 로 묶은 것(점 하나에 화살표 4개).
#    trigger의 목적어만 리터럴(값), 나머지는 IRI(관계).
ex:R-출장비-영수증 a ex:규정 ;
    ex:trigger "출장비 > 100,000원" ;
    ex:owner   ex:재무팀 ;
    ex:verify  ex:정산시스템-필수필드 .
예제 ⓓ′ — 위 데이터 트리플 4개를 N-Triples와 JSON-LD로 (같은 그래프)
# N-Triples — 축약이 전혀 없다: 접두어도, a 도 없이 전체 주소.
#   한 줄 = 완전한 트리플 하나. 도구엔 쉽고 사람에겐 고되다.
<http://example.org/R-출장비-영수증> <http://www.w3.org/1999/02/22-rdf-syntax-ns#type> <http://example.org/규정> .
<http://example.org/R-출장비-영수증> <http://example.org/trigger> "출장비 > 100,000원" .
<http://example.org/R-출장비-영수증> <http://example.org/owner> <http://example.org/재무팀> .
<http://example.org/R-출장비-영수증> <http://example.org/verify> <http://example.org/정산시스템-필수필드> .

# JSON-LD — 접두어는 @context 에 숨고, @type 이 a 의 자리.
#   목적어 구분이 그대로 보인다: 리터럴은 맨 문자열,
#   IRI(관계)는 {"@id": …} 로 감싼다.
{ "@context": { "ex": "http://example.org/" },
  "@id":   "ex:R-출장비-영수증",
  "@type": "ex:규정",
  "ex:trigger": "출장비 > 100,000원",
  "ex:owner":   { "@id": "ex:재무팀" },
  "ex:verify":  { "@id": "ex:정산시스템-필수필드" }
}
가능스키마 협상 없는 병합 — 서로 다른 출처의 트리플을 그냥 합쳐도 그래프가 된다(연합의 기반).
불가트리플 자체엔 의미도 제약도 없다 — «owner가 없으면 안 된다»를 말할 수단이 없다. 그 일은 위층(RDFS·SHACL)의 몫이다.

RDFS RDF Schema(RDF 스키마) · 스펙트럼 ③의 표준 부품

목적용어 자체에 관한 문장(스키마 트리플)을 추가해, 낱개 사실들을 계층으로 묶는다. 네 소절 — ⓐ 정체 ⓑ 핵심 어휘 ⓒ 롤업 ⓓ 함정. 이하 트리플 예제는 전부 Turtle 표기다 — RDFS는 문법이 아니라 어휘라서 어느 표기로든 적을 수 있다.
ⓐ 정체 — 새 문법이 아니라 «약속된 서술어» 묶음

RDFS는 별도 언어·별도 파일이 아니다. rdfs: 네임스페이스에 든 서술어들을 같은 트리플로, 같은 그래프에 적을 뿐이다. 차이는 문장의 주어다: 데이터 트리플은 사물이 주어("이 정산은 출장비다"), 스키마 트리플은 용어가 주어("출장비는 경비의 일종이다"). 주어가 한 층 올라간 것이 "트리플 위에 세운다"의 실체다.

예제 ⓐ — 스키마 트리플과 데이터 트리플의 주어 차이
ex:출장비 rdfs:subClassOf ex:경비 .   # 스키마: 주어가 «용어»(출장비 개념)
ex:정산-0312 a ex:출장비 .            # 데이터: 주어가 «사물»(3/12 정산 건)
ⓑ 핵심 어휘 — 여섯 개면 충분

rdfs:Class(유형 선언) · a=rdf:type(소속) · rdfs:subClassOf(유형의 계층) · rdfs:subPropertyOf(서술어의 계층) · rdfs:label(사람용 이름) · rdfs:comment(설명). 실무 RDFS는 대부분 이 여섯으로 끝난다.

예제 ⓑ — 러닝 예제의 어휘 계층 선언
ex:경비    a rdfs:Class .
ex:출장비  a rdfs:Class ;
    rdfs:subClassOf ex:경비 ;
    rdfs:label   "출장비"@ko ;
    rdfs:comment "업무 출장에 든 비용"@ko .
ⓒ 롤업 — 계층이 주는 능력

스키마 트리플이 있어야 기계가 사슬을 탈 수 있다: 정산-0312 → 출장비 → 경비. 이 사슬 덕에 «경비 전부» 질의가 개별 정산 건까지 잡는다(③ 택소노미 능력의 표준화). 스키마 트리플이 없으면 기계에게 출장비와 경비는 무관한 점 두 개일 뿐이다.

예제 ⓒ — 사슬 타기(롤업)의 동작 · «질의:» 이하는 설명용 의사 표기(실제 문법은 SPARQL 카드)
ex:출장비 rdfs:subClassOf ex:경비 .
ex:정산-0312 a ex:출장비 .

질의: «ex:경비 에 속하는 것 전부»
→ ex:정산-0312    # 경비라고 직접 선언한 적 없지만 사슬로 도달
ⓓ 함정 — domain/range는 검증이 아니라 추론이다

rdfs:domain/range는 "이 서술어의 주어/목적어는 이 유형이다"라는 선언인데, 잘못된 사용을 잡는 게 아니라 그 사용으로부터 새 사실을 추론해버린다. 검증을 기대하고 쓰면 정확히 반대로 동작한다 — 주제 2의 개방 세계 가정(OWA)이 표준에서 이렇게 나타난다.

예제 ⓓ — domain 선언이 오류 대신 추론을 낳는 사고 · «→» 이하는 추론 결과 설명
ex:trigger rdfs:domain ex:규정 .   # «trigger의 주어는 규정이다» 선언

ex:김OO ex:trigger "…" .           # 잘못된 사용(사람에게 trigger를 달았다)

→ 오류가 아니라 새 추론이 태어난다: ex:김OO a ex:규정 .
  # «김OO도 규정이구나» — 모양 검사를 원하면 SHACL로 가야 한다
가능롤업 질의의 표준화 — 계층을 아는 도구라면 어디서나 같은 의미로 동작한다.
불가검증은 못 한다 — domain/range조차 추론용이라, «owner 필수» 같은 모양 검사는 SHACL의 몫이다. RDFS의 관할은 유형·계층 선언까지다.

OWL Web Ontology Language(웹 온톨로지 언어) · 스펙트럼 ⑤ 중량의 표준형

목적RDFS와 같은 «기계적 확장»의 강화판 — 더 표현력 있는 논리 공리로 더 많은 암묵 지식을 결정적으로 도출한다(1.3의 중량 온톨로지). 네 소절 — ⓐ 정체 ⓑ 대표 공리 ⓒ 자동 분류 ⓓ 한계. 예제는 전부 Turtle 표기.
ⓐ 정체 — 방향은 RDFS와 같고, 표현력이 다르다

OWL도 RDFS처럼 «약속된 어휘» 묶음이다(owl: 네임스페이스). 동작 방향도 같다 — 잡는 게 아니라 사슬을 타고 기계적으로 확장한다. 다른 점은 말할 수 있는 것의 범위: RDFS가 "일종이다" 사슬만 안다면, OWL은 동치·역관계·개수 제한·조건 정의 같은 논리 공리를 안다. 이론 기반은 기술논리(Description Logic) — 추론이 반드시 끝나도록 결정 가능한 논리 조각만 골라 설계됐다. 이름의 Web은 실행 방식이 아니라 태생 표시다: W3C 시맨틱 웹 프로젝트 출신이라 IRI(웹 주소)·어휘의 웹 공개·연합 생태를 겨냥했다는 뜻이지, 런타임에 웹에서 데이터를 가져온다는 뜻이 아니다(owl:imports로 웹에 공개된 다른 온톨로지를 포함하는 부속 기능은 있다).

RDFS와의 차이 리트머스 — 문법이 아니라 «말할 수 있는 지식의 종류»가 다르다
"여비와 출장비는 같은 개념이다"        RDFS ✗ → owl:equivalentClass
"소유하다의 반대는 소유되다"           RDFS ✗ → owl:inverseOf
"규정이면서 사람일 수는 없다"          RDFS ✗ → owl:disjointWith
"owner는 정확히 1개다"                RDFS ✗ → owl:cardinality
"trigger가 있으면 발동형 규정이다"     RDFS ✗ → 조건 정의(자동 분류)

# 관계는 대체가 아니라 포함(RDFS ⊂ OWL) — 아래 ⓓ 첫 줄처럼
# rdfs: 와 owl: 어휘가 한 문장에 섞여 쓰인다. RDFS는 «계층»만,
# OWL은 그 위에 «논리» 전반을 얹는다.
# 정밀 단서: 완전한 상위집합은 이론판(OWL Full) 기준이고, 추론기가
# 실제 구현하는 OWL DL은 클래스/인스턴스 겸직(메타모델링)을 금지해
# 일부 합법 RDFS 그래프가 밖에 떨어진다 — 6번의 «클래스·인스턴스
# 혼동» 안티패턴을 표준이 강제로 막아주는 셈.
ⓑ 대표 공리 — 무엇을 말할 수 있게 되나

동치(equivalentClass·sameAs — 두 이름이 같은 것) · 역관계(inverseOf) · 서로소(disjointWith — 겹칠 수 없는 유형) · 개수 제한(cardinality) · 조건 정의(클래스를 조건식으로 정의). 아래 [ … ]는 이름 없는 보조 노드를 만드는 Turtle 문법이다.

예제 ⓑ — 동치·역관계·서로소 공리와 그 확장 효과
ex:여비 owl:equivalentClass ex:출장비 .   # 동치: 같은 개념의 두 이름
ex:소유하다 owl:inverseOf ex:소유되다 .    # 역관계
ex:규정 owl:disjointWith ex:사람 .        # 서로소: 규정이면서 사람일 수 없다

# 확장 효과: "R-출장비-영수증의 소유자는 재무팀" 하나로부터
# → "재무팀은 R-출장비-영수증을 소유한다"(역관계)가 공짜로 태어난다
ⓒ 자동 분류 — 확장 기계의 최대 장기

클래스를 조건으로 정의하면, 추론기(reasoner — HermiT·Pellet)가 조건을 만족하는 개체를 자동으로 그 클래스에 넣는다. 손 분류가 아니라 정의에 의한 분류 — 1.3에서 "중량이 정당화되는 조건 ①(명시 안 된 사실의 도출이 실제로 필요)"이 가리키던 능력이 이것이다.

예제 ⓒ — 조건 정의가 낳는 자동 분류 · «→» 이하는 추론 결과 설명
# «발동형 규정» = trigger를 가진 규정  (조건 정의)
ex:발동형규정 owl:equivalentClass
  [ a owl:Restriction ; owl:onProperty ex:trigger ;
    owl:minCardinality 1 ] .

ex:R-출장비-영수증 ex:trigger "출장비 > 100,000원" .

→ 추론: ex:R-출장비-영수증 a ex:발동형규정 .
  # 아무도 분류하지 않았지만 정의에 의해 자동 소속
ⓓ 한계 — 확장 기계라서 «부재»를 못 잡는다

OWL도 개방 세계(OWA) 위의 확장 기계다. 그래서 모든 입력을 확장의 재료로 해석하지, 위반으로 해석하지 않는다. OWL이 잡아주는 유일한 것은 논리적 모순(서로소 위반 같은)뿐이다. 부재·모양 검사는 원리적으로 불가능 — 여기에 작성·디버깅 난도와 추론 비용까지 얹혀, 검증 목적에는 부적합한 부품이다.

예제 ⓓ — «owner 정확히 1» 선언이 검증이 되지 못하는 두 가지 사고
ex:규정 rdfs:subClassOf
  [ a owl:Restriction ; owl:onProperty ex:owner ;
    owl:cardinality 1 ] .              # «owner 정확히 1» 선언

사고 1 — owner가 없는 규정:
→ 위반 아님. «어딘가 있는데 아직 모를 뿐»(OWA)

사고 2 — owner가 둘인 규정(재무팀·총무팀):
→ 위반 아님. «재무팀 = 총무팀이겠구나»(owl:sameAs 추론!)
  # 이름이 달라도 같은 것일 수 있다는 고유 이름 가정(UNA) 부재 —
  # 개수를 맞추려고 둘을 하나로 합쳐버린다. 확장 기계의 극단적 실례.

# 모양 검사를 원하면 부품이 틀렸다 — SHACL로 간다.
가능자동 분류·동치/역관계 확장·논리 모순 검출 — 명시 안 된 사실의 결정적 도출(같은 그래프면 언제나 같은 결론).
불가부재·모양 검사(SHACL의 몫) · 높은 작성 난도와 추론 비용. 1.3의 판정: 이 확장 능력이 실제로 필요할 때만 중량을 든다.

SHACL Shapes Constraint Language(모양 제약 언어) · 유사품 ShEx = Shape Expressions · 스펙트럼 ⑤ 경량(검증)의 표준 부품

목적데이터 모양의 계약 — 이 스택에서 처음 나오는 «잡는» 기계. 정한 모양과 대조해 위반 리포트를 낸다. 네 소절 — ⓐ 정체 ⓑ 핵심 어휘 ⓒ 위반 리포트 ⓓ 한계. 예제는 전부 Turtle 표기.
ⓐ 정체 — 방향을 정하는 것은 어휘가 아니라, 그 어휘를 읽는 기계다

SHACL도 RDFS·OWL처럼 «약속된 어휘» 묶음(sh:)이고 같은 트리플로 적는다. 결정적 차이는 소비하는 기계: RDFS·OWL 어휘는 추론기가 읽고 그래프를 확장하지만, SHACL 어휘는 검증기(validator)가 읽고 그래프를 한 트리플도 안 늘린 채 모양과 대조한다. 세계관도 반대다 — 폐쇄 세계(CWA): «적히지 않은 것은 없는 것»으로 취급해야 비로소 «부재»를 잡을 수 있다. 역할을 정확히 가르면: 검사를 실행하는 것은 검증기 프로그램(pySHACL 등)이고, 모양은 그 입력 데이터다 — JSON Schema가 그 자체로 JSON이듯 SHACL 모양은 그 자체로 RDF다. 즉 검사 규칙이 코드가 아니라 데이터라서 규칙 자체를 질의·병합·버전 관리할 수 있다(자체 lint 스크립트와의 실질 차이 — 선언적 vs 절차적).

ⓑ 핵심 어휘 — 모양(Shape)의 구조

sh:NodeShape(모양 선언) · sh:targetClass(누구를 검사하나) · sh:property+sh:path(어느 속성을) · 제약들: sh:minCount/maxCount(개수), sh:class(목적어의 유형), sh:datatype(값 타입), sh:pattern(문자열 패턴), sh:in(허용 값 목록).

예제 ⓑ — 러닝 예제의 모양 계약
ex:규정Shape a sh:NodeShape ;
    sh:targetClass ex:규정 ;                     # 모든 규정을 검사한다
    sh:property [ sh:path ex:owner ;
                  sh:minCount 1 ; sh:maxCount 1 ; # 정확히 1개
                  sh:class ex:부서 ] ;             # 목적어는 부서여야 한다
    sh:property [ sh:path ex:verify ;
                  sh:minCount 1 ] .               # 필수
ⓒ 위반 리포트 — OWL의 두 사고가 여기선 전부 잡힌다

검증기에 데이터와 모양을 넣으면 위반 리포트가 나온다(리포트 자체도 RDF다). OWL 카드 ⓓ의 두 사고를 같은 데이터로 다시 돌려보면 대비가 완성된다.

예제 ⓒ — 같은 데이터, 정반대 결과 · «→» 이하는 검증 결과 설명
데이터:
ex:R-부실규정 a ex:규정 .                        # owner도 verify도 없음
ex:R-겹벌규정 a ex:규정 ;
    ex:owner ex:재무팀 , ex:총무팀 .              # owner가 둘

→ 검증 리포트:
✗ ex:R-부실규정 — ex:owner  개수 0 (minCount 1 위반)
✗ ex:R-부실규정 — ex:verify 개수 0 (minCount 1 위반)
✗ ex:R-겹벌규정 — ex:owner  개수 2 (maxCount 1 위반)

# OWL에선 사고 1(부재→«아직 모름»)·사고 2(둘→sameAs 합체)였던
# 똑같은 데이터가, 여기선 전부 «위반»으로 떨어진다. 이게 CWA다.
ⓓ 한계와 자리

선언 층까지다 — 규칙이 잘 정의·기재됐는지는 잡지만, 실행 준수는 실행 인스턴스를 그래프에 올려야 본다(⑥). 산문의 뉘앙스·판단 기준은 여전히 밖이다. 모양 어휘로 표현 못 하는 복잡 규칙은 sh:sparql(질의를 제약으로 쓰는 탈출구)로 적는다. ShEx는 다른 계보의 유사품 — 역할은 같다.

가능부재·개수·타입·패턴 위반의 기계 검출 — OWL이 원리적으로 못 하는 «owner 정확히 1» 집행이 바로 된다. 결정적 백스톱의 표준 부품.
불가추론은 안 한다(확장은 RDFS·OWL 몫) · 실행 준수는 ⑥ 인스턴스 필요 · 산문 뉘앙스는 관할 밖.
핵심OWL vs SHACL = 추론 vs 검증 = OWA vs CWA. 주제 2의 세계관 구분이 도구 선택으로 착지하는 지점 — 이 문장이 이 절의 절반이다.

SPARQL SPARQL Protocol and RDF Query Language(재귀 약어 — 그래프 질의 언어) · 스펙트럼 ⑥의 질의 표준

목적SQL의 그래프판 — 역할은 같고(선언적 질의), 대상 모델이 다르다. 세 소절 — ⓐ SQL과의 대응 ⓑ 패턴 매칭 ⓒ 부재 질의와 사슬 경로.
ⓐ SQL과의 대응 — 역할은 같고, 본질이 다르다

겉모양(SELECT … WHERE)은 일부러 SQL을 닮게 설계됐다. 차이 셋: ① 대상이 테이블이 아니라 그래프 — WHERE의 본질이 행 필터가 아니라 패턴 매칭이다 ② 스키마를 몰라도 더듬을 수 있다 — ?s ?p ?o는 "이 노드에서 나가는 화살표 전부" ③ 이름의 Protocol은 질의를 HTTP 엔드포인트로 공개하는 표준이라는 뜻 — Wikidata에 누구나 질의를 던질 수 있는 이유.

ⓑ 패턴 매칭 — WHERE 안은 «구멍 뚫린 트리플»이다

변수(?r)가 든 트리플 패턴을 쓰면, 그래프에서 그 패턴이 성립하는 모든 대입을 찾는다. 같은 변수의 공유가 곧 SQL의 JOIN이다 — JOIN 키워드 없이 변수가 두 패턴을 잇는다.

예제 ⓑ — 변수 공유 = JOIN · «→» 이하는 결과 설명
SELECT ?r ?o WHERE {
  ?r a ex:규정 .          # 패턴 1: 규정인 ?r
  ?r ex:owner ?o .        # 패턴 2: 같은 ?r 의 owner — 변수 공유가 조인
}
→ (ex:R-출장비-영수증, ex:재무팀) …
ⓒ 부재 질의와 사슬 경로 — 이 카드의 두 필살기

부재 질의: FILTER NOT EXISTS로 «없음»을 물을 수 있다 — 질의 층에서 CWA를 흉내내는 표준 기법. 경로식(property path): *(0회 이상 반복)로 사슬을 한 줄에 탄다 — SQL이라면 재귀 CTE가 필요한 일. RDFS 카드 ⓒ에서 의사 표기로 남겼던 «경비 전부» 질의의 실제 문법이 이것이다.

예제 ⓒ — 부재 질의(수동 감사의 표준형)와 롤업 경로식
# «verify 없는 규정 전부»
SELECT ?r WHERE {
  ?r a ex:규정 .
  FILTER NOT EXISTS { ?r ex:verify ?v }
}

# «경비류에 속하는 것 전부» — subClassOf 사슬을 * 로 한 줄에
SELECT ?x WHERE {
  ?x a/rdfs:subClassOf* ex:경비 .
}
→ ex:정산-0312 …
가능전수 질의·집계·부재 질의·사슬 탐색, HTTP 엔드포인트 공개 — 수동 감사가 질의 한 줄이 되는 층.
불가질의는 검사 스케줄러가 아니다 — 언제 돌리고 위반을 어떻게 처리할지는 파이프라인의 몫. 그리고 그래프에 안 올라간 것은 못 찾는다(⑥의 전제).

SKOS Simple Knowledge Organization System(단순 지식 조직 체계) · 스펙트럼 ②·④의 표준 부품

목적통제 어휘·시소러스(②·④)를 적는 표준 어휘 — 그 목적(이름 통일·연관 탐색)에 추론이 원래 필요 없으므로, 논리를 뺀 값싼 전용 도구로 적는다. 실무 도입 다수가 이 층에서 끝난다. 세 소절 — ⓐ 정체 ⓑ «값싸게»의 정체 ⓒ 핵심 어휘.
ⓐ 정체 — 용어를 클래스가 아니라 «개념 인스턴스»로 다룬다

SKOS의 발상: 용어 정리에는 논리가 필요 없다. 모든 용어를 skos:Concept의 인스턴스로 두고, 계층도 논리 관계(subClassOf)가 아니라 조직 관계(broader/narrower — «더 넓은/좁은 주제»)로 잇는다. 도서관 주제어·태그 체계가 하던 일의 표준화다. RDFS의 대체가 아니다 — SKOS 자체가 RDFS/OWL로 정의된 기성품 어휘(언어의 타입 시스템 위에 얹힌 표준 라이브러리)이고, 용도가 다르다: «무슨 유형의 사물인가»(RDFS — 기계가 결론 내릴 계층)와 «이 용어는 어느 주제 아래 있나»(SKOS — 정리·탐색용 계층)는 같은 그래프에서 공존한다.

ⓑ «값싸게»의 정체 — 같은 어휘를 두 방식으로 놓고 보면

절약되는 값은 논리의 비용 3종이다: ① 용어마다 클래스/인스턴스 판정 ② «진짜 is-a인가» 검토(틀리면 추론 오염) ③ 추론 부작용. 이 절약의 방법은 추론 능력의 포기인데 — 능력을 버리는 게 손실인지는 목적이 그 능력을 쓰는지에 달렸다. ②·④의 목적을 기계 동작으로 분해하면: 이름 통일 검사 = 문자열 목록 대조(prefLabel·hiddenLabel), 연관 탐색 = 화살표 따라가기(broader·related 순회) — 어디에도 추론이 등장하지 않는다. 쓸 일 없는 능력을 버리고 비용만 아꼈으니 대가가 실질 0, 그래서 손실 없는 절약이다. 반대로 롤업 추론(③)·검증(⑤)이 목적이면 같은 포기가 진짜 손실이 된다 — 그때 SKOS를 고르는 것이 1.4 «고장 질문» 위반이다.

예제 ⓑ — 같은 계층을 논리(RDFS)로 vs 조직(SKOS)으로 · «→» 이하는 결과 설명
# A. RDFS/OWL 방식 — 용어가 클래스, 계층이 논리 약속
ex:출장비 a rdfs:Class ; rdfs:subClassOf ex:경비 .
#   약속: «모든 출장비 인스턴스는 경비다» — 추론기가 확장에 쓴다.
#   용어마다 물어야 한다: 클래스인가? 진짜 is-a인가?
ex:서울 rdfs:subClassOf ex:대한민국 .   # 잘못! 서울은 대한민국의 «일종»이 아니다
→ 추론: "서울의 모든 인스턴스는 대한민국의 인스턴스" # 논리 오염 확산

# B. SKOS 방식 — 용어가 전부 Concept 인스턴스, 계층이 조직 연결
ex:출장비 a skos:Concept ; skos:broader ex:경비 .
ex:서울   a skos:Concept ; skos:broader ex:대한민국 .   # 합법 — 조직상 상위일 뿐
→ 아무 추론도 일어나지 않는다 # 오염 0 · 판정 부담 0 · 느슨한 계층 허용

# A·B의 차이는 글자가 아니라 «서술어에 걸린 표준 의미론»이다 —
# 추론기는 서술어 IRI로 규칙표를 조회한다: subClassOf엔 확장 규칙이
# 공표돼 있고 broader엔 없다. 판단이 아니라 조회(결정적)이며,
# 추론기를 안 돌리면 둘 다 그냥 화살표다.
ⓒ 핵심 어휘 — 라벨 셋과 연결 셋

라벨: prefLabel(공식 표기 — 언어별 1개) · altLabel(허용 별칭) · hiddenLabel(검색엔 걸리되 노출 금지 — 금지 표기 lint의 표준 자리). 연결: broader/narrower(상하) · related(연관). 이 여섯이 ②(라벨 셋)와 ④(연결 셋)를 정확히 커버한다.

예제 ⓒ — 어휘 항목(voc-007)의 표준 표기
ex:voc-007 a skos:Concept ;
    skos:prefLabel   "출장비"@ko ;
    skos:hiddenLabel "여비"@ko , "출장 경비"@ko ;
    skos:broader     ex:경비 .
가능이름 통일(표기 lint의 재료)·연관 탐색·수천 용어의 부담 없는 정리 — ②·④의 목적 전부.
불가논리·제약이 없다 — broader 사슬로 추론기가 아무것도 확장해주지 않고(SPARQL 경로식 skos:broader*로 손수 탈 수는 있다), 검증은 SHACL·논리는 OWL 몫. 그 능력이 필요해지면 그때 올린다(1.4 고장 질문).

도구 생태 — 이름·자리·쓰는 시점 (전부 표준 채택 시에만 해당 — 차용이면 자체 lint가 이 자리를 맡는다):

Protégé (사실상 표준 편집기 · 무료 오픈소스 — Stanford)
구축 flow(A3~A5)에서 — 스키마·클래스 계층을 GUI로 저작·검토할 때. 스키마가 수백 클래스로 클 때 가치가 있고, 작으면 텍스트 편집으로 충분.
HermiT · Pellet (OWL 추론기 · HermiT 무료, Pellet은 상용 편입 시 유료)
중량(1.3) 선택 시에만 — 저작 중 공리 모순 검사 + 런타임 자동 분류. «확장 기계»의 실물. 경량(SHACL 검증)에 머물면 불필요.
Apache Jena/Fuseki · GraphDB · Oxigraph (트리플 스토어 · GraphDB만 상용, 나머지 무료 오픈소스)
⑥(지식 그래프) 도달 시에만 — 인스턴스가 대량이고 SPARQL 질의를 상시 서비스로 제공할 때. 그 전에는 파일로 충분.
rdflib + pySHACL (파이썬 라이브러리 · 무료 오픈소스)
실행 flow의 검증(B4)과 정본 lint에서 — 적재·SHACL 검증이 코드 몇 줄. 7.3 ⓐ′ 의사코드의 shacl_validate()가 실물로는 이것이다. 채택 시 가장 먼저, 소규모에선 종종 유일하게 쓰는 도구.

3.2 채택이냐 차용이냐 — 이 절의 실제 결정

표준 채택의 이득은 상호운용·도구 생태·검증된 의미론이고, 비용은 학습 곡선·트리플 스토어 운영·기존 관행과의 이중화 위험이다. 그런데 제3의 길이 정상 경로다: 개념은 공짜로 차용할 수 있다 — 표기법이 아니라 개념이 본체이므로(1.1), 자체 구현도 온톨로지적 실천이다(1.4).

# 표준 부품 ↔ 자체 구현 등가물
RDF 레코드      ↔  YAML 항목(안정 ID 포함)
SKOS 어휘       ↔  어휘 목록 파일(공식·금지 표기)
RDFS 계층       ↔  분류 필드·접두 규약
SHACL 검증      ↔  자체 lint 스크립트(예: anchor lint)
SPARQL 질의     ↔  스크립트 질의(grep+파서)

표준으로 갈아탈 신호 3가지: ① 스크립트 질의가 복잡해져 SPARQL을 재발명하기 시작할 때 ② 외부와 어휘·그래프를 연합해야 할 때 ③ 자체 lint 규칙이 늘어 SHACL을 재발명하기 시작할 때. 신호가 없는데 미리 채택하는 것은 1.4 «소비자 질문» 위반이다.

dddjango의 유력안은 «개념 차용»(YAML 레지스트리 + 자체 lint = RDF·SKOS·SHACL의 개념을 빌린 자체 구현)이지만, 그 판단이 유효하려면 3.2의 갈아탈 신호를 알고 내려야 한다 — 확정은 적용 단계에서. 이미 있는 anchor lint는 «SHACL 자리의 자체 구현»이라고 스택 지도 위에 좌표를 찍을 수 있다.

인접 개념과의 경계 — DDD 포함

핵심 — 최적 진입로

역량 질문 — «DB 스키마와 뭐가 달라?»에 답하고, DDD(Domain-Driven Design)의 개념들을 온톨로지 용어로 번역하며, 그 번역이 어디서 끊어지는지(온톨로지에 대응물이 없는 DDD 부분)까지 말할 수 있는가?

이 절의 위치 — 주제 1이 «어느 수준까지 형식화할까»(지도), 주제 3이 «무엇으로 만드나»(부품)라면, 이 절은 이미 아는 것들과의 경계선이다. 경계가 흐리면 도입 결정이 두 방향으로 오판된다: «DB 스키마가 있는데 왜 또?»(과소평가)와 «DDD를 하고 있으니 이미 있는 셈»(과대평가). 인접 개념마다 겹침 · 경계 · 판별 질문 세 줄을 긋는다. 새 부품은 없다 — 이미 아는 것들 사이에 온톨로지의 자리를 확정하는 장이라 술술 읽히면 그게 통과다. 대신 4.3의 세 가지는 도입 결정에 직접 쓰이므로 가져가야 한다.

4.1 스키마류·지식 그래프와의 경계

vs DB 스키마 · 타입 시스템 · JSON Schema 한 시스템 안의 모양 계약

겹침역할은 SHACL과 닮았다 — 모양을 선언하고 위반을 막는다(둘 다 CWA 검사). 실제로 조건부 규칙 일부는 DB의 CHECK 제약으로도 적을 수 있다.
경계차이는 표현력이 아니라 관할과 신분이다. ① 관할 — 스키마의 규칙은 «이 저장소에 도달한 데이터»만 지킨다. 신청서 단계, 다른 시스템, 사람의 판단에는 힘이 없다. ② 신분 — 스키마 안에서 규칙은 제약(술어)일 뿐 주어가 될 수 없다. 온톨로지에선 규칙 자체가 점(주어)이라, 소유자·발동 조건·집행 지점이 화살표로 달린다 — 주제 3 ⓓ에서 본 ex:R-출장비-영수증이 정확히 그 모습이었다.
예제 — CHECK로 적은 같은 규칙: 집행은 되지만 지식이 되지 못한다
-- 정산 DB의 자위(自衛) — 규칙의 «집행»은 여기서도 가능하다
ALTER TABLE expense_report ADD CONSTRAINT receipt_rule
  CHECK (amount <= 100000 OR corporate_card OR receipt_url IS NOT NULL);

-- 그러나 이 CHECK는:
--  · 이 테이블에 도달한 행만 지킨다 (다른 시스템·문서·사람에겐 무력)
--  · 규정집 §3과의 대응이 어디에도 없다 — «이 제약이 그 조항의 집행»이라는
--    사실 자체가 기록될 자리가 없다
--  · 소유자·개정 이력을 달 수 없다 — 규칙이 주어(점)가 아니기 때문
판별«이 규칙을 알아야 하는 소비자가 이 시스템 하나인가?» 하나면 스키마·타입으로 충분하고 온톨로지는 과잉이다. 여럿(사람·다른 시스템·LLM)이면 규칙을 데이터로 빼는 값을 한다. 타입 시스템과 JSON Schema도 같은 자리다 — 각각 한 코드베이스·한 응답의 모양 계약(주제 7의 structured output 논의로 이어진다).

vs 지식 그래프 스펙트럼 ⑥ — 복습

겹침같은 부품(RDF·SPARQL) 위에 있다 — 주제 1 ⑥에서 이미 본 관계.
경계온톨로지는 그래프의 스키마·문법 층, 지식 그래프는 온톨로지 + 대량 인스턴스 + 저장·질의 운영. 출장비로 치면 규칙·용어 수십 건이 스키마 층이고, 정산 건 수만 행이 인스턴스 층이다. 따라서 «온톨로지 도입»과 «지식 그래프 도입»은 규모가 다른 결정이다 — 후자는 트리플 스토어 운영까지 떠안는다.
판별인스턴스가 대량으로 쌓이고 그 위에 질의가 필요한가? 아니라면 스키마 층(용어·규칙·관계)까지만 가면 된다.

4.2 DDD 대응 — 이미 하던 설계의 형식화

먼저, 어느 층 이야기인지부터. dddjango 세계에 DDD는 두 층으로 존재한다 — 층 ①: 플러그인 자신의 규칙 코퍼스(파이프라인을 규율하는 규범 문장들: «판정 소유»·«현행 계약»·앵커 절…) · 층 ②: 플러그인으로 만드는 각 프로젝트의 도메인 코드(당신의 Django 애그리거트들). 온톨로지 도입 검토의 대상은 층 ①이다. 아래 번역표는 «층 ②의 구현 코드를 온톨로지로 이관하라»는 말이 아니라 학습의 다리다 — 당신이 이미 아는 DDD 개념 체계가 온톨로지 개념 체계와 거의 1:1로 대응되므로 새로 배울 것이 적다는 것.

층 ②는 옮겨야 하나? 기본값은 «아니오»다. 코드가 이미 정본이고, 코드에서 파생 가능한 구조(클래스·호출 관계)는 기계가 코드에서 직접 읽으면 되므로 옮길 소비자가 없다(1.4 소비자 질문). 층 ②에서 축적 가치가 있는 것은 코드에서 파생되지 않는 지식(용어 합의·외부 계약 상태·설계 이유)인데, dddjango는 이를 이미 현행 계약 문서·영구 테스트 입장 표로 반쯤 구조화해 축적하고 있다 — 그것을 더 형식화할지는 별개 질문이고, 역시 소비자가 생길 때 1.4의 4질문으로 다시 묻는다.

예제 읽는 법 — 자리바꿈. 러닝 예제(출장비)는 형태만 보면 «업무 시스템의 결과물 데이터에 온톨로지를 씌운 것»이라 층 ②처럼 보인다. dddjango로 옮길 때는 배역을 바꿔 읽어야 한다: 규정집 §3 = 규칙 코퍼스(산문 규범) · 정산 시스템의 CHECK = 백스톱 스크립트(집행 지점) · 정산 건 = 파이프라인 산출물(설계 명세·판정·transcript). 온톨로지는 항상 어떤 도메인 위에 앉는데, 층 ①에서 그 도메인은 고객 데이터가 아니라 파이프라인 운영 자체다 — dddjango가 회사라면 코퍼스가 규정집이고, 세션의 산출물이 정산 건이다.

DDD ↔ 온톨로지 번역표 Domain-Driven Design과의 개념 대응

목적DDD를 아는 사람에게 온톨로지는 새 분야가 아니라 «유비쿼터스 언어를 기계가 읽게 만든 것»이다. 번역표로 전체를 잡고, 소절 ⓐ~ⓓ가 주요 행을 러닝 예제로 확인한다. 판정: ≈ 그대로 · △ 부분 · ✗ 없음.

ⓐ 유비쿼터스 언어 = 통제 어휘

유비쿼터스 언어의 실체는 «이 컨텍스트에서 이 낱말은 정확히 이것»이라는 합의 — 스펙트럼 ②(통제 어휘)와 같은 물건이다. 차이는 거주지 하나: DDD의 언어는 사람의 대화와 코드 식별자에 살고, SKOS로 옮기면 기계가 검사할 수 있는 데이터가 된다.

예제 ⓐ — 재무 컨텍스트 언어 한 항목을 SKOS로 (Turtle 표기)
fin:출장비 a skos:Concept ;
    skos:prefLabel   "출장비"@ko ;                # 공식 표기 — 유일
    skos:hiddenLabel "여비"@ko , "출장 경비"@ko .  # 검출·반려용 (주제 3 SKOS)
ⓑ Bounded Context = 네임스페이스

BC의 본질은 «낱말의 뜻은 경계 안에서만 유효»다. 온톨로지의 네임스페이스가 정확히 같은 장치인데 한 발 더 나간다 — 개념의 정체가 낱말이 아니라 IRI라서, 두 컨텍스트가 같은 낱말을 써도 주소가 달라 충돌이 원천적으로 불가능하다.

예제 ⓑ — 같은 낱말 «출장», 컨텍스트마다 다른 개념 = 다른 주소
@prefix fin: <http://example.org/finance/> .  # 재무 BC
@prefix hr:  <http://example.org/hr/> .       # 인사 BC

fin:출장비 a fin:경비유형 .   # 재무: 돈의 분류
hr:출장   a hr:근태상태 .    # 인사: 근무 형태 — 낱말이 겹쳐도 무해
ⓒ Context Map = 정렬(alignment)

컨텍스트 맵은 «경계 사이의 번역 관계»를 그린 그림이다. 온톨로지에선 이를 정렬이라 부르고, 번역 관계 자체가 트리플이 된다 — 그림이 아니라 기계가 읽는 데이터. 경량이면 skos:exactMatch(논리 약속 없음 — 사람·도구용 표지), 중량이면 owl:equivalentClass(추론기가 실제로 합쳐 읽는다 — 주제 3 OWL의 sameAs 합체와 같은 계열이므로 같은 위험도 함께 온다).

예제 ⓒ — 외부 ERP와의 통합 지점(ACL 자리)을 정렬 트리플로
fin:출장비 skos:exactMatch erp:TravelExpense .  # 표지만 — 추론 없음
# 중량판: fin:출장비 owl:equivalentClass erp:TravelExpense .  # 합쳐 읽음
ⓓ 애그리거트 불변식 = 제약 — 단, 정적 조건만 이주한다

불변식이라는 지식은 어디 사는가가 갈림길이다. 코드에 살면 그 시스템만 집행하고 규칙은 if문 속에서 익명이다. SHACL로 빼면 규칙이 ID를 가진 일급 사실이 되어 사람·검증기·LLM이 같은 정본을 읽는다. 단 이주하는 것은 정적 조건뿐 — 상태 전이(제출→승인→정산)와 트랜잭션 일관성은 애그리거트에 남는다. 주제 3의 ex:규정Shape가 «규칙 목록 자체»의 모양을 검사했다면, 아래 모양은 «정산 데이터»를 검사한다 — 같은 부품이 두 층 모두에 쓰인다.

예제 ⓓ — 같은 불변식의 두 거주지: 코드(익명) vs 데이터(일급)
# ① 코드 거주 — 애그리거트 안 (이 시스템만 집행, 규칙은 익명)
if amount > 100_000 and not corporate_card:
    require(receipt)

# ② 데이터 거주 — SHACL 모양 (규칙이 주어가 되어 소유자를 달 수 있다)
#   «초과 ∧ 법인카드 아님 → 영수증»을 sh:or(셋 중 하나면 통과)로 뒤집어 표현
fin:영수증Shape a sh:NodeShape ;
    sh:targetClass fin:출장비정산 ;
    sh:or ( [ sh:path fin:금액 ;     sh:maxInclusive 100000 ]
            [ sh:path fin:법인카드 ; sh:hasValue true ]
            [ sh:path fin:영수증 ;   sh:minCount 1 ] ) .
가능DDD 설계 산출물(용어집·컨텍스트 맵·불변식 목록)을 거의 기계 번역 수준으로 온톨로지 초안에 옮길 수 있다 — 온톨로지를 만들기로 결정했다면 시작 비용이 급감한다는 조건부 이야기지, 만들라는 권고가 아니다. 학습자에게는 이 대응 자체가 «최적 진입로»다.
불가행위·상태 전이·트랜잭션 일관성은 못 옮긴다 — 온톨로지는 명사와 사실의 층이다. 그래서 관계는 대체가 아니라 적층이다: DDD는 그대로 두고, 그 위의 정적 지식 층만 형식화한다.

4.3 이 절에서 가져갈 것 — 결정에 쓰이는 세 가지

  1. 소비자 판별 질문. 규칙을 코드·스키마에서 데이터로 빼는 것이 정당한 조건은 하나뿐이다 — 소비자가 여럿인가. dddjango 코퍼스는 소비자가 여럿이다(claude·codex 양판 에이전트 · 사람 · 백스톱 · anchor lint). 층 ① 도입 논거의 반쪽이 여기서 나온다.
  2. 규칙의 신분. 스키마·CHECK와의 진짜 차이는 표현력이 아니라 «규칙이 주어가 되는가»다. 규칙이 ID를 가진 점이어야 소유자·발동 조건·집행 지점이 화살표로 달린다 — Phase 0 센서스가 재는 것이 정확히 이 신분이다.
  3. 번역의 한계선. 행위·절차·상태 전이는 온톨로지로 못 간다. 코퍼스의 규범 문장 중 «게이트 순서·단계 절차»류는 온톨로지 대상이 아니고, 정적 지식(용어·소유·커버 관계)만 대상이다 — 과형식화(주제 6)를 막는 선이 여기서 그어진다.
① 지식 스킬의 «판정 소유»·«현행 계약»·«touched»는 이미 유비쿼터스 언어다 — 곧 통제 어휘 항목이자 클래스 후보(ⓐ). ② houserules 이중 §공간 충돌은 BC 없이 낱말(§번호)을 공유하다 난 사고 — 네임스페이스(ⓑ)가 구조적 처방이고 anchor lint는 그 수제 선행판이다. ③ 결정적 백스톱 27종이 지키는 규칙 대부분은 아직 «코드 속 익명»(ⓓ의 ①번 거주지) — 어떤 규칙이 어느 거주지에 있는지 세는 것이 Phase 0 센서스다.

대표 안티패턴
과형식화(ontological overcommitment): 뉘앙스가 본체인 산문까지 공리로 옮기다 유지 불능 · is-a/part-of 혼용 · 클래스와 인스턴스 혼동 · 아무도 안 쓰는 관계 남발.
«형식화할 것은 뼈대(ID·소유자·발동 조건·커버 여부), 뉘앙스는 산문 유지»가 과형식화 회피의 실전 답이고, 이는 전역 코딩 원칙 06(성급한 추상화 경계)과 같은 원칙이다.
7

LLM 시대의 온톨로지

핵심 — 결정 직결

역량 질문 — «LLM이 생성하고 기호 층이 검증한다»는 분업에서 온톨로지가 검증 층의 어떤 부품이 되는지 설명하고, 2000년대에 실패한 이 기술이 왜 LLM 시대에 되살아나는지를 비용과 소비자 양면으로 말할 수 있는가?

이 절의 위치 — 1~4가 온톨로지 자체라면, 이 절은 «왜 지금인가»다. 온톨로지는 2000년대 시맨틱 웹과 함께 한 번 실패한 기술이다 — 만들기는 비쌌고(전문가 필요), 만들어도 읽을 소비자가 없었다. LLM은 이 두 사인(死因)을 동시에 뒤집는다: 구축 비용을 무너뜨리고(7.4), 자신이 첫 대량 소비자가 된다(7.1~7.3) — 그것도 자신의 비결정성 때문에. 이 역전이 도입 결정의 «지금» 논거다. 구성으로 보면 기호 층이 LLM을 양쪽에서 감싼다 — 입력 쪽(7.2 그라운딩: 읽을 재료를 «걸리는 것 전부»로 공급)과 출력 쪽(7.3 검증: 산출물을 모양에 맞을 때까지). 두 개입은 성격이 다르다: 입구는 틀릴 확률을 줄이는 «공급»(개선일 뿐 보장 아님)이고, 출구는 틀린 것이 못 나가게 하는 «강제»(계약 범위 안 보증)다. LLM 자체는 그 사이에서 끝까지 확률 기계로 남는다 — 결정적이 되는 것은 LLM이 아니라 출구를 통과한 것의 성질이다. 7.4는 그 기호 층 자체를 LLM이 짓는 역방향이다.

7.1 확률 기계와 결정 기계 LLM의 읽기는 왜 흔들리는가 — 이 절 전체의 전제

목적같은 지식이라도 «누가 읽느냐»에 따라 결과의 성질이 다르다는 구분을 세운다. 세 소절 — ⓐ 확률 기계 ⓑ 결정 기계 ⓒ 이름 정리(기호 층).
ⓐ LLM은 확률로 읽는다

LLM은 산문을 문맥으로 이해한다 — 그래서 유연하지만, 같은 입력에 늘 같은 판정을 보장하지 않는다. 문서가 커질수록 어떤 절이 주의에 들어올지도 확률적이어서, 규칙이 존재하는데도 적용이 누락되는 고장이 구조적으로 가능하다.

ⓑ 결정 기계는 조회한다

주제 3에서 도출한 원리가 여기서 힘을 쓴다 — 추론기·검증기는 판단하지 않고 서술어 IRI로 규칙표를 조회한다. 같은 입력이면 영원히 같은 출력. 대가는 유연성 제로: 규칙표에 없는 상황(새 유형의 경비)은 처리하지 못한다. 그래서 관계는 대체가 아니라 분업이다.

예제 — 같은 질문, 두 기계의 답
질문: "영수증 없는 9만 원 법인카드 정산, 통과?"

신입 담당자(확률 기계)  규정집 전체를 읽고 → 대체로 "통과" —
                      그러나 바쁜 날은 §3을 놓치고 다르게 답할 수 있다
SHACL 검증기(결정 기계) 금액 ≤ 10만 → sh:or 첫 분기 충족 → 통과 —
                      천 번 물어도 같은 답, 단 모양에 적힌 것만 본다
ⓒ 이름 정리 — 기호 층(symbolic layer)

«기호»는 거창한 게 아니다. 이 문서에서 계속 봐 온 ex:출장비 같은 IRI, 트리플, sh:minCount 1 같은 제약 — 글자로 적어 놓은 표식이 전부 기호다. 기호의 성질은 하나만 기억하면 된다: 두 기호는 같거나, 다르거나, 둘 중 하나다. ex:출장비와 ex:여비는 문자 그대로 다르다 — 끝. «얼마나 비슷한가»라는 중간 지대가 없다. 그래서 기호로 적힌 지식은 조회·대조가 가능하고, 결과가 매번 같다.

반대로 LLM 안에는 이렇게 적힌 지식이 없다. 규정집을 학습해도 내용은 수십억 개의 가중치(숫자)에 흩어져 녹아 있어서, «출장비 규칙은 여기 있다»고 가리킬 자리가 없다. 꺼내는 방법은 생성뿐이고, 생성은 ⓐ에서 봤듯 확률적이다.

AI는 이 두 방식에 이름을 붙여 두었다 — 지식을 가중치에 녹이는 쪽이 뉴럴(신경망), 기호로 적는 쪽이 심볼릭(기호주의). 둘을 붙여 쓰는 구조가 7.3의 뉴로심볼릭이다. 헷갈리기 쉬운 지점: 주제 3의 부품들(RDF·Turtle·RDFS·OWL·SHACL·SPARQL)은 전부 심볼릭 쪽 부품이지 뉴로심볼릭이 아니다 — 뉴로심볼릭은 부품의 이름이 아니라, LLM(뉴럴)과 이 부품들(심볼릭)을 분업시킨 시스템 구조의 이름이다. 검증기 하나만 돌리면 그냥 심볼릭 시스템이고, LLM이 생성하고 검증기가 판정하는 루프를 짜야 그 전체가 뉴로심볼릭이다. 기호 층은 시스템에서 심볼릭 쪽 전체를 부르는 말이다: 기호로 적힌 지식(온톨로지·SHACL 모양) + 그 기호를 결정적으로 다루는 기계들(검증기·추론기·질의 엔진). 이 문서에서 «검증 층»·«결정 기계 쪽»이라 불러온 것이 전부 이것이고, dddjango의 백스톱도 기호 층의 부품이다.

예제 ⓒ — 같은 지식의 두 존재 방식
지식: "출장비 10만 원 초과는 영수증 필수"

신경망 쪽  신입 담당자의 머릿속 / LLM의 가중치 —
          어디 있는지 가리킬 수 없고, 꺼내면 매번 조금 다를 수 있다
기호 층    ex:R-출장비-영수증 트리플 + fin:영수증Shape —
          파일 몇째 줄이라 가리킬 수 있고, 언제 읽어도 같다
가능이 구분이 서면 «어떤 일을 어느 기계에 맡길까»가 설계 질문이 된다 — 이해·생성은 확률 기계에, 판정·검증은 결정 기계에.
대응dddjango 비결정성 진단(«자료는 충분한데 사용이 비정형»)의 정체가 이것이다 — 규칙 적용 전부를 확률 기계 하나에 맡긴 구조.

7.2 구조 그라운딩 grounding — 검색을 구조에 딛게 하기 · RAG(Retrieval-Augmented Generation)의 한계와 GraphRAG 계열

목적확률 기계가 읽을 재료를 «비슷한 것»이 아니라 «걸리는 것 전부»로 공급한다. 두 소절 — ⓐ 벡터 검색의 한계 ⓑ 그래프 그라운딩.
ⓐ 벡터 RAG — 유사도는 의미 관계가 아니다

벡터 검색은 질문과 비슷한 문단을 가져온다. «관련 문서»는 찾지만 «적용 규칙»은 못 고른다 — 유사한 문장과 걸리는 규칙은 다른 물건이기 때문이다. 주의: «전혀 못 찾는다»는 뜻이 아니다 — 대체로 찾아온다. 문제는 «걸리는 규칙 전부»라는 보장이 없고, 빠뜨렸다는 사실을 알 방법도 없다는 것이다. 유사 문서 탐색이 목적인 곳에선 벡터 검색이 여전히 옳은 도구다.

ⓑ 그래프 그라운딩 — 확장은 화살표를 따라 결정적으로

벡터를 버리는 게 아니라 분업이다: 시작점만 벡터 검색으로 잡고(자연어 질문을 그래프 어느 지점에 붙일지), 확장은 그래프 화살표(is-a 계층·verify 관계)를 따라 결정적으로 간다. GraphRAG(Microsoft — 그래프+커뮤니티 요약), OG-RAG(Ontology-Grounded RAG)·OntologyRAG 등 이름은 많지만 원리는 하나다. 병목도 하나다: 그래프에 없는 지식은 그라운딩할 수 없다 — 그래프 품질·커버리지가 곧 상한.

예제 — 질의 «출장 경비 어떻게 처리?»에 두 검색이 가져오는 것
벡터 검색       출장 후기 문단(유사) + 경비 일반 문단(유사) + §3 일부 —
                «비슷한 순서»라 예외 조항이 잘려 나갈 수 있다

그래프 그라운딩  출장비 ─is-a→ 경비 계층에 걸린 규칙 전부
                + R-출장비-영수증 ─trigger·verify·owner→ 이웃 통째로 —
                규칙·예외·검증 절차·소유자가 빠짐없이 따라온다
가능규칙 적용의 재현율(recall) — 빠뜨림이 확률이 아니라 커버리지의 문제로 바뀐다(커버리지는 셀 수 있다).
불가그래프 밖 지식은 못 가져온다 — 그래서 도입하면 «무엇이 그래프에 있나»의 센서스가 먼저다.

7.3 뉴로심볼릭 분업 neurosymbolic · 생성은 확률 기계, 판정은 결정 기계

목적LLM 산출물의 품질 보증을 확률에서 계약으로 바꾼다. 두 소절 — ⓐ 루프 ⓑ structured output과의 관계.
ⓐ 생성 → 검증 → 피드백 루프

LLM이 후보를 생성하고, 기호 층(SHACL 검증기·OWL 추론기)이 기각하거나 통과시키고, 위반 리포트가 LLM에 피드백되어 재생성한다(예: LLM + HermiT 추론기 검증, 에이전트 행동을 온톨로지 제약으로 묶는 ontology-constrained agents 연구). 검증이 결정적이므로 생성자를 믿지 않아도 결과를 믿을 수 있는 구조가 된다. 주의 — 뉴로심볼릭은 제3의 기계가 아니라 두 기계를 붙인 구조의 이름이다: 생성(무엇이 나올지)은 여전히 확률적이고, 판정(나온 것이 계약을 지켰는지)만 결정적이다. 루프가 몇 번 돌지는 확률이지만, 통과 도장이 찍힌 산출물이 모양의 규칙을 지켰다는 사실은 확실하다 — 확률이 제거되는 게 아니라 확률이 사는 자리가 «결과 품질»에서 «소요 횟수»로 옮겨간다. 이 이동이 곧 채택 이유다: 품질이 확률인 것(조용한 위반)은 감당 불가능하지만, 횟수가 확률인 것(재시도 비용)은 감당 가능하다. 그래서 LLM에게 중요한 일을 시키는 곳에서 이 구조는 사실상 표준이다.

예제 — LLM이 쓴 정산 초안이 루프를 도는 모습
① LLM 초안   fin:정산-0817 a fin:출장비정산 ;
              fin:금액 180000 ; fin:법인카드 false .   # 영수증 누락
② 검증기      fin:영수증Shape 위반 — sh:or 세 분기 모두 불충족
③ 피드백      "영수증 필요 (R-출장비-영수증)" → LLM이 첨부해 재제출
④ 재검증      통과 — 이 판정은 LLM의 컨디션과 무관하다

그럼 뉴로심볼릭 시스템 자체는 어떻게 «작성»되는가 — 전용 언어는 없다. 지식은 Turtle·SHACL 데이터로 살고(심볼릭), 생성력은 LLM에 살고(뉴럴), 시스템의 실물은 둘을 잇는 평범한 루프 코드다. 아래 코드에 도메인 지식이 한 줄도 없다는 점이 핵심이다 — 규칙을 바꾸고 싶으면 코드가 아니라 모양 파일을 고친다.

예제 ⓐ′ — 위 루프를 시스템으로 조립한 실물 (의사코드)
shapes = load("finance-shapes.ttl")        # 심볼릭 부품 — 지식은 데이터로 존재

draft = llm("부산 2박 출장 정산서 작성, 18만 원")   # 뉴럴 부품 — 확률적 생성
while True:
    report = shacl_validate(draft, shapes)  # 심볼릭 부품 — 결정적 판정
    if report.conforms: break               # 통과 = 계약 준수 보장
    draft = llm("위반 수정: " + report.violations)  # 피드백 → 재생성

submit(draft)   # 몇 바퀴 돌지는 확률, 제출물의 규칙 준수는 확실
ⓑ structured output — 실행 시점의 집행 수단

JSON Schema 강제 출력은 «한 응답의 모양» 계약이고, 온톨로지는 «도메인 전체의 의미» 계약이다. 층이 다르며 전자는 후자에서 파생되는 실행 시점 집행 수단이 된다 — 정본(온톨로지)에서 응답 스키마를 뽑아 쓰는 관계. 정리하면 LLM을 모양에 맞추는 방식은 둘이다: 사후 검증(ⓐ의 루프 — 자유 생성 후 위반을 되돌려 보냄)과 사전 강제(structured output — 애초에 벗어난 출력을 못 만들게). 실전은 조합이다 — 형식(필드 존재)은 사전 강제로, 의미 규칙(초과인데 영수증 없음)은 사후 검증으로.

가능«AI를 안 믿어도 되는 구조» — 이 문장의 학계 이름이 뉴로심볼릭이다.
불가검증 층이 아는 것만 잡는다 — 모양에 없는 위반은 조용히 통과한다(1.2의 고장 질문과 같은 원리). 검증 층 자체의 품질 관리가 주제 6이다.
대응백스톱 27종과 에이전트의 관계가 정확히 이 분업의 수제판이다 — 즉 dddjango는 뉴로심볼릭을 이미 쓰고 있다. 차이는 하나: 지금은 규칙(산문)과 백스톱(코드)이 따로 살아서 검증 층이 정본에서 파생되지 않는다. 그래서 온톨로지 도입 질문은 «뉴로심볼릭을 쓸까»가 아니라 «이미 쓰는 뉴로심볼릭의 기호 층을 정본 파생 구조로 업그레이드할까»다.

7.4 역방향 — LLM이 온톨로지를 만든다 ontology learning의 재부상 · 구축 비용의 붕괴

목적첫 실패의 사인이었던 구축·유지 비용이 무너졌음을 확인한다. 두 소절 — ⓐ 왜 죽었었나 ⓑ 무엇이 바뀌었나.
ⓐ 왜 죽었었나

2000년대 시맨틱 웹의 온톨로지는 전문 온톨로지스트가 손으로 지었다 — 비싸고 느렸으며, 완성돼도 그것을 읽어줄 소비자(응용)가 드물었다. 대부분 갱신이 끊긴 «죽은 온톨로지»로 끝났다.

ⓑ 무엇이 바뀌었나 — 만드는 쪽도, 읽는 쪽도 LLM

LLM이 산문에서 클래스·관계·제약 후보를 추출하고(OntoGPT류) 어휘 사이 정렬 후보를 대준다(Agent-OM류). 사람의 역할이 작성자에서 심의자로 바뀌어 구축이 며칠 단위가 됐다. 동시에 소비자 문제도 풀렸다 — 온톨로지의 첫 대량 소비자가, 자신의 비결정성 때문에 그것을 필요로 하는 LLM 자신이라는 역설.

예제 — 규정집 산문 → LLM 초안 → 사람 심의
입력   규정집 §3 산문 (1.2 ① 카드의 그 문장)
LLM    "클래스·속성·제약 후보를 Turtle로 추출해줘"
       → ex:출장비정산, fin:금액, fin:영수증, 영수증Shape 초안 …
사람   재무팀이 심의: trigger 경계값(10만 «초과»인가 «이상»인가),
       법인카드 예외의 범위 확정 → 승인분만 정본 등재
가능«작은 팀의 온톨로지»가 현실이 됐다 — 도입 문턱이 조직 문제에서 절차 문제로 내려왔다.
불가심의 없는 자동 구축은 검증 층까지 확률로 오염시킨다 — 결정성의 원천은 도구가 아니라 «사람이 승인한 정본»이라는 절차다.
이 절이 도입 논거의 나머지 반쪽이다. 4.3-①(소비자 여럿)이 정당성이라면, 7은 필요성(주 소비자인 에이전트가 확률 기계라서 — 7.1)과 가능성(구축 비용 붕괴 — 7.4)을 준다. 판정-소유 대조 표·수신 구문 검사·anchor lint는 전부 뉴로심볼릭 검증 층의 수제 부품(7.3)이고, 도입이란 이 부품들을 하나의 정본에서 파생시키는 것이다. 그리고 그 정본의 구축 자체가 7.4 방식(LLM 초안 + 사용자 심의)으로 진행될 것이다.
