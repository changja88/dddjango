dddjango-web 2.1.0 · 웹 표준 트리

web/ 하나에 간소화 DDD 4층 — 지식은 한 방향

dddart 의 표준 파일트리를 그대로 가져와 구현 기술만 Django · HTML · HTMX · JS 로 바꿨다. BC 마다 domain · application · infra · presentation 네 층을 두고, 화면 지식은 View → VM → UseCase → Repo 한 방향으로만 흐른다. 기존 코드의 위반은 면제가 아니라 빚이다 — 이번 요청이 손대는 범위의 빚은 G0 에서 묻고, 고르면 기능보다 먼저 동작 그대로 정리한다.

목적

대상 Django 프로젝트에 붙는 앱 web 하나가 dddjango-web 이 만드는 화면 코드의 뿌리다. 백엔드 코드(application/·framework/)는 고치지 않고, 화면은 이 프로젝트 안의 JSON API 를 같은 프로세스 안에서 불러 데이터를 얻는다.

파일트리가 곧 규약이다 — 어떤 파일을 어디에 어떤 이름으로 만드는지가 핵심 강제이고, 기계로 셀 수 있는 부분은 결정적 백스톱 86종이 게이트에서 본다.

들어오는 것

엔트리포인트 셋(__init__.py·apps.py·urls.py) + 컨테이너 다섯(root/·application/·common/·design_system/·static/) + 승인된 공식 SDK 가 있을 때만 sdk_registry.json. 테스트는 web/ 밖 형제 web_test/ 에 둔다.

호스트 쪽 연결(settings 의 INSTALLED_APPS·TEMPLATES·STATICFILES_DIRS·MIDDLEWARE·ALLOWED_HOSTS · 루트 urls 의 include("web.urls")·404/500 연결 · htmx 2.0.10)은 Coordinator 가 G0 에서 점검하고 승인받아 넣는다.

안 들어오는 것

백엔드 application.·framework. import(IM25)와 상대 import(IM24). 시동 로직이 쌓인 apps.py, URL 분기 조립이 쌓인 urls.py.

표준 트리 밖 옛 배치 폴더(1.x 의 <screen_area>/·client/·base/ 류) — 면제가 아니라 빚이다. 빚 스캔이 파일마다 ST0 로 내고, 이번 요청이 손대는 범위에 들면 슬라이스 0 이 새 트리로 옮긴다.

이 모양이 된 까닭

2.0.0 부터 dddart 표준 파일트리(운영 앱 실측)를 그대로 가져와 구현 기술만 Django · HTML · HTMX · JS 로 바꿨다. 간소화 DDD(repository 인터페이스 · DTO · ACL 없음 — 뼈대 4계층은 유지) + 철저한 MVVM(View → VM → UseCase → Repo 한 방향).

목적

전체를 아는 유일한 곳이다 — application/·common/·design_system/ 세 컨테이너를 모두 안다. 그래서 application/ 밖, apps.py·urls.py 옆에 있다.

들어오는 것

계층 없이 역할 4폴더 — router/(내비 그래프) · scaffold/(문서 셸 + 전역 게이트) · handler/(이벤트원당 1파일) · initializer/(시동). scaffold 만 종류 2차(view/·view_model/·state/)를 갖는다. 모든 파일은 root_ 접두다.

안 들어오는 것

BC 어휘 화면 — 여러 BC 를 비추는 화면(피드 등)도 root 가 아니라 자기 이름의 일반 BC 다. Repo · DataSource 직접 호출 — root 도 BC 의 UseCase 만 부른다.

이 모양이 된 까닭

BC 가 root 를 알면 전체를 알게 되어 격리가 무너진다. root 를 아는 곳은 web/apps.py·web/urls.py·호스트 settings 뿐이다 — 예외는 페이지 템플릿의 {% extends "root/scaffold/view/root_view.html" %} 한 줄이다. BC 코드에 import …root_… 한 줄이 보이면 바로 위반으로 식별된다.

목적

바운디드 컨텍스트(BC) = 기능 영역 하나. BC 폴더 안에 4계층(domain_layer·application_layer·infra_layer·presentation_layer)을 둔다. 이 탭은 BC 루트와 순수 Python 층 domain_layer 를 펼친다.

들어오는 것

BC 루트 직속은 <bc>_router.py·<bc>_navigator.py 둘 + 패키지 표지 + 국소 ruff.toml. domain_layer 는 항상 애그리거트(개념) 1차 — 작아도 애그리거트 폴더부터 만들고, 개념이 불명확하면 BC 와 같은 이름의 애그리거트가 기본이다.

골격 완비 — BC 를 만들면 4계층과 표준 종류 폴더를 전부, 비어 있어도 만든다. 선택 폴더는 없다.

안 들어오는 것

domain_layer 의 django import 와 common import(예외: common/util/json_field.py 하나). application/ 직속 조립 파일(→ root/). area·BC 이름의 계층명·컨테이너명.

이 모양이 된 까닭

간소화 DDD — repository 인터페이스 · DTO · ACL 은 버렸지만 뼈대(4계층 · 개념 1차 · 종류 2차)는 지킨다. 판정·계산은 1곳째부터 domain 이 소유한다(빈혈 방지).

area 는 G0 에서 사용자가 판정할 때만 쓰는 순수 시각 그루핑이다 — 식별자·클래스명·URL name 어디에도 나오지 않고, 지워도 경로만 바뀐다.

한 칸씩 — 무엇이 오나15칸
  1. application/도메인
    BC 컨테이너. 직속에는 BC 폴더(또는 area 폴더)만 온다.
  2. <area>/도메인
    같은 접두 BC 가 여럿일 때 사용자가 G0 에서 «area 로 묶기»를 고르면 생긴다. 직속은 BC 폴더만 · 중첩 1단.
    규칙에이전트가 스스로 만들지 않는다 — 판정은 config 의 area_prefixes 에 남는다
  3. <bc>/도메인
    바운디드 컨텍스트 하나. 이름은 web 전역 유일(area 를 써도 접두 유지).
    규칙골격 완비 — 4계층 + 모든 표준 종류 폴더, 비어 있어도
  4. <bc>_router.py도메인
    urlpatterns + app_name + class <Bc>Routes(URL name 상수) — URL path·name 의 단일 출처.
    규칙라우트 리터럴은 이 파일 안에서만 — navigator · root_destination_handler 는 상수만 참조 · 템플릿의 {% url %}·경로 리터럴은 NM13
  5. <bc>_navigator.py도메인
    정적 href 헬퍼(reverse) — URL name 만 참조한다. View 를 import 하지 않는다.
    규칙VM 만 navigator 를 부른다 — 템플릿은 State 가 준 href 를 쓴다
  6. ruff.toml도메인
    생성 폴더 국소 lint — 함수 인자·반환 타입 명시(ANN). BC 루트 · common/ · root/ 마다 두고, 호스트 루트 ruff 설정은 고치지 않는다.
  7. domain_layer/도메인
    django import 금지 — dataclasses·enum·typing·datetime·decimal 같은 표준 라이브러리만.
  8. <aggregate>/도메인
    애그리거트 1차.
  9. <aggregate>.py도메인
    일관성 경계. 상태 전이는 루트 메서드가 새 인스턴스를 돌려준다.

application_layer/UseCase · VM 3변종 · StateMVVM
목적

Model 의 관문(UseCase)과 화면 상태의 주인(ViewModel 3변종 — VM · SharedState · Service), 그리고 그들이 내놓는 State 가 산다.

들어오는 것

종류 5폴더 — use_case/·view_model/·state/·shared_state/·service/. 두 번째 개념이 등장하면 개념 1차(<개념>/)로 나누고 그 안에 종류 폴더를 완비한다 — 나뉜 뒤 옛 직속 종류 폴더는 동결.

안 들어오는 것

request·HttpRequest·HttpResponse 와 django import(django.utils 제외 — IM12). VM 의 design_system 참조. UseCase 의 UI 직접 호출(템플릿 render·응답 반환). 과거형 사건명 shared_state.

이 모양이 된 까닭

철저한 MVVM — 지식은 View → VM → UseCase → Repo 한 방향. dddart 의 상주 VM 자리를 web 에서는 요청마다 만드는 VM이 맡고, 요청 사이에 남는 값은 세션 수명(SharedState)·프로세스 수명(Service)으로 나눈다.

한 칸씩 — 무엇이 오나6칸
  1. application_layer/MVVM
    상태를 갖는 동작(State 조립 · 세션 보관 · 시그널 수신)은 VM 3변종에만 온다. UseCase 는 무상태 plain class.
  2. use_case/MVVM
    Model 의 관문 — command·query 통합, Either 를 그대로 돌려준다(새 raise 를 만들지 않는다).
    이름화면이 아니라 도메인 개념 단위로 짓는다 — 여러 VM 이 한 UseCase 를 공유한다.
  3. view_model/MVVM
    요청마다 view 가 만드는 VM — 화면 하나의 상태 주인. build() 가 State 를 조립하고, 조회 실패는 BadRequestResponse 로 올린다.
    이름<화면>_vm.py · <화면>VM — <화면>_view_vm ✗
  4. state/MVVM
    frozen dataclass — 템플릿이 읽는 유일한 입력. 액션 실패는 error 필드(에러 2채널).
    이름_view_state.py ✗ · _state 접미 필수.
  5. shared_state/MVVM
    화면·조각 사이에 공유되는 값 — 세션 매핑으로 산다. 바뀌면 응답 HX-Trigger 로 보는 조각이 다시 요청한다.
  6. service/MVVM
    헤드리스 VM — 시그널·비화면 요청이 구동한다. 시그널 연결은 root_initializer 몫.
infra_layer/DataSource · Repo · 수동 SDK계약
목적

데이터가 web 바깥(백엔드 JSON API)과 오가는 자리다. DataSource 는 같은 프로세스 안 ApiClient 로 엔드포인트를 불러 도메인 엔티티를 직접 돌려주고, Repo 는 safe_api_call 로 모든 예외를 정규화해 Either(Right = 성공)를 돌려준다.

들어오는 것

평면 — 개념 분할 없이 종류 3폴더(data_source/·repository/·service/). 로컬 저장 층은 없다(web 은 매 요청 서버에서 다시 조회한다).

안 들어오는 것

백엔드 모델·서비스 import(IM25) · common/network 밖 HTTP 호출과 DataSource 밖 API URL 리터럴(IM27) · repository 인터페이스 · DTO 계층.

이 모양이 된 까닭

계약은 URL + JSON 뿐이다. 엔드포인트 근거는 G1 직후 기계로 절단한 server-contract.json(동결 OpenAPI 의 명세 인용분)이고, 필요한 API 가 없으면 가정 계약으로 짓고 실제 API 는 /dddjango 로 요청하라고 안내한다.

「주문 목록」 하나를 끝까지 따라간다 — 내려갔다가 값만 올라온다

GET /orders/ 요청 하나가 왼쪽 열을 따라 내려가 같은 프로세스의 백엔드 JSON API 를 부르고, 오른쪽 열을 따라 올라와 HTML 이 된다. 상자에 적힌 것은 1 장 트리의 폴더·파일 이름 그대로다(order·order_list 는 예시).

읽는 요령 — 아래로 가는 화살표는 «아는» 방향이다. view 는 VM 을, VM 은 UseCase 를, UseCase 는 Repo 를 안다. 거꾸로 아는 일은 없다. 위로 올라오는 것은 값(엔티티 · Either · State · HTML)뿐이다.

상자와 경로를 누르면 1장 트리의 그 행으로 간다.

연결 — 요청이 오기 전에 이미 놓여 있다
  1. ·
    호스트 settings · 루트 urls — Coordinator G0 «Django 연결 설정 점검»연결
    INSTALLED_APPS "web" · TEMPLATES(DIRS web/ · builtins · context_processors)
STATICFILES_DIRS 접두 튜플 · MIDDLEWARE RootRequestHandler
include("web.urls") · handler404/500 · ALLOWED_HOSTS "testserver"

    빠진 줄은 G0 보고에 보이고 승인받은 뒤 Coordinator 가 넣는다 — 에이전트가 아니라 진행자 몫이다.

A · 내려가는 길 — GET /orders/
  1. ①
    셸
    path("", include("web.application.order.order_router"))   # BC 네임스페이스 = app_name

    URL 조립만 한다 — 화면 path 리터럴은 각 BC router 에 있다.

  2. ②
    도메인
    app_name: str = "order"
class OrderRoutes: LIST: str = "order:list"
path("orders/", order_list_view, name="list")

    URL path·name 의 단일 출처. navigator 는 이 상수만 쓴다.

  3. ③
    MVVM
    def order_list_view(request: HttpRequest) -> HttpResponse

    함수 view — VM 을 만들어 build() 하고 render 한다. 판단·가공은 없다.

  4. ④
    MVVM
    OrderListVM().build() -> OrderListState   # Left 면 BadRequestResponse 를 올린다

    request 를 모른다 — 세션은 매핑으로, API 신원은 root_request_handler 가 심은 contextvar 로 간다.

  5. ⑤
    MVVM
    OrderUseCase().get_orders() -> Either[BadRequestResponse, list[Order]]

    Model 의 관문 — Repo 의 Either 를 그대로 넘기거나 조합한다.

  6. ⑥
    계약
    return safe_api_call(lambda: self._remote.get_orders())

    모든 예외를 BadRequestResponse 로 정규화해 Right = 성공.

  7. ⑦
    계약
    data: object = self._client.get("/api/v1/orders")   # URL 근거: server-contract.json

    in-process ApiClient — 같은 프로세스 안 HTTP. 백엔드 코드를 import 하지 않는다.

B · 올라오는 길 — 값만 돌아온다
  1. ⑧
    도메인
    [Order.from_json(item) for item in json_field(data, "orders", list)]

    JSON 을 도메인 엔티티가 직접 파싱한다 — DTO 가 없다.

  2. ⑨
    계약
    Right(value=[Order, …])  |  Left(value=BadRequestResponse(…))

    실패도 값으로 돌아온다 — 성공만 꺼내고 실패를 버리는 코드는 금지.

  3. ⑩
    MVVM
    @dataclass(frozen=True, slots=True, kw_only=True)
class OrderListState: rows: tuple[OrderRowState, ...]; detail_href: str

    템플릿의 유일한 입력. href 도 State 가 준다(navigator 경유).

  4. ⑪
    MVVM
    {% extends "root/scaffold/view/root_view.html" %}
{% include "application/order/presentation_layer/section/order_list_rows_section.html" %}

    페이지 템플릿만 셸을 extends 한다. 색·간격은 foundation 변수로만.

  5. ⑫
    MVVM
    <section id="order-list-rows">{% for row in state.rows %}…{% endfor %}</section>

    HTMX 부분 교체 단위 — 조각 응답도 같은 section 을 그린다. 오류 조각은 200 으로 돌려준다.

  6. ⑬
    셸
    <script src="{% static 'web/htmx/htmx.min.js' %}" defer></script>

    문서 셸 — htmx core · app_theme.css · {% block scripts %}.

기존 코드 — 면제가 아니라 빚

게이트는 이번 작업이 들인 위반만 잡는다. 기존 위반은 G0 빚 스캔이 다루고, 이번 요청이 손대는 파일과 그 파일을 부르는 곳의 빚만 묻는다 — «지금 정리(권장) / 사유와 결정 출처를 적고 미룸 / 리팩토링 입구로 따로 정리». 이번 결과를 해치는 위반은 미룰 수 없다. 정리는 기능 앞 슬라이스 0 에서 동작 그대로 하고, 정리 앞뒤로 기존 테스트를 돌려 새 실패가 없는지 본다. 단위 하나를 통째 정리하려면 /dddjango-web:refactor <단위>.
