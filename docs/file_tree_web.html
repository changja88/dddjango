Model이 없다 — 화면이 한 폴더, 지식은 한 방향

1장표준 파일트리 2장흐름 3장격리·백스톱
web/ 표준 트리 v3.1 — 값의 정본: discipline-web-houserules references/final.md §1

왼쪽이 파일 트리, 오른쪽이 설명이다. 파트를 누르면 그 아래로 트리가 펼쳐지고, 줄을 누르면 오른쪽의 그 칸으로 간다. 파트 순서는 요청이 들어와 나가는 순서다 — 셸 → 영역 → 화면 → 계약, 그다음이 시각 재료다. 분할 축은 셋 — 영역 1차 → 화면 개념 1차 → 종류 폴더 2차. 구역은 색으로 말한다 — MVVM 화면 삼총사 · 계약 client · 시각 design_system·static · 회색은 셸. 표식 WS·WI·WN·WP 는 그 행을 지키는 백스톱 패밀리, D번호 는 확정 결정이다 — 호버하면 근거가 뜬다.

목적

이 폴더 하나가 대상 프로젝트의 웹 표현계층 전부다. 저장소 최상위에서 백엔드 표준 트리(application/·framework/)와 공존하며, 두 세계는 트리 위치로 기계 구분되고 연결은 실물 API 계약(URL+JSON)뿐이다.

web 은 «내부의 외부 클라이언트»다 — Model 이 없다. 같은 저장소에 살지만 백엔드 BC 의 domain·use_case·infra 를 소유하지도 import 하지도 않는다. dddart 검증 판형의 현지화이되, BC·DDD 개념은 전부 덜어냈다 — 분할 축은 도메인 경계가 아니라 내비게이션 영역이다.

파일트리가 곧 규약이다 — 어떤 파일을 어디에 어떤 이름으로 만드는지가 이 플러그인의 핵심 강제이고, 그 기계 판별 가능 부분을 백스톱 4패밀리(WS·WI·WN·WP)가 게이트에서 지킨다.

들어오는 것

일곱 가지 — urls.py · apps.py · base/ · <screen_area>/(여럿) · client/ · design_system/ · static/. 컨테이너 최초 생성 때 골격을 전부 만든다 — 폴더는 무조건, 코드는 필요할 때만.

안 들어오는 것

test/ — web 트랙은 자동 테스트를 두지 않는다. test_*.py·빈 테스트 파일도 금지다. 검증 채널은 사용자 육안 + 결정적 백스톱 + 규율 감사 셋이다.

루트 직속의 화면 파일·유틸 모듈. 화면은 반드시 <screen_area>/<view>/ 안이고, 공용 조각은 widget·component 로 판별해 들어간다 — «어디에도 못 넣는 파일»이 생기면 트리가 아니라 판별이 틀린 것이다.

이 모양이 된 까닭

dddart 의 «표준 트리가 곧 규약» 판형이 운영에서 검증됐고(D11 — 전수 현지화), web 은 거기서 Model·BC·상주 상태·테스트를 뺀 것이다. 뺀 자리마다 이유가 결정 대장에 있다 — Model 은 실물 계약 소비(D5)로, 상주 상태는 요청 구동(D6)으로, 테스트는 «사용자가 항상 본다»로 대체됐다.

한 칸씩 — 무엇이 오나5칸
  1. web/셸
    일곱 가지만 온다 — urls.py·apps.py·base/·<screen_area>/·client/·design_system/·static/. 여덟째는 없다.
    규칙컨테이너 최초 생성 시 골격 완비 — urls·apps·base·tokens·component/·static 3칸을 비어 있어도 전부 만든다. 마커: Python 패키지는 __init__.py, HTML 전용 폴더는 .gitkeep
    이름고정 이름 web/ — 백엔드 트리와 최상위에서 형제다. 호스트 배선(INSTALLED_APPS·TEMPLATES·STATICFILES·ROOT_URLCONF include·testserver)은 커맨드 Phase 0 소관.
  2. urls.py셸
    전 영역 urls 를 include 로 합산만 한다. 자기 path 리터럴을 새로 만들지 않는다 — 영역 리터럴은 각 <screen_area>/urls.py 가 소유한다.
    규칙합산 전용 — 여기에 화면 path 가 보이면 리터럴 거처 위반(§5④)
    이름고정 이름. Django 관례 그대로 — 발명하지 않는다.
  3. apps.py셸
    AppConfig 클래스 WebConfig 하나. 부팅 훅을 여기에 쌓지 않는다 — web 은 요청 구동이라 부팅 때 할 일이 없다.
    이름고정 이름 · 클래스 WebConfig 고정.
  4. base/셸
    base.html 하나로 시작한다. 공통 문서 골격의 거처 — 다른 파일이 먼저 생기면 판별이 틀린 것이다.
    이름고정 이름 폴더.
  5. base.html셸
    «거의 빈» 규범이다 — 공통 문서 골격(<html>·<head>)·내비 셸·전역 게이트만 오고 화면 어휘가 등장하지 않는다. {% extends %} 를 받는 유일한 템플릿 층이다.
    규칙무엇이 base 에 «들어가도 되는가»의 판별 절차는 undecidable-web.md §6 — 에이전트 재량이 아니다
    이름고정 이름. layout.html ✗ · _base.html ✗ — Django 관례 낱말 그대로.
<screen_area>/내비게이션 영역MVVM
목적

전역 내비에서 한 묶음으로 노출되는 단위다 — 도메인 경계도, 백엔드 BC 경계도 아니다. 사용자가 «주문», «정산» 하고 부르는 화면 묶음 하나가 폴더 하나다.

영역 신설·귀속 판정은 에이전트 재량이 아니다 — 커맨드 G0 게이트의 배치축 3선택(undecidable-web.md §4)으로 사용자가 확정한다.

들어오는 것

직속에 오는 것은 셋뿐 — urls.py · 화면 개념 폴더(<view>/) · widget/. 신규 영역은 urls.py + widget/ 골격으로 시작한다.

안 들어오는 것

그 외 직속 파일 전부(마커 __init__.py·.gitkeep 만 예외) · 영역 중첩(1단이다) · 빈 영역. 영역·화면 이름에 컨테이너명(web·base·client·design_system·static)과 종류명(view·view_model·state·form·section·widget)을 쓰지 않는다.

이 모양이 된 까닭

dddart 의 BC 1차 축을 내비게이션 영역으로 치환했다 — web 에 도메인 경계가 없으니 사용자가 실제로 오가는 화면 묶음이 유일하게 안정적인 1차 축이다. 영역 직속을 셋으로 잠근 것은 «영역이 잡동사니 서랍이 되는» dddart 실측 병의 예방이다.

한 칸씩 — 무엇이 오나4칸
  1. <screen_area>/MVVM
    내비 묶음 하나 = 폴더 하나. 직속은 urls.py·<view>/·widget/ 셋뿐이다.
    규칙중첩 금지(1단) · 빈 영역 금지 · 신설·귀속은 G0 배치축 3선택 — 재량 아님
    이름내비 어휘로 짓는다 — orders/ ✔ · order_views/ ✗(종류명) · web_orders/ ✗(컨테이너명).
  2. urls.pyMVVM
    영역 path·name 리터럴의 단일 출처. 페이지는 name="<view>", HTMX fragment 는 name="<view>_<조각>". 그 외 어디서든 — 템플릿 href·hx-get·redirect — {% url %}/reverse 로 이름만 참조한다.
    규칙리터럴 거처 2곳 원칙(§5④)의 web 쪽 절반 — 나머지 절반은 client 모듈(BC API URL)
    이름고정 이름 · name 은 화면 개념과 같은 철자다.
  3. widget/MVVM
    영역 재사용 조각의 거처 — 영역 수준이다. 화면 개념 폴더 안에 widget/ 을 만들지 않는다. 화면 전속 조각은 그 화면 section/, 영역 재사용 조각만 여기.
    규칙입장 판별 — 재사용 + BC 어휘 보유면 widget, 어휘가 없으면 design_system 승격(판별 순서는 architecture-web §2 단독 소유)
    이름고정 이름 폴더.
  4. <widget>.htmlMVVM
    화면 비전속 조각 — 명시 context 만 받는다. {% include %} 로만 합성되고 extends 없는 조각이다.
    규칙타 영역 include 금지(§5⑦) — 교차 재사용은 BC 어휘를 탈피해 design_system 승격 경유 · 복제 금지 · 탈피 불가면 설계 반송
    이름view 이름 금지 — order_status_badge.html ✔ · order_list_badge.html ✗(화면 이름이 박히면 전속이라는 뜻이라 section 이어야 한다).
<view>/화면 개념 — 요청 구동 MVVM 삼총사MVVM
목적

화면 개념 하나가 폴더 하나다 — 예: order_list/. 첫 화면부터 종류 4폴더(view/·view_model/·state/·section/)로 시작하고, 영역 직속에 화면 파일을 평면으로 두는 단계는 없다.

요청 구동 MVVM — 지식은 view → VM → client 한 방향이고, 상주 상태·구독(watch)이 없다. 요청이 오면 조립하고, 응답이 나가면 버린다. 갱신 표준은 HTMX 부분 재렌더 — 페이지가 아니라 section 조각이 다시 그려진다.

들어오는 것

종류 폴더 다섯 — view/(진입+페이지 템플릿) · view_model/ · state/ · form/(조건 생성) · section/. 삼총사 + 페이지 템플릿은 같은 접두 1:1:1:1 대응이다.

안 들어오는 것

화면 폴더 안의 widget/ — widget 은 영역 수준이다. 두 번째 화면 개념 — 다른 개념이 등장하면 기존 폴더에 section·state 를 얹지 말고 새 <view>/ 폴더다(식별·판별은 undecidable-web.md §5). HTTP 호출 코드 — client 전속이다.

이 모양이 된 까닭

dddart 의 view·view_model·state 삼총사를 그대로 가져오되(D6 — «장고 web 도 MVVM 이 표준이라면 최대한 dddart 를 차용»), Flutter 의 상주 ViewModel·구독을 요청 구동으로 바꿨다 — HTTP 는 요청마다 죽는 세계라 상태를 들고 있을 곳이 없고, 들고 있으려는 순간 세션·캐시라는 새 문제를 산다. 부분 갱신은 Flutter 의 rebuild 대신 HTMX 부분 재렌더가 같은 자리를 진다.

한 칸씩 — 무엇이 오나12칸
  1. <view>/MVVM
    화면 개념 1차. 신규 화면은 종류 4폴더 전부로 시작한다 — form/ 만 입력 form 이 생길 때 만든다.
    규칙같은 개념은 위치가 달라도 같은 철자·어순 — order_list ↔ list_order 금지. 판별 배정은 undecidable-web §5
    이름화면 개념으로 짓는다 — order_list/ ✔ · list/ ✗(개념이 아니라 종류) · 종류명·컨테이너명 금지.
  2. view/MVVM
    진입 코드와 페이지 템플릿이 병치되는 폴더 — 화면의 «입구»는 한 폴더에서 함께 읽힌다.
    이름고정 이름 종류 폴더.
  3. <view>_view.pyMVVM
    진입점 — URL 바인딩·VM 호출·render·fragment 분기를 소유한다. 함수 뷰 고정(CBV 아님) — 주 이름은 동명 함수 order_list_view. 표시 판정은 여기 없다 — VM 것이다. 가벼운 흐름 제어(인증 리다이렉트·fragment 분기)만 온다.
    규칙view 는 VM 만 호출한다(§5⑥) — client·HTTP 직접 호출 금지
    이름접두 <view> 는 이 파일 stem 에서 _view 를 뗀 것 — order_list_view_view_model.py 류 접두 오염 금지.
  4. <view>.htmlMVVM
    페이지 템플릿. {% extends "base.html" %} 하는 유일한 템플릿 층이고, section·widget·component 를 {% include %} 로 합성한다. state 만 읽는다 — VM 메서드 호출·client 접근 금지.
    규칙상속 채널은 base.html extends 하나 · 합성 채널은 include 하나 — 커스텀 templatetags 신설 금지
    이름view 와 동일 접두 — order_list.html ✔.
  5. view_model/MVVM
    표시 판정과 조립의 거처. 골격 완비 대상 — 비어 있어도 만든다(__init__.py 마커).
    이름고정 이름 종류 폴더 — vm/ ✗ 축약 금지.
  6. <view>_view_model.pyMVVM
    VM — client 를 호출하고 응답을 표시 상태로 조립한다. 클래스 OrderListViewModel(모듈 수준 조립 함수 허용). 검사 방향은 VM 기준 — VM 이 존재하면 같은 접두의 view·state·페이지 템플릿이 대응해야 한다. 상태 조립이 필요 없는 정적 화면(약관·안내)은 view+템플릿만으로 허용된다.
    규칙HTTP 를 직접 부르지 않는다 — client 경유(§5②) · 역방향 참조 금지(§5⑥)
    이름접미 전체 표기 — _vm.py ✗. 접미 판별은 긴 것 우선 — _view_model.py 는 view_model 종류다.
  7. state/MVVM
    표시 상태의 거처. 요청마다 조립되고 응답과 함께 버려진다 — 상주하지 않는다.
    이름고정 이름 종류 폴더.
  8. <view>_state.pyMVVM
    표시 상태 dataclass OrderListState — 템플릿이 읽는 유일한 것이다. view 에서 context dict 를 직접 조립하는 브라운필드 관행의 표준 대체다(§8 교정 사전).
    규칙예외 하나 — Django Form 1종은 state 필드로 허용된다(입력 화면의 오류 재표시用) — 그 외 프레임워크 타입 반입 금지
    이름클래스 OrderListState — 파일명의 PascalCase 대응.
  9. form/MVVM
    조건 생성 종류 폴더 — 입력 form 이 있는 화면만 만든다(골격 완비 비대상, exception.py 판형). 읽기 전용 화면엔 이 폴더가 없는 것이 사실이다.
    이름고정 이름 종류 폴더 — 전역 forms.py 모음 ✗(§8 교정 사전).

    입력 검증 Django Form OrderListForm. 검증 실패는 오류를 state 에 담아 같은 조각을 다시 그린다 — 별도 오류 페이지를 만들지 않는다.
    이름view 와 동일 접두 · 클래스는 PascalCase 대응.

client/계약 소비 — in-process HTTP계약
목적

백엔드와 만나는 유일한 칸이다. web 은 같은 프로세스에 살지만 마치 외부처럼 백엔드 driving_layer 의 api 표면을 URL+JSON 으로만 소비한다 — django.test.Client 로 네트워크 없이 in-process HTTP 를 쏜다(D7).

BC 1차 — 계약을 제공하는 백엔드 BC 하나가 폴더 하나다. 같은 BC 의 capability 가 늘면 폴더가 아니라 파일이 는다.

들어오는 것

<capability>_client.py(여럿) · response/ · exception.py(조건 생성). 신규 BC 폴더는 client 파일 + response/ 골격으로 시작한다.

안 들어오는 것

application.·framework. import — 0 이다. driving_layer 의 schema·타입 import 도 금지다(§5①). 백엔드 서버렌더 페이지·admin·내부 경로 호출(§5③). 가정 계약 — 필요한 API 가 없으면 만들어 내지 말고 «/dddjango 로 발주»를 안내한다.

이 모양이 된 까닭

사용자 확정(D7) — «파이썬 코드로 직접 부르는 게 아니라, 같은 프로젝트에 있지만 마치 외부에 있는 것처럼 driving_layer 의 api 를 호출한다. 절대 다른 건 호출 금지. 백스톱으로도 있어야 한다.» import 한 줄이 생기는 순간 계약이 코드 결합으로 바뀌어 «내부의 외부 클라이언트»가 그냥 내부가 된다. dddart 의 safeApiCall·Either 계약은 web 에 없다 — 같은 프로세스라 전송 실패 축이 없고, 계약 오류는 exception.py 표현 하나로 충분하다.

한 칸씩 — 무엇이 오나6칸

    API 호출 코드의 전속 칸. view·VM·템플릿에서 HTTP 를 직접 수행하면 위반이다 — VM 이 client 를 호출하고, view 는 VM 만 호출한다.
    규칙입장 판별 대상이 아니다 — API 호출 코드는 언제나 여기다(§5②)
    이름고정 이름 컨테이너.
  2. <bounded_context>/계약
    계약을 제공하는 백엔드 BC 이름 그대로의 폴더. capability 마다 폴더를 쪼개지 않는다.
    이름백엔드 application/<bc>/ 와 같은 철자 — 계보가 이름으로 보인다.

  5. <response>_response.py계약
    web 소유 응답 모델 OrderSummaryResponse — 계약 JSON 을 자기 모델로 받는다. 백엔드 schema 를 import 하면 계약이 코드 결합이 된다.

    계약 오류 표현 *Exception 모음 — 첫 계약 오류 표현이 필요할 때 생성한다(조건 생성). VM 은 이 표현을 받아 표시 상태의 오류로 바꾼다.
    이름고정 이름 — 주 클래스 규칙의 명시 예외(모음 파일).

격리 7규칙 — §5 ①~⑦
① 백엔드 import 0
web/** 에서 application.·framework. import 금지 — driving_layer 의 schema·타입 import 도 금지다. 두 세계의 계약은 URL+JSON 뿐이다. 왜 — import 한 줄이 생기는 순간 계약이 코드 결합으로 바뀐다. 필요한 API 가 없으면 «/dddjango 로 발주»를 안내한다 — 가정 계약 금지.
② API 호출은 client/ 전속
view·VM·템플릿에서 HTTP 를 직접 수행하지 않는다. VM 이 client 를 호출하고, view 는 VM 만 호출한다. 왜 — 계약 소비 지점이 한 칸이어야 계약 변경이 한 칸에 갇힌다.
③ api 표면 패턴만
client 가 부르는 URL 은 백엔드 driving_layer api 표면뿐 — 서버렌더 페이지·admin·내부 경로 호출 금지. 왜 — 화면이 화면을 부르면 계약이 아니라 스크래핑이다.
④ 라우트 리터럴 거처 2곳
web 자신의 path·name 은 urls.py 뿐(영역 리터럴은 <screen_area>/urls.py, web/urls.py 는 합산만). BC API URL 은 그 계약의 client 모듈이 유일 거처. 그 외 어디서든 {% url %}/reverse 이름 참조만. 왜 — 흩어진 URL 문자열은 깨진 링크의 온상이다.
⑤ D12 순수성 — JS 는 htmx 하나
커스텀 .js 신설 금지 · 타 라이브러리 vendored 추가 금지 · inline <script> 금지. 동작은 HTMX 속성과 CSS 로 표현하고, 표현 불가한 동작 요구는 우회 스크립트가 아니라 설계로 반송한다.
⑥ 지식은 한 방향
view → VM → client — 역방향 참조(client 가 VM 을, VM 이 view·템플릿을 아는 것) 금지. 템플릿은 state 만 읽는다 — VM 메서드 호출·client 접근 금지, widget 에는 명시 context 만. 왜 — 역방향이 생기면 요청 구동 MVVM 의 교체 가능성이 죽는다.
⑦ 수평 격리
타 영역 widget {% include %} 금지. 교차 재사용은 BC 어휘를 탈피해 design_system 승격 경유 — 탈피 불가면 설계 반송, 복제 금지. 합성 채널은 include 하나(커스텀 templatetags ✗) · 상속 채널은 base.html extends 하나. 왜 — 수평 결합은 영역 경계를 무의미하게 만든다.
