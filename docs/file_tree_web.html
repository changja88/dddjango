dddjango-web 플러그인 · 표준 파일트리 · 확정 — v0.1.0(08-23)부터 현행

Model이 없다 — 화면이 한 폴더, 지식은 한 방향

web은 «내부의 외부 클라이언트»다. 같은 저장소의 web/에 살지만 백엔드 BC의 실물 API 계약(URL+JSON)만 소비하고, domain·use_case·infra를 소유하지도 import하지도 않는다. 화면 하나는 요청 구동 MVVM 삼총사(view·view_model·state)가 사는 한 폴더이고, 갱신 표준은 HTMX 부분 재렌더다. 값의 단일 출처는 discipline-web-houserules references/final.md — 이 문서는 그 읽기 지도다.

1장 · 표준 트리 v3.1

web/ — 백엔드 트리와 공존하고, 계약으로만 만난다

대상 프로젝트 최상위에서 web/은 백엔드 표준 트리(application/·framework/)와 공존한다. 분할 축은 셋 — 영역(<screen_area>) 1차 → 화면 개념(<view>) 1차 → 종류 폴더 2차. 오른쪽 배지는 그 행을 지키는 백스톱 패밀리(WS 구조·골격 / WI 격리 / WN 명명 / WP 순수성)와 출처 결정(D번호)이다.

셸 — 컨테이너·배선 화면 — 요청 구동 MVVM 계약 — client · in-process HTTP 시각 — design_system · static

│ ├─ view_model/<view>_view_model.py VM — client 호출·표시 상태 조립. 클래스 OrderListViewModel(모듈 수준 조립 함수 허용). 접미 전체 표기 — _vm.py 축약 금지 WNWI
│ ├─ state/<view>_state.py 표시 상태 dataclass OrderListState — 템플릿이 읽는 유일한 것. 상주 상태·구독 없음(요청마다 조립) WN
│ ├─ form/<view>_form.py조건 생성 입력 검증 Django Form OrderListForm — 입력 form이 있는 화면만 생성(골격 완비 비대상, exception.py 판형) WN
│ └─ section/<view>_<section>.html 화면 전속 조각 · HTMX 재렌더 단위 — 소속 view 접두 필수(order_list_filter_bar.html). 받은 state 렌더만으로 성립하는 조각이 온다 WN
└─ widget/<widget>.html영역 수준 영역 재사용 조각(BC 어휘 보유·화면 비전속) — 이름에 view 이름 금지·명시 context만 전달. 화면 폴더 안에 widget/을 만들지 않는다. 타 영역 include 금지(§5⑦) WNWI

└─ <bounded_context>/백엔드 BC명 계약을 제공하는 백엔드 BC 하나가 폴더 하나 WS

   ├─ response/<response>_response.py web 소유 응답 모델 OrderSummaryResponse — 백엔드 schema를 import하지 않고 계약 JSON을 자기 모델로 받는다 WNWI

├─ foundation/tokens.css고정 이름 색·타이포·간격 토큰의 단일 출처(--color-*·--space-*) — 화면 CSS는 var()로만 참조 WN
└─ component/<부품군>/<component>.html BC 어휘 없는 순수 부품 — 부품군 1차·직속 파일 금지·정크드로어 군 금지. 부품군 폴더 = 파일 접미사(button/ 안은 *_button.html) WSWN

├─ css/<이름>.css 화면 CSS — 시각 값은 tokens.css의 var() 참조(색·크기 리터럴은 교정 대상) WN
├─ js/htmx.min.js원명 그대로 vendored htmx 단일 — 커스텀 .js·타 라이브러리·inline <script> 전부 금지. HTMX 속성·CSS로 표현 불가한 동작은 설계로 반송 WPD12
└─ images/<이름>.<확장자> 시안 이미지 착지 칸 — 절단 도구가 snake_case로 정규화해 착지, fetch 도구·asset-manifest 배선(에셋 규율은 implementation-ui 소유) WN

골격 완비비어 있어도 형태를 유지한다

  • web/ 최초: urls·apps·base·tokens·component/·static 3칸 전부 생성
  • 신규 영역: urls.py + widget/
  • 신규 화면: 종류 4폴더 전부 — form/만 조건 생성
  • 마커: Python 패키지는 __init__.py, HTML 전용 폴더는 .gitkeep
  • test/ 없음 — web 트랙은 자동 테스트를 두지 않는다(육안 + 백스톱 + 규율 감사)

명명종류는 폴더가, 접미사가 재확인

  • 파일명 snake_case — .py는 주 클래스 하나(파일명의 PascalCase 대응)
  • 삼총사+페이지 템플릿은 같은 접두 1:1:1:1 — 접두는 view 파일 stem에서 _view를 뗀 것
  • 검사 방향은 VM 기준 — 정적 화면(약관·안내)은 view+템플릿만 허용
  • 같은 개념은 위치가 달라도 같은 철자·어순 (order_list ↔ list_order 금지)

입장 판별조각은 어디에 두나

  • 자기 표시 상태 조립 필요 → 새 <view>/ 삼총사
  • 한 화면 전속(받은 state 렌더만) → 그 화면 section/
  • 영역 재사용 + BC 어휘 보유 → widget/
  • 재사용 + BC 어휘 없음 → design_system/component/
  • 판별 순서는 architecture-web §2 단독 소유 — 회색지대 6종은 undecidable-web

2장 · 흐름

「주문 목록」 하나를 끝까지 따라간다 — 두 번 지나간다

첫 진입은 페이지 전체를, 이후 갱신은 section 조각만 다시 그린다. 두 경로 모두 지식은 view → VM → client 한 방향이고, 백엔드와는 계약(URL+JSON)으로만 만난다.

A · 최초 진입 GET /orders/ — 페이지 전체 렌더

1web/urls.py → orders/urls.pyinclude 합산 → 영역 라우팅. path("", order_list_view, name="order_list") — 리터럴은 여기가 유일 거처
2view/order_list_view.py함수 뷰 진입 — 요청을 받고 VM을 호출한다. 표시 판정을 여기서 하지 않는다(가벼운 흐름 제어만)
3view_model/order_list_view_model.pyVM이 client를 호출하고 응답을 표시 상태로 조립한다 — HTTP를 직접 부르지 않는다
4client/order/order_query_client.pydjango.test.Client로 in-process HTTP — 백엔드 driving_layer api 표면만. 같은 프로세스지만 마치 외부처럼 URL+JSON으로만 만난다. python import 호출 금지(D7)
5client/order/response/계약 JSON → web 소유 응답 모델(OrderSummaryResponse)로 변환. 계약 오류는 exception.py의 표현으로
6state/order_list_state.pyVM이 응답을 표시 상태 dataclass로 조립해 view에 돌려준다 — 요청이 끝나면 상태도 끝(상주 없음)
7view/order_list.htmlrender() — 페이지 템플릿이 {% extends "base.html" %} 하고 state만 읽으며 section·widget·component를 {% include %}로 합성한다
8design_system · statictokens.css의 var()가 시각 값을, static/js/htmx.min.js 하나가 동적 속성을 공급한다 — 커스텀 JS 없이 완성

B · 필터 적용 HTMX POST — section 조각만 재렌더

1section/order_list_filter_bar.htmlhx-post="{% url 'order_list_filter_bar' %}" — 라우트는 이름으로만 참조, 대상은 자기 조각(hx-target)
2view/order_list_view.py같은 view의 fragment 분기가 받는다 — fragment 라우트도 orders/urls.py의 name="order_list_filter_bar"
3form/order_list_form.py입력 검증 — Django Form(조건 생성된 화면만). 실패면 오류를 state에 담아 같은 조각을 다시 그린다
4VM → client → stateA-3~6과 동일한 한 방향 — 경로가 짧아질 뿐 규율은 같다
5render(section)페이지가 아니라 order_list_filter_bar.html 조각만 렌더해 반환 — HTMX가 그 자리를 갈아끼운다

필요한 API가 없으면? web에서 백엔드를 고치거나 계약을 가정하지 않는다 — «/dddjango로 발주»를 안내하고 멈춘다. 계약이 생긴 뒤 client부터 다시 잇는다.

3장 · 격리 · 백스톱

기계가 지키는 것 — 규율 7 + 검사 패밀리 4

격리 규칙(§5)의 기계 판별 가능 부분은 결정적 러너 scripts/backstop.py가 게이트에서 검사한다. 발견은 전부 blocker — 일괄 반송이다. 러너가 못 보는 의미 판별 6종(view/section·화면 전속·BC 어휘·영역 귀속·두 번째 개념·base «거의 빈»)은 undecidable-web.md가 판별 절차의 단일 출처다.

격리규칙왜
①web/**에서 application.·framework. import 0 — schema·타입 import도 금지import 한 줄이 생기는 순간 계약이 코드 결합으로 바뀐다 — «내부의 외부 클라이언트»가 그냥 내부가 된다
②API 호출 코드는 client/ 전속 — view·VM·템플릿의 직접 HTTP 금지계약 소비 지점이 한 칸이어야 계약 변경이 한 칸에 갇힌다
③client가 부르는 URL은 백엔드 api 표면 패턴만 — 서버렌더 페이지·admin 호출 금지화면이 화면을 부르면 계약이 아니라 스크래핑이다
④라우트 리터럴 거처 2곳뿐 — web 자신은 urls.py, BC API는 그 client 모듈흩어진 URL 문자열은 깨진 링크의 온상 — 이름 참조만 남긴다
⑤D12 순수성 — 커스텀 JS·inline <script>·타 라이브러리 금지, JS는 vendored htmx 단일표현 불가한 동작 요구는 우회 스크립트가 아니라 설계 반송으로
⑥지식은 view → VM → client 한 방향 — 템플릿은 state만 읽는다역방향 참조가 생기면 요청 구동 MVVM의 교체 가능성이 죽는다
⑦타 영역 widget include 금지 — 교차 재사용은 design_system 승격 경유, 복제 금지수평 결합은 영역 경계를 무의미하게 만든다
