# dddjango 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md`가 해당 runtime에 대한 권위 있는 가이드 사본입니다.
manifest의 homepage는 최신 온라인 가이드(latest-online)를 발견하는 경로이며, 설치 버전의 정본을
대신하지 않습니다. 이 문서는 Claude Code와 Codex 양쪽에서 사용할 수 있습니다.

## 1. 언제 쓰는가

`dddjango`는 **기존 Django 프로젝트의 한 기능**을 비즈니스 요구 정리 → DDD 설계 → TDD 구현으로
진행하는 도구입니다. 주문 취소, 사용 한도 변경, 외부 정산 결과 반영처럼 행위와 결과가 분명한
기능에 적합합니다. 신규 기능도 기존 프로젝트 안에서 시작합니다.

Django 화면 구현은 `dddjango-web`의 대상입니다. 프로젝트 bootstrap이나 “서비스 전체를 DDD로
다시 설계해 줘”처럼 경계가 없는 전면 재설계는 이 가이드의 대상이 아닙니다. 먼저 한 기능의
사용자, 규칙, 보존 계약, 범위를 정하세요.

요청서가 구체적이면 조사와 판단을 돕지만, 긴 작업에서도 질문과 G0·G1·G2 승인 게이트는 남습니다.
모르는 내용을 모두 알아내야 시작할 필요는 없습니다. 확인되지 않은 항목은 `미확정`으로 적으세요.

## 2. 가장 빠른 시작

Claude Code에서는 slash command로 시작합니다.

```text
/dddjango 기존 Django 프로젝트에 회원의 주문 취소 기능을 만들어 줘.
결제 완료·배송 시작 전 주문만 취소할 수 있고, 취소 실패 시 주문·환불 상태는 그대로여야 해.
현행 주문 조회 API 계약을 보존해 줘. 환불 완료 시점은 미확정이야. G0에서 확인해 줘.
```

Codex에서는 사용할 플러그인을 자연어로 지정합니다.

```text
dddjango를 사용해 기존 Django 프로젝트에 회원의 주문 취소 기능을 만들어 줘.
결제 완료·배송 시작 전 주문만 취소할 수 있고, 취소 실패 시 주문·환불 상태는 그대로여야 해.
현행 주문 조회 API 계약을 보존해 줘. 환불 완료 시점은 미확정이야. G0에서 확인해 줘.
```

아래 템플릿을 시작 문장 뒤에 붙여도 됩니다. 예시의 규칙과 경로는 설명용이므로 실제 업무에 맞게
바꾸고, 확인하지 못한 사실은 그대로 복사하지 마세요.

## 3. 30초 최소 요청

꺾쇠괄호를 아는 만큼 채우세요. 관련 없는 조건부 항목은 `해당 없음`, 아직 모르는 항목은
`미확정`이라고 적으면 됩니다.

```text
dddjango를 사용해 기존 Django 프로젝트의 <기능>을 <신규 구현/수정>해 줘.
<사용자/행위자>가 <목적>을 위해 <시작 행동/사건>을 수행하면 <성공 상태>가 되어야 해.
핵심 규칙은 <규칙 2~5개>이고, 실패하면 <사용자에게 보일 결과>이며 <그대로 남을 상태>는 그대로여야 해.
보존할 기존 동작·API·데이터 계약은 <계약 또는 해당 없음/미확정>이야.
핵심 용어는 <용어와 뜻>이고, 그 사실을 소유하는 기존 영역은 <영역 또는 미확정>이야.
조사 evidence는 <관련 코드·문서·테스트 경로 또는 미확정>에 있어.
범위 안은 <포함>, 범위 밖은 <제외>이고, 미확정 항목은 <확인할 내용>이야.
```

Claude에서는 첫 문장의 `dddjango를 사용해`를 `/dddjango`로 바꾸면 됩니다.
이 최소 요청은 G0의 시작점이며, 후속 질문과 기존 영역의 검사를 생략하는 승인이 아닙니다.

## 4. 품질을 높이는 네 가지 작성 원칙

1. **사실과 판단을 구분하세요.** 중요한 항목에만 `사실`, `필수 제약`, `선호`, `미확정`을
   붙이세요. 사실은 관찰·확인한 내용, 필수 제약은 반드시 지킬 조건, 선호는 이유에 따라 다른
   선택을 제안해도 되는 방향입니다. 모든 줄에 라벨을 달 필요는 없습니다.
2. **결과를 사례로 쓰세요.** “안전하게 처리” 대신 이전 상태, 행동, 성공 결과와 실패 뒤 남을 상태를
   적으세요. 경계값과 금지 사례가 있으면 설계와 테스트의 판단 기준이 선명해집니다.
3. **제품 계약과 조사 증거를 구분하세요.** 제품 계약은 현재 지원하기로 승인한 요구, 소비자,
   API·데이터·이벤트 의미입니다. 기존 코드·문서·테스트는 그 계약을 찾는 증거이며, 기존 coverage가
   있다는 사실만으로 현재도 지원해야 하는 계약이라고 확정할 수는 없습니다.
4. **내부 설계보다 도메인 언어와 소유권을 알려 주세요.** “가용 재고”의 뜻, 재고 사실을 소유하는
   영역, 주문이 그 영역에 확인해야 할 내용을 적으세요. 영역을 모르면 설계자가 조사하도록
   `미확정`으로 남기세요.

계약을 종료하거나 약화하려면 지원 종료 근거, rollout 순서, 이미 저장된 데이터와 발행된 이벤트의
처리 방침을 함께 제시하세요. “테스트가 낡았다”는 설명만으로 보존할 계약을 삭제하지 않습니다.

## 5. 복잡한 기능을 위한 권장 요청서

```text
[작업]
기능명 / 신규·수정:
사용자·행위자와 사업 목적:

[성공 시나리오]
사전 상태 → 행동 → 결과 상태:

[규칙과 경계값]
허용/금지 규칙:
같음 포함 여부, 최소·최대·0·null 사례:

[실패와 원자성]
실패 조건 / 사용자에게 보일 결과:
실패해도 변경돼야 할 것 / 그대로여야 할 것:
반드시 함께 성공하거나 함께 취소돼야 할 변경:

[중복·재시도·동시성]
업무상 중요한 경쟁 상황:
동일 요청 재시도·중복 실행·서로 다른 요청의 동시 실행 시 기대 결과:
해당 없음 또는 미확정:

[도메인 언어와 소유권]
핵심 용어와 정의:
어떤 영역·팀이 어떤 사실을 소유하는지:
알려진 기존 영역과 협력 / 미확정:

[외부 효과와 일관성]
응답 전에 끝나야 하는 효과 / 지연 허용 효과:
중복 전달 결과 / 실패 뒤 보상·잔존 상태:
해당 없음 또는 미확정:

[보존·변경·종료할 제품 계약]
승인 요구와 지원 소비자:
API·데이터·이벤트 의미:
호환·지원 종료·deprecation·rollout 근거:
저장 데이터·이미 발행한 이벤트 처리:

[조사 증거와 기존 coverage]
관련 코드·OpenAPI·문서 경로:
배포된 consumer와 기존 테스트 경로:
각 증거가 보여 주는 내용 / 확인할 내용:

[범위]
포함 / 제외:

[제약과 미확정]
필수 제약과 이유·관찰 가능한 완료 조건:
선호:
미확정:
```

모든 항목을 채우는 것이 목적은 아닙니다. 적용되지 않는 항목을 `해당 없음`으로 표시하고,
필수 규칙인지 아직 결정하지 못했다면 `미확정`으로 남기세요. 멱등성 같은 강건성 요구도 업무상
필수인지, 설계 단계에서 검토할 제안인지 구분합니다.

## 6. 규칙·상태 전이·실패 원자성 쓰기

다음처럼 같은 규칙의 허용·금지·경계를 한 묶음으로 쓰면 좋습니다.

| 상황 | 기대 결과 |
|---|---|
| 사용 가능한 포인트 1,000점 → 600점 사용 | 성공, 잔여 400점 |
| 사용 가능한 포인트 1,000점 → 1,000점 사용 | 성공, 잔여 0점 |
| 사용 가능한 포인트 1,000점 → 1,001점 사용 | 거절, 잔액과 사용 내역은 그대로 |
| 0점·음수·null 사용 요청 | 각각 허용/거절 여부와 사용자에게 보일 결과를 명시 |

“주문 생성은 원자적”이라는 말에는 범위를 덧붙이세요. 예를 들어 “재고 부족으로 실패하면 주문,
재고 차감, 결제 요청, 주문 생성 이벤트가 모두 남지 않아야 한다”처럼 변경 단위를 적습니다.
실패 로그처럼 남아야 하는 것이 있다면 별도로 표시하세요.

외부 결제 성공 뒤 내부 저장이 실패하는 상황은 위 예시만으로 결정되지 않습니다. 사용자에게
어떤 상태를 보여 줄지, 환불이나 후속 처리를 허용할지, 언제까지 일관성이 회복되어야 하는지를
알려 주세요. 업무 결정이 없으면 구현 수단을 지정하지 말고 `미확정`으로 둡니다.

## 7. 위험이 있을 때만 보충하기

### 공개 API

지원 소비자와 승인된 method/path, 요청·응답·오류의 필드 및 상태 코드, 호환 조건을 적으세요.
알고 있는 exact shape는 OpenAPI·응답 표본·소비자 계약의 evidence path와 연결하고, 모르는 필드는
추측하지 마세요. 신규·변경 오류 shape를 초기 요청에 적는 것만으로 shape 승인이 끝나지는 않습니다.
특히 공통 오류 schema의 신규 생성·변경은 구체적인 shape와 의미를 제시한 뒤 일반 G1과 별도의
명시 승인을 받는 대상입니다.

### DB·동시성·재시도

깨지면 안 되는 불변식과 경쟁 상황을 적으세요. 예를 들어 “재고가 1개일 때 두 회원이 동시에
구매하면 한 명만 성공하고 재고는 0”입니다. 동일 요청이 재전송될 때 같은 결과를 반환해야 하는지,
새 요청으로 처리해도 되는지와 그 구분에 쓰는 업무상 식별자를 알면 알려 주세요.
어느 변경이 함께 저장되거나 취소돼야 하는지도 명시합니다. 구체적인 락은 설계자가 정합니다.

### 외부 연동·이벤트

응답 전에 완료돼야 하는 효과와 지연을 허용하는 효과를 나누고, 허용 지연을 알면 적으세요.
외부 서비스 실패·시간 초과·재시도·중복 전달 시 남을 상태, 보상 필요 여부, 이벤트 소비자가
관찰해야 할 결과를 알려 주세요. “이벤트를 발행해 줘”에는 이벤트 의미와 소비자도 필요합니다.

### 기존 기능 수정(brownfield)

보존할 실제 계약과 변경할 규칙을 구분하고 관련 코드·계약 문서·테스트의 evidence path를 주세요.
기존 배치 자체가 모든 새 코드의 설계 기준이 되는 것은 아닙니다. 승인 범위의 신규 파일과 기존
파일에 추가·변경하는 코드에는 플러그인 규율을 적용하며, 범위 밖 기존 배치의 이동·개명·재배선은
별도 G0 결정 없이 진행하지 않습니다.

## 8. 플러그인에 맡길 결정

다음은 요청서에서 정답처럼 고정하기보다 설계자가 규칙과 증거를 보고 결정하도록 두세요.

- bounded context(BC)·aggregate·entity/value object 경계
- repository·port·service·use case 클래스명과 파일 트리
- CQRS·event sourcing·saga·outbox 같은 패턴 채택
- `select_for_update` 같은 구체적인 락과 트랜잭션 수단
- 테스트 파일 수·case 수·coverage quota

실제 환경 제약이면 이유와 관찰 가능한 완료 조건을 제시하세요. 예를 들어 “필수 제약: 운영 중인
소비자는 오류 필드 `code`와 `message`에 의존하므로 두 필드의 의미와 타입을 유지해야 한다.
소비자 계약은 <경로>”라고 적습니다. 단순한 기술 취향은 `선호`로 두면 됩니다.

## 9. G0·G1·G2에서 무엇을 검토하는가

### G0 — 문제와 범위 승인

- 행위자·성공·실패·보존 계약과 포함/제외 범위가 맞는지 확인합니다.
- lens는 설계 검토 관점입니다. `ddd`는 항상, 외부 관찰 계약이 생기거나 바뀌면 `api`,
  스키마·인덱스·제약·트랜잭션·마이그레이션이 바뀌면 `db`가 활성화되는지 확인합니다.
- 기존 `.dddjango/...` 기능 폴더를 이어 쓸지 새 기능인지 확인합니다. 기존 영역과 관련되면
  새 영역으로 분리할지, 기존 영역에 포함할지, 설계자에게 맡길지도 확인합니다.
- 대상 영역의 선행 위반 조사와 증거를 보고 지금 정리할지 연기할지 결정합니다. 미룰 수 없다고
  판정된 항목의 이유도 확인하세요. 새로 발견한 작업을 기존 승인에 조용히 끼워 넣지 않습니다.

### G1 — 설계와 영구 테스트 입장 승인

내부 클래스 이름보다 도메인 언어·사실 소유권·불변식·상태 전이·실패·외부 효과·호환 계약이
요구와 맞는지 읽으세요. 리뷰에서 남긴 선택지가 필수 제약과 충돌하지 않는지도 확인합니다.

영구 테스트 입장표는 어떤 테스트 변경을 왜 허용하는지 기록합니다. 보호할 계약과 evidence,
그 테스트만 검출하는 고유 production failure, 기존 권위 coverage와의 중복, 담당 역할과 경로를
확인하세요. 결정은 `add/update/reuse/retain/remove/reject/pending`으로 표시됩니다.
`pending=0`이어야 구현으로 갈 수 있으며, “승인”이라고 답해도 미확정 입장이 없어지지는 않습니다.
기존 보호를 재사용하는 결정도 유효하므로 테스트 개수가 늘어야 좋은 설계인 것은 아닙니다.

pre-gate 결과는 최종 명세에 대한 최신 결과인지 확인합니다. green의 증명 범위는 아래 12절과
같습니다. 신규·변경 오류 shape에 필요한 별도 승인도 일반 설계 승인과 구분하세요.

### G2 — 구현 결과와 증거 승인

승인된 설계·테스트 입장과 실제 코드·테스트 변경이 일치하는지, 성공뿐 아니라 실패·경계·동시성의
승인 사례도 검증했는지 확인합니다. 관련 검증과 전체 suite 결과를 구분하고, baseline의 무관 실패가
있으면 전체 green이라고 읽지 마세요.

최종 명세에 대한 pre-gate 최신성, registry 결과, legacy 잔존·승인 유입·미측정 사각의 별도 보고와
감수 결과를 확인합니다. 테스트 green이나 백스톱 green 하나가 G2 사용자 승인을 대신하지 않습니다.

## 10. 부분 수정과 중단 후 재개

부분 수정은 “바꿀 규칙”과 “보존할 계약”을 나누어 요청하세요. 설계 변경이 있으면 영향받는 검토를
거쳐 G1′에서 바뀐 부분을 다시 승인합니다. 작은 수정이라는 이유만으로 설계·계약 확인이 사라지지
않습니다.

```text
dddjango를 사용해 기존 작업을 이어서 수정해 줘.
작업 폴더: .dddjango/<기존 기능 폴더>/
마지막 승인 위치: <G0/G1/G1′/G2, 대화 또는 기록 위치>
바꿀 규칙: <이전 → 이후>
보존할 계약: <요구·소비자·API·데이터·이벤트 의미>
마지막 승인 이후 변경:
- 코드·스키마·dependency·merge: <변경 내용과 evidence 또는 변경 없음>
- expected result·지원 계약: <변경·지원 종료 여부>
- 테스트 move/split/rename/remove/weaken 및 입장 결정: <변경 여부>
관련 evidence·기존 테스트 경로: <경로>
미확정: <내용>
```

Coordinator는 기존 폴더의 `build_anchor`를 읽어 유지합니다. 요청자가 새 anchor를 선택하거나
제공하는 절차가 아닙니다. 같은 기능의 기록 폴더도 재사용합니다.

마지막 승인은 기록을 찾기 위한 탐색 힌트이며 현재 작업의 재사용 허가가 아닙니다. Coordinator가
현행 `design-spec.md`, contract evidence와 모든 관련 test admission을 다시 확인하고
`pending=0`인지 검증한 뒤 G1′ 생략 여부를 정합니다. 설계 변경이 없는 순수 구현 수정만 생략을
검토할 수 있습니다. 지원 종료, expected result 변경, `move/split/rename/remove/weaken` 또는
입장 결정 자체의 변경이 있으면 G1′을 생략하지 않습니다. 생략 가능한 경우에도 G2 검증은 남습니다.

## 11. 나쁜 요청을 좋은 요청으로 바꾸기

아래는 각각 독립적인 예시입니다. 예시 경로와 규칙은 실제 증거로 바꾸세요.

### 모호한 주문 요청

나쁜 요청: “주문 기능을 DDD로 만들어 줘.”

좋은 요청: “회원이 장바구니를 주문하면 재고가 충분할 때만 주문이 확정돼야 해. 수량은 1 이상이고
가용 재고와 같으면 허용해. 재고 부족이면 주문·재고 차감·주문 생성 이벤트가 남으면 안 돼.
현행 주문 조회 계약은 보존하고 evidence는 `docs/contracts/orders.md`에 있어.
쿠폰·배송 화면은 제외하고 결제 처리 시점은 미확정이야.”

### 내부 클래스를 미리 지정한 요청

나쁜 요청: “OrderAggregate, StockRepository, CheckoutService로 파일을 나눠 줘.”

좋은 요청: “주문 영역은 구매 의사를, 재고 영역은 판매 가능한 수량을 소유하고 있어.
주문 확정 전에 판매 가능 여부를 확인하고, 취소된 주문의 수량은 다시 판매 가능해야 해.
현재 영역은 `application/orders/`와 `application/inventory/`에 있어.
두 영역의 경계·협력 방식은 이 규칙과 기존 계약을 보고 설계해 줘.”

### 테스트 개수·비율 요청

나쁜 요청: “테스트 100개와 coverage 100%를 채워 줘.”

좋은 요청: “잔액보다 큰 차감은 거절되고 잔액·원장은 그대로라는 계약을 보호해 줘.
현재 `tests/billing/test_debit.py`가 무엇을 보호하는지 확인하고, 승인 계약·고유 실패·기존
coverage를 비교해 추가·수정·재사용할 테스트를 설계해 줘. 같은 금액 차감은 허용이야.”

### 기존 규칙 변경 요청

나쁜 요청: “취소 조건을 좀 느슨하게 바꾸고 기존 테스트도 맞춰 줘.”

좋은 요청: “기존에는 결제 전만 취소 가능했지만 이제 결제 완료·배송 시작 전에도 허용하려 해.
배송 시작 후 거절과 주문 조회 응답은 보존해 줘. 승인 요구는 `docs/product/cancel-policy.md`,
기존 coverage는 `tests/orders/test_cancel.py`야. 환불 실패 시 주문 상태와 기존 소비자 rollout은
미확정이므로 먼저 확인해 줘.”

### API·동시성·외부 이벤트가 있는 요청

나쁜 요청: “재고 예약 API에 락과 outbox를 넣어서 안전하게 해 줘.”

좋은 요청: “소비자는 checkout이고 예약 API 계약 후보는 `POST /reservations`야.
가용 재고 1개를 두 주문이 동시에 예약하면 한 주문만 성공해야 해. 같은 요청 식별자의 재시도는
새 예약을 만들지 않아야 하고, 재고 부족이면 예약·차감·예약 이벤트가 남으면 안 돼.
성공 응답 전 예약은 확정돼야 하지만 알림은 1분 이내 전달을 허용해. 이벤트 소비자가 중복 수신해도
업무 처리는 한 번이어야 해. 요청·응답 후보와 소비자 증거는 `docs/contracts/reservations.json`에
있고, 신규 오류 shape와 식별자 재사용 기간은 미확정이야.”

## 12. 완료 시 받는 것과 증명의 한계

한 기능의 `.dddjango/...` 폴더에 스코프, 설계 명세, 리뷰·검증 기록이 모이고, 승인된 범위의 구현
코드와 입장된 테스트 변경, 실행 결과가 제시됩니다. 어떤 계약을 구현했는지, 어떤 검증이 통과했는지,
남은 실패·미측정·승인된 유예가 무엇인지 함께 읽으세요.

| 결과 | 증명하는 범위 | 증명하지 않는 것 |
|---|---|---|
| G1 pre-gate green | 측정 대상인 일부 구조·계약 계획 위반의 예보가 0 | 설계 의미의 정답, 모든 계약 실존·동작, G2 검증 완료 |
| G2 registry green | 고정 anchor 이후 이번 스코프에 귀속된 신규 위반이 0 | 저장소 전체가 clean이라는 보장은 아니며, legacy 잔존·승인 유입·미측정 사각은 별도 보고 |
| 입장된 테스트 green | 검증한 현행 계약 사례가 실행 결과와 일치 | 모든 가능한 결함의 부재, 실행하지 않은 전체 suite의 성공 |

백스톱과 테스트는 서로 다른 범위를 확인합니다. green을 읽을 때는 대상·기준선·실행 결과를 함께
확인하고, 미확정이나 검증하지 못한 부분을 완료로 간주하지 마세요.
