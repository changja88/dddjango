# dddjango 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md`가 해당 runtime에 대한 권위 있는 가이드 사본입니다.
manifest의 homepage는 최신 온라인 가이드(latest-online)를 발견하는 경로이며, 설치 버전의 정본을
대신하지 않습니다. 이 문서는 Claude Code와 Codex 양쪽에서 사용할 수 있습니다.

## 1. 언제 쓰는가

`dddjango`는 기존 Django 프로젝트의 한 기능을 업무 요구 정리 → DDD 설계 → TDD 구현으로
진행하는 플러그인입니다. 주문 취소, 사용 한도 변경, 외부 정산 결과 반영처럼 원하는 행동과
결과가 있는 기능에 사용합니다. 신규 기능도 기존 프로젝트 안에서 시작합니다.

한 요청에는 한 기능을 담습니다. 따로 확인해야 할 결과가 여럿이거나 여러 업무 영역을 크게
바꾸는 일이면 나눠서 요청하세요. 요청이 커질수록 확인할 질문과 멈출 지점도 함께 늘어납니다.
나눈 요청 사이에 먼저 끝나야 하는 작업이 있으면 그 사실을 알려 주세요.

시안 재현 중심의 웹 화면 작업은 `dddjango-web`에 요청하세요. Django admin이나 기존 업무
기능에 포함된 화면 변경은 `dddjango`가 담당하는 경우도 있습니다. 구분이 어려우면 현재 화면과
원하는 변화를 알려 주세요. 플러그인이 기존 코드를 조사해 담당 범위를 안내합니다.

새 프로젝트 구성이나 서비스 전체의 전면 재설계는 이 가이드의 범위 밖입니다.

## 2. 바로 시작

Claude Code에서는 `/dddjango:dddjango`로 시작합니다. 명령은 요청의 맨 앞에 직접 입력합니다.
긴 문서를 붙여 넣을 때도 명령을 먼저 입력한 뒤 붙이거나, 문서는 파일 경로로 알려 주세요.

```text
/dddjango:dddjango 기존 Django 프로젝트에 회원이 배송 시작 전 주문을 취소할 수 있게 해 줘.
```

Codex에서는 사용할 플러그인을 자연어로 지정합니다.

```text
dddjango를 사용해 기존 Django 프로젝트에 회원이 배송 시작 전 주문을 취소할 수 있게 해 줘.
```

조금 더 정해 둔 내용이 있다면 아래 네 묶음 중 아는 내용만 보태세요. 모두 채울 필요는 없습니다.

```text
dddjango를 사용해 기존 Django 프로젝트에서 <기능과 원하는 변화>를 구현해 줘.
대표 성공 결과: <어떤 행동 뒤에 무엇이 보이거나 어떤 상태가 되어야 하는지>
이미 정한 핵심 규칙과 실패 결과: <반드시 지킬 조건, 실패할 때 보일 결과와 남아야 할 상태>
범위: <유지할 기존 동작 / 이번에 바꿀 부분 / 제외할 부분>
```

한 기능과 원하는 변화만으로 시작할 수 있습니다. 규칙을 아직 정하지 못했거나 자료 위치를
몰라도 괜찮습니다. 플러그인이 프로젝트에서 확인할 수 있는 내용을 먼저 조사한 뒤, 사용자가
결정해야 하는 결과를 질문합니다.

범위는 기능과 동작으로 적습니다. “환불 기능은 이번에 제외”처럼 적고, 수정해도 되는 파일이나
건드리면 안 되는 경로의 목록은 적지 않습니다. 파일 단위로 막으면 플러그인이 작업하는 업무 영역의
기존 코드를 표준에 맞게 정리할 수 없습니다. “유지할 기존 동작”은 응답·저장되는 데이터·연동처럼
밖에서 보이는 결과입니다. 기존 폴더 배치는 유지할 동작이 아닙니다.

Claude Code에서는 템플릿 첫 문장의 `dddjango를 사용해`를 `/dddjango:dddjango`로 바꾸면 됩니다.

## 3. 알려 주면 좋은 제품 정보

이번 기능의 결과에 영향을 주고 이미 정한 내용이 있을 때만 보충하세요. 사용자·행위자나 목적도
그에 따라 허용되는 행동이나 결과가 달라질 때 알려 주면 됩니다.

- 성공 전후에 바뀌는 업무 상태와 항상 지켜야 하는 규칙
- 금액·수량·기간의 경계에서 허용하거나 거절할 결과
- 실패할 때 사용자에게 보일 결과와 바뀌지 않아야 할 주문·재고·결제 등의 상태
- 중복 요청·재시도·동시 실행이 생겼을 때 기대하는 결과
- 외부 알림·결제 등이 완료돼야 하는 시점과 실패 뒤 허용되는 업무 상태
- 기존 사용자나 연동 시스템이 계속 이용할 동작과 의도적으로 바꿀 동작

예를 들어 “사용 가능한 포인트가 1,000점이면 1,000점 사용까지 허용하고, 1,001점 사용은
거절하며 잔액과 사용 내역은 그대로여야 해”처럼 허용 범위와 실패 뒤 상태를 함께 설명할 수 있습니다.
해당하지 않거나 아직 정하지 못한 항목을 채울 필요는 없습니다.

다음은 동시 구매와 알림까지 기대 결과가 정해진 요청의 예시입니다.

```text
dddjango를 사용해 기존 Django 프로젝트의 재고 예약 기능을 만들어 줘.
남은 재고와 같은 수량까지 예약할 수 있고, 성공하면 예약한 수량만큼 판매 가능한 재고가 줄어야 해.
재고가 1개일 때 두 주문이 동시에 예약하면 한 주문만 성공하고 재고는 0이 되어야 해.
같은 예약 요청이 다시 도착해도 예약이 추가로 생기거나 재고가 더 줄어들면 안 돼.
재고 부족이면 사용자에게 예약 실패를 알리고, 예약과 재고 변경이 남으면 안 돼.
예약 성공은 즉시 보여 주고, 알림은 1분 이내 전달하면 돼. 알림 전달에 실패해도 예약은 유지해 줘.
기존 재고 조회 응답은 유지하고, 결제와 배송 기능은 이번 범위에서 제외해 줘.
```

## 4. 플러그인이 하는 일과 요청에 적지 않을 것

플러그인은 관련 코드·문서·기존 테스트를 찾아 현재 동작을 조사합니다. 자료 사이에 다른 해석이
있으면 확인한 내용을 정리하고, 원하는 제품 결과를 선택해야 하는 부분을 질문합니다.

업무 규칙에 맞는 DDD 구조를 설계하며 aggregate·repository 배치와 API·DB 구현 방법을 정합니다.
새로 만드는 파일과 기존 파일에 더하거나 바꾸는 부분은 프로젝트의 기존 폴더 배치와 관계없이
플러그인의 표준 형태로 씁니다. 기존 파일의 위치는 그대로 두며, 옮기는 정리는 6장의 조건을 따릅니다.
진행 방식, 사용할 agent·skill, 테스트 구조와 필요한 수량, TDD 구현과 검증 절차도 플러그인이
판단합니다.

진행 중에 필요하면 플러그인이 사용자에게 직접 묻는 결정이 있습니다. 각 질문에는 선택지마다
대가가 함께 나옵니다.

- 이 기능을 기존 업무 영역에 넣을지 새 영역으로 나눌지. 정해 둔 것이 없으면 플러그인에 맡길 수 있습니다.
- 작업하는 업무 영역을 조사해 기존 코드의 표준 위반을 찾았을 때, 동작을 바꾸지 않고 먼저 정리할지
  이번에는 미룰지. 그대로 두면 이번 작업을 해치는 위반은 미룰 수 없습니다. 기존 기능의 작은 수정에서는
  이 조사를 하지 않을 수 있습니다.
- 이전 작업의 기록을 이어 쓸지 새 작업으로 시작할지.
- 설계 단계에서 스스로 정할 수 없는 선택, 외부에서 보이는 결과가 갈리는 선택.

이 질문들의 답을 요청에 미리 적어 둘 필요는 없습니다. 이미 정한 결정이 있다면 요청에 적어 주세요.

설계는 플러그인이 합니다. 요청에 다음을 적으면 플러그인의 설계 판단과 규칙 검사를 가로막거나,
규칙을 어긴 기존 코드를 새 코드에 옮겨 오게 됩니다. 원하는 것이 있으면 결과로 적어 주세요.

- 진행 방식(새로 만들기·부분 수정), 리뷰 구성, 작업 단계의 수
- 만들 파일·클래스·함수의 이름과 두는 위치, 수정해도 되는 파일이나 건드리면 안 되는 경로의 목록
- “이 코드를 본떠라” 같은 선례 지정. 참고할 코드가 있으면 위치만 알려 주세요.
- 실행 입구의 형태, 테스트 방식, 재시도·잠금 같은 구현 수단과 사용할 라이브러리
- 사용자가 정하지 않은 기존 코드 정리 미룸이나 생략. 정리 여부는 조사 결과와 대가를 본 뒤 정합니다.
- 검사나 승인 단계를 줄이거나 건너뛰라는 지시

단, 사용자가 직접 정한 결정과 방침은 적을 수 있습니다. 예를 들어 사용할 API 프레임워크, 기능을 둘
업무 영역, 새 의존성을 들이지 않는다는 방침, 기존 코드 정리를 이번에는 미룬다는 결정입니다.

## 5. 알고 있는 자료가 있으면 함께 주기

자료가 있으면 위치만 알려 줘도 됩니다. 자료 없이 시작할 수 있으며, 요청 전에 찾아서 분석하거나
정리할 필요는 없습니다.

- 관련 코드·제품 문서·기존 테스트 경로. 예를 들어 `apps/orders/`, `docs/orders.md`, `tests/orders/`
- OpenAPI, 요청·응답 예시, 연동 시스템을 설명하는 자료
- 경계 사례·동시 실행·외부 연동의 실제 상황을 보여 주는 문서나 샘플
- 외부 자료의 접근 조건 등 이미 알고 있는 사실
- 실행 환경: 테스트에 쓸 DB와 가상환경, 같은 DB·서버 같은 자원을 함께 쓰는 다른 작업

알고 있는 코드 사실을 위치와 함께 적어 주면 조사가 빨라집니다. 플러그인은 그 사실을 현재 코드에서
다시 확인하고, 기존 코드가 표준과 다르면 그대로 따르지 않습니다.

실제로 정해진 환경 제약이 있으면 그 이유와 지켜야 할 결과를 함께 알려 주세요. 예를 들어 실제 결제나
외부 발송을 하면 안 되는 환경, 개발 DB를 쓰면 안 된다는 조건, 같은 코드나 파일을 동시에 고치는 다른
작업이 있다는 사실입니다. 편집 금지 경로 목록이나 게이트·검사 절차를 지정하는 명령은 환경 제약이 아닙니다.

## 6. 수정하거나 이전 작업 이어가기

이전 작업을 이어간다는 사실과 바꿀 결과, 유지할 동작을 말하면 됩니다. 부분 수정으로 진행할지
새로 설계할지는 플러그인이 조사해 정합니다. 이전 작업이 끝난 뒤 다른 작업이 합쳐졌거나 세션 밖에서
바뀐 사실을 알고 있다면 함께 알려 주세요.

```text
dddjango를 사용해 이전 주문 취소 작업을 이어서 수정해 줘.
이제 결제 완료 후에도 배송 시작 전이면 취소할 수 있어야 해.
배송 시작 후 취소 거절과 기존 주문 조회 응답은 유지해 줘.
대화가 끝난 뒤 환불 서비스가 새 버전으로 바뀌었어.
```

이전 작업이나 새 자료의 위치를 알면 덧붙일 수 있습니다. 플러그인이 기존 기록과 현재 상태를
확인하고, 이어 쓸 작업 기록을 목록에서 고르게 한 뒤 필요한 질문·승인을 안내합니다.

동작을 유지하면서 코드 구조를 정리하고 싶다면 대상 기능과 현재 불편한 점을 알려 주세요.

```text
dddjango를 사용해 주문 취소의 현재 동작은 유지하면서,
규칙 하나를 수정할 때 여러 곳을 고쳐야 하는 불편을 줄여 줘.
```

새로 만드는 코드와 이번에 바꾸는 부분은 표준 형태로 작성합니다. 기존 파일을 옮기거나 이름을 바꾸는
정리는 플러그인이 조사해 찾은 표준 위반 가운데 사용자가 먼저 정리하기로 정한 항목에만 적용하며,
동작을 바꾸지 않는 선행 단계로 처리합니다. 그 조사를 하지 않는 작은 수정이면 옮기는 정리도 하지
않습니다. 표준 위반이 아닌 불편은 이번에 바꾸는 코드의 범위 안에서 다룹니다.

## 7. 다른 세션에 맡겨 요청할 때

다른 에이전트나 세션이 사용자를 대신해 요청을 쓰고 진행 중 질문에 답하도록 맡길 수 있습니다.
이때도 결정은 사용자가 합니다.

- 요청에는 사용자가 이미 정한 결과·규칙·범위만 담고, 각 결정에 사용자가 말한 원문과 시각을 함께
  적습니다. 사용자가 정하지 않은 것은 비워 둡니다. 플러그인이 조사한 뒤 묻습니다.
- 대신 쓰는 쪽이 조사로 찾은 코드 사실이나 위험은 위치와 함께 사실로 적고, 어떻게 할지는 정하지 않습니다.
- 대신 답하는 쪽은 플러그인이 제시한 결과를 확인해 진행을 승인하고, 사용자가 정한 결정과 방침을
  전달할 수 있습니다. 선택지가 갈리는 설계 결정, 사용자 방침이 없는 기존 코드 정리 미룸, 외부에서
  보이는 결과가 갈리는 선택은 대신 승인하지 않고 사용자에게 올립니다.
- 4장의 “요청에 적지 않을 것”은 맡긴 요청에도 그대로 적용됩니다. 긴 요청 문서를 쓰더라도 진행 방식·
  파일 위치·경로 목록·선례·구현 수단 지시를 넣지 않습니다.
- 작업이 끝나면 맡은 쪽은 완료 보고가 사용자가 정한 결과와 맞는지 확인해 사용자에게 알립니다.

## 8. 완료 보고 읽기

구현한 업무 사례, 실제로 실행한 검증, 남은 미확정이나 제한을 확인하세요. 원하는 성공·실패 결과와
보존할 동작에 차이가 있으면 그 결과를 알려 주세요. 이번에 정리하지 않은 기존 코드의 표준 위반은
별도 항목으로 보고됩니다. 자동 검사 통과는 확인한 사례와 범위에 대한 결과이며, 모든 가능한 결함이
없음을 보장하지는 않습니다.
