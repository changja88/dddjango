# Hotel 애그리거트 설계 리뷰

## 잘 된 부분

- `make_reservation`과 `cancel_reservation`이 비즈니스 의도를 드러내는 메서드명을 사용하고 있다. `updateStatus()`가 아닌 `cancel_reservation()`처럼 유비쿼터스 언어를 반영한다.
- 예약 생성 시 객실 가용 여부를 확인하는 불변식(`room.is_available`)을 애그리거트 내부에서 보호하고 있다.
- 비즈니스 로직(예약 생성, 취소, 리뷰 등록)이 서비스가 아닌 도메인 객체 안에 위치해 있어 빈혈 도메인 모델을 피하고 있다.

## 개선이 필요한 부분

### 1. 거대 애그리거트 -- Vernon 규칙 2 위반

```
[Vernon 규칙 2: 작은 애그리거트를 설계하라]
-- Hotel이 rooms(수백 개), reservations(수천 건), reviews(수천 건), amenities를
   모두 포함하는 거대 애그리거트다. 이는 Vernon이 명시적으로 경고하는 안티패턴이다.
```

Hotel을 로딩할 때마다 수천 건의 Reservation과 Review까지 함께 로딩해야 한다. 리뷰 하나를 추가하려면 Hotel 전체를 잠가야 하므로 동시성 충돌이 빈번해진다. Vernon은 "루트 엔티티와 최소한의 속성/값 객체로 제한하라"고 명시한다.

**분리 기준 -- 진정한 불변식 식별:**
- Hotel의 진정한 불변식은 호텔 자체의 기본 정보(이름, 위치 등)뿐이다.
- "같은 객실이 같은 기간에 중복 예약되면 안 된다"는 Room 수준의 불변식이지, Hotel 전체의 불변식이 아니다.
- 리뷰는 호텔 정보와 아무런 불변식을 공유하지 않는다.
- 따라서 Hotel, Reservation, Review는 각각 별도의 애그리거트여야 한다.

### 2. 직접 객체 참조 -- Vernon 규칙 3 위반

```
[Vernon 규칙 3: 다른 애그리거트는 ID로만 참조하라]
-- rooms: List[Room], reservations: List[Reservation], reviews: List[Review]가
   모두 직접 객체 참조(object reference)다. ID 참조로 전환해야 한다.
```

직접 객체 참조는 애그리거트 간 결합도를 높이고, 로딩 시간과 메모리 사용을 증가시킨다. Reservation이 Room을 직접 참조(`room=room`)하는 것도 동일한 문제다. `room_id: str`로 ID 참조해야 한다.

### 3. 결과적 일관성 부재 -- Vernon 규칙 4 위반

```
[Vernon 규칙 4: 일관성 경계 밖에서는 결과적 일관성을 사용하라]
-- 리뷰 추가, 예약 생성 등 서로 다른 관심사가 모두 Hotel 하나의 트랜잭션 안에서
   동기적으로 처리된다. 도메인 이벤트를 통한 결과적 일관성이 적용되지 않았다.
```

예약이 생성되면 `ReservationCreated` 이벤트를 발행하고, 이를 구독하여 알림 전송, 통계 업데이트 등 후속 처리를 결과적 일관성으로 수행해야 한다. 리뷰 추가도 마찬가지로 Hotel 애그리거트와 같은 트랜잭션일 필요가 없다.

### 4. 원시 타입 과용 -- 값 객체 추출 필요

```
[값 객체 우선 원칙]
-- guest_id: str, room_id: str, check_in/check_out 등이 원시 타입으로 표현되어 있다.
   도메인 개념을 담은 값 객체로 추출해야 한다.
```

- `check_in`, `check_out` --> `DateRange` 값 객체로 묶으면 기간 겹침 검증 로직을 값 객체 안에 캡슐화할 수 있다.
- `rating` --> `Rating` 값 객체로 만들면 1~5 범위 검증을 생성 시점에 보장할 수 있다.
- `status = "cancelled"` --> 문자열 대신 `ReservationStatus` Enum을 사용해야 오타와 잘못된 상태 전이를 방지한다.

### 5. 도메인 이벤트 부재

```
[도메인 이벤트 패턴]
-- 예약 생성, 예약 취소, 리뷰 등록 같은 비즈니스적으로 중요한 사건이 발생해도
   도메인 이벤트가 발행되지 않는다.
```

`ReservationCreated`, `ReservationCancelled`, `ReviewAdded` 등의 도메인 이벤트를 정의하고, 애그리거트 내부에 이벤트를 수집한 뒤 UoW 커밋 시점에 디스패치해야 한다. 이를 통해 애그리거트 간 결과적 일관성과 후속 프로세스 연동이 가능해진다.

### 6. 바운디드 컨텍스트 경계 미정의

```
[전략 설계 우선 원칙]
-- 전략 설계(바운디드 컨텍스트 경계) 없이 전술 패턴을 적용하고 있다.
   Hotel 하나에 예약, 리뷰, 시설 관리가 모두 섞여 있다.
```

호텔 예약 시스템에서는 최소한 다음 컨텍스트를 고려해야 한다:
- **숙박 관리(Property Management)**: 호텔, 객실, 시설 정보
- **예약(Reservation)**: 예약 생성, 변경, 취소
- **리뷰(Review)**: 투숙 후기, 평점

각 컨텍스트에서 "Hotel"이라는 용어가 다른 의미로 쓰인다. 예약 컨텍스트에서는 객실 가용성이 중요하고, 리뷰 컨텍스트에서는 평점 집계가 중요하다. 이 차이가 바운디드 컨텍스트의 경계다.

## 리뷰 체크리스트 결과

| 항목 | 결과 |
|------|------|
| 바운디드 컨텍스트 경계가 명확한가 | X -- 경계 미정의, 예약/리뷰/숙박관리가 혼재 |
| 애그리거트가 너무 크지 않은가 | X -- Hotel이 수천 건의 연관 객체를 포함 |
| 애그리거트 간 ID 참조를 사용하는가 | X -- 직접 객체 참조 사용 |
| 빈혈 도메인 모델이 아닌가 | O -- 비즈니스 로직이 도메인 객체 안에 있음 |
| 값 객체로 표현할 수 있는 것이 엔티티로 되어 있지 않은가 | X -- DateRange, Rating 등 값 객체 미추출 |
| 도메인 이벤트로 처리해야 할 것이 직접 호출로 되어 있지 않은가 | X -- 도메인 이벤트 전혀 없음 |
| 유비쿼터스 언어가 코드에 반영되어 있는가 | O -- 메서드명이 비즈니스 의도를 반영 |
| 하위 도메인 유형에 맞는 복잡성 수준을 적용하고 있는가 | - -- 하위 도메인 분류 자체가 되어 있지 않음 |

## 권장 애그리거트 분리안

```
[현재]
Hotel (거대 애그리거트)
  +-- rooms: List[Room]
  +-- reservations: List[Reservation]
  +-- reviews: List[Review]
  +-- amenities: List[Amenity]

[권장]
Hotel 애그리거트        -- 호텔 기본 정보만 (name, location, amenity_ids)
Room 애그리거트         -- hotel_id로 Hotel 참조, 객실 속성 관리
Reservation 애그리거트  -- hotel_id, room_id로 ID 참조, 예약 생명주기 관리
Review 애그리거트       -- hotel_id, guest_id로 ID 참조, 리뷰 독립 관리
```

각 애그리거트는 자신의 불변식만 보호하며, 애그리거트 간 연동은 도메인 이벤트를 통한 결과적 일관성으로 처리한다.
