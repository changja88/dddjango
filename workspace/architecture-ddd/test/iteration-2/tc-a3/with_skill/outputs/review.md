# 이커머스 플랫폼 바운디드 컨텍스트 설계 리뷰

## 리뷰 대상 설계 요약

| 바운디드 컨텍스트 | 책임 |
|------------------|------|
| 상품 컨텍스트 | 상품 등록, 카테고리, 재고 관리 |
| 주문 컨텍스트 | 장바구니, 주문, 결제 |
| 배송 컨텍스트 | 배송 추적, 반품 |
| 회원 컨텍스트 | 회원 정보, 등급, 포인트 |

---

## 잘 된 부분

**바운디드 컨텍스트 분리 자체는 올바른 방향이다.** 상품, 주문, 배송, 회원이라는 네 가지 영역은 이커머스 도메인에서 자연스러운 경계를 형성한다. 각 컨텍스트가 서로 다른 유비쿼터스 언어를 가질 수 있는 지점에서 경계를 나누었다는 점에서 전략 설계의 기본 방향은 적절하다.

---

## 개선이 필요한 부분

### 1. 컨텍스트 간 직접 모델 참조 -- 바운디드 컨텍스트 경계 위반

```
[바운디드 컨텍스트 독립성 원칙] -- 주문 컨텍스트가 상품 컨텍스트의 Product 모델을
직접 import하고 있어 두 컨텍스트가 강결합되어 있다.
```

바운디드 컨텍스트는 "유비쿼터스 언어가 적용되는 명시적 경계"다. 각 컨텍스트는 자신만의 모델을 소유해야 하며, 다른 컨텍스트의 내부 모델을 직접 참조하면 경계가 무너진다. 상품 컨텍스트의 `Product` 모델이 변경되면 주문 컨텍스트가 함께 깨지고, 두 컨텍스트를 독립적으로 배포할 수 없게 된다.

**개선 방향:** 주문 컨텍스트에 자신의 언어로 표현된 값 객체(예: `OrderLineItem`에 `product_id`, `product_name`, `price` 등 주문 시점에 필요한 정보만 포함)를 정의한다. 상품 컨텍스트의 데이터가 필요하면 충돌 방지 계층(ACL)을 통해 자신의 모델로 변환하여 수용한다.

```python
# 나쁜 예: 주문 컨텍스트가 상품 컨텍스트 모델을 직접 import
from product.domain.models import Product  # 경계 위반

class Order:
    def __init__(self, product: Product):  # 외부 모델에 직접 의존
        self.product = product

# 좋은 예: 주문 컨텍스트 자체의 값 객체 사용 + ID 참조
@dataclass(frozen=True)
class OrderLineItem:
    """주문 컨텍스트의 값 객체 -- 주문 시점의 상품 스냅샷"""
    product_id: str        # 상품을 ID로만 참조
    product_name: str      # 주문 시점에 복사된 이름
    price: Money           # 주문 시점에 확정된 가격
    quantity: int
```

### 2. 주문 완료 시 재고 직접 차감 -- 결과적 일관성 원칙 위반

```
[Vernon 규칙 4: 일관성 경계 밖에서는 결과적 일관성을 사용하라] -- 주문 컨텍스트가
상품 컨텍스트의 재고 차감 메서드를 직접 호출하고 있어, 서로 다른 애그리거트(더 나아가
서로 다른 바운디드 컨텍스트)를 하나의 트랜잭션에서 수정하고 있다.
```

주문과 재고는 서로 다른 바운디드 컨텍스트에 속하며, 서로 다른 애그리거트다. 직접 호출 방식은 다음 문제를 발생시킨다:

- **트랜잭션 결합**: 주문 처리와 재고 차감이 하나의 트랜잭션으로 묶여, 재고 차감 실패가 주문 전체를 롤백시킨다.
- **시간적 결합**: 상품 서비스가 일시적으로 불가용하면 주문 자체가 불가능해진다.
- **확장성 제약**: 두 컨텍스트를 독립적으로 스케일링할 수 없다.

**개선 방향:** 주문 컨텍스트는 `OrderPlacedEvent` 도메인 이벤트를 발행하고, 상품 컨텍스트의 이벤트 핸들러가 이를 구독하여 별도 트랜잭션에서 재고를 차감한다.

```python
# 주문 컨텍스트: 이벤트 발행
class Order:
    def place(self) -> None:
        self._status = OrderStatus.PLACED
        self._raise_event(OrderPlacedEvent(
            order_id=self.id,
            line_items=[(item.product_id, item.quantity) for item in self.order_lines],
            occurred_at=datetime.now(),
        ))

# 상품 컨텍스트: 이벤트 구독 -> 별도 트랜잭션에서 재고 차감
class InventoryEventHandler:
    def handle_order_placed(self, event: OrderPlacedEvent) -> None:
        for product_id, quantity in event.line_items:
            inventory = self._repo.find_by_product_id(product_id)
            inventory.decrease_stock(quantity)
            self._repo.save(inventory)
```

### 3. 배송 컨텍스트의 Order 모델 직접 참조 -- 동일한 경계 위반 반복

```
[Vernon 규칙 3: 다른 애그리거트는 ID로만 참조하라] -- 배송 컨텍스트가 주문 컨텍스트의
Order 모델을 직접 참조하고 있어 두 컨텍스트가 강결합되어 있다.
```

배송 컨텍스트에서 필요한 것은 Order의 전체 도메인 모델이 아니라, 배송에 필요한 정보(배송지, 수령인, 상품 목록 등)의 스냅샷이다. 직접 참조는 배송 컨텍스트의 모델이 주문 컨텍스트의 변경에 종속되게 만든다.

**개선 방향:** 배송 컨텍스트는 `order_id`만 보유하고, 필요한 배송 정보는 주문이 확정될 때 도메인 이벤트(`OrderConfirmedEvent`)를 통해 전달받아 자신의 모델(`Shipment`)로 변환한다.

```python
# 배송 컨텍스트: 자체 모델 정의
@dataclass
class Shipment:
    id: str
    order_id: str                    # 주문을 ID로만 참조
    receiver_name: str               # 이벤트로 전달받은 정보
    receiver_address: str
    items: list[ShipmentItem]
    status: ShipmentStatus

# 배송 컨텍스트: ACL을 통해 이벤트 데이터를 자체 모델로 변환
class ShipmentCreator:
    def from_order_confirmed(self, event: OrderConfirmedEvent) -> Shipment:
        return Shipment(
            id=str(uuid4()),
            order_id=event.order_id,
            receiver_name=event.receiver_name,
            receiver_address=event.receiver_address,
            items=[ShipmentItem(product_id=i.product_id, quantity=i.quantity)
                   for i in event.items],
            status=ShipmentStatus.PENDING,
        )
```

### 4. 상품 컨텍스트의 책임이 과하다 -- 재고는 별도 컨텍스트 후보

```
[바운디드 컨텍스트 경계 설정] -- 상품 등록/카테고리와 재고 관리는 유비쿼터스 언어가
다르고, 변경 빈도와 이해관계자도 다르다. 하나의 컨텍스트에 묶여 있으면
애그리거트가 비대해질 가능성이 높다.
```

"상품"이라는 용어가 상품 카탈로그 관점("이름, 설명, 가격, 카테고리")과 재고 관점("SKU, 가용 수량, 입출고")에서 다른 의미를 가진다. 상품 등록은 MD(상품 기획자)가, 재고 관리는 물류 담당자가 주 이해관계자다. 이는 같은 용어가 다른 의미로 쓰이는 전형적인 바운디드 컨텍스트 분리 신호다.

**개선 방향:** 카탈로그 컨텍스트(상품 정보, 카테고리)와 재고 컨텍스트(입출고, 가용 수량)로 분리를 검토한다.

### 5. 주문 컨텍스트에 결제가 포함되어 있다 -- 관심사 분리 부족

```
[하위 도메인 유형 분류] -- 결제는 PG사 연동 등 외부 시스템 의존도가 높은 일반(Generic)
하위 도메인이고, 주문은 비즈니스 핵심 규칙이 집중된 핵심(Core) 하위 도메인이다.
하위 도메인 유형이 다르면 복잡성 관리 전략도 달라야 한다.
```

주문(주문 생성, 상태 전이, 비즈니스 규칙)과 결제(PG 연동, 환불, 정산)는 변경 이유가 다르다. 결제는 PG사 정책 변경에 따라 바뀌고, 주문은 비즈니스 정책 변경에 따라 바뀐다. 또한 결제는 일반 하위 도메인으로 외부 솔루션 활용이 가능하지만, 주문 로직은 사내 구현이 필수적인 핵심 하위 도메인이다.

**개선 방향:** 결제 컨텍스트를 분리하고, 주문 컨텍스트는 `PaymentRequested` 이벤트를 발행, 결제 컨텍스트가 처리 후 `PaymentCompleted` 이벤트로 응답하는 구조를 고려한다.

### 6. 컨텍스트 맵이 정의되어 있지 않다

```
[컨텍스트 맵 부재] -- 바운디드 컨텍스트를 정의했지만, 컨텍스트 간 관계 유형
(파트너십, 고객-공급자, ACL 등)이 명시되지 않아 통합 전략이 불분명하다.
```

현재 "직접 import" 방식으로 통신하고 있다는 것은, 컨텍스트 간 관계 유형이 의식적으로 선택되지 않았음을 의미한다. 컨텍스트 맵은 각 관계에서 어느 쪽이 업스트림/다운스트림인지, 어떤 통합 패턴(ACL, OHS, 파트너십 등)을 사용할지 명시해야 한다.

**개선 방향:** 다음과 같은 컨텍스트 맵을 정의한다.

```
상품(카탈로그) ──[OHS/PL]──> 주문      (상품 정보 조회)
주문 ──[이벤트/ACL]──> 재고            (재고 차감)
주문 ──[이벤트/ACL]──> 배송            (배송 생성)
주문 ──[이벤트/ACL]──> 결제            (결제 요청/완료)
회원 ──[OHS/PL]──> 주문               (회원 정보 조회)
주문 ──[이벤트]──> 회원                (포인트 적립)
```

## 리뷰 체크리스트 결과

- [x] 바운디드 컨텍스트 경계가 명확한가 -- 기본 분리는 되어 있으나, 상품/재고와 주문/결제는 추가 분리 검토 필요
- [ ] 애그리거트 간 직접 참조가 아닌 ID 참조를 사용하는가 -- **위반.** 주문->상품, 배송->주문 모두 직접 모델 참조
- [ ] 도메인 이벤트로 처리해야 할 것이 직접 호출로 되어 있지 않은가 -- **위반.** 재고 차감을 직접 메서드 호출로 처리
- [ ] 하위 도메인 유형(핵심/지원/일반)에 맞는 복잡성 수준을 적용하고 있는가 -- 결제(일반)와 주문(핵심)이 분리되지 않음
- [x] 유비쿼터스 언어가 코드에 반영되어 있는가 -- 컨텍스트 이름 수준에서는 적절 (내부 코드는 미제공)
- [ ] 빈혈 도메인 모델이 아닌가 -- 코드가 제공되지 않아 판단 불가
- [ ] 값 객체로 표현할 수 있는 것이 엔티티로 되어 있지 않은가 -- 코드가 제공되지 않아 판단 불가

## 핵심 요약

현재 설계의 가장 심각한 문제는 **바운디드 컨텍스트 간 직접 모델 참조와 직접 메서드 호출**이다. 이는 컨텍스트 경계를 사실상 무의미하게 만들며, 컨텍스트를 나눈 이점(독립적 배포, 독립적 모델 진화, 팀 자율성)을 모두 잃게 한다. 우선 순위에 따른 개선 권장 순서:

1. **컨텍스트 간 직접 참조 제거** -- ACL 도입, ID 참조로 전환
2. **직접 호출을 도메인 이벤트로 전환** -- 재고 차감, 배송 생성 등을 이벤트 기반으로 변경
3. **컨텍스트 맵 정의** -- 각 관계의 업스트림/다운스트림, 통합 패턴 명시
4. **컨텍스트 경계 재검토** -- 상품/재고 분리, 주문/결제 분리 검토
