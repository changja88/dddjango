# 이커머스 플랫폼 바운디드 컨텍스트 설계 리뷰

## 1. 컨텍스트 분리 평가

### 상품 컨텍스트: 상품 등록, 카테고리, 재고 관리

**문제: 재고 관리가 상품 컨텍스트에 포함되어 있다.**

재고(Inventory)는 상품 정보(Product Catalog)와 변경 빈도, 비즈니스 규칙, 관심사가 다르다.

- 상품 정보(이름, 설명, 카테고리)는 MD(마케팅/머천다이징) 팀이 관리하며 변경 빈도가 낮다.
- 재고는 주문, 입고, 반품 등 여러 이벤트에 의해 실시간으로 변동하며, 동시성 제어가 핵심 관심사다.

재고를 상품 컨텍스트에 두면 상품 정보 수정과 재고 차감이 같은 Aggregate에서 일어나 Lock 경합이 발생하고, 주문 컨텍스트가 상품 컨텍스트에 강하게 결합되는 원인이 된다.

**권장:** 재고 컨텍스트(Inventory Context)를 별도로 분리한다.

### 주문 컨텍스트: 장바구니, 주문, 결제

**문제: 결제가 주문 컨텍스트에 포함되어 있다.**

결제(Payment)는 독립적인 도메인이다.

- 결제는 PG사 연동, 부분 환불, 결제 수단 관리 등 자체적으로 복잡한 비즈니스 규칙을 가진다.
- 주문 취소와 결제 취소는 항상 1:1로 대응하지 않는다 (부분 취소, 부분 환불 등).
- 결제 시스템의 장애가 주문 시스템 전체를 마비시키는 위험이 있다.

**권장:** 결제 컨텍스트(Payment Context)를 별도로 분리한다.

**장바구니에 대한 추가 고려사항:** 장바구니는 주문 전 단계로, 주문과 라이프사이클이 다르다. 장바구니는 로그인 없이도 존재할 수 있고, 여러 날에 걸쳐 유지되며, 주문으로 전환되지 않을 수도 있다. 규모가 커지면 장바구니를 별도 컨텍스트로 분리하는 것도 고려할 수 있으나, 현재 규모에서는 주문 컨텍스트에 두는 것이 합리적이다.

### 배송 컨텍스트: 배송 추적, 반품

**문제: 반품이 배송 컨텍스트에 포함되어 있다.**

반품(Return)은 단순히 배송의 역방향이 아니다.

- 반품은 환불 금액 계산, 반품 사유 관리, 재입고 판단, 교환 처리 등 자체적인 비즈니스 로직이 있다.
- 반품은 결제(환불), 재고(재입고), 주문(주문 상태 변경) 등 여러 컨텍스트와 관계를 맺는다.
- 배송 컨텍스트에 두면 배송이 반품의 모든 복잡성을 떠안게 된다.

**권장:** 반품 컨텍스트(Return Context) 또는 CS/After-Sales 컨텍스트로 분리를 검토한다.

### 회원 컨텍스트: 회원 정보, 등급, 포인트

비교적 적절한 분리다. 다만 포인트 적립/차감은 주문, 리뷰, 이벤트 등 다양한 트리거에 의해 발생하므로, 포인트가 복잡해지면 별도 컨텍스트(Loyalty/Reward Context)로 분리하는 것을 고려할 수 있다.

## 2. 컨텍스트 간 통신: 핵심 문제

현재 설계에서 가장 심각한 문제는 컨텍스트 간 직접 참조(direct import)다.

### 문제 1: 주문이 상품의 Product 모델을 직접 import

```
# 현재 (안티패턴)
from product_context.models import Product  # 컨텍스트 경계 위반

class Order:
    def create(self, product: Product, quantity: int):
        ...
```

이것이 왜 문제인가:

- **컨텍스트 자율성 파괴:** 상품 컨텍스트의 Product 모델이 변경되면 주문 컨텍스트가 함께 깨진다. 두 컨텍스트를 독립적으로 배포할 수 없다.
- **유비쿼터스 언어 오염:** 주문 컨텍스트에서의 "상품"은 상품 컨텍스트에서의 "상품"과 의미가 다르다. 주문 컨텍스트에서는 주문 시점의 상품명, 가격, 수량만 중요하지, 상품의 카테고리 트리나 SEO 메타데이터는 관심 대상이 아니다.
- **데이터 정합성 위험:** 주문 이후 상품 가격이 변경되면, 주문 내역의 가격도 변경되는 버그가 발생할 수 있다.

**해결 방향:**

```
# 개선: Anti-Corruption Layer + 값 복사
class OrderLineItem:  # 주문 컨텍스트 내부 모델
    product_id: int           # ID로만 참조
    product_name: str         # 주문 시점 스냅샷
    unit_price: Money         # 주문 시점 스냅샷
    quantity: int
```

주문 컨텍스트는 상품의 ID만 알면 되고, 필요한 정보(이름, 가격)는 주문 생성 시점에 복사(스냅샷)하여 자체 모델로 보관한다.

### 문제 2: 주문 완료 시 상품 컨텍스트의 재고를 직접 차감

```
# 현재 (안티패턴)
class OrderService:
    def complete_order(self, order):
        order.status = "COMPLETED"
        product_service.decrease_stock(order.product_id, order.quantity)  # 직접 호출
```

이것이 왜 문제인가:

- **트랜잭션 경계 혼란:** 주문 완료와 재고 차감이 하나의 트랜잭션에 묶이면, 재고 서비스 장애가 주문 완료를 막는다. 두 작업이 서로 다른 Aggregate에 속하므로 하나의 트랜잭션으로 묶는 것은 DDD 원칙에 위배된다.
- **순환 의존 위험:** 재고가 상품 컨텍스트에 있으므로, 주문 -> 상품 -> (혹시 상품이 주문 상태를 확인해야 한다면) -> 주문 순환이 발생할 수 있다.
- **확장성 제약:** 동기 호출이므로 주문 처리량이 재고 서비스의 처리량에 종속된다.

**해결 방향: 도메인 이벤트 기반 비동기 통신**

```
# 개선: 이벤트 발행
class OrderService:
    def complete_order(self, order):
        order.status = "COMPLETED"
        # 이벤트 발행 (재고 차감은 재고 컨텍스트가 자율적으로 처리)
        domain_events.publish(OrderCompleted(
            order_id=order.id,
            items=[
                OrderedItem(product_id=item.product_id, quantity=item.quantity)
                for item in order.items
            ]
        ))

# 재고 컨텍스트 (이벤트 구독)
class InventoryEventHandler:
    def handle_order_completed(self, event: OrderCompleted):
        for item in event.items:
            inventory.decrease_stock(item.product_id, item.quantity)
```

### 문제 3: 배송이 주문의 Order 모델을 직접 참조

동일한 문제다. 배송 컨텍스트는 배송에 필요한 정보(배송지 주소, 수령인, 상품 목록)만 자체 모델로 가져야 하며, Order 전체 모델을 참조해서는 안 된다.

```
# 개선: 배송 컨텍스트 자체 모델
class Shipment:
    shipment_id: str
    order_id: str             # ID로만 참조
    recipient_name: str       # 필요한 정보만 스냅샷
    recipient_address: Address
    items: list[ShipmentItem]
    status: ShipmentStatus
```

## 3. 권장 컨텍스트 맵

```
[상품 카탈로그]  ──(이벤트)──>  [재고]
      |                          ^
      |                          |
   (이벤트)                   (이벤트)
      |                          |
      v                          |
   [주문]  ──(이벤트)──>  [결제]
      |
   (이벤트)
      |
      v
   [배송]  <──(이벤트)──  [반품/CS]

   [회원]  ──(이벤트)──>  (주문, 결제 등에서 구독)
```

| 컨텍스트 | 핵심 Aggregate | 역할 |
|---------|--------------|------|
| 상품 카탈로그 | Product | 상품 정보, 카테고리, 가격 정책 |
| 재고 | InventoryItem | 재고 수량, 입출고, 동시성 제어 |
| 주문 | Order | 장바구니, 주문 생성, 주문 상태 관리 |
| 결제 | Payment | PG 연동, 결제/환불 처리 |
| 배송 | Shipment | 배송 생성, 배송 추적 |
| 반품/CS | ReturnRequest | 반품 접수, 교환, 환불 연계 |
| 회원 | Member | 회원 정보, 등급, 포인트 |

## 4. 핵심 개선 원칙 요약

| 원칙 | 현재 상태 | 개선 방향 |
|------|----------|----------|
| 컨텍스트 간 모델 공유 금지 | Product, Order를 직접 import | ID 참조 + 필요 데이터 스냅샷 |
| Aggregate 간 트랜잭션 분리 | 재고 차감을 동기 호출 | 도메인 이벤트로 비동기 처리 |
| 각 컨텍스트의 자율성 보장 | 상품 변경 시 주문이 깨짐 | Anti-Corruption Layer 도입 |
| 단일 책임 | 하나의 컨텍스트에 여러 관심사 혼재 | 재고, 결제, 반품 분리 |

---

## 5. 실행 우선순위

1. **(긴급) 컨텍스트 간 직접 참조 제거** -- 모든 cross-context import를 ID 참조로 전환하고, 필요한 데이터는 이벤트 또는 API를 통해 스냅샷으로 복사한다. 이것이 해결되지 않으면 나머지 개선이 무의미하다.
2. **(높음) 재고 차감을 도메인 이벤트 기반으로 전환** -- 주문 완료 이벤트를 발행하고, 재고 컨텍스트가 구독하여 자율적으로 차감한다.
3. **(중간) 재고 컨텍스트 분리** -- 상품 카탈로그와 재고를 분리하여 독립적 확장과 배포를 가능하게 한다.
4. **(중간) 결제 컨텍스트 분리** -- 주문과 결제를 분리하여 결제 장애가 주문 전체를 마비시키지 않도록 한다.
5. **(낮음) 반품 컨텍스트 분리** -- 반품 로직이 복잡해지는 시점에 분리한다.
