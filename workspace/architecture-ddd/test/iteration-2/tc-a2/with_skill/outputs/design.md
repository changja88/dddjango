# 대형 병원 통합 시스템 -- DDD 전략 설계

## 1. 도메인 비전 선언문 (Domain Vision Statement)

대형 병원 통합 시스템은 진료 예약부터 보험 청구까지의 전체 환자 여정을 하나의 플랫폼으로 통합한다. 이 시스템의 핵심 가치는 **진료 프로세스의 최적화**(예약-진료-처방-수납의 끊김 없는 흐름)와 **임상 데이터의 정확한 기록 및 활용**(EMR)에 있다. 이 두 영역이 병원의 의료 서비스 품질과 운영 효율성을 직접적으로 결정하며, 경쟁 우위의 원천이다.

## 2. 하위 도메인 식별 및 분류

### 2.1 분류 기준

| 유형 | 경쟁 우위 | 복잡성 | 변동성 | 솔루션 전략 |
|------|----------|--------|--------|------------|
| 핵심(Core) | 직접적 경쟁력 | 높음 | 잦은 변경 | 사내 구현 필수 |
| 지원(Supporting) | 없음 | 낮음 (CRUD 수준) | 낮음 | 하청 가능, RAD |
| 일반(Generic) | 없음 | 높음 (알려진 문제) | 낮음 | 외부 솔루션/오픈소스 |

### 2.2 하위 도메인 분류 결과

| # | 하위 도메인 | 유형 | 분류 근거 |
|---|-----------|------|----------|
| 1 | 진료 예약 및 대기열 관리 | **핵심(Core)** | 병원마다 진료과 구성, 의사 스케줄, 대기열 정책이 다르며, 환자 경험과 병원 운영 효율을 직접 결정한다. 실시간 대기열 최적화 알고리즘은 병원 고유의 경쟁력이다. |
| 2 | 전자 의무 기록(EMR) | **핵심(Core)** | 환자의 진료 이력, 검사 결과, 진단 기록을 관리하는 임상 데이터의 중심이다. 의료 품질과 직결되며, 병원 고유의 진료 프로토콜과 임상 워크플로우를 반영해야 한다. 규제 요건(의료법)에 따른 잦은 변경이 발생한다. |
| 3 | 처방전 발행 및 약국 연동 | **핵심(Core)** | 처방 적정성 검증(약물 상호작용, 용량 확인), DUR(Drug Utilization Review) 규칙은 환자 안전과 직결된다. 병원 자체 처방 가이드라인과 약국 시스템 간의 실시간 연동은 높은 도메인 복잡성을 갖는다. |
| 4 | 수술 스케줄링 및 수술실 자원 관리 | **핵심(Core)** | 수술실, 장비, 의료진의 제약 조건 하에서 최적의 스케줄을 산출하는 것은 병원 운영 효율의 핵심이다. 응급 수술 삽입, 수술 시간 예측, 자원 충돌 해결 등 높은 도메인 복잡성을 가진다. |
| 5 | 보험 청구 및 수납 | **지원(Supporting)** | 건강보험심사평가원(HIRA) 청구 규칙은 모든 병원에 공통이지만, 병원별 수가 체계와 수납 정책에 따른 커스터마이징이 필요하다. 비즈니스 로직의 복잡성은 중간 수준이며, 핵심 경쟁력보다는 운영 지원 성격이다. |
| 6 | 환자 포털 (예약 조회, 검사 결과 확인) | **지원(Supporting)** | 핵심 도메인(예약, EMR)의 데이터를 환자에게 노출하는 프레젠테이션 계층이다. 자체적인 복잡한 비즈니스 로직은 없으며, 주로 CRUD와 조회 기능으로 구성된다. |
| 7 | 사용자 인증 및 권한 관리 | **일반(Generic)** | 모든 시스템에 공통으로 필요한 인증/인가 기능이다. OAuth2, RBAC 등 표준화된 솔루션이 이미 존재하며, 병원의 경쟁 우위와 무관하다. |

## 3. 솔루션 전략

### 3.1 핵심 하위 도메인 -- 사내 구현 필수

핵심 도메인에는 최고의 인재와 정교한 설계를 집중한다. 풍부한 도메인 모델(Rich Domain Model)을 적용하며, DDD 전술 패턴(애그리거트, 도메인 이벤트, 값 객체)을 전면 활용한다.

#### 진료 예약 및 대기열 관리

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (도메인 모델 패턴) |
| 근거 | 병원별 예약 정책(진료과별 슬롯 관리, 우선순위 규칙, 대기열 알고리즘)이 경쟁 우위를 결정한다 |
| 설계 방향 | Appointment 애그리거트 + WaitingQueue 애그리거트 분리, 도메인 이벤트(AppointmentBooked, PatientCalledIn)로 비동기 연결 |
| 투자 수준 | 최고 수준 -- 시니어 개발자 배치, 도메인 전문가(진료 담당자)와의 반복적 지식 탐구 |

#### 전자 의무 기록(EMR)

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (도메인 모델 패턴) |
| 근거 | 임상 데이터 모델은 병원의 진료 체계를 직접 반영하며, 의료법 규제에 따른 잦은 변경이 발생한다 |
| 설계 방향 | MedicalRecord 애그리거트를 중심으로, Diagnosis(진단), Examination(검사) 등 값 객체 활용. 이력 관리가 중요하므로 이벤트 소싱 검토 |
| 투자 수준 | 최고 수준 -- 의료 도메인 전문가(의사, 간호사)와의 긴밀한 협업 필수 |

#### 처방전 발행 및 약국 연동

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (도메인 모델 패턴) |
| 근거 | 처방 적정성 검증 규칙과 DUR 로직은 환자 안전과 직결되며, 약국 연동 프로토콜은 병원별로 차이가 있다 |
| 설계 방향 | Prescription 애그리거트에 약물 상호작용 검증 로직 내재화, 약국 시스템 연동에는 ACL(충돌 방지 계층) 적용 |
| 투자 수준 | 최고 수준 -- 약제부 도메인 전문가 참여, 규제 변경 대응 체계 구축 |

#### 수술 스케줄링 및 수술실 자원 관리

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (도메인 모델 패턴) |
| 근거 | 수술실/장비/의료진 제약 조건 하의 스케줄링 최적화는 병원 고유의 도메인 복잡성이다 |
| 설계 방향 | SurgerySchedule 애그리거트 + OperatingRoom 애그리거트 분리, 스케줄링 최적화 알고리즘은 응집력 있는 메커니즘(Cohesive Mechanism)으로 분리 |
| 투자 수준 | 최고 수준 -- 수술실 운영 담당자와의 협업, 응급 수술 삽입 시나리오 등 엣지 케이스 집중 탐구 |

### 3.2 지원 하위 도메인 -- 하청 가능, RAD 프레임워크 활용

지원 도메인은 핵심 도메인을 보조하는 역할이다. 복잡한 비즈니스 로직이 없으므로, Transaction Script 또는 Active Record 패턴으로 충분하다. 사내 주니어 개발자 또는 외부 하청으로 구현 가능하다.

#### 보험 청구 및 수납

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (Active Record 패턴) 또는 부분 하청 |
| 근거 | HIRA 청구 규칙은 공통이지만 병원별 수가 체계와 수납 정책에 따른 커스터마이징이 필요하여 완전한 외부 솔루션 채택은 어렵다 |
| 설계 방향 | 청구 규칙 처리는 HIRA 연동 API에 ACL 적용, 수납 기능은 CRUD 중심 |
| 투자 수준 | 중간 -- 주니어 개발자 또는 외부 하청 배치 가능, RAD 프레임워크(Django Admin 등) 활용 |

#### 환자 포털

| 항목 | 내용 |
|------|------|
| 전략 | 사내 구현 (Transaction Script 패턴) 또는 하청 |
| 근거 | 핵심 도메인의 데이터를 읽기 전용으로 노출하는 프레젠테이션 계층이다. 자체 비즈니스 로직이 거의 없다 |
| 설계 방향 | 예약/EMR 컨텍스트의 데이터를 CQRS 읽기 모델로 제공, 별도의 도메인 모델 불필요 |
| 투자 수준 | 낮음 -- 하청 또는 주니어 개발자, UI/UX에만 집중 |

### 3.3 일반 하위 도메인 -- 외부 솔루션 채택

일반 도메인은 모든 조직이 동일하게 해결하는 알려진 문제다. 외부 솔루션 또는 오픈소스를 활용하여 구현 비용을 최소화한다.

#### 사용자 인증 및 권한 관리

| 항목 | 내용 |
|------|------|
| 전략 | 외부 솔루션 채택 |
| 후보 | Keycloak, Auth0, AWS Cognito, 또는 병원 기존 SSO 시스템 연동 |
| 근거 | OAuth2, OIDC, RBAC 등 표준화된 프로토콜이 존재하며 사내 구현의 이점이 없다. 보안 전문성이 필요한 영역이므로 검증된 외부 솔루션이 오히려 더 안전하다 |
| 설계 방향 | 외부 인증 시스템과의 연동에 ACL 적용하여 외부 모델(사용자 DTO)이 내부 도메인 모델을 오염시키지 않도록 차단 |
| 투자 수준 | 최소 -- 통합 설정 및 ACL 구현에만 집중 |

## 5. 바운디드 컨텍스트 경계 (초안)

하위 도메인 분류를 기반으로, 바운디드 컨텍스트 경계를 다음과 같이 설계한다. 하위 도메인과 바운디드 컨텍스트를 1:1로 매핑하는 것을 기본으로 하되, 도메인 간 용어 충돌이 발생하는 지점을 경계로 삼는다.

| 바운디드 컨텍스트 | 대응 하위 도메인 | 유비쿼터스 언어 예시 |
|-----------------|----------------|-------------------|
| 예약 컨텍스트 (Scheduling) | 진료 예약 및 대기열 관리 | 예약(Appointment), 슬롯(Slot), 대기열(WaitingQueue), 호출(CallIn) |
| 임상 기록 컨텍스트 (Clinical Records) | 전자 의무 기록(EMR) | 의무기록(MedicalRecord), 진단(Diagnosis), 검사(Examination), 소견(Finding) |
| 처방 컨텍스트 (Prescribing) | 처방전 발행 및 약국 연동 | 처방(Prescription), 약품(Medication), DUR검증(DURCheck), 조제(Dispensing) |
| 수술 관리 컨텍스트 (Surgery) | 수술 스케줄링 및 수술실 자원 관리 | 수술일정(SurgerySchedule), 수술실(OperatingRoom), 수술팀(SurgicalTeam) |
| 청구/수납 컨텍스트 (Billing) | 보험 청구 및 수납 | 청구(Claim), 수납(Payment), 수가(FeeSchedule), 급여(Coverage) |
| 환자 포털 컨텍스트 (Patient Portal) | 환자 포털 | 내 예약(MyAppointment), 검사결과(TestResult) -- 다른 컨텍스트의 용어를 환자 관점으로 재정의 |
| 인증 컨텍스트 (Identity) | 사용자 인증 및 권한 관리 | 사용자(User), 역할(Role), 권한(Permission) -- 외부 솔루션 모델 |

**용어 충돌 사례** -- "환자(Patient)"라는 용어가 컨텍스트마다 다른 의미를 갖는다:
- 예약 컨텍스트: 예약자(Booker) -- 예약을 잡고 대기하는 사람
- 임상 기록 컨텍스트: 환자(Patient) -- 진료를 받고 의무 기록이 생성되는 대상
- 청구/수납 컨텍스트: 수납 대상자(Payer) -- 비용을 부담하는 주체
- 환자 포털 컨텍스트: 회원(Member) -- 포털에 로그인하여 정보를 조회하는 사용자

## 6. 컨텍스트 맵 (초안)

### 연동 관계

| 업스트림 | 다운스트림 | 연동 패턴 | 근거 |
|---------|-----------|----------|------|
| 예약 컨텍스트 | 임상 기록 컨텍스트 | 고객-공급자(Customer-Supplier) | 예약 확정 시 진료 기록 생성을 트리거한다. 임상 기록이 예약 데이터의 소비자다. |
| 임상 기록 컨텍스트 | 처방 컨텍스트 | 파트너십(Partnership) | 진료와 처방은 밀접하게 결합되어 있으며, 양쪽의 변경이 상호 영향을 준다. |
| 처방 컨텍스트 | 외부 약국 시스템 | ACL(충돌 방지 계층) | 외부 약국 시스템의 모델을 제어할 수 없으므로 ACL로 내부 모델을 보호한다. |
| 예약 컨텍스트 | 수술 관리 컨텍스트 | 고객-공급자(Customer-Supplier) | 수술 예약은 일반 예약의 특수 형태로, 예약 슬롯 데이터를 소비한다. |
| 임상 기록 컨텍스트 | 청구/수납 컨텍스트 | 고객-공급자(Customer-Supplier) | 진료/검사 완료 이벤트가 청구 데이터를 생성한다. |
| 청구/수납 컨텍스트 | 외부 HIRA 시스템 | ACL(충돌 방지 계층) + 순응주의자(Conformist) | HIRA 청구 프로토콜은 변경할 수 없으므로 순응하되, 내부 모델 보호를 위해 ACL을 둔다. |
| 핵심 컨텍스트들 | 환자 포털 컨텍스트 | OHS(오픈 호스트 서비스) + Published Language | 여러 핵심 컨텍스트가 포털에 데이터를 제공한다. 공개 API + JSON Schema로 표준화한다. |
| 인증 컨텍스트 | 모든 컨텍스트 | ACL(충돌 방지 계층) | 외부 인증 솔루션의 모델이 각 도메인 모델을 오염시키지 않도록 ACL을 적용한다. |

## 7. 솔루션 전략 요약표

| 하위 도메인 | 유형 | 구현 패턴 | 솔루션 전략 | 인력 배치 |
|-----------|------|----------|------------|----------|
| 진료 예약 및 대기열 관리 | 핵심 | 도메인 모델 | 사내 구현 | 시니어 개발자 + 도메인 전문가 |
| 전자 의무 기록(EMR) | 핵심 | 도메인 모델 (이벤트 소싱 검토) | 사내 구현 | 시니어 개발자 + 의료진 |
| 처방전 발행 및 약국 연동 | 핵심 | 도메인 모델 + ACL | 사내 구현 | 시니어 개발자 + 약제부 |
| 수술 스케줄링 및 수술실 자원 관리 | 핵심 | 도메인 모델 + Cohesive Mechanism | 사내 구현 | 시니어 개발자 + 수술실 운영팀 |
| 보험 청구 및 수납 | 지원 | Active Record / Transaction Script | 사내 구현 또는 부분 하청 | 주니어 개발자 또는 하청 |
| 환자 포털 | 지원 | Transaction Script + CQRS 읽기 모델 | 하청 가능 | 주니어 개발자 또는 하청 |
| 사용자 인증 및 권한 관리 | 일반 | 외부 솔루션 + ACL | Keycloak/Auth0 등 외부 솔루션 | 통합 설정만 |
