# DDD 리뷰: 온라인 경매 시스템 도메인 모델

## 잘 된 부분

- `Auction`이 입찰 목록(`bids`)을 내부에 포함하여 "경매에는 입찰이 있다"는 도메인 개념을 반영하고 있다.
- `place_bid`에서 현재가보다 높은 금액만 입찰 가능하도록 비즈니스 규칙을 검증하고 있다.

---

## 리뷰 체크리스트 점검 결과

### 1. 바운디드 컨텍스트 경계가 명확한가

- [x] **위반 확인**

[바운디드 컨텍스트 경계 부재] -- `Auction` 하나의 클래스가 경매(Bidding), 결제(Payment), 배송(Shipping), 리뷰(Review) 등 최소 4개의 서로 다른 하위 도메인 관심사를 모두 포함하고 있다. 경매 컨텍스트에서 "결제"와 "배송"은 전혀 다른 유비쿼터스 언어를 사용하는 별도의 바운디드 컨텍스트다. 이를 하나의 모델에 합치면 각 영역의 변경이 다른 영역에 파급되어 복잡성이 통제 불가능해진다.

### 2. 애그리거트가 너무 크지 않은가

- [x] **위반 확인**

[Vernon 규칙 2: 작은 애그리거트를 설계하라] -- `Auction`이 `bids`, `payment`, `shipping`, `reviews`를 모두 내부에 포함하고 있다. Vernon은 "루트 엔티티와 최소한의 속성/값 객체로 제한하라. 올바른 최소치는 일관성을 유지하는 데 필요한 만큼이며, 그 이상은 아니다"라고 말한다. 입찰 내역이 수천 건이 되면 경매 하나를 로딩할 때마다 전체 입찰 목록을 메모리에 올려야 하며, 동시 입찰 시 경합(contention)이 발생한다. `reviews`는 경매 종료 후 별도 생명주기를 가지므로 경매의 불변식과 무관하다.

### 3. 애그리거트 간 직접 참조가 아닌 ID 참조를 사용하는가

- [x] **위반 확인**

[Vernon 규칙 3: 다른 애그리거트는 ID로만 참조하라] -- `self.seller`가 User 객체를 직접 참조하고, `self.item`이 Item 객체를 직접 참조하며, `self.payment`가 Payment 객체를, `self.shipping`이 Shipping 객체를 직접 참조하고 있다. 직접 객체 참조 대신 `seller_id: str`, `item_id: str`처럼 식별자로 참조하면 결합도가 낮아지고, 로딩 시간과 메모리 사용이 줄어든다.

### 4. 빈혈 도메인 모델이 아닌가

- [x] **위반 확인**

[빈혈 도메인 모델 안티패턴] -- `Auction` 클래스는 데이터만 보유하고 비즈니스 로직이 전혀 없다. 입찰 검증(`amount <= auction.get_current_price()`), 상태 전이(`auction.status = "closed"`), 낙찰자 결정(`max(auction.bids, ...)`) 등 모든 핵심 비즈니스 로직이 `AuctionService`에 분산되어 있다. Millett는 이를 "가장 흔한 DDD 실패 사례"로 지적한다. 비즈니스 규칙은 엔티티 안에 캡슐화되어야 한다. 예를 들어 `Auction.place_bid()`, `Auction.close()` 메서드가 애그리거트 내부에 존재해야 한다.

### 5. 값 객체로 표현할 수 있는 것이 엔티티로 되어 있지 않은가

- [x] **위반 확인**

[값 객체 미사용] -- `start_price`가 `int` 원시 타입으로 선언되어 있다. 금액은 통화(currency)와 함께 다뤄야 하는 개념적으로 완전한 하나이며, `Money` 값 객체로 표현해야 한다. 값 객체는 자기 검증(음수 방지 등)과 연산(더하기, 비교)을 캡슐화하여 원시 타입이 분산시키는 유효성 검사 로직을 응집시킨다. 마찬가지로 `status`가 문자열(`"active"`, `"closed"`)로 관리되고 있는데, `AuctionStatus` Enum 값 객체로 표현하면 유효하지 않은 상태 전이를 컴파일 타임에 방지할 수 있다.

### 6. 도메인 이벤트로 처리해야 할 것이 직접 호출로 되어 있지 않은가

- [x] **위반 확인**

[Vernon 규칙 4: 결과적 일관성을 사용하여 경계 밖을 업데이트하라] -- `close_auction`에서 경매 종료 시 `Payment.create()`와 `Shipping.create()`를 동기적으로 직접 호출하고 있다. 결제와 배송은 경매 애그리거트의 불변식이 아니다. 경매가 종료되면 `AuctionClosedEvent`를 발행하고, 결제 컨텍스트와 배송 컨텍스트가 각각 이 이벤트를 구독하여 결과적 일관성으로 처리해야 한다. 현재 방식은 결제 시스템 장애가 경매 종료 자체를 실패시키는 결함을 내포하고 있다.

### 7. 유비쿼터스 언어가 코드에 반영되어 있는가

- [x] **위반 확인**

[유비쿼터스 언어 미반영] -- `update_status()`는 비즈니스 의도를 드러내지 않는 기술적 이름이다. Evans는 `updateStatus()` 대신 `confirm()`, `cancel()`처럼 비즈니스 의도를 드러내는 이름을 사용하라고 강조한다. 경매 도메인에서는 `open()`, `close()`, `cancel()`, `extend()` 등의 용어가 적절하다. 또한 `place_bid`가 서비스에 있지만 경매 도메인에서 "입찰하다"는 경매 자체의 행위이므로 `Auction.receive_bid()` 또는 `Auction.place_bid()`가 자연스럽다.

### 8. 하위 도메인 유형에 맞는 복잡성 수준을 적용하고 있는가

- [x] **위반 확인**

[하위 도메인 유형 미분류] -- 경매(입찰/낙찰)는 이 시스템의 핵심(Core) 도메인으로 정교한 도메인 모델이 필요하지만, 현재는 빈혈 모델로 구현되어 핵심 도메인에 요구되는 복잡성 수준을 충족하지 못한다. 반면 결제와 배송은 일반(Generic) 또는 지원(Supporting) 하위 도메인으로, 외부 솔루션을 활용하거나 별도 컨텍스트로 분리하여 핵심 도메인의 복잡성을 줄여야 한다.

## 소견 요약

| # | 원칙 | 위반 내용 | 심각도 |
|---|------|----------|--------|
| 1 | 바운디드 컨텍스트 경계 | 경매/결제/배송/리뷰가 하나의 모델에 혼재 | 높음 |
| 2 | Vernon 규칙 2 (작은 애그리거트) | bids, payment, shipping, reviews를 모두 포함하는 거대 애그리거트 | 높음 |
| 3 | Vernon 규칙 3 (ID 참조) | User, Item, Payment, Shipping 객체 직접 참조 | 높음 |
| 4 | 빈혈 도메인 모델 | 모든 비즈니스 로직이 서비스에 분산 | 높음 |
| 5 | 값 객체 미사용 | 금액이 int, 상태가 문자열 원시 타입 | 중간 |
| 6 | Vernon 규칙 4 (결과적 일관성) | 결제/배송 생성을 동기 직접 호출 | 높음 |
| 7 | 유비쿼터스 언어 | update_status 등 기술적 명명 | 중간 |
| 8 | 하위 도메인 유형 | 핵심 도메인에 빈혈 모델, 일반 도메인 미분리 | 중간 |

전체 8개 항목 중 8개 위반이 확인되었다. 가장 시급한 개선 순서는 (1) 바운디드 컨텍스트 분리, (2) 애그리거트 축소 + ID 참조 전환, (3) 빈혈 모델을 풍부한 도메인 모델로 전환, (4) 도메인 이벤트 도입 순이다.
