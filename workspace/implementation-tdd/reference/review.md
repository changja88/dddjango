# TDD 의사결정 문서: Internal vs External 상충 분석

---

### 1. Mock 객체의 역할과 가치 평가

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | Unit Testing Principles (Khorikov) |
| 주장 | Mock은 가독성 향상 도구이자 유용한 테스팅 패턴이다 | 통신 기반 테스트(Mock 중심)는 세 가지 테스트 스타일 중 가장 낮은 우선순위다 |

**Internal 근거**: Mock 객체의 가치를 "가독성"에 둔다. 사실적 데이터가 가득한 DB보다 Mock이 왜 14개가 올바른 답인지 더 명확하게 보여준다고 설명한다. Mock을 여러 테스팅 패턴(셀프 션트, 크래시 테스트 더미 등)과 동등한 수준의 도구로 다루며, 사용 빈도나 우선순위에 대한 제한을 두지 않는다.

**External 근거**: Khorikov는 테스트 스타일을 출력 기반 > 상태 기반 > 통신 기반 순서로 명확히 서열화한다. Mock 중심의 통신 기반 테스트는 회귀 방지 "중간", 리팩토링 내성 "낮음", 유지보수성 "낮음"으로 세 항목 모두에서 열세다. 가능하면 비즈니스 로직을 순수 함수로 추출하여 출력 기반 테스트를 극대화하라고 권고한다.

**추천**: External ▶ (Mock은 외부 의존성 격리에 한정하고, 핵심 로직은 출력/상태 기반 테스트를 우선한다)

### 2. 테스트 작성 순서: Assert First vs AAA 패턴

**상충 유형**: 모순

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | The Art of Unit Testing (Osherove) |
| 주장 | 단언(assert)을 제일 먼저 쓰고, 거꾸로 올라가며 설정을 채운다 | Arrange-Act-Assert 순서로, 준비부터 시작하여 순방향으로 작성한다 |

**Internal 근거**: "단언 우선(Assert First)" 패턴을 권장한다. 완료 시 통과해야 할 단언부터 작성하고, reply는 어디서 오는가 -> reader에서, reader는 어디서 오는가 -> 서버 접속, 서버를 먼저 열어야 한다... 식으로 역방향으로 필요한 설정을 도출한다. 결과를 먼저 정의함으로써 테스트의 목적을 명확히 하는 데 초점을 둔다.

**External 근거**: Osherove의 AAA 패턴은 Arrange(준비) -> Act(실행) -> Assert(검증)의 순방향 흐름을 제시한다. 테스트의 가독성을 높이기 위해 세 단계를 명확히 분리하고, 최종 코드의 읽기 순서가 위에서 아래로 자연스럽게 흘러야 한다는 관점이다.

**추천**: 병합 (사고 과정은 Assert First로 목적부터 정하되, 최종 코드는 AAA 순서로 정리한다)

### 3. TDD 개발 방향: Inside-Out 단독 vs Inside-Out + Outside-In 병용

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | GOOS (Freeman & Pryce), Mocks Aren't Stubs (Fowler) |
| 주장 | "아는 것에서 모르는 것으로" 방향, Inside-Out 접근만 다룬다 | Inside-Out과 Outside-In 두 방향 모두 유효하며 상황에 따라 선택한다 |

**Internal 근거**: "한 단계 테스트"에서 "아는 것에서 모르는 것으로 방향을 잡는다"고 명시하며, 도메인 핵심부터 시작하여 바깥으로 나아가는 Inside-Out 접근만을 다룬다. "시작 테스트"에서도 가장 단순한 경우(빈 장바구니 등)부터 점진적으로 확장하는 Bottom-Up 방식을 취한다.

**External 근거**: Fowler는 고전 학파(Inside-Out)와 런던 학파(Outside-In)를 동등하게 구분하고, Freeman & Pryce는 Outside-In TDD를 이중 루프(인수 테스트 + 단위 테스트)와 Walking Skeleton으로 체계화한다. External은 순수 도메인 로직에는 고전 학파, 새 기능 전체 설계 탐색에는 Outside-In을 권장하는 상황별 선택 가이드를 제공한다.

**추천**: External ▶ (두 방향 모두 알고 상황에 따라 선택하는 것이 실전에 유리하다)

### 4. 회귀 테스트의 위상: 사후 대응 도구 vs 테스트 품질의 핵심 기둥

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | Unit Testing Principles (Khorikov) |
| 주장 | 회귀 테스트는 시스템 장애 보고 시 작성하는 사후 대응 패턴이다 | 회귀 방지(Protection against Regressions)는 좋은 테스트의 4대 기둥 중 하나다 |

**Internal 근거**: 회귀 테스트를 "빨간 막대 패턴" 중 하나로 분류하며, "시스템 장애가 보고될 때 가장 먼저 할 일"로 정의한다. 즉, 버그가 발견된 후에 그 버그를 재현하는 테스트를 작성하는 사후 대응적 성격으로 다룬다.

**External 근거**: Khorikov는 회귀 방지를 테스트 품질을 평가하는 4대 기둥의 첫 번째로 격상시킨다. 모든 테스트가 처음부터 갖춰야 할 속성이며, 코드 커버리지와 실행되는 코드량으로 측정한다. 회귀 방지는 사후 대응이 아니라 테스트 설계 시점부터 고려해야 할 설계 원칙이다.

**추천**: External ▶ (회귀 방지를 테스트 설계의 기본 원칙으로 내재화하는 것이 예방적 품질 관리에 효과적이다)

### 5. 리팩토링과 테스트의 관계: 암묵적 전제 vs 명시적 품질 기둥

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | Unit Testing Principles (Khorikov) |
| 주장 | 리팩토링 후 초록 막대로 돌아가면 된다 (테스트가 깨지지 않음을 암묵적으로 전제) | 리팩토링 내성은 테스트 품질의 독립적 기둥이며, Mock 과용이 이를 훼손한다 |

**Internal 근거**: Red-Green-Refactor 사이클에서 "올바르게 만든다 -- 중복을 제거하고 초록 막대로 되돌리자"로 설명한다. 리팩토링 시 테스트가 당연히 통과할 것이라는 전제 하에, 테스트 자체가 리팩토링에 취약해질 수 있는 문제는 다루지 않는다.

**External 근거**: Khorikov는 리팩토링 내성(Resistance to Refactoring)을 독립적 품질 기둥으로 정의하고, 거짓 양성(false positive) 빈도로 측정한다. 특히 Mock 과용이 구현에 결합된 테스트를 만들어 "내부 구현을 바꿀 때마다 테스트가 깨지는" 문제를 구체적으로 경고한다. 회귀 방지 + 빠른 피드백 조합이 리팩토링 내성을 희생시키는 트레이드오프도 CAP 정리 유사성으로 명시한다.

**추천**: External ▶ (리팩토링 내성을 명시적으로 의식하고 테스트 설계에 반영해야 장기 유지보수 비용이 줄어든다)

### 6. 테스트 격리 전략: 실행 순서 독립 vs 공유 상태 제거

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | 테스트주도 개발 (Kent Beck) | xUnit Test Patterns (Meszaros) |
| 주장 | 각 테스트는 실행 순서에서 독립적이어야 하며, 환경 세팅이 쉽고 빨라야 한다 | 순서 독립만으로는 불충분하며, Erratic Test 냄새의 근본 원인인 공유 상태 자체를 제거해야 한다 |

**Internal 근거**: "격리된 테스트" 패턴에서 "각각의 테스트는 서로 독립적이어야 하며, 실행 순서에서도 독립적이어야 한다"는 원칙과 "환경 세팅이 쉽고 빨라야 한다"는 실용적 지침을 제시한다. 격리의 달성 방법보다는 격리의 목표를 선언하는 데 초점을 둔다.

**External 근거**: Meszaros는 Erratic Test(불안정 테스트) 냄새를 정의하고, 그 원인을 전역 공유 상태로 진단한다. 해결책으로 pytest fixture를 사용한 테스트별 독립 상태 생성을 구체적으로 제시하며, "공유 상태 제거"라는 구현 수준의 전략을 명시한다.

**추천**: 병합 (Internal의 격리 원칙을 목표로 삼되, External의 공유 상태 제거를 구체적 실행 전략으로 채택한다)
