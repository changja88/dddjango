# TDD 여부 분석: StringCalculator

## 결론: TDD로 작성되었을 가능성이 높다

이 코드는 전형적인 TDD Kata인 **String Calculator Kata** (Roy Osherove가 고안)의 구현체다. 단순히 유명한 카타라는 사실 외에도, 코드 자체에서 TDD의 흔적이 여러 군데 관찰된다.

---

## TDD의 흔적

### 1. 테스트가 점진적 복잡도 순서로 나열되어 있다

테스트 순서가 TDD의 전형적인 "baby step" 패턴을 따른다:

| 순서 | 테스트 | 복잡도 |
|------|--------|--------|
| 1 | 빈 문자열 -> 0 | 가장 단순한 케이스 (degenerate case) |
| 2 | 숫자 하나 | 최소 입력 |
| 3 | 숫자 둘 | 기본 구분자 동작 |
| 4 | 숫자 여러 개 | 일반화 |
| 5 | 개행 구분자 | 요구사항 추가 |
| 6 | 커스텀 구분자 | 요구사항 추가 |
| 7-8 | 음수 예외 | 에러 처리 |
| 9-10 | 1000 초과 무시 | 경계값 처리 |

이 순서는 test-last로 작성할 때 나타나는 패턴(기능 단위 묶음, 경계값 한꺼번에 처리)과 다르다. TDD에서는 "다음에 실패할 가장 단순한 테스트"를 추가하며 진행하기 때문에 복잡도가 단조 증가하는 경향이 있고, 이 코드가 정확히 그 패턴이다.

### 2. 각 테스트가 정확히 하나의 동작만 검증한다

모든 테스트가 단일 assert 또는 단일 예외 검증으로 구성되어 있다. test-last 방식에서는 하나의 테스트에 여러 시나리오를 몰아넣는 경우가 흔한데, 여기서는 그런 흔적이 없다.

### 3. String Calculator Kata의 단계와 정확히 일치한다

Roy Osherove의 String Calculator Kata는 TDD 연습용으로 설계된 것으로, 다음 단계를 따른다:

1. 빈 문자열
2. 숫자 하나
3. 숫자 둘
4. 임의 개수
5. 개행 구분자
6. 커스텀 구분자
7. 음수 예외
8. 1000 초과 무시

테스트 목록이 이 단계와 1:1로 대응된다. 이는 카타의 가이드라인을 따라 TDD로 진행했음을 강하게 시사한다.

### 4. 프로덕션 코드에 불필요한 추상화가 없다

`StringCalculator` 클래스는 테스트가 요구하는 것 이상의 코드가 없다. 메서드가 `add` 하나뿐이고, 미래를 위한 확장 포인트나 유틸리티 메서드가 없다. 이는 "테스트를 통과시키기 위한 최소한의 코드만 작성한다"는 TDD 원칙(YAGNI)과 일치한다.

### 5. 에러 메시지가 테스트에서 먼저 정의된 느낌이다

`'음수는 허용되지 않습니다'`라는 에러 메시지가 테스트의 `match` 패턴과 프로덕션 코드에서 동일하게 사용된다. TDD에서는 테스트에서 기대값을 먼저 정하고 구현을 맞추기 때문에 이런 일관성이 자연스럽게 나타난다.

---

## test-last와 구별되는 점

test-last로 작성된 코드에서 흔히 보이는 특징들이 이 코드에는 부재하다:

- **통합적 테스트 없음**: test-last에서는 "전체 기능이 동작하는지" 확인하는 큰 테스트가 먼저 오는 경향이 있다. 여기서는 그런 테스트가 없다.
- **테스트 간 중복 제거 과도하지 않음**: `setUp`이나 fixture로 `calc`를 공유하지 않고 매 테스트마다 `StringCalculator()`를 생성한다. TDD에서는 각 테스트의 독립성을 중시하기 때문에 이런 패턴이 자연스럽다. (반면 test-last에서는 리팩터링 과정에서 중복을 제거하는 경우가 많다.)
- **구현 세부사항 테스트 없음**: `_parse_delimiter` 같은 내부 메서드를 별도로 테스트하지 않는다. TDD에서는 외부 동작(public API)만 테스트하는 것이 원칙이다.

---

## 미세한 의문점

완전히 확신할 수 없는 부분도 있다:

- **테스트와 프로덕션 코드가 같은 파일에 있다**: 실제 TDD 실무에서는 분리하는 것이 일반적이다. 다만 카타 연습이나 교육 목적에서는 같은 파일에 두는 것이 흔하다.
- **리팩터링 흔적이 약하다**: TDD의 Red-Green-Refactor 중 Refactor 단계의 흔적(예: 헬퍼 메서드 추출, 구분자 파싱 분리)이 보이지 않는다. 프로덕션 코드가 비교적 단순해서 리팩터링 필요성이 낮았을 수도 있고, 리팩터링 단계를 건너뛰었을 수도 있다.

## 최종 판단

**TDD로 작성되었을 가능성: 높음 (85~90%)**

근거 요약:
- String Calculator Kata라는 TDD 전용 연습 문제의 정확한 구현
- 테스트의 점진적 복잡도 증가 패턴
- 각 테스트의 단일 책임 원칙 준수
- 프로덕션 코드의 YAGNI 원칙 준수
- test-last에서 나타나는 전형적 패턴의 부재
