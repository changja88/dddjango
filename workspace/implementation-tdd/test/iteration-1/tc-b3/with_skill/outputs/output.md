# TDD 흔적 분석: StringCalculator

## 결론: TDD로 작성되었을 가능성이 높다

이 코드는 TDD의 고전적 카타(kata)인 **String Calculator Kata** (Roy Osherove 제안)를 따르고 있으며, TDD의 흔적이 다수 관찰된다. test-last로 작성된 코드에서 나타나는 전형적 패턴과는 명확하게 구분된다.

---

## TDD 흔적 (긍정적 증거)

### 1. 테스트 진행 순서가 Red Bar Pattern의 "시작 테스트"와 "한 단계 테스트"를 정확히 따른다

[Red Bar Patterns - 시작 테스트] -- 오퍼레이션이 아무 일도 하지 않는 경우를 먼저 테스트한다.

테스트 순서가 다음과 같이 점진적으로 복잡해진다:

1. `test_empty_string_returns_zero` -- 가장 단순한 경우 (null operation)
2. `test_single_number` -- 단일 입력
3. `test_two_numbers` -- 두 개 입력
4. `test_multiple_numbers` -- 여러 개 입력
5. `test_newline_delimiter` -- 새로운 구분자
6. `test_custom_delimiter` -- 커스텀 구분자
7. `test_negative_number_raises` -- 에러 처리
8. `test_multiple_negatives_shows_all` -- 에러 상세화
9. `test_numbers_over_1000_ignored` -- 경계값 필터링
10. `test_exactly_1000_included` -- 경계값 정밀 검증

이 순서는 "아는 것에서 모르는 것으로" 이동하는 TDD의 한 단계 테스트 패턴과 일치한다. test-last 코드에서는 이런 체계적 진행이 아니라, 구현 완료 후 기능 단위로 뭉뚱그려 테스트를 작성하는 경향이 있다.

### 2. Green Bar Pattern의 적용 흔적이 보인다

[Green Bar Patterns - 변환 우선순위 전제] -- 더 단순한 변환을 우선 적용하면 TDD 교착 상태를 줄일 수 있다.

구현 코드의 구조가 점진적 변환의 결과물처럼 보인다:

- 빈 문자열 검사 (`if not numbers: return 0`) -- `nil -> constant` 변환
- 기본 구분자로 분리 (`split(delimiter)`) -- `constant -> scalar` 변환
- 커스텀 구분자 파싱 (`if numbers.startswith('//')`) -- `unconditional -> if` 변환
- 음수 검증 로직 -- 이후 단계에서 추가된 요구사항 처리

각 변환이 대응하는 테스트와 1:1로 매핑되며, 이는 테스트가 구현을 주도한 전형적 패턴이다.

### 3. 테스트 하나가 정확히 하나의 행위를 검증한다

[Four Pillars - 유지보수성] -- 테스트를 이해하고 실행하기 쉬운가.

각 테스트 메서드가 하나의 행위만 검증하며, 이름이 검증 대상 행위를 명확히 서술한다. Eager Test 냄새가 없다. TDD에서 "하나의 실패하는 테스트를 작성하고, 통과시키고, 다음으로 넘어가는" 리듬의 산물이다.

### 4. "하나에서 여러 개로" 패턴이 관찰된다

[Red Bar Patterns - 하나에서 여러 개로] -- 먼저 단일 항목에 대해 구현하고 나서 컬렉션으로 확장한다.

`test_single_number` -> `test_two_numbers` -> `test_multiple_numbers`의 진행은 스칼라에서 컬렉션으로의 확장 패턴을 그대로 따른다.

### 5. 경계값 테스트가 별도로 분리되어 있다

[Red Bar Patterns - 또 하나의 테스트] -- 구현 도중 새로운 아이디어가 떠오르면 테스트 목록에 추가한다.

`test_numbers_over_1000_ignored`와 `test_exactly_1000_included`가 별도 테스트로 존재한다. 특히 1000과 1001의 경계를 나눠서 테스트한 것은 TDD 과정에서 "1000 이하만 합산"이라는 요구사항을 구현할 때 경계값을 삼각측량(Triangulation)한 흔적이다.

### 6. 고전적 TDD 카타를 충실히 따른다

이 코드는 Roy Osherove의 String Calculator Kata의 표준 단계를 정확히 밟고 있다:
- Step 1: 빈 문자열, 하나, 둘
- Step 2: 임의 개수
- Step 3: 개행 구분자
- Step 4: 커스텀 구분자
- Step 5: 음수 예외
- Step 6: 1000 초과 무시

이 카타 자체가 TDD 연습용으로 설계된 것이며, 테스트 순서가 카타의 단계와 일치한다는 것은 TDD 프로세스를 따랐다는 강력한 증거다.

### 7. 테스트 스타일이 출력 기반(Output-based)이다

[Four Pillars - 세 가지 테스트 스타일] -- 출력 기반 > 상태 기반 > 통신 기반 순으로 선호하라.

모든 테스트가 `add()` 메서드의 반환값 또는 예외를 검증한다. Mock이 전혀 없고, 순수 함수의 입출력만 검증한다. 이는 고전 학파 TDD의 전형적 특성이며, 리팩토링 내성이 높다.

## 주의할 점 (TDD와 무관하거나 약한 증거)

### 구현 코드가 최종 리팩토링된 상태이다

현재 `StringCalculator.add()` 메서드는 깔끔하게 정리된 최종 상태다. TDD 과정에서는 중간에 Fake It이나 상수 반환 같은 단계가 있었을 것이나, 최종 코드에서는 리팩토링이 완료되어 그 흔적이 남아 있지 않다. 이것 자체는 정상적이다 -- TDD의 Refactor 단계에서 중간 구현은 제거되기 때문이다.

### 테스트 코드에 약간의 중복이 있다

[Test Smells - Test Code Duplication] -- 여러 테스트에서 동일한 설정/검증 코드가 반복됨.

`calc = StringCalculator()` 가 모든 테스트에서 반복된다. pytest fixture로 추출할 수 있으나, 이 정도는 테스트의 명시성(각 테스트가 독립적으로 읽힘)과의 트레이드오프이므로 심각한 문제는 아니다. 다만, Refactor 단계에서 이를 정리하지 않은 것은 TDD 리듬이 다소 느슨했을 수 있음을 시사한다.

## test-last로 작성된 코드와의 차이

test-last 코드에서 전형적으로 나타나는 패턴과 비교하면 이 코드가 TDD로 작성되었다는 판단이 더 명확해진다:

| test-last의 전형적 특징 | 이 코드에서 관찰되는가 |
|------------------------|---------------------|
| 테스트가 구현의 내부 구조를 반영 (메서드별 테스트) | 아니오 -- 행위 단위로 테스트 |
| 한 테스트에서 여러 기능을 한꺼번에 검증 (Eager Test) | 아니오 -- 한 테스트, 한 행위 |
| 테스트 순서에 논리적 진행이 없음 | 아니오 -- 단순에서 복잡으로 체계적 진행 |
| 경계값 테스트 누락 | 아니오 -- 1000/1001 경계 모두 검증 |
| 구현 완료 후 "커버리지 채우기" 식의 테스트 | 아니오 -- 각 테스트가 구현 단계와 대응 |
| Mock 과용 또는 구현 결합 | 아니오 -- 순수 출력 기반 테스트 |

---

## 최종 판단

**TDD 가능성: 높음 (90%)**

이 코드는 String Calculator Kata를 TDD로 수행한 결과물의 전형적 형태를 보인다. 테스트의 점진적 진행 순서, 각 테스트와 구현의 1:1 대응, 출력 기반 검증 스타일, 경계값 삼각측량 모두 TDD 프로세스의 산물이다. 남은 10%의 불확실성은 커밋 히스토리나 개발 과정 기록 없이는 "실제로 테스트를 먼저 작성했는지"를 100% 확인할 수 없기 때문이다 -- 숙련된 개발자가 TDD 패턴을 알고 있다면 test-last로도 이런 구조를 만들어낼 수 있다.

그러나 코드의 **구조적 증거**는 TDD를 강하게 지지한다.
