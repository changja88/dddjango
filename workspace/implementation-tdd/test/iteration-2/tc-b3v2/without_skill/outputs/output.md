# TDD vs Test-Last 분석: TokenManager

## 결론: Test-Last로 작성되었을 가능성이 높다

확신도: **약 75-80%** (test-last 쪽)

---

## 근거

### Test-Last를 시사하는 신호들

**1. 프로덕션 코드가 완결적이고 테스트가 그것을 "확인"하는 구조**

TDD에서는 실패하는 테스트를 먼저 쓰고, 그 테스트를 통과시키기 위한 최소한의 코드를 작성한다. 이 과정에서 프로덕션 코드는 점진적으로 성장하며, 불필요한 기능이 미리 들어가지 않는다. 그런데 이 코드의 `TokenManager`는 처음부터 완성된 형태로 보인다:

- `active_count()`에서 만료 토큰을 자동 정리하는 로직이 포함되어 있지만, 이 동작을 검증하는 테스트가 없다. TDD였다면 "만료된 토큰이 active_count에서 제외되는가"라는 테스트가 먼저 존재하고, 그 테스트를 통과시키기 위해 정리 로직이 추가되었을 것이다.
- `validate()`에서도 만료 토큰을 삭제하는 부수효과(side effect)가 있지만, "validate 후 해당 토큰이 내부 저장소에서 실제로 제거되었는가"를 직접 검증하는 테스트는 없다.

**2. 테스트가 공개 API의 표면을 고르게 훑는 패턴**

테스트 목록을 보면:
- create -> 반환값 포맷 확인
- validate -> 정상 / 미존재 / 만료
- revoke -> 존재 / 미존재
- active_count -> 기본 동작
- 기타: 서로 다른 유저 토큰 구분, 커스텀 TTL

이것은 이미 완성된 클래스의 메서드를 하나씩 살펴보며 "이 메서드는 이런 경우에 이렇게 동작해야 한다"를 나열한 전형적인 test-last 패턴이다. TDD에서는 보통 기능 요구사항 단위로 테스트가 나타나며, 메서드 단위가 아니라 행위(behavior) 단위로 묶이는 경향이 있다.

**3. 경계 조건 테스트의 깊이가 얕다**

TDD에서는 Red-Green-Refactor 사이클을 반복하면서 경계 조건을 점진적으로 발견하게 된다. 이 코드에서는:
- 같은 유저로 토큰을 여러 번 생성하는 경우 테스트 없음
- revoke 후 active_count가 줄어드는지 확인하는 테스트 없음
- TTL이 정확히 경계 시점(만료 직전/직후)에서의 동작 테스트 없음
- `datetime.now()`를 여러 번 호출하는 race condition 가능성에 대한 고려 없음

이런 빈틈은 "구현을 먼저 하고, 주요 경로만 테스트로 덮은" 패턴에서 자주 나타난다.

**4. 테스트에서 내부 구현 지식이 드러나지 않는다**

TDD에서 점진적으로 발전시킨 코드라면, 리팩토링 과정에서 테스트가 내부 구조 변화를 반영하며 함께 진화한 흔적이 남을 수 있다. 이 테스트들은 전부 순수하게 공개 인터페이스만 사용하고 있어서, 오히려 "완성된 API를 보고 테스트를 작성한" 느낌이 강하다.

**5. `time.sleep` 사용 패턴**

`test_expired_token_returns_none`에서 `ttl_minutes=0`으로 설정하고 `time.sleep(0.01)`을 쓰고 있다. TDD에서는 시간 의존성을 제어하기 위해 보통 시간을 주입하거나 mock을 사용한다. sleep을 쓰는 것은 "이미 있는 구현을 건드리지 않고 테스트만 추가한" 접근이다. TDD였다면 테스트 용이성을 위해 `datetime.now()` 대신 시간 소스를 주입받는 설계로 자연스럽게 흘러갔을 가능성이 높다.

---

### TDD였을 수도 있다고 볼 여지

- 테스트가 비교적 잘 정리되어 있고, 각 테스트가 하나의 관심사만 검증한다.
- 프로덕션 코드에 테스트되지 않는 복잡한 기능이 과도하게 들어있지는 않다.
- 테스트 파일과 프로덕션 코드가 같은 파일에 있는 것은 TDD 작업 흐름에서도 나타날 수 있는 구조이다.

---

### 불확실성 요인

코드 스냅샷만으로 작성 순서를 단정하는 것은 본질적으로 한계가 있다. 다음 요소가 있으면 판단이 달라질 수 있다:

- **git 커밋 이력**: 테스트와 구현의 커밋 순서가 가장 확실한 증거다.
- **리팩토링 이력**: TDD의 Refactor 단계 흔적이 있는지.
- **작성자의 의도 설명**: 동일한 최종 결과물이 TDD에서든 test-last에서든 나올 수 있다.

---

## 요약

| 항목 | 판단 |
|---|---|
| 전체 평가 | Test-Last 가능성 높음 (75-80%) |
| 핵심 근거 | 완결적 구현 + 표면적 API 커버리지 + 시간 의존성 미분리 + 경계 테스트 부족 |
| 불확실성 | 커밋 이력 없이는 확정 불가, 잘 정리된 TDD 결과물일 가능성도 배제할 수 없음 |
