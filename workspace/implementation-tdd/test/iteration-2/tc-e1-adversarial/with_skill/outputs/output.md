# TDD 관점 테스트 코드 리뷰: Money

## 잘한 점

이 코드는 TDD의 고전적인 예제인 Kent Beck의 Money 패턴을 충실히 따르고 있으며, 여러 측면에서 좋은 TDD 관행을 보여준다.

**Value Object 패턴의 올바른 적용.** `@dataclass(frozen=True)`로 불변성을 보장하고, `test_is_immutable`에서 이를 명시적으로 검증한다. Kent Beck의 테스트주도 개발에서 Value Object는 "객체가 생성된 이후 그 값이 절대 변하지 않게 하여 별칭 문제가 발생하지 않게 한다"고 정의하며, 이 코드는 이를 정확히 구현했다.

**고전 학파(Classical/Inside-Out) TDD의 적절한 선택.** 순수 도메인 로직에 대해 실제 객체와 상태/출력 기반 검증을 사용한다. Mock이 전혀 없으며, Khorikov의 권고(출력 기반 > 상태 기반 > 통신 기반)를 따르고 있다.

**출력 기반 테스트 스타일.** 모든 테스트가 SUT의 반환값 또는 예외를 검증한다. 이는 Khorikov의 4대 기둥 중 리팩토링 내성과 유지보수성을 극대화하는 가장 권장되는 스타일이다.

**불변성에 대한 독립적 검증.** `test_addition_returns_new_instance`와 `test_multiplication_returns_new_instance`가 원본 객체가 변경되지 않음을 확인한다. Value Object의 핵심 계약을 테스트로 보호하고 있다.

**테스트 격리.** 각 테스트가 독립적이며, 공유 가변 상태가 없다. 테스트 실행 순서에 무관하게 항상 동일한 결과를 보장한다.

## 개선이 필요한 점

### 1. 테스트가 프로덕션 코드와 함께 제시됨 -- TDD 사이클 증거 부재

[Red-Green-Refactor 사이클] -- 테스트와 프로덕션 코드가 완성된 상태로 한꺼번에 제시되어 있어, Red-Green-Refactor 사이클을 따랐는지 확인할 수 없다. TDD의 세 가지 법칙(실패하는 테스트 먼저 작성, 테스트를 통과시키는 최소한의 코드, 초록 막대에서 리팩토링)을 따랐다면, 테스트와 프로덕션 코드가 점진적으로 성장하는 과정이 보여야 한다. 현재 `Money` 클래스가 `plus`, `times`, 에러 처리를 모두 갖춘 완성형으로 존재하며, 이는 big-bang 구현의 징후다.

### 2. 점진적 개발 흔적 부재

[빨간 막대 패턴 - 시작 테스트] -- TDD에서는 "오퍼레이션이 아무 일도 하지 않는 경우를 먼저 테스트"하고, "아는 것에서 모르는 것으로" 진행한다. 이 코드의 테스트 순서가 TDD의 점진적 발전 경로를 반영하는지 불분명하다. TDD로 Money를 개발했다면 다음과 같은 진행이 자연스럽다:

1. Money 생성 (가장 단순한 경우)
2. 같은 통화 덧셈 (Fake It -> Triangulation -> Obvious Implementation)
3. 다른 통화 덧셈 거부 (에러 경로)
4. 곱셈

현재 코드는 이 경로를 따른 것처럼 보이지만, 프로덕션 코드가 이미 완성되어 있어 실제로 점진적으로 개발되었는지 확인할 수 없다.

### 3. 경계/엣지 케이스 테스트 부족

[빨간 막대 패턴 - 테스트 목록] -- 테스트 목록을 작성했다면 다음 경계 케이스들이 포함되었어야 한다:

- **음수 금액**: `Money(-1000, 'KRW')`가 유효한가? 허용한다면 그에 대한 테스트, 거부한다면 그에 대한 검증이 필요하다.
- **음수 배수**: `times(-1)`의 동작이 정의되지 않았다.
- **0원 생성**: `Money(0, 'KRW')`에 대한 명시적 테스트가 없다. `test_multiplies_by_zero`가 결과적으로 0원을 만들지만, 0원 자체의 생성과 동등성은 별도로 검증할 가치가 있다.
- **빈 문자열 통화**: `Money(1000, '')`에 대한 방어가 없다.
- **동등성의 대칭성/추이성**: Value Object로서 `Money(1000, 'KRW') == Money(1000, 'KRW')`를 명시적으로 테스트하고 있지 않다. `dataclass`가 이를 자동 생성하지만, Value Object의 핵심 계약을 테스트로 문서화하는 것이 TDD의 "설명 테스트" 원칙에 부합한다.

### 4. 테스트 데이터에서 의미 있는 차이 부족

[테스팅 패턴 - 테스트 데이터] -- "동일한 상수를 여러 의미로 쓰지 마라"는 원칙에서, `test_adds_same_currency`의 `Money(1000, 'KRW').plus(Money(2000, 'KRW'))`는 좋은 예다. 서로 다른 금액(1000, 2000)을 사용하여 어느 쪽이 결과에 반영되었는지 구분할 수 있다. 그러나 `test_multiplies_amount`에서 `Money(1000, 'KRW').times(3)`의 결과가 `Money(3000, 'KRW')`인데, 이 3000이 `1000 * 3`인지 `1000 + 2000`인지 테스트 자체만으로는 완전히 구분되지 않는다. 명백한 데이터 패턴을 적용하면 관계가 더 명확해진다:

```python
# 현재: 결과값만 제시
assert result == Money(3000, 'KRW')

# 개선: 계산 관계를 드러냄
assert result == Money(1000 * 3, 'KRW')
```

### 5. 테스트 이름이 행위를 충분히 서술하지 않음

[테스팅 패턴 - 테스트 명명 규칙] -- 현재 테스트 이름은 간결하지만, `[테스트 대상 단위]_[상태/조건]_[기대 행위]` 패턴을 완전히 따르지 않는다. 예를 들어:

| 현재 | 개선안 |
|------|--------|
| `test_adds_same_currency` | `test_plus__same_currency__returns_sum` |
| `test_rejects_different_currency` | `test_plus__different_currency__raises_value_error` |
| `test_multiplies_amount` | `test_times__positive_multiplier__returns_multiplied_money` |
| `test_multiplies_by_zero` | `test_times__zero_multiplier__returns_zero_amount` |

이는 테스트가 실패했을 때 이름만으로 무엇이 어떤 조건에서 왜 실패했는지 즉시 파악할 수 있게 해준다.

### 6. `assert`를 프로덕션 코드에서 에러 처리에 사용하는 것과의 비교

[Value Object 패턴] -- 레퍼런스의 Value Object 예제에서는 `assert self.currency == other.currency`를 사용하지만, 리뷰 대상 코드는 `ValueError`를 `raise`한다. 이 선택은 실제로 더 올바르다. `assert`는 `-O` 플래그로 비활성화될 수 있어 프로덕션에서 방어 로직이 사라질 수 있기 때문이다. TDD 관점에서, 이 설계 결정이 테스트(`test_rejects_different_currency`)에 의해 주도되었다면 좋은 사례다.

## 리뷰 체크리스트 점검 결과

| 점검 항목 | 판정 | 비고 |
|-----------|------|------|
| 테스트가 프로덕션 코드 이후에 작성됨 (test-last) | **판단 불가** | 테스트와 프로덕션 코드가 동시에 제시되어 순서를 확인할 수 없음 |
| Red-Green-Refactor 사이클 증거 없음 | **해당** | 완성된 코드만 존재, 점진적 발전 이력 부재 |
| 구현 세부사항에 결합된 테스트 (낮은 리팩토링 내성) | **해당 없음** | 모든 테스트가 공개 인터페이스의 반환값/예외만 검증 |
| 내부 협력자에 대한 Mock 과용 | **해당 없음** | Mock이 전혀 사용되지 않음. 고전 학파 접근에 부합 |
| 테스트 격리 누락 (공유 가변 상태) | **해당 없음** | 모든 테스트가 독립적이며 공유 상태 없음 |
| 테스트 냄새 | **경미** | Assertion Roulette -- `test_creates_with_amount_and_currency`에서 두 개의 assert가 한 테스트에 존재하지만, 동일 행위(생성)의 서로 다른 속성을 검증하므로 심각하지 않음 |
| 점진적 개발 없음 (big-bang 구현) | **해당** | 위 1번 참조 |
| 출력 기반 대신 통신 기반 테스트 사용 | **해당 없음** | 출력 기반 테스트를 올바르게 사용 |
| 경계/엣지 케이스 테스트 누락 | **해당** | 위 3번 참조. 음수, 빈 통화, 동등성 등 미검증 |
| 설계를 주도하지 않는 사후 테스트 | **판단 불가** | 테스트가 설계를 주도했는지 확인할 수 없음 |

## 종합 평가

이 테스트 코드의 **테스트 품질 자체는 높다**. 출력 기반 테스트, 실제 객체 사용, 테스트 격리, Value Object 패턴의 불변성 검증 등 고전 학파 TDD의 모범적인 특성을 갖추고 있다. Khorikov의 4대 기둥 관점에서 리팩토링 내성, 빠른 피드백, 유지보수성이 모두 우수하다.

그러나 **TDD 프로세스의 관점에서는 증거가 부족하다**. TDD는 결과물(테스트 + 프로덕션 코드)뿐 아니라 과정(Red-Green-Refactor 사이클의 점진적 반복)이 핵심이다. 현재 코드는 "좋은 테스트가 있는 코드"이지, "TDD로 개발된 코드"라고 단정하기 어렵다. Kent Beck이 말한 대로 "작동하는 것부터 먼저 해결하는 나누어서 정복하는 방식"의 흔적이 보이지 않는다.

**우선 개선 사항 3가지:**
1. 경계 케이스 테스트 추가 (음수 금액, 음수 배수, 동등성, 빈 통화)
2. 테스트 이름을 `[대상]__[조건]__[기대행위]` 형식으로 구체화
3. TDD 사이클 증거를 남기기 위해, 앞으로는 커밋 이력이나 테스트 목록으로 Red-Green-Refactor 과정을 기록할 것을 권장
