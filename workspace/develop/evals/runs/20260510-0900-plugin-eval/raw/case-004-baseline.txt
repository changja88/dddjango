아래 4개 요청은 서로 독립 요청으로 보고 순서대로 답합니다. 파일은 읽기만 했고 수정하지 않았습니다.

**1. DRF 말고 Ninja Router/Schema + Problem Details**

신규 API 기준은 DRF가 아니라 Django Ninja로 잡는 게 맞습니다.

- `Router`: HTTP adapter만 담당
- `Schema`: request/response 계약과 OpenAPI 표현 담당
- application service: 유스케이스 실행
- domain/application 예외: Problem Details로 변환

권장 형태:

```python
router = Router(tags=["orders"])

@router.post(
    "/orders",
    response={201: OrderResponseSchema, 400: ProblemDetails, 409: ProblemDetails},
)
def create_order(request, payload: CreateOrderSchema):
    try:
        order = create_order_service(payload.to_command(), actor=request.user)
    except DomainError as exc:
        raise problem(exc, status=409)

    return 201, OrderResponseSchema.from_domain(order)
```

Problem Details는 최소한 `type`, `title`, `status`, `detail`, `instance`를 맞추고, 도메인 코드가 필요하면 `code`나 `errors`를 extension field로 둡니다. Ninja validation error도 기본 응답 그대로 두지 말고 같은 Problem Details handler로 통일하는 편이 좋습니다.

**2. 모델 validation / 상태변경 / 외부 호출 경계**

모델에 남겨도 되는 것은 “도메인 불변식과 상태 전이”입니다.

- domain: 수량 양수, 주문 금액 계산, 취소 가능 상태인지, `PENDING -> PAID` 같은 상태 전이 규칙
- value object: 금액, 수량, 주소처럼 값 자체의 유효성이 의미인 것
- domain service: 특정 엔티티에 자연스럽게 붙지 않는 순수 비즈니스 정책
- application service: 객체 로드, 트랜잭션, 저장, 외부 provider 호출, idempotency, 이벤트 발행 조정
- API schema: HTTP 입력 모양 검증
- DB constraint: uniqueness, FK, not null, 동시성 보호

외부 호출은 모델에서 빼는 게 맞습니다. 모델 메서드는 `order.mark_paid(payment_id)`처럼 도메인 상태를 바꾸고, 결제 승인 API 호출은 application service가 provider port/adapter를 통해 조정해야 합니다.

**3. pytest 주문 생성 fixture / factory / fake / mock 경계**

fixture가 복잡해졌다면 “데이터 생성”과 “협력자 대체”가 섞였을 가능성이 큽니다.

- factory: 유효한 `Order`, `OrderLine`, `Customer` 같은 객체/DB row 생성
- fixture: 테스트 실행에 필요한 공통 wiring 제공
- fake: application service 테스트에서 in-memory repository/provider처럼 상태를 가진 대체 구현
- mock: 외부 payment provider 호출 여부, 실패, payload 같은 상호작용 검증
- domain test: mock 없이 실제 도메인 객체로 상태와 결과 검증
- API test: DB + factory + Ninja TestClient + 외부 provider mock
- application service test: fake repository/provider로 유스케이스 흐름 검증

복잡한 fixture 하나가 모든 주문 상태를 만들게 하지 말고, `order_factory(status=...)`, `order_line_factory(...)`, `fake_payment_provider.approve_next(...)`처럼 테스트 본문에서 시나리오가 보이게 나누는 게 좋습니다.

**4. payment provider에 repository/outbox가 필요한지**

repository와 outbox는 기본 세트가 아닙니다. 과하면 빼야 합니다.

repository가 필요한 경우:

- 도메인 관점의 컬렉션 추상화가 필요함
- application service를 ORM 없이 빠르게 테스트해야 함
- 저장소 교체나 복잡한 조회/저장 계약이 실제로 있음

단순 QuerySet wrapper라면 만들지 않는 게 낫습니다.

outbox가 필요한 경우:

- DB commit 이후 반드시 외부 메시지/이벤트를 잃지 않고 보내야 함
- 결제 승인 이후 재시도 가능한 비동기 후속 처리가 있음
- 다른 bounded context로 `PaymentAuthorized` 같은 integration event를 안정적으로 발행해야 함

단순 동기 결제 승인이라면 우선순위는 repository/outbox보다 `PaymentProvider` port, idempotency key, payment attempt 기록, `transaction.atomic()`, 외부 side effect의 commit 전후 위치 정리입니다. 다만 “돈이 움직이는 호출”이면 중복 호출 방지와 실패 복구 설계는 반드시 필요합니다.
