```text
운영 중인 주문 테이블에 status 컬럼을 추가하고 기존 데이터를 채운 다음 NOT NULL, check constraint, index를 순차 적용하려고 해. rolling deploy 기준으로 안전한 migration plan을 세워줘.
```

codex
가정: PostgreSQL + Django, `orders` 테이블이 운영 중이고 rolling deploy가 필요함.

**Migration Plan**

1. **앱 선배포**
   - 새 코드가 `status` 컬럼이 없어도 동작하거나, 최소한 nullable 상태를 허용하게 만든다.
   - 신규 주문 생성 시 애플리케이션에서 `status` 값을 반드시 채우도록 한다.
   - 읽기 경로는 일시적으로 `status IS NULL`을 기존 기본 상태로 해석하게 둔다.

2. **DB expand migration**
   ```sql
   ALTER TABLE orders ADD COLUMN status text;
   ```
   - 처음에는 `NOT NULL`, `DEFAULT`, `CHECK`, index를 붙이지 않는다.
   - 대형 테이블이면 즉시 검증/스캔/락을 유발하는 작업을 피한다.

3. **앱 배포**
   - 모든 신규/수정 주문이 `status`를 쓰도록 rolling deploy한다.
   - 이 시점에도 구버전 앱이 살아있을 수 있으므로 DB 제약은 아직 걸지 않는다.

4. **기존 데이터 backfill**
   - 작은 배치로 반복 처리한다.
   ```sql
   UPDATE orders
   SET status = 'pending'
   WHERE status IS NULL
   AND id >= :start_id
   AND id < :end_id;
   ```
   - 배치마다 짧게 커밋한다.
   - lock timeout, statement timeout, sleep/throttle을 둔다.
   - 진행 중에는 `COUNT(*) WHERE status IS NULL`을 모니터링한다.

5. **check constraint 추가**
   ```sql
   ALTER TABLE orders
   ADD CONSTRAINT orders_status_valid
   CHECK (status IN ('pending', 'paid', 'cancelled', 'shipped'))
   NOT VALID;
   ```

6. **NOT NULL 보호용 check 추가**
   ```sql
   ALTER TABLE orders
   ADD CONSTRAINT orders_status_not_null
   CHECK (status IS NOT NULL)
   NOT VALID;
   ```

7. **constraint validate**
   ```sql
   ALTER TABLE orders VALIDATE CONSTRAINT orders_status_valid;
   ALTER TABLE orders VALIDATE CONSTRAINT orders_status_not_null;
   ```
   - PostgreSQL에서는 `VALIDATE CONSTRAINT`가 일반 쓰기를 오래 막지 않으므로 rolling deploy에 적합하다.

8. **index 생성**
   ```sql
   CREATE INDEX CONCURRENTLY idx_orders_status ON orders (status);
   ```
   - Django migration에서는 `atomic = False`가 필요하다.
   - 실제 쿼리가 `WHERE status = ... ORDER BY created_at` 형태라면 복합 인덱스를 검토한다.

9. **최종 NOT NULL 적용**
   ```sql
   ALTER TABLE orders ALTER COLUMN status SET NOT NULL;
   ```
   - 이미 validated `CHECK (status IS NOT NULL)`이 있으면 PostgreSQL 버전에 따라 테이블 전체 검증 비용을 줄일 수 있다.
   - 적용 전 반드시 `SELECT COUNT(*) FROM orders WHERE status IS NULL;` 결과가 `0`인지 확인한다.

10. **정리**
   - 앱의 `NULL` fallback 로직 제거.
   - 필요하면 `orders_status_not_null` check는 `NOT NULL`과 중복이므로 제거 가능.
   ```sql
   ALTER TABLE orders DROP CONSTRAINT orders_status_not_null;
   ```

**Django 주의점**

- `AddField(null=True)` 먼저.
- backfill은 `RunPython`보다 별도 관리 커맨드나 배치 잡이 안전한 경우가 많다.
- `CREATE INDEX CONCURRENTLY`는 `RunSQL` + `atomic = False`.
- `ALTER COLUMN SET NOT NULL`은 마지막 별도 migration으로 분리한다.
