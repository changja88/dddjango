전제: PostgreSQL + Django 기준으로 작성합니다. MySQL이면 `CONCURRENTLY`, `NOT VALID / VALIDATE CONSTRAINT` 부분을 해당 DB의 online DDL 옵션으로 바꿔야 합니다.

**Rolling Migration Plan**

1. **사전 결정**
   - `status`의 허용값을 먼저 고정합니다. 예: `pending`, `paid`, `cancelled`, `fulfilled`.
   - 기존 주문을 어떤 기준으로 어떤 status에 매핑할지 명확히 정합니다.
   - 애매한 기존 데이터가 있으면 임시값을 만들기보다 별도 리포트로 빼고, 백필 전에 정책을 확정합니다.

2. **Expand: nullable 컬럼만 추가**
   - 첫 migration에서는 `orders.status`를 `NULL 허용`으로만 추가합니다.
   - `NOT NULL`, `CHECK`, `INDEX`는 아직 추가하지 않습니다.
   - DB default는 도메인상 항상 맞는 값일 때만 둡니다. rolling 중 구버전 앱이 새 주문을 만들 수 있으므로, default가 부정확하면 차라리 nullable 상태로 두고 백필로 정리합니다.

   예시 SQL, 실행하지 않음:
   ```sql
   ALTER TABLE orders ADD COLUMN status varchar(32);
   ```

3. **앱 배포 1차**
   - 새 코드가 주문 생성/변경 시 항상 `status`를 쓰도록 배포합니다.
   - 읽기 로직은 아직 `status IS NULL`을 허용해야 합니다.
   - 새 쿼리가 `WHERE status = ...`에 의존한다면 feature flag로 막거나, 인덱스 생성 후 활성화합니다.

4. **Backfill**
   - 대량 테이블이면 Django migration의 `RunPython` 한 방으로 처리하지 말고, management command / 배치 job / SQL job으로 나눠 실행합니다.
   - 작은 batch 단위로 커밋합니다. 예: PK range, `LIMIT` 기반 반복, `status IS NULL` 조건.
   - 각 batch는 idempotent 해야 합니다.

   예시 SQL, 실행하지 않음:
   ```sql
   UPDATE orders
      SET status = CASE
          WHEN cancelled_at IS NOT NULL THEN 'cancelled'
          WHEN paid_at IS NOT NULL THEN 'paid'
          ELSE 'pending'
      END
    WHERE id > :from_id
      AND id <= :to_id
      AND status IS NULL;
   ```

   운영 중 모니터링:
   - `status IS NULL` 남은 건수
   - invalid status 건수
   - replication lag
   - lock wait
   - batch latency
   - write throughput 저하
   - dead tuples / autovacuum 영향

5. **Catch-up 확인**
   - 모든 앱 인스턴스가 새 코드로 교체된 뒤 백필을 한 번 더 실행합니다.
   - 구버전 writer가 더 이상 `NULL status`를 만들지 않는지 일정 시간 확인합니다.

   확인 SQL, 실행하지 않음:
   ```sql
   SELECT count(*) FROM orders WHERE status IS NULL;

   SELECT status, count(*)
     FROM orders
    GROUP BY status;
   ```

6. **Contract 1: CHECK constraint**
   - 허용값 check를 먼저 추가하고 검증합니다.
   - PostgreSQL이면 `NOT VALID`로 추가한 뒤 별도 단계에서 `VALIDATE`합니다. 한 migration에 섞지 않는 편이 안전합니다.

   예시 SQL, 실행하지 않음:
   ```sql
   ALTER TABLE orders
     ADD CONSTRAINT orders_status_valid
     CHECK (status IN ('pending', 'paid', 'cancelled', 'fulfilled')) NOT VALID;

   ALTER TABLE orders
     VALIDATE CONSTRAINT orders_status_valid;
   ```

7. **Contract 2: NOT NULL**
   - `status IS NULL`이 0이고, 새 write가 모두 status를 채운다는 증거가 생긴 뒤 적용합니다.
   - PostgreSQL에서는 `CHECK (status IS NOT NULL) NOT VALID`를 검증한 뒤 `SET NOT NULL`로 전환하면 테이블 스캔/락 리스크를 줄일 수 있습니다.
   - `lock_timeout`, `statement_timeout`을 짧게 두고 실패하면 재시도하는 방식이 안전합니다.

   예시 SQL, 실행하지 않음:
   ```sql
   ALTER TABLE orders
     ADD CONSTRAINT orders_status_nn
     CHECK (status IS NOT NULL) NOT VALID;

   ALTER TABLE orders
     VALIDATE CONSTRAINT orders_status_nn;

   ALTER TABLE orders
     ALTER COLUMN status SET NOT NULL;

   ALTER TABLE orders
     DROP CONSTRAINT orders_status_nn;
   ```

8. **Contract 3: index**
   - `status` 단독 인덱스는 저카디널리티라 효과가 낮을 수 있습니다.
   - 실제 쿼리가 보통 `status + created_at`, `status + shop_id`, `status + updated_at` 형태라면 그 쿼리 모양에 맞춘 composite index가 낫습니다.
   - PostgreSQL/Django에서는 `CREATE INDEX CONCURRENTLY` 또는 Django `AddIndexConcurrently`를 쓰고, migration은 `atomic = False`여야 합니다.

   예시 SQL, 실행하지 않음:
   ```sql
   CREATE INDEX CONCURRENTLY idx_orders_status_created_at
     ON orders (status, created_at DESC, id);
   ```

9. **Rollback / Forward-fix**
   - 컬럼 추가와 백필 단계는 rollback 대신 forward-fix가 기본입니다.
   - `NOT NULL` 이후에는 구버전 앱이 status 없이 insert하면 실패할 수 있으므로, 이 단계 전에는 구버전 재배포 가능성을 제거해야 합니다.
   - check constraint rollback은 constraint drop, index rollback은 `DROP INDEX CONCURRENTLY`로 분리합니다.
   - 백필 결과가 틀렸다면 되돌리기보다 source-of-truth 기준으로 재백필하는 스크립트를 준비합니다.

**피해야 할 것**

- 컬럼 추가, 전체 백필, `NOT NULL`, check, index를 한 migration에 묶기
- 큰 주문 테이블을 단일 transaction으로 업데이트하기
- 백필 전에 `NOT NULL` 적용하기
- 새 앱 쿼리를 먼저 열고 나중에 인덱스 만들기
- status 단독 인덱스를 실제 쿼리 검증 없이 추가하기
