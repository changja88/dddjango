### 1. 주문 상태 컬럼 migration 계획

1. `status` 컬럼을 nullable로 먼저 추가한다.
2. 기존 주문 데이터를 기준으로 `status`를 backfill한다.
   - 예: 결제 완료 주문은 `PAID`, 취소 주문은 `CANCELED`, 배송 완료 주문은 `COMPLETED`
3. 애플리케이션 코드에서 신규 주문 생성 시 항상 `status`를 쓰도록 배포한다.
4. backfill 검증 쿼리로 `status IS NULL`이 없는지 확인한다.
5. `status`에 `NOT NULL` 제약을 추가한다.
6. 조회 패턴에 맞춰 index를 추가한다.
   - 예: `status`, 또는 `status + created_at`
7. PostgreSQL이면 큰 테이블에서는 `CREATE INDEX CONCURRENTLY`를 고려한다.

### 4. 주문 상태 전이 리팩터링

- `StrEnum`으로 상태를 명시한다.
- `dataclass(frozen=True)`로 전이 규칙을 표현한다.
- 전이 함수는 `OrderStatus -> OrderStatus`를 명확히 반환한다.

```python
from dataclasses import dataclass
from enum import StrEnum


class OrderStatus(StrEnum):
    PENDING = "pending"
    PAID = "paid"
    CANCELED = "canceled"
    SHIPPED = "shipped"
    COMPLETED = "completed"


@dataclass(frozen=True)
class StatusTransition:
    source: OrderStatus
    target: OrderStatus


ALLOWED_TRANSITIONS: set[StatusTransition] = {
    StatusTransition(OrderStatus.PENDING, OrderStatus.PAID),
    StatusTransition(OrderStatus.PENDING, OrderStatus.CANCELED),
    StatusTransition(OrderStatus.PAID, OrderStatus.SHIPPED),
    StatusTransition(OrderStatus.SHIPPED, OrderStatus.COMPLETED),
}


def can_transition(source: OrderStatus, target: OrderStatus) -> bool:
    return StatusTransition(source, target) in ALLOWED_TRANSITIONS
```

- 쿠폰 검증

- 알림 발송
- 외부 API 호출
- 여러 aggregate를 함께 변경하는 흐름
- transaction 경계가 필요한 application workflow

판단 기준은 “Order 하나만 알아도 판단 가능한가”이다. 그렇다면 model method, 아니면 service/usecase가 적합하다.

### 6. 쿠폰 할인 정책 TDD 계획

테스트부터 작성한다.

- 최소 주문 금액 미만이면 할인 불가
- 최소 주문 금액 이상이면 할인 가능
- 이미 사용한 쿠폰은 재사용 불가
- 만료일 당일 23:59:59까지 유효한지 정책 명시
- 만료일 다음 순간부터 불가
- 할인 금액이 주문 금액을 초과하지 않음

구현 순서:

1. 실패 테스트 작성
2. `CouponPolicy` 또는 domain service 구현
3. boundary case 추가
4. DB 상태가 필요한 “사용됨” 검증은 repository 또는 fixture로 분리

- Bounded Context:

- Aggregate:

  - `OrderShipmentRequested`

### 9. 결제 승인 유스케이스 아키텍처 판단

적용 권장:

- Repository: 결제 승인 시 주문 조회/저장을 추상화할 가치가 있음
- UoW: 주문 상태 변경, 결제 기록, outbox 저장을 같은 transaction으로 묶어야 함
- Outbox: 결제 승인 후 알림, 배송 요청, 재고 확정 이벤트 발행이 필요하면 권장
- ACL: 외부 PG 응답 모델을 내부 payment/order 모델로 직접 들이지 않기 위해 권장

Hexagonal architecture는 외부 결제 API와 DB 의존성이 명확하므로 적용할 가치가 있다. 단, 초기 MVP라면 port/interface를 최소화하고 결제 gateway, repository, UoW 정도부터 시작한다.

### 10. 재고 차감과 예약 확정 동시성 설계

- DB constraint:
  - `available_quantity >= 0`
  - reservation unique key
  - idempotency key unique constraint
- Transaction:
  - 재고 차감과 예약 확정을 하나의 transaction으로 처리
- Locking:
  - PostgreSQL 기준 `SELECT ... FOR UPDATE`
  - SKU 또는 inventory row 단위 lock
- Idempotency:
  - `idempotency_key`
  - `request_hash`
  - `status`
  - `response_body`
  - `locked_until` 또는 처리 상태
- 중복 요청이면 같은 key의 기존 결과를 반환한다.
- lock timeout과 deadlock retry 정책을 별도로 둔다.

### 11. 주문 생성 REST API 설계

- Endpoint: `POST /api/orders`
- 성공:
  - `201 Created`
  - `Location: /api/orders/{order_id}`
- Idempotency:
  - `Idempotency-Key` header 필수 권장
  - 같은 key + 같은 request body면 기존 응답 반환
  - 같은 key + 다른 body면 `409 Conflict`
- 오류:
  - Problem Details 사용
  - content type: `application/problem+json`
- 주요 status code:
  - `400` malformed request
  - `401` unauthenticated
  - `403` forbidden
  - `409` idempotency conflict or business conflict
  - `422` validation/business rule violation
- OpenAPI:
  - request schema
  - response schema
  - problem schema
  - auth requirement
  - idempotency header 명시
