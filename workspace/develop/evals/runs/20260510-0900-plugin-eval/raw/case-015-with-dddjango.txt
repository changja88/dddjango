원자료 한계: public packet에는 “결제 승인 흐름”이라는 정보만 있고, PG/은행 연동 여부, 동기/비동기 승인 방식, 주문/결제 애그리거트 경계, API idempotency 정책, DB 스키마가 없다. 또한 `architecture-implementation-patterns`는 현재 전용 final reference가 아니라 fallback 기준을 쓰는 provisional skill이다. 아래 판단은 확정 설계가 아니라 dddjango 기준의 조건부 판단이다.

**판단**

- `ports/adapters`: 적용 가능성이 높다. 결제 승인이 외부 PG/은행/SDK/HTTP를 호출한다면 application service는 `PaymentGateway`/`PaymentAuthorizer` 같은 역할 기반 port에 의존하고, 실제 PG SDK/HTTP 코드는 infrastructure adapter로 둔다. Router/View는 request 검증, 인증, DTO 변환, use case 호출만 담당해야 한다. 외부 연동이 없는 단순 내부 상태 변경이면 과한 구조다.
- `repository`: 조건부다. `PaymentAuthorization` 또는 `Payment` 애그리거트의 저장/조회가 도메인 컬렉션처럼 표현되어야 하거나, ORM 모델과 도메인 모델을 분리해야 하거나, application service 테스트에서 fake repository 이득이 크면 쓴다. 단순히 `Payment.objects.get()`을 감싸는 얇은 QuerySet wrapper라면 dddjango 기준으로 피한다. Django에서는 먼저 model method + service + `transaction.atomic()`이 기본 선택지다.
- `outbox`: 결제 승인 상태 변경과 외부/타 컨텍스트 메시지 발행을 신뢰성 있게 묶어야 하면 적용한다. 예: `PaymentAuthorized` integration event를 주문, 정산, 알림, 배송 컨텍스트가 소비해야 한다면 승인 상태 저장과 outbox message 저장을 같은 DB transaction에 넣고 별도 dispatcher가 at-least-once로 발행한다. 단순한 동일 프로세스 후속 처리면 `transaction.on_commit()`으로 충분할 수 있다. 단, outbox는 PG 승인 호출 자체와 DB commit을 원자적으로 묶는 마법이 아니므로 idempotency, 재시도, reconciliation, 필요 시 saga/compensation 판단이 별도로 필요하다.
- `ACL`: 외부 PG/레거시 결제 시스템의 상태, 식별자, 금액 단위, 승인/매입/취소 lifecycle이 내부 결제 모델과 다르면 적용한다. 번역은 adapter 경계에 둔다. 외부 모델이 내부 언어와 거의 같고 SDK DTO가 도메인으로 새지 않는다면 작은 translator 정도로 충분하다.

**Risky Write Consistency Block**

- transaction owner: `AuthorizePayment` 같은 결제 승인 application service.
- locking/idempotency: 중복 승인 방지를 위한 idempotency key 또는 provider request id의 unique constraint가 필요할 가능성이 높다. 정확한 key는 API 계약과 PG 정책이 없어서 단정할 수 없다.
- side-effect timing: PG 호출은 port를 통해 격리한다. 승인 결과 저장 후 타 컨텍스트 발행은 outbox 또는 `on_commit()` 중 신뢰성 요구에 맞춰 선택한다.
- isolation/retry: 결제/주문 상태를 동시에 바꾸면 optimistic locking, `select_for_update`, unique constraint 중 실제 invariant에 맞춰 선택해야 한다. 현재 정보만으로 특정 isolation level은 확정할 수 없다.
- tests: 중복 요청, 동시 승인, PG timeout/retry, outbox 재발행, consumer idempotency 테스트가 필요하다.

결론: “전부 적용”이 아니라 `ports/adapters`는 외부 결제 의존성 격리 때문에 우선 고려, `repository`는 복잡한 애그리거트/ORM 분리 필요가 있을 때만, `outbox`는 승인 후 integration event의 신뢰성 요구가 있을 때, `ACL`은 PG/레거시 언어가 내부 도메인을 오염시킬 때 적용하는 쪽이 dddjango 기준에 맞다.
