3. DB: 예약 행과 재고 행은 일관된 순서로 `select_for_update()` 하거나 조건부 update로 차감합니다. `Idempotency-Key`, 예약 확정 고유 제약, 결제 provider transaction id 고유 제약을 둡니다.
4. API: `POST /reservations/{id}/confirm` 같은 명령형 endpoint로 두고 `Idempotency-Key`를 요구합니다. 성공은 `200`/`201`, 재고 부족은 `409`, 잘못된 상태 전이는 `409` 또는 `422`, 오류는 Problem Details로 고정합니다.
5. Django: `transaction.atomic()` 안에서 예약/재고/결제 기록을 원자적으로 갱신합니다. 외부 후속 작업은 `transaction.on_commit()` 또는 outbox로 넘깁니다.
6. TDD/Test: 먼저 불변식 테스트, 그다음 API 계약 테스트, 마지막으로 `TransactionTestCase`/pytest transaction 기반 동시성 테스트를 둡니다.
7. Review: 중복 확정, 이중 차감, 결제 승인 중복 처리, lock 순서, retry 정책을 집중 검토합니다.
8. Integration: 도메인 불변식, DB 제약, API 계약, Django 구현, 테스트가 같은 용어와 상태 전이를 쓰는지 맞춥니다.
