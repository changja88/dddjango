## When To Role-Decompose

Use role decomposition when:

- two or more of DDD, DB, API, Django, tests, TDD, or review are genuinely coupled;

## When To Stay Direct

Do not force the workflow for:

- small single-file edits;
- simple model field renames;
- local CRUD changes with no invariant or rollout risk;
- short conceptual explanations;

Use the relevant implementation, architecture, test, or clean-code skill directly in these cases.

- constraints on what not to edit;
- validation expectations.

`Scope`: 예약 확정과 재고 차감, 외부 결제 승인 반영을 하나의 일관성 경계로 설계합니다.

`Inputs Used`: 사용자 요구사항만 사용했습니다. 프로젝트 소스 파일은 읽지 않았습니다.

`Decisions`: DB 트랜잭션 소유자는 Django application service. 외부 결제 호출은 트랜잭션 밖. 승인 결과는 unique key로 멱등 저장. 예약 확정과 재고 차감은 같은 DB 트랜잭션에서 처리.

`Files`:
`May edit`: 실제 작업 시 domain/service/model/migration/router/tests 파일을 역할별로 분리 지정.
`Must not edit`: 역할 소유 밖 파일, unrelated settings, 기존 사용자 변경.

`Output`: 역할별 설계안, migration, service 구현, API contract, 테스트, 리뷰 체크리스트.

`Risks`: deadlock, 중복 결제 승인 이벤트, 재고 음수, 결제 승인 성공 후 로컬 확정 실패, API retry 중복 처리.

`Required Follow-up`: 결제가 “이미 승인된 callback을 받는 구조”인지 “확정 시 외부 승인 호출을 직접 하는 구조”인지 먼저 확정해야 합니다.

`dddjango Checks`: 도메인 불변식, DB 제약/락, Problem Details, Django transaction boundary, pytest concurrency 검증을 모두 포함합니다.

## Integration Checklist

**Risky Write Consistency Block**

| 항목 | 결정 |
|---|---|
| Transaction owner | Django application service |
| Locking strategy | 예약 row 먼저 `select_for_update()`, 재고 row는 deterministic order로 lock 또는 조건부 update |
| Uniqueness/idempotency | `reservation_id` confirmation unique, `(provider, approval_id)` unique, `(scope, idempotency_key)` unique |
| `Idempotency-Key` API behavior | 필수. 같은 key+payload는 같은 결과 반환, 다른 payload면 `409 Conflict` |
| External side-effect timing | DB transaction 안에서 외부 HTTP 호출 금지. `transaction.on_commit()` 또는 outbox 사용 |
| Isolation/retry | 기본 `READ COMMITTED` + row lock. deadlock/serialization failure는 제한적 retry |
| Test criteria | 동시 요청 N개에서 확정 1건만 성공, 재고 음수 없음, 결제 승인 중복 이벤트 무해 |
