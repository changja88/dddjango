1. **주문 상태 컬럼 migration 계획**

- Expand: `Order.status`를 nullable 컬럼으로 먼저 추가합니다. 예: `CharField(max_length=32, null=True, choices=OrderStatus)`.
- Backfill: 기존 주문 데이터를 상태 규칙으로 매핑합니다. 예: 결제 완료 + 취소 아님은 `paid`, 배송 완료는 `completed`, 취소 기록은 `cancelled`, 판단 불가 데이터는 별도 리포트 후 기본 상태 결정.
- 운영 데이터가 크면 `RunPython` 단일 트랜잭션보다 배치 backfill 관리 명령 또는 `atomic = False` migration을 고려합니다.
- Verify: `status IS NULL` 건수가 0인지 확인합니다.
- Contract: `null=False`로 변경하고 DB check constraint 또는 choices와 일치하는 제약을 둡니다.
- Index: 조회 조건이 `status`, `status + created_at`, `customer_id + status`라면 실제 쿼리에 맞춰 복합 index를 우선 검토합니다. PostgreSQL 대용량 테이블이면 `CREATE INDEX CONCURRENTLY` 방식으로 lock 위험을 줄입니다.

9. **결제 승인 유스케이스 architecture 판단**

- Hexagonal: 결제 PG/PSP가 외부 시스템이면 `PaymentGatewayPort`와 adapter를 두는 것이 타당합니다.
- Repository/UoW: 단순 Django CRUD면 과하지만, 결제 승인처럼 `Order`, `PaymentAttempt`, `Outbox`를 한 transaction으로 묶으면 UoW 또는 명시적 application service transaction이 필요합니다.
- Outbox: 결제 승인 후 주문 상태 변경, 알림, 배송 시작 이벤트가 필요하면 적용 권장입니다.
- ACL: PG 응답 모델을 도메인 모델에 직접 흘리지 않도록 anti-corruption layer를 둡니다.
- 결론: “순수 hexagonal 전체 도입”보다 결제 승인 usecase 주변에 port, adapter, transaction boundary, outbox, ACL을 국소적으로 적용하는 것이 적절합니다.

10. **재고 차감/예약 확정 동시성 설계**

- Constraint: `available_qty >= 0`, `reserved_qty >= 0`, reservation은 `(order_id, sku_id)` unique.
- Transaction: 같은 SKU 재고 row를 `select_for_update()`로 잠그거나 조건부 update `available_qty >= requested_qty`를 사용합니다.
- Ordering: 여러 SKU를 잠글 때는 SKU id 정렬로 lock 순서를 고정해 deadlock을 줄입니다.
- Idempotency: `idempotency_key`, `request_hash`, `status`, `response_body`를 저장하고 unique key를 둡니다.
- Replay: 같은 key + 같은 hash는 저장 응답 반환, 같은 key + 다른 hash는 `409 Conflict`.
- Tests: 실제 DB transaction 기반 concurrency test가 필요합니다. 단순 unit test로는 locking 보장이 어렵습니다.

11. **주문 생성 REST API 계약**

- Endpoint: `POST /api/orders`.
- Success: 동기 생성이면 `201 Created` + `Location: /api/orders/{id}` + 주문 요약 body.
- Async 처리면 `202 Accepted` + operation/status resource를 반환합니다.
- Idempotency-Key: 중복 주문 방지를 위해 필수 header로 권장합니다. 누락은 `400`, 같은 요청 replay는 최초 응답 재현, 다른 body는 `409`.
- Errors: validation `422`, 재고/상태 충돌 `409`, 인증 `401`, 권한 `403`, rate limit `429`, 일시 장애 `503`.
- Problem Details: `type`, `title`, `status`, `detail`, `instance`, 필요 시 `errors` 확장 필드.
- OpenAPI: header, request schema, `201/400/401/403/409/422/429/503` response, Problem Details schema, idempotency 동작 예시를 문서화합니다.
