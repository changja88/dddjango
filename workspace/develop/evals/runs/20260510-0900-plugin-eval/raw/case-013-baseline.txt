**Raw Answer**

실제 주문 API 구현 파일은 이 저장소에 없어서 코드 기준 diff는 못 봤고, 공개 `dddjango` 가이드 기준으로 DRF → Django Ninja 이전 체크리스트를 정리합니다.

DRF `ViewSet/Serializer`는 Ninja에서 명시적인 `Router` operation과 request/response `Schema`로 나누는 게 맞습니다. Router에는 요청 파싱, 인증/인가 연결, 서비스 호출, 응답 매핑, 오류 변환만 두고 주문 생성/상태 전이/재고/결제 같은 규칙은 서비스나 도메인 쪽에 남기세요.

호환성에서 먼저 고정할 것:
- 기존 URL, method, trailing slash, versioning 전략
- 응답 field 이름/type/nullability/decimal/date 포맷
- list pagination envelope와 query parameter
- filter/sort/search parameter 이름
- 인증 실패 `401`과 권한 실패 `403` 구분
- 기존 클라이언트가 의존하는 DRF error shape

권장 status code 기준:
- `GET /orders`: `200`
- `GET /orders/{id}`: `200`, 없거나 숨김이면 `404`
- `POST /orders`: `201` + 가능하면 `Location`
- 비동기 주문 생성이면 `202`
- `PATCH/PUT /orders/{id}`: body 반환 시 `200`, 반환 없으면 `204`
- 삭제/취소가 body 없으면 `204`
- malformed request는 `400`
- 의미상 유효하지 않은 주문 요청은 계약에 따라 `422`
- 중복 주문, 상태 충돌, idempotency payload 불일치는 `409`
- rate limit은 `429`

Error response는 같은 API version 안에서는 기존 DRF shape를 깨지 않는 게 우선입니다. 새 버전으로 분리할 수 있다면 RFC 9457 Problem Details를 표준으로 두고 `application/problem+json`, `type`, `title`, `status`, `detail`, 필요 시 `instance`와 문서화된 extension field를 쓰세요. DRF의 `{field: ["..."]}`, `non_field_errors`, `detail` 형태와 Ninja/Pydantic validation error 형태는 달라질 수 있으므로 exception handler에서 명시적으로 매핑해야 합니다.

주문 생성은 재시도 중복 위험이 높으니 `Idempotency-Key`를 지원하거나 요구하는 계약을 정하세요. 같은 key+같은 payload는 저장된 첫 응답을 replay하고, 같은 key+다른 payload는 `409`로 두는 방식이 안전합니다. 저장 위치, TTL, 동시성 처리는 DB/트랜잭션 설계와 같이 결정해야 합니다.

OpenAPI 차이는 반드시 diff 대상입니다:
- path/method/operationId/tag
- request schema와 response schema 분리
- status별 response body
- Problem Details 또는 legacy error schema
- auth requirement
- pagination/filter/sort params
- `Idempotency-Key` header
- enum/nullable/required field 차이
