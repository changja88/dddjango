현재 작업 디렉터리에는 실제 DRF 주문 `ViewSet/Serializer` 구현이 없어 구체 코드 diff는 못 했습니다. 그래서 호환성 관점의 전환 기준으로 보면, 같은 API 버전을 유지한다면 **URL, trailing slash, path param 이름, status code, error JSON shape를 DRF와 동일하게 맞춘 뒤** 내부만 Django Ninja `Router/Schema`로 옮기는 게 맞습니다. 새 계약으로 바꿀 수 있을 때만 Problem Details와 Ninja 기본 validation error를 노출하세요.

핵심 차이:
- DRF router는 기본적으로 `{prefix}/`, `{prefix}/{lookup}/` 형태의 trailing slash를 붙입니다. Ninja route는 명시한 path가 그대로 계약이므로 기존 `/orders/`, `/orders/{pk}/`를 유지해야 합니다.
- DRF validation error는 보통 `400` + `{field: ["..."], "non_field_errors": [...]}`입니다. Django Ninja 기본 request validation error는 `422` + `{"detail": [...]}`라서, 기존 클라이언트 호환이 목표면 `ValidationError` handler로 `400`과 DRF형 body를 맞춰야 합니다.
- `create/list/retrieve/update/partial_update/destroy`는 Ninja에서 각각 `post/get/get/put/patch/delete` operation으로 풀어 쓰고, `201`, `200`, `204`, `400`, `401`, `403`, `404`, `409` 같은 응답을 `response={...}`에 명시해야 OpenAPI도 맞습니다.
- 기존 DRF custom `@action`은 URL과 method를 그대로 보존해서 별도 Ninja route로 옮겨야 합니다.
- OpenAPI는 component schema 이름, required/nullable, readOnly/writeOnly, operationId, auth scheme, error response schema가 달라질 가능성이 큽니다. 생성된 `old_openapi.json`/`new_openapi.json`을 diff해서 “삭제된 path/status/schema 필드 없음”을 기준으로 봐야 합니다.

권장 마이그레이션 순서:
1. 기존 DRF API의 golden contract를 먼저 고정: 성공/검증 실패/권한 실패/404/비즈니스 충돌 응답의 status와 body.
2. `Serializer`를 request schema와 response schema로 분리: DRF의 `read_only`, `write_only`, `source`, nested serializer 동작을 Ninja/Pydantic schema에 명시.
3. ViewSet 액션을 Ninja Router operation으로 1:1 매핑: 비즈니스 규칙은 router에 넣지 말고 기존 service/usecase로 유지.
4. 중앙 error handler 작성: 같은 v1이면 DRF error shape 유지, 새 v2면 Problem Details로 전환.
5. Ninja `TestClient`로 status/error/body 계약 테스트를 먼저 통과시킨 뒤 OpenAPI diff를 확인.
