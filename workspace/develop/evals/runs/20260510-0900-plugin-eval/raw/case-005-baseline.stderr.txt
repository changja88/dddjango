codex
현재 디렉터리에는 실제 Django 앱보다 평가/문서 자료가 중심으로 보여서, 파일 수정 없이 구현 계획만 정리합니다.

**구현 계획**

1. DDD 경계 분리
- `orders/domain`: `Order` aggregate, `OrderLine`, `Money`, `Quantity`, `OrderStatus`
- `inventory/domain`: `Stock` 또는 `InventoryItem`, 재고 예약/차감 규칙
- `payments/domain`: `PaymentAttempt`, `PaymentStatus`, 승인 결과 값 객체
- `orders/application`: `CreateOrderService`
- `orders/api`: Django Ninja router/schema
- `orders/infra`: Django ORM repository, payment gateway adapter, idempotency store

2. 주문 생성 흐름
```text
POST /orders
Header: Idempotency-Key

1. 요청 body canonical hash 생성
2. transaction.atomic()
   - idempotency row 생성/lock
   - 같은 key + 같은 hash + 완료됨이면 저장된 응답 반환
   - 같은 key + 다른 hash면 409
   - 상품/재고 row를 SKU 정렬 후 select_for_update()
   - Order(PENDING_PAYMENT) 생성
   - 재고 reserve 또는 available 차감
   - PaymentAttempt(PENDING) 생성
3. DB commit 후 결제 gateway 승인 호출
4. transaction.atomic()
   - 승인 성공: payment APPROVED, order CONFIRMED/PAID, 재고 차감 확정
   - 승인 실패: payment DECLINED, order PAYMENT_FAILED, 예약 재고 release
   - idempotency 응답 저장
5. 응답 반환
```

핵심은 결제 승인 외부 호출을 DB transaction 안에 오래 물고 있지 않는 것입니다. DB 상태 변경은 `transaction.atomic()`으로 묶고, 결제 gateway에는 동일한 `Idempotency-Key` 기반 gateway idempotency key를 넘겨 중복 승인을 막습니다.

3. DB 모델/제약
- `Order`: `id`, `user_id`, `status`, `total_amount`, `currency`, timestamps
- `OrderLine`: `order_id`, `sku`, `unit_price`, `quantity`, `line_total`
- `InventoryStock`: `sku unique`, `available`, `reserved`, check `available >= 0`, `reserved >= 0`
- `PaymentAttempt`: `order_id`, `gateway`, `gateway_payment_id`, `status`, `amount`
- `IdempotencyRecord`: `scope`, `key`, `request_hash`, `status`, `response_status`, `response_body`
- unique constraints:
  - `(user_id, scope, idempotency_key)`
  - gateway payment id
  - order number if exposed

4. Django Ninja API
- `POST /orders`
  - required header: `Idempotency-Key`
  - body: `items[{sku, quantity}], payment_method`
  - response: `order_id`, `status`, `payment_status`, `total`, `lines`
- error mapping:
  - validation error: `400`
  - idempotency key body mismatch: `409`
  - insufficient stock: `409`
  - payment declined: `402` or domain-specific `409`
  - gateway timeout: `202` with `PENDING_PAYMENT` if retry/reconciliation is supported

5. Domain tests
- 빈 주문 생성 거부
- 수량 0 이하 거부
- 주문 총액 계산
- 상태 전이 검증: `PENDING_PAYMENT -> CONFIRMED`, `PENDING_PAYMENT -> PAYMENT_FAILED`
- 결제 실패 시 재고 예약 해제
- 재고 부족 시 주문 생성 실패

6. API/application tests
- 같은 `Idempotency-Key` + 같은 body 재요청 시 주문/결제 중복 없음
- 같은 key + 다른 body는 `409`
- 결제 승인 성공 시 주문 확정 및 재고 차감
- 결제 거절 시 주문 실패 및 재고 복구
- 결제 gateway timeout 시 pending/outbox/retry 상태 확인
- 동시 주문에서 `select_for_update()`로 재고 음수 방지
  이 테스트는 `TransactionTestCase`와 PostgreSQL 기준으로 작성하는 것이 안전합니다.
