# 이체 꼴 판정 + 함께 커밋(이름 붙은 승인 예외) 계획 v1 (dddjango 2.36.0 후보 · 2026-11-10)

설계 정본은 같은 폴더 `design.md`(v4.2 — 방향 판정 · 칸 문법 · 검사기 판정 차례 · 잠금 · 글 자리 · 한계 · 검토 처분)다. 이 문서는 판 범위 · 단위 · 일하는 법 · 멈출 기준만 적는다.

판 번호: 2.36.0 — 이체 꼴(따로 조회한 같은 타입 둘을 한 트랜잭션에서 저장)이 새로 막히고, 설계 승인 칸 · 코드 주석 · G2 대조가 새로 생기므로 minor.

## 결정

- 사용자 결정 «나.»(2026-11-10): 평소 한 트랜잭션(한 `with <uow>:`)은 애그리거트 하나를 바꾼다. 같은 BC · 같은 DB 안에서 이미 있는 애그리거트 둘 이상을 함께 바꿔야 하면 불변식 이름 · 묶는 애그리거트 · 잠금 순서를 설계에 적고 G1 승인받은 구간만 허용한다. 조회한 여럿을 돌며 고치거나 지우는 묶음은 예외 밖(2.35.0). 새로 여럿 만드는 `save_all` 은 지금대로.
- 사용자 결정 «가.»(2026-11-10): 승인 장치와 이체 꼴 판정은 2.35.0 에서 빼 이 판으로. 사용자 «좋아 진행해줘.»(19시 17분): 다음 판 = 이 일.
- 사용자 «진행해»(2026-11-10 21시 45분): 계획 v1 승인(요약 설명 뒤).
- 질문 생략 · 설계 처리 · 이의 시 뒤집음:
  - 승인이 사는 곳 = 코드 주석(설계 §3.1 방향 E). 승인 목록 파일(v3)은 셋째 확인에도 막힘이 남아 버렸다 — 같은 보증을 장치 하나 덜고 낸다.
  - 플러그인 실행 밖에서 손으로 단 승인 주석 · 폐기한 실행이 남긴 주석은 받되, 빌드 시작(G0) 배너에 그 BC 의 함께 커밋 주석 목록 1행을 늘 싣는다(설계 §10 W1 · W2 — 결정 «G1 승인받은 구간만» 에서 답이 나옴 · 검토 추천 «가»).

## 사용자에게 보이는 흐름(예: 계좌 이체)

1. 설계 명세의 그 유스케이스 행 끝에 세 칸을 적는다 — `함께 account×2, transfer  잠금 account(id)  불변식 보낸 돈과 받은 돈이 같고 잔액은 0 밑으로 내려가지 않는다`.
2. G1 배너에 «함께 커밋 승인 n건» 이 한 줄로 보이고, 사용자가 G1 을 승인한다. 조정자는 배너에 보인 행의 지문을 실행 기록에 한 줄 남긴다 — 배너에 안 보인 행은 G2 에서 승인으로 치지 않는다.
3. 코더가 그 트랜잭션 바로 위에 같은 글의 주석 `# joint-commit: …` 을 단다.
4. 검사기는 주석 칸과 코드가 맞는지(묶는 것 · 잠금 순서 · 둘째 저장이 실패하면 첫째도 되돌아가는지)를 보고, G2 는 이번 실행에서 새로 단 주석이 G1 배너에 보인 행과 같은지 맞춰 본다. 주석 없이 둘을 함께 바꾸면 막는다(#550 행 3 · #546).
5. 빌드 시작(G0) 배너에는 그 BC 에 이미 있는 함께 커밋 주석 목록이 늘 한 줄로 보인다 — 플러그인 밖에서 단 것도 여기 나온다.

## 받아들이는 한계(설계 §10 요지)

- 플러그인 실행 밖 주석 · 폐기 실행이 남긴 주석은 받는다 — G0 배너 목록으로만 보인다.
- G2 대조는 조정자가 G1 · G1′ 배너 때 남긴 지문 기록을 믿는다(기록을 쓰는 것은 조정자뿐 — 실행 줄 · 앵커 기록과 같은 신뢰).
- 주석의 `×n` 이 코드보다 크게 적힌 것은 기계가 받는다(G2 감수 · db 리뷰 몫). 승인된 함께 커밋을 이번 실행이 걷고 둘로 나눈 것은 G2 요약 «걷은 주석 k» 로만 보인다.
- 도움 메서드 · 틀 부품을 거친 함께 쓰기 · 이름에 담은 묶음 이체 · 같은 BC 승인끼리 잠금 차례 · 불변식의 뜻은 리뷰어 몫.
- 잠금 차례는 글자 차례다.
- `suppress` 별칭으로 삼키는 꼴 · 표준 밖 배치에서 같은 area 안 다른 깊이의 같은 이름 유스케이스는 기계가 가르지 못한다(설계 §10).

## 일하는 법

- 구현은 단위마다 옛 판(2.35.0 · 태그 `dddjango--v2.35.0` 사본) 붉음(또는 놓침) → 새 판 녹색 · 대조군 통과를 실제로 돌린다. 시제품(`workspace/scratch/joint-commit-next/v4/proto/` · `patch_v41.py`)과 장난감(검사기 70 · G2 30 · 검토 장난감)을 출발점으로 쓴다.
- 현장 줄 차이(읽기만 · git 을 쓰지 않는 검사기 · 레코드는 자기 폴더로): 2.35.0 대비 0 이어야 한다(설계 시제품 실측 0).
- 계획 승인 → 구현(단위별 · 병렬은 파일이 겹치지 않게) → 구현 독립 검토 → 고침 · 좁은 재확인 → 묶기 → 봉인 · 커밋 → `make verify` · `make verify-mutation` → 장부 다시 읽기 → 배포.
