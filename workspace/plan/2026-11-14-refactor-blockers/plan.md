## 사용자에게 보이는 흐름

1. 리팩토링 G0 deps — 표식 없이 착륙한 옛 실행을 «도는 실행» 으로 세지 않는다(설계 §1).
   - BC-나 · BC-가 는 G0 deps 를 지난다(클론 exit 2 → 0).
   - 계정 BC · 이용 정책 BC 는 순환이 남는다(판 B 질문).
2. 폴더 · 실행 선택(세 모드) — 고를 폴더를 `run-state <폴더>…` 한 번으로 본다.
   - `끝(착륙 …)` 은 «끝난 실행» 으로 보인다.
   - 다른 작업 트리가 쓰는 중이면 `미종료 · ② 쓰는 중` 이다.
3. 묶음 빚 · 창 — `folder_group draft` 가 없는 BC 이름 · 한 낱말 아닌 이름을 exit 1 로 멈춘다. 조정자가 그 exit 1 을 처리한다(설계 §2).
4. 검사기 — 받은 글 검증 try(#473) 넷이 빠진다. pydantic `TypeAdapter`(#134) 하나가 빠진다. 지우고 스테이지 안 한 파일의 #15 사용 오류가 사라진다. 표준 자리 admin 이름 검사가 선다(설계 §3 ~ §6).

## 계획 승인 때 사용자에게 밝힐 것

한 번에 하나씩, 쉬운 말로 밝힌다(CLAUDE.md «사용자에게 묻고 알리는 법»).

- ① 표식 없이 착륙한 폴더는 ⑵ 물음(잇기 · 승인됨 · 폐기) 없이 «끝난 실행» 으로 보인다 — 사용자 물음이 하나 준다.
  - G2 없이 착륙한 폴더(중간 착륙 · 접은 실행)였다면, 지금의 «출처 없는 폐기는 위임되지 않는다» 물음이 «착륙 = G2» 관례로 대신 닫힌다.
  - 변경은 이미 main 에 들어갔으니 대가는 작다(설계 §9 ②).
- ② admin 이름 검사가 서면 다른 BC 에 새 빚 3 줄이 뜬다 — BC-라 · BC-바 의 #345(운영 기능 하나 = 파일 하나) 둘과 BC-마 의 ⓓ#343 후보 하나다.
  - 그 BC 의 다음 실행 G0 에 빚으로 보인다. ⓓ 후보는 exit 에 들지 않는다(설계 §4).
- ③ 꼴 ② #473 한 줄은 남는다(실제로는 오탐).
  - 그 BC 를 리팩토링할 때 길은 둘이다. G0 빚 질문 ⓑ(사용자 직접 답) 또는 슬라이스 0 STOP(플러그인 결함) → `ⓐ 재상정` 이다.
  - 레인 안에서 코드를 옮겨 지우지 않는다(설계 §3 «남는 한계»).
- ④ 빨리 감기 · squash 착륙은 효과가 없다(보수 쪽 — 지금처럼 도는 실행으로 셈).
  - 빨리 감기가 main 직접 실행을 삼키는 꼴만 거짓 끝이다(설계 §1 «남는 한계»).
- ⑤ 요청 가이드(`dddjango/REQUEST_GUIDE.md`)에 «착륙은 머지(`--no-ff`)로 — main 을 레인으로 빨리 감지 않는다» 한 줄을 넣을지 — 제안만 한다.
  - 넣으면 Codex 짝은 byte 복사다. 안 넣으면 배포 보고에 «바뀔 것 없음» 을 적는다.

1. **계획 승인** — 위 «밝힐 것» ① ~ ⑤ 를 하나씩 밝히고, ⑤ 는 답을 받는다. 계획 승인은 사용자의 명시적 답(«진행» 등)으로만 받는다.
2. **장부 다시 읽기**(계획 확정 때) — 장부 `workspace/eval/field-report-4/` 에서 F4-110 · 158 ~ 176 의 새 줄을 본다. 범위가 바뀌면 계획을 고쳐 다시 묻는다.
3. **구현** — Claude 구현자 셋. 파일이 겹치지 않게 나눈다:
   - 도구 A · B(refactor_audit · folder_group · 그 시험).
   - 검사기 C(검사기 넷 · 행렬 · 골든).
   - 글 · 문서 A 몫 · B 몫 · E(조정자 Claude · Codex 같은 뜻 · README · master).
   - 단위마다 옛 판(2.37.0 · 태그 `dddjango--v2.37.0` 사본)이 붉음(또는 놓침)이고 새 판이 녹색 · 대조군 통과임을 실제로 돌린다.
   - 시제품을 출발점으로 쓰되, 시제품 패치의 «(설계 … 시제품)» 주석은 런타임 글이 아니므로 docstring · 주석을 규칙대로 다시 쓴다.
4. **현장 줄 차이**(리허설 클론 · 읽기만 · `DJR_VIOLATIONS_DIR` 은 작업 폴더로):
   - 검사기 넷은 설계 재측정과 같아야 한다 — #473 5 → 1 · #134 1 → 0 · naming 새 줄 3 · 그 밖 2.37.0 대비 차이 0.
   - `refactor_audit deps` 네 BC 와 `run-state` 219 는 설계 §1 클론 표와 같아야 한다.
5. **구현 독립 검토** — Claude 검토자 둘. 설계를 주지 말고 코드 · 글을 주고 장난감 하네스를 함께 넘긴다(DEVELOPMENT §7.5).

   - 글: 조정자 Claude · Codex 같은 뜻 · 세 모드 폴더 선택 문단 · exit 1 처리 · 문서.
6. **고침 · 좁은 재확인** — 차단은 고친 뒤 좁게 다시 확인한다. 셋째 확인에도 안 닫히면 멈추고 묻는다.
7. **묶기 · 봉인 · 커밋** — 봉인 대상(DEVELOPMENT §4)을 바꾸면 커밋 직전에 봉인한다. 경로를 하나씩 `git add` 하고, 사용자 로컬 파일은 커밋하지 않는다.
8. **검사** — `make verify` 전체(core 플러그인 · 도구 · 픽스처를 바꿈) · `make verify-mutation`(refactor_audit · folder_group · 검사기 변이). 매니페스트 · 구조를 바꾸면 `claude plugin validate dddjango --strict`.
9. **장부 다시 읽기**(배포 직전).
10. **배포** — push 한 main 의 깨끗한 클론에서 `make release`(2.38.0) → 봉인 chore → 판 기록 `plan-2.38.0.md`(검토 처분 · 검사 수치 — 마지막 실행 값만) 커밋.
11. **배포 뒤** — 장부 처분 줄(아래) · `work_list.html` 끝난 항목 지움 · 요청 가이드 확인 한 줄.
12. **정리**(DEVELOPMENT §7.4) — 이 일의 시제품 · 하네스 사본 · 작업 트리 · 임시 브랜치 · 띄운 프로세스를 지우고 남은 것을 확인해 보고에 적는다. 리허설 클론(약 8.7G)은 시험 드라이브 준비에 다시 쓴 뒤 지운다.
