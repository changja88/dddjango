## 결정

- **사용자 원칙**(2026-11-13): «openapi 문서는 해당 api 에서 발생하는 에러도 다 적는 게 맞다» · «리팩토링 절차에도».
- **사용자 결정**:
  - «나.»(2026-11-13 01:52) — 경로 앞 오류는 API 모듈 한 곳에서 자동으로 붙인다.
  - «그러자.»(08:34) — 계획 v1 승인.
  - «나»(17:49) — 캐시 지시 머리(`Cache-Control` · `Pragma` · `Expires`)는 오류 문서 머리 대조에서 뺀다.
    - 계획 멈출 기준(c 밖 새 판정이 기존 정상 코드를 막음)에 걸려 물었다.
    - 현장 사본 한 곳의 머리 빚 211 가운데 183 이 함수 맨 위 `Cache-Control` 이었다.
- **운영자 처분**(질문 생략 · 설계 처리 · 이의 시 뒤집음):
  - 자리 셋으로 나눔(#437 · #415 이웃 규칙).
  - 의도된 답만 적음 · 못 가르는 것은 «날 수 있다» 쪽.
  - 숫자 문자열 키 막음.
  - 흐름을 못 가른 머리 · 답은 ⓓ(셋째 확인 뒤).
  - #437 은 api.py 안 재정의 없는 하위 클래스를 그대로 막음.

## 바뀐 옛 판단

- **결정 기록 D27**(2026-08-06)의 «OpenAPI 도 같다» 는 그때 걷은 api.py 전역 handler 와 함께 문서 생성 재정의 · 후처리를 모두 막았다.
  - 그 목적은 «문서가 실제 동작과 어긋나지 않게» 였고, 경로 앞 오류는 고려 밖이었다.
  - 2.37.0 은 정해진 꼴 하나(정본 지문 · 동작 시험으로 «문서 = 실제 응답» 을 기계로 지킴)만 받는다.
- **D25 T41**(2026-08-09)이 `framework/ninja/` 규칙 클래스를 «닿을 수 없는 관문» 으로 뺀 까닭은 D27 의 재정의 금지였다. 이제는 정해진 클래스 하나로 닿는다.
- 기록은 두고 여기 적는다(2.36.0 선례).

## 한계

`design.md` §8 · §15 그대로다. 사용자에게 닿는 것:

- 선택 인증 401 · 파일만 받는 경로의 Django 상한 400 등은 «날 수 있다» 쪽으로 적힌다.
- 경로 객체로 못 가르는 답은 표 `operations` 행으로만 적는다. 빠짐은 리뷰어 몫이다.
  - 승인 endpoint 406 · 415 · 인증 안 `HttpError` · 확립 표면 경로 코드의 `HttpError`.
- 서드파티 미들웨어 · 앞단 행 · ⓓ 줄은 리뷰어(G1 api 리뷰어 · G2 감수자) 몫이다.
- 미들웨어 판독은 한 단계 도움까지만 한다.
- 같은 반복 몸통에서 머리보다 앞의 오류 return 은 보지 않는다.
- 여러 루트 API 의 자리는 F4-150 큰 판이다.
