# API 문서에 그 경로에서 날 수 있는 오류를 모두 — 경로 앞 응답 계획 v1 (dddjango 2.37.0 후보 · 2026-11-13)

설계 정본은 같은 폴더 `design.md`(v3.1 — 재현 · 시제품 · 꼴 · 검사기 · 글 자리 · 리팩토링 길 · 한계 · 검토 처분 셋)다. 이 문서는 판 범위 · 단위 · 일하는 법 · 멈출 기준만 적는다.

판 번호: 2.37.0 — 문서에 경로 앞 오류를 붙이는 정해진 꼴이 새로 생기고, 그 꼴이 없는 프로젝트는 새 경로를 만들 때 막히므로 minor.

## 결정

- 사용자 원칙(2026-11-13): «openapi 문서는 해당 api 에서 발생하는 에러도 다 적는 게 맞다» · «이건 리팩토링 절차에도 들어가야».
- 사용자 결정 «나.»(2026-11-13 01시 52분): 경로 앞 오류는 경로마다 손으로 적지 않고 API 모듈 한 곳에서 자동으로 붙인다(경로의 인증 · 입력을 보고 · 미들웨어 답은 표 하나로).
- 사용자 «그러자.»(2026-11-13 08시 34분): 계획 v1 승인(요약 설명 뒤).
- 질문 생략 · 설계 처리 · 이의 시 뒤집음:
  - 자리 셋으로 나눔 — `api.py` 의 정해진 클래스 하나 + `framework/ninja/` 파일 둘(정본 · 프로젝트 표). 이웃 규칙(#437 api.py 닫힌 목록 · #415 framework 모듈)이 api.py 에 다 두는 것을 막는다.
  - 적는 것은 코드 · 설정 · 앞단 설정에 그 status 가 적힌 «의도된 답» — 미식별 500 · 앞단 502/504 는 결함이라 약속이 아니고 꼴도 정해지지 않는다.
  - 기계가 가를 수 없는 것(선택 인증의 401 등)은 «날 수 있다» 쪽으로 적는다.
  - 지금 허용된 «성공 응답 머리 보충» 의 숫자 문자열 키(`"200"`)도 막는다 — 문서에서 그 응답 몸통이 사라진다(시제품 재현).

## 사용자에게 보이는 흐름

1. 경로 코드는 그대로다(`@router.post("/books", auth=…, response={201: …, 409: …})`).
2. 프로젝트에 한 번 `api.py` 클래스와 `framework/ninja/` 파일 둘을 둔다 — 설계(G1)가 미들웨어 · 앞단 답의 표를 근거와 함께 적고 승인받는다.
3. 생성 문서에 경로마다 401 · 403 · 429 · 400 · 422(Ninja) · 미들웨어 · 앞단 답이 실제로 나는 경로에만 붙는다. BC 오류의 `Retry-After` 같은 머리도 문서에 선다.
4. 표의 행마다 «그 답을 실제로 일으켜 문서 꼴과 맞는지» 시험이 붙는다.
5. 그 꼴이 없는 프로젝트는 검사기가 경로마다 «경로 앞 오류가 문서에 없다» 를 낸다 — 기존 경로는 빚(리팩토링이 갚음) · 새 경로는 막힘.

## 받아들이는 한계(설계 §8 요지)

- 기계가 가를 수 없는 답은 «날 수 있다» 쪽 — 선택 인증 401 · 파일만 받는 경로의 Django 상한 400 · «읽기만 허용» 권한의 GET 403 · `A | AllowAny` 권한 403 · 필수 인증 경로의 익명 throttle 429.
- 경로 객체로 못 가르는 답(승인 endpoint 의 406 · 415 · 인증 안 `HttpError`)은 표 `operations` 로만 — 빠짐은 리뷰어 몫.
- 미들웨어 판독(d)은 정해진 꼴만 · 못 읽은 것은 ⓓ 후보 · 서드파티 미들웨어와 앞단(nginx) 행은 리뷰어 몫.
- 정본은 Ninja 내부에 기댄다(1.6 이상) — 판 올림은 동작 시험 · 행 시험이 잡는다.

## 일하는 법

- 구현은 단위마다 옛 판(2.36.0 · 태그 `dddjango--v2.36.0` 사본) 붉음(또는 놓침) → 새 판 녹색 · 대조군 통과를 실제로 돌린다. 시제품(`workspace/scratch/f4-173-openapi-errors/` — `make_v3.py` · `proto3/` · `join3/` · 검토 장난감 셋)을 출발점으로 쓴다.
- 현장 줄 차이(읽기만 · git 을 쓰지 않는 검사기 · 레코드는 자기 폴더로): c 줄이 경로 수만큼 새로 서는 것 말고 2.36.0 대비 다른 차이 0 이어야 한다(c 줄 수는 보고에 적음).
- 계획 승인 → 구현(구현자 셋 — 검사기 A · B / 리팩토링 · 시험 C · D / 글 E · F — 파일이 겹치지 않게) → 구현 독립 검토 → 고침 · 좁은 재확인 → 묶기 → 봉인 · 커밋 → `make verify` · `make verify-mutation` → 장부 다시 읽기 → 배포.

## 멈출 기준

- 검토 차단이 셋째 확인에도 닫히지 않으면 멈추고 묻는다.
- 새 판정이 c 밖에서 정상 코드를 새로 막으면 그 갈래를 멈추고 알린다.
- 동작 시험 환경(`.venv-probe` 에 Ninja)이 Django 6.1 고정 판과 맞지 않으면 멈추고 다른 길(별도 고정 venv)을 알린다.
