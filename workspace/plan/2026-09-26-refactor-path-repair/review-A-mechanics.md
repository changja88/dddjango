# 적대 검토 A — 규범 기계·정합 (design-v2 · 2026-09-26)

대상 `design-v2.md`(이하 D) · 결정 B1/R1/R2(`progress.md`)는 전제로 둔다. 표기: C = `dddjango/commands/dddjango.md` · HR = `dddjango/skills/discipline-houserules/SKILL.md` · G = `dddjango/REQUEST_GUIDE.md` · RG = `dddjango/scripts/registry_gate.py` · AD = `dddjango/scripts/anchor_diff.py`. 파일 쓰기는 이 문서 1건 · 검사기 실행 0 · Serena/Graphify 미사용.

## 판정: **수정 후 승인** — C5(실행·앵커)는 부분 재설계

C1·C2·C3·C7 은 방향이 결정 B1/R1/R2 와 맞고 HR:29·final §4 와 정합한다. C5 는 운반체가 설계 안에서 모순되고, 세탁 경로 셋을 새로 연다. C4 는 R2 의 핵심 사례(발주자 실시간 답 21건)를 기계적으로 가르지 못한다. 아래 blocker 3건과 major 8건을 고친 뒤 계획 단계로 간다.

## Blocker

**B-1 실행 줄 운반체가 설계 안에서 모순되고, 두 기존 규범을 위반한다**
- D:49 는 실행 줄을 «`scope.md` 끝에 append», D:56(C6)은 «`refactor-scope.md` 첫 줄 = 실행 줄»로 쓴다. 재개/새 실행 판정의 단일 출처가 둘이면 판정이 갈린다.
- `scope.md` 는 «사람이 정한 범위»다(C:18 · R-0133 «섞지 않는다»). 또 «`scope.md` 에는 스코프 결정만 적는다»(C:92 · R-0246)고 되어 있다. 앵커 SHA·시각은 기계 메타라 두 규범 모두에 어긋난다.
- «`scope.md`/`refactor-scope.md` 사후 개정은 위임되지 않는다 … 그 지점에서 정지»(C:209 · R-0452)와 «사후 scope 개정 제외»(C:58)가 있다. 자율 실행에서 Phase 2 진입(앵커 추기)과 마무리(D:49)가 문자 그대로 STOP 사유가 된다.
- **처방**: 운반체는 `refactor-scope.md` 첫 줄 하나로 둔다. 이 파일은 코디 소유의 «이번 작업 기록»(C:18)이라 실행 단위와 같은 이유로 바뀐다. `scope.md` 추기는 삭제한다. R-0452·C:58 에는 «실행 줄의 기계 메타 추기(시각·앵커·종료)는 사후 개정이 아니다»를 한정 문구로 넣는다. D §6 에 s002/b2(R-0133)·s003/b10·s011/b5(R-0451·R-0452)를 추가한다.

**B-2 규칙 이전 폴더와 새 세션 재개가 세탁 경로다**
- D:52 의 두 문장이 충돌한다. «실행 줄 없음 → 새 G0 승인이 첫 실행 줄을 만든다(=새 실행 · 새 앵커)»와 «실행 줄 없이 진행 중인 실행(재개)은 앵커를 건드리지 않는다»다.
- Coordinator 에는 Phase 2 재개 진입점이 없다. 모든 호출은 «시작: 모드 판별»(C:64-67)에서 G0 로 가고, «재개»라는 말은 C:210 의 «재개 첫 커밋» 한 곳에만 나온다.
- 그래서 업그레이드 전에 Phase 2 중이던 레인을 새 세션으로 이으면 반드시 새 G0 를 지나고, 첫 문장에 걸려 앵커가 HEAD 로 덮인다. 앞 작업 커밋의 귀속이 legacy 로 흡수된다.
- 이 사용자의 레인은 릴리즈 창 규칙(D:69)이 막는다. 마켓 `ref: main` 일반 사용자에게는 창이 없다.
- **처방**: `build_anchor` 가 있고 실행 줄이 없으면 «미완 실행»으로 본다. 첫 실행 줄은 기존 SHA 를 승계해 쓴다(`실행 <시각> — G0 승인 · build_anchor <기존 SHA>(이전 규칙 승계)`). 새 앵커는 B-3 의 «앞 작업 종료/폐기» 선택이 출처와 함께 있을 때만 쓴다.
- 이 기본값은 과귀속(fail-closed) 쪽이다. 6-3-2 형(끝난 작업의 낡은 앵커)은 사용자 선택 한 번으로 풀린다.

**B-3 «마무리»는 관측할 수 없고, 영속되지 않으며, 행위자가 스스로 쓴다**
- D:49 는 Phase 3 마무리 때 코디가 `· 마무리` 를 덧붙인다. 그런데 Phase 3 에는 게이트가 없다(C:171-174). 마지막 사용자 사건은 G2 승인이다.
- 세 경로가 열린다. ① G2 승인 뒤 세션이 끝나거나 마무리 줄이 커밋되지 않으면(워크트리 폐기 포함), 다음 G0 가 «재개»로 읽혀 끝난 작업이 새 작업의 귀속으로 잡힌다. 그 귀속의 1차 처방은 «철회»(C:114 · R-0310)라서 이미 승인된 코드를 되돌리라는 반송이 된다. ② 반대로 코디가 G2 전에 마무리를 적으면, 다음 G0 에서 새 앵커를 쓰게 된다. 앵커를 actor 가 고르지 않는다는 원칙(RG:15-18)이 깨진다. ③ «사용자가 G0 에서 앞 실행을 버린다고 명시»(D:51)에는 입력 경로가 없다. G0 질문(C:80)에는 그 선택지가 없고, 사용자는 미완 실행이 있다는 사실도 모른다.
- **처방**:
  - 실행 종료는 **G2 승인 응답의 기록 착지**로 정의한다(`· G2 승인 <시각>`). 이 종료 표기는 G2 승인분 산출물 커밋에 포함하도록 의무화한다(C:26 커밋 원칙과 결합).
  - G0 는 선택한 폴더의 최신 실행이 미종료이면 닫힌 선택지 «앞 작업 이어서 / 앞 작업 폐기하고 새로»를 대가와 함께 반드시 제시한다. 폐기의 대가 줄은 «앞 작업이 남긴 변경(앵커..HEAD n커밋)이 기준선으로 흡수돼 이후 귀속되지 않는다»다.
  - 폐기 결정은 C4 와 같은 출처 규칙을 따르고 자율 위임하지 않는다(C:209 목록에 추가).
  - s007/b57(G2 · R-0406~0411)을 D §6 에 추가하고, «Phase 3 절» 항목은 삭제한다.

## Major

**M-1 새 폴더를 고르면 C5 세탁 차단이 우회된다 · C2 폴더 문구가 :24 와 충돌한다**
- D:51 은 같은 폴더 안의 세탁만 막는다. G0 폴더 선택 ⓑ «새 기능(신규 폴더)»(C:80)를 고르면 새 앵커를 얻는다.
- D:31 은 수정 모드의 폴더 절차를 «Phase 0 4번 그대로(=ⓑ 신규 포함)»로 바꾼다. 이것은 «수정 모드 포함 새 폴더 금지»(C:24 · R-0137/R-0138)와 정면으로 모순된다.
- **처방**: 수정 모드는 기존 폴더만 고르게 하고(R-0138 유지, «보통»만 삭제) R-0417 문면을 맞춘다. G0 폴더 목록에는 각 폴더의 미종료 실행 표시를 붙인다. 같은 BC 의 미종료 실행이 있는데 신규 폴더를 고르면 B-3 의 폐기 선택을 먼저 거치게 한다.

**M-2 C4 ①«사용자가 직접 답함»은 코디가 판정할 수 없다 (R2 불충실)**
- 현장 ⓑ 51건 중 21건은 발주자가 같은 입력 채널로 게이트에 답했다(diag-A §3). 코디 쪽에서는 AskUserQuestion 응답이 모두 «직접 답»으로 보인다.
- D:42 «대화형이면 다시 묻는다»는 대리 세션에서 대리가 다시 답해 닫힌다. 그래서 C4 는 암묵 28건과 코디 단독 1건만 막고, R2 의 핵심 사례는 그대로 통과한다.
- **처방**: ⓑ 선택지는 «사유 + 출처(본인 직접 | 사용자 원문 인용)»를 필수 입력으로 받는다. 출처 없는 ⓑ 답은 받지 않는다.
- 원문 인용이면 `출처 = <파일:행>` 으로 받고, 코디가 Read 로 인용 문자열이 실재하는지 확인한다(결정적 · 위조하면 기록에 남는다).
- 원문은 해당 BC 나 항목의 미룸을 명시해야 한다. 캠페인 착수 발화 같은 일반 방침(diag-A §1 «BC 하나씩 리팩터링»)은 출처가 아니다.
- G §7(:176-178)에도 «대리 답의 ⓑ 는 원문 파일:행 필수»를 명기한다.

**M-3 C4 가 위임·충돌 규범과 맞지 않는다**
- (a) «위임되는 것은 승인 입력뿐»(C:209 · R-0451)과 C:58 의 사전 위임 제외 목록에 «출처 없는 G0 ⓑ»가 없다. 발주 위임이 ⓑ 를 «승인 입력»으로 넘기는 읽기가 남는다. 두 곳에 추가한다.
- (b) D:41 의 충돌 선택지 «경계를 넓혀 정리 / 사용자 원문으로 미룸»은 «미룰 수 없음» 항목에 ⓑ 를 연다(C:80 · R-0199 위반). 그 항목의 선택지는 «경계를 넓혀 정리 / 작업 중단» 둘로 한다.
- (c) G §5(:136-138)는 «같은 파일을 동시에 고치는 다른 작업» 사실을 적법한 환경 제약으로 둔다. B1 아래에서 두 레인이 같은 BC 의 ⓐ 로 같은 파일을 옮기는 경우를 C4 가 어디로 보내는지 정하지 않았다. 이 경우를 C4 충돌 유형 «동시 작업 소유»로 명시하고 닫힌 선택지를 둔다(순서 조정 | 원문 있는 ⓑ). 환경 제약 사실은 출처가 아니다.

**M-4 재개 G0 의 스캔·기록 처분이 정해지지 않았다**
- D:51 «G0 를 다시 거쳐도 재개»와 D:56 «새 실행만 `refactor-scope.md` 를 새로 쓴다» 사이에, 재개 G0 에서 Phase 0 3번 스캔을 다시 하는지, 새 빚을 어디에 적는지, ⓐ 동결 시점(C:80 · R-0203)이 언제인지 빠져 있다.
- main 머지 뒤 재개(0924-0502)에서 머지가 새 빚을 들여온 경우가 바로 걸린다. 레인마다 달리 처리하게 된다.
- **처방**: 재개 G0 는 다시 스캔한다. 새 빚만 추가로 ⓐ/ⓑ 를 묻고, `refactor-scope.md` 에 «재개 G0 <시각>» 절로 append 한다. ⓐ 동결은 최신 G0 승인 시점으로 하고, 앵커는 무변으로 둔다.
- 이 조항은 R-0203 개정으로 넣는다(G2 재상정 C:152 와 같은 형태).

**M-5 C2 의 수정 모드 기계가 빠졌다**
- 수정 모드 G1′ 은 «영향받는 lens 만»(C:182)이고, discipline lightweight(C:89)는 부르지 않는다. 그런데 슬라이스 0 이 models·migrations 를 옮기면 db lens 가, controllers·schemas 를 옮기면 api lens(operationId·URL)가 필요하다. 의미 보존 재조직의 입장 감사도 필요하다.
- 수정 모드 3번(C:183)에는 슬라이스 도출과 «슬라이스 0 선행·혼합 금지»(C:105 · R-0270)가 없다. task 리스트 하위 task(C:35 ⓑ)도 수정 모드에 닿지 않는다.
- «국소 수정은 전체 파이프라인을 다시 돌지 않는다»(C:179 · R-0415)와 «영향 범위만 빠르게»(C:181 · R-0416)는 문면이 거짓이 된다.
- **처방**:
  - 슬라이스 0 의 경로 목록에 Phase 0 2번 lens 판정(R-0173/R-0174)을 적용해 G1′ lens 에 합친다.
  - 슬라이스 0 이 있으면 discipline lightweight 를 G1′ 다발에 합류시킨다.
  - C:183 에 R-0270 을 준용하는 문장을 넣는다.
  - R-0415·R-0416 을 개정한다(«설계는 영향 lens 만 · G0 빚 스캔·질문은 Phase 0 그대로»).

**M-6 이관 빚(legacy-debt) 사전 승인이 출처 없는 미룸의 우회로다**
- D:70 은 legacy-debt 를 «변경 없음»으로 둔다. 그런데 현장 레인은 발주서가 사전 승인한 `legacy-debt.txt` 로 순이동 귀속을 뺐다(diag-A §5.5 · 0909-1841 RS:13,22).
- legacy-debt 등재는 «이 위반을 이번에 고치지 않는다»는 미룸이다. R2 의 논리를 따르면 C4 와 같은 출처 규칙이 필요하다.
- **처방**: C:152 의 «사용자 승인 이관 빚»에 «출처 = C4 ①|②, 발주 사전 등재는 원문 파일:행 필수»를 붙인다. 아니면 이 채널을 범위 밖이라고 §4 에 명시해 세탁 경로로 남는다는 사실을 기록한다.

**M-7 C2 의 «범위를 좁혀 지정해도» 문구가 R-0194/R-0195 와 충돌한다**
- D:33 «도구·검사기·범위를 좁혀 지정해도 27종 계약 그대로»의 «범위»는 스캔 범위(= 스코프 BC · C:79 · R-0194)까지 금지하는 것으로 읽힌다. 요청이 정당하게 BC 를 좁히는 것까지 막는다.
- **처방**: «도구·검사기 목록·TARGET·flag»로 한정한다. 새 문장을 추가하지 말고 R-0190(스캔 계약)·R-0191(차분 도구 대체 금지)을 개정한다.

**M-8 C1b 의 «이동이 필요한가» 판정은 설계 판단이다**
- D:26 은 G0 에서 코디가 «이 항목은 기존 파일 이동이 필요하다»를 판정한다. 이는 «갈림길 표면화만 · 설계 근거 생성 금지»(C:80 · R-0205)를 넘는다. 이동 여부는 architect 가 명세를 쓸 때 정해진다.
- **처방**: G0 에서는 사용자 문면에 기존 경로와 이동·분리·개명 동사가 함께 있는 기계적 신호가 있을 때만 C1b 를 올린다. 그 밖의 경우는 G1 에서 discipline lightweight 가 «승인 목록 밖 기존 파일 이동» 발견을 내면(`discipline-reviewer.md:99`) STOP 으로 같은 두 선택지를 제시한다.
- C7 의 가이드 문구 «옮기는 정리는 따로 묻는다»(D:61)는 이동이 승인될 수 있다는 오해를 준다. «현행 규칙상 옮기지 않으며, 바꾸는 줄 안에서 다룰지 뺄지 묻는다»로 바꾼다.
