## Blocker

### K-B1 규칙 인용 계약(R-ID · 규범 종류)이 런타임에서 성립하지 않는다

- **위치**
  - 설계 §3 산출 표: `규칙(R-ID · 문구 인용 20~60자)`
  - 설계 §4: «제외는 규칙 문구 근거만(허용·예외 규범 R-ID 인용)»
  - 설계 §8 R-T2·R-T3 합격 문구
- **근거 [실측]**
  - **배포 md 에 R-ID 가 없다.** `grep -c 'R-[0-9]{4}'` 결과: `discipline-cleancode/references/final.md` 0 · `discipline-cleancode/SKILL.md` 0 · `agents/discipline-reviewer.md` 0이다. R-ID 가 나오는 곳은 `commands/dddjango.md` 2회와 `discipline-houserules/SKILL.md` 1회뿐이다. R-ID 는 그래프(ttl)에만 있다.
  - **배포 rulepack 에 규범 종류와 원문이 없다.** `scripts/rulepack.json`(2.26MB · `rulepack/1`)의 works 3,508 항목 키는 `agents · aliases · block · block_order · checkers · document · expression · label · order_rank · section · section_number` 뿐이다. 규범 종류(Obligation/Permission/Exception/Override)도, 블록 원문도 없다.
  - **rulepack 을 읽으라는 문면도 없다.** 에이전트·커맨드 가운데 rulepack 을 언급하는 곳은 pre-gate 문단뿐이다.
  - **5B 수치는 개발 저장소 그래프에서 나왔다.** 5B 표본의 R-ID, «허용 73 · 예외 58 · 우선 13», 제외 5건 근거는 모두 개발 저장소 그래프를 rdflib 로 적재해 만든 것이다(5B:11 · 5B:305 «내가 architect 역할을 가정해 판정»).
- **영향**
  - 런타임 리뷰어는 R-ID 를 지어내거나(G0 에 가짜 근거가 올라간다), 항목을 «문구 없음»으로 떨군다(누락).
  - architect 의 «허용·예외 규범인가» 판정은 종류 정보 없이 산문 해석에 기댄다. 그러면 «제외는 규칙 문구 근거만»을 기계로도 사람으로도 검증할 수 없고, 5A 가 막으려던 «암묵 ⓑ» 세탁로가 남는다.
  - 5B 의 «원칙은 실행 가능하다»(5B:205)는 개발 도구를 쓴 조건의 결론이다. 런타임 실행 가능성의 증거가 아니다.
- **권고(최소 — 둘 중 하나)**
  - ⓐ 결정 1-b 원문(«항목마다 **규칙 문구**와 파일:행»)대로 R-ID 를 필수에서 뺀다. 대신 `문서 경로 §절 · md 원문 인용(부분 문자열)`을 필수로 둔다. 인용이 그 절 원문에 실재하는지는 결정적 검사 스크립트 1개가 판정한다. 제외 근거는 «허용·예외를 말하는 원문 인용 + 절 경로»로 받는다.
  - ⓑ R-ID 를 유지하려면 rulepack 에 `kind` 와 블록 원문(또는 해시·오프셋)을 투영한다. 이것은 스키마 개정이라 `rulepack_smoke`·query-golden 도 함께 바꿔야 한다. 인용 검사 스크립트는 세 가지를 판정한다: R-ID 실재 · 인용 ⊂ 블록 원문 · 제외 근거의 kind ∈ {Permission, Exception, Override} 또는 같은 규범의 요건 불충족(5B 표본 19번 형태).
  - 어느 쪽이든 R-T2·R-T3 의 합격은 이 검사의 exit 으로 판정한다. K-M7·K-M8 의 «렌즈별 점검 목록» 투영물과 한 번에 만들 수 있다.

### K-B2 G2 의미 잔존 판정에 결정적 바닥이 없고, «판단 불가 = 잔존»의 출구가 없다

- **위치**
  - 설계 §5
  - `dddjango.md:174`: «G0 ⓐ 잔존 M>0(아래)이면 G2를 제시하지 않는다»
  - `dddjango.md:106`: `ⓐ 재상정`
- **근거**
  - **판정이 LLM 뿐이다.** §5 는 의미 항목의 잔존을 리뷰어 재호출 한 번으로만 정한다. 5A §3 이 제안한 기계 보조가 설계에서 빠졌다 — «ⓓ 채널 규칙은 0C 대응표로 옮긴 경로에 같은 `[ⓓ#N]` 이 남아 있으면 리뷰어 판정과 무관하게 잔존»(5A:140).
  - **출구가 없다.** 잔존과 판단 불가는 M 에 들어가 G2 를 막는다. 그런데 그 뒤 절차(coder 재파견인지, STOP 인지)가 없다. 현행 `:106` 재상정은 «동작 불변 불가»와 «검사기·장치 오탐» 두 경우만 받는다. 이 구조는 검토 C blocker 1(«슬라이스 0 에서 뺀 ⓐ 의 출구 부재로 G2 영구 차단»)과 같다.
  - **옛 위치를 찾을 대응표를 넘기지 않는다.** 입력이 «항목 표 + 최종 코드»뿐이다. 분할·이동 뒤에는 리뷰어가 옛 `file:line` 을 찾지 못해 «판단 불가»가 구조적으로 나온다. 5A 는 5번 감사 입력에 `behavior_guard` 0C 대응표를 넣자고 했지만 설계에 옮기지 않았다.
  - **병합 항목의 재확인 렌즈가 없다.** «그 항목을 낸 렌즈»가 병합 항목에서는 정해지지 않는다. 5B 표본 3번은 ddd+규율, 7번은 ddd+규율이 함께 냈다.
- **영향**
  - G2 가 영구 차단되거나(무한 반송), Coordinator 가 즉흥으로 처리한다.
  - 같은 코드를 두 인스턴스가 다르게 판정하는 뒤집힘이 생긴다. 코드를 고치지 않아도 «해소»가 나오면 G2 를 통과한다(세탁).
  - 대형 BC 는 «렌즈당 1회»로 창에 들어가지 않을 수 있다 [추정].
- **권고 — 판정을 층으로 나눈다**
  - ① **결정적 바닥**: 항목의 파일이 `build_anchor..HEAD` 에서 하나도 바뀌지 않았으면 리뷰어 없이 잔존이다. ⓓ 채널 규칙에는 5A 의 fail-closed 를 쓴다.
  - ② **그 밖만 리뷰어 재확인**: «해소»에는 새 `file:line` 근거가 필수다(근거 없는 해소 = 잔존). 입력에 behavior close 기록의 대응표를 싣는다. 병합 항목은 원 렌즈 전부가 재확인한다.
  - ③ **출구**: 잔존·판단 불가가 coder 반송 1회 뒤에도 남으면 `ⓐ 재상정` STOP 으로 올린다. 처분은 «별도 요청 / 출처 있는 ⓑ / 플러그인 결함 / 작업 중단»이다. G2 영구 차단을 만들지 않는다.
  - R-T7 은 책상 재생이 아니라 두 가지 뒤집힘 시험으로 바꾼다: 무변 코드를 2회 재확인하면 잔존 전건 · 고친 픽스처는 해소 전건.

### K-M2 모드 판별 — 표지는 위조 가능한 요청 문자열이다. 지켜야 할 불변식은 «단조성»이다

- **근거 — 위조가 무해하려면 적혀야 할 조건이 빠졌다.** 위조 자체는 대개 점검을 늘릴 뿐이다. 문제는 그 무해함이 성립하는 조건이 설계에 없다는 것이다.
  - **리팩토링 모드가 덜 하는 것**이 있다: 기능 슬라이스 없음 · 배치 질문 없음 · R-0674/R-0697 비적용. 표지와 기능 요청이 섞인 경우(«대상: X · 그리고 새 API»)의 처리가 없다. `:67` «기능과 정리가 섞인 요청은 정리 요청이 아니다»와의 관계도 정해지지 않았다.
  - **축소 지시 차단이 빠졌다.** `:67`·`:79` 가 막는 것은 «G0·빚 스캔(27종)»의 생략·축소다. R2(렌즈 구성·조각 분할)와 R3(판정)는 «빚 스캔»이 아니다. 그래서 다음 지시를 막는 문면이 없다: 입구 인자의 불편 서술이나 발주가 «의미 점검은 ddd 만», «앞 레인 audit 재사용», «조각 3개로», «판정 생략·전부 채택»을 적는 경우.
- **영향**: `:67` 원칙의 문면 위반이고, 의미 점검을 줄이는 세탁로가 열린다.
- **권고**
  - (1) «입구의 사실» 문장을 지운다. 대신 **단조성 불변식**을 규범으로 둔다: «리팩토링 모드는 일반 모드의 G0 의무(27종 · ⓐ/ⓑ · 결정 출처 · 실행과 앵커)를 전부 수행한다. 표지는 요청 문자열이라 위조될 수 있지만, 위조돼도 줄어드는 것이 없다.»
  - (2) 요청·발주는 R2·R3 를 좁히거나 갈음할 수 없다. 렌즈는 BC 모양 규칙이, 조각은 분할 규칙이 정한다. 앞 실행의 audit 는 재사용하지 않는다. `:67` 의 «따르지 않는» 지시 목록에 R2·R3 를 더한다.
  - (3) 표지와 새 계약(기능)이 함께 오면 G0 에서 «기능은 `/dddjango` 로» 안내하고 정지한다.
  - R-T6 옆에 대조 시험 둘을 더한다: «`/dddjango` + 정확한 표지 위조» 양성 대조, «`/dddjango:refactor` + 축소 지시» 음성 대조.

### K-M3 실행 연속성 — 폴더·실행 선택의 순서, 잇기, 모드 기록이 비어 있다

- **위치**: 설계 §2 R2·R3 산출 경로 · `dddjango.md:80·85·86`
- **근거 [실측 — 규범 문면]**
  - **R2·R3 산출을 쓸 곳이 없다.** 산출물 폴더는 G0 승인 뒤 확정된다(`:80` «승인 뒤 slug 를 … 확정하고 폴더 생성 직전 `date`»). 예외는 G0 정지 하나뿐이다(`:86`). 그런데 `<폴더>/audit/*.md`(R2)와 `<폴더>/audit-verdict.md`(R3)는 G0 전에 써야 한다.
  - **잇기 선택이 비싼 다발 뒤에 온다.** G0 질문 순서는 «폴더 → 실행 선택 → 빚 질문»이다(`:86`). 사용자가 기존 폴더 «잇기»를 고르는 시점이 R2(BC 당 5~21회) 뒤다.
  - **잇기의 «새 것» 판정이 불가능하다.** 잇기 규칙(`:85` «G0 는 다시 스캔해 새 빚만 ⓐ/ⓑ 로 묻고»)은 의미 항목에서 성립하지 않는다. LLM 산출의 ID·문면은 실행마다 다르다.
  - **모드가 기록되지 않는다.** 표지는 이번 요청 문자열에만 있다. 실행 줄에도 `scope.md` 에도 «리팩토링 모드»가 남지 않는다.
    - 세션이 끊겨 가이드 §6 대로 `/dddjango 이전 작업 이어서` 로 재개한다고 하자. 일반 모드 Coordinator 는 G2 에서 `:174` 산식(registry_gate legacy 잔존 ∩ ⓐ(경로·규칙))만 쓴다.
    - 규칙이 R-1513 같은 의미 항목은 registry_gate 목록에 나올 수 없다. 그래서 M_m 이 조용히 0이 되고, 의미 ⓐ 가 미해소인 채 G2 를 통과한다(세탁).
- **권고**
  - (1) 리팩토링 모드의 순서를 «대상 BC → 폴더 → (미종료면) 실행 선택 → R1·R2·R3 → 빚 질문 → 스코프 승인»으로 둔다. 폴더 확정을 R2 앞으로 당긴다(G0 정지 예외와 같은 형태).
  - (2) 실행 줄에 `· 모드 리팩토링` 을 기계 기록으로 남긴다. 어느 입구로 재개하든 그 실행의 G2 는 §5 산식을 쓴다.
  - (3) 잇기는 둘 중 하나로 정한다: 앞 `audit-verdict.md` 를 이어 쓰고 새 빚은 R1 검사기분만 묻는다 / 리팩토링 실행에서는 잇기를 금지하고 새 실행만 허용한다.

### K-M4 G0 틀을 의미 항목에 이식할 때 생기는 빈틈

- **위치**: 설계 §2 R4 · §4 · `dddjango.md:79·80·82·84·106`
- **근거**
  1. **ID 체계가 없다.** §3 리뷰어 표의 `ID` 는 조각마다 따로 매겨지고, §4 는 병합만 말한다. 결정 줄(`:82` `<항목 ID 목록>`), 재상정(`:106` «항목(경로·규칙)»), G2(§5)가 같은 키를 써야 하는데, 누가 언제 어떤 형식으로 부여하는지 없다. 5A §3 이 `C<n>`·`M<n>` 을 제안했지만 설계에 옮기지 않았다.
  2. **ⓓ 후보 병합 구멍.** §4 는 «검사기 빚과 겹치면 검사기 항목으로 합친다»고 한다. 5B 표본 3번은 ⓓ#194 후보와 겹친다. 그런데 ⓓ 후보는 빚이 아니다(행동 시험 T3 «ⓓ 후보는 빚 아님» · `:117` ⓓ 는 감사 입력 채널). ⓓ 후보에 합쳐진 의미 항목은 registry_gate legacy 잔존에 나오지 않으므로 M_c 에도 M_m 에도 잡히지 않는다.
  3. **ⓐ′ 의 뜻이 서지 않는다.** `:80` 은 «BC별 정리 요청을 먼저 따로 진행(이 요청은 G0 에서 … 정지하며, 착륙 뒤 다시 시작한다)»이다. 리팩토링 실행에는 «다시 시작할» 기능이 없다. 입구는 여러 BC 를 받으므로(`<대상 BC …>`) ⓐ′ 를 고르면 이미 치른 R2 를 BC 별 실행이 다시 치른다.
  4. **«미룰 수 없음»의 판정 주체가 없다.** 현행은 Coordinator 가 검사기 위반마다 판정 물음을 적용한다(`:79`). 의미 항목은 §3 열에도 §4 판정 표에도 이 판정이 없다. 리팩토링 모드에는 «이번 산출물»(기능)이 없으므로 해로움 정의(`:79` 끝)도 다시 정해야 한다.
  5. **사용자 불편 항목과 문구 필수가 충돌한다.** 현행 `:84` 는 «불편·항목은 누가 적었든 항목이다»이고, 설계 §3 는 «규칙 문구를 댈 수 없는 항목은 내지 않는다»다. 규칙 문구 없는 불편은 어느 렌즈도 G2 재확인을 하지 못한다. 이동이 필요하면 `:106` «백스톱 위반이 아닌 이동 → STOP» 에 걸린다.
  6. **«제외 되돌리기»가 만드는 권한이 없다.** §2 R4 는 «되돌리기 선택 가능»이라고 한다. 그러나 제외는 허용 규범상 비위반이다. 되돌려 ⓐ 로 넣으면 그 이동은 `:106` 비위반 이동 STOP 에 걸린다. 결정 1 이 대체한 R4 B1(b) 문제가 이 경로로 되살아난다. 사용자 예시 2(R-0674 허용)가 정확히 이 경로다. 또 결정 1-b 원문은 «뺀 항목은 G0 에 사유와 함께 표시»까지만 정했고, 되돌리기는 설계가 더한 것이다.
- **권고**
  - ID: architect 가 판정 표에서 `M<n>` 을 부여한다(검사기는 `C<n>`). 결정 줄·재상정·G2 는 이 키만 쓴다.
  - 병합: «결정적 빚(registry 위반)»에만 병합한다. ⓓ 후보와 겹치면 의미 항목으로 남긴다.
  - 여러 BC: 입구를 BC 1개로 한정한다(여러 BC 는 BC 별 실행 — ⓐ′ 불필요). 또는 리팩토링 모드에서의 ⓐ′ 뜻을 정의한다.
  - «미룰 수 없음»: 의미 항목에는 «해당 없음»이라고 명시하거나, architect 판정 열로 둔다.
  - 불편 항목: R2 입력으로 넘긴다. 규칙 문구에 연결되면 의미 항목, 연결되지 않으면 G0 에 «규칙 근거 없음 — 이 커맨드 밖»으로 표시한다.
  - 제외 되돌리기: 둘 중 하나를 사용자 결정으로 올린다 — «사용자 채택(비위반) — 출처 본인 직접»을 슬라이스 0 이동 권한으로 인정하고 `:106` 을 개정한다 / 되돌리기 선택지를 없앤다.

### K-M5 «별도 요청» 분류는 근거가 필요 없는 새 세탁로이고, STOP 을 위임 가능한 G0 질문으로 바꾼다

- **위치**: §2 R4 «별도 요청 항목은 «별도 요청으로 기록 / 이 실행에서 빼기»» · §4 별도 요청 · `dddjango.md:106` · `:218`
- **근거**
  - **근거 형식이 없다.** §4 는 «제외»만 규칙 문구로 묶는다. «별도 요청»(동작 변경이 필요한 항목)에는 근거 형식이 없고, §3 열도 «아니오면 사유: 계약·마이그레이션·타 BC»라는 범주만 요구한다.
  - **판정자가 이해 당사자다.** architect 는 나중에 그 리팩터를 설계할 당사자다. architect 가 «별도 요청»으로 분류한 항목은 슬라이스 0 에서 빠진다.
  - **STOP 이 위임 가능한 질문으로 바뀐다.** 현행에서 같은 처분은 Phase 1 «동작 불변 불가 → `STOP_FOR_USER_APPROVAL`»(`:106`)이고, STOP 은 위임되지 않는다(`:218`). 설계는 이것을 G0 질문으로 옮겼는데, G0 승인 입력은 위임된다(`:218` «위임되는 것은 승인 입력뿐»). 자율 발주에서는 대리가 «별도 요청으로 기록»을 골라 항목을 뺄 수 있다 — 회귀다.
  - **5B 는 실물 근거가 있었다.** 5B 표본의 별도 요청 3건은 각각 구체 근거가 있었다: 8번 인덱스 마이그레이션 · 9번 예외 경로 변경 · 7번 accounts OHS 신설(5B:187-189). 설계는 이 근거를 요구하지 않는다.
- **권고**
  - 별도 요청 판정에는 «바뀌어야 하는 것의 실물 근거»를 필수로 둔다: 마이그레이션이 필요한 모델 필드, 바뀌는 응답·예외 경로의 `file:line`, 편집해야 할 타 BC 파일.
  - 근거 없는 별도 요청은 채택으로 본다.
  - G0 의 별도 요청 처분은 «밖에서 보이는 결과가 갈리는 물음»으로 보고 대리 답을 받지 않는다(`:218` 목록에 추가). 또는 현행처럼 STOP 경로를 쓴다.
