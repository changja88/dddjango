- 수정 제안 (비용은 v3 와 같은 수준이고, 코드가 오히려 단순하다)
  1. **정의 단위 대응표**
     - 창 안에서 바뀐 제품 파일의 최상위 정의(def · class · 모듈 수준 대입)를 `(이름, 노드 AST 해시)` 로 모은다. 옛 모듈에서 사라지고 다른 모듈에 **하나만** 나타나면 `옛모듈.이름 → 새모듈.이름` 이다.
     - 모듈 단위 대응은 두 가지다. ① import 를 뺀 AST 가 같은 삭제·추가 쌍. ② 옛 모듈의 함수·클래스 정의가 옮겨 간 곳(후속 모듈 — 상수만 옮겨 간 곳은 제외).
  2. **AST 비교**
     - 테스트 파일은 import 를 «바인딩 집합»으로 본다. 바인딩은 `(묶인 이름, 모듈 | 모듈.속성)` 이다. `from P import N` 에서 `P.N` 이 모듈이면 모듈 바인딩으로 푼다. 상대 import 도 푼다.
     - import 가 아닌 본문은 AST dump 를 비교한다. 그래서 순서·괄호·줄바꿈·주석은 판정에 안 들어간다.
  3. 치환은 **옛 판에만 한 번** 적용한다. 새 경로가 옛 경로를 접두로 품는 승격(`…x` → `…x.x`)에서 두 번 치환하지 않기 위해서다(재생 중 실제로 겪었다). 문자열은 식별자 경계로 최장 접두를 치환한다(`"a.old.helper"` → `"a.new.helper"`).
  4. 재생 결과(§1): 순수 이동 41파일 중 40파일이 green 이다. 계약 변경 커밋의 red 는 그대로다.

## 3. Major

### M-1. close ↔ 창 감사 순서가 여전히 순환이다. red 뒤·감사 반영 뒤 close 를 다시 돌리는 규칙이 없다 (G2 N-1 미해소)

- 근거
  - v3:33: close 는 «마지막 슬라이스 보고와 **그 경량 감사 반영**을 받은 뒤»에 한다.
  - v3:66: DR 은 «창 경량 감사 입력에 **close 보고**(0T 의 테스트 diff 목록 · 0C 의 치환 목록)를 준다».
  - 감사는 close 보다 앞서야 하면서, 동시에 close 산출을 입력으로 받아야 한다.
  - red 처방(v3:71 철회)이나 감사 반영 편집 뒤에는 close 를 다시 돌려야 green 이 된다. 그런데 v3 에는 close 재실행 규칙이 없다. `w<n>-close.json` 은 한 벌뿐이고, «닫힌 창 재open 거부»만 있다. verify 는 «모든 창 close green»이어야 green 이다(v3:34). 그래서 철회로 고친 창은 G2 로 갈 길이 없다.
- 수정 제안
  - 순서를 «마지막 슬라이스 보고 → `close` → (red 면 철회 → `close` 재실행) → 다음 파견»으로 고정한다.
  - close 는 다음 파견 전까지 몇 번이든 돌릴 수 있다. 마지막 판정이 유효하고, 앞 판정은 파일에 append 로 남긴다.
  - 감사는 §5-2(창별 감사 신설 제외)대로 기존 주기에 두고, close 보고를 홀리스틱 입력에 붙인다. 창 감사를 남기려면 «close → 감사(close 보고 입력) → 반영 편집이 있으면 close 재실행» 순서로 적는다.

### M-2. 0C 치환 편집·0T 테스트 편집의 규범 근거가 없다. AT 에게 대응표를 건넬 시점도 없다 (G2 N-3 부분)

- 근거
  - DR «Phase 2 hunk 대조»: «일반 `retain` 은 무편집»(DR:58). 0C 의 치환 hunk 에는 입장 행이 없다(기존 테스트는 `retain`). v3 §3 은 DR 에 입력만 더했고 이 규칙의 예외를 두지 않았다. 그래서 기계가 green 이라 한 치환이 DR blocker 가 된다.
  - AT: «행이 없거나 owner 가 아니면 쓰지 않는다»(acceptance-tester.md:29). v3:65 는 AT 를 e2e 치환의 소유자로 두지만, 행 없는 편집을 허용하는 문면이 없다.
  - **대응표는 close 가 만든다**(v3:41). 그런데 AT 는 close **전에**(창 안에서) 편집해야 한다. 창 중간에 대응표를 내는 명령이 없다. Coordinator 가 대응표를 손(LLM)으로 만들게 된다.

## 5. 빼거나 단순화할 수 있는 것 (두 보장 유지)

1. **AT 를 창에서 뺀다** — 0C 의 치환 편집은 소유와 무관하게 coder 가 하고, 판정은 close 다(M-2). AT 문면과 Codex 미러 1곳, 창 중간 대응표 전달 문제가 함께 사라진다. SDS 에서 e2e 가 제품 모듈을 import 하는 경우는 0 이라 잃는 것이 없다.
2. **창별 경량 감사 신설(v3:62)을 뺀다** — 기존 감사 주기를 유지하고, close 보고를 홀리스틱 입력에 붙인다. M-1 순환이 사라지고, 슬라이스 0 이 있는 레인마다 DR 호출 1~2회가 줄어든다. 0T 단언 약화 판정이 홀리스틱으로 밀리는 것이 대가다. SDS 현존 0T ⓐ 는 7건이고 전부 factories 의 주석(#645·#647)이다.
3. **`accepted.txt`·«장치 오탐» 라벨을 뺀다** — 장치 오탐이면 기존 `ⓐ 재상정` 처분 «플러그인 결함»(C:106)으로 항목을 슬라이스 0 에서 빼고 편집을 철회한다. 그다음 close 를 다시 돌린다(M-1). 새 파일 소유(산출물 위치 절)와 새 처분 라벨(G2 m2-12)이 둘 다 필요 없다.
4. **verify 의 ⓐ 건수 파서를 grep 1줄로 바꾼다**(m-6).
5. **토큰 diff 를 AST 비교로 바꾼다** — B-1 의 수정 자체다. 토큰 정렬·괄호·주석 처리 코드가 통째로 빠진다.
6. **제품 쪽 전체 해시 맵을 빼고 HEAD + dirty 로 둔다**(m-7).
7. **동적 마이그레이션은 close 빠른 경로로 둔다**(M-8 — No changes 면 open 불필요).
8. **창 안 머지는 재open 대신 «머지 경로 제외 + 겹침만 exit 1»로 한다**(M-7 (가)).
- 빼면 안 되는 것: B-1 의 정의 단위 대응·AST 비교 · M-3 의 테스트 쪽 비 `.py`·pytest 설정 · M-4 의 분류 중립 이동 · M-6 의 수정 모드 한 구절 · M-1 의 close 재실행.
- 사용자에게 올릴 것: M-5 의 (가)/(나) 1건. 결정 7 정리가 이 장치를 지나가므로 로드맵 5 전에 정해야 한다.
