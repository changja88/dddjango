### 1-2. 모드 판별 — 단조성 불변식

- 판별 입력은 둘뿐이다.
  - ① 요청 첫머리의 **정확한 표지** `리팩토링 모드(입구 /dddjango:refactor) · 대상: …`.
  - ② 고른 폴더의 미종료 실행 줄 `· 모드 리팩토링`(재개 — §2-3).
- **단조성 불변식**(규범): «리팩토링 모드는 일반 모드의 G0 의무(27종 스캔 · ⓐ/ⓑ · 결정 출처 · 실행과 앵커)를 전부 수행하고 R2·R3 를 더한다. 표지는 위조될 수 있으나 위조돼도 줄어드는 G0 의무가 없다.»
- 리팩토링 모드가 덜 하는 것(기능 슬라이스 · 배치 질문)은 **기능이 없을 때만** 성립한다. 기능 혼입은 R0 에서 입구 인자로 판정한다. 불편 서술이 새 동작·새 계약을 요구하면 입구 정지 + «기능은 `/dddjango` 로».
- **표지 fail-closed**: 요청 첫머리가 표지 접두 `리팩토링 모드(입구` 로 시작하나 정확한 표지가 아니면, 일반 모드로 강등하지 않고 입구 정지(«표지 손상 — 입구를 다시 부른다»). 본문 어딘가에 입구 이름이 나오는 기능 발주는 해당 없음.
- **R2·R3 축소 금지**
  - 대상 지시: 요청·발주·불편 서술·**게이트 피드백**.
  - 따르지 않는 내용: 렌즈 구성·조각 분할·앞 실행 audit 재사용·판정 생략·일괄 채택·결과 지정. 렌즈와 조각은 §3 결정적 규칙이 정한다.
  - 모드 판별 절의 «따르지 않는 지시» 목록에 이것들을 더한다.
- 요청문의 «리팩토링 모드로» 류 문구(표지 아님)는 판별 입력이 아니다.

### 1-3. `/dddjango` 로 들어온 정리 요청 (결정 11 — 설계 (가))

- 표지 없는 `/dddjango` 요청이 «구조 정리만»(기능 없음)이면 **모드 판별 직후 · 27종 실행 전**에 `/dddjango:refactor <BC>` 를 안내하고 입구 정지(기록 없음 · 폴더 없음).
- 현행 «정리 요청»(검사기 빚만 정리하는 풀 파이프라인) 경로는 없어진다. 기능 요청의 G0 빚 처리(검사기 빚 ⓐ/ⓑ)는 그대로다.
- 기능 요청 G0 의 ⓐ′(`:80` «BC별 정리 요청을 먼저 따로 진행»)는 안내 대상이 `/dddjango:refactor <BC>`(BC별 실행)로 바뀐다. 그 실행은 의미 점검까지 하므로 ⓐ′ 대가 줄에 «BC별 리팩토링 실행(의미 점검 포함)»을 적는다.
- 재개(`/dddjango 이전 작업 이어서`)는 정리 요청이 아니다 — 모드는 실행 기록이 정한다(§2-3).

### 2-2. 모드 기록

- 실행 줄: `실행 · G0 승인 <값> · 모드 리팩토링`(기계 기록 · 경계 절의 «사후 개정» 아님).
- 어느 입구로 재개하든 그 실행은 리팩토링 모드다. G2 는 §7 산식을 쓴다(`/dddjango 이전 작업 이어서` 재개에서 M_m 이 0 으로 빠지는 세탁을 막는다).

### 2-3. 폴더·실행 선택과 재개

- **폴더 후보**(리팩토링 모드): `refactor-<bc 케밥>` 계열 폴더만 보인다(기능 폴더는 보이지 않는다 — «한 기능 = 한 폴더» `:24` 보존).
  - 같은 BC 폴더가 있으면 그 폴더만 보이고 «새 폴더»는 없다. 끝난 실행 뒤의 새 점검은 그 폴더의 «새 실행»이다.
  - 없으면 «새 폴더»뿐이다. 신규 slug = `refactor-<bc 케밥>`(`:22` 영문 케밥)이고, 이 시점에 확정한다(`G0 정지` 와 같은 «승인 뒤 확정»의 예외).
- **폴더 후보**(기능 모드): `refactor-` 폴더는 미종료 리팩토링 실행이 있을 때만 «미종료 리팩토링 실행 잇기»로 보인다. 기능 실행이 리팩토링 폴더에 들어가지 않는다.
- **잇기**: 미종료 실행이 `모드 리팩토링` 일 때만 잇는다. R2·R3 를 다시 돌리지 않고 그 실행의 `verdict.md` 가 그대로다(M 목록 동결). 새 빚은 현행대로 R1 검사기분만 묻는다.
- 미종료 실행이 기능 모드면 리팩토링 모드에서는 잇기가 없다(기능 실행을 표지로 잇지 않는다). 반대로 `/dddjango`(표지 없음)로 리팩토링 실행을 잇는 것은 허용된다(모드는 기록이 정한다).
- **`/dddjango` 재개의 전환 지점** = 실행 선택에서 `모드 리팩토링` 실행을 잇기로 고른 순간이다.
  - 그때 일반 모드 Phase 0 산출(lens 제안·배치 질문)은 버리고 리팩토링 흐름의 다음 단계로 잇는다.
  - 요청에 기능이 섞였으면 G0 정지 + `/dddjango` 안내(기능은 별도 실행).
- **새 실행**: R2·R3 를 새로 돌린다(`audit/<새 R2 시각>/` — 앞 실행 audit 재사용 없음).
- **G0 정지 재개**
  - 리팩토링 실행의 `G0 정지` 절에 `모드 리팩토링 · audit <R2 시각>` 을 적는다.
  - 같은 폴더에서 다시 시작했고 최신 기록이 이 정지이면, 두 조건을 모두 만족할 때 **그 audit·verdict 를 재사용**하고 R1(검사기)만 다시 돈다.
    - audit 시각 이후 대상 BC 파일이 바뀌지 않았다(`git diff --quiet <audit 앵커> -- application/<bc>/` · 작업 트리 포함). 새 파일도 없다(`git ls-files --others --exclude-standard -- application/<bc>/` 가 비었다).
    - `check-verdict` 를 다시 돌려 exit 0 이다.
  - 파일이 바뀌었으면 새 점검이다.
  - 재사용 거부(«새로 점검»)는 사용자 본인 직접만 한다.
  - 효과: 사용자 판단 답이 착지하고, 자율 레인의 같은 정지 반복이 끊긴다.

- **`plan` 규칙**
  - 렌즈: ddd·discipline 은 항상 켠다. api = HTTP 어댑터 파일 있음. db = Django 모델 있음.
  - 보안 절(결정 12 의 ORM·보안 몫 가운데 보안)은 db 렌즈가 켜지면 db 가, 아니면 api 가 맡는다. 모델 없이 HTTP 어댑터만 있는 BC(현장 4개)에도 판정 주체가 선다.
  - 조각: 표준 트리 #81 층 순서(`driving_layer → application_layer → domain_layer → driven_layer → composition_root → published_event → test`). 트리 밖 파일은 «트리 밖» 조각이다. 조각 문턱은 5,000행이고, 문턱을 넘는 단일 파일은 단독 조각이다.
- **정규화**: 강조 `**`·`*` · 백틱 · 인용 줄머리 `> ` 를 지우고, **공백류(줄바꿈 포함)를 전부 지운다** — 인용·문서 양쪽에 같은 정규화를 쓴다(문장 중간 강제 줄바꿈에 걸린 인용도 맞는다). 절 경계는 그 제목부터 같은 수준 이상의 다음 제목 전까지다(하위 절 포함).
- **문장**(§4-3 한정 어구 판정 단위 — N-M3): 결속 범위 원문을 `다.`·`.`+공백·목록 머리·표 칸·원숫자·빈 줄에서 나눈 뒤 각 문장을 정규화한다. 인용이 걸친 문장 전부가 «인용이 든 문장»이다.
- **블록 결속**(M-M3 반영)
  - rulepack 에 블록별 투영을 더한다: `blocks: {<block id>: {"h": <정규화 sha256[:16]>, "n": <행 수>, "works": [R-ID…]}}`.
  - 블록은 이관 명세가 고른 **행 범위**다(`ontology_migrate.py:11~18`). 렌더러는 블록을 구분자 없이 잇는다(`ontology_render.py:79`). 해시는 `ontology_rulepack.py` 가 렌더 함수를 빌려 계산하고, 블록 원문은 싣지 않는다(q4 «`djr:text` 금지»·동결 개정 8 무접촉).
  - `refactor_audit.py` 는 설치본 문서 **전체**를 행 단위로 읽는다. 블록마다 `n` 행 창을 밀며 정규화 해시가 같은 행 범위 [i, j] 를 찾는다. 인용이 그 범위 본문 안에 있으면 결속이 선다.
  - 내용 기반이라 byte 미러·의미 미러·플랫폼을 가리지 않는다(M 실측: Codex 의미 미러에도 블록 원문이 65~90% 그대로 있다).
  - **결속 실패 행**(블록을 못 찾거나 인용이 어느 블록에도 없음)은 R-ID 가 없어 제외·오탐 근거가 될 수 없다(fail-closed · 채택 쪽).
  - 인용이 **서로 다른 블록 둘 이상**에 적중하면 결속 실패다(더 긴 인용이 필요하다 · N-m5 — 한 블록의 겹친 창 여럿은 같은 블록이다).
  - Codex 는 의미 미러라 결속 실패 블록이 있다(N 실측: 범위 블록 14/43 · 허용·예외 42/352). fail-closed 그대로 둔다 — 판정이 채택 쪽으로만 기울고, 그 항목은 G0 ⓐ/ⓑ 질문으로 사용자에게 보인다. 의미 미러 원문 복원은 하지 않는다. R-T0 의 Codex 1회에 이 경우를 기록한다(N-m10).
  - 한 블록이 여러 규범을 진술하면 결속은 «블록의 규범 집합»까지다.
- **rulepack 투영 필드**
  - works 에 `norm_kind`(Obligation·Prohibition·Permission·Exception·Override — 기존 어휘 `djr:kind`(블록 종별)와 겹치지 않는 이름).
  - works 에 `overrides`(대상 R-ID 목록 · `djr:overrides` 는 vocab `djr.ttl:165` 에 있고 지금 사용 0 · SHACL property shape 추가).
  - 최상위에 `blocks`.
  - 연쇄: q4 질의 · `ontology_rulepack.py` · `rulepack_smoke` · query-golden · `make rulepack`.
- **플랫폼 경로 사상표**: Claude `dddjango/skills/<x>/…` ↔ Codex `codex-dddjango/skills/<y>/…`, 에이전트 md ↔ 역할 SKILL. 인용은 그 플랫폼 설치본 파일에서 찾는다.
- 리뷰어·architect 에게는 Bash 가 없다 — 이 도구는 **Coordinator 만** 돌린다. `outline`·`sections` 는 파일로 쓰고 경로만 넘긴다(리뷰어·architect 는 Read 가 있다 · Coordinator 출력을 불리지 않는다).

### 3-3. 산출 표

`행# | 규칙 = <문서> §<절> «원문 인용 20~60자» | 반대 방향 규칙(있으면 같은 형식) | 파일:행 | 위반 요지 | 동작 불변 정리 가능(예 / 아니오 — 사유: 계약·마이그레이션·타 BC) | C<n> 과 같음(있으면 ID)`

- R-ID 는 요구하지 않는다(배포 md 에 R-ID 가 없다). R-ID 는 `check` 가 블록 결속으로 붙인다.
- 규칙 문구를 댈 수 없는 항목은 내지 않는다.
- **불편 서술 항목**은 예외다. 규칙에 이으면 일반 행으로 낸다. 잇지 못하면 `규칙 = 근거 없음(불편 #k)` 행으로 내고, G0 에 «규칙 근거 없음 — 이 커맨드 밖»으로 표시된다.
- **표만 낸다**(산문 없음). Coordinator 는 받은 표를 그대로 `Write` 하고 대화에 다시 출력하지 않는다.

- **기술 규칙 분담(결정 12 (가))**
  - api 에 ninja 약 80 · db 에 Django ORM 과 보안 약 117(보안은 `plan` 규칙대로 api 가 대신 맡을 수 있다) · discipline 에 python 약 73.
  - 점검 절 목록에 해당 스킬 절을 더하고 **플러그인 루트 경로로 읽는다**(frontmatter 스킬 목록은 모드별로 바꿀 수 없다 · Codex 는 역할 SKILL 에 같은 경로 열람 문면).

- **테스트 충분성은 점검 항목이 아니다**(원칙): 단언 강도·보호 범위·커버리지 부족은 내지 않는다.
- 이 모드에서 푸는 리뷰어 행동 조항(구현 코드 열람 금지 · diff 한정 · «기술 구현 정확성은 보지 않는다» 경계 등)은 대상 목록의 **⑵ 몫**이다(§4-4 — 문면 해제와 판정 검사가 한 목록을 쓴다). ⑵ 는 BC_AUDIT 모드(R2 점검·G2 잔존 확인)와 R3 에서만 풀리고, 슬라이스 0 의 Phase 1 리뷰·Phase 2 감사에서는 그대로다. 구현 체크리스트의 «Phase 2 implementation 에서만»(DR `:72`)은 BC_AUDIT 에 적용할 항목(입장 표·diff 전제 항목 제외)을 문면으로 정한다.
- ddd·db 리뷰어에는 «실행 모드» 절이 없다 → 모드 절을 신설한다. 기본 모드는 지금의 Phase 1 리뷰이고, 명시 입력이 있을 때만 BC_AUDIT 이다.

## 4. design-architect «의미 항목 판정» 모드

### 4-1. 입력

- `check.md`(통과 행 + 인용 불일치 목록).
- `sections.md`: 인용 절과 반대 방향 절의 절 전체(같은 절의 허용·예외·우선이 함께 온다) + 적용 범위 규범 원문·대상 목록.
- `outline.md` · `C<n>` 목록 · 자기 도구 Grep.

### 4-2. 판정 범주와 ID

`M<n> | 원 행(렌즈-조각#행) | 판정 | 근거 | 파일:행 목록`

- 판정 범주
  - **채택**.
  - **병합 → M<k> 또는 C<n>**.
  - **제외**.
  - **오탐**(규칙 문면상 위반 아님 · 요건 불충족 포함).
  - **사용자 판단**(규칙 충돌 — 두 규칙이 반대 방향이고 문면으로 가를 수 없음 · 5B 표본 5·7).
  - **별도 요청**.
- `M<n>` 은 architect 가 부여한다. 결정 줄·재상정·G2 는 이 키만 쓴다. R3 재실행(§5 수정 요청)에서 기존 `M<n>` 은 유지하고 새 항목만 뒤에 번호를 붙인다.
- 비용·일정·규모는 빼는 사유가 아니다(그것은 사용자의 ⓑ 다).

### 4-3. 빠지는 출구 네 가지와 검사 (증명 책임은 빼는 쪽)

| 출구 | 필수 근거 | `check-verdict` 가 보는 것 |
|---|---|---|
| **제외** | `R-ID «인용»` | 아래 ①~④ 전부 |
| **오탐**(요건 불충족 포함) | **위반으로 인용된 바로 그 블록의 요건 문구 인용** | 인용 ⊂ 위반 행의 결속 블록(같은 절의 다른 문장은 불가) · 결속 블록 `works` ∩ 대상 목록 ≠ ∅ 이면 **인용이 든 문장**이 적용 한정 어구를 포함할 때 red |
| **별도 요청** | 리뷰어 행 «동작 불변 정리 가능 = 아니오 — 사유» + 유형별 근거(§4-5) | 리뷰어 «아니오» 가 없으면 채택으로 재분류 · 근거 유형 검사(§4-5) |
| **병합** | 대상 ID | M → M: 대상 = **채택** `M<k>` 뿐(제외·별도 요청 항목으로 사슬 병합 금지). M → C: 리뷰어가 그 행에 «`C<n>` 과 같음»을 적었을 때만(같은 파일 갈래는 걷었다 — N-m1) |

- **제외 검사 ①~④**
  - ① 인용이 결속된다(§3-1).
  - ② 근거 R-ID 가 결속 블록의 `works` 에 있다. 종류 ∈ {Permission, Exception}, **또는** 리뷰어가 «반대 방향 규칙» 열에 적은 규칙(종류 무관 — 5B 표본 R-1395 Prohibition 형). Override 갈래는 두지 않는다(N-B1 — 그래프에서 `overrides` 를 갖는 규범은 적용 범위 Override 하나뿐이라 정당한 용도가 없다. R-1279 형 정당한 Override 는 «반대 방향 규칙» 열로 들어온다).
  - ③ 근거 R-ID 가 **대상 목록**(§4-4)에도, **적용 범위 규범 자신**에도 없다. 결속 블록이 대상 목록 규범을 품으면 **인용이 든 문장**(§3-1)이 적용 한정 어구를 포함하지 않는다.
  - ④ **혼합 블록**(의무·금지와 허용·예외가 한 블록에 함께 있음)이면 제외 인용 구간이 위반 행의 인용 구간과 겹치지 않는다.
- **사용자 판단 검사**: 반대 방향 규칙 인용에 ③ 과 같은 식을 쓴다 — 적용 범위 규범 자신이거나, 결속 블록이 대상을 품고 인용이 든 문장이 적용 한정 어구를 포함하면 red 다(N-m2 — 블록 집합 교집합이면 범위 블록의 대상 아닌 형제까지 막힌다). 결정 18 이 이미 가른 충돌이라 묻지 않는다.
- 근거 없는 별도 요청 → 채택으로 재분류(`verdict-log.md` 기록). 그 밖 검사 실패 → `check-verdict` red → architect 재호출(1회) → 또 red 면 그 행은 **채택**으로 기록하고 exit 0 에 이른다(재분류 기록 포함).
- **되돌리기 선택지는 두지 않는다**(결정 1-b 원문은 «뺀 항목은 G0 에 사유와 함께 표시»까지다. 되돌린 항목은 비위반 이동이라 `:106` STOP 에 걸린다). 판정 이의는 §5 «수정 요청»으로 한다.

### 4-4. 적용 범위 규범과 대상 목록 (결정 18 (가))

- **규범**: Coordinator «리팩토링 모드» 절에 규범 1개를 둔다(새 R-ID · `norm_kind = Override`). 문면은 두 몫이다(N-M1 — v4 처럼 리뷰어 행동 조항은 BC 점검에서만 푼다).
  - ⑴ «리팩토링 모드의 BC 점검과 그 슬라이스 0 은 표준을 대상 BC 의 기존 코드 전체에 적용한다. 규범의 신규·touched·이번 작업 적용 한정과 기존 코드·레거시 형태·확립 표면·기존 배치의 보존·면제·존중 조항은 기능 요청의 범위 규범이라 이 점검과 그 슬라이스 0 에는 적용하지 않는다.»
  - ⑵ «리뷰어의 diff·touched 한정 관찰, 구현 코드 열람 금지, Phase 2 한정 체크리스트, ⓓ 신규분 동봉 조항은 BC 점검(점검과 잔존 확인)과 그 판정에서만 적용하지 않는다. 슬라이스 0 의 리뷰와 감사는 이 조항을 그대로 따른다.»
  - 끝에 적용 한정 어구 닫힌 목록 «…».
- **대상 목록**(`djr:overrides`)
  - 정본은 `scope-limit-norms.md` 표 1(T·T*)의 전수 목록이다. 기준은 셋이다.
    - 적용 조건이 신규·touched·손대는·이번 diff/작업·untouched·grandfather·레거시·기존 형태·기존 배치·확립 표면 보존인 규범(종류 무관).
    - §3-4 리뷰어 행동 조항(⑵ 몫).

## 7. G2 «ⓐ 잔존» — 층 판정

- `M_c`: 현행(`registry_gate` legacy 잔존 ∩ `C<n>` ⓐ). M → C 병합 항목은 그 `C<n>` 을 따른다(§4-3 병합 제한 — 리뷰어 «`C<n>` 과 같음» 표시 행만 — 이 전제).

  1. **결정적 바닥**: 항목의 `파일:행` 파일이 `build_anchor..작업 트리` 에서 하나도 바뀌지 않았으면 리뷰어 없이 **잔존**. ⓓ 겹침 항목은 0C 대응표로 옮긴 경로에 같은 `[ⓓ#N]` 이 남아 있으면 잔존(fail-closed).
  2. **리뷰어 재확인**: 그 밖 항목만 원 렌즈별로 **렌즈마다 항목 묶음 1회**를 부른다(병합 항목이면 원 행의 렌즈 전부 · `BC_AUDIT` «잔존 확인» 입력 = 항목 행 + 0C 대응표 + 최종 코드). 결과는 `해소 | 잔존 | 판단 불가` 다. **해소에는 새 `파일:행` 근거가 필수**다(`residual` 이 실재 검사 · 근거 없는 해소 = 잔존).

- **출구**
  - M>0 이면 해당 항목만 그 항목의 원 창 종류(0T|0C)로 **새 창을 열어** coder 에 1회 반송 → close → 1·2 재실행.
