## 1. 입구와 모드 판별

### 1-1. 입구 (스파이크 실측으로 확정)

  - frontmatter: `description` · `argument-hint` · `disable-model-invocation: true`(사용자만 부른다) · **`allowed-tools: Skill(dddjango:dddjango)`**(없으면 기본 권한에서 프롬프트·거부 — 스파이크 run2/run3).
  - 본문(규범 없는 산문 3~5줄): «Skill 도구로 `dddjango:dddjango` 를 부르고 args 로 아래 줄을 한 글자도 바꾸지 말고 넘긴다. 다른 일은 하지 않는다» + `리팩토링 모드(입구 /dddjango:refactor) · 대상: $ARGUMENTS`.
  - 실측: Coordinator 본문 전문 적재(68,893자 · 절단 0) · `$ARGUMENTS`·`${CLAUDE_PLUGIN_ROOT}`(30곳) 치환 · Coordinator `allowed-tools` 적용.

### 1-2. 모드 판별 — 단조성 불변식

- 판별 입력은 둘뿐이다: ① 요청 첫머리의 **정확한 표지** `리팩토링 모드(입구 /dddjango:refactor) · 대상: …` ② 고른 폴더의 미종료 실행 줄 `· 모드 리팩토링`(재개 — §2-3).
- **단조성 불변식**(규범): «리팩토링 모드는 일반 모드의 G0 의무(27종 스캔 · ⓐ/ⓑ · 결정 출처 · 실행과 앵커)를 전부 수행하고 R2·R3 를 더한다. 표지는 위조될 수 있으나 위조돼도 줄어드는 G0 의무가 없다.» v1 의 «표지는 입구의 사실» 문장은 쓰지 않는다(거짓).
- 리팩토링 모드가 덜 하는 것(기능 슬라이스 · 배치 질문)은 **기능이 없을 때만** 성립한다. 기능 혼입 판정은 R0 에서 입구 인자로 한다 — 불편 서술이 새 동작·새 계약을 요구하면 입구 정지 + «기능은 `/dddjango` 로»(R1~R3 헛돌기 방지).
- **표지 fail-closed**: 요청 첫머리가 표지 접두 `리팩토링 모드(입구` 로 시작하나 정확한 표지가 아니면 일반 모드로 강등하지 않고 입구 정지(«표지 손상 — 입구를 다시 부른다»). 본문 어딘가에 입구 이름이 나오는 기능 발주는 해당 없음.
- **R2·R3 축소 금지**: 요청·발주·불편 서술·**게이트 피드백**이 렌즈 구성·조각 분할·앞 실행 audit 재사용·판정 생략·일괄 채택·결과 지정을 요구해도 따르지 않는다 — 렌즈와 조각은 §3 결정적 규칙이 정한다. 모드 판별 절의 «따르지 않는 지시» 목록에 R2·R3 와 게이트 피드백을 더한다.
- 요청문의 «리팩토링 모드로» 류 문구(표지 아님)는 판별 입력이 아니다(모드 판별 절 원칙 유지).

### 1-3. `/dddjango` 로 들어온 정리 요청 (결정 11 — 설계 (가))

- 표지 없는 `/dddjango` 요청이 «구조 정리만»(기능 없음)이면 **모드 판별 직후 · 27종 실행 전**에 `/dddjango:refactor <BC>` 를 안내하고 입구 정지(기록 없음 · 폴더를 만들지 않는다).
- 현행 «정리 요청»(검사기 빚만 정리하는 풀 파이프라인) 경로는 없어진다. 기능 요청의 G0 빚 처리(검사기 빚 ⓐ/ⓑ)는 그대로다.
- 기능 요청 G0 의 ⓐ′(`:80` «BC별 정리 요청을 먼저 따로 진행»)는 안내 대상이 `/dddjango:refactor <BC>`(BC별 실행)로 바뀐다 — 그 실행은 의미 점검까지 하므로 ⓐ′ 대가 줄에 «BC별 리팩토링 실행(의미 점검 포함)»을 적는다.
- 재개(`/dddjango 이전 작업 이어서`)는 정리 요청이 아니다 — 모드는 실행 기록이 정한다(§2-3).

### 2-2. 모드 기록

- 실행 줄: `실행 · G0 승인 <값> · 모드 리팩토링`(기계 기록 · 경계 절의 «사후 개정» 아님).
- 어느 입구로 재개하든 그 실행은 리팩토링 모드다 — G2 는 §7 산식을 쓴다(`/dddjango 이전 작업 이어서` 재개에서 M_m 이 0 으로 빠지는 세탁을 막는다).

### 2-3. 실행 선택과 재개

- **잇기**: 미종료 실행이 `모드 리팩토링` 일 때만 리팩토링 모드에서 고를 수 있다. R2·R3 를 다시 돌리지 않고 그 실행의 `verdict.md` 가 그대로다(M 목록 동결) · 새 빚은 현행대로 R1 검사기분만 묻는다.
- 미종료 실행이 기능 모드면 리팩토링 모드에서는 잇기가 없다 — «승인됨 / 폐기»만(기능 실행을 표지로 잇지 않는다). 반대로 `/dddjango`(표지 없음)로 리팩토링 실행을 잇는 것은 허용된다(모드는 기록이 정한다).
- **`/dddjango` 재개의 전환 지점** = 실행 선택에서 `모드 리팩토링` 실행을 잇기로 고른 순간. 그때 일반 모드 Phase 0 산출(lens 제안·배치 질문)은 버리고 리팩토링 흐름의 다음 단계로 잇는다. 요청에 기능이 섞였으면 G0 정지 + `/dddjango` 안내(기능은 별도 실행).
- **새 실행**: R2·R3 를 새로 돌린다(`audit/<새 R2 시각>/` — 앞 실행 audit 재사용 없음).
- **G0 정지 재개**: 리팩토링 실행의 `G0 정지` 절에 `모드 리팩토링 · audit <R2 시각>` 을 적는다. 같은 폴더에서 다시 시작하면(어느 입구든) 최신 기록이 이 정지면 **그 audit·verdict 를 재사용**하고 R1(검사기)만 다시 돈다 — 사용자 판단 답이 착지하고, 자율 레인의 같은 정지 반복이 끊긴다. 재사용 거부(«새로 점검»)는 사용자 본인 직접만.

## 3. 리뷰어 `BC_AUDIT` 모드 (ddd · api · db · discipline)

### 3-1. 결정적 도구 `dddjango/scripts/refactor_audit.py` (신설 · Codex byte 미러)

| 하위 명령 | 입력 → 출력 | 쓰는 곳 |
|---|---|---|
| `plan <BC>` | BC 파일 목록 → 렌즈 구성(ddd·discipline 항상 · api = HTTP 어댑터 파일 있음 · db = Django 모델 있음) + 조각(표준 트리 #81 층 순서 `driving_layer → application_layer → domain_layer → driven_layer → composition_root → published_event → test` · 트리 밖 파일은 «트리 밖» 조각 · 5,000행 문턱 · 문턱 초과 단일 파일 단독) | R2 파견 계획 · Phase 2 조각 감사 |
| `outline <BC>` | 파일별 최상위 정의·클래스·메서드와 행 번호(AST) · 호출당 상한(약 8k 토큰)을 넘으면 최상위 정의만 | 모든 조각 호출에 동봉 — 교차 파일 발견 보조 |
| `check <audit 폴더>` | 행마다 ① 인용 ⊂ 그 문서 §절 본문(정규화: 강조 `**`·`*` · 백틱 · 인용 줄머리 `> ` · 줄바꿈·연속 공백 제거 · 절 경계 = 그 제목부터 같은 수준 이상의 다음 제목 전까지(하위 절 포함)) ② `파일:행` 이 **작업 트리**에 실재하고 BC 안 → 통과 행에 **블록 결속**(아래)의 R-ID·`norm_kind` 를 붙인다 · 실패 행 = 인용 불일치(사유) | R2′ |
| `sections <audit 폴더>` | 인용된 절 + 반대 방향 규칙 절의 **절 전체 원문**(블록별 R-ID·종류 주석) | R3 architect 입력 |
| `check-verdict <audit 폴더>` | 모든 통과 행에 판정 1개 · `M<n>` 유일 · 네 출구 검사(§4-3) · 병합 대상 검사 · 앞 판정 대비 대리 출처 축소 검사(§5) | R3 종료 조건(exit 0) |
| `fit <audit 폴더>` | 채택 항목의 정의 모양 변화(함수 → 메서드 · 시그니처 · 여러 정의 병합 · **메서드 개명**) × 테스트 참조(AST · import·patch 문자열)를 결정적으로 판정 → 장치 부적합 후보 목록 | R3 architect 입력(§4-6) |
| `residual <폴더>` | M 항목별 결정적 바닥(§7) + 리뷰어 재확인 입력 묶음(0C 대응표 포함) · 재확인 결과의 «해소» 근거 실재 검사 | G2 |

- **블록 결속**: rulepack 에 블록별 정규화 해시를 투영한다(`blocks: {<block id>: {"h": <sha256[:16]>, "works": [R-ID…]}}`). 해시 원천은 렌더러가 md 에 쓰는 그 블록 본문을 정규화한 것이다 — 블록 원문은 싣지 않는다(q4 «`djr:text` 금지»·동결 개정 8 무접촉 · 해시는 `ontology_rulepack.py` 가 렌더 함수를 빌려 계산). `refactor_audit.py` 는 md 절을 렌더 블록 경계(문단·목록 항목·표 행)로 나눠 같은 정규화 → 해시로 블록을 찾는다. 인용 ⊂ 그 블록 본문이어야 결속이 선다. 한 블록이 여러 규범을 진술하면(예: ninja `s010-2.3/b1` = R-0696·0697·0698·0699·3403) 결속은 «블록의 규범 집합»까지이고, 종류가 섞이면 행에 `혼합 블록` 표시 → G0 에서 사람이 본다.
- rulepack 투영 필드: works 에 `norm_kind`(Obligation·Prohibition·Permission·Exception·Override — 기존 어휘 `djr:kind`(블록 종별)와 겹치지 않는 이름) · `overrides`(대상 R-ID 목록 · `djr:overrides` 는 vocab `djr.ttl:165` 에 있고 지금 사용 0) · `blocks`. `overrides` 에 SHACL property shape 추가. 연쇄: q4 질의 · `ontology_rulepack.py` · `rulepack_smoke` · query-golden · `make rulepack`.
- **플랫폼 경로 사상표**: Claude `dddjango/skills/<x>/…` ↔ Codex `codex-dddjango/skills/<y>/…` · 에이전트 md ↔ 역할 SKILL. 인용은 그 플랫폼 설치본 파일에서 찾는다. 블록 결속은 byte 미러 문서(`references/final.md`)에서만 양 플랫폼 공통이다 — 의미 미러(에이전트 md ↔ 역할 SKILL · 스킬 SKILL.md)는 Codex 에서 **절 단위 결속**으로 떨어진다. 그래서 **제외·오탐 근거는 byte 미러 문서 인용 또는 리뷰어 «반대 방향 규칙»으로 한정**한다(빼는 근거만 강하게 · 위반 인용은 절 단위 허용).
- 리뷰어·architect 에게는 Bash 가 없다 — 이 도구는 **Coordinator 만** 돌린다.

### 3-2. 입력

- 대상 조각 파일 목록 · `outline` · 렌즈 · **렌즈별 점검 절 목록**(리뷰어 문면의 BC_AUDIT 절에 `문서 §절` 목록으로 고정 · 5B 코드 대상 분류에서 뽑는다 · `refactor_audit.py` 자가 시험이 목록의 절 실재를 대조) · 검사기 빚 `C<n>` 목록(중복 표시용) · 불편 서술 항목(있으면).

### 3-3. 산출 표

`행# | 규칙 = <문서> §<절> «원문 인용 20~60자» | 반대 방향 규칙(있으면 같은 형식) | 파일:행 | 위반 요지 | 동작 불변 정리 가능(예 / 아니오 — 사유: 계약·마이그레이션·타 BC)`

- R-ID 는 요구하지 않는다(배포 md 에 R-ID 가 없다). R-ID 는 `check` 가 블록 결속으로 붙인다.
- 규칙 문구를 댈 수 없는 항목은 내지 않는다. **불편 서술 항목**은 예외 — 규칙에 이으면 일반 행, 잇지 못하면 `규칙 = 근거 없음(불편 #k)` 행으로 내고 G0 에 «규칙 근거 없음 — 이 커맨드 밖»으로 표시된다.
- 검사기 빚과 같은 항목은 «`C<n>` 과 같음»으로 표시만.
- **표만 낸다**(산문 없음). Coordinator 는 받은 표를 그대로 `Write` 하고 대화에 다시 출력하지 않는다(«경로 + 3~5줄 요지» 원칙의 적용).

### 3-4. 분담·적용 범위·한정 조항

- 분담(5B): ddd = 도메인 모델·판정 소유·BC 경계 · api = HTTP 계약·컨트롤러 · db = 모델·인덱스·트랜잭션 · discipline = 클린코드·파일트리·타입·테스트 코드의 구조(배치·이름·픽스처 형태).
- **기술 규칙 분담(결정 12 (가))**: api 에 ninja 약 80 · db 에 Django ORM·보안 약 117 · discipline 에 python 약 73 — 점검 절 목록에 해당 스킬 절을 더하고 **플러그인 루트 경로로 읽는다**(frontmatter 스킬 목록은 모드별로 바꿀 수 없다 · Codex 는 역할 SKILL 에 같은 경로 열람 문면). web 102 는 dddjango-web 몫. DR 경계 규범 R-1137·R-1140(«기술 구현 정확성은 보지 않는다»)에 «BC_AUDIT 은 예외» 문면을 더한다.
- **적용 범위(결정 18 (가))**: BC_AUDIT 은 표준을 대상 BC 기존 코드 전체에 적용한다 — 규범 문면의 «신규·손대는 표면» 적용 한정과 레거시 보존 허용·의무는 이 점검에 적용하지 않는다(§4-4).
- **테스트 충분성은 점검 항목이 아니다**(원칙): 단언 강도·보호 범위·커버리지 부족은 내지 않는다. 테스트 코드의 구조 위반(배치·이름 등)은 항목이다(0T 창에서 정리 — 로드맵 4).
- 이 모드에서만 푸는 조항: «구현 코드 열람 금지»(R-3368 · R-3323 · R-2614) · 규율 리뷰어 diff 한정(R-1058 · R-0982 · R-1059 · R-3420) · 발견 채널 «빚 보고» → «점검 항목». 구현 체크리스트의 «Phase 2 implementation 에서만»(DR `:72`)은 BC_AUDIT 에 적용할 항목(입장 표·diff 전제 항목 제외)을 문면으로 정한다.
- ddd·db 리뷰어에는 «실행 모드» 절이 없다 → 모드 절 신설(기본 모드 = 지금의 Phase 1 리뷰 · 명시 입력이 있을 때만 BC_AUDIT).
- 리뷰어는 코드를 고치지 않는다. 오탐(5B 약 30% — 진단자 흉내값)은 §4 판정이 거른다.

## 4. design-architect «의미 항목 판정» 모드

### 4-1. 입력

### 4-2. 판정 범주와 ID

`M<n> | 원 행(렌즈-조각#행) | 판정 | 근거 | 파일:행 목록`

### 4-3. 빠지는 출구 네 가지와 검사 (증명 책임은 빼는 쪽)

| 출구 | 필수 근거 | `check-verdict` 가 보는 것 |
|---|---|---|
| **제외** | `R-ID «인용»` | 결속(§3-1) · 종류 ∈ {Permission, Exception} **또는** 리뷰어가 «반대 방향 규칙» 열에 적은 규칙(종류 무관 — 5B 표본 R-1395 Prohibition 형) **또는** Override 이면서 `overrides` 가 위반 R-ID 를 가리킴 · **그 R-ID 가 어떤 Override 의 `overrides` 대상이 아님**(§4-4). 의무를 되살리는 Override(R-1411·R-1489 형)는 제외 근거가 아니다 |
| **오탐**(요건 불충족 포함) | **위반으로 인용된 바로 그 블록의 요건 문구 인용** | 인용 ⊂ 위반 행의 결속 블록(같은 절의 다른 문장은 불가) · 그 블록의 `works` 에 `overrides` 대상이 있으면 G0 오탐 목록에 `범위 규범 블록` 표시(§4-4 — 사람이 본다) |

### 4-4. 적용 범위 규범 (결정 18 (가))

- Coordinator «리팩토링 모드» 절에 규범 1개(새 R-ID · `norm_kind = Override`): «리팩토링 모드의 BC 점검과 그 슬라이스 0 은 표준을 대상 BC 의 기존 코드 전체에 적용한다. 규범의 «신규·손대는 표면» 적용 한정과 레거시 보존 허용·의무는 기능 요청의 범위 규범이라 이 점검과 그 슬라이스 0 에는 적용하지 않는다.»
  - `djr:overrides` → R-0674(기존 함수형 Router 확립 표면 보존 · Permission) · R-0697(함수형 operation 레거시 취급·형태 보존 · Obligation) · R-0696(신규 표면 = 클래스 컨트롤러)·R-0698(touched 표면 클래스화)의 적용 한정 · R-3226(«리팩터링 대상을 따로 정의하지 않는다»). 전수 목록은 계획에서 «신규·touched·레거시 보존» 문면 grep 으로 확정한다.
  - 효과: 이 R-ID 들은 제외 근거가 될 수 없다(§4-3 검사 red). 기존 함수형 Router 는 R-0696 위반으로 채택될 수 있다(사용자 예시 2).
- 곁 문면: 해당 규범 블록(ninja R-0696~0698 블록 · houserules R-3226 블록)에 «리팩토링 모드 제외 — Coordinator 리팩토링 모드 절» 1구. coder·DR 이 슬라이스 0 에서 함수형 → 클래스 이관을 R-0697 위반으로 보지 않게 한다(파견 입력에 `모드 리팩토링` 이 실린다 — §6).
- «리팩터링 대상 = 백스톱 위반» 정의의 **사본 셋**(Coordinator `:79` · houserules final `:282` · ninja final `:858`)은 «기능 요청의 리팩터링 대상»으로 한정하는 문면으로 고친다(리팩토링 모드는 BC 점검 항목도 대상 — 결정 1).

### 4-5. 별도 요청 — 실물 근거 필수

- 근거 형식(하나 이상): 마이그레이션이 필요한 모델 필드 `파일:행` · 바뀌는 응답·예외 경로 `파일:행` · 편집해야 할 타 BC 파일 경로 · **장치 부적합**(§4-6)의 테스트 참조 `파일:행`.
- G0 에서 별도 요청은 **질문이 아니라 표시**다(슬라이스 0 에 넣을 수 없는 항목이라 고를 것이 없다). 자율 실행의 대리가 항목을 빼는 통로가 없어진다.

### 4-6. 장치 적합성 사전 판정

- 채택 후보가 **정의 모양을 바꾸는** 정리이고 테스트가 그 이름을 import·patch 문자열로 참조하면 0C 에서 red 다(결정 9 의 이름 치환은 «정의 본문이 이름 말고 같을 때»만 · `behavior_guard` `_match_defs` 는 최상위만 짝짓는다 → 메서드 개명도 red).
- 그런 항목은 **별도 요청(근거 = `fit` 이 낸 테스트 참조 `파일:행`)** 이다. 최상위 정의의 이동·개명·분할은 대응표 치환으로 통과하므로 해당 없음.
- 이 판정은 테스트를 고치지 않기 위한 분류다 — 테스트를 바꿔야 정리되는 항목은 슬라이스 0 에 넣지 않는다(원칙). 최종 관문은 여전히 0C 창의 장치 판정이다(예측이 틀리면 `ⓐ 재상정`).

### 4-7. 경계 예외

- `design-architect.md:32` «다른 산출물은 만들지 않는다» · `:112` «스킬 경계를 넘지 마라» → «리팩토링 모드 판정(`verdict.md`)은 예외 — 판정 근거는 `sections`·`fit` 이 공급한 것뿐»(자기 스킬 밖 규범을 스스로 찾아 읽지 않는다).
- architect 는 코드를 고치지 않는다 · 판정은 G0 전이다.

## 5. G0

- 배너 1행: `검사기 빚 N_c건(미룰 수 없음 k) · 의미 채택 N_m건 · 사용자 판단 u건 · 별도 요청 j건 · 제외 x건 · 오탐 d건 · 인용 불일치 q건 · 규칙 근거 없는 불편 f건` + 슬라이스 0 규모 1행(ⓐ 대상 항목 수 · 파일 수) + api 채택 항목에 ninja Schema 개명·Router 모듈 이동·함수 → 클래스(operationId 변화)가 있으면 «문서 층 변경(OpenAPI 이름)» 1행(차단 아님 — 결정 2 Q2 취지).
- 질문 순서: (폴더·실행 선택은 R0′ 에서 끝남) → **사용자 판단 항목**(항목마다 «위반으로 보고 정리 / 허용으로 보고 뺌») → 빚 질문(`C<n>`·`M<n>` 에 ⓐ/ⓑ · 결정 출처 규칙 그대로) → 스코프 승인.
- **사용자 판단은 STOP 이 아니라 G0 질문**이다(동작 불변이라 밖 결과는 같다). 다만 밖에서 보이는 결과가 갈리는 물음이라 **대리 답을 받지 않는다** — 경계 절 위임 불가 목록(`:218`)과 사전 위임 제외 목록(`:58`)에 «사용자 판단 항목»을 더한다. 결정 줄 정형(`:82`): `M<n> · 사용자 판단 = 위반|허용 · 출처 = …`.
- «미룰 수 없음»은 `C<n>` 에만 쓴다 — `M<n>` 은 «해당 없음»(리팩토링 실행에는 «이번 산출물»이 없어 해로움 정의가 서지 않는다).
- 제외·오탐·별도 요청·인용 불일치·규칙 근거 없는 불편은 **목록 파일 경로와 건수로 표시**한다(되돌리기·처분 질문 없음) · `혼합 블록`·`범위 규범 블록` 표시 행은 목록 안에서 구분한다.
- 후보가 도구 옵션 한도를 넘으면 전체 번호 목록을 배너에 먼저 출력한다(`:58` 규칙을 빚 질문에도 적용).
- **수정 요청(게이트 피드백)**: R3 를 다시 돌릴 때 받는 피드백은 «판정 근거 오류 지적»뿐이다. 결과 지정(채택 → 제외·오탐)은 사용자 판단 범주로만(본인 직접·사용자 원문 출처 · 대리 불가). 대리 출처 피드백의 R3 재실행은 채택 수를 줄일 수 없다(`check-verdict` 가 앞 판정 대비 채택 → 비채택 전환을 대리 출처에서 red). 사용자가 판정에 끝내 동의하지 않으면 끝 선택지 «판정대로 진행 / 작업 중단 / 플러그인 결함 보고».

## 7. G2 «ⓐ 잔존» — 층 판정

- `M_c`: 현행(`registry_gate` legacy 잔존 ∩ `C<n>` ⓐ).
- `M_m`: `refactor_audit.py residual` 이 층으로 가른다.
  1. **결정적 바닥**: 항목의 `파일:행` 파일이 `build_anchor..작업 트리` 에서 하나도 바뀌지 않았으면 리뷰어 없이 **잔존**. ⓓ 겹침 항목은 0C 대응표로 옮긴 경로에 같은 `[ⓓ#N]` 이 남아 있으면 잔존(fail-closed).
  2. **리뷰어 재확인**: 그 밖 항목만 원 렌즈 전부(병합 항목이면 원 행의 렌즈 전부)를 `BC_AUDIT` «잔존 확인» 입력(항목 행 + 0C 대응표 + 최종 코드)으로 1회씩 부른다 → `해소 | 잔존 | 판단 불가`. **해소에는 새 `파일:행` 근거가 필수**(`residual` 이 실재 검사 · 근거 없는 해소 = 잔존).
  3. `M_m` = 잔존 + 판단 불가.
- **출구**: M>0 이면 해당 항목만 그 항목의 원 창 종류(0T|0C)로 **새 창을 열어** coder 에 1회 반송 → close → 1·2 재실행 → 여전히 M>0 이면 `ⓐ 재상정` STOP(처분 «별도 요청 | 출처 있는 ⓑ | 플러그인 결함 | 작업 중단» — `:106` 처분 목록 그대로). `ⓐ 재상정`으로 뺀 항목은 `:114` 와 같이 그 항목의 변경을 **철회**하고 close 한 뒤 G2 로 간다. G2 영구 차단을 만들지 않는다.
- G2 배너: `G0 ⓐ N건 중 잔존 M(M_c · M_m)` · `재상정 제외 K건` · **제외 · 오탐 · 별도 요청 · 인용 불일치 네 목록을 다시 표시**(자율 실행에서 G0 승인이 위임됐어도 사용자가 G2 에서 본다).
