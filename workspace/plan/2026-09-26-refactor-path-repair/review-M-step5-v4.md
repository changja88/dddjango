### M-M1 별도 요청 출구의 구조 검사는 이름 문자열 일치라 공허하다 · `fit` 은 입력이 없어 결정적으로 설 수 없다

- **위치**: D4:85(`fit`) · D4:137(별도 요청 검사) · D4:153~160(§4-5·4-6) · D4:255(R-T13)
- **근거**
  1. **검사가 «그 행·그 파일에 항목 정의 이름»이 있는지만 본다** [실측 문면]. D4:137: «응답·예외 경로 = HTTP 어댑터 층 파일 ∧ 그 행에 항목 정의 이름 · 타 BC = BC 밖 경로 ∧ 그 파일에 항목 정의 이름 · 모델 필드 = … 또는 그 모델을 참조».
     - 컨트롤러는 유스케이스를 `use_case.execute(command)` 로 부르고, 도메인 예외를 `except InsufficientStock:` 로 잡는다(ninja final 표준 예시 · ttl `:2628`).
     - 그래서 `execute` 안의 항목이나 도메인 예외 파일의 항목은 «응답·예외 경로» 근거가 선다.
     - 저장소 어댑터는 모델을 참조하므로 «그 모델을 참조»도 선다. 흔한 이름이면 «타 BC 파일에 정의 이름»도 선다.
  2. **«BC 밖 경로»에 프로젝트 합성 파일이 섞인다** [실측 현장].
     - 선례 `839af8a0a`(함수 → `@api_controller` 이관)는 `spring_dream_server/urls.py` 를 고쳤다(`git show --stat`).
     - D4:137 로는 예시 2 형 항목이 «타 BC» 별도 요청으로 빠진다. R-T13 의 기대 «예시 2 채택»(D4:255)과 충돌한다.
  3. **`fit` 은 무엇을 판정할지 모른다** [실측 문면].
     - `fit` 의 입력은 audit 폴더다. 행 형식은 `규칙 | 반대 방향 | 파일:행 | 위반 요지 | 동작 불변 가능`(D4:100)뿐이다.
     - «정의 모양 변화(함수 → 메서드 · 병합 · 개명)»는 **정리 방식**이다. 그것은 Phase 1 설계에서 정해지며 R3 시점 입력에 없다.
     - architect 의 선언을 받으면 그 선언이 곧 출구 근거가 된다(자기 증명). 받지 않으면 추측이다. 테스트는 대개 코드를 import 하므로, «테스트 참조 있음»만으로 서는 목록은 거의 전부가 된다.
  4. **별도 요청은 질문 없이 표시만 된다**(D4:154).
- **영향**: 5B 표본 채택분의 주류인 예시 3 항목이 «응답·예외 경로» 또는 «장치 부적합»으로 별도 요청이 된다. 자율 실행에서 슬라이스 0 이 비고, G0·G2 목록에 줄만 남는다.
- **고칠 것(최소)**
  1. 별도 요청은 리뷰어가 그 행의 «동작 불변 정리 가능» 열(D4:100)에 **«아니오 — 사유»를 적은 행에만** 허용한다. architect 단독 별도 요청은 채택으로 재분류한다. 이미 있는 독립 입력을 교차 확인하는 것이다.
  2. 근거 유형을 좁힌다. 모델 필드 = 항목 **자기** `파일:행`이 모델 파일. 타 BC = `application/<다른 bc>/` 경로만. 프로젝트 합성 파일(`urls.py`·api 등록)은 BC 범위로 본다(기능 요청과 같다 · 표준 #437·#440·#441).
  3. **`fit` 을 걷는다.** 0C close red → 철회 → `ⓐ 재상정`(Coordinator `:114`·`:106` — 로드맵 4)이 이미 최종 관문이다(D4:160 도 그렇게 적는다). 남기려면 architect 참고 입력으로만 두고 출구 권한은 없앤다. R-T13 의 «사전 판정 예측 일치» 조건도 함께 걷는다.
- **원칙 필터**: 장치를 걷는 권고다(원칙 2). 기존 리뷰어 열과 기존 STOP 을 재사용한다. 테스트 보강이 아니다.
