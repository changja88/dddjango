## 1. 입구와 모드 판별

### 1-1. 입구 (스파이크 실측으로 확정)

- `dddjango/commands/refactor.md` → `/dddjango:refactor <대상 BC> [불편 서술]` [결정 13: 이름].
  - frontmatter: `description` · `argument-hint` · `disable-model-invocation: true`(사용자만 부른다) · **`allowed-tools: Skill(dddjango:dddjango)`**(없으면 기본 권한에서 프롬프트 — 스파이크 run2/run3).
  - 본문(규범 없는 산문 3~5줄): «Skill 도구로 `dddjango:dddjango` 를 부르고 args 로 아래 줄을 한 글자도 바꾸지 말고 넘긴다. 다른 일은 하지 않는다» + `리팩토링 모드(입구 /dddjango:refactor) · 대상: $ARGUMENTS`.
  - 실측: Coordinator 본문 전문 적재(68,893자 · 절단 0) · `$ARGUMENTS`·`${CLAUDE_PLUGIN_ROOT}`(30곳) 치환 · Coordinator `allowed-tools` 적용.
  - 보호: corpus-manifest 1행 + LEDGER prose 행 + **`manifest_seal.py` pipeline 글롭에 `commands/*.md`**(K-m1 — 지금은 `dddjango.md` 한 파일 고정이라 입구가 봉인 밖).
- **Codex** `codex-dddjango/skills/dddjango-refactor/SKILL.md`(얇은 스킬): «형제 `dddjango/SKILL.md` 를 `wc -l` 뒤 구간으로 나눠 끝까지 읽고 그 Coordinator 로 작동 · 요청 첫 줄 = 표지 + 인자».
  - `agents/openai.yaml` 에 암묵 호출 차단 정책(`allow_implicit_invocation: false` — 바이너리 문자열 확인 · 구현 때 실측 확정).
  - 스파이크: `cat` 출력이 모델 쪽에서 중간 절단 → 모델이 74~125행을 재독해 복구(1회). 구간 읽기를 문면에 명시해 모델 재량에 맡기지 않는다.

### 1-2. 모드 판별 — 단조성 불변식 (K-M2)

- 판별 입력은 둘뿐이다: ① 요청 첫머리의 **정확한 표지** `리팩토링 모드(입구 /dddjango:refactor) · 대상: …` ② 고른 폴더의 미종료 실행 줄 `· 모드 리팩토링`(재개 — §2-3).
- v1 의 «입구 표지는 모드 지정이 아니라 입구의 사실이다» 문장은 **지운다**(거짓 — 표지는 누구나 칠 수 있는 요청 문자열이다).
- 대신 **단조성 불변식**을 규범으로 둔다: «리팩토링 모드는 일반 모드의 G0 의무(27종 스캔 · ⓐ/ⓑ · 결정 출처 · 실행과 앵커)를 전부 수행하고 R2·R3 를 더한다. 표지는 위조될 수 있으나 위조돼도 줄어드는 G0 의무가 없다.»
- 리팩토링 모드가 덜 하는 것(기능 슬라이스 · 배치 질문)은 **기능이 없을 때만** 성립한다 → 표지와 새 계약(기능)이 함께 오면 G0 에서 «기능은 `/dddjango` 로 · 정리는 이 입구로» 안내하고 `G0 정지`(모드 판별 절 «기능과 정리가 섞인 요청은 정리 요청이 아니다»와 같은 취지).
- **표지 fail-closed**(K-M1): 요청에 입구 이름(`/dddjango:refactor`)이 있는데 정확한 표지가 없으면 일반 모드로 강등하지 않고 멈춘다(«표지 손상 — 입구를 다시 부른다» · 기록 없는 입구 정지 §2-1).
- **R2·R3 축소 금지**: 요청·발주·불편 서술이 렌즈 구성·조각 분할·앞 실행 audit 재사용·판정 생략·일괄 채택을 지정해도 따르지 않는다 — 렌즈와 조각은 §3 결정적 규칙이 정한다. 모드 판별 절의 «따르지 않는 지시» 목록에 R2·R3 를 더한다.
- 요청문의 «리팩토링 모드로» 류 문구(표지 아님)는 여전히 판별 입력이 아니다(모드 판별 절 원칙 유지).

### 2-2. 모드 기록

- 실행 줄: `실행 · G0 승인 <값> · 모드 리팩토링`(기계 기록 · 경계 절의 «사후 개정» 아님).

### 2-3. 실행 선택 (K-M3 (3))

- **잇기**: 미종료 실행이 `모드 리팩토링` 일 때만 리팩토링 모드에서 고를 수 있다. R2·R3 를 다시 돌리지 않고 그 실행의 `verdict.md` 가 그대로다(M 목록 동결) · 새 빚은 현행대로 R1 검사기분만 묻는다.
- 미종료 실행이 기능 모드면 리팩토링 모드에서는 잇기가 없다 — «승인됨 / 폐기»만(단조성: 기능 실행을 표지로 잇지 않는다). 반대로 `/dddjango`(표지 없음)로 리팩토링 실행을 잇는 것은 허용된다(모드는 기록이 정한다).
- **새 실행**: R2·R3 를 새로 돌린다(`audit/<새 R2 시각>/` — 앞 실행의 audit 는 재사용하지 않는다).

## 3. 리뷰어 `BC_AUDIT` 모드 (ddd · api · db · discipline)

### 3-1. 결정적 도구 `dddjango/scripts/refactor_audit.py` (신설 · Codex byte 미러 · K-M7 · K-B1 · K-B2)

| 하위 명령 | 입력 → 출력 | 쓰는 곳 |
|---|---|---|
| `plan <BC>` | BC 파일 목록 → 렌즈 구성(ddd·discipline 항상 · api = HTTP 어댑터 파일 있음 · db = Django 모델 있음) + 조각(층 순서 domain → application → infrastructure → presentation → tests · 5,000행 문턱 · 문턱 초과 단일 파일 단독) | R2 파견 계획 |
| `outline <BC>` | 파일별 최상위 정의·클래스·메서드와 행 번호(AST) | 모든 조각 호출에 동봉 — 교차 파일 발견 보조(K-M7 [추정] 손실 완화) |
| `check <audit 폴더>` | 행마다 ① 인용 ⊂ 그 문서 §절 본문(공백 정규화) ② `파일:행` 이 HEAD 에 실재하고 BC 안 → 통과 행에 그 절의 R-ID·종류 목록을 붙인다 · 실패 행 = 탈락(사유) | R2′ |
| `sections <audit 폴더>` | 인용된 절 + 반대 방향 규칙 절의 **절 전체 원문**(R-ID·종류 주석) | R3 architect 입력(K-M8) |
| `check-verdict <audit 폴더>` | 모든 통과 행에 판정 1개 · `M<n>` 유일 · 제외 근거 검사(§4-3) · 별도 요청 실물 근거 실재(§4-4) · 병합 대상이 registry 위반 `C<n>` 뿐 | R3 종료 조건(exit 0) |
| `residual <폴더>` | M 항목별 결정적 바닥(§7) + 리뷰어 재확인 입력 묶음(0C 대응표 포함) · 재확인 결과의 «해소» 근거 실재 검사 | G2 |

- rulepack 투영 2필드 추가(K-B1 ⓑ 의 최소판): works 에 `kind`(Obligation·Prohibition·Permission·Exception·Override) · `overrides`(대상 R-ID 목록). 블록 원문은 싣지 않는다 — 인용은 md 절 본문으로 검사한다. 연쇄: q4 질의 · `ontology_rulepack.py` · `rulepack_smoke` · query-golden · `make rulepack`.
- 리뷰어·architect 에게는 Bash 가 없다 — 이 도구는 **Coordinator 만** 돌린다.

### 3-2. 입력

- 대상 조각 파일 목록 · `outline` · 렌즈 · **렌즈별 점검 절 목록**(자기 스킬 전체가 아니다 — 리뷰어 문면의 BC_AUDIT 절에 `문서 §절` 목록으로 고정 · 5B 코드 대상 분류에서 뽑는다 · `refactor_audit.py` 자가 시험이 목록의 절 실재를 대조) · 검사기 빚 `C<n>` 목록(중복 표시용) · 불편 서술 항목(있으면).

### 3-3. 산출 표 (K-B1 · K-M8)

`행# | 규칙 = <문서> §<절> «원문 인용 20~60자» | 반대 방향 규칙(있으면 같은 형식) | 파일:행 | 위반 요지 | 동작 불변 정리 가능(예 / 아니오 — 사유: 계약·마이그레이션·타 BC)`

- R-ID 는 요구하지 않는다(배포 md 에 R-ID 가 없다 — K-B1 실측). R-ID 는 `check` 가 절에서 붙인다.
- 규칙 문구를 댈 수 없는 항목은 내지 않는다. **불편 서술 항목**은 예외 — 규칙에 이으면 일반 행, 잇지 못하면 `규칙 = 근거 없음(불편 #k)` 행으로 내고 G0 에 «규칙 근거 없음 — 이 커맨드 밖»으로 표시된다(K-M4-5).
- 검사기 빚과 같은 항목은 «`C<n>` 과 같음»으로 표시만.
- **표만 낸다**(산문 없음). Coordinator 는 받은 표를 그대로 `Write` 하고 대화에 다시 출력하지 않는다(K-M7 (1) · «경로 + 3~5줄 요지» 원칙의 적용).

### 3-4. 분담·한정 조항

- 분담(5B): ddd = 도메인 모델·판정 소유·BC 경계 · api = HTTP 계약·컨트롤러 · db = 모델·인덱스·트랜잭션 · discipline = 클린코드·테스트·파일트리·타입.
- 이 모드에서만 푸는 조항: «구현 코드 열람 금지»(R-3368 · R-3323 · R-2614) · 규율 리뷰어 diff 한정(R-1058 · R-0982 · R-1059 · R-3420) · 발견 채널 «빚 보고» → «점검 항목». 구현 체크리스트의 «Phase 2 implementation 에서만»(DR `:72`)은 BC_AUDIT 에 적용할 항목(입장 표·diff 전제 항목 제외)을 문면으로 정한다.
- ddd·db 리뷰어에는 «실행 모드» 절이 없다 → 모드 절 신설(기본 모드 = 지금의 Phase 1 리뷰 · 명시 입력이 있을 때만 BC_AUDIT).
- **[결정 12]** (가) api 에 ninja 80 · db 에 ORM·보안 117 · 규율에 python 73 — 점검 절 목록에 해당 스킬 절을 더하고 플러그인 루트 경로로 읽는다(frontmatter 스킬 목록은 모드별로 바꿀 수 없다) · web 102 는 dddjango-web 몫 / (나) 각 리뷰어 BC_AUDIT 절에 «기술 구현 정확성 규범은 이 점검 범위 밖» 1행.
- 리뷰어는 코드를 고치지 않는다. 오탐(5B 약 30% — 진단자 흉내값이라 런타임 품질은 미지수 · K-M8)은 §4 판정이 거른다.

## 4. design-architect «의미 항목 판정» 모드 (K-M4 · K-M5 · K-M8 · K-M9)

### 4-1. 입력

- `check.md`(통과 행 + 탈락 목록) · `sections` 출력(인용 절과 반대 방향 절의 절 전체 — 같은 절의 허용·예외·우선이 함께 온다) · `outline` · `C<n>` 목록 · 테스트 참조 조사를 위한 Grep(자기 도구).

### 4-2. 판정 범주와 ID

`M<n> | 원 행(렌즈-조각#행) | 판정 | 근거 | 장치 적합성 | 파일:행 목록`

- 판정: **채택** · **병합 → M<k> 또는 C<n>** · **제외** · **탈락**(오탐 — 규칙 문면상 위반 아님을 그 규칙 문구로) · **사용자 판단**(규칙 충돌 — 두 규칙이 반대 방향이고 문면으로 가를 수 없음 · 5B 표본 5·7) · **별도 요청**.
- `M<n>` 은 architect 가 부여하고, 결정 줄·재상정·G2 는 이 키만 쓴다.
- 병합은 **registry 위반 `C<n>` 또는 다른 `M<k>`** 로만 한다. ⓓ 후보(registry #4·#11 채널)와 겹치면 의미 항목으로 남긴다 — ⓓ 는 빚이 아니라 G2 legacy 잔존에 나오지 않는다(K-M4-2).

### 4-3. 제외 근거 (K-B1 · K-M6 · K-M8)

- 형식: `R-ID «원문 인용»`(architect 는 `sections` 출력에서 R-ID 를 고른다).
- `check-verdict` 가 본다: R-ID 실재 · 인용 ⊂ 그 R-ID 절 본문 · `kind ∈ {Permission, Exception, Override}` 또는 위반 규범과 같은 R-ID 의 요건 불충족 인용(5B 표본 19번 형태) · **그 R-ID 가 어떤 Override 의 `overrides` 대상이 아님**.
- 레거시 보존 규범(R-0674 함수형 Router 보존 허용 · R-0697 레거시 취급·형태 보존 의무 · houserules final `:282` «리팩터링 대상을 따로 정의하지 않는다») 곁에 **리팩토링 모드 Override 규범**을 하나씩 둔다(한 주제 한 소유자 — 그 규범 곁 · `djr:overrides`). 문면: «리팩토링 모드 실행의 BC 점검과 그 슬라이스 0 이 정리하는 G0 ⓐ 의미 항목에는 이 보존 허용·의무를 적용하지 않는다». 그래서 이 규범들은 제외 근거가 될 수 없고(검사 red), coder·DR 이 슬라이스 0 의 함수형 → 클래스 이관을 R-0697 위반으로 보지 않는다. 사용자 예시 2 가 이 경로다.
- 비용·일정·규모는 제외 사유가 아니다(그것은 사용자의 ⓑ 다).
- **제외 되돌리기 선택지는 두지 않는다**(K-M4-6 — 결정 1-b 원문은 «뺀 항목은 G0 에 사유와 함께 표시»까지다 · 되돌린 항목은 비위반 이동이라 `:106` STOP 에 걸린다). 사용자가 판정에 동의하지 않으면 G0 «수정 요청»으로 R3 를 그 피드백과 함께 다시 돌린다(게이트 공통 채널).

### 4-4. 별도 요청 — 실물 근거 필수 (K-M5)

- 근거 형식(하나 이상): 마이그레이션이 필요한 모델 필드 `파일:행` · 바뀌는 응답·예외 경로 `파일:행` · 편집해야 할 타 BC 파일 경로 · **장치 부적합**(§4-5)의 테스트 참조 `파일:행`.
- `check-verdict` 가 근거 실재를 본다. 근거 없는 별도 요청은 **채택으로 본다**(red 가 아니라 재분류 · check.md 에 기록).
- G0 에서 별도 요청은 **질문이 아니라 표시**다(슬라이스 0 에 넣을 수 없는 항목이라 고를 것이 없다 — v1 의 «기록 / 빼기» 질문을 지운다). 자율 실행의 대리가 항목을 빼는 통로가 없어진다.

### 4-5. 장치 적합성 사전 판정 (K-M9 (1))

- 채택 후보가 **정의 모양을 바꾸는** 정리(함수 → 메서드 · 시그니처 변경 · 여러 함수 → 한 메서드)이고 테스트가 그 이름을 import·patch 문자열로 참조하면(architect Grep) 0C 에서 red 다(대응표 치환 밖 — `behavior_guard` `_match_defs`).
- 그런 항목은 **별도 요청(근거 = 테스트 참조 `파일:행`)** 으로 분류한다. 이동·개명·분할은 대응표 치환으로 통과하므로 해당 없음.
- **[결정 14]** (가) «보호 추가» 창이 생기면: 보호가 모자란 채택 항목(예: 선례 `839af8a0a` 의 헤더 동작)은 architect 가 명세에 보호 추가 표로 올린다 / (나) 그런 항목도 별도 요청(«보호 테스트 먼저»)이다.

## 5. G0 (K-M4 · K-M5 · K-M8 · K-m10)

## 7. G2 «ⓐ 잔존» — 층 판정 (K-B2)

- `M_c`: 현행(`registry_gate` legacy 잔존 ∩ `C<n>` ⓐ).
- `M_m`: `refactor_audit.py residual` 이 층으로 가른다.
  1. **결정적 바닥**: 항목의 `파일:행` 파일이 `build_anchor..작업 트리` 에서 하나도 바뀌지 않았으면 리뷰어 없이 **잔존**. ⓓ 겹침 항목은 0C 대응표로 옮긴 경로에 같은 `[ⓓ#N]` 이 남아 있으면 잔존(5A fail-closed).
  2. **리뷰어 재확인**: 그 밖 항목만 원 렌즈 전부(병합 항목이면 원 행의 렌즈 전부)를 `BC_AUDIT` «잔존 확인» 입력(항목 행 + 0C 대응표 + 최종 코드)으로 1회씩 부른다 → `해소 | 잔존 | 판단 불가`. **해소에는 새 `파일:행` 근거가 필수**(`residual` 이 실재 검사 · 근거 없는 해소 = 잔존).
  3. `M_m` = 잔존 + 판단 불가.
- **출구**: M>0 이면 해당 항목만 coder 에 1회 반송 → 1·2 재실행 → 여전히 M>0 이면 `ⓐ 재상정` STOP(처분 «별도 요청 | 출처 있는 ⓑ | 플러그인 결함 | 작업 중단» — `:106` 처분 목록 그대로)로 올린다. G2 영구 차단을 만들지 않는다.
- G2 배너: `G0 ⓐ N건 중 잔존 M(M_c · M_m)` · `재상정 제외 K건` · **제외 x · 별도 요청 j 목록을 다시 표시**(자율 실행에서 G0 승인이 위임됐어도 사용자가 G2 에서 본다 · K-M8).
