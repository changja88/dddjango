## 5. 사용자 결정 기록

### 결정 1 — 검사기 밖 의미 위반의 기존 코드 정리 (2026-09-26 22시대 대화 · 22:33 기록)

§3-1 의 «비위반 기존 코드»는 잘못된 표현이었다(사용자 지적). 큰 파일 분할·함수형 API→클래스 컨트롤러·흩어진 업무 규칙은 모두 플러그인 규범이 금지하는 **의미 위반**이다. 검사기가 잡지 못하고, 기존 코드에서는 «빚 보고»만 된다.

사용자 원문(대화):
- «다가 맞을거 같아. 그런데 이건 신규 개발이 아니라 리팩토링 요청시에만 해야 하지 않을까? … 신규 기능을 만들때마다 … 점검을 하면 작업시간이 너무 오래 걸릴거 같은데?»
- «리팩토링 이라는 명시적인 커맨드를 만들어서 리팩토링 요청이 들어왔을때만 하는게 어때? … 사용자가 이부분도 정리해줘 라고 명시적으로 말할 필요가 있을까? 그냥 architector agent가 전체를 보는게 더 편하지 않아?»
- «그런데 최종 결정은 design-architect도 참여해야 하는거 아니야?»
- «dddjango-web도 당연히 만들어야지»
- «마자아 dddjango-web도 진행 방식은 dddjango와 동일하게 하자»

결정:
- **1-a**: 기존 코드의 의미 위반은 **전용 리팩토링 커맨드에서만** 찾고 정리한다. 기능 요청(`/dddjango` · `/dddjango-web`)에서는 의미 위반을 점검하지 않는다. 손대는 코드는 기존 diff 감사가 그대로 본다.
- **1-b**: 리팩토링 커맨드의 절차는 다음과 같다.
  - 기존 리뷰어 에이전트(discipline-reviewer · design-review-ddd 등)에 «BC 전체 점검 모드»를 더해, 이 리뷰어들이 찾는다. 항목마다 규칙 문구와 파일:행을 붙인다.
  - **design-architect 가 판정·중재**한다. 항목을 빼려면 규칙 문구를 근거로 대고, 뺀 항목은 G0 에 사유와 함께 표시한다.
  - 사용자가 G0 에서 승인한다.
  - 사용자가 항목을 열거하는 것은 필수가 아니고 선택이다.
- **1-c**: dddjango-web 에도 리팩토링 커맨드를 만든다.
- **1-d**: dddjango-web 기능 요청도 dddjango 와 같은 방식으로 한다. 검사기 빚은 항상 처리하고(B1·R1·R2 를 web 에 적용), 정리 요청은 리팩토링 커맨드로 안내한다. 현재 web 에는 G0 빚 조사 단계가 없다(커맨드에 «빚» 0회 · 백스톱은 touched 한정).
- 대체: R4 B1(b)(«열거 항목 → ⓐ») 틀과 캠페인 plan-v2 S8 의 B1(b) 항목은 이 결정으로 대체된다.
- **정정(09-27 · 적대 검토 L-M4)**: 위 «함수형 API→클래스 컨트롤러는 … 의미 위반이다»는 현행 문면으로는 틀렸다 — R-0696(신규 표면)·R-0698(손대는 표면)만 클래스 컨트롤러를 요구하고, R-0697·R-0674 는 기존 함수형을 레거시로 보존한다. 기존 코드에 적용할지는 **결정 18**(아침 브리프)로 사용자에게 묻는다. 큰 파일 분할·흩어진 업무 규칙의 규범 근거는 검토 L 이 반박하지 않았다(5B 표본 R-1513 계열).

진행 기본값(내 제안 · 사용자 이의 없음 · 결정으로 기록하지 않음): 새 커맨드·web 도입은 다음 수리로 분리해 캠페인 전에 끝낸다 · 이번 변경을 먼저 커밋한다 · dddjango 를 먼저, web 을 이어서 한다.
