**가르는 규칙(설계 처리 · 질문 생략)**
- 항목의 범주 = architect 반환 사유 가운데 **처방을 그대로 따를 때 막는 것 전부**(하나 이상). 동작을 지키려고 떠올린 우회(예: settings 를 바꿔 목적지를 맞춤)와 architect 의 재사용 선택은 범주가 아니다 — core §3 «architect 자신의 설계 선택은 범주가 아니다»와 같다.
- 전부 3 안이면 덮는다. 하나라도 밖이면 묻는다(core S14·S15 «혼합 → 묻는 항목»과 같은 규칙).
- 계속 묻는 것: «미룰 수 없음» 항목(사용자 결정 원문) · `C<n>`(core 와 같이 — «같은 한 줄»이 두 플러그인에서 같은 뜻) · 판단이 서지 않는 항목.
- 도구 확인(§4): 범주 낱말 ⊆ 3 · 막는 `파일:행` 1개 이상 실재. 범주 판단 자체는 도구가 대신하지 않는다 — core 도 판정 표 작성은 architect 몫이고 도구는 형식·실재만 본다.

**왜 Coordinator 가 가르나(architect 에 맡기지 않는 이유)** — architect 에 범주 반환을 시키려면 ⓐ 늘 시키면 파일 없는 흐름이 바뀌고 ⓑ 파일이 있을 때만 시키면 파견 입력이 파일 존재에 따라 달라진다(core R-3589 취지). 현행도 STOP 기록의 항목 줄은 Coordinator 가 쓴다(R8-WR «architect 판단 · Coordinator가 두 곳을 직접 확인»). 편향은 네 겹으로 줄인다: 막는 `파일:행` 실재(도구) · 혼합·불확실은 묻는다 · 리뷰어가 불가 주장을 본다(1-2 3행) · G1 배너에 항목별 범주가 보인다.
