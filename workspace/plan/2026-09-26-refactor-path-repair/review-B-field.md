# 적대 검토 B — 현장 재생 · 회귀 (design-v2 · 2026-09-26)

검토자 B(현장 재생). 읽기 전용이다. spring_dream_server 와 lane-8-B-5 워크트리는 읽기만 했고 검사기는 실행하지 않았다. Serena·Graphify 미사용.
표기는 diag-A 와 같다(SD · O/ · WT · RS · SC · C = `dddjango/commands/dddjango.md` · HR = houserules SKILL). 사용자 결정 B1·R1·R2 는 고정 전제로 두고, 설계가 그 결정을 충실히 이행하는지만 본다.

## 판정: 수정 후 승인

방향은 B1/R1/R2 와 맞다(C1 법리 통일 · C2 수정 모드 스캔 · C4 출처 · C5 실행 단위 앵커). 재생 11건 가운데 4건에서 현장의 법리 혼선과 낡은 앵커가 실제로 사라진다.
다만 blocker 2건이 남는다.
- **B1**: 위임 레인에서는 C4 출처 판별이 형식만 채우면 통과한다. ⓑ 51건 중 49건이 발주자 경로였으므로 R2 의 핵심이 현장에서 성립하지 않는다.
- **B2**: B1 ⓐ 가 «동작 불변으로는 못 고치는 빚»(#546 · #14)과 검사기 오탐(#195 · F4-20)을 슬라이스 0 에 밀어 넣는데, 그 항목들이 갈 경로가 없다. accounts 하드 빚 11건 중 4건이 여기 해당한다.

이 둘과 major 6건을 고치면 승인한다. 재설계는 필요 없다(모두 문면 추가 · 소형 검사).

## 2. 발견

### Blocker

**B1 — 위임 레인에서 C4 출처가 형식만 채워 통과한다(R2 불성립)**
- **현장**: 게이트 답은 발주자가 herdr 로 레인 대화에 입력한다. 예를 들어 WT 발주서 :16 은 GATE 파일 흐름을 정하고, GATE-fortune-teller-8b5-1.md:92 는 «> 발주자 답(…)»을 레인이 옮겨 적었다. ⓑ 51건 중 49건이 발주자 경로였다(diag-A:71-72).
- **구멍 ① — 사용자와 발주자를 구분하지 못한다.** C4 ① «이 실행에서 사용자가 직접 답함»을 코디네이터는 대화 입력으로만 판별한다. «대화형이면 사용자에게 직접 다시 묻는다»(design:42)의 재질문도 herdr 레인에서는 발주자에게 간다. 발주자가 답하면 코디는 그대로 «사용자 직접(<시각>)»으로 적는다. 발주자가 속일 필요조차 없다.
- **구멍 ② — 원문의 내용 요건이 없다.** ② «사용자 원문»은 원문·시각·출처만 갖추면 된다. 그런데 다음 발화들이 모두 그 형식을 갖춘다.
  - 발주 투입 발화: O/2026-09-18-fortune-house-b7-regeneration-removal.md:61 «오케이 그럼 이거 먼저 발주 넣자»
  - 캠페인 착수 발화: O/…accounts-4…:3
  - 순서 결정: plan-v2:97 «전부다 착륙하고 나면 리팩토링»

  마지막 발화는 «리팩터는 나중»으로 읽혀 모든 서비스 레인 ⓑ 의 근거로 인용될 수 있다. 같은 날 뒤에 나온 B1(plan-v2:101)과 충돌해도 코디는 그 사실을 알 수 없다.
- **구멍 ③ — 발주자 ⓐ 를 적을 칸이 없다.** 출처 칸(design:44)에 «발주자 답 ⓐ»가 없다. B1 이후 가장 흔한 경로는 발주자가 게이트에서 방침대로 ⓐ 로 답하는 것이다. 적을 곳이 없으니 «사용자 직접»이나 «발주 고정 ⓐ»로 잘못 적힌다. C4 가 막으려던 오표기(최소 8파일)가 다시 생긴다.
- **구멍 ④ — 재질문에 상한이 없다.** 발주자가 같은 ⓑ 를 되풀이하면 왕복이 끝없이 반복된다.
- **수리**:
  - (a) 발주가 게이트 답을 대리에게 위임한 실행(«게이트 답은 발주자» 류)이나 입력이 «발주자 답»으로 시작하는 실행에서는 출처 ① 을 쓸 수 없다. 이런 실행에서 ⓑ 는 ② 로만 받는다.
  - (b) ② 는 «이 실행(또는 이름을 든 BC·항목)의 기존 코드 정리를 미룬다»는 뜻을 담은 문장만 인정한다. 발주·투입 승인, 일정·순서 발화, 선례, 다른 레인의 처분은 출처가 아니다.
  - (c) 출처 칸에 `발주자 답 ⓐ(<GATE 파일:행> · <시각>)`을 추가한다(ⓐ 에만).
  - (d) 출처 없는 ⓑ 가 한 번 들어오면 재질문하지 않고 STOP 기록으로 넘어간다(대화형 실행도 같다).
  - (e) 가이드 §7 에 추가한다: «대신 답하는 쪽은 자기 답을 ‹발주자 답›으로 표시하고, 미룸 재질문에는 답하지 않고 사용자에게 올린다».

**B2 — B1 ⓐ 가 슬라이스 0 에 들어갈 수 없는 빚까지 밀어 넣는다**
- **동작이 바뀌는 빚**: #546(한 트랜잭션에서 쓰기 둘 이상)과 #14(UoW 안 크로스-BC 포트)는 고치면 실패 시 원자성이 바뀐다. 1538 RS:33 이 스스로 «쓰임새 트랜잭션(#546 · #14) 개조는 무변 범위를 건드린다»고 적었다.
  - 현장 분포: accounts 하드 11건 중 4건(RS:14 · :22-24) · chat_relay #546×2(0606 RS:35 · :55) · 0908-2137 «#546 두 건 = 승인된 이관 빚»(RS:107).
  - 캠페인도 이 부류를 K3(동작 변경)로 분류해 범위 밖에 두었다(plan-v2:21).
- **검사기 오탐**: fortune_library 의 #195 1건은 검사기 오탐이다(diag-B3-F4-20:4 · :78). 0502 가 ⓐ 로 가면 coder 가 오탐을 피하려고 멀쩡한 코드를 비튼다. 기존 발주 관행은 «우회 구현 금지 · STOP»이다(O/…accounts-4…:45).
- **왜 막히는가**: 옛 규칙에서는 발주자 ⓑ 가 이 두 부류의 조용한 출구였다. 새 규칙은 그 출구를 닫았지만 대체 경로를 주지 않는다. 결과는 셋 중 하나다: Phase 2 에서 coder 정지 · 설계 반송 · «동작 불변»이 아닌 슬라이스 0.
- **수리**:
  - G0 빚 표에 열 «동작 불변으로 정리 가능?»을 둔다. 판정은 규칙 부류 기준이다 — #546 · #14 · OHS 공개 예외 #456 등은 «아니오».
  - «아니오» 항목은 ⓐ(슬라이스 0) 대상에서 빼고 «동작 결정 STOP»으로 사용자에게 올린다. ⓑ 로 처리하지 않으므로 B1 과 충돌하지 않는다.
  - 검사기 결함이 의심되는 항목은 근거(재현 파일)와 함께 «플러그인 결함 STOP»으로 분리하고, 우회 구현은 금지한다.
  - 릴리즈 순서: F4-20 수리를 이 수리와 함께 또는 먼저 낸다.

### Major

**M1 — C1b 는 자리가 틀렸고, «줄 변경» 선택지는 불가능하거나 은밀한 이동이다**
- **자리 문제**: 이동이 필요한지는 설계(architect)가 판단한다. 그런데 C1b 는 G0(코디)에서 묻는다. 그러면 코디가 설계를 예단하게 되고(C:80 «설계 근거는 만들지 않는다» 위반), G1 에서 처음 드러나는 경우에는 규칙이 없다. 명세에 비위반 이동이 들어가면 discipline 반송 후 막힌다.
- **선택지 문제**: 분할(0606 ⓓ#644)과 이관(0207 · 0908-2137 plain→Ninja)은 옛 코드를 새 파일로 옮겨야 한다. «줄 변경으로 다룬다»를 고르면 «새 파일(스코프 산출물) + 옛 줄 삭제», 즉 이름만 바꾼 이동이 된다. HR:29 의 판정 물음이 스코프 메모에 적힌 산출물을 허용하기 때문이다. 결국 C1b 선택지 ①이 설계 §5 질문 4 가 걱정한 «몰래 만든 권한»이다.
- **수리**:
  - (a) «이동»을 정의한다: 기존 심볼이나 줄이 다른 경로에 다시 생기고(재작성 포함) 옛 자리에서 사라지는 변경 전부. 분할·개명·이관을 포함한다.
  - (b) C1b 선택지를 «범위에서 빼고 진행 / 요청 종료(규범 결정 R4 B1(b) 대기)»로 바꾼다.
  - (c) 같은 물음을 G1 에도 둔다. architect 가 비위반 이동이 필요하다고 보면 명세에 넣지 않고 G1 STOP 으로 올린다.
  - (d) 현장 영향을 명시한다: 비위반 분할과 프레임워크 이관 요청은 B1(b) 결정 전까지 수행할 수 없다. 이 비용을 저녁 결정 브리프에 적는다.

**M2 — C5 «마무리» 표식이 현장에서 남지 않는다 → 낡은 앵커 재발 + 사용자 대기**
- **현장**: 발주자는 레인의 끝 커밋 파일을 좁힌다. GATE-accounts-6-3-2-2.md:95 는 «두 파일만 커밋»으로 scope.md 를 제외했다.
- **결과**: 표식이 없으면 C5 는 «재개»로 판정해 옛 앵커를 유지한다(P5 그대로). 새 실행은 «사용자가 G0 에서 앞 실행을 버린다고 명시»할 때만 생긴다. 그래서 제품 결정이 없는 자율 레인이 사용자를 기다리게 된다.
- **수리**:
  - (a) 실행을 G2 승인을 기록할 때 닫는다(Phase 3 에 의존하지 않는다). 실행 줄 갱신은 build_anchor 처럼 코디 고유의 쓰기이며 발주의 커밋 제한 대상이 아니라고 명시한다.
  - (b) 표식이 없을 때는 결정적으로 판정한다. 옛 build_anchor..HEAD 의 레인 커밋이 전부 main(또는 approved-merges)에 있으면 끝난 실행이다 — 새 앵커가 숨길 것이 없다. 하나라도 main 밖에 있으면 재개다. 이렇게 하면 사용자 명시가 필요 없고, 앵커 세탁도 불가능하다.

**M3 — 교차 · 다 BC 수정에서 슬라이스 0 이 필요 이상 커진다**
- **정의 문제**: «이번 수정이 속한 BC»(design:30)는 다 BC 수정에서 모호하다. 좁히면 B1 을 놓치고, 넓히면 admin-names(21앱) 같은 표기 레인이 캠페인 전체(약 168건)를 흡수한다. G0 배너에는 규모 표시도 없다.
- **R1 과의 관계**: R1 은 «작은 수정이 커질 수 있음»을 수용했지만, 그 빚을 한 실행 안에 몰아넣으라고까지 요구하지는 않는다. B1 을 지키면서도 줄일 수 있다.
- **수리**:
  - (a) 스캔 BC = 이번 작업이 파일을 추가·변경하는 모든 BC(결정적).
  - (b) G0 배너에 슬라이스 0 규모 1행(항목 수 · 예상 이동 파일 · BC 수)과 대가를 적는다.
  - (c) ⓐ 의 한 형태로 «먼저 정리하는 별도 실행(BC별) → 착륙 뒤 이 요청 재개» 선택지를 둔다. 빚은 여전히 먼저 정리되므로 B1 과 같다. BC 가 2개 이상이면 이 선택지를 반드시 제시한다.

**M4 — 동시 레인과 경계 밖 소비자**
- **동시 레인**: B1 으로 두 레인이 같은 BC 빚을 동시에 ⓐ 로 정리하면, 같은 파일을 서로 다른 브랜치에서 옮기게 된다. 8-B 연작은 FH·FT 를 잇달아 건드린다(WT RS:26 «FT 25건 = 8-B-1 과 같은 목록»). 옛 규칙에서는 ⓑ 가 이 충돌을 흡수했다.
- **경계 밖 소비자**: 슬라이스 0 이동이 경계 밖 import 를 깰 수 있다. 발주자는 금지 경로에 있는 이름 묶인 소비자를 이미 알고 있다(8-B-5 발주서 :26 — rag_service_library 시험 · lane/8-B-2 web 파서). coder 는 영향받는 소비자 테스트를 돌리지만(agents/coder.md:46), 그 파일이 편집 금지면 Phase 2 에서 STOP 한다.
- **수리**:
  - (a) G0 에서 슬라이스 0 대상 모듈 경로를 BC 밖(tests/ · web/ · scripts/ · 다른 BC)에서 grep 한다. 걸리면 C4 충돌과 같은 방식으로 표면화한다.
  - (b) 가이드 §5 · §7 과 발주 운영에 규칙을 둔다: 한 BC 에서 슬라이스 0 이 진행 중인 레인은 하나뿐이다. 겹치면 뒤 레인은 앞 레인이 착륙한 뒤 G0 를 받거나, 사용자 원문 ⓑ 를 받는다.

**M5 — B1 을 현장에서 성립시킬 기계 장치가 없다**
- **산문 규범은 현장에서 깨졌다**: C:80 에 «코디네이터가 대신 판정하지 않는다»가 있는데도 0207 RS:69 는 코디 단독 ⓑ 를 적었다. ⓑ 51건 중 사용자 원문은 0건이다. C4 역시 산문이다.
- **G2 가 ⓐ 완결을 보지 않는다**: C:152 는 슬라이스 0 수리를 «승인된 작업»이라고만 하고, C:165 의 G2 조건에도 ⓐ 완결 검사가 없다. 슬라이스 0 이 일부 실패해도 legacy 잔존 보고에 섞여 통과한다.
- **동작 보존 증거가 약하다**: 슬라이스 0 발생률은 5/95 에서 약 65/95 로 는다. 동작 보존 증거는 여전히 LLM 판단뿐이다(diag-B2). 명세의 자가 결정으로 «11 BC 100파일»이 이동된 선례도 있다(agents/design-architect.md:63).
- **수리(최소)**:
  - (a) refactor-scope.md 결정 줄을 정형화하고(pregate 처분 행 정형과 같은 방식), G1 dispatch 전에 결정적으로 검사한다: 하드 빚 전건이 처분됐는가 · ⓑ 의 출처가 ① 이나 ② 인가 · «사용자 결정» 표기가 ① · ② 에만 쓰였는가.
  - (b) G2 배너에 1행 «G0 ⓐ N건 중 잔존 M»을 둔다. registry_gate legacy 잔존과 ⓐ 목록의 교집합으로 계산하고, M>0 이면 blocker 다.
  - (c) 슬라이스 0 은 독립 커밋으로 두고, 그 커밋에서 관련 스위트가 green 이어야 한다(0908-2137 RS:114 의 «독립 커밋» 관행을 규범화).

**M6 — 가이드(C7)가 런타임이 지키지 않을 약속을 한다**
- **멈춤 약속 불일치**: 가이드 §7 은 «원문·시각이 없는 미룸은 받지 않고 멈춥니다»라고 하지만, 런타임은 «대화형이면 다시 묻는다». 둘 중 하나로 맞춘다. B1-(d)를 채택하면 «멈춥니다»가 맞다.
- **C1b 문장이 과하게 약속한다**: §6 C1b 문장은 «물어본 뒤 옮길 수 있다»로 읽힌다. 실제 답은 «빼거나 끝내기»뿐이다(M1). 정직하게 쓴다: «표준 위반이 아닌 기존 코드의 이동·분할·이관은 지금은 하지 않습니다. 첫 단계나 설계 단계에서 범위에서 뺄지 묻습니다».
- **빠진 안내**: 동작을 바꿔야 고칠 수 있는 위반(B2)은 따로 묻는다는 안내가 없다. 작은 수정의 대가 — 먼저 정리하면 작업이 커질 수 있고, 규모를 첫 단계에서 보여 준다 — 도 없다.
- **가이드를 따른 짧은 요청의 재생**:
  - §6 예시(«규칙 하나를 수정할 때 여러 곳…»)는 대화형 사용자라면 끝까지 간다: 스캔 → ⓐ(직접) → 슬라이스 0 → 불편 항목. 불편 항목이 «새 파일 + 줄 변경»이면 통과한다.
  - 중복된 규칙을 옮겨 모아야 하는 설계라면, G1 에서 M1 의 빈칸에 빠진다.
  - 대리 요청(§7)은 B1-(a)~(e) 없이는 출처 표기가 틀린 채로 통과한다.
