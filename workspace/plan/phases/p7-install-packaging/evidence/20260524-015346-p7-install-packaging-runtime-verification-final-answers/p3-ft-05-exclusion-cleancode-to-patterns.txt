## Role Map

- **Coordinator**: 결제/재고 흐름의 최종 일관성 기준을 통합한다.
- **Domain**: 결제, 재고, 주문의 상태 전이와 불변식을 분리한다.
- **Architecture**: `outbox + inbox/idempotent consumer + saga/process manager` 조합을 선택한다.
- **DB**: outbox/inbox, idempotency key, unique constraint, 재고 예약 락 정책을 소유한다.
- **API**: 중복 요청, 처리 중 상태, 실패 응답 계약을 소유한다.
- **Django**: 서비스 레이어와 transaction boundary 구현을 소유한다.
- **TDD/Test**: 중복 이벤트, 재시도, 결제 성공 후 재고 실패, 재고 성공 후 결제 실패 시나리오를 검증한다.
- **Review**: 도메인 로직이 view/router/task/broker adapter로 새지 않는지 본다.

## Sequential Fallback

Real subagents were not executed; this is sequential fallback in the role order below.

Domain → Architecture → DB → API → Django → TDD/Test → Review → Integration 순서로 판단했다.

## 결정

**결제와 재고는 동기 호출이나 단일 트랜잭션으로 묶지 말고, transactional outbox로 분리한다.**

다만 “outbox만”으로 끝내지 말고, 주문/체크아웃 흐름을 하나의 장기 프로세스로 보고 **saga/process manager**를 둔다. 결제 컨텍스트와 재고 컨텍스트는 각각 자기 DB 트랜잭션 안에서 상태 변경과 outbox event 기록을 함께 커밋한다. 상대 컨텍스트는 broker에서 이벤트를 받아 inbox/idempotency 저장소로 중복을 막고 자기 트랜잭션을 수행한다.

권장 흐름은 보통 다음이다.

1. `CheckoutRequested`
2. 재고 컨텍스트가 재고 예약 시도
3. 성공 시 `InventoryReserved`, 실패 시 `InventoryReservationFailed`
4. 결제 컨텍스트가 결제 승인/매입 시도
5. 성공 시 `PaymentAuthorized` 또는 `PaymentCaptured`
6. 실패 시 `PaymentFailed`
7. 주문/process manager가 최종적으로 `Confirmed`, `Rejected`, `Compensating` 상태를 결정
8. 결제 성공 후 주문 확정 실패나 재고 해제가 필요하면 보상 이벤트를 발행

핵심은 **결제 서비스가 재고 테이블을 직접 만지지 않고, 재고 서비스가 결제 SDK/API를 직접 호출하지 않는 것**이다. 각 컨텍스트는 자기 언어와 불변식만 책임진다.

## Handoff Contract

**Scope**: 결제와 재고의 쓰기 흐름 분리, 이벤트 기반 일관성, 실패/재시도/중복 처리 결정.

**Inputs Used**: 결제/재고는 risky write이고, 외부 side effect와 DB 상태 변경을 안정적으로 연결해야 한다는 전제.

**Decisions**:
- Pattern: `transactional outbox` 필수.
- Process: 장기 흐름은 `saga/process manager`로 명시.
- Consumer: 모든 이벤트 소비자는 idempotent 해야 한다.
- Event contract: 내부 모델을 노출하지 말고 integration event 언어를 따로 둔다.
- Event sourcing: 선택하지 않는다. 감사/재생/시간축 복원이 핵심 요구로 제시되지 않았기 때문이다.
- Repository/UoW: Django 프로젝트라면 먼저 service layer + `transaction.atomic()` + model/QuerySet으로 충분하다. 순수 도메인 분리가 실제로 필요할 때만 추가한다.

**Files**:
- May edit: 현재는 설계 결정만 요청됐으므로 없음.
- Must not edit: 없음.

**Output**: 아키텍처 결정은 `outbox + inbox/idempotency + saga/process manager`.

**Risks**:
- 최종 일관성으로 인해 주문 상태가 잠시 `pending`, `reserved`, `payment_pending`, `compensating`일 수 있다.
- broker는 at-least-once delivery로 보고 중복 처리를 기본값으로 둬야 한다.
- 결제 gateway 호출은 DB 트랜잭션 안에서 실행하면 안 된다.
- 재고 차감은 “결제 완료 후 차감”보다 “예약 후 결제”가 보통 더 안전하다. 상품/비즈니스에 따라 반대 순서가 필요하면 보상 정책을 더 엄격히 둬야 한다.

**Required Follow-up**:
- DB: outbox/inbox schema, unique key, 재고 reservation lock, retry/dead-letter 정책 확정.
- API: `Idempotency-Key`, `202 Accepted`/상태 조회, Problem Details 응답 정책 확정.
- Test: 중복 이벤트, 순서 뒤바뀜, broker 재전송, 결제 성공 후 재고 보상 실패 테스트 작성.

**dddjango Checks**:
- domain invariant 우선.
- DB consistency와 transaction boundary를 분리해 명시.
- 외부 side effect는 after-commit/outbox worker에서만 실행.

## Integration Checklist

### Risky Write Consistency Block

| 항목 | 결정 |
|---|---|
| Transaction owner | 각 컨텍스트의 application service가 자기 aggregate와 outbox row를 같은 DB transaction으로 커밋 |
| Pattern decision | `service layer + transactional outbox + inbox/idempotent consumer + saga/process manager` |
| Locking strategy | 재고 예약은 DB Agent가 row lock 또는 조건부 update 방식으로 확정해야 함 |
| Uniqueness/idempotency storage | API idempotency table, consumer inbox table, outbox event unique id 필요 |
| Idempotency-Key API behavior | API Agent가 중복 checkout/payment 요청의 동일 응답 재사용 정책을 정해야 함 |
| External side-effect timing | 결제 gateway 호출과 broker publish는 DB commit 이후 outbox dispatcher가 수행 |
| Isolation/retry decision | DB Agent가 재고 경합 retry, dead-letter, poison event 정책을 정해야 함 |
| Test criteria | 중복 이벤트, 재시도, 부분 실패, 보상 실패, 순서 역전, 동시 재고 예약 테스트 필요 |

최종 한 줄 결정: **결제와 재고는 outbox로 분리하고, 주문/체크아웃 흐름은 saga/process manager가 조정한다. 동기 cross-service transaction, 직접 DB 공유, 결제 SDK 호출을 재고/주문 트랜잭션 안에 넣는 방식은 채택하지 않는다.**

Serena: 코드 심볼/참조 추적이 필요한 작업이 아니어서 사용하지 않았다.
