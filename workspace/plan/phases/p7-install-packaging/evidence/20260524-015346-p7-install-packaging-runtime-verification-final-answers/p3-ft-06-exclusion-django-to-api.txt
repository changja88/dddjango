권장 기본 계약은 `POST /orders`가 주문 생성을 **동기적으로 확정**하면 `201 Created`, 비동기 승인/재고확보/결제가 뒤따르면 `202 Accepted`입니다. 에러는 전 API에서 RFC 9457 Problem Details 형식인 `application/problem+json`으로 통일하는 게 좋습니다.

**성공 응답**

```http
POST /orders
Content-Type: application/json
Accept: application/json
Idempotency-Key: 8f4c9f2e-...
```

`201 Created`: 주문 생성이 서버에서 확정된 경우

```http
HTTP/1.1 201 Created
Content-Type: application/json
Location: /orders/ord_123
```

```json
{
  "id": "ord_123",
  "status": "created",
  "total_amount": "59000",
  "currency": "KRW",
  "created_at": "2026-05-24T10:30:00Z"
}
```

`202 Accepted`: 주문 요청은 접수됐지만 재고 예약, 결제 승인, 외부 시스템 처리 등으로 아직 최종 생성/확정이 끝나지 않은 경우

```http
HTTP/1.1 202 Accepted
Content-Type: application/json
Location: /orders/ord_123
```

```json
{
  "id": "ord_123",
  "status": "pending",
  "status_url": "/orders/ord_123"
}
```

`POST /orders`는 중복 생성 위험이 크므로 `Idempotency-Key`를 **필수 헤더**로 두는 것을 권장합니다. 같은 사용자/계정 범위에서 같은 key와 같은 request body가 재시도되면 기존 `201` 또는 `202` 결과를 재응답하고, 같은 key에 다른 body가 오면 `409 Conflict`로 처리합니다.

**에러 포맷**

모든 에러 응답:

```http
Content-Type: application/problem+json
```

기본 구조:

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/orders/requests/req_abc123",
  "errors": [
    {
      "field": "items[0].quantity",
      "code": "min_value",
      "message": "Quantity must be at least 1."
    }
  ]
}
```

필드 의미:

`type`: 안정적인 problem type URI. 클라이언트가 분기할 수 있는 식별자입니다.

`title`: 같은 problem type이면 항상 같은 짧은 제목을 씁니다.

`status`: 실제 HTTP status code와 반드시 일치해야 합니다.

`detail`: 이번 발생 건에 대한 설명입니다. 내부 클래스명, stack trace, DB 정보는 노출하지 않습니다.

`instance`: 이번 요청/에러 발생 건을 추적할 수 있는 URI 또는 request id 기반 경로입니다.

`errors`: 검증 에러에서만 사용하는 확장 필드입니다. 클라이언트가 필드별 메시지를 표시할 수 있게 `field`, `code`, `message`를 둡니다.

**권장 status code 매핑**

| Status | 상황 | Problem type 예시 |
|---:|---|---|
| `400 Bad Request` | JSON 파싱 실패, body가 객체가 아님, 요청 문법이 깨짐 | `/problems/bad-request` |
| `401 Unauthorized` | 인증 없음 또는 토큰 무효 | `/problems/unauthorized` |
| `403 Forbidden` | 인증은 됐지만 주문 생성 권한 없음 | `/problems/forbidden` |
| `404 Not Found` | URL 경로의 상위 리소스가 없거나 숨겨야 함. 예: `/customers/{id}/orders` 구조일 때 customer 없음 | `/problems/not-found` |
| `409 Conflict` | 현재 서버 상태와 충돌. 예: idempotency key 재사용 body 불일치, 재고/가격/쿠폰 상태 충돌, 중복 주문 방지 충돌 | `/problems/order-conflict` |
| `415 Unsupported Media Type` | `Content-Type`이 `application/json`이 아님 | `/problems/unsupported-media-type` |
| `422 Unprocessable Entity` | JSON은 유효하지만 필드 값이나 도메인 규칙이 유효하지 않음 | `/problems/validation-error` |
| `429 Too Many Requests` | rate limit 초과 | `/problems/rate-limit-exceeded` |
| `500 Internal Server Error` | 예상하지 못한 서버 오류 | `/problems/internal-server-error` |
| `503 Service Unavailable` | 일시적 장애, 외부 결제/재고 시스템 장애, 점검 | `/problems/service-unavailable` |

**대표 에러 예시**

Malformed JSON은 `400`:

```json
{
  "type": "https://api.example.com/problems/bad-request",
  "title": "Bad request",
  "status": 400,
  "detail": "Request body must be valid JSON.",
  "instance": "/orders/requests/req_abc123"
}
```

필드 검증 실패는 `422`:

```json
{
  "type": "https://api.example.com/problems/validation-error",
  "title": "Validation failed",
  "status": 422,
  "detail": "One or more fields are invalid.",
  "instance": "/orders/requests/req_abc123",
  "errors": [
    {
      "field": "shipping_address.postal_code",
      "code": "invalid_format",
      "message": "Postal code is invalid."
    },
    {
      "field": "items",
      "code": "required",
      "message": "At least one order item is required."
    }
  ]
}
```

재고 부족이나 가격 변경처럼 현재 상태와 충돌하면 `409`:

```json
{
  "type": "https://api.example.com/problems/order-conflict",
  "title": "Order conflict",
  "status": 409,
  "detail": "One or more items are no longer available in the requested quantity.",
  "instance": "/orders/requests/req_abc123",
  "conflicts": [
    {
      "field": "items[0].product_id",
      "code": "insufficient_stock",
      "message": "Only 1 item is available."
    }
  ]
}
```

Idempotency key 충돌도 `409`:

```json
{
  "type": "https://api.example.com/problems/idempotency-conflict",
  "title": "Idempotency conflict",
  "status": 409,
  "detail": "The same Idempotency-Key was used with a different request body.",
  "instance": "/orders/requests/req_abc123"
}
```

Rate limit은 `429`와 retry header를 같이 줍니다.

```http
HTTP/1.1 429 Too Many Requests
Content-Type: application/problem+json
Retry-After: 60
```

```json
{
  "type": "https://api.example.com/problems/rate-limit-exceeded",
  "title": "Rate limit exceeded",
  "status": 429,
  "detail": "Too many order creation requests. Retry after 60 seconds.",
  "instance": "/orders/requests/req_abc123"
}
```

정리하면, `POST /orders`의 기본 성공은 `201 Created + Location`, 비동기 처리면 `202 Accepted`, 클라이언트 입력 문제는 `400/415/422`, 상태 충돌과 중복 방지는 `409`, 모든 에러 body는 `application/problem+json`으로 통일하는 설계가 가장 예측 가능합니다.

Serena: 설계 질의라 사용하지 않았습니다. 코드 참조나 심볼 추적이 필요한 작업이 아니었습니다.
