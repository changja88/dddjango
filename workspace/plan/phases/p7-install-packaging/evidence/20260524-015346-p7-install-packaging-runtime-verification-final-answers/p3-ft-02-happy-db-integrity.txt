쿠폰 중복 사용은 **“사용 사실”을 별도 테이블로 만들고, 그 테이블에 unique constraint를 거는 방식**이 가장 안전합니다. 애플리케이션에서 `exists()`로 먼저 확인하는 방식은 동시 요청에서 깨질 수 있으니, 최종 방어선은 DB가 가져야 합니다.

예를 들면 핵심 테이블은 이렇게 잡습니다.

```sql
coupon_redemption
- id
- user_id
- coupon_id
- order_id
- status        -- reserved / used / canceled 등
- created_at
```

가장 단순한 정책이 “한 유저는 한 쿠폰을 평생 한 번만 사용 가능”이면:

```sql
UNIQUE (user_id, coupon_id)
```

정책이 “취소된 주문의 쿠폰은 다시 쓸 수 있음”이면 전체 unique가 아니라 **활성 사용 상태에만 걸리는 partial unique**가 맞습니다. PostgreSQL 기준:

```sql
CREATE UNIQUE INDEX uniq_active_coupon_redemption
ON coupon_redemption (user_id, coupon_id)
WHERE status IN ('reserved', 'used');
```

즉, `canceled`, `failed`, `expired` 같은 상태는 중복 검사 대상에서 빼고, 실제로 쿠폰 점유 또는 사용으로 보는 상태만 unique 대상에 넣습니다.

트랜잭션은 **쿠폰 사용 기록 생성, 주문 할인 반영, 결제/주문 상태 변경**을 하나의 원자적 단위로 묶어야 합니다.

```sql
BEGIN;

-- 필요하면 주문 row lock
SELECT *
FROM orders
WHERE id = :order_id
FOR UPDATE;

-- 중복 사용은 이 INSERT가 DB unique constraint로 막게 한다
INSERT INTO coupon_redemption (user_id, coupon_id, order_id, status)
VALUES (:user_id, :coupon_id, :order_id, 'used');

-- 주문 할인 금액 반영
UPDATE orders
SET coupon_id = :coupon_id,
    discount_amount = :discount_amount
WHERE id = :order_id;

COMMIT;
```

중요한 점은 이겁니다.

`SELECT 먼저 해서 없으면 INSERT`는 보조 검증으로만 쓰고, 정합성은 믿으면 안 됩니다. 동시 요청 두 개가 동시에 “없음”을 보고 둘 다 insert하려고 할 수 있습니다. 대신 **바로 insert하고 unique violation을 도메인 오류로 변환**하는 쪽이 안전합니다.

Django라면 대략 이런 흐름입니다.

```python
from django.db import IntegrityError, transaction

try:
    with transaction.atomic():
        order = (
            Order.objects
            .select_for_update()
            .get(id=order_id, user=user)
        )

        CouponRedemption.objects.create(
            user=user,
            coupon=coupon,
            order=order,
            status=CouponRedemption.Status.USED,
        )

        order.apply_coupon(coupon)
        order.save(update_fields=["coupon", "discount_amount"])
except IntegrityError:
    raise CouponAlreadyUsedError
```

`select_for_update()`는 중복 쿠폰 사용 자체를 막기 위한 핵심 장치는 아닙니다. 그건 unique constraint가 합니다. `select_for_update()`는 같은 주문에 동시에 쿠폰 적용, 결제 진행, 금액 변경 같은 일이 겹치지 않게 주문 row를 보호하는 용도입니다.

총 발급 수량이나 전체 사용 한도도 있으면 추가로 잠금이 필요합니다. 예를 들어 “이 쿠폰은 전체 100명만 사용 가능”이면 unique만으로는 부족합니다. 이 경우 쿠폰 row 또는 별도 quota row를 잠그고 카운터를 조건부로 갱신해야 합니다.

```sql
BEGIN;

SELECT *
FROM coupons
WHERE id = :coupon_id
FOR UPDATE;

-- remaining_count > 0 확인 후 차감
UPDATE coupons
SET remaining_count = remaining_count - 1
WHERE id = :coupon_id
  AND remaining_count > 0;

INSERT INTO coupon_redemption (user_id, coupon_id, order_id, status)
VALUES (:user_id, :coupon_id, :order_id, 'used');

COMMIT;
```

또는 더 나은 형태로는 조건부 update 한 번으로 처리합니다.

```sql
UPDATE coupons
SET remaining_count = remaining_count - 1
WHERE id = :coupon_id
  AND remaining_count > 0;
```

영향받은 row가 0개면 품절로 보면 됩니다.

**Risky Write Consistency Block**

- 불변식: 같은 사용자는 같은 쿠폰을 활성 상태로 두 번 사용할 수 없다.
- DB 제약: `UNIQUE (user_id, coupon_id)` 또는 상태 정책이 있으면 partial unique.
- 트랜잭션 경계: 쿠폰 사용 row 생성, 주문 할인 반영, 필요 시 쿠폰 수량 차감을 같은 `atomic` 안에 둔다.
- 락: 중복 사용은 unique constraint가 담당한다. 주문 동시 변경은 `orders FOR UPDATE`, 전체 수량 제한은 `coupons FOR UPDATE` 또는 조건부 update가 담당한다.
- 격리 수준: 보통 PostgreSQL `READ COMMITTED` + unique constraint + row lock이면 충분하다. `SERIALIZABLE`로 해결하려고 하기보다 명시적 제약과 잠금을 잡는 편이 운영상 예측 가능하다.
- 실패 처리: unique violation은 `CouponAlreadyUsed`, 조건부 수량 차감 실패는 `CouponSoldOut` 같은 도메인 오류로 변환한다.

요약하면, **중복 사용 방지는 unique constraint, 같은 주문/수량/상태 변경의 원자성은 transaction, 공유 카운터 경쟁은 row lock 또는 조건부 update**로 나누는 게 맞습니다.
