판단은 둘로 나누는 게 맞습니다.

결론: **재고 차감은 같은 DB/같은 bounded context 안의 핵심 불변식이면 서비스 트랜잭션에서 바로 처리하고, 알림 발송은 outbox로 분리**하세요. 단, 재고가 별도 서비스나 별도 DB에 있으면 재고 차감도 직접 호출하지 말고 **outbox + consumer**, 필요하면 **saga/보상 흐름**으로 봐야 합니다.

**추천 구조**
`결제승인 Application Service`가 하나의 트랜잭션에서:

1. 결제 상태를 `APPROVED`로 변경
2. 같은 DB에 있는 재고를 락/조건부 업데이트로 차감
3. `NotificationRequested` 또는 `PaymentApproved` outbox row 저장
4. 커밋 이후 outbox dispatcher가 알림 발송

즉, 같은 트랜잭션으로 보호해야 하는 것은 서비스 안에서 처리하고, 외부 부작용은 outbox로 넘깁니다.

**재고 차감 판단**
재고 차감은 “알림”이 아니라 주문/결제의 핵심 상태 변경입니다. 과판매 방지, 결제 승인과 재고 차감의 일관성이 중요하면 비동기로 밀어내기보다 결제 승인 use case의 트랜잭션 안에서 처리하는 편이 더 명확합니다.

다만 재고가 별도 Inventory 서비스라면 직접 HTTP/RPC 호출은 피하는 게 좋습니다. 결제 DB 커밋은 성공했는데 재고 호출이 실패하거나, 재고는 차감됐는데 결제 트랜잭션이 롤백되는 문제가 생깁니다. 이 경우 결제 쪽은 outbox에 `PaymentApproved`를 기록하고, 재고 쪽 consumer가 idempotent하게 차감해야 합니다. 재고 부족 가능성이 남아 있다면 승인 후 차감이 아니라 사전 예약 또는 saga 보상까지 필요합니다.

**알림 발송 판단**
알림은 외부 부작용입니다. 이메일, SMS, 푸시, 카카오톡, webhook 같은 것은 결제 트랜잭션 안에서 직접 호출하지 않는 게 맞습니다.

직접 호출하면 이런 문제가 생깁니다.

- DB는 롤백됐는데 알림은 이미 발송됨
- DB 커밋은 됐는데 알림 호출 실패로 승인 API 전체가 실패 처리됨
- timeout/retry 때문에 중복 알림 발생
- 외부 알림 장애가 결제 승인 흐름을 막음

알림이 유실돼도 되는 단순 best-effort라면 `transaction.on_commit()` 정도도 가능하지만, 결제 승인 알림처럼 운영상 재처리와 추적이 필요하면 outbox가 더 적절합니다.

**Risky Write Consistency Block**
| 항목 | 판단 |
|---|---|
| owning use case | `ApprovePayment` / `ConfirmPayment` application service |
| 재고 차감 패턴 | 같은 DB면 서비스 트랜잭션에서 동기 처리 |
| 알림 발송 패턴 | outbox |
| side-effect timing | 알림은 DB commit 이후 outbox dispatcher가 처리 |
| idempotency | 결제 승인 요청, 재고 차감, outbox consumer 모두 필요 |
| DB 후속 검토 | 재고 row lock, 조건부 update, 중복 승인 방지 unique/idempotency key |
| API 후속 검토 | 결제 승인 endpoint의 `Idempotency-Key`, 중복 승인 응답 정책 |
| 테스트 후속 검토 | 중복 승인, 동시 재고 차감, outbox 재시도/중복 발송 테스트 |

요약하면: **같은 DB의 재고 차감은 바로 처리, 알림은 outbox. 재고가 외부 서비스면 재고도 outbox/saga 대상**입니다.

Serena: 코드 변경이나 참조 추적이 필요한 작업이 아니라 사용하지 않았습니다.
