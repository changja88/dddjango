구체 코드/라우트가 없는 상태라, `exclusion` 리소스 기준의 API 계약 초안으로 정리합니다.

**API URL**

- Base prefix: `/api/v1`
- URL 규칙: lowercase, kebab-case, plural noun, trailing slash 없음
- Collection: `GET /api/v1/exclusions`
- Detail: `GET /api/v1/exclusions/{exclusion_id}`
- Create: `POST /api/v1/exclusions`
- Update: `PATCH /api/v1/exclusions/{exclusion_id}`
- Delete: `DELETE /api/v1/exclusions/{exclusion_id}`
- 부모 리소스에 강하게 종속된 워크플로우라면:
  - `GET /api/v1/{parent-resources}/{parent_id}/exclusions`
  - 단, 3단계 이상 중첩은 피함
- 필터는 query string 사용:
  - `/api/v1/exclusions?target_type=...&target_id=...&status=...`

**Status Code**

- `200 OK`: 목록 조회, 단건 조회, 수정 후 응답 본문을 돌려주는 경우
- `201 Created`: 생성 성공
  - `Location: /api/v1/exclusions/{exclusion_id}` 포함
- `204 No Content`: 삭제 성공, 또는 수정 후 본문이 필요 없는 경우
- `400 Bad Request`: JSON 파싱 실패, 잘못된 query/path/body 구조
- `401 Unauthorized`: 인증 없음 또는 토큰 invalid
- `403 Forbidden`: 인증은 됐지만 권한 없음
- `404 Not Found`: exclusion 또는 부모 리소스 없음, 혹은 보안상 숨김 처리
- `409 Conflict`: 이미 존재하는 exclusion 생성, 상태 충돌, 동시성 충돌
- `422 Unprocessable Entity`: 문법은 맞지만 도메인 규칙상 불가능한 요청
- `429 Too Many Requests`: rate limit 초과
- `500 Internal Server Error`: 예상하지 못한 서버 오류
- `503 Service Unavailable`: 일시적 장애/점검, 가능하면 `Retry-After` 포함

**Header 정책**

- 요청 공통:
  - `Authorization: Bearer <token>`
  - `Accept: application/json`
- body 있는 요청:
  - `Content-Type: application/json`
- 에러 응답:
  - `Content-Type: application/problem+json`
  - Problem Details의 `status`는 실제 HTTP status와 반드시 일치
- 생성 응답:
  - `201 Created`
  - `Location: /api/v1/exclusions/{exclusion_id}`
- 재시도 가능한 생성 요청:
  - `Idempotency-Key`를 `POST /api/v1/exclusions`에만 선택적으로 적용
  - 중복 생성 위험이 있으면 사실상 필수로 두는 편이 낫다
- 동시성 제어가 필요하면:
  - 응답에 `ETag`
  - 수정/삭제 요청에 `If-Match`
  - 불일치 시 `409 Conflict` 또는 `412 Precondition Failed` 중 하나로 정책 고정
- rate limit:
  - `429`에서 `Retry-After` 포함
  - 필요하면 `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset` 사용

Serena: 코드 수정/참조 추적 작업이 아니고 현재 디렉터리에 소스 파일도 없어 생략했습니다.
