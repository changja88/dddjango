기존 프로젝트 파일이 없는 빈 디렉터리라서, 일반적인 커머스 주문 도메인 기준으로 설계합니다. 핵심은 `orders` 하나에 고객, 배송지, 상품, 결제, 할인, 배송 상태를 모두 넣지 않고, 주문의 생애주기와 감사 추적이 필요한 값을 분리하는 것입니다.

**정규화 방향**

`orders`는 주문 헤더만 가진다.

```sql
orders
- id PK
- order_number UNIQUE NOT NULL
- customer_id FK -> customers(id) NOT NULL
- status NOT NULL
- currency NOT NULL
- subtotal_amount NOT NULL
- discount_amount NOT NULL DEFAULT 0
- shipping_fee_amount NOT NULL DEFAULT 0
- tax_amount NOT NULL DEFAULT 0
- total_amount NOT NULL
- placed_at NULL
- canceled_at NULL
- created_at NOT NULL
- updated_at NOT NULL
```

주문 상품은 반복 그룹이므로 `order_items`로 분리한다.

```sql
order_items
- id PK
- order_id FK -> orders(id) NOT NULL
- product_id FK -> products(id) NULL
- sku_id FK -> product_skus(id) NOT NULL
- product_name_snapshot NOT NULL
- sku_name_snapshot NOT NULL
- unit_price_amount NOT NULL
- quantity NOT NULL
- line_subtotal_amount NOT NULL
- line_discount_amount NOT NULL DEFAULT 0
- line_total_amount NOT NULL
- created_at NOT NULL
```

주소는 고객 주소록을 직접 참조하지 말고 주문 시점 스냅샷으로 둔다. 고객이 나중에 주소를 수정해도 과거 주문 배송지가 바뀌면 안 된다.

```sql
order_addresses
- id PK
- order_id FK -> orders(id) NOT NULL
- type NOT NULL -- shipping, billing
- recipient_name NOT NULL
- phone_number NOT NULL
- postal_code NOT NULL
- address_line1 NOT NULL
- address_line2 NULL
- city NOT NULL
- region NULL
- country_code NOT NULL
```

결제는 주문과 1:N 관계로 둔다. 실패/재시도/부분 결제를 표현하려면 `orders.payment_id` 하나로는 부족하다.

```sql
order_payments
- id PK
- order_id FK -> orders(id) NOT NULL
- provider NOT NULL
- provider_payment_id NULL
- method NOT NULL
- status NOT NULL
- amount NOT NULL
- approved_at NULL
- failed_at NULL
- created_at NOT NULL
```

상태 변경 이력이 필요하면 현재 상태는 `orders.status`, 이력은 별도 테이블로 둔다.

```sql
order_status_histories
- id PK
- order_id FK -> orders(id) NOT NULL
- from_status NULL
- to_status NOT NULL
- reason NULL
- changed_by_id FK -> users(id) NULL
- changed_at NOT NULL
```

배송은 주문 전체 배송만 있으면 `order_shipments`, 부분 배송이 있으면 `order_shipment_items`까지 둔다.

```sql
order_shipments
- id PK
- order_id FK -> orders(id) NOT NULL
- carrier_code NULL
- tracking_number NULL
- status NOT NULL
- shipped_at NULL
- delivered_at NULL

order_shipment_items
- id PK
- shipment_id FK -> order_shipments(id) NOT NULL
- order_item_id FK -> order_items(id) NOT NULL
- quantity NOT NULL
```

할인은 주문 단위와 상품 단위가 다를 수 있으므로 별도 테이블로 분리한다.

```sql
order_discounts
- id PK
- order_id FK -> orders(id) NOT NULL
- coupon_id FK -> coupons(id) NULL
- type NOT NULL
- amount NOT NULL
- label_snapshot NOT NULL

order_item_discounts
- id PK
- order_item_id FK -> order_items(id) NOT NULL
- coupon_id FK -> coupons(id) NULL
- type NOT NULL
- amount NOT NULL
- label_snapshot NOT NULL
```

**Foreign Key 설계**

추천 FK 정책은 다음과 같습니다.

```text
orders.customer_id              -> customers.id       ON DELETE RESTRICT
order_items.order_id            -> orders.id          ON DELETE CASCADE 또는 RESTRICT
order_items.product_id          -> products.id        ON DELETE SET NULL
order_items.sku_id              -> product_skus.id    ON DELETE RESTRICT
order_addresses.order_id        -> orders.id          ON DELETE CASCADE 또는 RESTRICT
order_payments.order_id         -> orders.id          ON DELETE RESTRICT
order_status_histories.order_id -> orders.id          ON DELETE CASCADE 또는 RESTRICT
order_shipments.order_id        -> orders.id          ON DELETE RESTRICT
order_shipment_items.shipment_id -> order_shipments.id ON DELETE CASCADE
order_shipment_items.order_item_id -> order_items.id   ON DELETE RESTRICT
```

실무에서는 주문은 감사 데이터이므로 물리 삭제를 거의 하지 않습니다. 그래서 `orders`를 삭제하지 않는 정책이면 자식 테이블 FK의 `CASCADE` 여부는 큰 의미가 줄어들고, 오히려 `RESTRICT/PROTECT`가 안전합니다. 테스트 데이터 정리나 강한 소유 관계를 DB에 표현하고 싶을 때만 `order_items`, `order_addresses`, `order_status_histories`에 `CASCADE`를 고려합니다.

상품 FK는 조심해야 합니다. 주문 라인은 과거 주문의 법적/정산 기록이므로 상품명이 바뀌거나 상품이 비활성화되어도 주문 내역은 보존되어야 합니다. 그래서 `product_name_snapshot`, `sku_name_snapshot`, `unit_price_amount` 같은 스냅샷 컬럼을 `order_items`에 둡니다. `product_id`는 조회 편의용으로 `SET NULL` 가능하게 두고, 실제 주문 기록의 의미는 스냅샷 값으로 보존하는 편이 안전합니다.

**필수 제약조건**

```sql
UNIQUE (orders.order_number)

CHECK (order_items.quantity > 0)
CHECK (order_items.unit_price_amount >= 0)
CHECK (order_items.line_subtotal_amount >= 0)
CHECK (order_items.line_discount_amount >= 0)
CHECK (order_items.line_total_amount >= 0)

CHECK (orders.subtotal_amount >= 0)
CHECK (orders.discount_amount >= 0)
CHECK (orders.shipping_fee_amount >= 0)
CHECK (orders.tax_amount >= 0)
CHECK (orders.total_amount >= 0)

UNIQUE (order_addresses.order_id, order_addresses.type)
UNIQUE (order_payments.provider, order_payments.provider_payment_id)
UNIQUE (order_shipments.carrier_code, order_shipments.tracking_number)
```

상태값은 DB enum 또는 `CHECK status IN (...)`로 제한할 수 있습니다. 단, 상태가 자주 추가되는 시스템이면 DB enum보다 `CHECK` 또는 별도 상태 코드 테이블이 운영상 덜 불편합니다.

**추천 인덱스**

```sql
-- 고객 주문 목록
INDEX orders_customer_created_idx
ON orders (customer_id, created_at DESC);

-- 관리자 주문 검색/필터
INDEX orders_status_created_idx
ON orders (status, created_at DESC);

-- 주문번호 조회
UNIQUE INDEX orders_order_number_uidx
ON orders (order_number);

-- 주문 상세 로딩
INDEX order_items_order_id_idx
ON order_items (order_id);

INDEX order_addresses_order_id_idx
ON order_addresses (order_id);

INDEX order_payments_order_id_idx
ON order_payments (order_id);

INDEX order_status_histories_order_changed_idx
ON order_status_histories (order_id, changed_at DESC);

-- 상품별 주문 라인 분석
INDEX order_items_sku_created_idx
ON order_items (sku_id, created_at DESC);
```

**최종 ERD 요약**

```text
customers 1 ── N orders
orders 1 ── N order_items
orders 1 ── N order_payments
orders 1 ── N order_status_histories
orders 1 ── N order_shipments
orders 1 ── 1 or 2 order_addresses
orders 1 ── N order_discounts

products 1 ── N order_items
product_skus 1 ── N order_items

order_shipments 1 ── N order_shipment_items
order_items 1 ── N order_shipment_items

order_items 1 ── N order_item_discounts
coupons 1 ── N order_discounts
coupons 1 ── N order_item_discounts
```

DDD 관점에서는 `Order` aggregate 내부에 `OrderItem`, `OrderAddress`, `OrderPayment` 같은 개념이 있어도, DB에서는 조회성/무결성/반복 그룹 제거를 위해 별도 테이블로 정규화하는 것이 맞습니다. 단, 주문 시점 가격, 상품명, 주소처럼 과거 기록으로 고정되어야 하는 값은 원본 테이블을 FK로만 따라가지 말고 주문 쪽에 스냅샷으로 보존해야 합니다.
