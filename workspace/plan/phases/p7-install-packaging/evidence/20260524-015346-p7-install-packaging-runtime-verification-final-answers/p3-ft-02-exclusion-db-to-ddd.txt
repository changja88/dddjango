코드 맥락이 비어 있어서 일반적인 커머스 주문 도메인 기준으로 모델링합니다. 핵심은 `Order`가 “결제, 재고, 배송까지 모두 품는 큰 객체”가 아니라 **주문 의사결정과 주문 상태 전이의 일관성 경계**라는 점입니다.

**Aggregate Boundary**
`Order`가 직접 소유할 것:

- `OrderId`
- `BuyerId` 또는 `CustomerId`
- `OrderLine[]`
- 주문 시점의 상품명, 단가, 옵션 같은 스냅샷
- 주문 금액 합계
- 배송지 스냅샷
- 주문 상태
- 주문 생성/확정/취소/결제확인 시각
- 주문 도메인 이벤트

`Order` 밖에 둘 것:

- `Product`, `Inventory`, `Payment`, `Shipment`, `Coupon` aggregate
- 실시간 재고 수량
- 결제 승인 처리
- 배송 처리 상태의 세부 생명주기
- 외부 PG, 택배사, 쿠폰 시스템 호출

다른 aggregate는 객체 참조가 아니라 ID나 스냅샷으로만 연결하는 편이 좋습니다.

---

**Order가 가져야 할 핵심 불변식**

1. **주문은 최소 1개 이상의 주문 라인을 가져야 확정될 수 있다**

`Order`는 빈 주문으로 `placed` 상태가 될 수 없습니다.

```text
PlacedOrder => order_lines.count >= 1
```

초안 주문을 허용한다면 `Draft` 상태에서는 빈 라인을 허용할 수 있지만, `place()` 시점에는 반드시 막아야 합니다.

---

2. **주문 라인의 수량은 항상 양수여야 한다**

```text
OrderLine.quantity > 0
```

수량이 0인 라인은 “삭제”이지 주문 라인이 아닙니다. 음수 수량은 반품/환불 같은 별도 도메인 개념으로 분리하는 것이 낫습니다.

---

3. **같은 상품/옵션 조합은 주문 안에서 중복 라인으로 존재하지 않는다**

```text
unique(product_id, option_id) within Order
```

같은 SKU를 두 번 추가하면 새 라인을 만드는 대신 기존 라인의 수량을 증가시키는 식으로 모델링합니다.

예외가 있다면 명시해야 합니다. 예를 들어 같은 상품이라도 판매자, 배송유형, 선물포장 옵션이 다르면 별도 라인일 수 있습니다.

---

4. **주문 금액은 주문 라인의 스냅샷 금액으로부터 계산된 값과 일치해야 한다**

```text
order.subtotal == sum(line.unit_price * line.quantity)
order.total == subtotal - discounts + shipping_fee + tax
```

`Order`는 상품의 현재 가격을 다시 조회해서 합계를 계산하면 안 됩니다. 주문 시점의 가격 스냅샷을 보관하고, 그 스냅샷 기준으로 합계를 보존해야 합니다.

---

5. **주문 안의 모든 금액은 같은 통화여야 한다**

```text
all(order.money.currency == order.currency)
```

`Money` value object로 `amount`와 `currency`를 묶는 것이 좋습니다. 서로 다른 통화가 섞인 주문은 별도 주문으로 나누거나, 환율 적용 정책을 다른 도메인 서비스로 빼야 합니다.

---

6. **최종 결제 금액은 음수가 될 수 없다**

```text
order.total >= 0
```

쿠폰이나 포인트가 상품 금액을 초과할 수 있더라도 결제 금액은 0 밑으로 내려가면 안 됩니다. 초과분 환급이나 적립은 `Order`의 기본 불변식이 아니라 별도 정책으로 다루는 편이 안전합니다.

---

7. **확정된 주문의 상품 구성과 가격 스냅샷은 임의로 변경될 수 없다**

```text
if order.status in [Placed, Paid, FulfillmentStarted, Completed, Cancelled]:
    order_lines cannot be changed directly
    price_snapshot cannot be changed
```

주문 확정 이후 변경이 필요하다면 `changeShippingAddress()`, `cancelLine()`, `requestReturn()` 같은 의도가 드러나는 행위로 열어야 합니다. 단순 setter로 바꾸면 주문 이력이 깨집니다.

---

8. **주문 상태 전이는 허용된 경로로만 가능하다**

예시 상태 모델:

```text
Draft -> Placed
Placed -> PaymentConfirmed
Placed -> Cancelled
PaymentConfirmed -> FulfillmentRequested
PaymentConfirmed -> Cancelled
FulfillmentRequested -> Completed
FulfillmentRequested -> CancellationRequested
Completed -> ReturnRequested
Cancelled -> terminal
```

중요한 불변식은 다음입니다.

```text
Cancelled order cannot be paid
Completed order cannot be cancelled normally
Draft order cannot be fulfilled
PaymentConfirmed order must have matching payment amount
```

상태 전이는 `order.status = ...`가 아니라 `place()`, `confirmPayment()`, `cancel()`, `requestFulfillment()` 같은 행위 메서드로만 일어나야 합니다.

---

9. **결제 확인은 주문 금액과 결제 금액이 일치할 때만 가능하다**

```text
payment.amount == order.total
payment.currency == order.currency
```

단, 결제 승인 자체는 `Payment` aggregate나 외부 PG 영역입니다. `Order`는 “승인된 결제 결과를 반영해도 되는가”만 판단합니다.

```python
order.confirm_payment(payment_id, paid_amount)
```

이 메서드는 금액과 통화가 맞는지 확인하고, 맞으면 `PaymentConfirmed` 상태로 전이합니다.

---

10. **취소는 주문의 현재 진행 상태가 허용할 때만 가능하다**

```text
order.can_cancel() == true
```

일반적으로 다음은 취소 불가 또는 별도 프로세스입니다.

```text
Completed order cannot be cancelled
FulfillmentStarted order cannot be cancelled directly
Cancelled order cannot be cancelled again
```

배송/출고 시작 여부는 `Shipment`의 세부 상태를 직접 들고 오기보다, 주문에 필요한 최소 상태만 이벤트로 반영하는 편이 좋습니다.

예:

```text
Order marks fulfillment_started when FulfillmentStarted event is accepted
```

---

11. **배송이 필요한 주문은 확정 시점에 유효한 배송지를 가져야 한다**

```text
if order.requires_shipping:
    shipping_address must be present and valid
```

디지털 상품만 있는 주문이라면 배송지가 없어도 됩니다. 그래서 이 불변식은 상품 유형에 따라 달라질 수 있습니다.

---

12. **Order aggregate 안의 child entity는 Order root를 통하지 않고 변경될 수 없다**

`OrderLine`은 독립 aggregate가 아닙니다. 외부에서 `OrderLine`을 직접 저장하거나 수정하면 안 됩니다.

```text
Only Order can add/remove/change OrderLine
```

이건 구현 관점에서도 중요합니다. Repository도 `OrderRepository`가 aggregate 단위로 저장해야지 `OrderLineRepository`를 따로 두면 불변식이 새기 쉽습니다.

---

**추천 모델**
```text
Order
- id: OrderId
- buyer_id: BuyerId
- status: OrderStatus
- lines: list[OrderLine]
- shipping_address: ShippingAddress | None
- subtotal: Money
- discount_total: Money
- shipping_fee: Money
- tax_total: Money
- total: Money
- placed_at: datetime | None
- paid_at: datetime | None
- cancelled_at: datetime | None

OrderLine
- line_id: OrderLineId
- product_id: ProductId
- variant_id: VariantId | None
- product_name_snapshot: str
- unit_price: Money
- quantity: Quantity
- line_total: Money
```

주요 행위:

```text
Order.add_line(...)
Order.change_line_quantity(...)
Order.remove_line(...)
Order.place()
Order.confirm_payment(payment_id, amount)
Order.cancel(reason)
Order.mark_fulfillment_requested()
Order.complete()
```

---

**Domain Events**
`Order`가 발생시킬 만한 이벤트:

```text
OrderPlaced
OrderPaymentConfirmed
OrderCancelled
OrderFulfillmentRequested
OrderCompleted
```

이벤트 소비자는 aggregate 밖입니다.

- `OrderPlaced` -> 재고 예약, 결제 요청, 알림
- `OrderPaymentConfirmed` -> 출고 요청
- `OrderCancelled` -> 재고 예약 해제, 결제 취소 요청
- `OrderFulfillmentRequested` -> 배송 컨텍스트로 전달

이 이벤트들은 보통 DB commit 이후 outbox 같은 방식으로 내보내는 것이 좋습니다. `Order` 내부에서 외부 시스템을 직접 호출하면 aggregate가 인프라에 묶입니다.

---

요약하면 `Order` aggregate의 핵심 불변식은 **주문 라인의 유효성, 금액 일관성, 가격 스냅샷 보존, 상태 전이 규칙, 결제 금액 일치, 취소 가능 조건**입니다. 재고 보유, 결제 승인, 배송 처리 자체는 `Order`의 내부 불변식이 아니라 다른 bounded context와의 이벤트/유스케이스 조율로 다루는 편이 DDD 모델로 더 안정적입니다.

Serena: 현재 경로가 git 저장소가 아니고 파일도 없어 사용하지 않았습니다. 기본 탐색으로 코드 맥락이 없음을 확인했습니다.
