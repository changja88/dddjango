## Role Map

| Role | Responsibility | Related skills |
|---|---|---|
| Coordinator | Work scope, role assignment, result integration | `workflow-dddjango-subagents` |
| Domain Agent | Subdomain, bounded context, ubiquitous language, aggregate, invariant, domain event | `architecture-ddd` |
| Architecture Agent | Implementation pattern, dependency direction, port/adapter, transaction boundary | `architecture-implementation-patterns` |
| DB Agent | Schema, constraints, indexes, transactions, rollout constraints, backfill/index-lock risk | `architecture-db`, `implementation-django` |
| API Agent | REST contract, status code, Problem Details, `Idempotency-Key` API behavior, OpenAPI | `architecture-api`, `implementation-django-ninja` |
| Django Agent | ORM, service, selector, concrete migration files, transaction, settings/security/performance, template/static/web, templates/static files | `implementation-django`, `implementation-django-web`, `implementation-python` |
| Test Agent | TDD flow, pytest, fixtures, test doubles, API/integration tests, ownership of `tests/**` files | `implementation-tdd`, `implementation-test` |
| Review Agent | Code quality, design risk, missing verification, regressions | `implementation-cleancode` |

현재 디렉터리는 빈 폴더이고 git 저장소도 아니어서 실제 기존 파일 경로는 확인할 수 없었습니다. 아래 계획은 Django + Django Ninja 기준의 권장 구조입니다. 실제 프로젝트에 적용할 때는 기존 앱 이름과 라우터 구조에 맞춰 경로만 조정하면 됩니다.

## Sequential Fallback

Real subagents were not executed; this is sequential fallback in the role order below.

1. Domain: 주문 결제의 상태 전이와 불변식을 먼저 확정한다.
2. Architecture: 결제 게이트웨이, 트랜잭션, outbox 또는 `transaction.on_commit()` 경계를 정한다.
3. DB: 중복 결제 방지, idempotency 저장소, 제약조건, 인덱스를 설계한다.
4. API: 결제 요청/응답, 상태 코드, Problem Details, `Idempotency-Key` 동작을 고정한다.
5. Django: 모델, 서비스, 라우터, 스키마, 마이그레이션을 구현한다.
6. TDD/Test: 도메인 단위 테스트, API 계약 테스트, 동시성/idempotency 테스트를 먼저 작성한다.
7. Review: 결제 중복, 외부 부작용, 상태 전이 누락, 테스트 공백을 검토한다.
8. Integration: 각 role 산출물을 합쳐 충돌을 닫고 남은 리스크를 명시한다.

## Handoff Contract

**Domain Agent**

- Scope: 주문 결제 유스케이스, 상태 전이, 불변식 정의.
- Inputs Used: 사용자 요구사항, 기존 주문/결제 모델이 있다면 해당 도메인 코드.
- Decisions: `Order`는 `PENDING_PAYMENT -> PAID` 또는 `PAYMENT_FAILED`로만 결제 결과를 반영한다. `CANCELLED` 주문은 결제 불가. 같은 주문은 성공 결제를 한 번만 가질 수 있다.
- Files: May edit `orders/domain.py`, `orders/services/payment.py`; Must not edit migration/API files.
- Output: 상태 전이 표, 도메인 예외, `pay_order` 유스케이스 규칙.
- Risks: 부분 승인, 환불, 쿠폰/포인트 차감이 범위에 들어오면 별도 정책 필요.
- Required Follow-up: DB Agent가 성공 결제 1회 보장을 제약조건으로 닫는다.
- dddjango Checks: 도메인 규칙을 Router/Schema에 두지 않는다.

**Architecture Agent**

- Scope: dependency direction, gateway adapter, transaction boundary.
- Inputs Used: Domain output, 기존 service/repository 패턴.
- Decisions: 결제 게이트웨이는 port/interface 뒤에 둔다. DB transaction 안에서는 주문/결제 시도 저장까지만 처리하고, 외부 결제 요청은 `transaction.on_commit()` 또는 outbox worker로 넘긴다.
- Files: May edit `orders/services/payment.py`, `payments/gateways/base.py`; Must not edit tests except review notes.
- Output: service boundary와 side-effect timing 결정.
- Risks: 동기 결제 응답을 즉시 반환해야 하면 API UX와 트랜잭션 전략을 재검토해야 한다.
- Required Follow-up: API Agent가 비동기/동기 응답 계약을 확정한다.
- dddjango Checks: core policy가 PSP SDK, HTTP client, env var에 직접 의존하지 않는다.

**DB Agent**

- Scope: schema, constraints, indexes, locking, idempotency storage.
- Inputs Used: Domain/Architecture decisions.
- Decisions: `PaymentAttempt` 또는 `Payment` 테이블을 둔다. `order_id`, `idempotency_key`, `status`, `amount`, `currency`, `gateway_reference`, `failure_reason`를 저장한다. 성공 결제는 주문당 하나만 허용한다.
- Files: May edit `orders/models.py`, `payments/models.py`, `*/migrations/*.py`; Must not edit API Router.
- Output: 모델 필드, unique constraint, partial unique constraint, indexes, migration rollout note.
- Risks: DB가 partial unique index를 지원하지 않으면 애플리케이션 락 또는 별도 성공 결제 테이블 전략 필요.
- Required Follow-up: Test Agent가 중복 요청/동시 요청 테스트를 작성한다.
- dddjango Checks: idempotency와 성공 결제 중복 방지를 앱 코드만으로 처리하지 않는다.

**API Agent**

- Scope: REST contract, status code, Problem Details, OpenAPI.
- Inputs Used: Domain states, DB idempotency strategy.
- Decisions: `POST /orders/{order_id}/payments` 사용. `Idempotency-Key` 필수. 최초 요청은 `201 Created` 또는 `202 Accepted`, 같은 key 재시도는 같은 결과 재응답, 다른 payload 재사용은 `409 Conflict`. 결제 불가 상태는 `409 Conflict`, 검증 실패는 `422`, 인증 실패는 `401/403`.
- Files: May edit `orders/api.py`, `orders/schemas.py`; Must not edit model constraints.
- Output: request/response schema, error schema, OpenAPI impact.
- Risks: 기존 API 버전이 있으면 backward compatibility 확인 필요.
- Required Follow-up: Django Agent가 Router/Schema를 구현하고 Test Agent가 계약 테스트를 작성한다.
- dddjango Checks: 오류는 RFC 9457 Problem Details 형태로 통일한다.

**Django Agent**

- Scope: ORM, service, selector, migration, transaction implementation.
- Inputs Used: DB/API/Architecture outputs.
- Decisions: `pay_order(order_id, user, amount, idempotency_key)` 서비스가 transaction owner다. `select_for_update()`로 주문 row를 잠그고 결제 시도를 생성하거나 기존 idempotency 결과를 반환한다.
- Files: May edit `orders/models.py`, `orders/services/payment.py`, `orders/api.py`, `orders/schemas.py`, migrations; Must not edit unrelated apps.
- Output: Django models, service method, Ninja endpoint, migration.
- Risks: 기존 주문 상태 enum/금액 계산 위치를 확인해야 정확한 구현 가능.
- Required Follow-up: Review Agent가 Router에 도메인 로직이 새지 않았는지 확인한다.
- dddjango Checks: transaction 범위가 명시적이고 외부 side effect는 commit 이후 실행된다.

**Test Agent**

- Scope: TDD flow, pytest, fixtures, API/integration/concurrency tests.
- Inputs Used: 모든 role의 계약.
- Decisions: 먼저 실패 테스트를 작성한다. 핵심 테스트는 결제 성공, 이미 결제된 주문 거부, 취소 주문 거부, 같은 `Idempotency-Key` 재시도 동일 응답, 다른 payload 충돌, 동시 결제 1건만 성공이다.
- Files: May edit `tests/orders/test_payment_domain.py`, `tests/orders/test_payment_api.py`, `tests/orders/test_payment_concurrency.py`, factories/fixtures; Must not edit production code except test-only fixtures.
- Output: pytest test suite and expected failures before implementation.
- Risks: 실제 DB 락 테스트는 SQLite가 아닌 PostgreSQL 기반 CI가 필요할 수 있다.
- Required Follow-up: Coordinator가 로컬/CI에서 DB별 테스트 실행 범위를 분리한다.
- dddjango Checks: API 계약과 DB consistency 테스트를 둘 다 둔다.

**Review Agent**

- Scope: code quality, regression risk, missing verification.
- Inputs Used: final diff, test output, role decisions.
- Decisions: 수정 권한 없음, read-only review.
- Files: May edit none; Must not edit all files.
- Output: severity-ordered findings with file/line references.
- Risks: 테스트 미실행 또는 DB 종류 차이로 concurrency 보장이 검증되지 않을 수 있음.
- Required Follow-up: Coordinator가 findings를 수정 작업으로 분리한다.
- dddjango Checks: 결제 중복, transaction, idempotency, API error contract를 우선 검토한다.

## Integration Checklist

**Risky Write Consistency Block**

| Item | Plan |
|---|---|
| transaction owner | Django service `pay_order(...)` |
| locking strategy | 주문 row `select_for_update()` plus DB unique constraint |
| uniqueness/idempotency storage | `PaymentAttempt(idempotency_key, order, request_hash, response_snapshot)` |
| `Idempotency-Key` API behavior | 필수 header, 같은 key+payload는 동일 결과, 같은 key+다른 payload는 `409 Conflict` |
| external side-effect timing | DB commit 이후 `transaction.on_commit()` 또는 outbox dispatch |
| isolation/retry decision | PostgreSQL `READ COMMITTED` 기준 row lock + unique violation retry path |
| integration/concurrency test criteria | 동시 결제 요청 N개 중 성공 결제 1개, 나머지는 idempotent replay 또는 conflict |

구현 순서는 `tests -> domain/service -> DB constraints -> API adapter -> integration review`가 맞습니다. 우선순위 충돌은 domain invariant, data consistency, transaction/security, API compatibility, testability, Django idiom 순서로 해결합니다.
