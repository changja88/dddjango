칸을 클릭해 보세요

이 도식은 dddjango 플러그인(v2.8.0)이 BC 하나를 짓는 전 과정입니다. 특히 다음 네 칸에 자세한 내용이 있습니다.

  • 슬라이스 분할·배차 — 누가, 어떤 기준으로 작업을 나누는지
  • 규율 감사 — AI 감사자가 정확히 무엇을 보는지
  • 기계 검사 — 무엇을 기계적으로 검사하고 누가 실행하는지 + 검사기 27종 전체 목록
  • 정지·질문 — 스스로 멈추는 두 장치

시작

입력: 사용자 요청 + 지시서(요청문·명세) + 표준 규정

레인 세션에서 /dddjango 명령이 실행되면 Coordinator가 파이프라인 전체(범위 확정 → 설계 → 테스트 → 구현 → 판정)를 지휘합니다. 옛 코드는 보지 않고 지시서만으로 다시 짓는 것이 원칙입니다(클린룸).

범위 확정 (G0)Coordinator

첫 번째 게이트 — 사용자 승인 필수

  • 이번에 지을 범위(BC·유스케이스)를 사용자와 합의하고 scope.md로 고정
  • 시작 전에 검사기 27종을 1회 돌려 옛 코드의 빚(기존 위반)을 목록화 — 「지금 정리할 것」과 「미룰 것」을 사용자가 결정
  • 시작 전 점검(preflight): 지시서와 검사기·표준이 충돌하지 않는지 8+1항목 사전 대조 — 헛 라운드 예방

설계 작성design-architect

사용 스킬: architecture-ddd · architecture-api · architecture-db

  • 승인된 범위를 받아 도메인·API·DB 세 관점을 하나의 설계 명세(design-spec.md)로 통합 작성
  • 어떤 테스트를 새로 쓰고/재사용하고/버릴지 테스트 입장 표까지 설계에 포함
  • 리뷰 4인의 지적을 반영·중재해 최종 명세를 만든다 — 코드는 쓰지 않음

설계 리뷰 — 4인 병렬4개 AI 동시 실행

한 명세를 네 관점이 동시에(병렬) 독립 검토 — 서로의 노트를 보지 않음

리뷰어보는 관점
design-review-ddd도메인 — 애그리거트 경계·불변식·도메인 이벤트
design-review-apiAPI 계약 — 경로·상태코드·오류 모양·OpenAPI
design-review-db데이터 — 인덱스·제약·트랜잭션·마이그레이션 안전
discipline-reviewer규율(경량) — 테스트 입장 표·소유권·금지 항목

파이프라인 전체에서 병렬 실행은 이 한 곳뿐입니다(나머지는 전부 직렬).

설계 게이트 (G1)Coordinator

두 번째 게이트 — 사용자 승인 필수

  • 리뷰 반영이 끝난 최종 설계 명세를 사용자에게 제시하고 승인받는다
  • 테스트 입장 표(추가/재사용/유지/삭제/거부)를 항목별로 나열 — 미정(pending)이 하나라도 있으면 구현으로 못 넘어감
  • 승인된 명세는 이후 테스트와 코드의 단일 근거가 된다

테스트 먼저acceptance-tester

사용 스킬: discipline-tdd · implementation-test — 구현을 보지 않는 블랙박스

  • 옛 코드를 안 보고 짓기 때문에, 바깥에서 보이는 동작(HTTP 응답·공개 계약)을 실패하는 테스트로 먼저 고정
  • 승인 입장 표에서 「추가/변경」으로 결정된 외부 계약만 Red로 만든다
  • 이후 구현은 「이 테스트를 통과시키는 일」로 좁혀진다

슬라이스 분할·배차Coordinator

근거: 규정서 Phase 2 3~4단계 — 구현을 몇 조각으로 나눠 한 조각씩 맡길지를 Coordinator가 결정

나누는 기준 (규정 문면):

  • 제품 구현 단위로 슬라이스 목록을 도출하고, 각 슬라이스에 관련 테스트 입장 행을 붙인다 — 테스트 커버리지 목표만으로는 슬라이스를 만들지 않음
  • 빚 정리는 슬라이스 0: 범위 확정 때 「지금 정리」로 결정된 옛 코드 빚은 동작 불변의 리팩터링 슬라이스로 만들어 맨 앞에 둔다 — 리팩터링과 기능 변경을 한 슬라이스에 섞지 않는다
  • 의존 순서(아래층부터): 실제 라운드에서는 도메인 → 응용(유스케이스) → DB·어댑터 → API → 관리자 화면 순으로 잘림 — 위층이 아래층 산출물 위에 서기 때문

배차 방식:

  • 슬라이스마다 coder를 호출 — 한 개 끝나야 다음 개(직렬). 슬라이스가 3개 이상이면 슬라이스마다 경량 규율 감사를 끼워 넣음
  • 같은 파일을 두 역할이 동시에 편집하는 것은 규정이 명시 금지(acceptance-tester → coder 순차 강제)
속도 관점: 직렬이 필연인 부분은 의존 사슬(아래층→위층)뿐이고, 의존이 없는 슬라이스 쌍과 감사 대기까지 전부 직렬인 것은 관행 — 병렬화 후보로 검토 중.

슬라이스 구현coder

사용 스킬: implementation-python·django·django-ninja·django-web·test + discipline-cleancode·houserules·tdd

  • 배차받은 슬라이스를 단위 Red → Green → Refactor로 구현 — 자기 소유(도메인·응용·DB·어댑터) 테스트만 편집
  • 구현 중 관련 검사기·테스트를 수시로 실행해 자기 검증(기계 검사가 슬라이스마다 내장 실행되는 이유)
  • Red를 위해 만든 임시 비계(loader·skip 등)는 첫 Green 직후 즉시 제거

규율 감사discipline-reviewer

읽기 전용 AI 감사자(Read·Grep만 — 코드 수정·검사기 실행 불가) · 슬라이스 3개 이상이면 슬라이스마다 경량 감사 + 마지막 홀리스틱 1회

정확히 무엇을 보나 — 기계 검사가 못 잡는 「의미」를 전담:

  • 테스트 변경 대조: 테스트 수정 하나하나가 승인된 입장 표의 결정과 일치하는가, 각 테스트가 고유한 실제 실패를 검증하는가(형식만 있는 빈 테스트 적발)
  • 몰래 쓰기 0: 「재사용/거부」로 결정된 행에 새 테스트를 몰래 쓰지 않았나 · 「유지」 행은 무편집인가 · 「삭제」는 승인된 대상만인가
  • 재조직 보호: 파일 이동·이름 변경 시 전후 보호(같은 동작을 같은 강도로 지키는가)가 유지되는가
  • 비계 잔존: 첫 통과용 임시 코드(skip·가짜 구현)가 남아 있지 않은가
  • 보존 규칙: 기존 migration 이력과 관련 테스트가 훼손되지 않았는가
  • 클린코드·하우스룰 의미 변종: 이름과 동작 불일치, 캡슐화 누수, 규칙을 글자로만 피한 코드

지적 반송처: 외부 계약 테스트 문제 → acceptance-tester · 구현 문제 → coder · 설계 오류 → 설계 게이트로 반송

기계 검사Coordinator가 직접 실행

검사기 = AI가 아니라 파이썬 스크립트 27종(규칙 ~675개). Coordinator가 레인 저장소 루트에서 터미널 명령으로 1회씩 실행하고 종료 코드·진단을 읽는다. 실행 시점 3곳: 시작 전 빚 스캔 · 구현 중 coder의 자기 검증 · 최종 판정 직전 공식 실행(판정본)

판정 방식 — 두 계열:

  • 차분 22종: 위반이 나와도 옛 코드 위반과 새 위반을 구분해, 이번 빌드가 새로 만든 위반만 정지 사유(옛 위반은 «legacy 잔존»으로 보고만)
  • 직접 차단 5종(#2·#5·#6·#15·#16): 위반이면 구분 없이 즉시 정지. 그리고 27종 전부, 검사기 자체가 분석 불능(exit 1)이면 즉시 정지 — 이 조합이 products 3차에서 codex를 막은 규정 결함 지점

최종 판정 (G2)Coordinator

세 번째 게이트 — 사용자 승인 후 커밋

  • 기계 검사 27종 공식 실행 + 차분 게이트(앵커 대비 「이번에 새로 생긴 위반」만 집계) + 전체 테스트 실행
  • 증거(모든 명령·종료 코드·진단)를 축약 없이 모아 배너로 제시 — 사용자가 승인하면 커밋
  • 새 위반 0 + 전체 테스트 green + 규율 감사 blocker 0이 통과 조건

정지·질문Coordinator → STOP 문서

스스로 멈추는 두 장치 — 정지는 실패가 아니라 지시서 결함을 찾아낸 수확

  • 정지 후 질문: 답이 지시서에 없으면 추측하지 않고 어느 단계에서든 멈춰 STOP 문서(STOP_FOR_USER_APPROVAL.md)로 결정 공백을 기록하고 사용자에게 묻는다
  • 수렴 회로: 재설계를 반복하며 작업 범위가 계속 커지면 강제로 멈춘다 — 끝없는 소용돌이 방지

products 3차 codex의 정지도 이 장치가 정상 작동한 것: 규정 충돌을 발견하고 4축으로 분류해 기록한 뒤 멈췄다.
