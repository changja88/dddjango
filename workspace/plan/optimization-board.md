**읽는 법**
- **실행시간** = AI가 실제로 일한 시간(승인 대기 등 멈춘 시간 제외). ✱ = 조건이 달라 시간 비교 대상에서 제외.
- **01~06 칸** = 레이어별 실행 시간(`plugin-pipeline.html` 도식의 층 번호: 01 지휘·게이트 / 02 설계 작성 / 03 설계 리뷰(병렬) / 04 테스트 / 05 구현 / 06 구현 검사). **2.8.0부터** 세션 기록의 하위 AI 호출 시각으로 실측 — 이전 행은 기록이 없어 ➖.
- **완료**: 완주 = 끝까지 감 · 정지 = 문제를 발견하고 스스로 멈춤(정당한 정지) · 중단 = 우리가 멈춤.
- **퀄리티**: 통과 = 기계 검사 3종 전부 통과 + AI 심사 치명 결함 0 · 불통과(사유) · ➖ = 정지·중단이라 판정 없음.
- **최적화/속도 칸** = 그 버전을 만들 때 반영한 개선(직전 시도의 교훈). 없으면 «없음» 명시. 〃 = 윗줄과 같음.

## 표가 보여주는 것 (2026-08-15 시점)

- **최적화(퀄리티) 작업은 매 버전 있었다** — 대부분 «실행해 보고 결함 발견 → 수정»의 반복.
- **속도 개선 작업은 2.5.0과 2.7.0 단 두 번** — 이후 3버전 연속 «없음».
- 레이어 실측(2.8.0 claude)이 가리키는 다음 표적: **05 구현(~60%)** → 구현자 병렬화 레버,
  **02 설계 왕복 4회(1h17m)** → 개정 횟수 줄이기.
- 아직 안 쓴 속도 개선 후보: ① 도구 사용 승인을 미리 허용해 왕복 제거(효과 최대)
  ② 구현 작업자를 여러 명 동시에 돌리기 ③ 시작 전 자동 점검으로 헛 라운드 줄이기
  — 2.8.0 라운드가 끝나면 이 중에서 골라 투입한다.
- products 3차 codex 정지가 새로 드러낸 퀄리티 결함(다음 버전 수정 후보): 검사기 4종이
  승인 범위(이번에 만든 코드)만이 아니라 **옛 코드 전체를 함께 검사해** 옛 위반 때문에
  통과가 원천 불가능해지는 문제 — 같은 조건에서 claude 레인은 통과 판정을 내려 두 레인의
  판정이 갈렸다(규정 문장 자체의 결함 증거).
