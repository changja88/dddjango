## A0 deps 판정 시점은 조정자가 밝힌다(A2 · A4 의 바탕)

- 지금: 도구가 이 폴더 `refactor-scope.md` 의 «G1 변경판 확정» 줄 유무로 G0 / 파견 직전을 짐작한다. 같은 폴더를 다시 쓰는 새 실행 · 폐기 뒤 새 실행은 파일만으로 잇기와 못 가른다(②) · 잇기 R1 도 «파견 직전»으로 읽힌다.
- 고침: `deps <bc> --out … --at <new|continue|dispatch>` — **필수**(빠지면 exit 1 · fail-closed). 조정자는 언제나 자기가 어느 자리인지 안다.
  - `new` — R1, 이번 시도가 새 실행일 때(새 폴더 · 끝난 실행 뒤 · 폐기 · 승인됨 뒤). 도구는 이 폴더의 앞 실행 기록(G1 확정 · 명세 다른 BC 편집 목록 · 앞 실행 G0 승인 값)을 판정 시점 · 맞물림 · 우리 경로에 쓰지 않는다 → G0 판정. 다만 다른 작업 트리에 든 «이 실행의 사본»(같은 폴더 · 같은 실행 줄)을 빼는 규칙은 앞 실행 줄로 그대로 둔다 — 끊으면 버린 앞 실행의 커밋된 사본과 겹쳐 G0 정지에서 못 나온다(그 가림은 새 G0 승인 뒤 실행 줄이 바뀌어 파견 직전 deps 가 잡는다). **구현 검토 보정(10-28)**: 그 트리의 자기 변경이 아닌 옛 사본(MH 판으로 판정)이 이 실행 폴더와 이름이 같으면 그 MH 판은 이 폴더의 앞 기록이거나 이 실행 자신이라 활성 실행에서 뺀다(`요약:` `이 폴더 옛 사본 뺌 n`) — 그 폴더가 정말 다른 곳에서 돌면 그 트리의 자기 변경으로 디스크 판정에 잡힌다(재현: 버린 앞 실행 사본 · 이 실행 커밋본이 파견 직전 자기와 겹침 · 뒤의 둘은 2.28.0 도 같음).
  - `continue` — R1, 이번 시도가 잇기일 때. 이 폴더에 끝나지 않은 실행 줄이 있어야 한다(없으면 exit 1). 판정 셈은 지금(2.28.0)과 같다 — G1 확정이 없으면 G0 판정 · 있으면 파견 직전 판정과 같은 셈. 다만 맞물림(먼저 G0 승인한 쪽이 나아감)은 G1 확정 유무와 무관하게 이 실행 줄의 G0 승인 값으로 건다 — 이 실행은 이미 다른 레인에 보이므로, 늦게 G0 승인한 앵커 없는 리팩토링 실행을 세면 그 실행도 파견 직전에 이 실행을 세어 서로 착륙을 기다린다(검토 2회 재현: 2.28.0 은 2 · 2 맞기다림 · 원형은 0 · 2). 설계 낡음(A4)은 돌지 않는다.
  - `dispatch` — Phase 2 첫 파견 직전 · G1′ 승인 직후 · 파견 정지 잇기. 끝나지 않은 실행 줄과 G1 확정이 있어야 한다(없으면 exit 1). 파견 직전 판정 + 낡음(A4).
  - **G0 정지 재개**의 값은 «지금 실행 선택 답»으로 고른다 — 잇기면 `continue` · 그 밖(G2 끝 뒤 자동 새 실행 포함)은 `new`(정지 절에는 시도 종류가 적히지 않는다 · 최신 실행 줄이 미종료면 실행 선택을 반드시 묻으므로 답이 늘 있다).
- 실행 줄 · G1 확정은 삼키지 않는 읽기로 읽는다 — 이 폴더 `refactor-scope.md` 를 UTF-8 로 못 읽으면 exit 1(파견 직전이면 파견 정지 · R1 이면 G0 정지 — 2.28.0 과 같은 fail-closed).
- `--at` 은 이 프로세스의 입력일 뿐 아무것도 쓰지 않는다 — 다른 레인의 판정은 바뀌지 않는다.
- 규칙 글(graph-owned): deps 블록 R-3625 개정(세 값과 고르는 법) · G0 정지 재개(:287) · 파견 정지 블록 R-3676(잇기는 `--at dispatch`) · Codex 의미 미러.

## A1 ① 거짓 순환 — 설명 글 키워드 인자

- 원인: `refactor_audit.py` `DepsScan._scan`(4185-4188)이 문장 자리 밖 str 상수 가운데 `/` 를 품은 것을 모두 HTTP 소비 글(`literals`)로 싣는다. 2.27.1 은 docstring · 주석만 뺐다.
- 고침: 새 도우미 `_doc_kwarg_ids(tree)` — `ast.Call` 의 키워드 이름이 닫힌 목록 `{"description", "summary"}` 인 값 아래 `ast.Constant` id 를 모아 `_scan` 에서 뺀다(f-string 조각 · `_()` 감싸기 포함).
- 그대로 세는 것: 호출 인자 · 경로 상수 · `url=` · dict 값(이름이 description 인 dict 키 포함 · `openapi_extra` 안 description 키 포함) · 모듈 상수를 `description=` 에 넘긴 꼴 · `title=`.
- **수락 조건(배포 전)**: 현장 저장소 사본(읽기 전용 복제 · 작업 폴더 안)에서 고친 도구로 deps 를 다시 재 현장 순환 성분 2 가 풀리는지 본다. 안 풀리면 남은 꼴을 보고 이름 하나 + 사례 하나씩 더한다.
- 규칙 글: 무변.
- 릴리즈 노트: 설명 글만으로 «HTTP 소비자»가 되던 파일이 빠진다 — 진행 중 실행의 `changes --gate`(다른 BC 편집 목록 대조)와 `check-verdict`(다른 BC 몫 재분류)가 옛 판과 다를 수 있다.

## A2 ② 같은 폴더 새 실행의 R1

- 원인: R1 deps 는 새 실행 G0 승인 전이라 `refactor-scope.md` 가 앞 실행 판이다. `cmd_deps` 5631 이 앞 실행 «G1 변경판 확정»을 집어 «파견 직전» · `mine` = 앞 실행 G0 → 늦게 G0 승인한 이웃을 뺀다(fail-open). 앞 실행 G1 기록이 판형 밖이면 실행 불능도 된다.
- 고침: A0 `--at new` 가 앞 실행 기록을 끊는다(판정 시점 · `mine` · 앞 실행 명세 다른 BC 편집 목록 — 이 실행 사본 빼기만 남김).
- 고르지 않은 안: 조건부 깃발 `--new-run`(빠뜨리면 지금 결함 그대로 · 잇기 시도의 G0 정지 재개에 붙이면 늦은 이웃과 서로 착륙을 기다림 — 검토 재현) · R0′ 에서 `refactor-scope.md` 새로 쓰기(기능 모드 공유 규칙의 쓰는 때를 바꿈) · 앞 실행 줄에 폐기 표식(다른 레인 활성 판정까지 번짐).

## A3 ③ 공급자 상태 — 도는 실행 표기

- 원인: `_supplier_state` 5576 이 G2 리팩토링 실행 줄을 이 트리 파일 전체(`# 앞 실행` 절 포함)에서 찾는다. 공급자 실행이 다른 작업 트리에서 돌면 이 트리 사본은 앞 실행 G2 판이라 «정리»를 낸다.
- 고침(표기 · 순서 예외 질문은 늘리지 않는다): 공급자 상태를 `_active_runs` 결과(모든 작업 트리 · MH 판 · 끝 표식 판정 그대로)에서 고른다 — 리팩토링 실행이고 그 실행의 대상 BC(실행 폴더 이름 · `plan.md` BC — file-plan BC 와 섞지 않는 따로 칸)가 공급자인 것.
  - 겹침으로 선 실행이면 `미정리(도는 실행 <폴더>)` — 정지는 이미 겹침이 정한다(표기만 바로잡음).
  - 맞물림으로 뺀 실행이면 `도는 실행(맞물림 — 이 실행 뒤) <폴더>` — 순서는 맞물림이 이미 정했으므로 R-3627 순서 예외를 묻지 않고 `unsettled` 셈에 넣지 않는다(검토 2회 I5 재현: 묻고 «이 실행 정지»를 고르면 공급자 파견 직전 deps 가 우리를 세어 맞기다림 — 같은 트리의 G2 없는 공급자로 2.28.0 에도 있던 어긋남).
  - 없으면 지금 규칙(정리(재상정 n) → 못 읽음 → 미정리).
- R0′~G0 승인 전 공급자(실행 줄 아직 없음)는 정리 그대로 — «G0 승인 전 실행은 안 보임»과 같은 선.
- 규칙 글(graph-owned): R-3627 «미정리» 정의 + «도는 실행(맞물림 — 이 실행 뒤)»는 묻지 않음.
- **이번 판 밖(받아들인 한계 · 2.28.0 과 같음)**: 다른 작업 트리에서 G2 로 끝났지만 main 에 아직 착륙하지 않은 실행은 deps 에 안 보인다(검토 2회 I2). 3판에서 «MH 에 폴더 없음 → 착륙 전»으로 셌더니 착륙 뒤 폴더를 치운 main · squash 착륙 · 그 가지에서 갈라진 레인에서 거짓 겹침이 났고(3회 I-1 재현 — 옛 판 0 → 2), 같은 폴더를 다시 쓰는 두 번째 리팩토링에서는 빈틈이 그대로였다(3회 I-2 재현). 대안 «그 트리의 미착륙 코드 경로»도 squash 착륙 뒤 main 이 같은 파일을 다시 고치면 거짓 겹침이 난다 — 배포 직후 오래된 작업 트리들에서 대량 정지 위험. 운용으로 막는다: G2 승인 레인은 바로 착륙하고, 엮인 레인은 그 착륙 뒤에 띄운다(릴리즈 노트 · 캠페인 계획 «앞 차수가 모두 착륙한 뒤»). 다음 판 후보로 적는다.

## A4 ④ 파견 직전 낡음

- 원인: 조정자 «파견 정지» 재개(R-3676)의 무변 조건이 대상 BC 경로의 작업 트리만 보고(main 착륙은 안 봄), 정지 없는 첫 파견에는 그런 확인조차 없다. deps 는 활성 실행만 보고 G2 를 받은 실행이 착륙시킨 변경은 재지 않는다.
- 고침(도구 · `--at dispatch` 에서만 · 실행 줄에 `build_anchor` 가 없을 때만):
  - 공통 셈:
    - 커밋 차분 = `<기준>..HEAD` ∪ (MH ≠ HEAD 면) `<기준>...<MH>` · 좁히기는 pathspec 으로만(하위 폴더 프로젝트에서 글자 비교 0 건 fail-open 방지) · `--no-renames` 로 옛 · 새 경로 모두.
    - **내용 같음 빼기**: 세 점 차분이 낸 경로마다 `git diff --quiet <기준> <MH> -- <경로>` 가 같으면 뺀다 — 레인이 main 착륙분을 체리픽 · squash 로 받아 조상 관계가 없어도 거짓 낡음을 내지 않는다(검토 2회 I3 재현).
  - **대상 낡음** — 기준 = 이 실행 audit `plan.md` 의 `- HEAD` · 범위 = `application/<bc>/` · 커밋 차분만.
    - 작업 트리 미커밋은 보지 않는다 — 3판에서 «audit `BC 미커밋 변경 0` 이면 작업 트리 포함 · 아니면 대상 기준 모름»으로 넣었더니, 사용자 작업 중 파일 · ignore 안 된 `.DS_Store` 같은 미커밋은 폐기로 지워지지 않아 «폐기 → 새 audit 이 미커밋을 셈 → 대상 기준 모름 → 폐기»가 끝없이 돌았다(3회 C1 재현). 첫 파견 직전의 사용자 미커밋은 2.28.0 도 보지 않고, 파견 정지 재개의 지금 무변 조건(R-3676 · 작업 트리)은 그대로 남는다 — 옛 판보다 약해지지 않는다.
    - 기준을 못 읽음 · 못 풂 → `대상 기준 모름: <사유>`(대상 낡음과 같은 처분 — 새 audit 이 기준을 다시 적으므로 되풀이되지 않는다).
    - 있으면 `대상 낡음: <경로> …` · exit 2. 조정자 처분: **main 받기 → 폐기 → 새 실행**(앵커 전이라 대가 없음 · 새 audit 이 받은 main 위에서 뜬다 — main 을 안 받고 폐기하면 새 audit 도 레인 HEAD 에서 떠 다시 대상 낡음이 서는 순환을 막는다 · 검토 2회 B1 재현 · 3회 재현으로 닫힘 확인).
    - «main 받기» = 레인에서 `git merge --no-edit <MH>` · 충돌이면 `git merge --abort` 뒤 정지(재개 조건: 사용자가 충돌을 푼 뒤) — 앵커 전 레인은 보통 깨끗하다.
  - **설계 낡음** — 기준 = 이 실행 설계 기준선(마지막 실행 경계 뒤 마지막 `## pre-gate 예보` 절의 `기준선 SHA`) · 범위 = 명세 file-plan 경로 ∪ 다른 BC 편집 목록 경로 ∪ 공급 면 경로(deps 가 이미 셈하는 `face_paths`). 커밋 차분만 본다(G1 전부터 있던 미커밋이 G1′ 로 지워지지 않아 되풀이되는 것을 막는다 — 1회 M2).
    - 있으면 `설계 낡음: <경로> …` · exit 2. 조정자 처분: 수정 모드 2번(G1′) — main 착륙분을 먼저 받고 바뀐 파일 · 차분을 architect 입력에 싣고, G1′ 의 pre-gate 는 캐시 건너뜀 없이 `--base HEAD` 로 돈다(새 예보 절 = 새 기준선).
    - 공급 면이 BC 전체로 넓혀진(`widened`) 공급자의 경로만 바뀌었으면 `설계 낡음(넓힌 공급 면 — 보고만)` · exit 0 — main 이 바쁜 공급 BC 에서 착륙마다 사용자 재승인이 되풀이되는 것을 막는다(file-plan · 다른 BC 편집 경로 · 좁은 공급 면이 바뀌면 그대로 G1′). 놓치는 쪽의 교환이므로 그 보고 줄은 coder 파견 입력과 G2 배너에 싣는다.
  - **설계 기준선 모름**(출력 `설계 기준선 모름(<갈래>): …` · 갈래 다섯 — 구현 검토 보정 10-28):
    - «명세 없음» · «예보 절 없음» · «기준선 SHA 못 풂» · «차분 못 잼» → 설계 낡음과 같이 G1′(pre-gate `--base HEAD` 가 새 예보 절을 쓴다).
    - «경계 값 다름»(판정은 `_spec_doubt` 를 다시 쓴다 — 경계 행 없음 + 기준선 행 ≥ 2 → 모름 · L121 «없으면 전부»와 맞춤) → 실행 선택 «폐기»(앵커 전이라 대가 없음).
    - 파견 정지로 두지 않는다 — 재개 조건을 조정자가 이룰 수 없어 끝없이 같은 정지로 돌아온다(검토 2회 I4).
  - 차례: 겹침 · 보류가 있으면 파견 정지가 먼저 · 그다음 대상 낡음(폐기)이 설계 낡음(G1′)보다 먼저 · 줄은 모두 낸다.
- 조정자 무변 조건(graph-owned): G0 정지 재개(:287)와 **앵커 없는** 파견 정지 재개(R-3676)의 «무변»에 `<audit HEAD>...<MH> -- application/<bc>/`(내용 같음 빼기 포함)이 비어 있음을 더한다 — main 에만 대상 BC 착륙이 있으면 Phase 1 · G1 을 다시 치르기 전에 잡아 «main 받기 → audit 다시»로 간다(검토 2회 B1). 앵커 있는 파견 정지는 지금 규칙(승인 병합 → G1′) 그대로 — 정지 종류별로 나눠 쓴다(3회 s1).
- 받아들인 한계(릴리즈 노트):
  - 앵커 뒤(G1′ 재발화)는 이 갈래 밖 — 지금 규칙(대상 BC 가 바뀌면 G1′)이 사실상 덮는다. 슬라이스가 대상 BC 를 건드리지 않은 드문 경우는 남는다.
  - 첫 파견 직전 대상 BC 의 사용자 미커밋은 보지 않는다(2.28.0 과 같음 · 위).
  - MH = 로컬 주 작업 트리 HEAD 다 — 원격(PR 병합)으로만 착륙하고 로컬 main 을 당기지 않았으면 못 본다 · 레인이 주 작업 트리이고 받은 변경을 커밋하지 않았으면(`merge --squash` 미커밋 · 충돌 중 병합) 못 본다.
  - 배포 때 G1 을 받고 파견 전인 실행은 새 판의 첫 `--at dispatch` 에서 대상 낡음 · 설계 낡음으로 폐기 · G1′ 될 수 있다.
- 규칙 글(graph-owned): 파견 정지 블록 R-3674/R-3676 문면 + 새 R-ID 하나(대상 낡음 · 대상 기준 모름 · 설계 낡음 · 넓힌 공급 면 · 설계 기준선 모름의 처분과 차례).
- 픽스처: 기존 파견 직전 사례(`_dispatch_own`)가 예보 절과 `--at dispatch` 를 쓰게 고친다 — 기존 기대 exit 무변 확인.

## A5 S 고칠 시험이 실행 정의에 실렸나 — G1 관문으로

- 원인: 조정자 «시험 명령 기록 · 지원 확인»(R-3623 «질문 없음» · R-3624)은 기존 전체 suite 를 글로 고정만 하고, 그 정의가 이 실행이 고칠 시험을 싣는지 대조하지 않는다.
- 고침(도구 · `changes` 계열): G1 관문(`changes <폴더> --candidate` 와 `--gate`)이 결속한 지원 기록의 수집 파일과 **이 실행이 실제로 고칠 시험 모듈**을 견준다. 빠진 모듈은 **확인 필요** 줄 `실행 정의 밖이거나 skip 인 편집 시험: <경로>` 로 낸다(관문 red 가 아니다 — 지원 기록은 «정의 밖»과 «정의 안인데 모듈 skip(importorskip 등)»을 못 가르고, skip 모듈을 red 로 두면 개명 전파라 피할 수 없는 편집에서 나갈 길이 없다 · 3회 I-3 재현).
  - 고칠 시험 모듈 = 명세 file-plan · 다른 BC 편집 목록 · 입장 표 owner/path(`경로::케이스` 와 `경로.py` 둘 다 읽는다 — retain 행은 `::` 가 없다) 가운데 **이미 있고 · 프로젝트 `python_files` 에 맞고 · 정적 케이스가 있는** 시험 모듈.
  - 대상 밖: conftest · 팩토리 · fake · 시험 자료(JSON 등)는 수집 파일이 아니다 — 그 파일의 실림은 G0 관찰 범위 · 창 close 가 본다(검토 2회 I6 재현) · 0F 이동의 새 경로(아직 없음)도 창 close 가 본다.
  - 입장 표 `add` 행의 새 파일은 `behavior_guard._collectible`(프로젝트 `python_files` · `testpaths`) 판정으로 수집 꼴 밖이면 같은 확인 필요 줄 `수집 꼴 밖 새 시험 파일: <경로>` — 3판의 «목적지 폴더 수집 0 이면 알림»은 수집 가능한 새 하위 폴더에서 늘 울리고 `check_new.py` 꼴은 놓쳐 걷는다(3회 s3 재현).
  - G0 레인 전체(고치지 않을 HTTP 소비 시험까지)가 아니라 고칠 모듈만 본다 — 모듈 skip · 수집 제외 파일 때문의 영구 정지와, 고치지 않을 큰 · 유료 시험 타깃을 붙이는 일을 피한다.
  - 같은 지원 기록에 결속하므로 G1 이 묶는 정의와 대조한 정의가 늘 같다.
- 조정자 규칙(graph-owned · 해소 판정 절차 · G1 블록 + 새 R-ID) — 확인 필요 줄이 있으면 G1 배너 전에:
  - 그 파일을 모으는 기존 프로젝트 명령(Makefile · README · CI)이 있으면 시험 명령에 보태 지원 확인을 새 시각 폴더로 다시 돌고 관문을 다시 돈다(기존 suite 의 일부라 묻지 않는다 · 다른 settings 를 쓰는 타깃은 명령 줄 안에 `--ds=` · `env X=Y pytest …`).
  - 없거나 다시 돌아도 남으면(이 환경에서 모듈 skip 포함) G1 배너에 «이 실행이 고칠 시험 n 개는 실행 정의에서 돌지 않는다: <경로>»를 싣고 사용자 승인으로 넘긴다 — 2.28.0 은 말없이 넘어갔다.
  - 수집 꼴 밖 새 시험 파일은 architect 에 반송해 이름 · 자리를 고친다.
  - 다시 돈 지원 확인이 exit 2 · 1 이면 R-3624 와 같은 처분(정지 · 재개 조건 같음).
- 덧(R-3623 글): «전체 suite 가 여러 타깃으로 나뉘었으면 모두 옮긴다»를 시험 명령 기록에 한 줄.
