# dddjango 2.27.3 — #473 은 상대 창구 코드가 돌 수 있는 try 에만 기저 예외를 요구한다(F4-111) (10-26)

## 바탕
- 바탕: main(dddjango 2.27.2 봉인 뒤). 2.27.3 은 patch — 검사기 판정 범위 고침 · 진단 자리 표기(새 규칙 · 새 질문 · 새 기록 칸 · 배포 md · 그래프 문면 변경 없음).
  매니페스트 판은 `make release` 가 올린다. 봉인(`manifest_seal`)은 같은 판에 함께 들어가는 고침과 묶어 한 번 한다. dddjango-web 무변.
- 결함(장부 F4-111): check-context-isolation #473 이 상대 창구(OHS)를 import 하는 ACL 파일의 **모든** try 에 «마지막 except 에 상대 창구의 기저 예외» 를
  요구했다. 받은 글을 `json.loads` 로 읽기만 하고 `except ValueError` 로 끝나는 try 가 붉었고, 진단이 파일 단위라 어느 try 인지 찾기 어려웠다.
- 판정: 결함. 근거 — 트리 개정 명세 #473 은 «파일 안 모든 try» 를 말하지 않고, 근거 결정(D36 — 상대 BC 의 예외가 ACL 을 지나가지 못하게)은 창구 예외가
  닿는 try 에만 걸린다. #473 문면은 배포 md · 온톨로지 그래프에 없다(번호 나열뿐) — 규범 개정 · LEDGER · rulepack 재소성 불필요.
- 설계: 1판(재현 · 현장 분류 · 시제품 «창구를 부르는 try 만») → 적대 검토(다시 설계 · 차단 1 · 중요 4 · 사소 4) → 검토가 지은 단순한 판(K «알려진 바깥만 면제»)으로
  갈아탐 → 구현(K + 검토 지적 + 구현 중 찾은 놓침 셋).

## 고침
- 판정 방향: 기저를 안 잡는 try 는 그 몸통에서 **상대 창구 코드가 돌 수 없음이 글자로 보일 때만** 면제하고, 나머지는 지금처럼 요구한다(모르면 돈다고 본다).
  돌 수 없다 = 몸통(기저를 잡고 다시 던지지 않는 안쪽 try 의 몸통은 뺀다)에서
  1. 창구 · ACL 안(상대 import · `anticorruption_layer` 경로) import 이름 · 같은 파일 함수/클래스 이름이 글자로 없고(인자 · 람다 안 포함 — 콜백이 잡힌다),
  2. 모든 호출 · `with` · 반복 · `await` · `yield from` 대상과 속성을 읽는 값의 뿌리가 «알려진 바깥» 이고
     (내장 · 창구 밖 import(상대 계약 타입 포함) · 그것들로만 지은 모듈 상수 — 파일 안에서 다시 묶인 이름은 바깥이 아니다),
  3. 넘긴 값을 끝까지 읽거나 넘긴 함수를 부르는 내장(`list` · `tuple` · `dict` · `sorted` · `sum` · `any` · `enumerate` · `zip` · `map` · `filter` 등)에
     바깥 아닌 맨 이름을 넘기지 않는다.
  이름 · 값을 거쳐 아무 코드에나 닿는 내장(`super` · `type` · `getattr` · `hasattr` · `setattr` · `delattr` · `vars` · `next` · `iter` · `anext` · `aiter` · 동적 실행)은
  «알려진 바깥» 이 아니다.
- 진단: `<파일>:<try 줄>` + 옛 판정문 + 꼬리 « — 상대 창구가 돌 수 있는 try · `<클래스.함수>`»(모듈 수준 try 는 `모듈`). try 마다 한 줄, 소스 차례.
  기저 import 가 아예 없는 파일의 파일 단위 줄은 그대로다.
- 판정 도구(`_WindowTry`)는 기저를 안 잡는 try 가 있는 파일에서만 짓는다.
- Codex byte 미러 · `pregate_symbol_kinds.json` 재소성(검사기 소스가 바뀜) · 트리 개정 명세 #473 행에 날짜 붙은 «대상 try 부칙» 한 문장.

## 적대 검토 반영
- 차단(조용한 놓침): 1판 시제품은 «창구를 부르는 try» 를 찾아 따라가는 판정이라, 같은 파일 객체 · 주입 객체 · 매개변수 객체의 메서드 · `super()` · 콜백 인자 ·
  property · `with` · 데코레이터 · 같은 이름 재대입 · 창구가 돌려준 생성기를 도우미가 읽는 꼴(진행 중 작업의 스트리밍 ACL 에 실제로 있다)을 «안 부름» 으로 갈라
  기저 요구를 뺐다 → 판정 방향을 뒤집은 단순한 판(위 «고침»)으로 갈아탔다. 같은 놓침 탐침 22 꼴 모두 붉다.
- 중요: 크기(시제품 +349 줄 → 검사기 안 약 +130 줄 · 설명 포함) · 부칙 · 진단 문면을 «부르는 try» 가 아니라 «돌 수 있는 try» 로 ·
  안쪽 try 가 기저를 잡고 `raise` · `raise <잡은 이름>` 으로 다시 던지면 바깥 try 는 면제하지 않는다 · «붉음 유지» 시험을 더한다.
- 사소: 빚을 좁힐 때는 줄 번호가 아니라 함수 꼬리로(아래 행동 변화 3) · except · else · finally 안 창구 호출은 한계로(아래 한계 3).
- 구현 중 찾은 검토 판(K)의 놓침 셋(모두 고침 · 시험 있음):
  1. self · 매개변수 객체의 **속성**을 바깥 함수에 콜백으로 넘김(`asyncio.to_thread(self._lookup, request)` — 현장 ACL 이 창구를 self 속성에 주입하는 꼴) →
     속성을 읽는 값의 뿌리가 바깥이 아니면 돈다고 본다(property 읽기도 같이 잡힌다).
  2. 비동기 생성기를 `anext` 로 읽음 → `anext` · `aiter` 를 `next` · `iter` 와 같이 «아무 데나 닿는 내장» 에.
  3. 창구가 돌려준 생성기를 `list(responses)` 로 다 읽음(검토가 «공통 남은 놓침» 으로 둔 꼴) → 위 «고침» 3.

## 행동 변화 · 받아들인 한계
1. 알려진 바깥 코드만 도는 try(받은 글 JSON 읽기 · 상대 계약 타입 만들기 · 안쪽 try 가 기저를 잡아 번역한 뒤의 읽기 · except 몸통에만 창구 호출)는 기저를
   요구하지 않는다. 그 밖 꼴(지역 자료 반복 · 매개변수 글의 메서드 · self 메서드 · 같은 파일 도우미 · 같은 묶음 schema 모듈 · 예외 객체 속성 읽기 등)은
   옛 판처럼 붉다 — 새 붉음은 없다.
2. #473 try 줄이 try 마다 `경로:줄` 과 함수 꼬리를 단다. 옛 판은 같은 파일의 나쁜 try 들이 같은 글자 한 줄씩이라 G2 귀속(앵커 · 현재 정규화 줄의 차)이
   «이미 나쁜 try 가 있는 파일에 새 나쁜 try» 를 못 갈랐다 — 새 판은 함수가 다르면 가른다(같은 함수 안 둘은 여전히 같은 줄이다).
3. 빚 대조: 줄 번호는 정규화(`:N`)되므로 빚 부분 문자열에 줄 번호를 적으면 안 맞는다 — 좁힐 때는 함수 이름(꼬리)으로. 옛 꼴 `#473 <경로>: try 의 …`
   (경로 바로 뒤 쌍점)는 새 줄(`<경로>:<줄>: …`)에 안 맞는다. 이 꼴로 적힌 빚은 신고한 그 try 하나였고, 그 줄은 새 판에서 사라진다.
4. 진행 중 레인은 검사기 묶음 지문이 바뀌어 pre-gate 를 다시 예보한다(#473 전용 예보 자리는 없다 — 스텁 사본에는 try 가 없다).
5. 한계(실제 코퍼스 0 건 · 모두 옛 판은 붉혔다):
   1. 알려진 바깥 함수(내장 밖)는 넘겨받은 맨 이름(지역 · 매개변수)을 자료로 쓴다고 본다 — 창구 함수를 지역 이름에 담아 `asyncio.to_thread(lookup, request)` 로
      넘기거나, 창구가 돌려준 생성기를 맨 이름으로 바깥 검증기에 넘기면 놓친다.
   2. 모듈 상수를 지은 뒤 그 안에 창구 함수를 넣는 꼴(`_TABLE["x"] = get_x` · `_NS.x = get_x`)은 그 상수를 계속 바깥으로 본다.
   3. except · else · finally 안 창구 호출은 그 try 가 받지 못하니 아무 줄도 없다(옛 판은 우연히 그 try 를 붉혔다) — «try 밖 창구 호출» 과 한 묶음으로 다음 판 후보.
