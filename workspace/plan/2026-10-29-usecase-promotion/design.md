# 큰 유스케이스 부품 승격(②′) 설계 — dddjango 2.30.0

판 요약은 `plan-2.30.0.md`. 이 문서는 설계 v2 의 규칙 · 검사기 · 리팩토링 모드 · 남용 위험 · 크기 절만 싣는다(현장 대입 절은 공개 저장소에 싣지 않는다 — 본문의 «§5» · «§7» · «§8» 참조는 그 절을 가리킨다).

## 0. 한눈에 — 추천 설계

1. **캐스케이드에 ②′를 넣는다.** 차례는 ① 이동 → ② 역할 밖 응집 승격 → **②′ 역할 내 독립 흐름 승격** → ③ 유지다.
   - ②′는 **유스케이스 칸(트리 42행)에만** 선다.
   - 다음 셋이 모두 서야 ②′이고, 하나라도 빠지면 ③이다.
     - (가) **판정 도메인 먼저** — 본체는 도메인이 낸 닫힌 값에 `match`만 한다.
     - (나) **갈래끼리 독립** — 도구 · 틀을 거쳐 다른 갈래를 부르는 것도 갈래끼리 부름이다.
     - (다) **갈래 부품마다 클러스터**다.
2. **부품은 네 종류다.**

   | 종류 | 무엇 | 비고 |
   |---|---|---|
   | **갈래** | 본체 `case` 한 곳이 부르는 흐름 | |
   | **단계** | 두 곳 이상이 부르는 흐름 | |
   | **틀** | 부품들이 함께 쓰는 실행 도구(쓰기 경계 자원 · 발행 · 스트림 · 실패 접기 · 화자) | 폴더에 많아야 하나 · 이름 `<유스케이스 이름>_frame.py` 고정 |
   | **잎** | 두 곳 이상이 쓰는 무상태 정의(실행 기억 타입 · 순수 함수 · 상수) | 시험에서 3개 필요했음 |

   - 실행 틀은 **틀 부품으로 옮기는 것을 추천**한다(§1.10).
   - 사본 시험이 고른 꼴(«부품 안 Protocol + 본체가 self를 넘김»)은 도구를 거쳐 갈래끼리 부르기가 남는다(한 갈래 → 다른 갈래 메서드 5개 이상). 그래서 «갈래끼리 0»을 기계가 볼 수 없다.
3. **의존은 한 방향이다**: 본체 → 갈래 → 단계 → 틀 → 잎.
   - 역방향 0 · 갈래끼리 0 · 부품끼리 순환 0이다.
   - 본체 객체(`self`)도, 본체 메서드(`self.<메서드>` · `self` 잡는 람다 · 안쪽 함수 · `partial`)도 부품에 넘기지 않는다.
4. **쓰기 경계 — 이 BC 의 저장소 · UoW 는 본체와 틀만 쥔다**(R-3411 넓힘 · 읽기 포함).
   - 사실 발행 · 커밋 뒤 등록도 본체와 틀에만 둔다.
   - 다른 BC · 바깥 port 호출과 스트림 방출은 이 규범의 쓰기가 아니다.
   - 틀은 갈래를 모른다. 트랜잭션 안에서 무엇이든 돌리는 범용 틀 메서드는 금지다.
   - 쓰기 경계가 갈래 흐름을 감싸면 (i) 본체 구간 또는 (ii) 갈래 모르는 틀 쓰기 도구로 쓴다.
5. **공개 이름은 둘만이다** — 부품 클래스와 틀 계약. 잎이 정의한 타입은 `_` 여도 된다. 폴더 밖 비공개는 `__init__` 비재수출과 #662가 지킨다.
6. **그대로 두는 것**: 감사 주도 · 크기는 트리거가 아님 · #189 · #192(부품마다) · #641 1단 평평 · #643 · #644(물리 줄) · #68 · 바깥 import 표면 불변 · `git mv`.
7. **검사기**
   - 새 번호 넷: #659 쓰기 경계(check-transaction-boundary) · #660 방향 · #661 이름(check-layer-skeleton) · #662 바깥 import(check-usecase-dto-placement).
   - #643 을 넓힌다.
   - 본체만 보던 내용 검사를 넓힌다(§3.4). 시험에서 검사기 27종이 그대로 녹색이었고 한 갈래 부품의 UoW 직접 사용도 보지 못했다 — 넓히지 않으면 나누기가 위반을 검사 밖으로 빼돌린다.
   - ⓓ 새 신호는 두지 않는다. (가)(나)(다) · 틀 표면은 감수 물음 R-3720 이 받친다.
8. **리팩토링 모드** — 승인 · 실행 · 검증이 규칙 개정만으로 선다.
   - 시험이 본체 비공개 메서드를 바꿔 끼우는 자리(현장 1곳)는 현 판 0F 창으로 된다.
   - 빈자리 하나: G2 `residual` 의 ⓓ 겹침 바닥(G8 · 코드 읽기만 · 재현 먼저).
9. **기능 모드** — 새 유스케이스 파일은 감사 → 반송 → coder 집행이다. 기존 ③ 파일의 ②′ 는 리팩토링 모드 몫이다.

## 1. 규칙 문장 개정안

### 1.1 캐스케이드 자리

| ② | 동명 폴더 승격 | 역할 밖 응집 단위(자기 상태 클래스 · 닫힌 무상태 클러스터) | 승격 허용 칸 전부 |

| ③ | 유지 | 셋 다 아니면 한 파일 | 전부 |

  - 다른 행위 칸에는 이미 자기 규범이 있다. 컨트롤러는 #125 «변환 · 1회 호출», repo 구현은 저장 규범이 맡는다.
  - 근거: research §2.7 ㉠~㉥은 모두 유스케이스 칸의 어긋남이다.

### 1.2 ②′ 술어와 성립 조건 — R-3717 초안 (SKILL §1 캐스케이드 2와 3 사이)

> 2′. **역할 내 독립 흐름(②′)** — 유스케이스 칸(트리 42행)에만 선다. ①·② 가 서지 않는(전부 역할 내) 유스케이스 파일이 입구 하나 안에 서로 독립인 흐름 갈래를 품었으면 동명 폴더로 승격하고 안을 부품으로 나눈다 — 유스케이스는 하나이고 입구도 하나(`execute`)다. 다음이 모두 서야 하고, 하나라도 서지 않으면 ③ 이다.
> (가) **판정 도메인 먼저** — 본체는 갈래를 도메인 층이 정의한 닫힌 값(Enum · StrEnum · 봉인 합 타입) 하나에 대한 `match` 로만 고른다. 그 값은 도메인 메서드 · 도메인 서비스 호출 하나가 내고(바깥 요청의 종류는 그 호출의 인자로 넘긴다), 본체는 고르려고 상태를 읽거나 비교하지 않는다.
> (나) **갈래끼리 독립** — 갈래 부품은 본체 `match` 의 `case` 한 곳에서만 들어가고 다른 갈래의 흐름을 부르지 않는다 — 틀 · 넘겨받은 도구를 거쳐 부르는 것도 같다. 두 곳 이상(본체 `case` 포함)이 함께 지나는 흐름은 단계 부품이고, 다른 갈래로 다시 가야 하는 갈래는 갈래가 아니다 — 본체가 도메인 값으로 다시 고른다.
> (다) **갈래 부품은 클러스터** — 갈래 부품 하나는 ② 의 클러스터(사적 정의 둘 이상이 서로만 참조하는 닫힌 성분)다. 메서드 하나짜리 갈래는 본체에 남고, 한 곳만 부르는 흐름은 부르는 쪽 안 `_` 사설 함수로 남는다(#192).
> ②′ 승격 뒤 형태(부품 종류 · 의존 방향 · 쓰기 경계 · 이름)는 `references/final.md` §0 이 소유한다. ②′ 판정이 (가) 를 위해 판정 이동(#194 발견)을 먼저 요구하면 발견문에 그 선행 발견을 적고 집행은 판정 이동 → 승격 차례다. 승격을 집행하기 전의 모듈 경로 참조 전수 조사(② 의 문장)는 ②′ 에도 그대로다.

**조건별 근거**

- **유스케이스 하나 · 입구 하나**: #635 «진입점 클래스 하나 · `execute` 하나», #125 «컨트롤러는 1회 호출». research ㉢이 이 둘이 입구 하나 쪽으로 당긴다고 적었다.
- **(가) 판정 도메인 먼저**
  - #194 «유스케이스는 업무 규칙을 갖지 않는다».
  - Simons: «genuine selection nodes … whose sole purpose is to dispatch to the alternatives».
  - Evans: «This layer is kept thin. It does not contain business rules».
  - 실측: 현장 갈래 고르기 열쇠가 바깥 의도 3 · 저장 상태 3으로 섞여 있고, 같은 네 조건이 두 곳에 있다(§5.3). 도메인 먼저가 없으면 나눈 뒤 이 조건이 부품마다 복제된다.
- **바깥 요청 종류도 도메인 호출의 인자로**: 열쇠가 섞인 고르기를 한 값으로 닫아야 `match` 하나가 된다. 고르기를 두 곳(본체 if + 도메인 값)으로 나누면 Simons의 «선택 마디»가 둘이 된다.
- **(나) 갈래끼리 독립**
  - RUP: «If alternate and exception flows are completely independent, separate them as well».
  - Bogard: «Minimize coupling between slices».
  - 실측: 갈래끼리 부름이 5곳이다(§5.3).
- **(나) «도구를 거쳐 부르는 것도 같다»**
  - 사본 시험 걸림 10 «도구가 갈래끼리 부르기를 세탁»: 한 갈래 부품은 넘겨받은 도구로 본체의 다른 갈래 메서드 5개 이상을 계속 불렀다.
  - 이 구절이 없으면 import만 한 방향이고 실제 흐름은 갈래끼리 엉킨 채 «독립»으로 통과한다.
- **«다시 가는 갈래는 본체가 다시 고른다»**: Simons는 의존을 «고르는 쪽 → 갈래»로 둔다. 실측: 다시 시도 갈래(25줄)는 실제로 다른 갈래 셋을 고르는 선택 마디다.
- **(다) 클러스터**
  - ② 술어의 «함수 하나는 클러스터가 아니다»를 그대로 쓴다.
  - Cockburn: «Extracting a sub use case is easy, but it adds cost» · «merge trivial sub use cases».
- **판정 이동 → 승격 차례**: research-usecase-books 종합 5 «갈래 · 단계 부품은 판정 이동 뒤에만». Fowler: «behaviorally rich controller objects manipulating dumb data objects».
- **집행 전 조사 그대로**
  - 현행 ② 문장 «재수출 `__init__`의 import 표면 불변은 읽기 표면만 보증하고 패치 표면은 보증하지 않는다».
  - 실측: 현장 시험 1곳이 본체 메서드를 바꿔 끼운다(§5.5).
  - 시험에서 로거 이름이 부품마다 바뀐 것도 이 조사(settings 등 dotted-path 문자열 참조)가 덮는다.

### 1.3 부품 종류 — R-3718 초안 (final.md §0 승격 형태, «승격 폴더는 리프로 닫은 폴더가 아니다» 문단 뒤 새 문단)

> **②′ 승격의 부품** — 부품은 유스케이스가 아니다: `execute` · `…UseCase` 이름 · 합성 루트 등록이 없고, 승격 폴더 밖의 제품 코드(컨트롤러 · 다른 유스케이스 · 합성 루트)는 부품 모듈을 import 하지 않는다(`__init__.py` 재수출은 본체의 공개 이름뿐이다). 부품은 네 종류다 — **갈래 부품**(본체 `match` 의 `case` 한 곳이 부르는 흐름) · **단계 부품**(본체와 부품 가운데 두 곳 이상이 부르는 흐름) · **틀 부품**(갈래 · 단계 부품이 함께 쓰는 실행 도구 — 쓰기 경계 자원 · 사실 발행 · 스트림 · 실패 접기 같은 것 — 폴더에 많아야 하나 · 이름은 `<유스케이스 이름>_frame.py`) · **잎**(두 곳 이상이 쓰는 무상태 정의 — 실행 기억 · 결과 타입 · 순수 함수 · 상수 — 흐름도 실행 도구도 아닌 것). 한 곳만 쓰는 흐름 · 정의는 부품이 아니라 그 곳 안 `_` 사설 정의다(#192). 업무 판정은 잎이 아니라 도메인이다(① · #194). 틀 부품과 잎은 갈래 · 단계 부품이 있을 때만 선다. 부품은 본체가 만든다 — 본체 `__init__` 이 생성자로 받은 의존으로 틀 → 단계 → 갈래 차례로 부품 클래스를 만들어 `self` 속성에 대입하고 필요한 것만 넘긴다(본체 생성자 시그니처와 합성 루트는 그대로다). 실행마다 바뀌는 상태는 잎이 정의한 실행 기억 객체 하나로 인자로 넘기고, 부품은 실행 사이 상태를 두지 않는다. **부품 클래스**(본체 `__init__` 이 만들어 `self` 속성에 대입하는 형제 모듈 클래스) · **틀 계약**(부품이나 본체가 부르는 틀 클래스 메서드) · **본체가 부르는 부품 메서드**는 공개 이름(앞 `_` 없음)이다 — 잎이 정의한 타입 · 상수 · 함수는 형제가 import 해도 `_` 이름이어도 된다. 폴더 밖에 대한 비공개는 재수출하지 않음과 바깥 import 금지가 지킨다. 각 부품에는 캐스케이드가 다시 걸린다 — 부품 안 ②′ 의 실현도 하위 폴더가 아니라 형제 부품 분할이다.

**근거**

- **갈래 · 단계 두 종류**
  - RUP: «encapsulate the main flow of events and alternate flows of events in different control classes».
  - OOSE: «several simple control objects, with specific and limited tasks» · «a control object can be assigned to each concrete or abstract use-case».
  - AOSD p.176: included 흐름은 application-generic 칸에 둔다.
- **단계 = 두 곳 이상**: #192 «사설 조각은 제 파일 안 `_` 함수». 실측: 입력 다시 받기는 본체 `case` · 갈래 둘, 세 곳이 부른다.
- **틀 부품 하나**
  - 실측: 부품이 부르는 본체 도구가 30메서드 · 606줄이다.
  - 한 곳에 모으지 않으면 부품마다 본체를 불러야 한다.
  - AOSD에 «non-use-case-specific slice» 개념이 있다.
- **잎**
  - 사본 시험 걸림 3: «공용 비공개 항목은 본체에 둘 수 없어 잎 파일 필요(7 중 3) — #192 «제 파일 안 `_`»와 부딪침».
  - 실제로 생긴 잎: 실행 기억 타입 180행 · 가르기 대본 함수 89행 · 답 출력 해석 71행.
  - 이름을 주지 않으면 같은 파일이 «helpers»로 생긴다.
- **업무 판정은 잎이 아니다**: #189 처방 «업무 판정이면 `domain_layer/`»와 같은 축이다. 잎이 판정을 품으면 (가)를 우회한다.
- **이름 고정(틀)**: 종류를 선언할 다른 표지 없이 기계가 틀을 알아보게 한다(§3.2).
- **틀 · 잎은 갈래 · 단계가 있을 때만**: 갈래 없이 틀 · 잎만 떼면 기술 층으로 나눈 것이다. #643(부품 0 = 환원 신호)과 같은 위장이다.
- **본체가 만든다 · 차례 · 합성 루트 그대로**
  - 현행 «바깥 import 표면 불변».
  - 전역 원칙 03 예외: 내부에 닫힌 협력자는 직접 생성해도 된다.
  - 사본 시험 걸림 13 «부품 사이 의존이 생기면 조립 순서가 본체 `__init__` 몫». 방향 표(1.4)의 역순이 곧 조립 차례다.
  - «본체 `__init__` 이 만들어 `self` 속성에 대입» 은 기계가 부품 클래스를 알아보는 표지이기도 하다(§3.2).
- **실행 기억은 잎에서 · 인자로**
  - 실측: 부품 메서드가 이미 실행 기억을 인자로 받는다(갈래 53/57 · 가장 큰 단계 74/81).
  - 사본 시험도 이 타입을 잎으로 뺐다. 그것만으로 시험 수정이 import 경로뿐이었다.
- **공개 이름은 셋(처분 5 · 10-29 운영자 처분 3 으로 받는 쪽 넓힘 — 검사기 #661 ⓑ 가 규범 글보다 엄해지지 않게)**
  - 사본 시험 걸림 2 · 11: 본체 이름 그대로 두니 객체를 넘는 비공개 접근이 63곳(ruff SLF001)이었다.

- **부품은 유스케이스가 아니다**: 사용자 결정 원문. Bittner: «Where there is only one useful thing being done, there should only be one use case».
- **부품 안 ②′도 형제 분할**: 현행 ② «주어가 승격 폴더 내부 부품이면 ②의 실현은 하위 폴더가 아니라 형제 부품 파일 분할» · #641.

### 1.4 의존 방향 — R-3719 초안 (같은 문단에 이어서)

> 의존은 한 방향이다 — 본체 → 갈래 부품 → 단계 부품 → 틀 부품 → 잎. 본체는 모두를, 갈래 부품은 단계 · 틀 부품과 잎을, 단계 부품은 다른 단계 부품 · 틀 부품 · 잎을, 틀 부품과 잎은 잎만 import 한다(② 로 선 형제 부품도 방향에서는 잎이다). 다음은 위반이다 — 부품 → 본체 import(`TYPE_CHECKING` 아래 · 함수 안 포함), 본체 객체를 부품에 넘기는 것(`self` 를 위치 · 키워드 인자로 — 부품이 Protocol 로 받아도 같다), 본체 메서드를 부품에 넘기는 것(`self.<메서드>` · `self` 를 잡는 `lambda` · 안쪽 함수 · `functools.partial`), 갈래 → 갈래, 부품끼리의 순환, 틀 · 잎 → 잎 아닌 형제.

**근거**

- **한 방향**
  - AOSD p.176: «There is a dependency from application-specific packages to application-generic packages».
  - Cockburn: include 화살표는 base → included 방향이다.
  - Simons: 고르는 쪽 → 갈래.
- **역방향 0**: 실측으로 공용 → 갈래 역방향 간선이 지금 0이다. 이미 한 방향이라 규칙이 현장을 거스르지 않는다.
- **본체 객체 넘김 금지(Protocol 포함)**
  - 사본 시험 꼴(부품 안 Protocol + `self`)은 import가 한 방향이어도 실행 때 부품 → 본체 호출 고리가 된다. 사용자 조건 «역방향 0»을 실제 흐름에서 어긴다.
  - 그 고리로 갈래끼리 부르기가 세탁됐다(걸림 10).
  - Protocol 시그니처가 155줄 겹쳤다(걸림 2).
- **본체 메서드 넘김도 금지(검토 9)**
  - bound method · `self` 를 잡는 람다 · 안쪽 함수 · `partial` 은 `self` 자체를 넘기지 않아도 실행 때 부품 → 본체 호출이다.
  - 사본 시험 걸림 10(«C → 본체 다른 갈래 메서드 5+ 은 도구로 남김»)이 이 세탁의 꼴이다. `self` 만 막으면 메서드 하나씩 넘겨 같은 고리를 만든다.
- **단계끼리는 순환만 금지**: 실측으로 단계 → 단계 부름 3곳이 있다. 다 막으면 그 흐름이 갈 곳이 없다. 순환은 모듈 import 순환이 된다.
- **틀은 갈래 · 단계를 모른다**: AOSD p.179 «quickly become heavyweight and entangled». 틀이 갈래 · 단계를 알면 공용 조각이 갈래 지식을 빨아들인다.
- **잎을 끝에 두는 까닭**: 현행 ②도 형제 부품(잎)을 낳는다. 틀도 실행 기억 타입(잎)을 써야 한다. 잎이 방향 표에 없으면 #660이 정상 꼴을 막는다.

### 1.5 쓰기 경계 — R-3411 개정 초안

- 현행: «저장(save)류 쓰기 호출은 본체에만 둔다.»
- 개정:

> 저장(save)류 쓰기 호출은 본체에만 둔다. ②′ 승격이면 이 BC 의 쓰기 경계 자원 — 저장소(`…Repository`)와 UoW(`…UnitOfWork` 와 그것을 내는 팩토리) — 은 본체와 틀 부품만 받는다. 갈래 · 단계 부품과 잎은 그것을 매개변수 · 속성으로 받지도, 다른 객체의 속성 너머로 닿지도 않고(읽기 포함), 틀 부품의 이름 있는 메서드를 불러서만 읽고 쓴다 — 한 실행 안의 여러 번 저장(스트림 도중 저장 포함)도 이 길이다. 사실(도메인 이벤트) 발행과 커밋 뒤 등록도 본체와 틀 부품에만 둔다. 다른 BC · 바깥 시스템 port 호출과 스트림 방출은 이 규범의 쓰기가 아니다. 틀 부품은 갈래를 모른다 — 콜백 · 컨텍스트를 받아 작업 단위 안에서 무엇이든 돌리게 하는 범용 틀 메서드는 위반이다. 틀이 다시 읽은 애그리거트 하나에 루트 메서드를 적용하는 변경 함수(애그리거트만 받고, CAS 미스 때 다시 적용된다)는 그것이 아니다. 쓰기 경계가 갈래 흐름을 감싸면 둘 가운데 하나로 쓴다 — (i) 트랜잭션 구간을 본체에 두고 본체가 갈래 부품의 앞 · 뒤 조각을 부른다, (ii) 갈래를 모르는 틀 쓰기 도구(예: 애그리거트 여럿을 한 작업 단위에서 CAS 저장)를 쓰고 읽기 · 판정을 작업 단위 밖으로 옮긴다 — (ii) 는 그렇게 옮겨도 동작이 같을 때(시험이 확인)만이다. 틀 부품의 쓰기에도 유스케이스 쓰기 규범(#195 · #197)이 본체와 같이 걸린다.

### 1.7 시험이 가져오는 비공개 이름 — R-3408 개정 초안 (final.md 승격 형태 첫 문단 «바깥 import 표면» 구절)

> 바깥 import 표면(`...<칸>` 모듈 경로로 공개되는 이름 집합)은 … 불변이어야 한다 — 앞 `_` 이름은 표면 밖이다. `_` 정의를 다른 파일로 옮기면, 그 이름을 옛 모듈 경로로 가져오는 시험을 찾아 같은 창(단계)에서 정의를 가진 파일의 경로로 고친다 — 옛 모듈이 그 이름을 다시 import 해서 시험이 우연히 통과해도 같다.

- **coder 문단**(위치표 11)에 집행 문장을 둔다: «`_` 정의를 옮길 때 시험의 옛 모듈 import 를 찾아 정의 파일 경로로 같은 창에서 고친다».

**근거**

- 현행 문면 «공개되는 이름 집합» — `_` 이름은 처음부터 공개가 아니다.
- 사본 시험 걸림 1: 시험 3파일 4줄이 모두 비공개 이름 import 경로였다. 그중 1곳은 본체가 다시 import 해서 우연히 통과했다(그 시험 파일은 mypy `ignore_errors`).
- 우연 통과를 두면, 본체가 그 import를 지우는 다음 일감에서 원인과 먼 곳이 깨진다. 그래서 «찾아서»를 문장에 둔다.
- **#664(기계 검사)를 걷은 까닭(처분 7)**: check-usecase-dto-placement 는 시험을 읽지 않는다(검토 8). 시험을 읽는 새 스캔을 세우는 대신, 정의를 옮기는 사람(coder)의 절차로 둔다(원칙 05). 고친 줄은 0C dm 대응으로 설명되어 묶음 감사로 간다(§4.2 G2).

### 1.9 감사 주도 · 크기 — R-3418 · R-3419 개정 초안 (R-3420 무변)

- **R-3418(③)**:

> 3. **유지(③)** — ①·②·②′ 가 모두 아니면 한 파일(부품이면 한 부품 파일)을 유지한다. 전부 역할 내인 초대형 파일도 ②′ 가 서지 않으면 ③ 이다 — 크기는 트리거가 아니다.

- **R-3419(감사 주도)**: 바꾸는 곳은 두 군데다.
  - «①/② 판정은 권고가 아니라 반송 대상 발견이고 …»를 «①/②/②′ 판정은 …»으로 바꾼다.
  - 뒤에 다음 문장을 덧붙인다.

> ②′ 발견의 열거는 부품마다 종류(갈래 · 단계 · 틀 · 잎)와 들어가는 자리(본체 `case` · 부르는 부품)를 적고, 쓰기 경계가 갈래 흐름을 감싸는 자리마다 고른 꼴((i) 본체 구간 · (ii) 틀 쓰기 도구)과 그 근거를 적는다. 전 빌드 ③ 판정 파일의 ②′ 는 리팩토링 모드 몫이다 — 위 재판정 조건은 그대로다.

- **R-3420(ⓓ#644 신호)**: 바꾸지 않는다.

**근거**

- **감사 주도 유지**: 사용자 지시. Cockburn «adds cost» · Bittner 분해 남용 경고. 둘 다 «구조 술어로만 발동»과 맞는다. ②′도 coder가 스스로 발동하지 않는다.
- **②′도 «반송 대상 발견»**: ②′는 ②를 넓힌 것이고, 현행 정의가 «①/② 판정은 권고가 아니라 반송 대상 발견»이다.
- **크기는 트리거가 아님**: 사용자 지시. 판정 의무는 ⓓ#644가 열지만, 성립은 (가)~(다) 술어만으로 정한다.
- **(i)/(ii) 를 감사 열거에서 고르는 까닭(처분 2)**: 어느 꼴이 맞는지는 그 자리의 읽기가 잠금 · 격리에 기대는지에 달렸다. 고르는 기준은 셋이다.
  1. 작업 단위 안 읽기가 잠금(`select_for_update` 같은 것)이나 기본보다 높은 격리에 기대면 (i).
  2. 작업 단위 안 판정이 저장 결과 말고 다른 I/O(다른 port 호출)에 기대면 (i).
  3. 둘 다 아니고 쓰기가 CAS 로 경합을 가리며 그 자리를 지나는 시험이 있으면 (ii).
- **«기존 ③ 파일의 ②′ 는 리팩토링 모드 몫»(처분 6)**
  - SKILL:44 재판정 조건은 «역할 밖 후보가 새로 생긴 diff»뿐이다. ②′ 는 역할 내라 기능 모드에서는 다시 걸리지 않는다(검토 7).

  - 기능 모드 재판정 조건에 ②′ 후보를 더하는 길(검토 7의 다른 길)은 diff 마다 역할 내 흐름 판정 의무를 열어 감사 비용을 키운다(원칙 05).
- **R-3420 을 바꾸지 않는 까닭(처분 4 · 검토 5)**
  - 머리 뺀 셈은 «승격 폴더 안 `.py`»에 행 구분 없이 걸려 42행 밖 승격 컨트롤러 본체 셋을 문턱 아래로 내린다(239 → 173 등).

**② 꼴 세부**

- 틀은 클래스 하나다. 생성자로 저장소 · UoW 팩토리와 틀 도구가 쓰는 port 를 받는다(실행 사이 상태 없음). 메서드는 실행 기억을 첫 인자로 받는다 — 현장 부품의 현행 꼴이다.
- 실행 기억 · 결과 타입은 잎(예: `<…>_memory.py`)에 두고, 틀 · 부품 · 본체가 import한다. 이름은 `_` 여도 된다(1.3).
- 본체 `__init__`은 `self._frame = <틀>(…)` → 단계 → 갈래 차례로 만든다.
  - 시험 걸림 6 «포트 9개를 본체와 C가 함께 쥠»: 부품만 쓰는 port는 본체 속성에서 걷는다.
  - 생성자 시그니처는 그대로다.

### 3.2 부품 종류를 어떻게 아는가 (선언 없이)

1. **본체** = `<폴더 이름>.py`(현행 #638).
2. **틀** = `<본체 이름에서 `_use_case` 뺀 이름>_frame.py`. 이름 고정이 곧 선언이다.
3. **부품 클래스** = 본체 클래스 `__init__` 에서 `self.<속성> = <C>(…)` 또는 `self.<속성>: T = <C>(…)`(AnnAssign — 하우스룰 «모든 이름의 첫 대입에 타입» 때문에 오히려 기본 꼴) 로 만들어 대입하는 클래스 `C` 가운데, 형제 모듈에서 import 한 것(처분 5 정의). 틀 클래스도 이 꼴로 만들어진다. 판별은 `checker_target.use_case_part_kinds(folder)` 한곳에 두고 skeleton · transaction-boundary · usecase-dto · domain-model 이 같이 쓴다(계획 C0 — `ClassDef.bases` 는 읽지 않는다).
4. **흐름 부품**(갈래 · 단계) = 틀이 아니면서 부품 클래스를 정의한 형제 모듈.
5. **잎** = 나머지 형제 모듈(본체 · 틀 · 흐름 부품이 아닌 것).
6. **②′ 폴더** = 틀 파일이 있거나 흐름 부품이 하나 이상인 42행 승격 폴더. 그 밖의 42행 승격 폴더는 기존 ② 폴더다.

- **방향은 «본체 → 부품»으로 읽는다.** v1 의 «본체만 import하면 갈래 후보»는 «본체만이 import 하는 부품»이라는 뜻이었다(검토 11). v2 는 import 그래프가 아니라 «본체가 만든다»로 가른다.
- **갈래와 단계는 가르지 않는다.** 결정적 검사가 쓰지 않는다.
  - «갈래 → 갈래»는 기계에 흐름 부품 → 흐름 부품(허용 · 순환만 금지)으로 보인다. 감수 물음 (나)가 가른다.
  - 기계가 못 하는 것을 결정적이라 부르지 않는다(memory «검사기 통과 ≠ 표준 준수»).
- **예**: 잎만 import 하는 작은 갈래 `gift_card_payment.py`.
  - 본체 `__init__` 이 `self._gift_card_payment = GiftCardPayment(frame=self._frame)` 로 만든다 → 흐름 부품이다.
  - v1 의 import 고정점 정의(«잎 아닌 형제와 본체를 import 하지 않는 부품 = 잎»)로는 이 파일이 잎이 됐다. 그러면 틀이 이 파일을 import 해도 «틀 → 잎»이라 #660 이 통과시켰다.
- **본체가 만들지 않는 클래스**: 다른 부품 안에서 만들어지는 클래스는 부품 클래스가 아니다. 그 모듈은 잎이 되고, 그것이 틀 · 흐름 부품을 import 하면 #660 «잎 → 잎 아닌 형제»가 된다. R-3718 «부품은 본체가 만든다» 위반이 방향 위반으로 드러난다.
- **실행마다 만드는 타입**: `execute` 안 지역 변수로 만드는 클래스(실행마다 하나 만드는 채널 같은 것)는 `__init__` 대입이 아니라 잎 타입이다. `_` 이름이어도 된다(1.3).

- **#197 넓힘 (check-transaction-boundary · ②′ 폴더)**
  - 본체 공개 메서드: 도달 범위(`_uow_write_reach`)가 `self.<틀 속성>.<메서드>(…)` 를 만나면 틀 클래스의 그 메서드와 그 `self._` helper 닫힘으로 이어 간다. 틀의 저장소 · UoW 속성도 그 안에서 쓰기 수신자로 센다.
  - has_uow 는 본체가 UoW 를 쥘 때만이다. 본체가 UoW 를 틀에만 넘기면 본체 공개 메서드는 #197 대상이 아니다.
  - 틀: 틀 클래스가 UoW 를 쥐는데 틀의 어느 메서드의 도달 범위에도 save · remove · `after_commit` 이 없으면 한 줄(클래스 단위). 메서드마다 돌리지 않는다.
- **#660 (check-layer-skeleton)**
  - import 그래프: 폴더 안 `.py` 각각의 `from .<모듈> import …` · 절대 경로 import 를 모듈 간선으로 만든다. `if TYPE_CHECKING:` 아래와 함수 안 import 도 센다(숨은 역방향 막기).
  - 위반 간선: 부품 → 본체 · (②′ 폴더) 틀 · 잎 → 본체 · 틀 · 흐름 부품 · 부품끼리 순환(강한 연결 성분 크기 2 이상).
  - **본체가 넘기는 것**: 받는 호출은 형제 모듈 클래스의 생성 호출과 `self.<부품 속성>.<메서드>(…)`(부품 속성 = 부품 클래스를 대입한 속성 — 틀 포함)다. 그 호출의 위치 · 키워드 인자 가운데 다음이면 한 줄이다.
    1. `Name(id="self")` — 키워드 `x=self` 포함.
    2. `Attribute(value=Name("self"), attr=m)` 이고 `m` 이 본체 클래스에 정의된 메서드(bound method).
    3. `Lambda` 이고 몸에 `Name("self")` 가 있다.
    4. 같은 함수 안에서 정의한 안쪽 함수의 이름이고, 그 몸에 `Name("self")` 가 있다.
    5. `functools.partial(…)` · `partial(…)` 호출이고 인자에 1번이나 2번 꼴이 있다.
  - 부품 생성자 · 메서드 인자 주석이 본체 클래스로 풀린다(문자열 주석 포함).
  - 통과: `self.<메서드 아닌 속성>`(예 `self._frame`) · `self` 를 잡지 않는 람다(예 `lambda order: order.pay(amount)`).

### 4.2 빈자리와 수리

**G1 (v1 «막힘» → 걷음) — 본체 비공개 메서드를 바꿔 끼우는 시험 자리.**

- **무엇**: 틀로 옮기는 본체 메서드를 시험이 `patch.object(<받는 쪽>, "<옛 이름>", …)` 로 바꿔 끼우거나 읽으면, 그 자리를 새 자리(`<받는 쪽>.<틀 속성>.<새 이름>`)로 고쳐야 한다.
- **현 판으로 되는 길**: 그 메서드 이동(과 그것을 부르는 자리의 이동)을 **0F 창** 하나에서 한다. 시험 파일에는 입장 표 `retain` 재조직 행(candidate `재조직 — <옛 자리> 바꿔 끼움을 틀 <새 이름> 으로`)을 둔다. 그 파일이 0F 허용 파일이 되고, close 가 개별 감사 키로 처분한다.
  - 규범: Coordinator 리팩토링 절 «0F = `follow`(명세의 `retain` 재조직 행이 있는 파일만)»(307행) · «기대 의미가 그대로인 시험 편집은 V 가 아니다 — 0F 의 `retain` 재조직 행 … 감사가 본다»(313행).
  - 코드: `behavior_guard.dispose_test_file`(2621행) 우선순위 «(follow · change) 허용 파일 → 개별 감사».
  - 재현(운영자 10-29 · 현장 시험 사본 두 자리를 고쳐 배포판 `dispose_test_file` 에 넣음):
    - `code`(0C) → red «치환으로 설명되지 않는 변경: 본문 문장 15 이 다르다»
    - `follow`(0F) + 허용 파일 → `개별 감사 · 허용 파일`
    - `follow` + 허용 파일 아님 → red
    - D 확정 0
- **걷은 것**: `mt` 대응 꼴 · 명세 «메서드 이동» 행 · R-3721/R-3722 · `behavior_guard`/`refactor_audit` 수리 · Coordinator 문장 · 그 fixture(원칙 05). `mt` 가 얻었을 것은 시험 파일 1개의 «개별 감사 → 묶음 감사» 차이뿐이었다(검토 1).
- **창 차례에 주는 영향**
  - 0C 창은 시험 고정이라, 바꿔 끼움 대상 메서드는 0C 동안 본체에 남아야 한다.
  - 그 메서드를 (거쳐) 부르는 흐름을 0C 에서 부품으로 옮기면 부품 → 본체 호출이 생긴다.
  - 그래서 틀 · 흐름 부품 만들기를 그 메서드 이동과 같은 0F 창에 둔다(§4.3).
  - 창 사이 상태는 형태 검사 대상이 아니다. 검사기 27종은 마지막 창 뒤에 돈다.

**G2 (문장 · coder 문단으로 닫음) — 시험이 가져오는 `_` 이름과 우연 통과.**

- 사본 시험: 3파일 4줄 고침이 모두 `_` 이름 import 경로였다. 글자 그대로 옮긴 정의라 0C dm 대응(묶음 감사)으로 된다.
- **함정 둘**
  - 옮기면서 한 글자라도 고치면 dump가 달라져 0C red다. 시험이 가져오는 `_` 이름은 같은 창에서 바꾸지 않는다. 잎 타입은 `_` 그대로 둬도 되므로(R-3718) 바꿀 까닭도 없다.
  - 우연 통과 — 시험을 안 고쳐도 녹색이라 대응표에 안 잡힌다. 기계 검사(#664)는 걷었다. R-3408 개정과 coder 문단 «`_` 정의를 옮길 때 시험의 옛 모듈 import 를 찾아 정의 파일 경로로 같은 창에서 고친다»가 받는다. 고친 줄은 dm 으로 설명된다.

**G3 (위험 · 기존 사각) — 재수출 심을 남긴 이동의 문자열 patch 헛돎.**

- 현행 «승격 전 모듈 경로 참조 전수 조사»(② 문장)가 그대로 막는다. ②′ 문장도 «그대로»라고 적는다(1.2).
- 로거 이름 변화(시험 걸림 12)도 같은 조사(dotted-path 설정 참조)가 덮는다.

**G4 (세탁) — 내용 검사가 본체만 본다.**

- §3.4로 같은 판에서 닫는다.
- 닫지 않으면 «나누니 검사기가 조용해졌다»가 해소로 잘못 세어진다(G2 빚 잔존 판정 오염).
- 사본 시험이 실측했다: 27종 그대로 녹색, 부품 UoW 직접 사용 못 봄.

**G5 (차례 · 수리 없음).**

- 판정 이동(#194 — 도메인 enum · 메서드 신설, 본체가 그것을 부름)은 시험 무변 제품 변경이라 0C 창 하나다.
- 승격 · 잎은 다음 0C 창이다. 틀 · 흐름 부품은 G1 때문에 0F 창이다. 현행 «0T → 0C → 0F → S1… · 한 번에 창 하나»(307행)로 된다.
- 갈래끼리 부르기 끊기와 쓰기 경계 (ii) 바꾸기는 동작 불변 제품 편집이라 그 창 안에서 한다.
  - 다시 시도를 본체 다시 고르기로 바꾸고, 입력 다시 받기를 단계로 내린다.
  - 사본 시험은 C → N을 «본체 재분기(꼬리 호출 5단 bool 반환)»로 끊었다. 추천 꼴에서는 N이 단계 부품이라 C → N은 **갈래 → 단계 직접 부름**으로 허용된다. bool 사슬이 필요 없다.
  - 재분기는 «다른 갈래의 입구로 다시 가는» 자리에만 쓴다.
  - (ii) 의 «동작 같음»은 그 창의 suite 가 확인한다. 그 자리를 지나는 시험이 없으면 (i) 을 고른다(1.9 기준 3).

**G7 (기능 모드) — 새 파일은 빈자리 없음 · 기존 ③ 파일은 리팩토링 모드 몫.**

1. ⓓ «고르기» — 본체에서 `case` 몸이 부품을 부르는 `match` 의 패턴이 도메인 닫힌 타입(Enum · StrEnum 멤버 · 도메인 클래스 패턴)이 아니거나, 주어가 호출 하나의 결과가 아니면 신호. 본체 `if` 사슬이 부품 둘 이상을 가르면 신호. 받침: 감수 물음 (가).
2. ⓓ «다시 고르기» — 부품 안 분기(`match` · `if`)의 갈래 둘 이상이 서로 다른 형제 부품을 부르면 신호. 받침: (나).
3. ⓓ «부품 자격» — 메서드 하나짜리 흐름 부품 · import 하는 곳이 하나인 단계 · 잎. 받침: (다) · «두 곳 이상».
4. ⓓ «틀 표면» — 아무 부품도 안 부르는 틀 공개 메서드 · 한 부품만 부르는 틀 메서드. 받침: 감수 물음 «틀 표면».
5. 신호 부풀림 — ⓓ#644 를 승격 폴더 안에서 머리 뺀 줄로 세기 · ⓓ#68 을 칸 실현 단위로 세기. 들인다면 42행(또는 ②′ 폴더)로 좁혀 42행 밖 결과를 바꾸지 않는다(검토 5).
