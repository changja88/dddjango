# 명세 조각 ③ — brownfield 면제를 없애고 «리팩터링 의무»로 바꾼다

## 0. 무엇을 정했나

**결정 (2026-08-09 · 사용자):**

> 「지금은 플러그인을 대폭 수정하고 있어서 **기존에 이미 작성된 건 보존하고 새로 쓰는 것부터 수정한다. 이런 건 말이 안 돼.** 플러그인 정책으로도 refactoring 을 보장해야 해. 즉 **언제든 문제가 있는 건 기존에 작성이 되어 있더라도 수정해야 해.**」
>
> 「**brownfield 보존 범위라는 건 있으면 안 될 것 같은데?**」 · 「legacy 판정은 좋아. 그런데 **legacy 라고 그냥 두는 건 말이 안 돼.**」
>
> 「보통 작업이 BC 별로 이루어지니까 **해당 BC 를 작업할 때 brownfield 가 있다면 같이 수정**하는 방향도 좋을 것 같아. 즉 **신규 개발과 리팩터링은 항상 동시에** 이루어지는 방향인 거지. 그리고 **리팩터링이 필요할 경우 리팩터링을 진행하고 신규 개발이 들어가는 방식**이야.」
>
> 「**미룰 수 있게 해야지만 이건 사용자에게 반드시 물어봐야** 할 것 같아. 그리고 지금 `.dddjango` 에 남기는 문서가 있는데 **여기에 리팩터링 scope 도 남겨야** 할 것 같아.」

**정식화 — 일곱**

```
① 규칙을 바꾸는 릴리스는 «이관 계획» 없이 나가지 않는다          (새 부채를 안 만든다)
② BC 를 작업하면 그 BC 의 미이관을 «먼저» 정리하고 시작한다       (있는 부채를 갚는다)
③ 「가만 있어도 해로운」 위반은 ②를 기다리지 않는다               (안전 예외)
④ brownfield·legacy 는 «면제»가 아니라 «아직 안 갚은 것»이다      (낱말 정리)
⑤ 「리팩터링 대상」을 따로 정의하지 않는다 — 백스톱이 내는 위반이 곧 그것이다
⑥ 그 백스톱을 Phase 0 에서 «한 번 더» 돌려 G0 배너에 올린다
⑦ 미루기는 «사용자에게 물어서만» 가능하고 `.dddjango/` 에 기록된다
```

## 1. 왜 — 근거 넷

### ⑴ brownfield 는 «코드의 속성»이 아니라 «규칙 변경의 그림자»다

```
어제   api.py 의 코드 = 규칙에 맞음
오늘   플러그인이 규칙을 바꿈 → «같은 코드»가 위반이 됨
```

코드는 한 글자도 안 바뀌었다. brownfield 를 만든 것은 **규칙 변경**인데, 지금 구조는 그 부채를 **코드 쪽에 떠넘기고 면제**한다. 그러면 규칙을 바꾸는 비용이 **0** 이라 규칙이 늘기만 하고, 부채는 주인이 없어 아무도 안 갚는다.

### ⑵ 판정이 되는 물음이 아니다

「brownfield 인가」는 **«언제 쓰였나»**를 묻는데, 언제부터가 brownfield 인지 답이 없다. 실제로 중요한 것은 **«누가 의존하나»**와 **«되돌릴 수 있나»**다.

- 어제 쓴 코드도 배포돼 소비자가 붙었으면 wire 를 못 바꾼다
- 3년 된 코드도 소비자가 0이면 그냥 고친다

### ⑶ ★ 원리가 이미 두 자리에 있는데 셋째에만 반대로 적용됐다

`discipline-houserules/SKILL.md` §1.1 이 스스로 이렇게 적는다.

> *이번 작업이 touched 한* 데이터소스 앱의 루트 평면 배치는 — **이미 `Product` 모델·`0001` 마이그레이션이 있어도** — **'확립된 규약'으로 보지 않는다**
> **같은 원리로** *이번 작업이 touched 한* published_service 의 구 `read.py`/`write.py`·평면 구조·구 3파일형 contract 는 … **'확립된 규약'으로 보지 않는다**

| 대상 | 「이미 있다」의 처분 |
|---|---|
| 데이터소스 앱 평면 배치 | 확립된 규약 아님 → **고친다** |
| published_service 구 구조 | 확립된 규약 아님 → **고친다** |
| **오류 계약·핸들러·helper** | 「이미 승인된 legacy scope」면 **«유지»** ← 여기만 다르다 |

**이 명세는 새 원리를 만드는 것이 아니라 «같은 원리로»의 세 번째 적용이다.**

### ⑷ 실측 — 지금은 위반이 «보이지도» 않는다

`broccoli_server/api.py` **731줄**: 도메인 예외 import 92개 · `_DOMAIN_PROBLEMS` 매핑 테이블 · `@api.exception_handler` **20개** · 마지막이 **`@api.exception_handler(Exception)` catch-all**. 플러그인이 문장으로 금지한 것과 한 글자도 안 다르다.

```
$ check-api-error-controller-contract.py . --error-profile dddjango-code-json …   exit=0 · 0건
$ … --error-bc lessons 를 주면
  → exit=1 «사용 오류: 필수 canonical ErrorOut source 없음:
             application/lessons/presentation_layer/schema/error_out.py»
$ … --error-profile preserve-established                                          exit=0 · 0건
```

`_run()` 첫 줄이 그렇게 돼 있다:

```python
if config.profile == "preserve-established":
    return sorted(set(analysis)), []      # 한 줄도 «안 본다»
if not config.error_bcs:
    return sorted(set(analysis)), []
```

**즉 백스톱은 «이관을 마친 BC»만 지키고 «이관해야 할 BC»는 검사를 시작조차 못 한다.** 위반 건수를 셀 방법이 없어, 「안 고치는 것」과 「못 고치고 있는 것」이 **둘 다 «없는 것»으로 보인다**.

## 3. `refactor-scope.md` — 무엇을 적나

**성격**: 이 작업이 **이번에 무엇을 갚았고 무엇을 왜 미뤘는지**의 기록. **«부채 장부»가 아니다.**

```markdown
# 리팩터링 스코프 — <BC 이름>

## 스캔 결과 (Phase 0)
백스톱 <목록> · 미이관 N건

| # | 위반 | 백스톱 | 미룰 수 있나 |
|---|---|---|---|
| 1 | api.py 가 LessonsError 핸들러를 소유 | check-api-error-controller-contract | 예 |
| 2 | @api.exception_handler(Exception) catch-all | check-error-centralization | **아니오 — 가만 있어도 해롭다** |

## 사용자 결정 (G0)
- ⓐ 지금 정리 : 1, 2
- ⓑ 미룸      : (없음)
  ※ 미룬 항목은 사유를 적는다

## 슬라이스 0 (동작 불변)
…
```

**★ 「미룬 목록」을 파일에 «쌓지» 않는다.** 다음 작업에서 백스톱을 다시 돌리면 **미룬 것이든 새것이든 똑같이 다시 나온다** — 상태를 파일에 누적하면 실제와 어긋난다. 이 자는 T37 에서 이미 썼다(*「진행표를 만들지 말고 애그리거트에 넣는다 — 조건이 곧 커서다」*).
그래서 `refactor-scope.md` 는 **읽어서 이어붙이는 파일이 아니라 그 작업의 기록**이고, 「전에 미뤘다」는 사실은 **폴더 목록으로** 남는다.

**왜 `scope.md` 와 별도 파일인가** — `scope.md` 는 **사람이 정한 범위**이고 `refactor-scope.md` 는 **기계가 낸 부채 + 그에 대한 결정**이다. 서로 **다른 이유로 바뀐다**. 섞으면 다음 작업에서 「이 줄이 사람이 쓴 것인가 기계가 쓴 것인가」를 가릴 수 없다.

## 4. 남는 회색 — 정직하게

**⑴ 「추가 개발이 안 되는 BC」는 남는다.** ②는 BC 를 열 때만 발화하므로, 아무도 안 여는 BC 는 영원히 미이관이다.
**이 명세는 그것을 감수한다** — 안 열리는 BC 는 «바뀌지 않는 코드»라 구조 부채의 실제 비용이 0에 가깝다(부채는 손댈 때 이자를 문다). 다만 **③이 그 구멍을 막는다** — 「가만 있어도 해로운」 것은 BC 작업을 기다리지 않는다.

**⑵ ①(릴리스가 이관을 진다)은 이 명세에서 «문장»으로만 선다.** 집행 수단(릴리스 체크리스트·CI)은 6번에서 정한다. 지금 규칙 변경이 어떤 절차로 나가는지는 이 저장소의 릴리스 관행에 달려 있고, 아직 안 읽었다.

**⑶ 이관 규모를 아직 못 쟀다.** S-R9·S-R10 이 적용돼야 「이 저장소에 미이관 N건」을 셀 수 있다. **그래서 순서는 C → B → A 가 아니라, C(셀 수 있게) 를 먼저 적용하고 그 숫자를 본 뒤 ①의 강도를 정한다.**
