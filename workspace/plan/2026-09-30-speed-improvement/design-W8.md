## 2. 설계

### 2-1. 무엇을 재나 — `assets/style_census.js`(새 · 동기 스니펫)

v3 와 같다. 레인 캡처 자리에서 `page.evaluate` 를 한 번 더 하고, 새 드라이버는 없다. 인자는 `{root, placeholders, exclude, routeSet, sdkGlobals, page, pageSize, budgetMs}` 다.

- **스키마(v4 · 검토 V5)**: meta 에 `census_version: 4`, `root_matched`(1 이어야 함), `route_set` 을 **반드시** 둔다. 셋 중 하나라도 없으면 대조기는 미실행으로 친다.
  - v3 대조기는 키가 없으면 기본값(1 · 표준)으로 봤다. 그래서 v2 스니펫의 «없는 루트 → body 대체» census 가 그대로 대조돼 차단 14 가 났다 [검토 실측].
  - v4 는 그런 census 를 `schema` 미실행으로 돌려준다 [실측 합성 `test_dv4_v5.txt`].
- **SDK 교차 확인(v4 · 검토 V5)**: `route_set` 은 하네스가 스스로 적는 값이다. 그래서 스니펫이 meta 에 실제 상태를 함께 적는다.
  - `vendor`: 페이지가 실제로 받은 `/static/vendor/**` 자원과 응답 코드. Resource Timing 의 `responseStatus` 다.
  - `sdk_globals`: 등재 SDK 전역 변수(예: `Kakao`)가 있는지.
  - `style-scope.json` 의 case 별 SDK 기대값(등재 목록에서 옴)과 대조한다.
    - **SDK case**: `route_set == ["operator-hosts"]` 이고, 기대 파일이 200/304 로 받아졌고, 전역 변수가 있어야 한다.
    - **SDK 아닌 case**: `route_set == null` 이고 벤더 자원이 없어야 한다.
    - 어긋나면 미실행이다.
  - 합성 시험 [실측]: 정상 → 대조 · SDK 파일 404 → 미실행 · `route_set` 빠짐 → 미실행 · SDK 아닌 case 에 벤더 로드 → 미실행.
- **그대로인 것**: 루트 정확히 1 요소(N7) · 가림 단계 예산 초과 → `partial` → 미실행(N12) · DOM 어휘 `vocab`(N10) · 그림 지문 전체 URL 열쇠·`unreadable` 은 URL 별 값(N9) · 보이지 않는 칠 제외 · `blurocc` · `inf` · 글꼴 실검사.
- **캡처 하네스 의무(v4 · 독립 판정에서 나옴)**: 판정자가 잘라 볼 수 있게 **전체 높이 스크린샷**(`full_page=True`)을 함께 남긴다. 이번 리허설은 화면 높이(844)까지만 찍혀서, 판정자가 그 아래는 census 값과 소스로만 판단했다.

### 2-2. 짝짓기 — DOM 이 달라도 «보이는 것»끼리

v3 의 순서에 v4 가 하나를 더했다.
- 페인트 영역을 묶고, DOM 조상을 칠하는 가장 작은 면을 부모로 둔다.
- 라벨은 세로 이동만 허용하고, 짝지어진 부모 안 위치로 짝짓는다.
- 같은 자리(±6px)를 짝짓는다.
- 쌍둥이를 짝짓는다.
- 글리프는 가운데 정사각형으로 본다.
- 앞 형제와의 틈을 잰다.
- 앵커가 없으면 위치를 비교하지 않는다.
- **v4: 양쪽에 모두 있는 구역(절 머리 글) 사이에서는 짝을 짓지 않는다.**
  - 심은 결함 시험에서 «형충회합» 행 간격을 늘렸더니, 같은 한자(丑)의 글리프가 «귀인·추가 신살» 구역의 글리프와 짝지어져 가짜 모양 차이(그림자·글자 크기)가 났다.
  - 같은 데이터 대조에서 그 가짜 차이가 12 → 0 이 됐다 [실측].
  - 구역 이름이 한쪽에만 있으면(이름이 데이터에 따라 바뀌는 머리 글 등) 제약을 걸지 않는다.

**스냅숏 생성 재렌더(v4 · 검토 V4)**
- **스냅숏**: 3-1 캡처가 case 마다 `data-snapshot/<case_id>.json` 을 남긴다. 그 화면을 그린 데이터(view-model·state 를 JSON 으로 · sha256 기록)다. ② 에서는 평가자 하네스가 쓴 데이터를 남긴다.
- **대응표(G0 · 입력범위 리뷰)**: `style-scope.json` 의 `rerender_map` 이다. 시안의 데이터 원천마다 «스냅숏 경로 + 허용 변환»을 적는다.
  - 시안의 데이터 원천은 셋이다: props 필드 · 데이터 묶음 파일 · 이름 붙은 데이터 상수.
  - 허용 변환: 그대로 · 서식 문자열 · G0 에 적은 열거 대응표.
  - 스타일을 고르는 필드(tone·variant·size 류)는 대응표에 들 수 없다.
- **생성**: 도구가 대응표와 스냅숏으로 재렌더 입력을 만든다(props JSON · 데이터 묶음 파일 · 상수 치환 목록). 하네스가 실제로 쓴 입력과 **byte 동일**해야 한다.
- **확인**
  - 바뀐 값은 **형과 무관하게**(문자열·불·수·열거) 대응하는 스냅숏 값을 변환한 결과와 같아야 한다.
  - 대응표 밖의 필드는 G0 원본 값 그대로다.
  - archive digest 는 동결 manifest 와 같아야 한다.
  - 하나라도 어긋나면 거절이다.
- **세탁 시도의 예**: 공망 «·» 색이 `isVoid` 같은 불 필드로 정해진다고 하자. 레인이 그 값을 손으로 바꿔 시안이 틀린 색을 그리게 해도, 스냅숏 값과 다르니 거절된다.
- **실현성 — 정적 확인만 했고, 재렌더 자체는 미측정이다**
  - P2 시안
    - 데이터 원천: 열거 props(`bookCover`·`contentImg`·`reviewState`·`loadState`·`tellerId`)와 별도 데이터 묶음 파일(`cm-books.js`·`cm-tellers.js`·`cm-contents.js`).
    - 구현 하네스 데이터(책 4 · 콘텐츠 2)는 그 묶음의 부분집합이고, 이름·설명·가격이 같다.
    - 표지 유무 같은 항목별 값은 전역 열거 props 로는 표현되지 않는다. 그래서 데이터 묶음 파일을 스냅숏에서 생성해 바꿔 끼워야 한다(라우트 fulfill).
  - P1 시안
    - 표본 원국·시각이 페이지 스크립트 안 `const` 다(`CM_PILLARS`·`CM_NOW_YEAR = 2026`·`CM_NOW_MAJOR = 4`·`CM_GUESTS`).
    - props 는 일부(`calendar`·`majorDir/Num`·`maskGuest`)뿐이라 **이름 붙은 상수 치환**이 필요하다.
  - 재렌더 증명은 그림자 평가자의 처분 모의(§6 관문 6)와 커밋 ① 수용 시험에서 처음 잰다.

**공용 부품 수리 경로(v4 · 검토 V7)**

- 결정 없이 공용 정의를 바꾸면 그 레인의 백스톱·감사가 막는다(기존 규칙).

## 5. 리스크

1. **«또 하나의 브라우저 서브시스템»**: 드라이버가 없다. 동기 스니펫 + 예산(두 단계) · 재수집 두 번 상한 · 순수 함수 대조기다. ② 는 레인 밖에서만 돈다.
2. **기준(원본·비교용 데이터)이 틀리면 기계도 틀린다**: `style-scope` 를 첫 구현 census 전에 동결하고 입력범위 리뷰를 거친다. 심은 결함 시험이 «데이터가 다르면 목록 안을 놓친다»를 실측으로 보였다. 그래서 승격 조건이 비교용 데이터 일치를 전제로 둔다.
3. **D 가 크다**(P1 전 회차 35묶음): 재렌더는 미측정이고, P1 시안은 상수 치환이 필요하다. 재렌더가 비싸거나 불가하면 ③ 비용이 커진다. 처분 모의가 그 비용을 재고, 관문 10 이 손익을 다시 본다.
4. **② 결과의 품질 위험(검토 V1)**: 재렌더가 없으면 D 와 T 를 기계로 가를 수 없다. 그래서 레인 도중에는 아무것도 넘기지 않는다. 끝 판 공개는 D?/T?(낮은 일치율)를 따로 표시한다. 후속 수리는 사용자가 정한다. 데이터에 맞게 옳은 스타일을 시안 예시 값으로 «고치는» 회귀를 이렇게 막는다.
5. **평가자·발주자 비용**: 레인당 평가자 모델 시간 3.8~8.5시간(P1 형)·2.3~5.1시간(P2 형)에 하네스 준비 1.5~5시간, 발주자 시간 2~4.5시간이 든다. 사용 한도는 사용자가 관리한다.
6. **G2 사용자 결정 항목 남용**: 재렌더 불가 + G0 선언 case 에서만 생긴다. 레인당 ≤ 2 묶음이다.
7. **공용 부품 수정의 파급**: 기본은 지역 변형이다. 공용 수정은 사용자 결정 + 영향 화면 목록이 있어야 한다.
8. **속도 근거가 약하다(보수 셈)**: ③·④ 만으로는 본전 근처다. 처분·분류 비용이 예상보다 크면 W8 은 품질 도구로만 남는다. 관문 10 이 그 판단을 사용자에게 올린다.
9. **증거 레인 도중 도구 수정**: 판정을 본 뒤 도구를 고치면 증거가 표본 안이 된다. 관문 0(도구 판 고정)으로 막는다.
10. **재현율 표본이 첫 제출에 몰린다**: 중간 회차는 좁힌 검증이라 재현율 분모에 넣지 않는다. 중간 회차에서 생긴 회귀를 W8 이 잡는지는 관문 1 의 «좁힌 회차 놓침 신호»와 심은 결함 시험으로만 본다.

**② 평가자 절차(운영 문서 · 플러그인 밖)**
1. **분리**: 평가자는 운영 세션이 레인마다 띄우는 별도 에이전트다. 발주자·레인과 다르다. 두 번째 판정자(F/H 라벨)는 또 다른 에이전트다.
2. **범위 동결**: 레인의 첫 G2 제출 전에 시안 archive · 명세로 `style-scope.json` 과 비교용 데이터를 만든다. 범위는 **design-input 전 case** 다. 그 sha 를 장부에 적는다. 첫 구현 census 를 연 뒤 고치면 H 로 센다. 구현 상태 도달은 레인의 캡처 스크립트 사본으로 한다(§4 하네스 준비).
   - **도구 판 고정(관문 0)**: 같은 때 스니펫·대조기·재렌더 생성기의 sha 를 장부에 고정한다.
3. **공약**: G2 제출마다 그 커밋을 scratch 사본에서 재생한다(`cp -c` · 전체 높이 스크린샷 · 데이터 스냅숏). census · 대조를 돌리고 `(시각, 커밋, 도구 판, scope sha, census sha, 결과 sha)` 를 장부 `shadow-ledger.tsv` 에 덧붙인다. 결과는 발주자가 읽지 않는 경로에 둔다.
4. **발주자 판정 기록**
   - **첫 제출과 끝 제출**에서는 발주자가 **전수 대조**(계산 스타일 포함)를 한다. 첫 제출 전수 대조는 별도 검증 에이전트로 돌려 레인 수리와 겹친다. 그 범위(case · 속성)를 장부에 적는다.
   - **중간 재검**은 지금처럼 좁혀도 된다. 범위를 «좁힘»으로 장부에 적는다.
   - 반송문의 항목마다 출처 표지 «발주자(전수)»·«발주자(좁힘)»를 달고, 반송문 sha 를 장부에 적는다. 그다음에만 평가자가 결과를 연다.
5. **대조**: 발주자 항목 ⊂ W8 차단? 결과를 장부에 남긴다. 새 차단 묶음을 라벨한다(T/D?/T?/F/H). 레인에는 아무것도 보내지 않는다.
6. **끝 판**
   - 심은 결함 시험을 한다. 심을 값이 시안 값과 다른지 먼저 확인한다.
   - 두 번째 판정자가 F/H 를 전수 라벨한다.
   - D 처분 모의를 한다(스냅숏 생성 재렌더).
   - W8 만 찾은 차이를 근거(전체 높이 잘라 보기 · 시안 값 · 데이터 의존 판단)와 함께 사용자에게 공개한다. D?·T?(낮은 일치율)·재렌더 대기 항목은 따로 표시한다.
7. 장부의 순서가 어긋난 회차(결과 sha 가 판정 뒤에 적힘 · 결과가 공약 sha 와 다름)는 증거에서 뺀다.

**승격 조건(③) — 재생 그림자 레인 두 개 연속, 레인마다 모두**

0. **도구 판 고정(검토 W3)**: 첫 그림자 레인 시작 전에 스니펫·대조기·재렌더 생성기 sha 를 장부에 고정한다. 두 레인 동안 바뀌면 바뀐 판으로 **새로** 두 레인을 센다. 이전 회차를 고친 판으로 재생한 결과는 참고일 뿐 증거가 아니다. 도구 결함을 찾으면 적어 두고, 다음 증거 레인 쌍 전에 고친다.
1. **재현율(봉인 전 원래 항목만 · 검토 W1)**
   - 분모는 **전수 회차(첫·끝 제출)** 의 출처 «발주자(전수)» 항목이다. 그 가운데 대조 case 의 것은 전부 해당 제출의 W8 차단에 있어야 한다(놓침 0).
   - 미대조·미실행 case 의 항목은 사람 확인·미대조 목록에 있다.
   - 결과 sha 가 그 회차 발주자 판정보다 먼저 장부에 있어야 센다.
   - **두 레인 합 전수 회차 원래 항목 ≥ 10**(빈 표본 방지). 모자라면 세 번째 레인을 돈다.
   - **좁힌 회차 놓침 신호**: «발주자(좁힘)» 항목이 대조 case 에 있는데 W8 차단에 없으면, 분모에는 넣지 않되 그 놓침을 설명할 때까지 승격을 보류한다.
   - 한계: 재현율 표본이 사실상 첫 제출 항목에 몰린다(끝 판은 통과 판이라 항목이 적다). 중간 수리가 만든 회귀를 W8 이 잡는지는 이 분모로 재지 못한다. 그래서 심은 결함 시험(관문 2)과 놓침 신호로 보탠다. 매 회차 전수를 요구하면 이 한계는 줄지만, 발주자 대기가 회차마다 늘어 레인 벽시계가 커진다(이번 두 레인 기준 좁힌 회차 P1 5 · P2 2 → 최대 +540 · +225분). 매 회차 전수가 꼭 필요하다는 근거는 찾지 못해 기본안으로 두지 않는다.
2. **심은 결함 시험**: 끝 판 사본 6계열 + 아이콘 · 20~30개(계열마다 ≥ 3 · 절반 이상 문턱 근처 · 절차는 §12) → **차단 검출 ≥ 95%(대역별 보고) · 심은 요소 밖 새 모양·있음/없음 차단 0**.
3. **발주자 전수 대조(첫·끝 제출)**: 그 레인의 첫 제출과 끝 제출에서 발주자가 전수 대조를 하고 범위를 장부에 기록했다. 아니면 그 레인은 증거가 아니다. 중간 재검은 좁혀도 되지만 범위를 적는다.
4. **정밀도(전 회차)**: 모든 제출 회차의 유일 차단 묶음 기준 **F ≤ 5%** · 회차당 F ≤ 3 묶음. **H = 0** — 동결 뒤 `style-scope` 수정 횟수 + H 라벨 묶음.
5. **판정자 분리**: F/H 라벨은 범위 설정·후보 라벨을 하지 않은 두 번째 판정자가 한다. 첫 판정자와 교차 표본(≥ 30 묶음) 일치율 ≥ 85% 다(이번 리허설 89% · 27묶음).
6. **처분**: 끝 판 D 는 평가자가 실제로 돌린 스냅숏 생성 재렌더로만 풀린다. 끝 판은 exit 0 이나 exit 3(사용자 결정 항목 ≤ 2 묶음)에 닿는다.
7. **T 확인**: 끝 판에 남은 T·T? 를 사용자가 실제 차이로 받아들였다. 받아들이지 않은 것은 F 로 센다.
8. **안정·데이터**: 미실행 루프 0(재수집 두 번 안) · 비교용 데이터 일치율 중앙값 ≥ 0.95 · 선언 미대조 ≤ 10% · 끝 판에 미선언 일치율 미실행 0.
9. **(④ 만)**: 같은 두 레인에서 «좁혔다면 뺐을 case»에 반송 결함 0(기록 재생).
10. **손익 재확인**: 평가자가 잰 처분 모의 시간·분류 시간·하네스 시간을 §4 ③ 표에 넣는다. ③+④ 의 중앙값이 0 이상(손실이나 본전)이면 승격을 사용자 결정으로 올린다(품질 이득 대 시간). SDK 화면이 있었다면 그 census 가 표준 라우트·교차 확인을 미실행 없이 통과했어야 한다.

- **데스크톱**은 따로 승격한다(폭 무시 대조 재리허설 + 같은 조건).
- **승격 뒤에도 늘** 발주자가 본다: 데스크톱 · 미대조 case · 사람 확인 목록 · G2 사용자 결정 항목.

## 9. 사용자 판단 — 지금 정할 것 둘

1. **재생 그림자 두 레인에 평가자·발주자 시간을 쓸까**
   - 배경: W8 이 막기 전에 두 레인 동안 «기계 = 발주자»를 증명해야 한다. 레인 절차는 바뀌지 않는다. 발주자는 첫·끝 제출에서 전수 대조를 한다(첫 제출은 별도 검증 에이전트로 겹쳐 돌림).
   - 비용(레인당 · 보수)
     - 레인 벽시계 **0**(겹침) · 최악 +110~+225(동기)
     - 발주자 시간 약 2~4.5시간
     - 평가자 모델 시간 약 2.3~8.5시간
     - 하네스 준비 약 1.5~5시간
     - 두 레인 합 약 13~31시간(모델·발주자 시간 합)
   - 얻는 것
     - 끝 판 통과 뒤 W8 만 찾은 차이 목록. 이번 P2 끝 판이라면 실제 차이 7 + 후보 5 묶음이다. 후속 수리는 그때 정한다.
     - 승격하면 W8 이 첫 제출 전에 실제 차이를 한꺼번에 드러낸다. 이번 P1 은 첫 제출에 35묶음이었고, 발주자는 일곱 회차에 걸쳐 찾았다.
     - 속도는 ③+④ 에서 본전 근처(중앙값 P1 형 +10 · P2 형 +20분)다. ⑤ 까지 가야 −75 · −70분이다.
   - 위험: 승격 조건을 못 채우면 그 시간은 손실이다. 레인 품질은 지금과 같거나 낫다. 비교용 데이터를 시안에 맞추는 하네스 준비가 승패를 가른다. 이번 P1 형 데이터 조건이라면 심은 결함 시험에서 떨어진다(24/27).
2. **(승격 뒤) 발주자가 자기 전수 대조를 표본 확인으로 줄여도 되나**
   - 레인당 약 −80~−95분이 더 준다. 이것이 W8 의 확실한 속도 이득이다.
   - 위험: 같은 기준을 둘이 함께 틀릴 수 있다. W8 이 못 보는 칸(데스크톱 · case 밖 hover · 문구·데이터 표기 · 실계정 · 긴 데이터)도 있다. 그래서 데스크톱 · 미대조 case · 사람 확인 목록 · 데이터 의존(D) 목록 · G2 사용자 결정 항목은 계속 발주자가 본다.

- 그 밖은 설계로 정했다: 모양 fail-closed · 미선언 일치율 미실행 · D = 스냅숏 생성 재렌더 · 공용 부품 차단 유지 + 지역 변형 기본 · ② 는 레인 무변경 · 도구 판 고정 · 승격 조건 숫자.

## 12. 구현 단계 메모(검토 `closure-v4.md` §3 — 그대로 옮김)

- **심은 결함 절차 굳히기**
  - 대상은 스크립트가 구현 census 에서 무작위·층화로 고르고, 데이터가 다른 목록 행을 포함한다. 씨앗은 장부에 적는다. 심는 이는 범위를 정한 평가자가 아니어야 한다.
  - 크기 대역의 절반 이상을 문턱 근처(색 Δ6~12/255 · 글자·아이콘 +1px · 반경·틈 ±2px · 그림자 알파·흐림 소폭)로 둔다.
  - 한 요소만 바꾸는 심기(`:nth-of-type`)를 섞는다.
  - 재현율은 대역별로 보고한다. 계열마다 ≥ 3개, 대역마다 최소 수를 둔다(관문 2).
  - 지금 판형(굵은 변이 · 손으로 고른 클래스 전체)으로는 미래의 쉬운 시험을 막지 못한다. 이번 측정상 P2 형은 문턱 근처로도 통과한다(26/27).
- **D 는 «스타일이 데이터에 맞다»만 증명한다**
  - 독립 판정자는 지장간 한글 15묶음을 D 로 봤다. 발주자는 G2#1 ③ 에서 그것을 결함으로 반송했다. 재렌더(스냅숏 = 한글)도 D 로 통과시킨다.
  - 그래서 D 로 처분된 묶음은 «데이터 의존» 목록으로 감사·발주자에게 계속 보인다. 문구·데이터 표기는 W8 밖이라고 배너에 적는다.
- **SDK 교차 확인**
  - `style-scope` 에 SDK 기대값이 없으면 확인을 건너뛴다. 그러나 `web/sdk_registry.json` 이 있는 프로젝트에서 SDK 절이 없으면 **미실행**으로 둔다.
  - 캐시(304·메모리 캐시)·중단 요청의 `responseStatus` 경계를 픽스처로 둔다.
- **P1 형 상수 치환**: 선언된 `const` 의 초기값만 구문 단위로 바꾼다. 원본 파일은 손대지 않고 route fulfill 로만 바꿔 끼운다. 그래야 archive digest 확인과 양립한다.
- **재생 원천과 자원**
  - 재생 사본은 발주자 regcopy, 또는 제출 시점 레인 작업 트리의 `cp -c` 다. herdr 워크트리에서는 git 을 쓰지 않는다. 어느 쪽을 썼는지 운영 문서·장부에 적는다.
  - 같은 기계에서 레인과 겹쳐 돌면 부하가 늘어난다(리허설 1분 부하 15~23 / 20코어). 재생은 레인 대기 구간에 돌리거나 동시 실행 상한을 둔다.
