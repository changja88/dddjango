### 3-3. 검출기(K2a) — 일반 규칙만

- **X3 지운 모듈의 남는 소비자**
  - file-plan 의 비후행 `remove` `.py`(패키지 `__init__.py` 제외) 모듈을 기준선에서 import 하는 파일 가운데, 계획에 없는 것을 찾는다. 절대 import(`from M …` · `import M`)와 같은 패키지 안 상대 import(`from .x import` · `from . import x`)를 본다.
  - 제외 규칙(레인 고유 휴리스틱 0)
    - ① 같은 이름 폴더 승격 대체: 최종 상태에 `M/__init__.py` 가 있다(계획 add/empty/update, 또는 기준선 실존이고 remove 아님). import 경로가 살아 있다.
    - ② 소비자가 승격 폴더 부품이고, 그 `<칸>.py` 가 계획에 있다(R-3424 «경로는 언제나 `<칸>.py`»).
    - ③ 소비자 경로를 `_path_reject_reason` 이 거절한다(숨김 · 금지 세그먼트 — `.dddjango` 포함).
    - ④ 소비자가 계획에 있다 — 그 갱신이 처리한다고 본다(사각).
- **X4 입장 표 exact target(옛 계약 판형)**
  - 잘림: `update/remove/retain/weaken` 행의 `::이름…` · `::이름...` 이다.
  - 실존: `remove/retain/weaken` 행의 `::이름`(`::클래스::이름` 이면 끝 이름)이 그 행이 가리키는 `.py` 어디에도 정의되지 않았다.
    - 가리키는 `.py` = owner 칸과 coverage 칸의 경로 전부다. 맨 파일 이름은 기준선에서 같은 이름 파일이 하나뿐일 때만 그것으로 푼다.
    - 하나도 풀지 못하면 판정 불능이다(항목이 아니라 요약의 수).
    - retain/weaken 의 파일을 계획이 바꾸면 이름이 없어도 판정 불능이다. 이번 실행이 더한 case 일 수 있다.
  - `update` 행의 이름 실존은 보지 않는다. 옛 명세는 update 행에 새 case 이름을 적는 관례가 있었다(검토 B2). 계약 판형은 K2b 와 함께 보류한다.
  - `→` 오른쪽(새 이름)은 대조하지 않는다. 짝 행 판별 · 경로 접두 같은 레인 고유 규칙은 없다. 짝 행이 착륙이 더하는 파일을 가리키면, 그 파일은 기준선에 없고 계획 add 라 대조에서 빠진다.
- **X2 머리 import 차례(C7 표기가 있을 때)**
  - boundary-imports 행의 소비자를 본다. 소비자 슬라이스 범위의 **끝**보다 늦은 슬라이스에서 생기는(file-plan add) 모듈을 소비자가 import 하면 항목이다. 그 import 를 넣을 수 있는 슬라이스가 없으므로 확실 위반이다.
  - 소비자 범위 안에서 생기는 모듈은 보지 않는다. 그 슬라이스에 import 를 넣을 수 있기 때문이다.
- **사각**(리포트에 늘 적는다)
  - 계획 안 소비자는 처리된다고 낙관한다.
  - 동적 참조(`importlib` · 문자열 조립)는 보지 못한다.
  - boundary-imports 밖 import 는 보지 못한다. 다만 시험 파일 경계 import 는 R-3427 이 전부를 요구한다.
  - parametrize · 동적 생성 case 는 보지 못한다.
  - 동기 판형은 커밋된 기준선만 읽는다. 전체 실행은 overlay 사본으로 다시 판정한다.
  - 판정 불능 수를 적는다.

### 3-4. 도구 — `design_pregate.py`(byte 미러 `codex-dddjango/skills/dddjango/scripts/`)

  - **구현 제약**: 묶음 grep 1~2회 + `cat-file --batch` 1회로 읽는다. 파일마다 `git show` 를 부르는 것은 금지다(검토 m6 · 실측 근거 §2-3).

- **전체 실행에 합류**
  - 리포트에 `### 교차 예보` 절을 싣는다. 같은 항목을, 기준선 = HEAD 면 overlay 사본 기준으로 낸다.

  - 도구는 인용한 노트 파일의 그 줄에 같은 `x-` ID 와 «오탐»이 있는지까지 기계로 대조한다.
  - 하나라도 없으면 3(불비)이다.

### 3-5. 규범(graph-owned · Codex 의미 미러)

G1/G1′ 배너는 최종본 전체 실행의 `### 교차 예보` 항목이 전건 판정됐을 때만 낸다(근거 = `--check-report` exit 0) — 판정이 안 된 항목이 있으면 그 판정자를 G1 후보 다발(재리뷰 확인 다발 · arrange 점검)에 넣는다. 배너 예보 1행에 `교차 0 | 교차 k(판정 전건 · 실재 j)` 를 병기한다. `--cross-check` 가 실행 불능(exit 1)이면 그 1행을 기록하고 다발은 보낸다 — 최종본 전체 실행의 교차 절이 다시 판정한다(그것도 실행 불능이면 배너 1행에 사유를 적고 발주자에게 올린다).

## 6. K3 설계 — 발견의 전수 · 같은 종류 훑기 · 권고의 파급(보류 · 사용자 결정 2026-10-01 · v1 그대로 참고)

### 6-1. 무엇

리뷰어 넷의 산출 형식에 세 줄을 더한다.
- ① **전수**: 같은 종류의 흠이 여러 자리에 있으면 전부 적는다. 목록 대신 재현 검색(무엇을 · 어떤 패턴으로 · k곳)을 적어도 된다. «… 등»으로 줄이지 않는다.
- ② **같은 종류 훑기**: blocker · important 발견마다 명세 전체에서 같은 종류를 한 번 훑고 `같은 종류 훑기: <검색> → k곳 | 없음` 1행을 적는다. **확인(diff) 다발의 새 blocker · important 에도 적용한다** — 진단은 full 라운드 한정이었지만, 막는 A 인 db-R16-1 은 한 라운드 앞 확인 다발의 db-R15-2a 와 같은 종류였다(§2-3). 훑기는 판정 범위를 넓히는 것이 아니라 같은 흠의 다른 자리를 찾는 것이다.
- ③ **권고의 파급**: 권고 · 선택지를 낼 때는 그것이 바꿀 행 · 이름 · 수치를 적는다. 채택과 결정은 architect 가 실물 대조 뒤에 한다(권고는 가설 · K1 N+10 과 짝). 리뷰어는 결정 문안을 쓰지 않는다(한 주제 한 소유자 — 설계 명세 = architect).
