## 받아들인 한계

- 확정 줄은 자기 신고다(`--gate` 기록 결속은 다음 판 후보) · 까닭의 진위는 리뷰어가 본다.
- 마지막 창을 rebind 하면 다른 슬라이스만 건드린 확정의 verify red 가 풀리고, 닫힌 마지막 창을 rebind 만 하고 close 를 다시 안 해도 verify 가 초록이다(둘 다 2.45.1 도 같음 — 하려던 편집을 다른 창에 얹으면 close 가 막는다).
- 이미 집행한 V 가 든 보탬을 되돌리면 명세를 맞출 길이 없어 멈춘다(답을 다시 보탬으로 바꾸면 풀림).
- ⓐ 가 모두 `불가` 이고 계획이 0행인 명세의 `changes` 가 새로 붉다(계획 행 하나면 풀림).
- 리뷰어가 표 일부만 코드 상자에 넣으면 그 행은 빠진다.
- 마지막 슬라이스 뒤 감사가 승인 원소를 «기대 의미 그대로» 로 판정하는 드문 꼴은 멈춘다.

## 교훈

1. 도구 둘이 같은 표(창 허용 표)를 따로 지으면 이음에서 깨진다 — 되살리는 쪽도 같은 함수를 부르게 하고, 합친 뒤 진짜 도구 둘로 처음부터 끝까지 도는 사례를 둔다.
2. «이 창이 받는 파일» 을 계획 글에서 읽을 때는 결정 칸까지 본다 — 행에 적혔다고 편집 몫이 아니다.
3. 두 플러그인을 같은 클론에서 이어 낼 때는 core 배포 뒤 봉인 chore 를 먼저 push 한다 — `make release-web` 안의 `make verify` 가 판 올림으로 바뀐 매니페스트를 «봉인 후 변경» 으로 막는다(이 판은 web 배포가 한 번 검사에서 멈춘 뒤 다시 냈다 · 태그 · 커밋은 남지 않았다).
4. 여러 러너를 한꺼번에 돌리면 시간 상한 사례가 부하로 붉는다 — 붉은 사례만 따로 다시 돌려 가른 뒤, 기록 수치는 차례로 돈 마지막 실행의 것만.
