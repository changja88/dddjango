## 고침
- `_inflow_moves`(새): git 개명 쌍(옛 → 새) 가운데 아래를 모두 만족하는 것만 «승인 병합이 들인 이동» 으로 빼고 알림 줄(`[info] 승인 병합이 들인 이동 n파일 — 이 실행의 이동이 아니라 ⓑ 이동 묶음 의존에서 뺀다: …`)을 낸다.
  1. 옛 자리가 HEAD 에 없고, 기준..HEAD 첫 부모 사슬에서 그 경로를 바꾼 걸음이 하나 이상이며 전부 승인 병합의 상류판 그대로 수신(병합 판 == 둘째 부모 판)이다 — TG 수신 증명(`inflow.py` `receipt`)과 같은 술어 · 승인 목록 해석은 `subst.py` `_approved_merges` 재사용.
  2. 새 자리가 HEAD 에 있고, 사슬에서 그 자리를 마지막으로 만든 걸음(없음 → 있음)이 승인 병합의 상류판 그대로 수신이다.
  3. 승인 병합들이 상류에서 들인 개명(병합마다 공통 조상 → 둘째 부모의 git 개명 쌍 · 차례로 이음)이 옛 → 새 그대로다 — 받은 파일을 레인이 다시 옮겼으면(레인 커밋 · 병합 안 다른 자리 · 있던 자리에 덮어쓰기 · 작업 트리) 이 실행의 이동이다. 상류의 삭제 · 새 파일(개명으로 잡히지 않은 것)은 계보를 끊는다. 새 자리의 뒤 내용 고침은 이동이 아니다.
  4. 기준이 사슬 첫 걸음의 첫 부모다(TG · 치환 확인과 같은 경계).
- 판정이 안 서면(승인 목록 오류 · 기준 경계 밖 · git 실패 · OS 오류) 알림 줄 `[info] 승인 병합 이동 판정 불가 — …(git 개명 쌍을 모두 이 실행의 이동으로 센다)` 을 내고 2.4.0 판정으로 돈다. 승인 목록 해석의 역방향/합성 병합 의심 알림도 옮겨 낸다.
- 명세 `경로:` 가 옮긴다고 적은 G0 파일은 그대로 이 실행의 이동이다. 판정은 ⓑ 활성 ∧ 명세 밖 개명 ∧ `approved-merges.txt` 있음 일 때만 돈다 — 그 밖의 실행은 출력 · exit 가 2.4.0 과 같다.
- 의미 잔존(`refactor_audit.py residual`)도 같은 `moved_debt_files` 를 쓰고 같은 알림 줄을 낸다.
