# dddjango-web 2.8.3 — 실행 끝 커밋은 그대로 (마무리 합치기 걷기 · F4-109)

## 문제
- 현장 보고 F4-109: G2 승인 뒤 Phase 3 «미커밋 합치기»(`git reset --soft <pre_run_head>`)를 하기 전에 안전가드 넷을 본다. 그 가운데 ⓓ(HEAD == build-state `last_commit`)가 진행 기록 커밋 뒤에 통과하지 못해, 합치지 못하고 커밋 그대로 끝났다.
- 뿌리: 산출물 폴더(`.dddjango-web/`)는 기본으로 커밋되고, 그 안의 build-state 가 `last_commit` 을 담는다. 커밋은 제 해시를 담을 수 없으므로, 글자대로 따르면 가드 ⓒ(작업 트리 깨끗)와 ⓓ 가운데 하나는 늘 실패한다.
  - 2.0.0(dddart 화) 뒤로 합치기는 산출물 폴더를 git 밖에 둔 저장소에서만 돌 수 있었다.
  - 기본 설정에서는 한 번도 돌지 않았다(현장 기록의 `pre_run_head` 가 비워지지 않은 채 남아 있다).
- 가드를 고쳐 합치기를 살리는 길(설계 1판)은 적대 검토에서 차단 1 · 중요 5 가 나왔다. 합치기가 처음 실제로 돌면서 숨어 있던 길이 열린다:
  - 앞 실행이 남긴 `pre_run_head` 때문에 앞 실행 커밋과 사용자 커밋까지 한 묶음이 된다.
  - 반쯤 합친 뒤 재개하면 묶음이 쪼개진다.
  - G2 를 기다리는 동안 사용자가 만든 커밋이 섞인다.
  - 착륙 안내와 어긋난다.

## 사용자 결정
- (10-26) «가.» — 합치기를 걷고 dddjango(core)처럼 실행이 만든 커밋을 그대로 둔 채 끝낸다. 실제 레인 동작(커밋 그대로)에 글을 맞추는 수리다.

## 고침 (조정자 글만 · scripts · references · assets · 역할 7 · 스킬 무변)
- **Phase 3**: «미커밋 합치기» 절(가드 ⓐ~ⓓ · 실행 · 보고 · D+ 폴백 · 생략 케이스)을 걷고 새 문단 «커밋은 그대로 둔다» 하나로 바꾼다:
  - 이 실행이 만든 커밋을 합치거나 지우거나 고쳐 쓰지 않는다(`git reset` · squash · rebase · `--amend` 없음).
  - 커밋을 하나라도 만든 실행이면 보고 끝에 `커밋: 이 실행의 커밋은 그대로 둡니다(합치지 않음).` 한 줄.
  - 이 실행의 마무리 커밋(G2 승인 기록) 뒤에는 이 실행에서 build-state 를 더 고치지 않는다. 같은 폴더의 새 요청은 «`build-state.json` 스키마» 의 갱신 시점 · 리팩토링 «R0′ 폴더» 대로 시작한다.
  - 옛 판이 쓴 `pre_run_head` 키가 남아 있어도(세션 재개 · 같은 폴더를 다시 쓰는 요청) 무시하고 그 값으로 reset 하지 않는다(reset 명령도 안내하지 않는다).
  - 그 키가 있는 실행을 세션 재개로 이어 받았으면 보고에 `옛 판 G2 배너의 합치기는 이 판에서 하지 않습니다(커밋 그대로).` 한 줄.
- **G2 배너**: «합치기 고지 1줄» · «G2 승인이 합치기 동의를 겸한다» 를 걷는다. 그 대신 «승인 시 Phase 3» 앞에 마무리 커밋을 정한다 — 승인 답을 받으면 build-state 에 `g2_approved` · `g2_decision` 을 적어 산출물 폴더만 담은 마무리 커밋을 만든다(`last_commit` 은 고치지 않는다).
- **build-state `pre_run_head` 걷음**: 스키마 · «갱신 시점» · Phase 2 진입 준비 · 수정 모드 step 8 · 리팩토링 R0′ 새 점검의 실행 필드 · 리팩토링 Phase 2 진입 준비. 합치기 말고 읽는 곳이 없다(scripts · 역할 · 스킬 · references 0).
- **`last_commit` 은 둔다**: 중단 복구가 읽는다(«중단 복구는 `last_commit` 이후만 되돌린다»).
  - 스키마 설명: «네가 만드는 커밋마다(마무리 커밋 빼고) 갱신한다. 중단 복구 기준(Phase 2 슬라이스 다시 부르기 때만 — step 3.1)». «갱신 시점» 의 굵은 문장도 같은 범위로 고친다.
  - 마무리 커밋에서 고치지 않는 까닭: 고치면 그 고침이 미커밋으로 남아 실행이 더러운 작업 트리로 끝난다. 합치기 가드가 없어진 뒤로는 그 값을 읽을 일도 없다.
- 머리 · «경계» 의 «네가 직접 쓰는 것» 목록에서 «마무리 미커밋 합치기» 를 걷는다.
- Claude · Codex 같은 글(Codex 의 «Coordinator 직접 작업» · «Codex 함정» 덧말은 걷은 절에만 있었다).
- `Makefile` verify-web:
  - 문단 대조 표지 일곱을 더한다 — `"last_commit": "<` · `갱신 시점: 산출물 폴더 확정 직후` · `1. **Phase 2 진입 준비**` · `8. **G2 배너**` · `**커밋은 그대로 둔다**` · `8. **Phase 2 진입 준비·Phase 3 마무리는` · `설계 명세·구현 코드를 직접 쓰지 않는다 — 각각 architect·coder-web에 위임한다.`(«경계» 줄). 리팩토링 Phase 1~2 줄은 이미 표지가 있다.
  - 걷은 말 없음 검사 한 줄: 두 조정자에서 `pre_run_head` 는 정확히 1 줄(무시 문장)이고, `reset --soft` · `soft-reset` · `미커밋 합치기` · `미커밋으로 합` 은 0 줄이어야 한다. 줄 대조로 지킬 수 없는 줄(두 판이 일부러 다른 머리 줄 · R0′ 줄)과 한쪽에만 새 줄을 끼운 경우를 이 검사가 잡는다.
- 그림 문서:
  - web 동작 흐름(`docs/work_flow_web.spec.json` · `.html`)의 마무리 칸 «검증 보고 · 미커밋 합치기» → «검증 보고 · 커밋 그대로».
  - 가이드(`docs/work_flow_web_guide.html`)의 조정자 일 목록에서 «미커밋 합치기» 를 걷는다.
  - 가이드의 «04 · 끝» 카드: 제목 «검증 보고 · 커밋 그대로» · 본문 «실제로 돌린 검증만 보고합니다. 작업 중 만든 커밋은 합치지 않고 그대로 둡니다.»
- 자매 차이: dddart 에는 합치기 절이 있다(같은 가드 글이라 산출물 폴더를 기본으로 커밋하면 돌지 않는다) — AGENTS 의 «dddart 와 다른 점» 여섯째로 적는다.

## 행동 변화
- 기본 설정(산출물 폴더 커밋) 저장소: 끝 상태는 전과 같이 커밋 그대로다. 달라지는 것:
  - G2 배너의 합치기 고지 줄이 없다.
  - Phase 3 이 가드 git 명령 넷과 reset 을 돌지 않는다.
  - 끝 보고의 «`git reset --soft <pre_run_head>`로 미커밋으로 모을 수 있습니다» 안내 대신 «커밋은 그대로 둡니다(합치지 않음)» 한 줄.
  - build-state 에 `pre_run_head` 를 쓰지 않는다.
  - 마무리 커밋 뒤 `last_commit` 을 고치지 않아 깨끗한 작업 트리로 끝난다.
- 산출물 폴더를 git 밖에 둔 저장소: 전에는 합치기가 돌아 스테이징된 미커밋 한 묶음으로 끝났다. 이제는 커밋 그대로다.
- 슬라이스 0 의 파일 목록 · 참조 완전성 · 기록 경로를 Phase 3 보고에 다시 적던 것(«합치기 뒤에는 커밋 분리가 사라지므로»)은 걷었다. 커밋이 남고, G2 배너에 같은 내용이 있다.

## 한계
- 2.8.2 로 G2 배너(«승인 시 … 합칩니다»)를 보고 승인한 실행을 2.8.3 이 이어 끝내면 합치지 않는다. 대신 보고에 «옛 판 G2 배너의 합치기는 이 판에서 하지 않습니다» 한 줄을 둔다. 기본 설정에서는 그 배너 뒤에도 가드가 막아 커밋 그대로였으므로 결과가 같다(산출물 폴더를 git 밖에 둔 저장소만 다르다).
- 그런 판 사이 실행은 옛 판이 마무리 커밋 뒤 고친 build-state 가 미커밋으로 남아 있을 수 있다. 이 판은 그것을 고치지 않는다. 2.8.2 실제 레인도 늘 그 상태로 끝났고, 다음 요청의 G0 가 작업 트리가 깨끗하지 않은 것을 «커밋/스태시 vs 그대로» 로 묻는다.
- 변경을 하나로 모은 꼴이 필요하면 착륙 쪽(병합 방식)이나 사용자가 정한다. 플러그인은 이력을 고쳐 쓰지 않는다.
- 같은 폴더에 옛 판이 남긴 `pre_run_head` 값은 지우지 않는다(무시만). 옛 판으로 되돌려 같은 폴더를 다시 쓰면 그 옛 판의 합치기 글이 그 값을 읽는다. 판 되돌림은 지원 범위 밖이다.
- dddart 의 같은 절은 이 저장소 밖이다.

## 적대 검토 반영
설계 2판 적대 검토(차단 0 · 중요 1 · 사소 5)를 모두 반영했다. 설계 방향은 그대로다.

- **중요 — 가이드 «04 · 끝» 카드**: 걷기에서 빠져 «스테이징된 미커밋 한 묶음 · `git diff --staged` 로 보고 직접 커밋» 을 그대로 안내하고 있었다. 이 판 뒤에 그 명령을 열면 빈 출력이다. 카드를 «검증 보고 · 커밋 그대로» 로 고쳤다.
- **사소 — 문단 대조 빈틈**: 고친 줄 가운데 «경계» 줄은 두 판 글이 같은데 표지가 없었다. 일부러 다른 줄(머리 줄 · R0′ 줄)은 줄 대조로 지킬 수 없다. 표지 하나와 걷은 말 없음 검사 한 줄을 더했다.
- **사소 — `last_commit` 설명의 범위**: 스키마 줄의 «중단 복구 기준» 에 범위가 없어, 마무리 커밋이나 사용자 커밋까지 되돌린다고 읽힐 수 있었다. «Phase 2 슬라이스 다시 부르기 때만» 으로 좁혔다. 갱신하는 커밋 종류를 일부만 늘어놓던 괄호는 «네가 만드는 커밋마다(마무리 커밋 빼고)» 로 바꿨다.
- **사소 — 판 사이 실행의 설명**: 옛 판 G2 배너가 «합칩니다» 라고 약속한 실행을 이 판이 이어 끝내도, 약속이 바뀐 것을 말하지 않았다. 세션 재개로 이어 받은 실행에 옛 키가 있으면 보고에 한 줄을 둔다.
- **사소 — 마무리 커밋의 정의**: 이 커밋은 지나가는 말로만 나왔다. «깨끗한 작업 트리로 끝난다» 는 이 커밋에 기댄다. G2 배너 단계에 언제 · 무엇을 담는지를 적었다.
- **사소 — Phase 3 둘째 문장의 주어**: 괄호 «같은 폴더를 다시 쓰는 요청» 때문에, 새 요청을 시작할 때도 build-state 를 고치지 말라는 뜻으로 읽힐 여지가 있었다. 그렇게 읽으면 새 요청을 시작하는 규칙과 부딪친다. 주어를 «이 실행» 으로 좁히고, 새 요청은 어느 절대로 시작하는지 적었다.
- 대역 다섯(재개 넷 + 새 요청 하나) 어디에서도 reset · revert · 합치기는 일어나지 않았다.

## 다음 판 후보 (검토가 찾은 전부터 있던 것 · 이번 수리와 무관)
- 같은 폴더의 새 요청에서 앞 요청의 `slices` · `git_snapshot` · `test_rule` 이 Phase 2 진입 준비 전까지 남는다(갱신 시점은 `g2_*` 만 되돌린다).
- 진행 단계가 설계 이후인데 G0 기록이 없는 폴더를 다루는 규칙이 없다.
- 끝난 리팩토링 폴더에서 모드 판별 절과 리팩토링 «R0′ 폴더» 의 판별이 서로 다르다.
- Phase 2 진입 준비의 «미추적 산출물이 남으면 중단 복구가 명세를 쓸어낼 수 있다» 와 step 3.1 의 «미추적 파일 일괄 삭제 금지» 가 서로 어긋난다.

  - 음성: 고친 줄에 한쪽만 글을 덧붙이면 표지가 있는 줄은 모두 red(새 «경계» 표지 포함 · Claude 쪽 · Codex 쪽 둘 다).

- 대역(같은 모델 · 새 Phase 3 절만):
