# dddjango 2.31.1 · dddjango-web 2.9.1 — 요청 가이드 개정(가이드만)

실행 규칙 · 검사기 변경 없음. 두 플러그인의 `REQUEST_GUIDE.md` 와 Codex 짝만 고친다.

## 문제

가이드를 보고 써도 요청 글에 같은 문제가 난다. 실제 요청 글을 읽어 열두 가지로 정리했고, 가이드로 풀리는 것만 이번에 고친다.

- 사용자가 든 것: 요청을 쓴 날짜 같은 쓸데없는 문구 · 요청에 도움 안 되는 다른 문맥 · 정확히 적어야 할 스펙을 뭉뚱그림.
- 실제 글에서 찾은 것: 새로 정한 것이 지금 동작처럼 섞임 · 구현 세부까지 옮김 · 지어낸 낱말 · 규격을 적을 칸이 없음 · 항목끼리 번호로 가리킴.
- 이번 밖: 사실이 틀림 · 스펙이 빠짐 · 요청 글 리뷰가 못 잡음 · 고칠 때마다 크게 흔들림(리뷰 기준 · 검사 스크립트 · 요청을 쓰는 세션의 일하는 방식이라 가이드 밖이다).

## 결정

- 사용자: 구현 세부는 일반적으로 쓰지 않는다. 가이드로 고칠 수 있는 것부터 가이드만 고친다. 계획 승인.
- 운영자 해석(이의 시 뒤집음): 특별한 경우 = 사용자가 이름을 들어 넣으라고 한 규격. 웹 요청은 필요한 기능과 시안이면 되므로 `현행 그대로` · 규격 칸 · 나쁜 예는 dddjango 가이드에만 넣는다.

## 고침

기준 하나: 밖에서 보이는 결과 · 밖과 주고받는 값은 적고, 바뀌어도 그 둘이 그대로인 것은 구현 세부라 적지 않는다.

- 적는 항목은 뭉뚱그리지 않는다(갈래 · 사용자가 정한 값까지).
- 다른 저장소의 지금 동작을 옮겨 오는 항목은 글로 `현행 그대로: <동작 전체>`, 이 저장소의 지금 동작을 지키는 항목은 `유지: …`(dddjango).
- `제외:` 는 1번의 일로 오해해 만들 수 있는 것만 · 누가 어떻게 맡는지는 적지 않는다.
- 사용자가 이름을 들어 넣으라고 한 규격은 특별 기술 요청 사항에(dddjango).
- «대신 쓴 요청» 표시를 뺀다. 대신 쓴 요청의 미룸 · 승인(web 은 미룸)은 항목마다 `사용자 원문: «<그 말>» <절대 경로 파일:줄>(<시각>)` · 물음에 답한 말이면 ` · 물음 <절대 경로 파일:줄>` · 붙일 수 없으면 적지 않는다.
- «사용자가 정하지 않은 결과» → «사용자가 정하지 않은 새 결과는 지어 넣지 않고».
- 적지 않는 것에 더함: 구현 세부 · 옮겨 적은 코드의 폴더와 파일 · 칸 안의 군더더기(요청을 쓴 날짜 · 시각 · 사용자 말 인용 · 대화 기록 경로 · 쓰게 된 사정 · 결과를 바꾸지 않는 남의 속사정 · 운영 사정 · 지어낸 낱말 · 번호로 가리키는 말).
- 나쁜 예 하나(실제 실패한 요청 글 · 이름은 바꿈 · dddjango).

## 검토

독립 검토: 차단 3 · 중요 8 · 사소 4 → 좁은 재확인 둘 · 마지막 차단 0. 고친 큰 것 — 세 줄이 쓰던 서로 다른 기준을 하나로 · `사용자 원문:` 꼴을 조정자 «결정 출처» 확인 절차에 맞춤(인용 · 물음 줄) · 제외 기준이 나쁜 예를 통과시키던 것 · 나쁜 예를 실제 글로.

## 효과 재기

같은 일감(서버 나누기 요청 · 나쁜 예에 쓰지 않은 것)을 같은 재료로, 옛 · 새 가이드 각 두 번 새 세션이 쓰게 하고, 어느 판인지 모르는 새 세션이 같은 잣대로 셌다. 멈출 기준: 문제 수가 줄지 않거나 설계 지시 · 구현 세부가 늘면 멈춤 — 걸리지 않음.

## 한계

- 요청을 쓰는 세션의 지침과 검사 스크립트가 지금 «대신 쓴 요청» 표시를 요구하고 사용자가 정하지 않은 항목을 막는다. 그쪽을 함께 고치지 않으면 새 가이드대로 쓴 글이 막힌다(사용자 몫).
- «대신 쓴 요청» 표시를 빼는 대가: 규칙을 어기고 출처 없이 적은 미룸을 조정자가 사용자 결정으로 기록할 수 있다. 조정자 «결정 출처» 한 문장을 고치는 안은 다음 판 후보. 효과 재기에 미룸이 없어 재지 못했다.
- 사실이 틀린 문제 · 리뷰가 못 잡는 문제는 그대로다.
