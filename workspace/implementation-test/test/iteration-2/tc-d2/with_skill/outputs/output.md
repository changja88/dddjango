# PasswordValidator 테스트 코드 리뷰

## 잘된 점

테스트가 전반적으로 AAA 패턴을 따르고, 각 테스트가 하나의 행위를 검증하며, 테스트 간 상태 공유가 없다. `PasswordValidator`는 외부 의존성이 없는 순수 로직이므로 mock 없이 실제 객체로 테스트하는 것도 올바른 접근이다. 생성자 파라미터(`min_length`, `require_special`) 변형에 대한 테스트도 포함되어 있다.

---

## 발견 사항

### 1. 라인 커버리지 100%의 함정 -- 경계값 테스트 부재

[Coverage & Mutation Testing] -- 라인 커버리지 100%는 "모든 코드 줄이 한 번 이상 실행되었다"는 의미일 뿐, 모든 조건 분기가 제대로 검증되었음을 뜻하지 않는다. 이 테스트 스위트의 핵심 문제는 **경계값(boundary)에 대한 검증이 전혀 없다**는 점이다.

`validate` 메서드의 `len(password) < self.min_length` 조건을 예로 들면:

- `test_too_short`는 길이 4인 비밀번호(`'Ab1!'`)로 테스트 -- 8보다 훨씬 작다.
- `test_valid_password`는 길이 8인 비밀번호(`'Abcdef1!'`)로 테스트 -- 정확히 경계.
- 하지만 **길이 7(경계-1)**인 비밀번호에 대한 테스트가 없다.

만약 누군가 `<`를 `<=`로 바꾸면 (mutmut의 대표적 비교 연산자 변형), 길이 8인 비밀번호가 invalid로 판정되지만, 현재 테스트에서 `test_valid_password`는 길이 8로 통과하므로 이 변형을 잡는다. 그러나 `<`를 `!=`로 바꾸는 등의 다른 변형에는 취약하다.

`strength` 메서드에서는 문제가 더 심각하다:

- `len(password) >= 12` 경계: 길이 12인 비밀번호 테스트 없음 (11 vs 12)
- `len(password) >= 16` 경계: 길이 16인 비밀번호 테스트 없음 (15 vs 16)
- `special_count >= 2` 경계: 특수문자 1개 vs 2개 비교 없음
- `score >= 2` 경계: score 1 vs 2 비교 없음

**이것이 "라인 커버리지 100%인데 버그가 나오는" 핵심 원인이다.** 비교 연산자 하나만 바뀌어도 감지하지 못하는 테스트 스위트는 실질적으로 약하다.

### 2. 약한 단언 -- errors 내용 미검증

[The Liar / Secret Catcher] -- `test_too_short`, `test_no_uppercase`, `test_no_lowercase`, `test_no_digit`, `test_no_special` 모두 `assert valid is False`만 검증하고, `errors` 리스트의 **내용을 검증하지 않는다**.

```python
def test_too_short():
    v = PasswordValidator()
    valid, errors = v.validate('Ab1!')
    assert valid is False
    # errors에 '최소 8자 이상이어야 합니다'가 포함되어 있는지 확인하지 않음
```

이렇게 하면 `validate`가 잘못된 이유로 False를 반환해도 테스트가 통과한다. 예를 들어 `'Ab1!'`는 길이가 짧을 뿐 아니라 특수문자도 포함되지 않은 것처럼 판정될 수 있는데(실제로는 `!`가 포함되어 있으므로 아니지만), errors의 정확한 내용을 확인하지 않으면 어떤 검증 규칙이 어떤 에러를 생성하는지 보장할 수 없다.

### 3. 복합 에러 케이스 누락

[Dodger (회피자)] -- 현재 테스트는 한 번에 하나의 조건만 실패하는 입력만 사용한다. 하지만 실제 사용에서는 여러 조건이 동시에 실패하는 경우가 빈번하다.

- 빈 문자열 `''` 입력 시 모든 에러가 동시에 반환되는지
- 완전히 잘못된 입력(예: `'a'`)에서 여러 에러가 올바르게 누적되는지

이런 테스트가 없으면, 에러 누적 로직에 버그가 있어도(예: 조기 리턴으로 첫 번째 에러만 반환) 발견하지 못한다.

### 4. `strength` 메서드의 점수 조합 테스트 부족

[Dodger (회피자)] -- `strength` 메서드는 3가지 조건(길이 >= 12, 길이 >= 16, 특수문자 >= 2)의 **조합**으로 점수를 매기는데, 테스트는 한 가지 조합씩만 검증한다.

- `test_strength_medium`: `'Abcdef1!'` (길이 8, 특수문자 1개) -- score 0 -> medium
- `test_strength_strong`: `'Abcdefghijklmn1!@'` (길이 18, 특수문자 2개) -- score 3 -> strong

score가 정확히 1인 경우(medium)와 정확히 2인 경우(strong 경계)를 구분하는 테스트가 없다. 예를 들어:

- 길이 12이고 특수문자 1개: score 1 -> medium (테스트 없음)
- 길이 12이고 특수문자 2개: score 2 -> strong (테스트 없음)
- 길이 16이고 특수문자 1개: score 2 -> strong (테스트 없음)

### 5. 반복적 테스트 패턴 -- parametrize 미사용

[Missing parametrize] -- 실패 조건 테스트(`test_too_short`, `test_no_uppercase`, `test_no_lowercase`, `test_no_digit`, `test_no_special`)는 동일한 구조에 입력 데이터만 다르다. `pytest.mark.parametrize`를 사용하면 가독성과 유지보수성이 향상되고, 새로운 케이스를 추가하기도 쉬워진다.

### 6. Fixture 미활용으로 인한 반복

[Excessive Setup] -- 모든 테스트에서 `v = PasswordValidator()`를 반복 생성한다. 이 정도 크기에서는 심각하지 않지만, fixture로 추출하면 생성자 인터페이스가 변경될 때 수정 지점이 줄어든다.

## 핵심 요약

**"라인 커버리지 100%인데 버그가 나오는" 근본 원인은 경계값 테스트의 부재다.**

라인 커버리지는 "코드의 모든 줄이 실행되었는가"만 측정한다. 비교 연산자가 `<`인지 `<=`인지, `>=`인지 `>`인지의 차이는 경계값 입력으로만 검증할 수 있는데, 현재 테스트에는 그 경계를 정확히 찌르는 입력이 없다. 브랜치 커버리지를 활성화하고, 뮤테이션 테스트(mutmut)를 도입하면 이런 종류의 테스트 품질 문제를 체계적으로 발견할 수 있다.

가장 시급한 개선 순서:

1. **경계값 테스트 추가** -- `validate`의 길이 7/8, `strength`의 길이 11/12, 15/16, 특수문자 1/2개
2. **errors 내용 검증** -- 실패 테스트에서 반환된 에러 메시지가 정확한지 확인
3. **점수 조합 테스트** -- `strength`의 score 0/1/2/3 각 경우를 명시적으로 테스트
4. **parametrize 도입** -- 반복적인 실패 조건 테스트를 통합
