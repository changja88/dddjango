## 1. 데이터베이스 모델링 프로세스

### 1.1 작업 순서

```
업무 파악 → 개념적 데이터 모델링 → 논리적 데이터 모델링 → 물리적 데이터 모델링
```

### 1.2 업무 파악

- 말을 믿지 말자
- UI를 만들어서 상호 일치된 합의안을 갖자

### 1.3 개념적 데이터 모델링

관계형 모델링의 핵심. 이것을 잘 했다면 논리적, 물리적 데이터 모델링은 못할 수가 없다.

**ERD (Entity Relationship Diagram)**:
- 정보(Attribute) → Column이 된다
- 그룹(Entity) → Table이 된다
- 관계(Relation) → PK, FK가 된다

**ERD를 만드는 방법**:
1. 연관된 정보를 담고 있는 덩어리를 찾는다
2. 그룹별로 조회가 가능하며 조인에 유리하도록 분리한다
   - 큰 덩어리를 만들면 전체를 조회해야 하고 중복이 발생한다

**식별자(PK) 찾기**:

| 키 종류 | 설명 |
|---------|------|
| 후보키 (Candidate Key) | 식별자가 될 수 있는 키 |
| 기본키 (Primary Key) | 후보키 중에서 선택된 키 |
| 대체키 (Alternate Key) | 후보키 중에서 선택되지 않은 키 |
| 중복키 (Composite Key) | 두 가지 이상의 키가 합쳐져서 기본키가 된 경우 |

- 자연스럽게 기본키가 될 수 있는 컬럼이 없으면 인조키(surrogate key)를 만들어 사용한다

**Cardinality (기수)**:
- 1:1 관계
- 1:N 관계
- N:M 관계

**Optionality**:
- 한쪽에 NULL이 올 수 있는지 여부
- 1 표기: 반드시 있어야 한다
- O 표기: NULL일 수 있다

## 2. 정규화와 역정규화

### 2.1 정규화

논리적 데이터 모델링 단계에서 수행. 중복을 제거하고 데이터 무결성을 보장한다.

### 2.2 역정규화 (Denormalization)

성능이나 개발 편의성을 위해 정규화를 거스르는 것.

**핵심 원칙**:
- 정규화는 대체로 쓰기에 초점이 맞춰져 있다
- 정규화를 하면 표가 여러 개로 쪼개지고, 읽기 위해서는 JOIN이 필요하다
- 역정규화는 중복을 허용하여 JOIN을 없애서 읽기 성능을 올리는 작업이다
- **반드시 정규화를 먼저 하고, 필요한 경우에 역정규화를 한다. 읽기가 많다고 바로 역정규화하는 것은 잘못된 접근이다**

**역정규화 사례 4가지**:

| # | 기법 | 설명 |
|---|------|------|
| 1 | 테이블 병합 | 조인이 자주 발생하는 테이블을 하나로 합침 |
| 2 | 파생 컬럼 추가 | 자주 발생하는 집계를 컬럼으로 추가 |
| 3-1 | 수직 분할 | 용량이 큰 컬럼만 따로 테이블로 분리 (샤딩, 스케일 아웃) |
| 3-2 | 수평 분할 | ID 범위 기준으로 다른 테이블로 분리 |
| 4 | 관계의 역정규화 | FK를 추가하여 조인 횟수를 줄이는 지름길 |

## 3. 물리적 데이터 모델링과 성능 최적화

구체적인 제품에 맞는 현실적인 표를 만드는 단계. 성능이 핵심이다.

**최적화 순서** (순서를 지킬 것):
1. 슬로우 쿼리를 찾아서 최적화
2. 인덱스 적용
   - 읽기 성능을 비약적으로 올리고, 쓰기 성능을 비관적으로 희생시킨다
3. 애플리케이션 단에서 캐시 활용
4. **최후의 보루**: 역정규화 (대가가 크므로 반드시 다른 방법을 모두 시도 후)

## 4. 인덱스 아키텍처: B+Tree

### 4.1 B+Tree 특징

- 트리 구조, Key 값으로 정렬
- Child 노드가 여러 개 (높은 팬아웃)
- 각 노드가 메모리가 아닌 디스크에 존재
- **실제 데이터는 리프 노드에만 존재**
- Sibling 포인터 → Range 쿼리 가능

### 4.2 쓰기 (Create)

- 여러 번의 디스크 쓰기 발생 가능:
  - 새 노드 생성
  - 부모 노드 업데이트
  - 옆 노드에서 데이터 이동
  - 새 데이터 삽입
- 중간에 DB가 죽으면 데이터 오염 위험
  → **WAL (Write-Ahead Log)**: 실제 쓰기 전에 어떤 write를 할지 미리 기록

### 4.3 업데이트 (Update)

- 읽기와 동일하게 트리를 따라가서 리프 노드의 데이터만 갱신

## 5. 인덱스 아키텍처: LSM Tree

### 5.1 Log Structured Storage Engine

- log 파일 기반, append-only (수정 없음)
- 키-밸류 방식으로 저장
  - 쓰기는 매우 쉬움
  - 읽기는 풀 스캔 필요 → 인메모리 인덱스로 해결 (키 + 주소값)
- 데이터 중복 문제 → Segment File + Compaction으로 해결

### 5.2 Segment와 Compaction

- 하나의 파일이 아닌 여러 Segment 파일로 분리
- 현재 쓰고 있는 파일을 제외한 파일은 불변(immutable)
- 불변 파일에 대해 Compaction(중복 제거 + 병합) 수행

### 5.3 LSM Tree = SSTable (Sorted String Table)

- Segment 파일 내부가 **Key로 정렬**되어 있음
- 장점: 메모리에 모든 키를 가질 필요 없음 (범위 추론 가능)
- 장점: Range 쿼리 가능

### 5.4 쓰기 흐름

```
데이터 → MemTable (인메모리, 정렬) + Log 파일 (보조)
         ↓ 일정 용량 초과
         SSTable (디스크) → Log 파일 비움
         ↓ SSTable 증가
         Compaction → 더 큰 SSTable
```

### 5.5 읽기 흐름

```
MemTable → (없으면) → 인메모리 인덱스에서 범위 추론 → SSTable 스캔
```

### 5.6 B+Tree vs LSM Tree 비교

| 항목 | B+Tree | LSM Tree |
|------|--------|----------|
| 읽기 | 빠름 (트리 탐색) | 느림 (여러 SSTable 확인) |
| 쓰기 | 느림 (여러 번 디스크 쓰기 + WAL) | 빠름 (MemTable + Log만) |
| 적합 | 읽기 중심 워크로드 | 쓰기 중심 워크로드 |
| 사용 | 대부분의 RDBMS (MySQL, PostgreSQL) | NoSQL (Cassandra, LevelDB, RocksDB) |

## 6. 아키텍처 관점: 데이터베이스는 세부사항이다

> 출처: Robert C. Martin, *Clean Architecture*

### 6.1 핵심 원칙

- 아키텍처 관점에서 데이터베이스는 엔티티가 아니다. 데이터베이스는 **세부사항**이므로 아키텍처의 구성요소 수준으로 끌어올릴 수 없다
- 데이터를 테이블에 행 단위로 배치한다는 사실은 아키텍처적으로 전혀 중요하지 않다
- 애플리케이션의 유스케이스는 이러한 방식을 알아서는 안 되며 관여해서도 안 된다
- 데이터가 테이블 구조를 가진다는 사실은 오직 **아키텍처의 외부 원에 위치한 최하위 수준의 유틸리티 함수만** 알아야 한다

### 6.2 잘못된 설계

- 많은 데이터 접근 프레임워크가 테이블과 행이 객체 형태로 시스템 여기저기에 돌아다니게 허용한다
- 이렇게 하면 유스케이스, 업무 규칙, 심지어 UI조차도 관계형 데이터 구조에 결합된다

### 6.3 결론

- **데이터는 중요하다. 하지만 데이터베이스는 세부사항이다.**
