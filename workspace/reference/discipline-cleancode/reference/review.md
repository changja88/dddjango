# 클린코드 Internal vs External 상충/모순/불일치 의사결정 문서

> Internal: Clean Code [CC], 구현 패턴 [IP], 객체지향의 사실과 오해 [OO], 파이썬 클린코드 2nd [PC]
> External: A Philosophy of Software Design [APoSD], Code Complete [CodeC], The Pragmatic Programmer [PP], Refactoring [Ref], Google Python Style Guide [Google], PEP 문서 [PEP]

---

### [1] 주석의 역할과 필요성

**상충 유형**: 모순

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] / 구현 패턴 [IP] | A Philosophy of Software Design [APoSD] |
| 주장 | 주석은 코드로 의도를 표현하는 것에 실패했기 때문에 작성하는 "필요악"이다 | "좋은 코드는 주석이 필요 없다"는 통념에 반대하며, 인터페이스 주석과 멤버 변수 주석은 반드시 작성하라 |

**Internal 근거**: 주석 대신 코드 자체로 의도를 표현해야 한다. 주석은 코드와 동기화가 깨지기 쉽고, 유용한 주석은 법적 주석, 의도 설명, 경고 등 제한된 유형뿐이다. 주석을 정당화할 수 있는 경우에만 사용해야 하며, 코드와 주석 간 일관성 유지 비용을 고려해야 한다. [CC] [IP]

**External 근거**: 인터페이스 주석(모듈의 동작, 인자, 반환값, 부작용, 예외)과 멤버 변수 주석은 짧게라도 반드시 작성해야 한다. 구현 주석은 "무엇"이 아닌 "왜"를 설명하라. 주석은 복잡성을 줄이고 Unknown Unknowns를 방지하는 핵심 도구다. [APoSD]

**추천**: 병합 (인터페이스 주석/독스트링은 APoSD 방식으로 필수 작성하되, 인라인 주석은 CC 방식으로 최소화)

### [2] 함수/모듈의 크기 철학

**상충 유형**: 상충

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] | A Philosophy of Software Design [APoSD] |
| 주장 | 함수는 작게, 더 작게 만들어라. 한 가지만 해야 한다 | 최고의 모듈은 단순한 인터페이스 뒤에 강력한(큰) 기능을 숨기는 "깊은 모듈"이다 |

**Internal 근거**: 함수를 만드는 첫째 규칙은 "작게!"이고, 둘째 규칙도 "더 작게!"이다. 의미 있는 이름으로 다른 함수를 추출할 수 있다면, 그 함수는 여러 작업을 하고 있다. 추상화 수준을 하나로 유지해야 한다. [CC]

**External 근거**: 과도하게 작은 함수/클래스는 "얕은 모듈"이 되어, 인터페이스가 구현만큼 복잡해진다. 호출자가 여러 단계를 전부 알아야 하는 상황이 오히려 복잡성을 높인다. 단순한 인터페이스 뒤에 복잡한 구현을 숨겨 인지 부하를 줄여야 한다. [APoSD]

**추천**: 병합 (공개 인터페이스는 APoSD처럼 깊은 모듈로 설계하되, 내부 구현은 CC처럼 작은 private 함수로 분해)

### [3] DRY 원칙의 범위

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] / 파이썬 클린코드 [PC] | The Pragmatic Programmer [PP] |
| 주장 | 코드의 중복을 제거하라. 같은 작업의 반복은 아이디어를 제대로 표현하지 못한 증거다 | DRY는 코드 중복이 아니라 "지식의 중복"을 금지하는 것이다. 같은 코드라도 다른 지식이면 중복이 아니다 |

**Internal 근거**: "어쩌면 중복은 소프트웨어에서 모든 악의 근원이다." 코드에 있는 지식은 단 한번, 단 한 곳에 정의되어야 한다. 동일한 계산식이 반복되면 함수로 추출하라. [CC] [PC]

**External 근거**: 우연히 같은 코드지만 서로 다른 도메인 지식을 표현하는 경우(예: 사용자 나이 검증 `0 < age < 150`과 건물 층수 제한 `0 < floors < 150`)를 합치면 안 된다. 코드의 외형이 아니라 그것이 표현하는 지식이 같은지를 판단 기준으로 삼아야 한다. [PP]

**추천**: External ▶ (코드 형태가 아닌 지식 단위로 중복 여부를 판단하는 것이 과도한 추상화를 방지한다)

### [4] 오류 처리 전략

**상충 유형**: 상충

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] / 파이썬 클린코드 [PC] | A Philosophy of Software Design [APoSD] |
| 주장 | 오류 코드 대신 예외를 사용하라. 사전조건/사후조건을 명시적으로 정의하라 (DbC) | 예외 처리는 가장 큰 복잡성 원천이다. 가능하면 오류 조건 자체를 설계적으로 제거하라 |

**Internal 근거**: 오류 코드를 반환하면 호출자가 곧바로 처리해야 하고, 명령/조회 분리를 위반한다. 예외를 사용하고, 사전조건과 사후조건을 명시적으로 정의하여 책임 소재를 명확히 하라. try/catch 블록을 분리하여 정상 동작과 오류 처리를 구분하라. [CC] [PC]

**External 근거**: 예외 처리는 시스템의 복잡성을 크게 증가시킨다. 예외를 잘 다루는 것보다 오류 조건 자체가 존재하지 않도록 설계하는 것이 우선이다. 예: 선택이 없을 때 예외를 던지는 대신, 아무것도 하지 않도록 정상 흐름으로 처리한다. [APoSD]

**추천**: 병합 (먼저 APoSD처럼 오류를 설계에서 제거할 수 있는지 검토하고, 제거할 수 없는 경우 CC처럼 예외와 DbC를 적용)

### [5] 설계 착수 시점과 방법

**상충 유형**: 모순

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] / 객체지향의 사실과 오해 [OO] | A Philosophy of Software Design [APoSD] |
| 주장 | 처음에는 길고 복잡해도 좋다. 머릿속에 번뜩이면 바로 구현을 시작하고, 다듬으며 개선하라 | 모든 주요 설계 결정에 대해 최소 두 가지 근본적으로 다른 접근법을 먼저 고려하라. 첫 번째 생각이 최선일 가능성은 낮다 |

**Internal 근거**: "설계를 간단히 끝내고 최대한 빨리 구현에 돌입하라. 머릿속에 객체의 협력 구조가 번뜩인다면 그대로 코드를 구현하기 시작하라." 처음에는 길고 복잡하게 작성한 후 단위 테스트를 유지하며 반복적으로 다듬는다. [CC] [OO]

**External 근거**: "Design It Twice" -- 첫 번째로 떠오른 설계가 최선의 설계를 내놓을 가능성은 낮다. 최소 두 가지 근본적으로 다른 접근법을 비교한 뒤 구현에 착수해야 한다. 전술적 프로그래밍("일단 동작하면 된다")은 복잡성을 누적시키고 장기적으로 기능 추가 비용을 증가시킨다. [APoSD]

**추천**: 병합 (주요 아키텍처/인터페이스 결정은 APoSD처럼 두 가지 이상 비교하되, 세부 구현은 CC처럼 빠르게 작성 후 리팩토링)

### [6] 변수 이름 길이 기준

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] | Code Complete [CodeC] |
| 주장 | 이름 길이는 범위(scope) 크기에 비례해야 한다 | 변수 이름의 최적 평균 길이는 10-16자이며, 루틴 이름은 15-20자이다 |

**Internal 근거**: 검색하기 쉬운 이름을 사용하라. 넓은 범위에서 사용되는 변수일수록 긴 이름이 필요하고, 좁은 범위의 지역 변수는 짧아도 된다. 절대적인 글자 수가 아닌 범위와의 비례 관계가 기준이다. [CC]

**External 근거**: Gorla, Benander, Benander 연구에 따르면 변수 이름의 최적 평균 길이는 10-16자다. 너무 짧으면 의미를 전달하지 못하고, 너무 길면 가독성이 떨어진다. 루틴 이름은 15-20자가 최적이다. [CodeC]

**추천**: 병합 (CC의 범위 비례 원칙을 기본으로 하되, CodeC의 10-16자를 평균 목표 범위로 참고)

### [7] 한정자(qualifier) 배치 순서

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | Clean Code [CC] | Code Complete [CodeC] |
| 주장 | 의미 있게 구분하라 (불용어 금지, 구체적 이름 사용) | 핵심 개념을 앞에, 한정자를 뒤에 배치하라 (revenue_total, revenue_average, revenue_max) |

**Internal 근거**: 불용어(Info, Data 등)를 사용하면 개념을 구분하지 못한 채 이름만 달리한 것이다. 의도를 분명히 드러내는 이름을 사용하되, 한정자 배치 순서에 대한 구체적 규칙은 제시하지 않는다. [CC]

**External 근거**: `total_revenue`, `avg_revenue`, `max_revenue`보다 `revenue_total`, `revenue_average`, `revenue_max`가 낫다. 핵심 개념(revenue)이 항상 앞에 위치하면 관련 변수들이 그룹으로 인식되어 가독성이 높아진다. [CodeC]

**추천**: External ▶ (핵심 개념을 접두어로 두면 IDE 자동완성과 알파벳 정렬에서도 이점이 있다)
