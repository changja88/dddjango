# DDD 아키텍처 의사결정 문서: Internal vs External 상충 분석

> Internal 출처: [A] 도메인 주도 개발 시작하기, [B] 도메인 주도 설계 첫걸음, [C] 도메인 주도 설계 구현(빨간책)
> External 출처: Eric Evans 파란책, Vaughn Vernon "Effective Aggregate Design" / "DDD Distilled", Scott Millett, Harry Percival & Bob Gregory "Cosmic Python", Greg Young, Martin Fowler

### [1] 엔티티의 독립적 사용 가능 여부

**상충 유형**: 모순

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 | Scott Millett, Patterns Principles and Practices of DDD |
| 주장 | 엔티티는 독립 패턴으로 도메인 기능을 직접 포함한다 | 엔티티는 반드시 풍부한 도메인 모델의 일부로서 행동을 캡슐화해야 한다 |

**Internal 근거**: [A]는 엔티티를 독립적으로 사용 가능한 전술 패턴으로 다루며, 엔티티 자체에 도메인 규칙(예: `change_password`)을 넣되 "하나의 함수가 같은 엔티티의 다른 함수를 호출하지 않도록" 한다는 자체 제약을 둔다. [B]는 반대로 엔티티를 "애그리거트의 일부로서만 사용된다"고 명시한다.
**External 근거**: Millett는 빈혈 도메인 모델을 "가장 흔한 DDD 실패 사례"로 지적하며, 엔티티가 독립적으로 존재하는 것이 아니라 풍부한 도메인 모델의 구성 요소로서 행동과 불변식을 캡슐화해야 한다고 주장한다. Evans 원전도 엔티티를 애그리거트 내에서 다룬다.
**추천**: External ▶ (엔티티를 애그리거트 없이 독립 사용하면 일관성 경계가 모호해지며, Internal 내부에서도 [B]가 이미 같은 입장)

### [2] CQRS의 적용 범위와 위상

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [C] 도메인 주도 설계 구현(빨간책) | Greg Young "CQRS Documents", Martin Fowler |
| 주장 | CQRS를 아키텍처 스타일 중 하나로 강조하며, 커맨드 모델에서 getter를 제거할 것을 권장 | CQRS는 최상위 아키텍처가 아니라 보조 패턴이며, 일부 바운디드 컨텍스트에만 선택적으로 적용해야 한다 |

**Internal 근거**: [C]는 CQRS를 핵사고날 아키텍처와 함께 주요 아키텍처 패턴으로 다루며, 커맨드 모델에는 "쿼리 메서드(getter) 없이 커맨드 메서드만 포함"할 것을 권장한다. 전체 시스템 수준의 아키텍처 결정으로 다루는 뉘앙스가 강하다.
**External 근거**: CQRS의 창시자 Greg Young 본인이 "CQRS는 최상위 아키텍처가 아니다! 보조 패턴으로 취급하고, 선택적으로 일부 바운디드 컨텍스트에만 적용하라"고 명시한다. Fowler도 CQRS를 모든 곳에 적용하는 것에 경고한다.
**추천**: External ▶ (패턴 창시자가 직접 적용 범위를 제한한 만큼, 시스템 전체가 아닌 필요한 컨텍스트에만 선택 적용하는 것이 안전)

### [3] 도메인 서비스를 애그리거트에 전달하는 방식

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 | Harry Percival & Bob Gregory, "Cosmic Python" |
| 주장 | 도메인 서비스 객체를 애그리거트의 메서드 파라미터로 전달한다 | 응용 서비스(또는 메시지 버스 핸들러)가 도메인 서비스를 호출하고, 애그리거트는 도메인 서비스를 알지 못한다 |

**Internal 근거**: [A]는 `calculate_payment(self, discount_service, coupons, member_grade)` 형태로 도메인 서비스를 애그리거트 메서드의 파라미터로 전달하되, "주입하지 않는다"는 점을 강조한다. 애그리거트가 도메인 서비스를 직접 사용하는 패턴이다.
**External 근거**: Cosmic Python은 응용 서비스/핸들러 레벨에서 도메인 서비스를 호출하고, 애그리거트는 순수 도메인 로직(엔티티 상태 변경, 이벤트 발행)만 담당하도록 분리한다. Unit of Work와 메시지 버스가 흐름을 제어하며, 애그리거트는 외부 의존성을 받지 않는다.
**추천**: 병합 (간단한 경우 [A] 방식이 직관적이나, 테스트 용이성과 의존성 분리를 위해 Cosmic Python 방식을 기본으로 하되, 순수 계산 로직에 한해 파라미터 전달도 허용)

### [4] 응용 서비스에서 여러 애그리거트를 수정하는 것의 허용 여부

**상충 유형**: 상충

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 | Vaughn Vernon, "Effective Aggregate Design" |
| 주장 | 응용 서비스에서 두 애그리거트를 같은 트랜잭션 내에서 각각 수정할 수 있다 | 하나의 트랜잭션에서는 반드시 하나의 애그리거트만 수정하고, 나머지는 도메인 이벤트를 통한 결과적 일관성으로 처리해야 한다 |

**Internal 근거**: [A]의 `change_shipping_info` 예시에서 `order.change_shipping_info(new_info)` 후 `member.change_address(new_info.address)`를 같은 응용 서비스 메서드 내에서 수행한다. "애그리거트에서 다른 애그리거트를 직접 수정하지 말고 응용 서비스에서 각각 수정하도록 구현한다"는 가이드를 제시한다.
**External 근거**: Vernon의 규칙 4 "일관성 경계 밖에서는 결과적 일관성을 사용하라"는 서로 다른 애그리거트 간의 일관성을 도메인 이벤트로 달성할 것을 명시한다. 즉시 일관성이 필요해 보여도 도메인 전문가에게 확인하면 지연이 허용되는 경우가 많다고 강조한다.
**추천**: External ▶ (트랜잭션 충돌 감소와 확장성을 위해 결과적 일관성이 원칙이되, 실무적으로 동일 DB 내 단순 케이스에서는 [A] 방식도 용인할 수 있음을 주석으로 명시)

### [5] 아키텍처 스타일의 우선순위

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 | Harry Percival & Bob Gregory, "Cosmic Python" |
| 주장 | 전통적 계층 아키텍처 + DIP를 기본 아키텍처로 제시 | 의존성 역전을 넘어 메시지 주도 아키텍처(Message Bus + Unit of Work)를 핵심 패턴으로 제시 |

**Internal 근거**: [A]는 4계층(표현-응용-도메인-인프라) 구조를 기본으로 하고 DIP를 적용하여 도메인이 인프라에 의존하지 않도록 한다. [C]는 핵사고날(포트와 어댑터)을 상세히 다룬다. 둘 다 직접 메서드 호출 기반의 동기적 흐름을 전제한다.
**External 근거**: Cosmic Python은 Repository + Unit of Work + Message Bus를 핵심 패턴 삼각형으로 제시하며, 커맨드와 이벤트가 메시지 버스를 통해 핸들러로 라우팅되는 구조를 권장한다. "커맨드는 정확히 하나의 핸들러, 이벤트는 0개 이상의 핸들러"라는 메시지 주도 설계가 기본이다.
**추천**: 병합 (프로젝트 초기에는 Internal의 계층 아키텍처+DIP로 시작하고, 이벤트 기반 흐름이 필요해지면 Cosmic Python의 Message Bus 패턴을 점진적으로 도입)

### [6] DDD 도입 시 전략 패턴 vs 전술 패턴의 우선순위

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 | Vaughn Vernon, "DDD Distilled" |
| 주장 | 전술 패턴(엔티티, 값 객체, 리포지토리 등) 중심으로 실무 구현에 집중 | 전략 설계(바운디드 컨텍스트, 컨텍스트 맵)가 반드시 먼저이며, 전술 패턴에만 집중하는 것은 실수 |

**Internal 근거**: [A]는 "전술 패턴 중심의 실무 구현"을 초점으로 하며, 바운디드 컨텍스트보다는 도메인 영역 내부의 모듈 구성에 집중한다. DDD 입문자를 대상으로 하여 즉시 코드에 적용 가능한 패턴을 우선 제시한다.
**External 근거**: Vernon은 "많은 팀이 전술 패턴에만 집중하는 실수"를 명시적으로 지적하며, "1. 핵심 도메인 식별 -> 2. 바운디드 컨텍스트 설계 -> 3. 컨텍스트 매핑 -> 4. 그 다음에 전술 패턴"이라는 순서를 강조한다.
**추천**: External ▶ (전략 설계 없이 전술 패턴만 적용하면 잘못된 경계에서 좋은 코드를 작성하는 결과가 되므로, 전략 우선 원칙을 따르되 [A]의 전술 패턴 가이드는 구현 단계에서 활용)

### [7] 도메인 이벤트의 발행 타이밍

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [B] 도메인 주도 설계 첫걸음, [C] 도메인 주도 설계 구현(빨간책) | Jimmy Bogard "A better domain events pattern", Cosmic Python |
| 주장 | 애그리거트 내부에서 이벤트를 리스트에 수집하고 외부에서 꺼내감 (수집까지만 다룸) | 이벤트 수집 후 반드시 Unit of Work의 커밋 직전/직후에 디스패치하는 타이밍까지 명시 |

**Internal 근거**: [B][C]는 애그리거트 안에 `_domain_events` 리스트를 두고 `collect_domain_events()`로 꺼내가는 수집 패턴을 보여주지만, 언제 디스패치해야 하는지(커밋 전/후)에 대한 구체적 가이드가 없다.
**External 근거**: Bogard의 패턴과 Cosmic Python은 "수집 -> 커밋 직전에 디스패치 -> 커밋" 또는 "커밋 -> 커밋 직후 디스패치"라는 명확한 타이밍을 제시하며, Unit of Work가 이 역할을 담당한다. 커밋 전 디스패치는 동일 트랜잭션 내 부수 효과에, 커밋 후 디스패치는 외부 통합에 적합하다.
**추천**: External ▶ (디스패치 타이밍이 명시되지 않으면 이벤트 유실이나 트랜잭션 불일치가 발생하므로, Unit of Work 연동 패턴을 기본으로 채택)

### [8] 리포지토리 인터페이스의 위치

**상충 유형**: 불일치

| | Internal | External |
|---|---------|----------|
| 출처 | [A] 도메인 주도 개발 시작하기 (Django 패키지 구조) | Cosmic Python, [C] 도메인 주도 설계 구현(빨간책) |
| 주장 | `domain/order_repository.py`에 인터페이스를 두고 `services/` 디렉토리에 도메인 서비스와 응용 서비스를 혼합 배치 | 도메인 계층은 어디에도 의존하지 않으며, 응용 계층과 도메인 서비스를 명확히 분리 |

**Internal 근거**: [A]의 Django 프로젝트 구조에서 `services/` 디렉토리에 `order_service.py`(응용 서비스 성격)와 `discount_service.py`(도메인 서비스)를 함께 배치한다. `views/`에 표현 계층과 응용 계층을 합치는 등 실용적이지만 경계가 모호한 구조이다.
**External 근거**: Cosmic Python은 `domain/`(순수 Python, 무의존성), `application/`(도메인에만 의존), `infrastructure/`(인터페이스 구현), `interface/`(표현)를 명확히 분리한다. [C]도 유사한 4계층 분리를 제시한다.
**추천**: External ▶ (도메인 서비스와 응용 서비스의 혼합 배치는 비즈니스 로직의 누수를 유발하므로, 4계층 명확 분리를 기본으로 하되 Django 등 프레임워크 제약 시 [A] 방식을 차선으로 허용)
