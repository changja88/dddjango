Findings

  • [High: 동시성/DB 트랜잭션] -- 재고 차감이 레이스 컨디션에 취약합니다.

    • Product.objects.get()으로 읽고 product.stock -= ...; product.save()로 쓰면 동시에 checkout이 들어올 때 둘 다 같은 재고를 보고 차감할 수 있습니다. 또한 Order.objects.create() 이후 재고 처리나 쿠폰 조회에서 예외가 나면 빈 주문이 남을 수 있습니다. 최소한 transaction.atomic()으로 묶고, 재고는 조건부 UPDATE 또는 select_for_update()로 보호해야 합니다.

  • [High: 외부 gateway 의존성] -- DB 트랜잭션과 외부 결제 준비 호출의 경계가 불명확합니다.

    • payment_gateway.prepare(total)이 서비스 한가운데 직접 호출됩니다. 이 호출이 실패하면 이미 차감된 재고와 주문 상태를 어떻게 되돌릴지 불명확하고, 호출이 성공한 뒤 DB 저장이 실패하는 반대 상황도 생깁니다. 결제는 포트/어댑터 같은 거대한 구조를 강제할 필요는 없지만, 최소한 PaymentGateway 역할을 좁게 정의하고 transaction.on_commit() 이후 호출하거나, PAYMENT_PENDING 주문을 먼저 커밋한 뒤 결제 준비를 별도 단계로 처리하는 편이 안전합니다.

  • [Medium: 책임 과다] -- CheckoutService.checkout()이 유스케이스 조율, 재고 정책, 가격 합산, 쿠폰 적용, 결제 준비, 영속성을 모두 직접 처리합니다.

    • “서비스가 있다” 자체는 문제라기보다, 변경 이유가 너무 많이 섞인 점이 문제입니다. 예를 들어 쿠폰 정책이 바뀌어도, 재고 차감 방식이 바뀌어도, 결제 gateway 계약이 바뀌어도 같은 메서드를 수정해야 합니다. 다만 이 정도 코드에서 대규모 DDD 계층을 만들 필요는 없고, reserve_stock, calculate_total, apply_coupon, prepare_payment 정도의 작은 경계부터가 적절합니다.

  • [Medium: ORM query] -- 루프 안 Product.objects.get()과 개별 save()가 상품 수만큼 쿼리를 늘립니다.

    • item이 10개면 상품 조회 10번, 저장 10번입니다. 상품을 한 번에 가져오고, 재고 차감은 F() 기반 조건부 update나 잠금 조회 후 bulk_update()로 줄이는 편이 낫습니다. 특히 결제 경로는 latency와 lock 시간이 사용자 경험에 직접 영향을 줍니다.

  • [Low: 도메인 오류 표현] -- ValueError("out of stock")는 호출자가 복구 가능한 업무 오류를 구분하기 어렵습니다.

    • OutOfStockError, InvalidCouponError처럼 checkout 흐름의 실패 원인을 명확히 분리하는 편이 API 응답, 로깅, 테스트가 쉬워집니다.

작은 개선 방향

핵심은 “거대한 계층 구조”가 아니라 트랜잭션 경계와 변경 이유 분리입니다.


from django.db import transaction
from django.db.models import F


class OutOfStockError(Exception):
    pass


class CheckoutService:
    def checkout(self, user, items, coupon_code, payment_gateway):
        with transaction.atomic():
            order = Order.objects.create(user=user)

            total = 0
            for item in items:
                updated = Product.objects.filter(
                    id=item["product_id"],
                    stock__gte=item["quantity"],
                ).update(stock=F("stock") - item["quantity"])

                if updated != 1:
                    raise OutOfStockError(item["product_id"])

                product = Product.objects.get(id=item["product_id"])
                total += product.price * item["quantity"]

            if coupon_code:
                coupon = Coupon.objects.get(code=coupon_code)
                total -= coupon.discount_amount

            order.total_amount = total
            order.save(update_fields=["total_amount"])

            transaction.on_commit(lambda: payment_gateway.prepare(order.id, total))

        return order

이 코드는 아직 최종 설계라기보다 위험을 줄이는 최소 방향입니다. 다음 단계에서는 상품 조회를 배치화해서 가격 계산용 Product.objects.in_bulk(...)를 쓰고, payment_gateway에는 total만 넘기기보다 order.id 같은 추적 가능한 식별자를 함께 넘기는 편이 좋습니다.

Verification

  • 동시 checkout 테스트: 같은 상품 재고 1개에 대해 두 요청을 동시에 실행했을 때 하나만 성공하는지 확인
  • 실패 테스트: 쿠폰 없음, 재고 부족, gateway 실패 시 주문/재고 상태가 기대대로 남는지 확인
  • 쿼리 회귀 테스트: 여러 item checkout에서 쿼리 수가 상품 수에 선형으로 폭증하지 않도록 assertNumQueries 추가
