커머스의 bounded context는 “기능 메뉴”보다 업무 언어와 변경 이유로 나누는 게 안전합니다. 주문, 결제, 배송, 정산은 비슷한 데이터(order_id, 금액, 상태)를 공유하지만 상태의 의미와 변경 주기가 다릅니다.

| Context | 책임 | Aggregate Root | 주요 불변식 | 금지 동의어 | |---|---|---|---|---| | 주문 | 고객의 구매 의사, 주문서, 취소 가능성 | Order | 결제 확정 전/출고 전까지만 변경 가능 | payment_status, tracking_status | | 결제 | 승인, 매입, 실패, 환불, PG 멱등성 | Payment | 승인 금액은 주문 청구 금액과 일치 | charge, transaction를 도메인 핵심어로 직접 사용 | | 배송 | 출고 요청, 송장, 배송 상태, 반품 회수 | Shipment | 출고 후 배송지는 임의 변경 불가 | order_status, settlement_status | | 정산 | 수수료, 지급 대상, 지급 보류, 지급 확정 | Settlement | 지급 확정 후 금액 재계산 불가 | payment_amount 그대로 사용 |

분리 기준은 이렇게 잡으면 됩니다.

  • 같은 단어가 다른 의미를 갖는가

    • 금액은 주문에서는 고객 청구 금액, 결제에서는 승인/환불 금액, 정산에서는 판매자 지급 금액입니다. 같은 Money 값 객체는 공유할 수 있지만, OrderTotal, ApprovedAmount, PayoutAmount는 각 context 언어입니다.

  • 변경 이유가 다른가

    • 주문은 쿠폰/취소 정책 때문에 바뀌고, 결제는 PG/카드사/간편결제 정책 때문에 바뀝니다. 배송은 택배사 SLA와 창고 운영, 정산은 회계/세무/수수료 정책 때문에 바뀝니다.

  • 트랜잭션으로 반드시 함께 지켜야 하는 불변식이 다른가

    • 주문 생성과 결제 승인은 하나의 큰 트랜잭션으로 묶지 않습니다. OrderPlaced, PaymentApproved, ShipmentDispatched, SettlementConfirmed 같은 이벤트로 최종 일관성을 사용합니다.

  • Django app과 bounded context를 1:1로 강제하지 않는다

    • 작은 서비스라면 apps.commerce 하나의 Django app 안에 네 context 패키지를 둘 수 있습니다. 반대로 운영 규모가 크면 context별 Django app을 나눌 수 있습니다. 기준은 Django 자동 탐색 편의가 아니라 도메인 경계와 변경 이유입니다.

Context map은 다음처럼 시작하는 편이 좋습니다.

| 관계 | 패턴 | 통합 방식 | |---|---|---| | 주문 → 결제 | Customer-Supplier + Published Language | 주문은 RequestPayment command를 보내고, 결제는 PaymentApprovedV1 발행 | | 주문 → 배송 | Customer-Supplier | 주문은 결제 확정 후 FulfillmentRequestedV1 발행 | | 결제/배송/주문 → 정산 | ACL + Published Language | 정산은 외부 이벤트를 SettlementFact로 번역 | | 결제 → PG | ACL | Toss/Stripe 어휘를 PaymentGateway 뒤에 격리 |

핵심 코드 스케치는 이 정도만 있으면 경계 의도가 드러납니다.


@dataclass(frozen=True)
class Money:
    amount: int
    currency: str = "KRW"

    def __post_init__(self):
        if self.amount < 0:
            raise InvalidMoney("amount must be non-negative")


class AggregateRoot:
    def __init__(self):
        self._events = []

    def _record_event(self, event):
        self._events.append(event)

    def collect_events(self):
        events, self._events = self._events, []
        return events


class Order(AggregateRoot):
    """Invariant: 주문은 결제 확정 전까지만 취소/배송지 변경 가능."""

    def confirm_payment(self, payment_id: PaymentId, amount: Money) -> None:
        if self.total != amount:
            raise PaymentAmountMismatch()
        self.status = OrderStatus.PAID
        self._record_event(OrderPaid(order_id=self.id, payment_id=payment_id))

검증은 이벤트 스토밍으로 확인합니다.


Given 주문이 접수됨
When 결제가 승인됨
Then 주문은 PAID가 되고 FulfillmentRequestedV1이 발행된다

Given 배송이 출고됨
When 주문 취소가 요청됨
Then 주문 취소가 거절되고 환불 command는 발행되지 않는다

Given 결제/배송/주문 이벤트가 수신됨
When 정산 기준일이 도래함
Then Settlement는 지급 금액을 확정한다
