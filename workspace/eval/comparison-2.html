dddjango 2차 비교 — codex-3 vs claude-2

같은 프롬프트("재고 부족 409·충분 시 차감·주문 생성 API")로 Codex 포트와 Claude 플러그인을 각각 한 번 더 실행한 결정성 검증(N=2). 1차(codex-2 vs claude-1) 결론이 재현되는지 확인하고, 양쪽이 게이트에서 던진 질문까지 1:1로 대조한다.

한 줄 결론 정직한 요약

1차의 "claude 압도(13:2:5)"는 상당 부분 N=1 분산이었다.

2차에서 프레임워크 무관 코드 품질은 대등했고(오히려 실질 결함은 claude-2 쪽이 1건 더 많음), 가장 중요한 축인 도메인 소유(B1)는 양쪽 모두 위반했다. 런타임 간 지속적·재현되는 차이는 "감사 깊이"가 아니라 ① 게이트에서 결정을 얼마나 노출하는가(상호작용 철학)와 ② 기본 기술 스택을 얼마나 풍부하게 잡는가였다.

⚠️ 2차는 통제가 1차만큼 깨끗하지 않다. claude-2는 이번 런에서 프레임워크/러너 게이트가 노출되지 않아 Ninja+pytest 기본 스택으로, 구조는 G1에서 "옵션 B 최소 변경"을 골라 평면 구조로 진행됐다. codex-3는 plain Django+Django test+완전 §0 4계층. 따라서 구조 트리·프레임워크 세부·테스트 개수는 우열 비교 불가이며, 프레임워크와 무관한 신호(도메인 소유·DB 불변식·동시성·죽은 코드)만 유효 비교한다.

① 게이트 질문 비교 가장 깨끗한 비교 — 같은 입력, 다른 물음

두 런타임이 사용자에게 무엇을·어떻게 물었는가. 통제가 깨진 코드 비교와 달리, 이건 같은 프롬프트 위에서 순수하게 런타임의 상호작용 철학을 드러낸다. 1차 패턴이 그대로 재현됐다.

관찰

claude는 설계 결정을 잘게 쪼개 근거·추천과 함께 사용자에게 노출하고, codex는 최소한만 묻고 나머지는 스스로 결정한다. 이 차이는 1차에서도 동일하게 나타났고 2차에서 또렷이 재현됐다 — 즉 게이트 철학은 런타임의 결정적 특성이다. (단 claude의 프레임워크/러너 게이트 노출 여부 자체는 런마다 흔들렸다.)

② 핵심 신호의 결정성 1차 vs 2차, 양 런타임

1차에서 claude 우위의 근거였던 세 신호가 매 런 재현되는지(결정적) 아니면 런마다 흔들리는지(분산) 확인. 프레임워크와 무관한 축이라 통제 이탈의 영향이 적다.

결정성 판정: "감사 깊이 격차"는 결정적이지 않다

  • B1(도메인 소유)은 claude에서도 비결정적이다. claude-1은 도메인 메서드를 배선했지만 claude-2는 같은 프롬프트에서 미배선+합리화로 codex와 같은 anemic 패턴을 재현했다.
  • stock≥0은 codex에서 비결정적이다. codex-2는 누락했지만 codex-3는 명시 CHECK + 마이그레이션 음수행 가드까지 갖췄다.
  • → 1차의 "claude가 잡고 codex가 놓친다"는 양쪽 다 런마다 흔들리는 분산이었다. N=1이 격차를 크게 부풀린 것.

③ 프레임워크 무관 코드 비교 codex-3 ↔ claude-2

구조·프레임워크·테스트 개수는 통제 이탈로 제외. 로직·계약·집행·죽은 코드 등 프레임워크와 무관한 코드 품질만 본다.

④ 독립 서브에이전트 리뷰 1차와 동일하게 2종 참여

표준 부합 리뷰어

"프레임워크 무관 축만 보면 한쪽의 분명한 우월은 없고 대체로 대등. B1에서 둘 다 권위를 infra에 두는 동일 위반(claude-2=죽은 도메인 메서드, codex-3=엔티티 부재). claude-2는 포트가 도메인 엔티티를 반환하는 점에서, codex-3는 명시 CHECK·마이그 안전가드·일관 네이밍에서 각각 소폭 앞서 상쇄. 1차 'claude 압도' 선입견은 이 쌍엔 적용 안 됨."

코드 품질 리뷰어

"핵심 동시성·오류 로직은 동치이나 코드 품질은 codex-3가 우위 — claude-2엔 죽은 도메인 코드 + (거짓 테스트 의혹) 결함, codex-3는 무해한 잔재 1건."

⚠️ 검증으로 정정: "거짓 테스트" 주장은 오판. 실제 스키마에 CHECK(stock≥0)가 존재하고 테스트 4/4 PASS(PositiveIntegerField가 SQLite에 CHECK 자동 생성). 정정 후 codex-3 우위 근거는 죽은 코드 1건 + 오류처리 폭으로 좁혀짐(claude-2는 available 보고가 더 나음). 순효과 대등~codex 근소.

두 리뷰어 모두 "1차만큼의 claude 압도는 이 쌍에 없다"로 수렴. 코드 품질 리뷰어의 단일 강한 주장(거짓 테스트)은 메인이 직접 스키마·테스트 실행으로 반증해 문서에 반영함 — 서브에이전트 결과도 무비판 수용하지 않고 검증.

⑤ 무엇이 지속되고 무엇이 분산인가

🔁 재현되는(결정적) 차이

  • 게이트 노출 철학 — claude는 결정을 잘게 쪼개 근거·추천과 함께 노출, codex는 최소만 묻고 자체 결정. (1·2차 모두)
  • 기본 스택 풍부도 — 제약 없을 때 claude는 Ninja·pytest 등 풍부한 도구로, codex는 plain Django·Django test 최소로. (1·2차 모두)

🎲 런마다 흔들리는(분산) 차이

  • B1 도메인 소유 — claude 1차 배선 / 2차 미배선. codex 양차 미흡. 양쪽 ddd 리뷰가 "infra 집행을 도메인 소유로 합리화"를 런마다 수용/반려.
  • stock≥0·마이그레이션 안전 — codex 1차 누락 / 2차 철저. DB 감사 깊이가 런마다 흔들림.
  • claude 프레임워크/러너 게이트 노출 여부 — 1차 노출 / 2차 미노출.

그래서 "왜 1차엔 claude가 압도적이었나"

1차는 N=1이라, 양쪽 다 비결정적인 세 신호가 우연히 모두 claude에 유리한 방향으로 정렬된 한 표본이었다. 2차에서 그 정렬이 풀리자 코드 품질 격차는 사라졌다. 런타임/모델의 결정적 "감사 깊이" 격차라는 1차 가설은 약해졌다 — 실제로 codex-3의 DB 감사는 claude-2보다 날카로웠다. 남는 견고한 차이는 상호작용 철학(게이트)과 스택 취향이며, 이는 코드 정확성의 우열이 아니라 제품 성격의 차이다.

⑥ 한계

  • 여전히 표본이 작다. 런타임당 2회. 분산을 "확인"했을 뿐 분포를 추정하진 못한다.
  • 2차 통제 이탈. claude-2 = Ninja+pytest+평면 / codex-3 = plain Django+Django test+완전 §0. 구조·프레임워크·테스트수는 비교 불가. B1은 프레임워크 무관이라 분산 결론은 견고하나, "옵션 B 최소구조" 선택이 claude-2의 도메인 빈약에 일부 기여했을 가능성은 배제 못 함(완전 통제 재런으로만 분리 가능).
  • 게이트 노출 철학은 두 런 모두에서 재현돼 가장 신뢰할 결론이지만, 이는 "표준 준수 우열"이 아니라 런타임 UX 설계 차이다.
