## 의미적 변종 / backstop-blind 메타 (주 산출물 — §1.3)

- 이 런에 `[결정 PASS ∧ 의미 FAIL]` 의미적 변종은 **없음**(SD-6 결정·의미 둘 다 PASS). NJ-4는 결정 레인 자체가 FAIL(`response=`에 오류 미선언).
- **🔴 backstop-blind(DR-24 동형)**: NJ-4 `openapi_extra` 일탈 + `JsonResponse` idiom 둘 다 **G3 response-schema 백스톱·P1a error-centralization 백스톱이 exit0**으로 통과시킨다(백스톱은 `response={}` 선언분·`application_layer` HTTP 누수만 봄). 코디네이터 자기보고도 "백스톱 4종 exit0"만 보고. → 의미/결정 레인 정독만 포착. **이 miss가 `EVAL-METHOD §1.2 에러경로 정독 의무` + `RUBRIC` NJ-4 조임(openapi_extra≠pass)의 동기**(도구 하드닝 반영됨).

## 조정자 노트

- **SD-6 / P1a clean (C2 회피 — 검증)**: p1a-v3-codex가 FAIL한 바로 그 자리. 이 런은 app이 비즈예외를 catch하지 않고(`create_order_app.py:23-33` try/except 0) status를 든 객체를 흘리지 않는다(도메인 `Order` 반환) → 중앙 핸들러 6개가 전부 live. **차이의 뿌리 = 멱등성 미발명**(Q-1): status-bearing snapshot(p1a-v3의 `IdempotencySnapshot`)이 애초에 안 생겼다. 태스크가 멱등성을 금지했고 디자인이 범위밖으로 문서화 → 스코프크립이 안 일어나 P1a 변종도 안 났다.
- **NJ severity 보정(§6.2 대조)**: 핸들러가 problem dict를 손수 빌드해 반환하는 형태는 §6.2 line344-356의 *처방*이다 → 중앙화·dict 빌드·problem+json·스키마 분리는 **준수**(SD-6 'raw 응답'·NJ-1 'plain leak'·"죽은 schema"로 over-call 금지). **진짜 일탈은 2건**: (a) `ninja.responses.Response` 아닌 `django.http.JsonResponse`=경미(🟡 NJ-1 idiom, 치명 게이트 '스택 채택'은 통과) · (b) 오류를 `response={}` 아닌 `openapi_extra`로=**NJ-4 FAIL**(가시성 달성해도 §2.2 line111 위반, '강' 항목이라 품질 상한 '중').
- **catalog orphan(SH-9 ❌·Q-7 🟡, 비치명)**: 이주는 이행됐으나(active=`application/catalog/`) 루트 `catalog/`(평면·`Product` 모델·`0001`·스텁)를 미삭제 → 디스크에 Product 2벌. INSTALLED_APPS 밖이라 *비활성 orphan*(C8/C9급 잔해)이고 러너도 안 깨지나, 정리 누락은 실결함.
- **과거 Codex 런 대조**(맥락 — 직접 차분 아님): smoke4-codex=SH-1·4·SD-3 치명 FAIL(catalog 평면 유지+판정 SQL 복제), p1a-v3-codex=SD-3·SD-6·SH-7 치명 FAIL. **이 런은 그 척추 치명을 전부 통과**. 단 **N=1·태스크 동일군**이라 "Codex가 좋아졌다"는 단정 금지 — 공유 하드닝 효과 ∨ 표본 분산 미분리.
