dddjango 최종 스모크 — Claude vs Codex 인사이트

2026-05-30 · 표준이 라이브 /dddjango 런에서 실제로 발화하는지 검증 (12축) · clean fixture (ninja 미설치)
⚠️ 읽기 전 경계 — 이건 "우열 판정"이 아니다
각 런타임 N=1이고 서로 다른 태스크를 돌렸다 (Claude=단일 컨텍스트 재고예약 · Codex=cross-context 주문생성). 통제 비교가 아니므로 차이가 런타임 차이인지 태스크 차이인지 분리되지 않는다. 목적은 "표준 12축이 살아 발화하나"(sanity)지 "누가 더 낫나"가 아니다. 진짜 우열 결론은 같은 태스크 N≥5 블라인드 + 루브릭이 따로 필요하다.

① 런타임별 성향 (이번 런에서 드러난 것)

Claude — 태스크 A
재고 예약 API (단일 컨텍스트, 기존 catalog.Product)
성향: 깊이·DDD 순수성 최대화
표준을 끝까지 적용한다. 평면 catalog를 통째로 4계층 트리로 완전 이주하고 Product를 도메인 애그리거트로 승격(빈혈 차단), 동시성도 race 10/10까지 집요하게 검증. 그 깊이가 과잉으로 번질 때가 있다 — 테스트 관찰성 때문에 프로덕션에 커스텀 DB 백엔드까지 손댐.
  • ③ 완전 이주 + Product.reserve() 단일 판정 소유 (DDD 모범)
  • 동시성 race 10/10 행위 검증 (oversell 0 실증), e2e 테스트까지
  • ninja 에러를 중앙 exception_handler로 — operation은 얇게 유지
  • 테스트 관찰성 위해 프로덕션 BEGIN IMMEDIATE 커스텀 백엔드 배선 (가드레일 미차단)
  • 에러 바디 raw JsonResponse + OpenAPI content-type 미패치(spec/런타임 불일치)
Codex — 태스크 B
주문 생성 API (cross-context, 주문→catalog 재고 차감)
성향: 실용·스코프 보수성 (최소 침습)
기존 코드에 최소한으로만 손댄다. 신규 orders는 풀 DDD로 짓되, 기존 catalog는 평면 유지 + published_service 공개계약만 추가(전면 재배치는 "스코프 밖"). 동시성 원시도구도 깔끔(커스텀 백엔드 없이 select_for_update+CAS+CHECK). 대신 깊이가 얕아 빈틈이 남는다 — 동시성 테스트 부재, 에러 처리 우회.
  • ⑥ cross-context 교과서적 — Port/ACL/published_service, 동기 OHS, 직접 import 0
  • 동시성: select_for_update+CAS+CHECK, 커스텀 백엔드 없음 (가드레일 준수)
  • 스코프 규율 — 기존 catalog 전면 재작성 회피, 근거 명세 기록
  • ③ catalog 미이주 — 판정이 도메인 애그리거트 아닌 트랜잭션 스크립트(published_service 함수)
  • 동시 oversell 행위 테스트 부재(구조 가드만), 에러 바디 operation 내 수제 + OpenAPI 몽키패치

한 줄 요약: Claude는 과잉건축(깊이·순수성, 때로 너무 멀리) · Codex는 절제건축(실용·최소, 때로 너무 얕게). ※ 태스크가 달라 성향이 태스크 탓일 가능성 배제 못 함.

③ 표준이 수렴시킨 곳 vs 판단을 남긴 곳

수렴 WIN 양 런타임이 같은 곳

  • ④ Ninja + 버전 핀 — plain 편향(Codex)·미설치 fixture에도 둘 다 Ninja 채택+핀. DR-16/17 boost가 양 런타임·인터랙티브까지 작동.
  • §0 구조 · §4 명명 · 테스트 의미군 — 둘 다 STRONG. 구조/명명 표준은 런타임 무관하게 안정 발화.
  • 게이트·TDD·규율 감사 — 둘 다 전 게이트 통과, 테스트 green, blocker 0.

분기 DIVERGE 표준이 판단 여지를 남긴 곳

  • ③ 판정-소유 이주 — Claude=완전 이주, Codex=스코프 한정. 둘 다 DR-16 허용 범위 안. ③는 런타임/태스크 간 비결정.
  • 동시성 깊이 — Claude=race 테스트→커스텀 백엔드, Codex=테스트 없음→백엔드 없음. 깊이 선택이 정반대.
  • ninja 에러 경로 — 둘 다 수제 JsonResponse지만 Claude=중앙화(얇은 op)/Codex=op내+몽키패치.

④ 스모크가 끄집어낸 실행가능 후속

A. §6.2 boost 후보 (양 런타임 공통)
두 런 모두 RFC 9457 problem+json을 수제 JsonResponse로 만들었다 — 표준이 ninja 네이티브 problem+json 경로(커스텀 renderer/response class)를 안 보여줘서다. → §6.2에 네이티브 problem+json 방법 + "중앙 exception_handler·얇은 operation"(Claude 패턴)을 명시 보강.
B. 코더 가드레일 재보강 후보 (Claude 성향)
f9ea088 가드레일("커스텀 백엔드 우회 금지")이 프로덕션 커스텀 백엔드를 또 막지 못했다. 이번엔 정당화·투명(코더가 env 갭 보고+§3.2 개정 제안)했으나 설계 반송 대신 자가결정. → "테스트 관찰성 위한 DB 백엔드는 테스트 전용 설정에 격리(프로덕션 ENGINE 변경 금지), 아니면 설계 반송" 규칙 추가.
C. 동시성 행위 테스트 (Codex 성향)
Codex/B는 구조 가드(CAS+CHECK)는 있으나 동시 oversell 행위 테스트가 없다. → acceptance/coordinator 단계에서 동시성 기능이면 race 테스트를 요구하는지 점검(또는 표준에 명시).
