## 🔴 FC-1 핵심 결함 — 성공경로 500 (`ninja.Status` × ninja-extra 비호환, stale .pyc 마스킹)

**증상**: 재고충분 주문(`stock≥quantity`) → **201 기대 / 실측 500** `application/problem+json {"type":"/probs/internal-error"}`. 클린 빌드(`python -B`·0 pyc) **결정적 ×7 재현**(normal·-B·단독 probe·pytest 일치).

**근본**: `order_controller.py:58·65` `def place_order(...) -> Status:` + `return Status(201, OrderOut(...))`. `from ninja import Status`(=`ninja.responses.Status`)는 유효 import이나, **ninja-extra `@route.post` 다중 status `response={201:OrderOut, 404/409/422/503/500:ProblemOut}` 경로에서 201→OrderOut 스키마 바인딩에 실패** → `_result_to_response`가 OrderOut(`status='PLACED'`)을 **ProblemOut**(`type`/`title`/`status:int` 필수)으로 `model_validate` → `int_parsing 'PLACED'` ValidationError → catch-all → 500.
- **A/B 확정**: `return Status(201, OrderOut(...))` → **성공테스트 3 failed(500)** / `return 201, OrderOut(...)`(deprecated tuple) → **통과**(DeprecationWarning만). **`Status` 래퍼가 범인.**
- **아이러니**: Codex의 "deprecated tuple 반환"(NJ-5 🟡로 깎은 것)은 **기능상 정상**이고, Claude의 "더 깔끔한 `Status()`"가 **기능 파괴**. NJ-5 형태 우열이 역전.

**마스킹 메커니즘(라이브가 통과로 보인 이유)**: 라이브 런 산출 `__pycache__`에 **이전 동작하던 형태(tuple)의 바이트코드 `.pyc`가 남아** 깨진 `Status` 소스를 가림. 코더 TDD가 tuple로 green → 최종 NJ-5 "개선"으로 `Status` 교체 → **재실행 없이 종료**(discipline-reviewer는 정적 리뷰라 런타임 ninja-internal 비호환 미포착) → 소스(깨짐)+`.pyc`(동작) 동봉 배포. **이 픽스처를 깨끗이 purge하면(또는 CI·재체크아웃) 500.**
> **메타(eval 방법론)**: stale `.pyc`가 기능 결함을 가린다 → **하니스는 채점 전 바이트코드 purge 필수**(`python -B` 또는 `__pycache__` 완전 제거). 본 채점은 그 후 실측. ⟶ DEVLOG 후속.
