# A8 시각 재현 누락 — 당시 진단과 교정 근거

현재 상태: 아래 A8-V1~V3는 플러그인 지침 교정·실행 평가·독립 적대 구현 리뷰를 완료했다. 이번 플러그인 수정 범위에 미처리 결함은 없다. [개발 검증 기록](README.md)과 [최종 리뷰](final-review.md)가 현재 결과를 소유한다. 아래는 수정 전 진단의 사실과 판정 경계를 보존한 기록이며, 실제 A8 앱을 수정 완료했다는 뜻은 아니다.

- 날짜: 2026-09-13
- 당시 단계: 문제 확인 완료. 진단 작성 시점에는 수정 계획·적대적 리뷰·플러그인 구현·실행 평가를 수행하지 않았다.
- 요청: A8의 입력창 포커스 링 문제를 근거로 dddjango-web의 원인을 확인하고, 합의한 기준으로 관례 절차를 진행한다.
- 대상: dddjango-web 1.1.10의 원본 대조, 역할 위임, 시각 검증 반환과 완료 판단.
- 당시 산출: 이 진단 기록 하나. 진단 단계에서는 A8 코드·산출물·세션과 플러그인 배포 파일을 변경하지 않았다.

### A8-V1 — 원본은 전달됐지만 구현에 보존되지 않음

**확인 사실**

- 코더 원문 117행의 `Read`는 `design-ref/관계인.dc.html`의 100행부터 175행 분량을 요청한다.
- 118행의 도구 응답에는 원본 108행의 `padding: 2px 2px 4px;`가 실제로 포함돼 있다.
- 입력 기준과 S3 구현 커밋의 시안 파일은 위 SHA-256으로 동일하다. 구현 도중 시안이 바뀌어 여백이 사라진 것이 아니다.
- S3에서 추가한 `web/static/css/related_persons.css:389`의 `.rpe-scroll`은 `display`, `flex-direction`, `flex`, `min-height`, `gap`, `overflow-y`를 선언하지만 `padding`은 없다.
- 공용 입력창의 포커스 표현은 1px border와 바깥쪽 3px box-shadow다. 앞선 브라우저 분리 실험에서는 이 실제 CSS와 스크롤 부모 조합으로 좌우 링 잘림을 재현했고, 입력창 위치·300×52px 크기를 유지한 채 링의 공간을 확보하면 좌우가 이어졌다. 이는 전체 A8 로그인 화면의 새 인수 검증이 아니라 CSS 원인의 분리 실험이다.

**기존 계약**

- `dddjango-web/agents/coder-web.md:52`: 원본 DOM 관계·CSS 조합을 먼저 보존해 옮기고 실제 출력 확인으로 연결한다.
- `dddjango-web/skills/implementation-ui/references/final.md:52–57`: 실제 부품 정의·최종 스타일·배치·간격·테두리·그림자·필터 조합을 대조한다. 기존 부품도 상태 외형까지 일치할 때 재사용한다.

**판정 경계**

입력 수집 실패나 HTML/CSS 표현력 부족으로 분류하지 않는다. 정확히 어떤 내부 판단으로 한 선언을 누락했는지는 관찰할 수 없다. 확인된 것은 원문 수신 뒤의 보존 실패다. 원본의 좌우 2px만 복원하면 3px 링이 완전히 정상이라는 결론도 내리지 않는다.

### A8-V2 — 미실행 보고와 외형 일치 주장이 함께 반환됨

**확인 사실**

- Coordinator 원문 1945행은 `dddjango-web:coder-web`으로 S3를 호출한다. 호출문의 `Green criteria`는 check·mypy·ruff·registry·pytest·스텁·기존 선택자 무변경을 열거하며 실제 브라우저 대조는 포함하지 않는다.
- S3 원문 도구 호출은 Read 43, Bash 18, Write 9, Edit 4다. 직접 PNG 열람 호출은 없으며, 반환은 자신이 브라우저 없이 in-process HTML을 확인했다고 명시한다.
- 코더 최종 반환 306행은 브라우저·서버 환경을 전달받지 않았으므로 실제 화면 검증은 `Coordinator G2`라고 적는다.
- 같은 반환의 대체 구현 보고는 `Visual outcome matches the frozen 시안 in each case`라고 주장한다. 실제 렌더로 확인하지 않은 항목의 외형 일치 근거가 없다.

**기존 계약**

- `dddjango-web/agents/coder-web.md:37,54`: 시스템 green과 실제 화면 확인을 구별하고 실행 결과·미실행·스타일 적용 근거를 반환한다.
- `dddjango-web/commands/dddjango-web.md:177,180,190`: 반환과 실제 실행 범위를 대조하며, 미확인을 검증 완료로 보고하지 않는다.

**판정 경계**

브라우저 환경이 없거나 다른 담당자가 검증하는 것 자체는 결함이 아니다. 코드 검사가 통과했다는 사실도 부정하지 않는다. 미실행 범위에 외형 일치를 부여한 것이 결함이다. “브라우저 작업을 전부 코더에게 강제”하거나 “코드 green 자체를 금지”하는 해결을 미리 확정하지 않는다.

### A8-V3 — 관련 시각 상태가 검증 전달 과정에서 탈락함

**확인 사실**

- 입력 기준의 `design-input.json`은 화면·단계 중심의 13 case를 선언한다. 등록/수정 step1은 있지만 이름 필드 포커스 상태의 관찰 근거는 연결하지 않는다.
- `motion-notes.md`의 m2 focus는 출처가 `스캔`이다. 비고는 m1~m9가 DS 재사용으로 자동 확보된다고 적는다.
- `coverage-review.md`는 주로 원본의 조건 분기로 화면 상태를 열거한 뒤 누락 없음으로 판정한다. 위 포커스 상태를 실제로 확인한 근거는 없다.
- Coordinator 2069행의 규율 감사 호출은 구조·명명·타입 등의 검토로 범위를 정하고, 기록된 시각 항목은 하우스룰을 위반하지 않으면 다시 다루지 말라고 지시한다.
- Coordinator 2094행의 브라우저 대행 호출은 지정된 화면 캡처·PNG 대조를 요청한다. 등록 폼을 연 상태는 있지만 이름 칸 포커스 조작·링 확인은 없다. 해당 작업은 정식 최종 시각 감사의 대체 증거로 취급할 수 없다.

**기존 계약과 도구 범위**

- `dddjango-web/agents/design-review-web.md:23–25`: 시각 상태와 원본 관찰의 범위를 검토한다.
- `dddjango-web/commands/dddjango-web.md:180,182,184`: 관련 상호작용을 발동하고 모든 요구 case와 상태 효과를 최종 감사한다. 포커스도 실제 대조 대상으로 명시돼 있다.
- `check_design_evidence.py`는 선언된 case 집합과 증거 포인터의 정합성을 검사한다. 선언되지 않은 의미상 상태를 독자적으로 발견하는 검사기가 아니다.
- `check_motion_spec.py:267–288`는 파일·선택자·토큰을 확인하며 실제 클리핑은 판정하지 않는다.
- `compare_render_audit.py:6–17`는 텍스트·위치 등의 제한된 축을 비교한다. 모션 인벤토리 존재는 포커스 후 외형의 실측이 아니다.

**판정 경계**

모든 요소의 모든 pseudo-state를 별도 case로 무조건 늘리는 요구는 아니다. 이번 원본과 구현에 존재하고 결함을 드러내는 관련 상태가 검증 경로에 연결되지 않은 점을 확정한다. 규율 감사와 브라우저 대행을 나누는 행위 자체도 결함이 아니다. 빠진 범위를 최종적으로 확인할 책임과 증거가 필요하다.

## 3. 이번 문제로 확정하지 않는 주장

- 원본 시안이 기술적으로 재현 불가능하거나 필요한 자료가 수집되지 않았다는 주장.
- 자동 검사기의 문서화된 검사 범위 밖이라는 이유만으로 검사기 계산 오류라고 보는 주장.
- 모든 CSS 선언·전체 화면 픽셀을 기계로 비교해야만 해결할 수 있다는 주장.
- A8가 최종 시각 검증과 G2까지 통과했다는 주장. 조사 당시 `implementation_visual: pending`, `g2_approved: false`였으며 후속 작업은 진행 중이다.
- 프롬프트 길이·모델 능력·주의력의 특정 내부 원인이 증명됐다는 주장.

## 4. 진단 당시 합의한 교정 판정 기준

사용자와 합의한 다음 기준을 유지한다. 여기서는 구현 방법을 확정하지 않는다.

1. A8와 같은 공용 입력창·스크롤 부모·포커스 링 사례에서 원본의 관련 구성과 실제 효과를 연결한다.
2. 원본 누락을 구현에서 예방했는지와, 이미 생긴 누락을 리뷰에서 발견했는지를 구별한다.
3. 브라우저 확인이 가능하면 관련 조작을 실제 수행하고, 불가능하면 미검증 범위와 후속 책임을 보존한다. 미검증과 외형 일치를 동시에 주장하지 않는다.
4. 재사용·코드 검사 green·선택자 존재·캡처 장수로 상태 효과의 검증을 대체하지 않는다.
5. 정상 사례와 정당한 미검증 인계는 불필요하게 차단하지 않는다. 추가 승인 단계나 전 CSS 속성 목록을 기본 해법으로 삼지 않는다.
6. 후속 구현은 Claude·Codex 양쪽에 반영하고 `make verify`와 실제 실행 평가를 구별한다. 선언 검사만으로 에이전트 행동의 개선을 입증했다고 보고하지 않는다.

후속 계획 적대적 리뷰에서는 A8와 같은 누락이 여전히 통과할 수 있는지, 정상 경로를 막는지, 지침 중복만 늘어나는지를 확인했다. 당시 Important 2건을 계획에 반영하고 재검토를 통과한 뒤 구현했다.

## 5. 진단 단계에서 수행한 검증

- S3 원문 118행에 원본 padding이 실제 전달됐음을 확인했다.
- 입력/S3 커밋의 원본 blob 동일성과 S3 CSS의 padding 누락을 대조했다.
- 코더 반환의 브라우저 미실행과 외형 일치 문구를 동일 반환에서 확인했다.
- 고정된 입력 case·motion·coverage 기록과 실제 Coordinator 위임을 대조했다.
- 관련 플러그인 정본과 설치 버전 1.1.10의 byte 동일성을 확인했다.
- 제품 코드 변경과 커밋이 없는 진단 단계이므로 `make verify`나 새 에이전트 실행 평가는 수행하지 않았다.
- Serena/Graphify: 정확한 파일·문자열·Git blob·기존 실행 원문 대조로 확인했다. 도구 초기화·그래프 갱신·서브에이전트 호출은 하지 않았다.
