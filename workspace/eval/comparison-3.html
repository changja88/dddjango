dddjango 3차 비교 — codex-4 vs claude-3

목적이 다르다. 1·2차는 "누가 더 나은 코드를 쓰나"였고, 3차는 "편집한 B1 표준이 두 런타임에서 실제로 결함을 막나"의 검증이다. 같은 마스터(dddjango-smoke-sample)에서 git clone한 바이트 동일 시작점 + 토씨 같은 프롬프트 + 고정 게이트로 동시 실행.

핵심 결과 headline

✅ B1(빈혈·판정 인프라 누수) = 양쪽 런타임 모두 설계·코드 끝까지 차단

편집한 B1 표준 — 원칙 단일출처(architecture-ddd §3.2 "판정·불변식은 도메인이 소유하고 프로덕션 경로에서 실행") + 리뷰어 2층 탐지(design-review-ddd 설계단계·discipline-reviewer 코드단계) — 이 Codex·Claude 두 런타임 모두에서 작동했다. 과거 결함이 둘 다 부재:

  • DR-13 codex-2 빈혈(Product.reserve() 죽은코드, 판정이 인프라 SQL에만) → 이번 codex-4엔 없음 (판정이 Order.create 도메인, 프로덕션 호출).
  • DR-14 claude-2 죽은코드(deduct_stock() 미배선) → 이번 claude-3엔 없음 (deduct_stock가 ACL→응용서비스로 프로덕션 배선).

정직 경계: 각 런타임 N=1. 이건 "표준이 작동·발화함"의 강한 sanity이지, B1 재발 빈도의 통계적 측정이 아니다(그건 N≥5 블라인드 필요). B1은 확률적 결함이라 1회 통과가 "항상 막는다"를 뜻하진 않는다.

⚠️ 통제 이탈(프레임워크): claude-3가 고정 답 plain Django를 어기고 django-ninja를 썼다 — Claude 파이프라인이 프레임워크를 게이트로 안 물어서 고정 답을 적용할 기회가 없었다(2차 DR-14와 동일 재현). 따라서 프레임워크-의존 코드·테스트 수는 비교 불가. 단 B1·판정소유·동시성 철학·게이트 노출은 프레임워크와 무관하므로 유효하게 비교된다.

소유 배치 분기: 코덱스는 판정을 요청측(orders 도메인)이 스냅샷 대비 내리고, 클로드는 소유자(catalog.Product)에 deduct_stock로 둔다. 둘 다 "판정=도메인·프로덕션 호출·SQL 무누수"라 B1-clean이며, 어느 BC가 판정을 소유하느냐만 다른 정당한 DDD 분기다.

게이트 노출 철학 재현되는 진짜 차이

1·2차에서 관측된 "claude가 결정을 더 많이 사용자에게 노출" 성향이 3차에서 다시, 더 또렷하게 재현됐다.

claude-3 — 결정 9개를 게이트로 분할

  • G0 (4분할): 배치 → 주문 단위 → 인증 → G0 승인
  • G1 (4분할): OD-1 판정소유 catalog 변경 → 멱등성 → FK → G1 승인
  • G2 (1): nice-to-fix 선택 + 승인

각 결정에 권장안·근거·트레이드오프를 동반. OD-1 옵션 텍스트에 "빈혈모델 회피"가 명문 등장 = B1 원칙을 사용자에게 노출.

codex-4 — 결정을 명세에 통합, 게이트 최소

  • G0 (1): 스코프+lens+배치+프레임워크+러너를 단일 승인으로
  • G1 (1): 설계 명세 단일 승인
  • G2 (1): 구현 단일 승인

판정소유·동시성·FK 결정을 명세에 조용히 박고 한 번에 승인 요청. PROMPT.md를 선제적으로 읽어 고정 답에 자발 정렬.

노출 입도 ≈ 9 : 3. 둘 다 *결정 내용*은 사실상 같은 지점에 도달하지만(판정=도메인, 새 BC, version CAS), 클로드는 사람에게 묻고 코덱스는 알아서 정한다. 어느 쪽이 우월이 아니라 제품 철학 차이(통제 가시성 vs 진행 속도).

종합 평가 verdict

1) 검증 목적 — 달성

편집한 B1 표준이 두 런타임 모두에서 설계→코드 끝까지 빈혈/판정 누수를 차단. 1·2차에서 비결정적으로 나타났던 B1 결함이 이번엔 양쪽 부재. 표준이 "발화하고 작동함"을 입증(N=1).

2) 코드 우열 — 이번에도 단정 불가, 대등

프레임워크 이탈로 head-to-head 코드품질 비교는 confound됨(DR-14 재확인). 유효축에선 대등 — 둘 다 완전 §0 4계층·ACL 분리·version CAS·B1 clean. 클로드가 오류 분류(503 분리)·동시성 방어(retry 3+IMMEDIATE)가 더 두텁고, 코덱스가 더 단순·집약적.

3) 재현되는 진짜 차이 = 게이트 노출 철학 + 스택 취향

1·2·3차 일관: 클로드는 결정을 사람에게 더 많이 노출(이번 9 vs 3)하고 기본 스택이 Ninja, 코덱스는 명세에 통합·plain Django. 코드 우열이 아니라 제품 철학·기본값 차이.

방법론 교훈: Claude는 프레임워크를 게이트로 안 물으므로, 스택을 통제하려면 고정 게이트 답이 아니라 프롬프트 본문에 "plain Django, django-ninja 금지"를 명시해야 한다. PROMPT.md의 프레임워크 항목을 게이트 표에서 프롬프트 본문으로 올리는 것이 다음 라운드 통제 개선.
