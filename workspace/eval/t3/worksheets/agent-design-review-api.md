## 0. 배선 정책 (문서 전역 — §16 4원 종합의 이 문서 적용판)

이 문서는 «절차 층»(command+agents) 소속이지만 본문 절반(s005·s006)이 **API 계약 lens 의 심사 규범**이라 위임 기본값 표를 세 갈래로 갈라 적용했고, 갈래마다 문면 근거를 §2 표에 남겼다. 갈래 이름은 선행 저작본(`agent-discipline-reviewer` 검수표 §0)의 P-A/P-B/P-C 판별자를 이 문서에 맞춰 승계한 것이다.

- **P-A 절차·입출력 규범**(호출·모드 선택·입력 격리·리포트 형식·집행성 판정·확인 토큰·스코프 확대 금지) → `delegatedTo: command-dddjango`. 근거 = §16 위임 기본값 표 «command+agents(절차 층) → Coordinator(절차 준수 판정 주체)». s001~s004·s007 b1·b3 이 여기 든다. 이 갈래에 `enforcedBy` 가 하나도 없는 것은 도피가 아니라 실독 결과다 — 27종 중 «에이전트 호출·모드·리뷰 입력 격리·노트 형식»을 보는 검사기가 0이다.
- **P-B 심사 대상(architect 명세의 계약 결정) 규범** → `delegatedTo: agent-design-review-api`. 근거 = ①문면 술어가 심사 행위(«…인지 본다/확인한다/검토한다», «…맞는가») + ④§16 위임 기본값 표 **architecture-api 행 → `agent-design-review-api`**. s005·s006 이 여기 들고, 같은 계약 축을 코드에서 집행하는 검사기가 실재하면 `enforcedBy` 를 병기해 «기계 절반 + 의미 잔여»를 분업시켰다(파일럿 ninja §6.2 배선과 축 일치).
  - **술어 형태에 따른 D 병기 기준**(적대 리뷰 F3·F4 반영 — 이 구분이 §0 에 없어 «의도인지 누락인지» 가 판별 불가였다): 술어가 **심사형**(«…인지 본다 / …하는지 확인한다 / 검토한다», «…맞는가»)이면 판정 주체가 실재하므로 `delegatedTo` 를 반드시 병기한다. 술어가 **직접 요구·금지형**(«…해야 한다», «…하면 blocker다» — 문장 자체가 코드 계약이고 심사 행위를 지시하지 않는다)이면 파일럿 **규정판**(`spec-implementation-django-ninja-final` s023-6.2 의 exception path·Result/None path·two-argument `Status` 행 전부 E-only) 판형을 승계해 `enforcedBy` 만 둔다. 이 기준으로 **norm 77 은 D 를 신설**했고(원문 «…직접 return하는지 **확인한다**» — 같은 블록 norm 74 와 동일 술어형), spec 104건 중 D 부재는 직접 요구형 3건(norms 75·76·78)으로 한정된다.
- **P-C 타 소유 명시** → 문면이 다른 역할을 판정 소유자로 지목한 조항만 그 Agent 병기(§16 «기본값 이탈은 문면 근거»). 판별자는 선행본과 같다 — «판정 소유 배분·중복 판정 배제 선언»(«…의 몫», «…에게 보낸다», «…소유이며 여기서는 …만 지적한다») → 지목 Agent. 적용: s004 b1-2(architect) · s004 b6-4(discipline) · s005 b4-2(db) · s006 b8-3·b12-6·b16-2(discipline) · s007 b2(ddd+db).
- **enforcedBy 절제 원칙(과잉 배선 방지)**: 축이 반대이거나 술어가 없는 검사기는 병기하지 않고 그 사실을 basis 에 적었다 — 멱등성(`check-idempotency-scope-creep` 은 «미요청 도입 차단»으로 축 반대) · `title` property · `str(exc)`/sensitive 노출 · `AuthenticationError` · Sunset/deprecation · 페이지네이션/레이트리밋 · `@api_controller` **형태** 요구(T3 선행 리뷰 F5 실증 — 27종에 형태 술어 0). 반대로 문면·docstring 근거가 있는데 기본값으로 도피한 자리는 0건이다.
- **절제 목록 추가 등재 + E 철회 1건**(적대 리뷰 F5·F9 반영):
  - ⑴ `check-transient-overmapping.py` — 초판에서 spec·검수표 어디에도 심의 흔적이 없었다(§0 이 «배제 사실도 basis 에 적는다»고 선언했으므로 미등장 자체가 공백). docstring 실독 결과 자기 축 선언이 «G1에서 이미 승인된 `preserve-established` brownfield handler 방어선»이고, «헬퍼 무조건-True 위장·register-only 핸들러는 **일부러 잡지 않는다**(저-recall)» 하며 의미 렌즈를 «② design-architect 생산자 예방 · ③ discipline-reviewer 의미 체크(transient 과잉매핑)»로 명시 이양한다. 실물은 `RETRYABLE_STATUSES = {503, 409}`(L91) + AND 4조건(핸들러 타입 ∧ 분기 부재 ∧ retryable 반환 ∧ 신규·수정 파일)으로 «분기 없는 무조건 매핑» 한 형태만 차단한다. 따라서 norm 72 의 **code-json 분기**(«raw infra 기본 500 … 정규화 후 `ErrorSchema` 생성 확인» — docstring 스스로 «code-json 에서는 custom handler 자체가 독립적으로 위배»라 이 검사기가 그 분기를 집행하지 않는다고 적었다)에도, norm 28 의 «409/422 선택이 의미론에 맞는가»에도 축이 어긋나 **병기하지 않고 두 규범 basis 에 심의 흔적을 남겼다**.
  - ⑵ **norm 28 의 기존 E 2종을 철회**했다(→ D-only). `check-business-vocabulary` #119 는 «framework 소유 status 의 BC 재선언·광고 금지»(= norm 86 의 축이고 거기 이미 정배선), `check-ninja-boundary-middleware` 는 «`driving_layer` 자작 미들웨어의 전역 `settings.MIDDLEWARE` 자가등록 차단»(= norm 90 의 축이고 거기 이미 정배선)이며 둘 다 «상태 코드 **선택**이 의미론에 맞는가» 술어를 갖지 않는다. norm 29 에서 `check-idempotency-scope-creep` 을 «축 반대·술어 없음»으로 배제한 것과 같은 강도를 적용한 결과다 — **오용-차단 축은 부분 커버로 인정하지 않는다**는 경계선을 여기서 긋고, 같은 검사기를 자기 축 규범(86·90)에만 두어 기계 커버리지 그림의 이중 계상을 막았다.

## 3. 재진술 유예 (교차 문서 — spec 미기입 · T3 소급 패스 대상)

브리프 규약대로 **다른 문서 상대는 spec `restates` 에 넣지 않고** 여기에만 기록한다(전 웨이브 완료 후 소급 패스가 일괄 연결). 좌표는 발주서·센서스 restate 열을 출발점으로 삼되 **상대 원문을 직접 열어 행을 확인**했다(`dddjango/agents/design-review-db.md` L12–26·L40–44 · `dddjango/agents/design-review-ddd.md` L13·L40–44 · `dddjango/agents/design-architect.md` s005 · `dddjango/agents/acceptance-tester.md` L23–48 · `dddjango/agents/discipline-reviewer.md` s003).

> **좌표 규약**: `design-architect.md`(마커 7행)·`discipline-reviewer.md`(마커 8행)는 이미 렌더 마커가 삽입돼 있어 현재 파일의 raw 행이 센서스 좌표와 어긋난다. 아래 표의 상대 좌표는 도구와 같은 기준인 **마커 제거본(센서스) 번호**다 — 예: architect 12-slot 도입문은 raw L44 = 센서스 L39.

## 4. 경계 판단 메모 (블록 경계·kind·계수의 애매점과 근거)

- **① (전문) 절의 프론트매터 처리**: s001 은 헤딩 라인이 `---`(YAML 여는 구분자)이고 도구가 그 한 줄을 `djr:headingSnapshot` 으로 가져간다. 나머지는 §13 자연 단위로 잘랐다 — `name:`(b1) · `description:`(b2·규범 3) · `tools:`(b3) · `skills:` 목록 3행(b4 — 마커 포함 verbatim 한 덩이) · 닫는 `---`+빈 줄(b5) · 본문 문단(b6). **kind=code 를 쓰지 않은 이유**: §13 은 code 리터럴을 «여는 펜스~닫는 펜스»로 한정하는데 프론트매터엔 펜스가 없다. 선행 저작본(`agent-design-architect`/s001)의 판형과 동일하다.
- **② 블록 간 구분자 귀속**: 전 절에서 §13 대로 **빈 줄은 선행 블록의 후행 스팬**에 붙였고(예: s004 b1 = L33–35 로 헤딩 직후 빈 줄 L33 + 본문 L34 + 뒤 빈 줄 L35), 절 선두 구분자만 첫 블록의 선두에 귀속시켰다. 절 끝 빈 줄은 마지막 블록이 삼킨다(s002 b3 = L17–18 등). 도구의 «헤딩+블록 연결 == 절 스팬» 단언이 통과해 byte 등가가 기계 확인됐다.
- **③ 불릿 목록의 블록 단위**: 리스트 항은 **항목당 한 블록**으로 잘랐다(§13 «리스트 항은 마커 포함 verbatim 으로 norm/prose 블록에 귀속»). s003 의 입력 6항(b3~b8)은 무규범 prose 로 두었다 — 부모 문장이 «다음 묶음을 준다»뿐이고 여섯 항이 전부 동사 없는 명사구(«… evidence», «… pin», «… dump»)라 항목별 독립 의무 동사가 없다. 선행본이 `agent-discipline-reviewer`/s002 에서 유사 목록을 개별 채번한 것은 그쪽 항목이 «…를 받는다»·«…를 추가로 받아 읽는다»처럼 **각자 술어를 가진 완결 문장**이어서다(두 원문 실독 대조 — 문면 차이가 판정 차이의 근거). 다만 이 여섯 항의 «수령» 의무 자체는 b2(L23)의 Work 1건이 이미 진다.
- **④ 같은 문서 안 재진술 판정(spec `restates` 0건)**: 두 쌍을 심의했다. ⑴ s001 b2-3(«명세나 코드를 직접 수정하지 않는다») ↔ s007 b1(«두 모드 모두 코드·명세를 수정하지 않는다») ⑵ s001 b6(«한 모드만 읽기 전용으로 수행») ↔ s002 b1·b2(모드 정의). 둘 다 **부분 중첩**이지 블록 사본이 아니다 — `djr:restates` 는 블록 대 블록 관계인데 s001 b2 는 프론트매터 description 한 줄(규범 3개 동거)이고 s007 b1 은 독립 불릿이라 사본 관계가 성립하지 않는다. 선행 저작본의 같은 판정(«부분 중첩 — restates 블록 사본 관계 아님»)을 따랐고, 대신 두 Work 의 basis 에 «동축 재진술 의심»을 남겨 소급 패스가 찾을 수 있게 했다.
  - **심의 대상 확장(F10 반영)**: «수정 금지» 동축은 2쌍이 아니라 **3각**이다 — ⓐ norm 3(s001 b2-3 «명세나 코드를 직접 수정하지 않는다») · ⓑ **norm 13**(s004 b1-2 «명세를 직접 고치지 않는다 — 반영은 architect의 몫») · ⓒ norm 102(s007 b1 «두 모드 모두 코드·명세를 수정하지 않는다»). 판정은 **부분 중첩 유지**다(ⓑ 는 `DESIGN_CONTRACT_REVIEW` 산출 문맥의 «명세» 한정이고 소유 배분절이 붙어 대상·모드가 좁다). 다만 초판은 ⓑ 에만 의심 태그가 없어 소급 패스가 세 번째 꼭짓점을 놓칠 수 있었으므로 norm 13 basis 에도 태그를 넣었다.
  - **소급 패스 통합 후보(F8·F10 반영)**: «Work #3 ↔ #13 ↔ #102 동축 3각» — 같은 규범 내용의 Work 가 그래프에 병존하므로 소급 패스에서 restates 연결 또는 통합 여부를 재판단한다(현 단계 처분은 3건 모두 독립 존치).
- **⑤ s006 을 한 절로 둔 것**: 12개 slot 은 번호 목록이지 헤딩이 아니라 기계 절 분할 단위가 아니다(E10-recon §1 «step 번호는 절 분할 단위가 아니다» 규약과 동일). 각 slot 은 **한 행 = 한 블록**이고 그 안의 문장들이 `djr:statesNorm` 다중 연결로 각자 Work 를 가리킨다(§13 «문장 해상도 = Work 채번 단위가 문장 · 행 중간 분할 불요»).
- **⑥ class 판정 기준**: 조건 한정·carveout 문장은 `Exception`(예 s002 b2-1 발동 조건, s005 b2-2 RFC 한정, s006 각 slot 의 `preserve-established` 문장), 금지 술어는 `Prohibition`, 인정·허용 술어는 `Permission`(s006 b3-2 external evidence 허용·b9-2 code 공유·b19-3 형태 중립)로 갈랐다. `Override` 는 0건이다 — 이 문서엔 다른 규범을 **우선해 무르는** 문장이 없다(«대신하지 않는다»류는 갈음 금지라 `Prohibition`).
- **⑦ 부분 커버 배선의 한계 표기**: `check-error-centralization` 을 slot 1·2 의 열거/입증 확인에 병기했으나 그 docstring 이 보증하는 것은 «project inventory correspondence»(코드 측 실물 대응)뿐이라 명세 기재 형식은 미집행임을 basis 에 적었다. 같은 방식으로 `check-composition-root`(registrar/URLconf provenance 축 한정 — 클래스 컨트롤러 **형태** 축은 27종 전체에 술어 0)·`check-ninja-boundary-middleware`(전역 미들웨어 자작 축 한정)·`check-synthetic-infra-exc`(합성 금지 축 한정, «기본 500» 판정은 미집행)에 한계를 명시했다. 선행 적대 리뷰 F3~F5 가 지적한 «과장 basis» 회피가 목적이다.
- **⑧ L69 2문째 선두절(«slot 6 shape와 별도 변경 승인은 유지하되»)을 접은 근거**(적대 리뷰 F6 반영): 이 절은 새 의무가 아니라 **slot 6 Work(norms 56–58)의 재확인 양보절**이다 — 술어가 없고(«유지하되»), 지시 대상이 이미 채번된 slot 6 규범과 동일하며, 규정판 architect 원문 slot 12 도 같은 2절 구조(«slot 6의 shape 및 별도 변경 승인은 보존하지만 … 자동 영구 테스트로 만들지 않는다»)다. 따라서 미채번하고 norm 82 를 금지 축 하나로 두었다(같은 문서에서 L52·L56·L71 을 분리 채번한 것은 그쪽 선두절들이 **독립 술어와 다른 소유자**를 가졌기 때문 — 분리 기준은 «술어+소유자가 갈리는가»이지 «절이 둘인가»가 아니다).
