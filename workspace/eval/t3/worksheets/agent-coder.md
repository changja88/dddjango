계수 규율(과대 방지): 한 문장 안의 절이라도 ⑴ **행위 대상이 다르거나** ⑵ 별개 축의 규범 유형이 갈릴 때만 분리 채번했다. 같은 축의 부정면 재진술(49행 «그대로 유지·검증하고 code profile로 암묵 이주하지 않는다», 63행 «실행한 것처럼 보고하지 않는다 — 미실행 사유를 명시한다», 16행 «`discipline-tdd` decision을 먼저 적용하고 `implementation-test`는 … mechanics로만 쓴다»)은 1 Work 로 합쳤다. 근거 문장(69행 «*왜* — 코더가 보는 건 한 슬라이스…», 34행 «골격 위반은 `check-layer-skeleton` 이 … 먼저 잡고 반송한다(#487)» 같은 검사기 동작 서술)과 열거 조각(22~25행 입력 목록의 명사구)은 규범으로 세지 않았다. 문면이 **서로 다른 규칙 번호를 명시 귀속**하면(34행 «#489·#490») 분리 신호로 읽었다.

**분리/병합의 1차 판별자(라운드 2 명문화 — R2-9 반려 근거)**: §13 «Work 채번 단위가 문장»을 이 문서에 적용할 때 단위는 **독립 종결절(종결어미로 끝나는 서술)**이다. 연결어미로 물린 부사절(«-지 않고»·«-며»)은 방식 한정이라 자체 Work 가 아니다. 종결절이 둘 이상이면 위 ⑴⑵ 로 가르고, 둘인데도 병합한 자리는 «같은 축의 부정면 재진술»로 사유를 남긴다. 이 판별자로 네 자리가 모두 정합한다 — 61행(종결절 1 → 1 Work) · 63행(종결절 2·같은 축 = 보고 정직성 → 병합, 사유 기록) · 67행(문장 2·행위 대상 상이 → 2) · 68행(종결절 2·행위 대상 상이 = 명세 변경 ↔ 보고 → 2). 42행의 «관찰 전용이며 판정·평가에 쓰지 않는다»는 독립 종결절 + 행위 대상 상이(수치의 «기재» ↔ 수치의 «사용»)라 라운드 2 에서 채번을 추가했다.

계수 규율의 경계 사례 4건:

1. **병합(16행 스킬 우선순위)**: «`discipline-tdd` decision을 먼저 적용하고 `implementation-test`는 승인된 `add/update`의 mechanics로만 쓴다»는 대상 스킬이 둘이지만 **한 결정의 두 면**(어느 층이 decision 을 주고 어느 층이 mechanics 만 주는가)이라 1 Work. 이 판정이 센서스 4(=description 2 + 16행 2)와 일치하는 근거이기도 하다.
2. **병합(49행 preserve 유지)**: «유지·검증하고 … 암묵 이주하지 않는다»는 design-architect 검수표의 «존중한다 — 암묵 재결정하지 않는다» 선례와 같은 꼴(부정면 재진술)이라 1 Work.
3. **분리(53행 관할 한정 ↔ 이동 금지)**: «이 표준의 관할은 승인 스코프가 낳는 산출물이다»(Exception — 적용 범위)와 «승인 스코프 밖 기존 배선·배치는 … 옮기지 않는다»(Prohibition — 행위 금지)는 성격이 갈려 분리. design-architect 검수표가 같은 두 축을 #127(Exception)·#95(Prohibition)로 나눈 선례와 일관된다.
4. **병합(53행 preserve native 범위 ↔ 기존 배선 실물 입력 배제)**: «preserve 가 유지하는 native 는 오류 wire 산출물이지 registration/composition 이 아니다 — 기존 BC 의 배선 실물은 배선 결정의 입력이 아니다»는 한 축(배선 답습 차단)의 앞뒤라 1 Work. design-architect #94 가 같은 쌍을 한 Work 로 처분한 판형을 그대로 따랐다.

## 4. 경계 판단 메모

- **블록 경계 규약 적용**: 블록 = 내용 행 + 후행 빈 줄(§13 «블록 간 구분자는 선행 블록의 후행 스팬에 귀속»). 절 첫 블록만 헤딩 직후 빈 줄을 선두에 흡수(§13 유일 예외 — s002 b1 은 19행 빈 줄부터, s003 b1 은 28행 빈 줄부터 시작). 도구가 연속·비중첩·전량 커버와 «헤딩 + 블록 = 절 스팬» byte 등가를 단언했고 **exit 0**(수리 루프 0회).
- **s001 헤딩**: 무앵커 선두 절이라 `djr:headingSnapshot` 이 프론트매터 개시 구분자 `---`(1행)다. 블록은 2~17행을 YAML 키 단위로 분해했고, `skills:` 는 키 + 목록 8행(5~13)을 한 블록으로 묶었다 — 들여쓴 목록이 키에 종속된 자연 단위이기 때문. 종결 `---`(14행)은 후행 빈 줄(15행)과 함께 prose 블록이고, 본문 문단(16행)은 후행 빈 줄(17행)을 물고 norm 블록이 된다.
- **kind 판정**: 이 문서에 코드 펜스 0 · 체크박스 0 · 표 0 이라 **norm/prose 2종만** 썼다. 프론트매터는 펜스가 아니므로 code 가 아니다(§13 «code = 여는 펜스~닫는 펜스 전체 라인»). 백틱 인라인 코드(`add/update`·`$PY` 등)는 펜스가 아니라 kind 에 영향이 없다.
- **norm/prose 가르기**: 프론트매터에서 규범을 지는 것은 `description`(3행) 하나다 — `name`·`tools`·`skills` 는 런타임 메타라 prose. s002 의 22·24행만 norm 이고 23·25행은 열거 조각이라 prose 로 남겼다(같은 불릿 목록 안에서 kind 가 갈리는 자리 — 블록은 행 단위로 나뉘므로 byte 등가에는 무해).
- **한 행 다규범의 실증**: s004 24 불릿이 98 Work 를 진다(행당 평균 4.1). 최대는 42행 **10 Work**(라운드 2 에서 «관찰 전용이며 판정·평가에 쓰지 않는다» 1건 추가) — 이 자리가 §13 «블록 내 문장→Work 대응(문장 등장 순 = 채번 순)»의 전형이라 `djr:statesNorm` 다중 연결로 처리했고 블록을 행 중간에서 쪼개지 않았다. 추가분의 자리는 문장 등장 순 그대로 «수치 기재 의무» 뒤·«실행 생략 금지» 앞이다.
- **basis 근거 유형 표기 정정(라운드 2 R2-11)**: 50~52행 계열(#76·#78·#79·#80·#81·#82·#84 등)의 basis 가 «②파일럿 §6.2 동형»을 ②(docstring § 인용) 자리에 적고 있었다. §16 의 4원은 ①문면 역할명 ②docstring ③P0 커버 ④registry #N 뿐이고 **«파일럿 선례»는 어디에도 없다** — 선례는 판정의 «참고»지 배선의 «근거»가 아니다. 실물 커버 자체는 구현 실측으로 성립하므로(constructor keyword 추출 L1357·L1822 · 무인자 생성 판정 L1368 · `_status_call` + `len(call.args) < 2` 두 인자 Status 게이트 L2851·L3553 · `_header_assignment_valid` L3082·L3158 · `_literal_error_status_call` L3563 · 위반 메시지 L7126 «direct two-argument Status(<approved HTTP status>, error)») 배선은 그대로 두고 **근거 유형만 ①(§16 역할명→«controller checker») + 실장 확인으로 다시 적었다**. docstring 원문 인용이 성립하는 자리(«Enforce direct controller-owned code-profile error mapping» 계열)는 ②를 함께 남겼다.

- **`check-composition-root.py` 의 lane 계약(라운드 2 R2-4 수리)**: 이 검사기는 두 레인이고 **profile 게이트가 서로 다르다**. ⑴ **DI 레인** — `_filtered_di_findings` 는 profile 과 무관하게 돌며 #497(«파일이 아니라 폴더» — 단일 파일 `composition_root.py` 모양)만 낸다. ⑵ **code-profile 레인** — registrar/URLconf 직접 import provenance·exactly-once(#107·#108·#109·#111·#440)는 docstring 문면 «명시적 `dddjango-code-json` lane 은 … 함께 검사한다. **preserve/auto 에서는 이 의미 검사를 적용하지 않되**»대로 code-json 한정이고, 구현에서도 `main()` 이 `config.profile == "dddjango-code-json"` 일 때만 `_composition_semantics` 를 부른다(실측). 라운드 1 저작은 이 구분을 놓치고 49·53행의 **preserve 맥락 규범** basis 에 «#107~#109 가 profile 무관 실행»이라 적었다 — 정확히 그 레인에서 꺼지는 백스톱을 켜져 있다고 쓴 셈이고, 같은 spec 의 53행 첫 Work 가 lane-gated 인용문을 그대로 싣고 있어 자기 모순이었다. 라운드 2 에서 두 basis(49행 Override · 53행 preserve native 한정)의 composition-root 레그를 «DI 레인(#497)만 profile 무관 · provenance/exactly-once 는 code-json 한정 → preserve 면 부분 공백»으로 정정했다. `check-layer-skeleton`·`check-test-config` 는 `--error-profile` 인자 자체가 없고 `check-context-isolation` 은 docstring 이 «registry 가 렌더하는 `--error-profile` 은 수용하되 무시»라고 못박으므로 **나머지 세 레그는 정정 불요**(실측 확인).
- **enforcedBy 병기/공란의 판별 기준(라운드 2 R2-12 명문화)**: 규범의 **자기 축**에 검사기 술어가 하나도 닿지 않으면 enforcedBy 공란 + 기본값(예: 42행 «Bash 로 실행해 Green 확인» · 55행 «skip/xfail 없이 실행» — 실행 «사실»을 보는 검사기가 없다). 자기 축의 **일부 국면**에 결정적 술어가 닿으면 enforcedBy 를 달고 basis 에 미커버 범위를 반드시 병기한다(예: 55행 header 도달 증명 — 코드 형태 축은 `_header_assignment_valid` 가 집행하고 «mounted client 도달의 테스트 증명»은 미커버 · 55행 OpenAPI 검증 — 선언 일치 축은 집행하고 실행 방식·보고 축은 미커버 · 40행 pytest 채택 — 바인딩 축만). **인접하되 담당 술어가 다른 자리는 병기하지 않는다**(아래 4번). `delegatedTo` 병기는 축 기준이다 — 구현 규율 축이면 ⓓ, 12-slot·오류 계약 축이면 `agent-design-review-api`. 라운드 2 에서 이 기준으로 #37(픽스처 선택 규율 축 — ⓓ 누락)·#82·#84(오류 계약 축 — review-api 누락)를 보정했다.
- **오배선 회피 기록 4건**(표면상 검사기가 있어 보이나 기본값을 유지한 자리):
  1. **53행 «승인 스코프 밖 기존 배선·배치 이동 금지»** — 표면상 트리 규범이지만 기존 배치의 **처분 권한**은 G0 사용자 빚 결정 소관이라 `check-layer-skeleton`/`check-app-container` 로 배선하면 **반대 의미**가 된다(검사기는 «옮겨라»를 요구하지 «옮기지 마라»를 요구하지 않는다). 56행의 대칭 규범도 같은 처분.
  2. **38행 migration 전용 테스트 금지** — `check-mechanism-ownership.py` ⑵ 의 #336~#338·#593 은 마이그레이션 «파일» 규율이고, `check-test-config.py` ⑵ 는 `test/` 층 성격 축이다. 어느 쪽도 «migration 을 대상으로 삼는 테스트를 만들지 마라»를 묻지 않으므로 검사 공백으로 두었다.
  3. **42행 실행 범위(BC-범위 기본·전역 스위트 금지·영향 소비자 경로 포함)** — `check-context-isolation`(#12 OHS·published_event)·`check-broker-contract` 는 그 표면의 **구조**를 볼 뿐 «어떤 테스트를 돌리라»는 실행 범위를 보지 않는다. 문면 자신이 «전역 판정은 게이트·완료 기준 소유»라고 못박아 기본값을 지지한다 — 도피가 아니라 문면 근거를 가진 기본값이다.
  4. **53·56행 «함수형 `Router` 발명·강제 금지»**(라운드 2 R2-5 수리 — 라운드 1 오배선 철회) — `check-ninja-boundary-middleware.py` 를 달았던 자리다. 이 검사기의 **유일 술어는 «`driving_layer/` 자가 정의 미들웨어가 전역 `settings.MIDDLEWARE` 에 자가등록됐는가»** 하나이고(판정 절 실독 + 구현 grep — Router 술어 0), 함수형 `Router` 의 발명·강제는 `MIDDLEWARE` 를 건드리지 않아 **구조적으로 발화 불가**다. basis 가 인용했던 «django-ninja 는 협상/임의 status 를 경계 안에서 네이티브로 낸다(§6.3)»는 이 검사기가 잡는 **대표 회귀의 rationale 문장**이지 담당 술어가 아니다 — 동기를 공유한다고 §16 이 요구하는 «집행 커버»가 되지는 않는다. 두 자리 다 enforcedBy 를 비우고 basis 에 «미들웨어 자작 변종 한정 인접 커버 — Router 형태는 검사 공백»을 명기했다(실측 근거를 가진 기본값이라 §16 «기본값 도피»가 아니다).
- **preserve-established 계열의 배선**: profile-gated 검사기 4종(`check-error-centralization`·`check-api-error-controller-contract`·`check-openapi-error-declaration`·`check-response-schema-bypass`)은 preserve 실행에서 «add no new error-mapping semantics»라 preserve 쪽 의무를 집행하지 않는다. 그래서 46·48·49·54·55·56행의 preserve 문장들은 enforcedBy 없이 `command-dddjango` + `agent-design-review-api` 로만 위임했고 basis 에 «검사 공백»임을 명시했다(기본값 도피와 구분). 예외는 49행 «preserve 가 보존하는 것은 오류 wire 계약 산출물까지다» — 이 문장은 **파일트리·배선·import 방향·테스트 규율이 profile 무관 표준임**을 선언하므로 그 네 축의 소유 검사기(`check-layer-skeleton`·`check-composition-root`·`check-context-isolation`·`check-test-config`)를 병기했다. **단 `check-composition-root` 레그는 DI 레인(#497)만 profile 무관**이라는 한정을 라운드 2 에서 basis 에 못박았다(위 lane 항 — R2-4).
- **`check-transient-overmapping.py` 의 이례적 인용**: 49행의 «승인된 RFC/custom handler·helper 를 code-profile 금지 때문에 제거·추출·리팩터링하지 않는다»와 «이 preserve branch 를 새 handler·helper·conversion point 를 만드는 근거로 쓰지 않는다» 두 자리에 이 검사기를 달았다. docstring 이 «G1에서 이미 승인된 preserve-established brownfield handler를 보존할 때 … 지키는 방어선»과 «이 checker가 발화하지 않아도 새 handler/recognizer를 만들 근거가 되지 않는다»를 **문면과 축자 동형**으로 적고 있어, 이 자리를 기본값으로만 두면 §16 «역도 성립»에 걸린다. **다만 두 번째 인용문은 «내 비발화를 근거로 삼지 마라»는 비집행 선언이고 그 문장의 주어는 `dddjango-code-json` 이다**(라운드 2 R2-7). 그 «직접 오류 경계 계약»의 실제 집행자 `check-api-error-controller-contract` 도 preserve 에서는 «add no new error-mapping semantics»라, 이 규범의 **본거지인 preserve 면은 검사 공백**이다 — basis 에 그 사실을 명기하고 `agent-design-review-api` 를 병기해 같은 불릿의 다른 preserve 규범들과 처분을 맞췄다.
- **71행 «스코프 고수»의 배선**: `check-idempotency-scope-creep.py` 를 달았다 — 이 검사기는 스코프크립 **일반**이 아니라 «미요청 멱등성» 1종만 결정적으로 커버하지만(docstring «이 checker의 소유는 … accepted scope 밖에 추가되는 것을 막는 데 한정»), 그 1종이 이 규범의 유일한 기계 백스톱이므로 병기하고 basis 에 커버 범위를 명기했다.
