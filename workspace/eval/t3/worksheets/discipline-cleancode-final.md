## 4. 경계 판단 메모

- **공백 소유(§13) — 실물 정정(적대 리뷰 F1 수용)**: 이 메모의 초판은 «블록 간 빈 줄을 선행 블록 후행 스팬에 귀속»이라고 적었으나 **spec 실물과 정반대**였다. 기계 재검(spec 288블록 전수): **비최초 블록 109개가 빈 줄로 시작**하고, **절-최종이 아닌 블록 중 빈 줄로 끝나는 블록은 0개**다. 즉 이 spec의 실제 관행은 **블록 간 구분자 = 후행 블록의 선두 스팬 귀속**(예: s005-1.2 b2=[62,63]·s006-1.3 b2=[70,71]·s013-2.1 b2=[113,121]). 절 선두 구분자는 89/89절 전건 첫 블록 선두 귀속(§13 명문 예외), 절 말미 `---` 수평선+빈 줄은 88/89절에서 마지막 블록(대개 prose)에 귀속했다(s011-1.6·s026-2.14·s038·s057-6.5·s068-8.6·s075-9.5·s084-10.8·s089-11.4·s103-13.3·s110-14.6·s130-16.6·s140-17.9·s141-18 등). byte 등가는 도구가 보장하고 «헤딩+블록 연결 = 절 스팬» 단언이 전 89절에서 통과했으므로 산출물 자체는 무결하다 — 정정 대상은 메모 문면뿐이다.
- **파일럿 판형 대조(F1 수정안 문면의 부분 교정)**: 리뷰 수정안은 후행 귀속을 «파일럿 판형과 동일 관행»이라 했으나 실측은 **지배적일 뿐 균일하지 않다** — `spec-architecture-ddd-final`은 lead 귀속 9건/trail 귀속 1건(s051-8 b2=[2061,2061]은 빈 줄 단독 블록이라 양쪽 계수에 중복 계상되는 퇴화 사례), `spec-implementation-django-ninja-final`은 lead 4건/trail 3건이며 그중 s023-6.2 b19=[626,627]은 **진성 선행 귀속 1건**이다. 따라서 정확한 진술은 «파일럿의 지배적 관행과 같고, 본 spec은 그 관행을 109/0으로 완전 일관되게 적용했다»이다.
- **kind 판정**: 코드 펜스는 여는~닫는 펜스 전체 1블록(kind=code, 60개), 표는 머리행·구분행 포함 행 단위(kind=table-row, 55개 — 계수에는 데이터 행만 산입), 불릿은 항목 1개=블록 1개(파일럿 ninja s022-6.1 판형 준용), 산문은 문단 단위. 규범을 실은 블록만 kind=norm(125), 나머지 산문은 prose(48). 체크박스(`- [ ]`)는 이 문서에 0건이라 checklist-item 미사용(s142는 표이지 체크박스가 아니다 — 센서스 문면과 일치).
- **코드 블록이 유일 운반체인 3절**: s018-2.6·s024-2.12·s025-2.13은 헤딩 아래 본문이 펜스뿐이라 헤딩 규칙 Work를 code 블록에 statesNorm으로 걸었다. 산문 블록이 없어 다른 자리가 없고, §13대로 kind는 code(리터럴 datatype xsd:string)를 유지했다. s025-2.13은 규칙이 코드 주석 라벨(«허용»/«좋은 예»)로만 표현돼 class를 Permission으로 잡았다(센서스 «보수 포함» 승계). **첫 사례 기록(F3 수용)**: 파일럿 2건은 code 블록 전건 norms=0이므로 «code 블록이 Work를 진술»하는 것은 코퍼스 최초다. 원문 재확인 결과 세 절의 절 스팬은 각각 [187,198]·[279,290]·[291,303]이고 헤딩 다음 행부터 닫는 펜스까지가 전부 펜스라 **다른 운반체가 물리적으로 없다** — 재량 판단이 아니라 강제다. BlockShape에 kind 제약이 없어 게이트도 통과(4단+SHACL exit 0). 규약 권고는 아래 §5에 상신한다.
- **s028-3.1 ↔ s029-3.2 축자 중복(P0 특이 발견 6)**: «의미 있는 이름으로 다른 함수를 추출할 수 있다면…» 문장이 두 절에 그대로 있다. 정본을 **s029-3.2/b2**로 판정했다 — 그 문장은 §3.2(«한 가지만 해라»)의 판정 기준이고 §3.1에서는 곁가지 인용이다. 사본 쪽 블록(s028-3.1/b1)에 restates를 걸었고, 같은 블록의 첫 문장(«함수는 작게»)은 독립 규범이라 Work를 유지했다 — 블록 단위 restates라 «한 문장만 사본»인 상황이 블록 전체로 표현되는 한계를 자인한다. 이 판정으로 두 절의 Work 수가 센서스(3/2)와 정확히 일치한다.
- **s142 사본 층 판정**: §1에 쓴 대로 28행 Work 미승격. 압축 재진술이라 1행이 여러 정본을 가리키는 팬아웃이 8행 있다(예: 2534행 → s070-9.1·s072-9.2·s073-9.3). restates는 다중 목적어가 허용되므로 그대로 표현했다.
- **문장↔Work 대응이 애매했던 절**: ① s016-2.4 — 151행이 2문장(«범위 비례» 의무 + «넓은 범위=긴 이름/좁은 범위=짧아도 됨» 허용)이라 b1에 2 Work, 153행 수치 가이드에 1 Work = 3. ② s092-12.2 — blockquote의 em-dash 이후 절을 독립 지시로 계상(«답이다» 판정 / «결과 분기를 쓴다» 의무 / «이 절의 raise 우선» 범위 한정) = 3, 본문 1 = 4. ③ s097-12.7 — 한 문단 3문장을 4 Work로(보호 / «외부» 경계 결정 / 경계에서 검증 / 구체 예외 한정). ④ s026-2.14 원리 1의 «과승격 방지» 문장은 pass-through 면제와 열린 집합 멤버 한정이 한 문장의 앞뒤 절이라 **1 Work(Exception)로 묶었다** — 쪼개면 절 합계가 28이 되어 발주서 27과 어긋난다. ⑤ s093-12.3 — 첫 문단의 «분리하면 이해·수정이 쉬워진다»는 효과 서술로 보아 비규범 처리, 둘째 문장(인지 경계 원칙 = 절대 명령 아님)과 셋째 문장(try 최외곽·구체 예외)만 계상해 2 + 후단 문단 5 = 7.

- **로스터 밖 도구**: s049-5.2의 Ruff는 registry Checker(check-*.py 27종)가 아니라 enforcedBy로 표현할 수 없다 — 위임으로 처리하고 근거 문면에 남겼다.
- **s015-2.3 kind=norm 유지(적대 리뷰 F4 기각)**: 리뷰는 «s018류는 body kind(code) 유지 + statesNorm인데 s015만 진단문을 kind=norm으로 승격 — 기준 불일치»라 했으나 **전제가 틀렸다**. kind 5종은 한 축이 아니라 두 축이다 — `code`·`table-row`·`checklist-item`은 **운반체 형태가 결정**하고(§13 «code 리터럴 = 여는 펜스~닫는 펜스 전체 verbatim»), `norm`↔`prose`는 **평문 문단·불릿의 내용이 결정**한다(T3-authoring-brief «norm = 규범 문장 포함 문단/불릿»). s015-2.3 b1=[136,137]은 펜스가 아닌 평문 문단(137행 «불용어(Info, Data, a, the)를 사용하면 … 이름만 달리한 것이다»)이므로 규범을 실은 이상 kind=norm이 정의상 강제다. s018-2.6은 헤딩 다음 행부터 절 끝까지 전부 펜스라 평문 블록이 아예 없어 code가 강제된 것이다. 두 절은 같은 축에서 갈린 것이 아니라 애초에 서로 다른 축에 놓여 있어 «불일치»가 성립하지 않는다. 제안된 대안(kind=prose + statesNorm)은 brief의 kind 정의를 정면으로 위반하므로 채택하지 않았다.

## 5. 소급 패스 인계·상위 보고 (적대 리뷰 처분에서 파생)

### 5.1 상위 보고 — 규약 §13 문면 vs 실측 판형 (F2)

authoring.md §13 문면은 «블록 간 구분자(공백·개행·빈 줄)는 **선행 블록의 후행 스팬**에 귀속»(절 선두만 유일 예외)인데, 파일럿 판형과 본 spec의 실측 관행은 **후행 블록 선두 귀속**이다(본 spec 109/0). 본 spec은 판형 준수이므로 무수정이며, 소급 패스 착수 전에 §13 문면 개정 또는 전 코퍼스 재슬라이스 중 하나를 결정해야 한다. 저작·수리 에이전트는 `ontology/`·`workspace/tools/` 문서를 쓸 수 없으므로 **결정과 반영은 규약 소유자 몫**으로 상신한다.

**단, F2의 «구조적 강제» 논거는 과장이라 교정해 상신한다.** 펜스 verbatim 규정이 선행 귀속을 불가능하게 만드는 것은 **구분자가 code 블록 *뒤*에 올 때뿐**이며, 본 spec의 lead 귀속 109건 중 그 구조적 강제에 해당하는 것은 **10건**, 나머지 **99건은 선택 여지가 있었는데도 일관성을 위해 후행 귀속을 택한 것**이다. 즉 §13 문면과 판형의 충돌은 «규정이 자기모순이라 강제된 결과»가 아니라 «규정이 강제하지 않는 99건에서 판형이 규정과 다른 길을 굳혔다»가 정확한 진단이며, 이 차이가 개정 방향(문면 개정 vs 재슬라이스)의 비용 판단을 바꾼다.

### 5.2 규약 추가 권고 — 헤딩-전용 규범 절의 통일 표기 (F3)

s018-2.6·s024-2.12·s025-2.13처럼 **헤딩 아래 본문이 펜스뿐인 절**은 헤딩 규칙 Work를 code 블록에 걸 수밖에 없다(코퍼스 최초 사례 3건). §13에 «헤딩-전용 규범 절: 평문 운반체가 없으면 헤딩 규칙 Work를 절의 **첫 블록**에 statesNorm으로 귀속하고 kind는 운반체 형태를 그대로 유지한다»를 명문화하면 후속 문서의 재량 편차를 없앨 수 있다. 본 spec은 이미 그 규칙과 동일하게 처리돼 있어 개정이 소급되어도 무수정이다.
