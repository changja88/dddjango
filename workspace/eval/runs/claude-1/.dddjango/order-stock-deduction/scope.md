# 스코프 메모 — 재고 차감 주문 생성 API

## 무엇을 (What)
주문 생성 요청을 받아, 대상 상품의 재고가 충분하면 **재고를 차감하고 주문을 생성**하고, 부족하면 **409로 거절**하는 HTTP API.

## 기대 동작 (외부 관찰)
- 재고 충분: 주문 생성 + 재고 차감, 성공 응답(생성됨 계열, 주문 식별자 반환).
- 재고 부족: 주문 미생성 + 재고 불변, **409 Conflict** + 에러 본문.
- 존재하지 않는 상품: 거절(상태 코드는 설계에서 확정).
- 잘못된 입력(수량 누락/0 이하 등): 거절(상태 코드는 설계에서 확정).

## 경계 (Scope boundaries)
- 포함: 단일 상품·수량의 주문 생성, 재고 검증·차감, 부족 시 거절.
- 제외(이번 범위 밖): 결제, 장바구니, 여러 상품 한 주문(멀티 라인), 주문 취소·환불, 인증/인가(명세에서 명시적으로 다루지 않으면 익명 허용), 재고 복원.

## 제약 (Constraints)
- 기존 `catalog.Product`(name, price, stock=PositiveIntegerField) 재고를 차감 대상으로 사용.
- 현재 설치 패키지: **Django 4.2.30만**. DRF·Django Ninja·pytest **미설치**. → API 어댑터·테스트 러너 선택이 도구 추가 여부와 직결(아래 미결정 항목).
- 동시 주문 시 재고 초과 차감(over-sell) 방지가 핵심 — 차감은 원자적/경쟁 안전해야 함(트랜잭션·조건부 갱신 = db lens 핵심 관심사).

## G0 결정 (사용자 승인 2026-05-28)
- 스코프·활성 lens(ddd·api·db): **승인**.
- **배치: 기존 `catalog` 앱에 포함** (주문을 새 앱으로 분리하지 않음).
- **API 어댑터: 순수 Django `JsonResponse` 뷰** (Ninja·DRF 도입 안 함, 의존성 0).
- **테스트 러너: Django 기본 `TestClient` + `manage.py test`** (pytest 도입 안 함).

## 미결정 → 설계에서 확정 (architect)
1. 성공 상태 코드(201 등), 입력 검증 실패·상품 없음의 상태 코드.
2. 에러 본문 형식(409 및 기타 에러의 JSON 구조).
3. 재고 차감 동시성 전략(트랜잭션 + 조건부 갱신/select_for_update 등 over-sell 방지).
4. 주문·주문항목 모델 구조(단일 라인 전제이나 모델 형태는 설계 결정).

## 활성 lens (제안)
- **ddd**: 항상 활성.
- **api**: 활성 — 새 엔드포인트·요청/응답·상태 코드(409 포함) 신설.
- **db**: 활성 — 재고 차감의 트랜잭션·동시성(over-sell 방지), 주문 테이블 신설·마이그레이션.

## 배치 (Placement) — G0에서 사용자 확인
주문(Order)은 신규 개념이고 기존 `catalog`(Product)의 재고를 건드린다. 둘 자리:
- ① 새 독립 앱(`orders`)으로 분리
- ② 기존 `catalog`에 포함
- ③ 설계자가 정함
(사용자 선택을 여기 기록 예정)
