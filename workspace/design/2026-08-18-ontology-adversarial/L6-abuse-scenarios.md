## S-0. 기존 빚 채널 — 반박 불성립 (명시 기록)

registry_gate의 `--legacy-debt-file` 채널을 «빚으로 밀고 잊는» 공격은 **성립하지 않는다**. 실물 확인(`dddjango/scripts/registry_gate.py:22-23, 209-211`): 빚은 사용자 승인 목록이어야 하고, exit에서 빼되 **매 실행 «빚» 절로 반드시 보고**(침묵 금지)한다. 잊힘 방지 마찰이 설계에 내장돼 있다. — 문제는 블루프린트가 신설하는 채널들이 이 자체 관례 수준의 마찰을 **하나도 물려받지 않았다**는 점이다(S-1·S-9).

## S-1. 미러 lint 화이트리스트 — 무상한·무재심 빚 채널 (major)

- **시나리오**: 릴리즈 직전 미러 lint가 새 잔차로 red → 시간 압박 → 잔차를 화이트리스트(또는 «전용 절 제외»)에 추가 → green → 영원히 재심 안 됨. 제외된 영역 안의 규범 충돌은 이후 영구 불가시.
- **실현 가능성 — 높음**: 초기 화이트리스트부터 대형이다. A3 §3.4 실측 — command 쌍 정규화 잔차 **178행**(대부분 정당한 플랫폼 재저작), coder 9행·design-architect 14행·discipline-reviewer 6행. 즉 «잔차 존재 = CI 차단»(§5)이 성립하려면 첫날부터 수백 행급 제외 자산이 필요하고, 이후 추가는 최저 저항 경로다.
- **방어 유무 — 없음**: 블루프린트 §5(69~72행)는 정규화 자작 규칙의 버전 관리·골든 회귀·마이그레이션까지는 R4를 수용했으나, R4 반례 2(R4 122행)의 명시 경고 — *«제외 규칙은 커질수록 검사를 스스로 무력화한다. 제외 목록 자체를 별도 자산으로 심의·상한 관리해야 한다»* — 는 **탈락**했다. 상한·재심 주기·매 실행 보고 의무 전부 미명세.
- **부수 결함 — §5 내부 모순**: «CI 차단은 결정 신호(해시·**잔차 존재**)만»과 «③ 잔차는 신호 등급 리포트(완전 자동 게이트가 아니라 사람 결정 보조)»가 같은 절에 공존한다. 잔차가 차단하면 화이트리스트 채널이 필연이고, 차단 안 하면 실증 피해(표류 2건)조차 사람 triage 습관에 의존한다 — 어느 쪽인지 동결 전에 갈라야 한다.
- **수정안**: 화이트리스트·전용 절 제외 목록을 항목별 {사유, 날짜} 필수의 독립 버전 자산으로 명문화 + registry_gate 빚 절 동형의 «매 실행 전량 보고» + S4 게이트 완료 기준에 «제외 목록 전수 재심» 추가 + §5의 차단/보조 관계를 한 문장으로 확정.

## S-2. fuzzy 해제의 습관화 (major)

- **시나리오**: claude 정본 갱신 → codex twin 자동 fuzzy=true → 소유자가 내용 확인 없이 `fuzzy: false`로 되돌리는 것이 습관화. 또는 반대로 fuzzy=true가 아무 결과도 없어서 무기한 방치.
- **실현 가능성 — 높음**: 1인 체제 + 해제가 YAML 한 줄 수정. gettext 세계에서 fuzzy 방치·기계적 해제는 알려진 운영 행태이고, R4 B-4의 K8s 사례가 보여주듯 대규모 조직조차 사람 판정 부하를 등급 분류로 낮춰야 했다.
- **방어 유무 — 없음**: §3(51행) 주석 «자동 true → 사람 해제»와 §1 D4가 전부다. ⑴ fuzzy=true의 집행 결과(릴리즈 차단? 보고만?)가 미정 — 차단이면 맹목 해제를 부르고, 비차단이면 방치를 부른다. 어느 쪽이든 마찰 설계가 없다. ⑵ 해제에 요구되는 최소 증거(같은 커밋의 codex 쌍 갱신, 또는 «정당 차이» 사유 기록)가 없다 — norm_hash 재기록은 기계적으로 가능하므로 «재검토했다»와 «해시만 다시 찍었다»를 lint가 구분 못 한다. ⑶ 자동 true의 트리거 자체(무엇의 해시를 무엇과 비교하나)도 미명세. ⑷ R4가 제시한 완화책 — mdbook식 «fuzzy면 낡은 미러 대신 정본 폴백»(R4 B-2 43~45행, 시사점 5 136행: *«낡은 규범은 미번역보다 해롭다»*) — 을 채택도 기각도 안 했다.
- **수정안**: D4에 명문 — fuzzy=true 잔존 레코드는 릴리즈 게이트에서 «빚 절» 방식으로 전량 보고(차단 여부는 결정해 적기), 해제는 같은 커밋에 codex 쌍 파일 변경 또는 사유 필드 기록을 동반해야 lint green, 수렴기 전 과도기의 정본 폴백 채택 여부를 명시 결정.

## S-3. alias 오매핑 (major)

- **시나리오**: 코퍼스 문면의 «#7»이 registry #7(1..27)인지 무접두 규칙 #7(538 공간)인지 비한정인 채로, alias 역인덱스가 이를 어느 한 규칙으로 «흡수 완료» 처리 → 잘못된 규칙이 참조되는데 lint는 «미흡수 잔여 참조 0»으로 green.
- **실현 가능성 — 중~높음, 실증 있음**: ⑴ `workspace/tools/corpus_lint.py:12`가 이미 명문으로 인정 — *«무접두 registry 순번이 생존 규칙 번호와 겹치면 기계로 [판별 불가]»*. ⑵ P0 §2-①(38행) — implementation-django §10.2가 문서 한정자 없는 «§11.1·§11.2»로 타 문서를 가리켜 자기 §11과 충돌한 실증. ⑶ A3 §3.4 — 번호 공간 판독을 지탱하는 산문 규약 문장(«범위 표기 #A~#B…») 자체가 codex판에서 누락된 표류 실증: 판독 규칙이 산문에 사는 한 그 산문도 표류한다. ⑷ «§3.2»는 architecture-ddd·ninja 등 복수 문서에 실재(저장소 grep 확인).
- **방어 유무 — 부분**: §2(24행)의 «lint가 alias→ID 전단사성과 미흡수 잔여 참조를 검사»는 **레지스트리 안에 선언된 alias 간 충돌**만 잡는다. 문면의 비한정 참조를 어느 alias로 귀속할지의 해소 규칙이 없으므로, 오귀속은 전단사성 검사에 안 걸린다. 그런데 §2의 alias 예시 자체가 비한정 좌표(«registry#7», «§3.2 판정소유»)를 포함한다.
- **수정안**: alias 등재 문법을 네임스페이스 한정형으로 닫는다(예: `reg#7` / `rule#7` / `ddd:의사결정#3` / `architecture-ddd§3.2` — 비한정 «#N»·맨 «§N.M»은 alias 등재 금지). 문면 비한정 참조의 해소는 anchor_integrity_check의 닫힌 문법 + 해소 실패=UNRESOLVED 보고 방식을 차용해 «흡수 완료» 오판을 «미해소 보고»로 강등.

## S-4. ID 재사용 — 기계 장치 부재 (major)

- **시나리오**: S3 중 잘못 등재한 레코드를 «깔끔하게» 파일 삭제로 정리(또는 일몰 후 정리 커밋) → 발행 사실이 저장소 현재 상태에서 소멸 → 이후 신규 발행 시 차번호 산정(현존 파일 스캔)이 그 번호를 재발행 → 서로 다른 두 의미가 한 ID를 시차 공유.
- **실현 가능성 — 중**: 레코드가 파일 1개(`registry/rules/DJR-0417.yaml`)라 삭제가 자연스러운 정리 동작이고, LLM 에이전트 보조 워크플로에서 «다음 번호»는 현존 파일 최대값+1로 계산되기 쉽다.
- **방어 유무 — 규약만, 기계 없음**: §2(22행) «발행된 ID는 영구 잔존, 재사용·재배정 금지»는 문장이고, §3(58행)의 lint 집행 항목은 «ID 유일성» — **현존 레코드 간** 유일성이지 발행 이력 대비 검사가 아니다. 차번호 할당 절차 자체가 미명세다. R1이 차용한 OBO·McMurry L7은 tombstone **잔존**까지가 규약인데, 잔존을 강제하는 기계가 없다.
- **수정안**: append-only 발행 대장(`registry/ISSUED` 또는 next_id 카운터 파일)을 두고, 신규 발행은 대장 경유만 허용 + registry_lint가 «대장에 있는 ID의 레코드 부재(상태 없는 소멸)»와 «대장에 없는 ID의 레코드 등장»을 exit 2로. (checker_registry.py의 import-시 로스터↔실재 assert와 동형 원리 — 저장소에 이미 있는 관례다.)

## S-5. quote 갱신 ↔ revision 미연동 — 개정 전파의 honor-system (major)

- **시나리오**: 산문 규범을 의미 변경하면서 같은 커밋에서 레코드의 `quote`(와 norm_hash)를 새 문장으로 같이 고침 → quote↔원문 대조 lint green, 미러 해시 green → `revision`은 1 그대로 → 그 ID를 인용하는 검사기·미러 절의 Outdated 강등(§2 «개정 전파의 기계화»)이 **한 번도 발화하지 않음**.
- **실현 가능성 — 높음**: lint가 이 행동을 **보상**한다 — quote를 안 고치면 red, 고치면 green. revision 증가는 사람의 기억에만 의존한다. 블루프린트 스스로 §2(25행)에서 P0 표류 2건을 «updates 미기록» 유형으로 진단했는데, 자기 기계가 정확히 같은 실패 양식(개정 사실의 메타데이터 미기록)을 갖고 있다. R3(192행)도 «기계 검출(인용문 해시 대조)과 수동 개정 신호(revision)는 상호 보완 병용»이라고 revision의 수동성을 인정한 상태다.
- **부수 결함 — quote 매칭 규율 미정**: 대조가 정확 일치인지 정규화 후 일치인지 미명세. 정확 일치면 마크다운 개행 reflow·중점(·)·«» 표기 변경만으로 위양성이 다발하고(R3 189행이 «인용 주석 대량 갱신 비용»으로 경고), 그 압력이 매칭을 느슨하게 틀게 만들며, 느슨해진 매칭은 의미 변화를 삼킨다 — 위양성 경로가 곧 위음성 경로다.
- **수정안**: registry_lint에 git 차분 기반 규칙 명문 — «`quote`/`norm_hash` 필드 변경 ∧ `revision` 미증가 → exit 2»(anchor_diff의 앵커 차분과 동형 구현). quote 대조는 미러 lint 정규화 층①과 **같은 자산**을 공유한다고 §3에 명시(정규화 규칙 이원화 방지).

## S-6. 스냅샷 배포와 정본의 시차 — 레지스트리 배포 지위 미정 (major)

- **시나리오 (a) 미동봉**: 레지스트리가 플러그인에 안 실리면, 배포 스냅샷 속 docstring `Rule-ID:`·문서의 DJR 참조가 소비 시점에 해소 불가 — P0 A4(76행)가 이미 실증한 구조(«무접두 #N 정본 미동봉 → 규칙 전문 그라운딩 원천 불가 축»)의 재생산.
- **시나리오 (b) 동봉**: 레지스트리가 claude/codex 양판에 실리면 새 미러 표면이 생기는데, 현행 미러 검사는 릴리즈 시점뿐이다 — `Makefile:94`(corpus_mirror_sync)·`Makefile:106`(scripts diff -rq), A3 §4 실측 «릴리즈 사이는 무검사». 릴리즈-사이에 정본 레지스트리가 revision 2로 올라가도 배포본 검사기·문서는 revision 1 기준으로 판정하며, 아무 장치도 이 시차를 보고하지 않는다.
- **방어 유무 — 없음**: §7(87행) «배포본은 무버전 정본의 날짜 스냅샷 파생물(schema.org 모델)» 선언 1행이 전부다. 스냅샷을 언제·무엇이 파생하는지, 레지스트리가 스냅샷에 포함되는지, S1~S5 어느 Stage가 이를 구현하는지 전부 공백 — 선언만 있고 사다리에 자리가 없는 «매달린 약속»이다.
- **수정안**: §7에 레지스트리 동봉 여부를 결정 명문(동봉이면 어느 미러 도구·어느 시점이 검사하는지까지) + 스냅샷 파생 절차를 담당 Stage 산출물로 배정 + 릴리즈-사이 창 축소 방안(미러 lint의 상시 실행 지점)을 명시.

## S-7. Stage 중단·일몰 잔재 (major)

- **시나리오**: S4에서 일몰 발동(«미러 lint·커버리지 표만 남기고 레지스트리 동결», §8 98·101행). 이미 발행된 10~30건 레코드는? 산문은 Active형 지속 개정(§7)이므로 동결 레코드의 quote·anchor·twins는 필연적으로 부패한다. 삼각 대조 lint를 계속 돌리면 산문 개정마다 red(→ lint를 끄게 됨), 끄면 죽은 좌표가 남아 에이전트·grep이 낡은 규범을 «정본인 줄 알고» 소비한다. R7 A-3(28~30행)이 인용한 바로 그 형태 — *«바꾸는 것이 위험해서 갱신되지 않는 온톨로지, 그 동결이 새 표류의 시작»* — 를 일몰 조항이 스스로 만든다. S3 도중 중단이면 draft 레코드가 남는데, draft를 소비자가 무시해야 한다는 규정도 없다.
- **방어 유무 — 부분**: §8 원칙 «산출물이 독립 가치를 갖도록 설계(중도 중단해도 손실 없음)»는 S1·S2에는 성립하지만(미러 lint·커버리지 표는 단독 유용), S3 산출물(발행 ID·레코드·참조)에 대해서는 **주장일 뿐 설계가 없다**. 일몰 조항이 동결본의 일부라고 명문화(§8)해 놓고 처분 절차는 비워 뒀다.
- **수정안**: 일몰 조항에 처분 절차 명문 — ⑴ 전 레코드 status 일괄 전이(retired + 일몰 사유) ⑵ docstring·문서의 DJR 참조를 제거하거나 tombstone임을 명시 ⑶ quote 대조·삼각 대조 lint의 스코프 종료 선언 ⑷ «draft 상태 레코드는 어떤 소비자도 규범으로 삼지 않는다»를 S3 진입 시점부터 규정.

## S-8. 신규 규칙의 등재 누락 — 무저항 경로 (major)

- **시나리오**: S3 이후, 규칙을 스킬 문서에만 추가하고 레지스트리 등재를 잊음(시간 압박 시 최저 저항 경로 — 문서 수정은 즉시, 등재는 별도 작업). «ID 발행은 신규·개정 규칙부터»(D3)는 규약이지 검출기가 아니다. 커버리지 표가 신규 절을 자동 todo로 받으면 todo는 합법 주차장이 되어 침묵 빚으로 축적된다.
- **실현 가능성 — 높음**: R7 반론 5(122행)가 정확히 이 축을 지목했다 — *«lint가 못 보는 축(… 새 문서 추가 시 등재 누락)»* — 그런데 v2는 이에 무응답이다.
- **방어 유무 — 없음**: §4-2 대차 0 마감은 «모든 절이 4값 중 하나»만 요구하고, 신규 절이 표에 **어떻게 진입하는지**(자동 todo인지, 미분류 실패인지)를 명세하지 않는다. §4-3 래칫은 후퇴만 차단하므로 신규 todo는 안 걸린다. S3 완료 기준(삼각 대조 green)은 등재된 것들 사이의 정합만 본다.
- **수정안**: 커버리지 파생 뷰 재생성 시 직전 스냅샷 대비 신규 절을 «미등기»로 exit 2(자동 todo 금지 — 사람이 4값 중 하나를 명시 선택해야 green) + S3 이후 게이트에 «이번 개정 diff에 걸린 절의 등재 여부 검사»를 추가.

## S-9. 래칫 후퇴의 사유 무기록 (minor)

- §4-3 «커버리지 스냅샷 체크인 + CI 대조 — 무단 후퇴 차단». 1인 저장소에서 모든 커밋은 자기 승인이므로 «무단»과 «승인된 후퇴»를 가르는 것은 기록뿐인데, 스냅샷 하향 수정에 사유 기록 의무가 없다. registry_gate 빚 채널(«반드시 보고»)과 비대칭. 스냅샷 수정 자체가 diff 흔적을 남기므로 minor — 수정안: 사유 없는 하향 diff를 lint가 exit 2로.

## 종합

동결 불가(blocker)급은 없다 — 여덟 건 모두 §9-4(동결 전 자유 개정)로 반영 가능한 명세 추가다. 그러나 공통 패턴이 뚜렷하다: **블루프린트의 신설 기계 장치들은 «성실한 소유자»를 전제하고, 게으름·시간 압박에 대한 마찰 설계가 체계적으로 빠져 있다.** 대조적으로 이 저장소의 기존 인프라는 그 마찰을 이미 갖췄다(registry_gate 빚 채널의 승인 목록+전량 보고, checker_registry의 import-시 자기 assert, 도구들의 self-test 선행 관례). 신설 장치가 자기 저장소의 관례 수준에 못 미치는 것이 이 렌즈의 핵심 결함이며, 수정은 전부 «기존 관례의 이식»으로 충분하다.
