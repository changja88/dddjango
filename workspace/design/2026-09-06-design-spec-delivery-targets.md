# dddjango 속도 개선 진행 현황

목표: **현재의 설계·코드 품질을 유지하면서 작업 시간을 줄인다.**

최종 갱신: 2026-09-06. 사용량 한도는 개선 대상에서 제외한다.

## 2번 — 설계 문서를 읽고 필요한 내용을 전달하는 시간 줄이기

**현재 상태: 기존 5종과 추가 ‘원문 전량 읽기’ 비교실험까지 실행 완료. 추가 실험은 읽기 단계만 빨라졌고 총시간 단축은 확인하지 못했다. 플러그인에 반영한 변경은 없다.**

아래 5번은 하나의 실험에서 검색 결과와 사람이 선별한 원문의 효과를 각각 비교한 것이다. **수동 선별 방식은 실수·누락 위험을 이유로 사용자 판단에 따라 후속 후보에서 제외했으며, 실행한 결과만 이력으로 남긴다.** 5번의 시간 감소율은 **전체 문서 전달 대비**이며, 두 수치는 **계정 교체 전 / 후** 순서다. 교체 전은 조건별 2회의 중앙값, 교체 후는 조건별 1회를 비교했다. 2·3번의 시간 단축 여부는 조회 시간 기준이며, 5번은 모델 작업 시간 기준이다.

**품질 변화:** O = 검사한 지표에서 변화 확인, X = 검사한 범위에서 변화 미발견. 개선·악화 방향은 ‘효과’ 컬럼에 적었다. 비교하지 않은 항목은 X 대신 **미검증**으로 표시한다. 1번은 원문 보존, 2번은 필수 내용 확보, 3번은 조회 결과, 5번은 제한된 동작·판단 검사 기준이다. 6번은 원문·내용 검사와 출력 형식을 구분한다. **X가 전체 설계·코드 품질의 동일성을 보장하지는 않는다.**

| 실험 | 무엇을 비교했나 | 시간 단축 | 품질 변화 | 효과는 어땠나 | 현재 판단 |
|---|---|---|---|---|---|
| **1. 문서 분할** | 큰 문서 그대로 읽기 ↔ 내용을 보존해 나눠 읽기 | **미측정** | X | 원문 읽기의 한도 초과 오류를 재현했다. 분할한 133조각은 전량 복원됐고, 실제 읽기 표본 3개도 손실 없이 읽혔다 | 읽기 안정성 개선 후보. 133조각 전부의 실제 도구 읽기는 미검증 |
| **2. 검색 방식** | 단순 검색 ↔ 제목 포함 검색 ↔ 관련 절 확장 | **단축 없음** | O | 제목 추가는 필수 내용 확보 **5/6 → 5/6으로 개선 없음**. 관련 절 확장은 필요한 내용을 찾고도 전달량 제한 처리에서 버려 **5/6 → 0/6으로 악화**. 조회 시간도 약 **65 → 73 / 87ms**로 증가 | 시험한 변경 방식에서는 개선 효과 없음. 단순 검색도 일부 핵심을 놓쳐 단독 사용 불가 |
| **3. 조회 엔진** | 같은 관계를 JSON ↔ SPARQL로 조회 | **단축 없음** | X | 같은 6개 조회 묶음의 중앙값이 **JSON 1.37ms / SPARQL 203.89ms**. 결과는 같고 SPARQL이 약 **202.52ms 더 느림** | 이번 구현·조회에서는 SPARQL의 속도 이점 없음 |
| **4. 개정·누락 검사** | 문서 개정과 관계 오류를 넣고 검출 여부 확인 | **미측정** | 미검증 | 오래된 자료와 잘못된 참조는 검출했지만 **관계 자체의 누락은 검출하지 못함**. 자동 재생성 약 13ms. 검사 적용 전후의 산출물 품질은 비교하지 않았다 | 안전성 일부 확보. 이것만으로 누락 방지나 속도 개선을 보장하지 못함 |
| **5. 모델 입력 — 검색 결과** | 전체 문서 전달 ↔ 검색 결과 전달 | 가드 구현 **85.5% / 90.3%** · 생성자 판단 **39.9% / 21.5%** | X | 두 과제 모두 작업 시간이 감소했고, 보정 후 제한된 동작·판단 검사에서는 전체 문서 전달과 같은 통과 결과였다 | 시간 감소 관측. 다만 2번 실험에서 질문에 따라 필수 내용이 빠짐 |
| **5. 모델 입력 — 선별 원문** | 전체 문서 전달 ↔ 사람이 필수 원문을 골라 전달 | 가드 구현 **85.3% / 95.7%** · 생성자 판단 **57.4% / 29.2%** | X | 두 과제 모두 작업 시간이 감소했고, 보정 후 제한된 동작·판단 검사에서는 전체 문서 전달과 같은 통과 결과였다. 사람이 고르는 시간은 포함하지 않았다 | **후속 후보에서 제외.** 수동 선별의 실수·누락 위험 때문에 사용자가 제외 결정. 실험 이력만 보존 |
| **6. 원문 전량 읽기** | 원본을 250행씩 읽고 오류 범위를 나눠 재시도 ↔ 같은 원문 38조각을 전부 읽기. 각 3회 | **읽기 단계 21.7% 단축 / 총시간 단축 없음** — 실패 포함 실제 시도는 23.9% 증가 | **X** 원문·19개 내용 검사 / **O** 출력 형식 | 원문 603KB는 전 6회 모두 전달됐다. 읽기 중앙값 **72.3→56.6초**, 크기 오류 **총 33→0회**. 실제 시도 총시간 중앙값은 **144.0→178.4초**. 내용 검사는 사후 동일 추출 후 전부 19/19지만, 지정 형식까지 통과한 응답은 원본 0/3·분할 1/3 | **전체 속도 개선책으로 채택 근거 없음.** 읽기 안정성·읽기 단계 이점만 관측. 형식 실패를 성공으로 바꾸지 않았으며 성공 완료 시간의 단축률은 산출 불가 |

5번 품질 확인: 실제 Claude의 정상 응답 **18회**를 확보했다. 원 채점은 **17/18 통과**였고, 채점기가 정상적인 문자열 연산을 거부한 1건을 독립 검토했다. 같은 보정 기준을 가드 응답 9개 전체에 적용한 결과, 제한된 동작·판단 검사는 **18/18 통과**했다. 원래 응답·채점·계정 한도 거부 기록은 보존했다.

6번 품질 확인: 별도의 신규 6회다. **5회는 JSON 앞 설명 문장 때문에 지정 형식 검사에 실패**했다. 모든 응답에 같은 규칙으로 JSON 본문을 추출해 기존 19개 검사를 적용하면 전부 통과하지만, 이는 사후 내용 확인이지 사전 성공 판정의 변경이 아니다. 표의 총시간에는 이 실패 시행도 포함되며, 형식 수정 시간은 측정하지 않았다. 읽기 단계는 CLI 시작부터 마지막 Read 반환까지다.

**효과의 해석 범위:** 위 감소율은 두 개의 작은 과제에서 관측한 실행 시간 차이이지, dddjango 전체의 확정 개선율이 아니다. 원문을 고르는 시간은 제외했고 캐시·추론량·실행 시점의 영향도 분리하지 못했다. 계정 교체 전후는 합산하지 않았다. 전체 설계·코드 품질, 자동 선정의 누락 방지, 선정·갱신 비용, 불필요 원문량은 아직 검증·측정하지 않았다.

**현재 결론:** 내용을 선별·생략하지 않는 전량 읽기는 원문 누락 없이 읽기 오류를 없앴지만, 이번 실험에서는 총시간 감소로 이어지지 않았다. **문서 분할만으로 작업 전체를 빠르게 만들 수 있다고 판단하지 않는다.** 검색 입력은 필수 내용 누락 때문에 그대로 적용하지 않고, 수동 선별은 제외 상태다. 2번 문제는 여전히 미해결이다. 승인된 추가 실험은 종료했으며 SPARQL 도입이나 3번 실험은 진행하지 않았다.

상세 실행 시간·계산 근거·실험 이력은 [에이전트용 참고 자료](2026-09-06-dddjango-speed-working-notes.md), [기존 실험 계획](../eval/design-spec-delivery/2026-09-06/protocol.md), [기존 결과 집계](../eval/design-spec-delivery/2026-09-06/summary.json), [6번 원 판정](../eval/design-spec-delivery/2026-09-06/full-read/summary.json), [6번 사후 내용·시간 대조](../eval/design-spec-delivery/2026-09-06/full-read/supplemental-audit.json)에 보존한다. 시간 감소율은 `(기준 시간 − 비교 시간) / 기준 시간 × 100`으로 계산했다.

## 3번 — 설계·규칙·검사기 판단 불일치로 인한 재작업 줄이기

**현재 상태: 문제 사례 확인 완료. 비교실험은 아직 하지 않았으며 효과는 미측정이다.**

fortune/account에서 설계대로 구현한 뒤 검사에 걸리거나, 수정한 방법이 다른 규칙에 걸려 다시 작업한 사례를 확인했다. 검사기의 오탐과 에이전트의 규칙 판단 오류가 모두 있어 검사기만 고치면 해결되는 문제는 아니다.

2번부터 다루기로 했으므로 3번의 개선 방법 비교·선정은 대기 중이다. 이번 속도 개선 작업에서 3번에 반영한 변경은 없다.
