2 이름의 문법 형태가 «책임의 방향»을 선언한다

이게 축이다. 과거형이냐 명령형이냐는 취향이 아니라, 실패를 누가 처리하는가를 코드에 박는 일이다.

책임의 방향이 정해지면 나머지가 전부 따라온다 — 실패 처리의 위치, 수신자의 수, 재시도의 주체, 계약이 바뀔 때 누가 깨지는가. 그래서 이름을 잘못 붙이면 그 뒤의 결정이 통째로 어긋난다.

4 Fowler 의 «수동공격적 커맨드»

“A simple example of this trap is when an event is used as a passive-aggressive command. This happens when the source system expects the recipient to carry out an action, and ought to use a command message to show that intention, but styles the message as an event instead.” Martin Fowler · What do you mean by “Event-Driven”? (2017)

왜 «수동공격적»인가 — 겉으로는 요구하지 않는 척하면서 실제로는 요구하기 때문이다.

5 우리 자리를 재보면 — 이름이 «안 닫힌 결정»을 드러낸다

여기가 진짜 발견이다. 우리 포트는 이름 · 의미 · 메커니즘 셋이 서로 다른 곳에 서 있다.

이것이 T19(전달 보장) 과 같은 뿌리다. 「전달 보장이 없다」가 추상적으로 들렸다면, 여기가 그 구체적인 자리다.

6 판정 규칙 — 물음 하나

「이 호출이 실패했을 때 «누가» 알아야 하나?」
  • 발신자 → 커맨드. 이름은 명령형, 실패는 시끄럽게, 재시도는 발신자 몫
  • 수신자만 → 사건. 이름은 과거형, 실패는 각자, 발신자는 성공으로 끝냄
  • 아무도 → 지워도 되는 코드다

7 그럼 open_host_service/ 와는 뭐가 다른가

여기서 한 번 헷갈리는 자리가 있다. OHS 도 «BC 사이의 계약»이고 사건도 «BC 사이의 계약»이라, 둘이 같은 자리를 두고 다투는 것처럼 보이기 때문이다. 그런데 축이 다르다 — 커맨드와 사건은 §2 에서 본 대로 «실패를 누가 지나»로 갈린 둘이고, OHS 는 그 축 위의 값이 아니라 «화살표의 반대편 끝»이다.

“Define a protocol that gives access to your subsystem as a set of SERVICES. Open the protocol so that all who need to integrate with you can use it.”
… “it only pays off when the subsystem’s resources can be described as a cohesive set of SERVICES and when there are a significant number of integrations.” Eric Evans · Domain-Driven Design (2003) · Open Host Service

원문이 OHS 를 «서비스의 집합» 이라고 정의한다는 데 주목할 것 — 부르면 하는 것이지 알리는 것이 아니다. 「여러 곳이 나를 통합해 올 때 번역기를 매번 새로 만들지 말라」가 이 패턴이 푸는 문제고, 그 문제 자체가 «남이 나를 부르는» 상황이다.

하나 — OHS 는 커맨드의 «반대편 끝»이다

이름이 둘인 것은 «누구의 어휘로 부르느냐»가 다르기 때문이다. 나가는 쪽은 내 어휘로 선언하고(port/<capability>/ — 내가 필요한 능력의 이름), 받는 쪽은 자기 어휘로 공개한다(open_host_service/<service>/ — 그 BC 가 제공하는 서비스의 이름). 그 둘 사이를 번역하는 자리가 adapter/anticorruption_layer/<bc>/ 다. 세 칸이 한 화살표를 셋으로 나눠 가진 것이지, 셋이 서로 다른 채널인 것이 아니다.

사건은 다르다. 반대편 끝이 정해져 있지 않은 것이 사건의 정의다(§2 — 받는 이가 여럿이고 누군지 모른다). 그래서 사건을 BC 밖으로 내보내기로 하면 반대편 끝을 새로 지어야 하고, 그 목록이 위 그림의 여덟 칸이다. 우리 트리는 그 칸을 열지 않았고, 그래서 도메인 이벤트는 BC 안에서만 산다.

둘 — 그럼 사건을 쓰면 OHS 가 필요 없어지나

흔한 오해 하나를 먼저 걷어내자. 「사건은 발행자가 구독자를 모르니 결합이 없고, OHS 는 소비자가 제공자를 아니까 결합이 있다」 — 이건 틀렸다. 둘 다 «말하는 쪽»은 «듣는 쪽»을 모른다. OHS 도 누가 부를지 모른 채 프로토콜만 공개하고(그게 Evans 가 «Open» 이라 부른 것이다), 발행자도 누가 구독할지 모른다. 무지의 구조는 같다.

진짜로 다른 것은 둘이다 — 누가 시작하나, 그리고 «언제»의 값인가.

여기서 결론이 나온다. 사건은 OHS 를 대체하지 못한다. 「지금 이 아이의 상태는?」이라는 물음에 사건의 흐름은 답할 수 없다 — 사건은 과거 조각의 나열이고, 거기서 «현재»를 만들려면 받는 쪽이 복제본을 쌓아 두어야 한다. 그 복제본을 만드는 것이 앞 그림 여덟 칸의 절반이 하는 일이고, 짓는 순간 「원본과 복제본이 다르면 어느 쪽이 맞나」라는 새 문제가 따라온다.

반대 방향은 된다. 사건으로 할 만한 일을 OHS + 커맨드로 하는 것 — 우리 트리가 지금 하고 있는 것이 그것이다. 값은 언제나 «지금» 것이고 복제본이 없으니 어긋날 자리도 없다. 대신 보내는 쪽이 실패를 진다 — 그 값을 치르는 것이 §5 에서 본 자리다.

★ 그래서 물음은 «OHS 냐 사건이냐»가 아니다
  • OHS · 커맨드 — 부른 자리에서 답이 온다. 실패가 그 흐름 안에 남는다.
  • 사건 — 답이 없다. 흐름이 거기서 끊기고 뒤는 다른 트랜잭션이 된다.
  • 그러므로 판정은 「이 일을 «끊을» 이유가 있나」 다 — 끊을 이유가 없으면 사건도 없다.

한국어로도 영어로도 사건처럼 들리는데, 실제로는 커맨드인 경우가 대부분이기 때문이다. 이 낱말이 보이면 반드시 §6 의 물음을 대 볼 것.

이 자는 우리 트리의 다른 자리에도 그대로 댈 수 있다 — open_host_service/…/contract/request/ 안의 타입이 명령형인지 과거형인지, port/<capability>/ 의 메서드가 「해라」인지 「알려줘」인지. 어휘가 판정을 흐리는 자리가 더 있을 수 있다.

ⓒ 권고

이름만 먼저 정리

의미가 커맨드이므로 이름도 커맨드로. 전달 보장은 T19 에서 따로 정한다. 지금 확실히 정할 수 있는 것만 정하는 길.

메시지의 의도 ① · Command Message

커맨드 — 「해라」

받는 이가 하나로 정해져 있고, 못 하면 보낸 쪽이 알아야 하는 메시지. 이름은 명령형 동사로 짓고, 실패는 선언한다.

1 한 문장으로

「내가 못 하는 일을 남에게 시킨다. 그리고 결과는 내가 받는다.」

축커맨드는 이렇다왜 그런가
받는 이하나 — 내가 지정한다「누구에게 시키는지」를 내가 알아야 시킨 것이다
답온다 — 성공 · 거절 · 실패내가 결과를 봐야 하니 돌아오는 길이 있다
실패를 아는 자보낸 나이게 커맨드를 커맨드이게 하는 한 가지다
거절될 수 있다상대가 선행조건을 못 맞추면 「못 한다」고 답한다
이름RevokeDevice · revoke_for_child()명령형 동사구 — 「해라」로 읽혀야 한다
“Use a Command Message to reliably invoke a procedure in another application.” Hohpe & Woolf · Enterprise Integration Patterns · Command Message

원문의 낱말이 invoke a procedure — 「절차를 부른다」다. 알리는 것도, 자료를 건네는 것도 아니고 남의 절차를 내가 부르는 것이라는 뜻이다. 그래서 부른 자리에 답이 돌아오고, 답이 돌아오니 실패도 돌아온다.

2 커맨드 하나를 만들면 «무엇이 생기나»

개념만 보면 「메서드 하나 부르는 것」인데, 트리에서는 네 조각이 생긴다. 이 그림이 이 페이지의 핵심이다.

네 조각이 각각 무엇인가

① 선언 — port/<capability>/<capability>.py

「무엇을 시키나」. 포트는 인터페이스가 아니라 «대화»다 — 대화 하나의 어휘 셋(무엇을 말하나 · 무엇을 듣나 · 무엇이 잘못되나)이 한 폴더에 산다. 이름은 내 어휘다. 상대가 그 일을 뭐라고 부르든 상관없다.

② 실패 — port/<capability>/exception.py

필수다. 이게 없으면 어댑터가 번역할 대상이 없어 django·SDK 예외가 그대로 안으로 샌다. 규칙 하나 더 — 도메인 예외를 상속하지 않는다. 포트 실패는 업무 규칙 위반이 아니다.

③ 자료 — port/<capability>/<payload>.py

원시값이나 값 객체로 안 될 때만 생긴다. DTO 도 값 객체도 아니다 — 유스케이스의 입출력이 아니고 도메인 개념도 아니다. «이 대화가 주고받는 자료»일 뿐이다. 자세한 건 자료 페이지에서.

④ 구현 — driven_layer/adapter/…/<capability>.py

adapter/ 아래 모든 .py 는 어떤 선언의 구현이고, 파일 이름이 그 선언과 같다. 1:1 이 폴더 규칙 하나로 걸린다. 기술 이름은 클래스에 붙인다 — DjangoOrderRepository 처럼.

구현 자리는 셋으로 갈린다 — 판정은 「밖에 «상대»가 있나」

상대가 누구인가구현이 사는 자리덧붙는 규칙
우리 저장소 안의 다른 BCadapter/anticorruption_layer/<bc>/ 타 BC 를 import 하는 건 여기뿐 · 상대 창구의 기저 예외를 반드시 잡는다
저장소 밖 시스템adapter/external_system/<system>/ 계약이 저장소 밖에 있다 · 타임아웃·재시도는 여기만
상대가 아예 없다
기술만 필요		adapter/<capability>/ 시계·해시·PDF 같은 것 · 계약에 업무 어휘가 0이면 나중에 framework/ 로 올라갈 «자격»

3 한 커맨드가 도는 모양 — 그리고 돌아오는 것 셋

# application_layer/port/device_revocation/device_revocation.py   ← ① 선언
class DeviceRevocation(Protocol):
    def revoke_for_child(self, child_id: ChildId) -> None: ...     # 명령형 — 「해라」

# application_layer/port/device_revocation/exception.py            ← ② 실패 (필수)
class DeviceRevocationFailed(Exception): ...                       # 도메인 예외를 상속하지 않는다

# driven_layer/adapter/anticorruption_layer/pairing/device_revocation.py   ← ④ 구현
class PairingDeviceRevocation:                    # 파일 이름 = 선언 이름 (1:1)
    def revoke_for_child(self, child_id):
        try:
            pairing_service.revoke(child_id.value)          # 상대의 open_host_service
        except PairingPublishedError as exc:                # 기저 예외 — 반드시 잡는다
            raise DeviceRevocationFailed(...) from exc      # 내 어휘로 번역해 올린다

4 지켜야 하는 것 넷

  1. 이름은 명령형 동사구 — 파일 이름만 보고 「무엇을 시키는가」가 읽혀야 한다. 과거형이면 다음 사람이 실패를 무시하는 코드를 쓴다(가름 페이지 §3).
  2. 실패는 선언한다 — exception.py 는 선택이 아니다. 번역 대상이 없으면 전역 제약(바깥 예외는 안으로 못 들어온다)이 여기서 깨진다.
  3. 받는 이는 하나 — 둘 이상이면 커맨드가 둘이거나, 애초에 사건이다. 「여럿에게 한 번에」가 필요해지는 순간이 사건을 검토할 때다.
  4. 어댑터는 «판정»하지 않는다 — 번역만 한다. 상대의 답을 보고 업무 결론을 내리면 업무 규칙이 드리븐 층으로 샌 것이다.

5 흔한 실수 셋

① 사건 이름을 단 커맨드

…_notification / notify() 처럼 이름은 사건인데 의미가 커맨드인 경우. Fowler 가 수동공격적 커맨드라 부른 것이고, 「반드시 해야 하는데 아무도 실패를 안 잡는」 자리가 생긴다.

② 커밋 뒤에 보내는 커맨드

after_commit 뒤에 부르면 실패해도 롤백을 못 한다. 커맨드라면 결과를 봐야 하는데, 볼 시점에 되돌릴 수단이 없다 — 커맨드로도 사건으로도 부족한 상태가 된다.

③ 어댑터가 상대 예외를 안 잡는다

구체 타입 두어 개만 잡고 기저 예외를 안 잡으면, 상대가 예외를 하나 늘리는 순간 이쪽 코드가 한 글자도 안 바뀌었는데 낡는다. 새 예외가 그대로 통과해 안으로 들어간다.

6 언제 커맨드가 «아닌가»

「이 호출이 실패하면 «누가» 알아야 하나?」에 발신자가 아니면 커맨드가 아니다
  • 수신자만 알면 된다 → 사건. 받는 이가 여럿이고 누군지 모른다면 더더욱.
  • 아무도 안 봐도 된다 → 지워도 되는 코드다. 「그래도 있으면 좋으니까」는 근거가 아니다.
  • 시키는 게 아니라 «건네는» 것이다 → 자료. 무엇을 할지는 받는 쪽이 정한다.
메시지의 의도 ② · Document Message

자료 — 「이것이다」

무엇을 하라고 시키지 않고 데이터만 넘긴다. 무엇을 할지는 받는 쪽이 정한다. 셋 중 압도적으로 많은데 가장 눈에 안 띄는 물건이다.

1 한 문장으로

「이게 그 값이다. 뭘 할지는 네가 정해라.」

축자료는 이렇다왜 그런가
받는 이상관없다지시가 아니니 «누구에게»가 의미를 안 바꾼다
답없거나, 자료 자체가 답이다질문에 대한 답으로 오는 것도 자료다
실패를 아는 자«실패»라는 개념이 약하다자료는 성공하지도 실패하지도 않는다
이름DeviceList · ChildSummary명사 — 「이것이다」로 읽힌다
그래서잘못된 자리에 있어도 돈다규칙으로 자리를 정해 줘야 하는 유일한 갈래다
“Whereas a Command Message tells the receiver to invoke certain behavior, a Document Message just passes data and lets the receiver decide what, if anything, to do with the data.” Hohpe & Woolf · Enterprise Integration Patterns · Document Message

2 왜 제일 많은데 제일 안 보이나

커맨드는 못 하면 터진다. 사건은 못 받으면 밀린다. 둘 다 잘못 두면 곧 표가 난다. 그런데 자료는 잘못된 자리에 있어도 그냥 돈다 — 실패 계약이 없기 때문이다.

그래서 자료만이 「어디에 두나」를 규칙으로 정해야 하는 갈래다. 아래 두 그림이 그 규칙 전부다 — 하나는 같은 값이 경계마다 옷을 갈아입는 모양, 다른 하나는 어느 옷이 어느 폴더에 사는가.

3 같은 값이 경계마다 «옷을 갈아입는다»

4 자료가 사는 다섯 자리 — 판정은 「누구의 경계를 넘나」

# driving_layer/api/child/schema/schema_in.py            ← HTTP 의 것
class EvictChildIn(Schema):
    child_id: str                       # 바깥이 보내는 «날것»의 모양

# application_layer/child/evict_child/dto/dto_in.py      ← 유스케이스의 것
@dataclass(frozen=True)
class EvictChildIn:
    child_id: ChildId                   # 검사하지 않는다 — 이미 검사된 값이 온다

# driving_layer/open_host_service/child_lifecycle/contract/response/eviction_result.py
@dataclass(frozen=True)
class EvictionResult:                   # 「거절도 답이다」
    accepted: bool
    rejected_reason: RejectionCode | None    # 사유는 «코드»로 — 자유 문자열이면 위반

5 지켜야 하는 것 다섯

  1. DTO 는 검사하지 않는다 — 검사 자리는 둘뿐이다. 막을 게 «사용자»면 입구와 애그리거트가, 막을 게 «개발자»면 테스트와 타입 체커가 한다. DTO 에까지 검사를 넣으면 진짜 판정이 어디인지 아무도 모르게 된다.
  2. 엔티티도 DB 로우도 경계 밖으로 넘기지 않는다. 넘기는 순간 바깥이 도메인 내부 구조에 묶인다.
  3. contract/ 는 표준 라이브러리와 «같은 BC 의 다른 계약» 말고는 import 하지 않는다. 계약이 또 다른 BC 의 계약을 담으면, 부르는 쪽이 폴더 하나 없이 제3의 BC 에 묶인다.
  4. response/ 는 «성공의 모양»이 아니라 «이 창구가 낼 수 있는 답 전부»다 — 거절도 답이다. 못 해 준 사유는 코드로 담는다. 자유 문자열이면 부르는 쪽이 문자열을 파싱하게 된다.
  5. <payload> 는 DTO 가 아니다. 유스케이스의 입출력이 아니고 도메인 개념도 아니다. 「이 대화가 주고받는 자료」일 뿐이다.

6 흔한 실수 셋

① schema 를 dto 로 그대로 쓴다

「같은 필드니까」가 이유다. 그런데 그 순간 HTTP 가 바뀌면 유스케이스가 바뀐다. 두 옷이 같아 보이는 건 지금뿐이고, 갈라놓는 값은 바뀔 때 나온다.

② DTO 에 검증을 넣는다

검사 자리가 셋(입구·DTO·도메인)이 되고, 어느 것이 진짜 판정인지 아무도 모르게 된다. 셋이 어긋나기 시작하면 버그는 「어디서 안 막혔나」를 찾는 일이 된다.

③ 사유를 자유 문자열로 담는다

reason: str = "정원 초과" 같은 것. 부르는 쪽이 문자열을 파싱하게 되고, 메시지 한 글자만 고쳐도 남의 코드가 깨진다. 코드로 담고 문구는 따로.

메시지의 의도 ③ · Event Message

사건 — 「일어났다」

이미 벌어진 사실. 거절할 수 없고, 받는 이가 몇인지 모르며, 못 받은 쪽이 스스로 감당한다. 셋 중 가장 매력적으로 들리고, 가장 비싸다.

1 한 문장으로 — 그리고 계보 하나

「이런 일이 있었다. 필요한 사람은 알아서 써라.」

축사건은 이렇다왜 그런가
받는 이여럿 — 누군지 모른다알면 그건 지목이고, 지목이면 커맨드다
답없다돌아오는 길이 없는 것이 사건의 정의다
실패를 아는 자각 수신자 — 발신자는 모른다발신자는 «보냈다»로 자기 일이 끝난다
거절불가이미 일어난 사실은 거절할 대상이 아니다
이름DeviceRevoked · ChildEvicted과거형 사실 — 「일어났다」로 읽힌다
★ 계보 — 도메인 이벤트는 DDD 의 «원래» 물건이 아니다
  • 2004 블루북의 빌딩블록 여덟에 이벤트가 없다.
  • Evans 가 2009 QCon London 에서 처음 얹었고 — “They are overemphasized. But let’s add another one anyway!”
  • 2015 『DDD Reference』 에 Domain Events * 로 등재되고 각주가 붙는다 — * New term introduced since the 2004 book.
  • Evans 가 감사의 말에서 출처를 밝힌다 — Greg Young · Udi Dahan(CQRS · Event Sourcing). 즉 EDA 에서 DDD 로 «역수입»된 개념이다.

그래서 「DDD 냐 이벤트 드리븐이냐」는 잘못된 이분법이다. 도메인 이벤트는 이미 이벤트 드리븐 쪽에서 건너온 물건이다.

덧붙여 — 원전은 «누가 읽는가»를 묻지 않는다. 『DDD Reference』 전문에 subscribe·consume·listen 이 각각 0회 나온다. Fowler(2005)도 반응 없는 이벤트를 정의에 포함시킨다 — “some may be worth recording but don’t provoke a reaction.” 「읽는 코드가 없으면 이벤트가 아니다」는 우리가 «좁힌» 규칙이고, 원전이 준 규칙이 아니다. 좁힌 이유는 §3 에 적는다.

2 사건은 둘로 갈린다 — 이 구분을 안 하면 대화가 안 된다

「이벤트를 쓰자」는 말이 두 개의 아주 다른 물건을 가리킨다. 둘의 값도 비용도 완전히 다르다.

축도메인 이벤트통합 이벤트
사는 곳한 BC 안BC 밖 · 프로세스 밖
어휘도메인 어휘 그대로공개 계약 — 번역해서 내보낸다
트랜잭션같은 커밋 또는 커밋 직후별도 커밋 — 끊긴다
깨지면내가 고친다남이 깨진다
필요한 장치없음 — 클래스 하나여덟 칸 (§4)
우리 트리domain_layer/<aggregate>/event/없다 — 열지 않았다 (§5)

앞으로 §3 은 도메인 이벤트, §4~§5 는 통합 이벤트 이야기다.

3 도메인 이벤트가 사는 칸 — 그리고 판정

# domain_layer/child/event/child_evicted.py
@dataclass(frozen=True)
class ChildEvicted:                  # 과거형 사실 — 거절할 수 없다
    child_id: ChildId
    occurred_at: datetime

# domain_layer/child/child.py
class Child:
    def evict(self) -> None:
        self._assert_can_evict()                        # 불변식 검사
        self._record(ChildEvicted(self.id, now()))      # 기록«만» 한다 — 아무도 부르지 않는다

규칙 넷

  1. 과거형 사실 하나 = 파일 하나.
  2. 같은 BC 안에서만 읽는다 — 밖에서 읽으면 그건 통합 이벤트이고, 우리 트리엔 그 칸이 없다.
  3. 애그리거트는 «기록»만 한다 — 아무도 부르지 않는다. 부르는 순간 도메인이 실행 순서를 알게 된다.
  4. 발행 장치(레지스트리 · dispatch)는 여기 안 산다 — 밖으로 나갈 일이면 애초에 포트다.

그래서 왜 「읽는 코드가 없으면 이벤트가 아니다」로 «좁혔나»

§1 에 적었듯 이건 원전이 준 규칙이 아니다. 좁힌 이유는 소비자 없는 이벤트가 실제로 맞는 운명 셋 때문이다 — 참조 구현들을 훑으면 셋 중 하나로 간다.

ⓐ 테스트 오라클이 된다

프로덕션 코드는 아무도 안 읽고 테스트만 읽는다. 의도한 설계면 괜찮지만, 그러면 테스트를 위해 도메인에 칸을 만든 것임을 문서에 적어야 한다.

ⓑ 이벤트 스토어가 읽는다

이벤트 소싱을 하면 «저장 형식» 자체가 소비자다. 우리는 이벤트 소싱을 하지 않는다 — 그러니 이 길은 닫혀 있다.

ⓒ 로거에 물려 썩는다

가장 흔한 결말. 헥사고날 참조 구현인 dddsample-core 에도 // TODO why is this unused? 가 그대로 남아 있다.

4 통합 이벤트를 켜면 «무엇이 생기나» — 여덟 칸

여기가 값을 치르는 자리다. 「이벤트를 발행한다」는 한 줄이 여덟 칸을 부른다 — 참조 구현 셋을 전수로 훑으면 셋 다 여덟을 전부 갖고 있다.

★ 그리고 이벤트가 결합을 없애 주지도 않는다

참조 구현 하나를 프로젝트 참조 전수로 재 보면 모듈 수준 순환이 3쌍 나온다 — 비동기 100% 강제인데도 그렇다. 저자 본인이 인정한다 — “coupling … exists only on the structure of Integration Events.”
Spring Modulith 는 아예 «이벤트를 듣는 것»도 의존으로 세고 순환 검사에서 예외를 주지 않는다. 결합을 없애는 것은 이벤트가 아니라 «의존 역전»이고, 이벤트는 그걸 실행하는 한 가지 수단일 뿐이다.

5 그런데 우리 트리엔 «통합 이벤트 계약»이 앉을 자리가 없다

여덟 중 ⑤ 하나가 특히 문제다. 양쪽이 같은 타입을 봐야 하는데, 그 타입을 어디 두든 우리 트리의 규칙 하나를 깬다.

6 사건의 실패 양식 — 「보냈다」가 「닿았다」가 아니다

사건에는 돌아오는 길이 없다. 그래서 실패가 조용하다. Django 위에서 흔히 쓰는 on_commit 방식의 실패 양식이 알려져 있다.

① 커밋과 발행 «사이»에서 죽는다

커밋은 됐는데 발행 전에 프로세스가 죽으면 그 사건은 영구히 사라진다. 아무도 모른다 — 원본 쪽은 성공으로 기록돼 있다.

② 브로커가 내려간 구간이 통째로 빈다

①보다 훨씬 흔한 양식. 브로커가 5분 죽어 있으면 그 5분치가 전부 없어진다. outbox 가 푸는 게 정확히 이 둘이다.

③ 순서가 보장되지 않는다

받는 쪽이 「생성 → 수정」을 뒤집어 받을 수 있다. 그래서 at-least-once + 멱등성 이 짝으로 따라온다.

Django 자체의 단서도 셋이다 — 콜백 하나가 터지면 뒤의 콜백이 안 돈다 · 트랜잭션 밖에서 부르면 즉시 실행된다(테스트와 프로덕션 동작이 갈린다) · TestCase 안에서는 한 번도 안 돈다(테스트가 초록인데 프로덕션에서 안 도는 전형적 함정).

“Where possible you should opt for directly calling the handling code.”
“If the sender and receiver of your custom signal are both within your project, you’re better off using an explicit function call.” Django 공식 문서 · topics/signals

7 그래서 언제 쓰나 — 자료가 주는 자

★ 이벤트는 «전파의 수단»이 아니라 «트랜잭션을 나누는 수단»이다
  • BC 안에서는 애그리거트 사이의 트랜잭션을 나눈다 — 「한 트랜잭션 = 한 애그리거트」를 지키려고.
  • BC 밖에서는 커밋 자체를 나눈다 — 「여기까지는 됐고, 다음은 나중에」.
  • 나눌 이유가 없으면 이벤트도 없다. 이게 하나뿐인 판정 기준이다.

하한은 명확하다

소비자가 하나뿐이면 이벤트 인프라를 걷어내는 편이 낫다. “If all the collaborating parties operate upon the same database, it’s better to make the flow of the domain logic explicit.”

상한은 «어떤» 1차 자료에도 없다

「소비자 몇이면 이벤트가 이긴다」는 숫자를 준 자료가 없다. 이건 확인 못 한 것이지, 없다는 뜻이 아니다 — 그러니 숫자로 정당화하지 않는다.

진짜 축은 «순환»이다

“Which of the two modules could exist without the other?” A 가 B 없이 못 살면 그냥 부르면 되고, 서로가 서로를 불러야 하면 그 짝에서만 방향을 뒤집는 수단으로 이벤트를 쓴다.

정리하면 — 사건은 「멀리 알리고 싶어서」 고르는 것이 아니라 「여기서 끊어야 해서」 고르는 것이다. 그리고 끊는 순간 §4 의 여덟 칸과 §6 의 실패 양식이 함께 온다. 그 값을 치를 이유가 있는지가 유일한 물음이다.

출처 — 전부 1차 자료로 원문 대조함
  1. Gregor Hohpe & Bobby Woolf, Enterprise Integration Patterns — Command / Document / Event Message
  2. Eric Evans, Domain-Driven Design ch.14 — OPEN HOST SERVICE: “Define a protocol that gives access to your subsystem as a set of SERVICES.”
  3. Eric Evans, Domain-Driven Design Reference (2015) — Domain Events * 및 각주 “* New term introduced since the 2004 book.” · 감사의 말(Greg Young · Udi Dahan)
  4. Martin Fowler, What do you mean by “Event-Driven”? (2017) — passive-aggressive command
  5. Martin Fowler, Event Sourcing / Domain Event (2005) — “some may be worth recording but don’t provoke a reaction”
  6. Jimmy Bogard, A better domain events pattern (2014) — “if I cared enough… couple myself directly”
  7. Percival & Gregory, Architecture Patterns with Python ch.10 — Event: fail independently / Command: fail noisily
  8. Vladimir Khorikov — 소비자가 하나면 이벤트 인프라를 걷어내라 · “operate upon the same database … make the flow explicit”
  9. Oliver Drotbohm (Spring Modulith) — “Which of the two modules could exist without the other?” · 이벤트 리스너도 의존으로 집계
  10. Kamil Grzybek, modular-monolith-with-ddd ADR 0014 — “We allow direct calls in the future, but this should be an exception, not a rule.”
  11. Open edX ADR-15 / openedx-events — on_commit 실패 양식 셋 · outbox 는 Provisional
  12. Django 공식 문서 topics/signals · topics/db/transactions — 직접 호출 권고 · on_commit 콜백은 트랜잭션의 일부가 아니다
  13. dddsample-core — 헥사고날 참조 구현인데 이벤트를 만들지 않고 이름 붙인 포트 메서드를 직접 부른다
