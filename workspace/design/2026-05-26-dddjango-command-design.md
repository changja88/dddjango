# dddjango Coordinator command 설계 메모

작성일: 2026-05-26
상태: 독립 리뷰 2건 반영 완료 (계획서 준비)
상위 근거: `workspace/design/2026-05-26-dddjango-plugin-pipeline-design.md` (이하 "설계 문서")

## 0. 이 메모의 범위

`commands/dddjango.md`(Coordinator)가 **어떤 형태로 무엇을 글로 규정하는지**를 고정한다. 파이프라인 자체(§3)·게이트·진행 가시성(§6)·이중 루프(§10)·수정 모드(§7)는 설계 문서가 이미 확정했다. 이 메모는 그것들을 command 파일에 *옮길 때* 새로 결정해야 하는 부분(설계 문서 §14 이월 항목 · 슬라이스 목록 소유권 · 설계 문서 §4/§9가 빌드 단계로 미룬 감사 빈도의 구체화)만 다룬다.

command 파일은 곧 Coordinator의 **런타임 시스템 프롬프트**다. 따라서 이 메모는 "Coordinator에게 시키는 말"의 골격이며, 메타코멘트(왜 이렇게 썼는지 같은 설명)는 command 파일 본문에 넣지 않는다(런타임 프롬프트 오염 방지 — 에이전트 빌드에서 확립한 원칙과 동일).

## 1. 확정 결정 (사용자 승인됨)

1. **하이브리드 형태**: 사용자에게 보이고 일관성이 중요한 부분(게이트 배너·트래커 라인·subagent 디스패치 시퀀스)은 **고정 템플릿**으로 못박고, 판단이 필요한 부분(lens 선택·슬라이스 크기·감사 빈도)은 **원칙+기준**으로 위임한다. Opus가 운전한다는 전제.
2. **Lens 선택**: Coordinator가 G0에서 스코프로 활성 lens를 **추론해 제안**하고, G0 게이트에서 사용자가 확정한다.
3. **슬라이스·감사**: Coordinator가 acceptance-tester의 인수 테스트(1테스트≈1슬라이스)에서 **슬라이스 목록을 도출**해 coder·discipline-reviewer에 전달한다. 감사 빈도는 기준 규칙으로 고정(§4).

## 2. 고정 템플릿

### 2.1 단계 트래커 라인 (설계 문서 §6.1)

매 단계 전환·게이트마다 한 줄 출력. `✓`=완료, `▶`=진행중, `·`=대기.

```
dddjango  [✓ 스코프] → [▶ 설계] → [· 구현] → [· 마무리]
```

활성 lens가 정해지면 설계 단계 표기에 덧붙인다: `[▶ 설계 (ddd·api)]`.

### 2.2 게이트 배너 (설계 문서 §6.3)

3부 고정 구조 — *방금 끝낸 것 / 승인 대기 / 다음에 할 것* + 승인 요청. 게이트별 채움:

```
─────────────────────────────────────
dddjango · {G0 스코프 | G1 설계 | G2 구현} 승인
방금 끝낸 것 : {요약}
승인 대기   : {산출물 경로 또는 요약}
다음에 할 것 : {다음 단계 요약}
승인하시겠어요? (수정 요청 가능 — 반려 시 이 단계를 피드백과 함께 재실행)
─────────────────────────────────────
```

- **G0**: 방금=스코프 정리 / 대기=스코프 메모(무엇·경계·제약) + **제안 lens** / 다음=설계.
- **G1**: 방금=통합 설계 명세(+리뷰 N건 반영·중재) / 대기=명세 경로 / 다음=인수 테스트→슬라이스 도출→구현.
- **G2**: 방금=구현+단위 테스트(+감수 리포트 반영) / 대기=코드·테스트·검증 결과 / 다음=마무리·검증 보고.

미해결 트레이드오프가 있으면 배너에 옵션으로 제시해 사용자가 G에서 고르게 한다(§9 리뷰어 충돌).

### 2.3 subagent 디스패치 시퀀스 (설계 문서 §5·§8)

command 본문에 단계별로 고정한다. `[ ]`=병렬, `→`=순차.

```
Phase 0 (Coordinator ↔ 사용자):
   요구·스코프 정리 → 활성 lens 추론·제안 → G0

Phase 1 (설계):
   design-architect (초안 작성)
   → [ design-review-ddd | design-review-api | design-review-db ]  (활성 lens만, 병렬)
   → (선택) 명세가 복잡하면 discipline-reviewer 경량 점검 (testability·단순성, 설계 문서 §4)
   → design-architect (리뷰 노트 반영·충돌 중재 → 최종 명세)
   → G1

Phase 2 (구현, 이중 루프):
   acceptance-tester (실패 인수 테스트 작성, Bash로 Red 확인)
   → Coordinator: 인수 테스트에서 슬라이스 목록 도출
   → 슬라이스 루프: coder (단위 TDD로 슬라이스 통과, 인수 Green 실행 확인)
        └ 슬라이스 ≥3일 때만 슬라이스마다 discipline-reviewer 경량 감사 → coder 반영
   → discipline-reviewer 감사 (기본: G2 직전 1회 / 슬라이스 ≥3이면 마지막 홀리스틱 1회)
   → coder (지적 반영) → (필요시 재감사 수렴)
   → G2

Phase 3 (Coordinator):
   검증 보고 (실행한 검증만; 미실행은 사유 명시, §9)
```

### 2.4 네이티브 task 리스트 (설계 문서 §14 이월 → 확정)

4단계를 최상위 task로, 핵심 하위단계를 하위 task로 둔다. Phase 2는 도출된 슬라이스를 하위 task로 펼쳐 안쪽 Red/Green을 노출한다(§6).

```
- 요구·스코프 (G0)
- 설계: architect 초안 → 리뷰(활성 lens) → 반영·중재 → G1
- 구현: 인수 테스트 → [슬라이스 1] 단위 TDD → [슬라이스 2] … → 규율 감사 → G2
- 마무리·검증 보고
```

슬라이스 수는 acceptance-tester 산출 후에 확정되므로, 구현 task의 슬라이스 하위 항목은 그 시점에 추가한다.

## 3. 위임 원칙 (하이브리드의 "판단" 쪽)

### 3.1 Lens 추론 휴리스틱 (G0)

스코프 메모에서 추론해 제안하고 G0에서 확정한다. 기본 규칙:

- **ddd**: 항상 활성(도메인 규칙·상태 전이가 없는 기능은 이 파이프라인 대상이 아님).
- **api**: 외부에서 관찰되는 계약(엔드포인트·요청/응답·상태코드)이 새로 생기거나 바뀌면 활성.
- **db**: 스키마·인덱스·제약·트랜잭션·마이그레이션 변화가 있으면 활성.

순수 도메인/내부 로직 변경이면 api·db를 빼고 제안한다. 모호하면 활성 쪽으로 제안하고 G0에서 사용자가 줄이게 한다.

### 3.2 슬라이스 도출 + 감사 빈도

- **도출**: acceptance-tester가 쓴 인수 테스트 각각(+덮는 행위 명시)이 슬라이스 1개(1테스트≈1행위, 설계 문서 §10). Coordinator가 이 목록을 만들어 coder("이번에 통과시킬 슬라이스")와 discipline-reviewer("감사 범위")에 전달한다.
- **감사 빈도(기본 기준)**:
  - 슬라이스 **≤2**: G2 직전 discipline-reviewer 1회.
  - 슬라이스 **≥3**: 슬라이스마다 경량 감사 + 마지막에 홀리스틱 감사 1회.
  - 이 임계값은 설계 문서 §4의 적응형 감사 빈도(§9가 빌드 단계로 미룬 값)를 사용자 확정에 따라 구체화한 **기본 기준**이다 — Coordinator의 운전 판단으로 조정 가능. discipline-reviewer 파일의 "감사 빈도(적응형)" 선언과 일치.
- 감사 리포트는 게이트 직전에 coder가 반영하고, 필요하면 재감사로 수렴한 뒤 G2 배너에 *수정된 결과 + 감수 리포트*를 함께 제시(설계 문서 §3 하단).

### 3.3 수정 모드 (설계 문서 §7)

```
G0 (영향 범위만 빠르게 확인)
→ 영향받는 lens만 재실행 → G1' (바뀐 설계 부분만 승인)
→ 영향받는 인수/단위 테스트만 → G2
```

설계 변경이 없는 순수 구현 수정이면 G1'을 생략하고 G0 다음 바로 테스트→G2로 간다. 진입 판단: 기존 코드·명세가 있고 변경이 국소적이면 수정 모드로, 아니면 풀 파이프라인.

## 4. 인터페이스 계약 (Coordinator ↔ subagent)

각 에이전트의 실제 입·출력 선언(`dddjango/agents/*.md`)과 일치해야 한다.

| subagent | Coordinator가 주는 입력 | 받는 산출 |
|---|---|---|
| `design-architect` (초안) | 승인된 스코프 메모 · 활성 lens 목록 · **명세 저장 경로** | 통합 설계 명세 1건(지정 경로에 Write) |
| `design-review-{ddd,api,db}` | architect의 설계 명세(초안)만 (타 리뷰 노트·코드 제외 — 편향 방지) | lens별 리뷰 노트(blocker→important→nit) |
| `design-architect` (반영) | 모은 리뷰 노트 | 리뷰 반영·충돌 중재된 최종 명세 |
| `acceptance-tester` | 승인된 설계 명세(G1) · 테스트 위치·관례 | 실패하는 인수 테스트(Bash로 Red 실행 확인) + 덮은 행위 목록 (블랙박스) |
| `coder` | 설계 명세 · 인수 테스트 · **이번 슬라이스** · 코드 위치·관례 | 슬라이스 통과 구현 코드 + 단위 테스트 (인수 테스트 Green 실행 확인) |
| `discipline-reviewer` | 코드+단위/인수 테스트 · (가능하면) 명세·슬라이스 목록 · **감사 범위·시점** | 감수 리포트 |

핵심 데이터 흐름(설계 문서 §8): 스코프 메모(G0) → 설계 명세(G1, architect 작성·리뷰어 보강) → 인수 테스트 + 코드·단위 테스트(G2) → 검증 보고(Phase 3). 설계 명세가 인수 테스트와 코드의 단일 근거.

산출물 경로 규약(제안): 스코프 메모·설계 명세는 작업 디렉터리 하위 일관 위치에 둔다(예: 사용자 프로젝트 내 `.dddjango/<기능>/`). 정확한 경로 규약은 계획서에서 확정.

## 5. 엣지 처리 (command이 인코딩, 설계 문서 §9)

- **게이트 거부**: 해당 단계를 피드백과 함께 재실행. 다음 단계로 넘어가지 않음.
- **리뷰어 충돌**: architect가 중재해 명세에 결정 명시. 미해결이면 G1 배너에 트레이드오프 옵션 제시.
- **인수 테스트가 계속 Red**: coder가 멈추고 보고 → 명세 가정 오류면 설계로 반송, 구현 난점이면 사용자에게.
- **잘못된 인수 테스트**: coder가 임의 수정 금지 → 보고 → acceptance-tester/설계로 반송.
- **검증 미실행**: 실행한 것처럼 보고 금지 — 미실행 사유 명시(코퍼스 acceptance 규칙).

## 6. command 파일 섹션 구성안

`commands/dddjango.md` 본문(런타임 프롬프트)의 골격:

1. **역할 선언** — 너는 dddjango Coordinator다(오케스트레이션·게이트·통합·보고; 코드·설계를 직접 쓰지 않고 subagent에 위임).
2. **진행 가시성** — 트래커 라인(2.1) · 네이티브 task 리스트(2.4) · 게이트 배너(2.2)를 매 전환·게이트에 출력.
3. **Phase 0~3 절차** — 각 단계의 디스패치 시퀀스(2.3) + 게이트.
4. **위임 판단 기준** — lens 추론(3.1) · 슬라이스/감사(3.2).
5. **수정 모드** — 3.3.
6. **엣지 처리** — §5.
7. **경계** — 코드·명세·테스트를 직접 쓰지 않는다; 단일 근거는 설계 명세; 한 주제 한 소유자.

> frontmatter는 command 스키마(name/description 등)를 따른다. 정확한 필드는 계획서에서 실제 command 파일 예시로 확인.
