# 수정 회귀 근본원인 분석 — 계획 (진단까지)

> 자기완결 계획서. 정본 신뢰원 = `workspace/DEVLOG.md`. 이 문서는 *진단을 어떻게 수행할지*의 계획이지 진단 결과가 아니다.
> 작성 2026-06-06 · 브랜치 `eval/codex-determinism-n2` · 방식 합의 = 하이브리드(C).

## 0. 동기 (왜 이 분석을 하나)

dddjango 표준 하드닝에서 **같은 부류 결함을 여러 번 고쳐도 회귀하거나 부분 미완으로 남는** 패턴이 반복됐다. 증거:
- **P1a**: DR-20→21→22→23→24 **다섯 번** 손대고도 릴리스 보류.
- **catalog 컨테이너**: DR-26에서 "회귀"로 명시(고쳤다 돌아옴).
- **NJ-2**: c4live→nj2live에서 런타임 판정 **반전**.
- **ACL(DR-44)**: 라이브(DR-45)서 **부분 미완**으로 재누수.
- `§3 DO-NOT-RETRY`에 **검증된 헛다리 14건** 누적.

→ 개별 발견을 각개격파하면 같은 실패 모드를 또 밟는다. **증상(기술 빈틈)을 패치하기 전에, 왜 수정이 stick 하지 않는지(메타-프로세스 근본)를 먼저 진단**한다.

## 1. 목표와 경계 (deliverable boundary)

**종착점 = 진단 문서까지.** 처방 설계·구현은 진단을 함께 본 뒤 **별도 합의**(이 계획에 선commit 안 함).

산출 = 진단 문서 1편, 내용:
1. 실패모드 분류표(정의 + 에피소드 증거 앵커)
2. 에피소드 × 모드 매트릭스
3. 근본 클러스터 순위(어느 근본이 가장 체계적인가)
4. 열린 발견(ACL 인프라누수·깨진 JSON·위장 테스트 2건)의 근본 클러스터 매핑
5. 근본별 **권고 개입 *방향*** (구체 설계 아님) + 정직 신뢰도·잔여 N=1

**비-목표(이 계획 밖):** 표준/백스톱/에이전트 텍스트 수정, 평가방법 개편 구현, 열린 발견의 코드 처방. (진단이 이들을 *가리키되* 실행하지 않는다.)

## 2. 분석 단위

**"수정 에피소드"** = 변경을 처방한 DR 또는 발견 하나. 예: `DR-44`(ACL 전수성), `P1a`(오류 중앙화), `catalog 회귀`(DR-26), `NJ-2`(§6.3 협상). 한 에피소드는 여러 실패모드를 동시에 보일 수 있다(매트릭스로 표현).

## 4. 방식 = 하이브리드(C) — 병렬 수집 → 합성 → 적대 검증

진단 자체가 우리가 연구하는 실패모드(특히 **L5 1차 진단 오류·앵커링**)에 빠지는 것이 최대 위험 → 독립 적대 검증을 내장.

### Phase 0 — 코퍼스 동결
스코프 확정 + **에피소드 마스터 리스트** 작성(에피소드 ID·소스 앵커). 이후 단계는 이 리스트를 공유 입력으로 받는다.

### Phase 1 — 병렬 증거 수집 (서브에이전트 fan-out)
실패모드 렌즈별 서브에이전트가 동결 코퍼스를 전수, 해당 모드를 보이는 에피소드를 **증거 앵커(DR#·file:line·결과지 인용)**와 함께 구조화 추출. 씨앗 렌즈(**닫힌 집합 아님** — 새 모드 발견·"무모드" 플래그 허용; 내 분류를 confirm-only로 강요하지 않음 = 확증편향 차단):

- **L1 비결정** — P4③ run-variance: 같은 입력·같은 표준인데 치명 FAIL 레인이 런마다 갈림.
- **L2 집행 갭** — reviewer prose/문구가 라이브 파이프라인서 미발화(강등 포함).
- **L3 백스톱 맹점** — 결정적 백스톱 exit0인데 의미 변종 통과, 또는 백스톱 부재(고정밀·저recall).
- **L4 부분 미완** — 처방 스코프를 너무 좁게 앵커(형제 변종 누수).
- **L5 1차 진단 오류** — 첫 진단 철회·방향 반전·헛다리.
- **L6 회귀** — 고쳤다 돌아옴. *핵심 가설*: L6 상당수가 실은 **L1×N=1 오측정**.

각 렌즈 산출 스키마(공통): `episode_id · mode · evidence_anchor · severity · is_open(열린 발견 여부) · note`.

### Phase 2 — 합성 (조정자 직접)
렌즈 산출 병합·중복 정리 → **에피소드 × 모드 매트릭스**. 클러스터 도출(어느 모드가 공기하나·어느 근본이 상류). **핵심 가설 검정**: "안 고쳐짐/회귀"의 몇 %가 *측정 문제(L1×N=1)* vs *진짜 수정 실패*인가 — 이게 갈리면 처방 방향이 "표준 강화"냐 "평가방법 개편"이냐로 근본부터 달라진다. 열린 발견 4건을 클러스터에 매핑.

### Phase 3 — 적대 검증 (서브에이전트 fan-out)
독립 회의론자가 Phase 2 분류표를 **반증**(기본값 "반증·불확실하면 기각"):
- (a) N=1서 과대일반화한 클러스터?
- (b) 인과 주장이 post-hoc 합리화 아닌가?
- (c) 합성이 놓친 에피소드/모드?
- (d) "근본"이 증상의 재진술에 불과한가?

살아남은 클러스터 = 확정. 강등/반증된 것은 진단 문서에 *기각 사유와 함께* 보존(투명성).

### Phase 4 — 진단 문서 산출 (deliverable)
§1의 5요소를 `workspace/eval/` 또는 `workspace/design/`에 1편으로 작성. **여기서 정지.**

## 5. 정직 경계

- **N=1 도처**: 코퍼스 전체가 런타임당 1회 관측 위에 있다. 진단은 *측정 문제*와 *수정 문제*를 구분하고, 잔여 불확실을 명시한다.
- **라벨 규율**: 발견·모드를 사용자에게 지칭할 땐 **루브릭 코드(NJ-2·SD-6·FC-1 등)·DR 번호**만. 새 약칭 발명 금지(작업방식 메모리). 렌즈 코드 L1~L6은 *이 분석 내부 작업 라벨*이며 진단 문서에선 DR/루브릭 앵커로 환원해 기술한다.
- **자기보고 불신**: 메모리·요약이 아니라 1차 소스(DEVLOG 본문·결과지·코드)를 증거로 앵커.
