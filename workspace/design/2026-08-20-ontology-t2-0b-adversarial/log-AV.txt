## 발견 1 — 판정 스칼라 V 의 계수 규약이 어디에도 없고, 남은 두 후보 정의가 서로 반대 결론을 낸다

**심각도: blocker**
**분류: 설계**

**근거**

```
$ grep -rn "계수 규약" workspace/design/ workspace/eval/ab/
workspace/design/2026-08-19-ontology-t2-plan.md:40:  - 판정 스칼라 = 결정적 검사기 위반 수 단독(severity=violation — 계수 규약은 T2-0b scorer 계약).
```

전 저장소에서 **한 번** 나오고, 그 한 번이 T2-0b 로의 전방 참조다. T2-0b 실물에는 그 계약이 없다 — `2026-08-20-ontology-t2-0b-design.md:110` 은 «결정적 검사기 위반 수(**판정 스칼라**)» 한 칸이 전부이고, manifest 의 `groups.scorer.why` 는 «판정 스칼라를 만드는 전부»라고만 쓴다(파일 37개를 봉인할 뿐 **호출 방식을 봉인하지 않는다**). `Makefile` 에 채점 타깃이 없고(`grep -n "^score\|판정" Makefile` = 0건), `workspace/tools/` 49개 도구 중 위반 수를 내는 것도 없다.

그런데 실물 파이프라인은 «위반 수»를 **최소 세 가지**로 낼 수 있다(`dddjango/commands/dddjango.md:128`):
ⓐ 27종 전수 full-tree · ⓑ 검사기별 touched 계약 · ⓒ `registry_gate` 귀속 차분(N∖L, legacy 강등 후).

**왜 문제인가**

셋 중 어느 것이냐에 따라 결론이 **뒤집힌다**, 완화되지 않는다.

- **V = ⓒ(귀속)이면**: 루프가 소비하는 재료가 정확히 `introduced.json` = N∖L 이다(`regen_core.py:261`). 즉 처치가 자기 채점표를 직접 지운다. 유일한 실측(B3 데모 — `2026-08-18-ontology-adoption-log.md:97`)은 1왕복에 `7→0`. B 가 수렴하면 `V̄_B,o = 0` → 계획서 정의상 **uninformative ceiling** → 유효 발주에서 제외(`t2-plan:36`). 판정 재료가 공집합이 될 때의 처분 규칙은 사전 등록에 **없다**.
- **V = ⓐ(full-tree)이면**: 분모에 «루프가 손댈 수 없는 질량»이 들어간다 — step 6′ 자신이 legacy 잔존 즉석 수리를 금지한다(`dddjango.md:128`). 같은 B3 실측에서 범위 밖 **41건 불변** vs 범위 내 7건. 이 비율이면 C 가 처치 가능분을 전멸시키고 B 가 하나도 못 고쳐도 `rate = 7/48 = 14.58%` 로 **D9 문턱 15% 아래**다. (한 검사기 한 데모의 수치이며 실제 발주로의 외삽이 아니다 — 그러나 «분모가 처치 불가 질량에 지배되면 문턱이 구조적 천장 위에 있을 수 있다»는 메커니즘은 그 수치와 무관하게 성립한다.)

D9 의 15% 는 이 분모가 무엇인지 정하기 전에 골랐다. 봉인은 **자를 봉인했지 재는 법을 봉인하지 않았다** — 그리고 재는 법은 산출물을 본 뒤에 정해지게 된다. 그것이 L-M #4 가 막으려던 판정 교락 그 자체다.

**처분 제안**
실런 전에 `scorer` 그룹에 **계수 규약 문서 1건을 추가 저작해 봉인**한다. 최소 고정 항목: ① 27종 각각의 exact argv(프로필 플래그·scope 렌더 포함) ② full-tree/touched 슬라이스의 검사기별 확정 ③ `--anchor` 차분 적용 여부와 앵커 지정 ④ severity 필터 ⑤ 집계 단위(`violation_id` = `(rule|sentinel|contract_ref, file, symbol)` 를 쓸지, `identity()` 의 라인 제거 축을 쓸지 — `regen_core.py:46-50` 이 «두 축을 합칠지는 T2-0b 봉인 때 확정한다»고 명시적으로 이 자리에 미뤄 두었고, 봉인은 그 결정을 하지 않았다) ⑥ 유효 발주가 0건일 때의 판정. 그리고 그 규약을 실행하는 스크립트를 `harness` 그룹에 넣는다 — 사람이 손으로 세는 판정 스칼라는 arm-blind 가 아니다.

## 발견 2 — 봉인된 배정표에서 A암은 블록 1번 자리에 **한 번도** 오지 않는다 (O-4·O-5 는 4블록 전부 2번 자리 고정)

**심각도: blocker**
**분류: 설계**

**근거**

```
$ python3 -c "... manifest['allocation']['rows'] 를 run_id 순으로 블록별 정렬 ..."
BK1 ['C', 'B', 'A']   BK2 ['B', 'A', 'C']   BK3 ['C', 'A', 'B']
BK4 ['B', 'A', 'C']   BK5 ['C', 'A', 'B']   BK6 ['B', 'A', 'C']

자리별 암 분포 (라틴 방진이면 각 자리 A=B=C=2):
  자리1: A=0 B=3 C=3
  자리2: A=5 B=1 C=0
  자리3: A=1 B=2 C=3

발주×암 → 자리: O-4/A {2:2} · O-5/A {2:2}   ← 네 블록 전부 A가 2번 자리
```

사전 등록 문면은 **라틴 방진**이다 — `t2-plan:55` 「18런의 발주×반복×암×순서×레인 배정표+공개 seed를 사전 등록(**라틴 방진**·각 암을 두 레인에 균형 배정)」. 실물 생성기는 방진이 아니라 블록마다 독립 i.i.d. 셔플이다 — `manifest_seal.py:292-294` `arms = list(ARMS); rng.shuffle(arms)`. 균형 제약이 코드에 존재하지 않는다.

**왜 문제인가**

세 암은 시간축을 공유한다고 저자 스스로 P6 근거에 적었다(`manifest_seal.py:281-282`). 그런데 뽑힌 표에서 **자리는 A 여부의 완전한 예측자**다(O-4·O-5 기준). 블록 안에서 단조 드리프트가 조금이라도 있으면 — 모델 부하, 워크트리 캐시 온도, 실행자 피로, 타깃 DB 상태 — 그 드리프트가 통째로 «A vs B/C» 로 실린다. 이것이 오염시키는 것은 보조 지표가 아니라 **사전 등록된 방향 조건 `V̄_B,o ≤ V̄_A,o`** 다.

P6(«블록 안 무작위») 자체는 AU 목록에 있으나, 자인 문면은 「블록이 6개뿐이라 균형이 **완전하지 않다**」이다. 실측은 «완전하지 않다»가 아니라 **자리1 에 A 가 0회**이고, 두 발주에서는 교락이 100% 다. 자인이 실물을 과소 진술한다.

덧붙여 `manifest_seal.py:296-297` `first = next(i for i, b in enumerate(blocks) if b["order"] == "O-7")` 는 셔플 뒤 **먼저 나온 O-7 블록**을 앞으로 옮긴다. O-7 블록은 rep1·rep2 둘이므로 «BK1 = O-7 **rep1**»(설계 §3 표·§68행)은 코드의 불변식이 아니라 이 seed 의 우연이다.

**처분 제안**
배정표를 재저작한다. 6블록 × 3자리는 6개 순열 전량을 정확히 한 번씩 쓰면 각 자리에 각 암이 정확히 2회인 완전 균형이 나온다 — seed 는 **6개 순열의 블록 대응**만 무작위화하는 데 쓴다. 재저작 후 자리별 분포 `A=B=C=2` 를 manifest 에 단언으로 싣고, `--check` 가 그 균형을 검사하게 한다. 첫 블록 O-7 고정은 `repeat == 1` 까지 조건에 넣는다. 이 재저작은 실런 전이므로 설계 §9 「봉인 전 자산 변경 = `--write` 재저작 자유」에 해당한다.

## 발견 3 — C암 처치의 «정확 조인» 채널은 규칙 3개뿐이고, 후보만 실린 런이 만점 처치로 계상된다

**심각도: blocker**
**분류: 설계**

**근거**

```
$ python3 -c "json.load(open('dddjango/scripts/rulepack.json'))"
by_alias n= 3   sample: [('#3','R-0124'), ('#486','R-0118'), ('#488','R-0120')]
works n= 125 · by_checker 검사기 16
$ 검사기 총 27 · 팩 등재 16 · 팩 밖 11   (tier3 = B와 동일 재료)
   check-broker-contract / common-container / event-publish / idempotency-scope-creep /
   mechanism-ownership / missable-entrance / naming / port-adapter-pairing /
   public-surface-annotation / test-config / transient-overmapping
```

`rulepack.py:183-190` `locate()` 에서 tier 1(정확 조인)은 `by_alias` 적중일 때만 난다 = **`#3`·`#486`·`#488` 세 규칙**. 스냅숏 실측 규칙 총수는 538(`t2-plan:27`). 나머지는 tier 2(검사기 축 후보) 또는 tier 3(팩 밖 = B와 동일).

tier 2 만으로 구성된 C 런을 실제로 돌렸다:

```
$ DJR_LOOP_SELECTOR=sparql python3 dddjango/scripts/regen_core.py \
    --introduced-json tier2.json --capacity-log c3.jsonl
exit=0 · stderr 없음
<rules> = R-0106/R-0107/R-0108 전부 "join": "candidate"
capacity: {'selector':'sparql', 'uninformative': False, 'rules_n': 3,
           'tiers': {'1': 0, '2': 1, '3': 0}, 'hit_ratio': 1.0}
```

**왜 문제인가**

주입문 자신이 candidate 를 **행동 금지**로 표시한다 — `regen_core.py:134-136` 「"candidate"면 그 검사기가 집행하는 후보일 뿐 이번 위반이 아닐 수 있다 — **candidate 를 근거로 다른 코드를 고치지 않는다**」. 즉 tier 2 는 정의상 «고치지 말라고 붙여 보내는 정보»다. 그런데 처치량 0 판정(`regen_core.py:299` `uninformative = args.selector == "sparql" and not rules`)은 **rules 가 통째로 비었을 때만** 켜진다. 정확 조인 0건 + 후보 31건인 런은 `uninformative=False`·`hit_ratio=1.0` 으로 «정상 C 런»이 되어 C−B 분모에 만점으로 들어간다.

`hit_ratio` 는 `priority != 3` 을 세므로(`regen_core.py:326`) exact 와 candidate 를 한 칸에 합친다 — 이름이 재는 것과 다르다.

결과: C−B 의 기대 효과 크기가 «3/538 규칙 + 16/27 검사기의 후보 잡음»으로 구조적으로 눌려 있는데, 그 희석을 걸러낼 사전 등록 문턱이 없다. 그리고 차이가 안 나왔을 때 **«그래프가 소용없다»와 «투여량이 0에 가까웠다»를 가를 장치가 판정 규칙 안에 없다**(발견 각도 5). tiers 는 로그에 남지만 어떤 사전 등록 규칙도 tiers 를 읽지 않는다.

**처분 제안**
사전 등록에 **투여량 하한**을 추가한다: 런의 `tiers["1"] == 0`(정확 조인 0건)이면 그 런을 `uninformative` 와 같은 등급으로 분리 보고하고 C−B 유효쌍에서 뺀다 — `regen_core.py:299` 를 `not rules or not any(r["join"]=="exact" for r in rules)` 로 바꾸고 stderr 문면도 분기한다. `hit_ratio` 는 `exact_ratio`/`candidate_ratio` 로 쪼갠다. 아울러 A/B 리포트에 «alias 대장 3건·팩 밖 검사기 11/27» 을 **한계 문구로 내장**한다(현재 리포트 한계 문구 목록 `t2-plan:107` 에 이 항목이 없다).

## 발견 4 — `DJR_LOOP_SELECTOR` 가 안 잡히면 C암 런이 조용히 B 처치를 받고 exit 0 으로 끝난다

`workspace/eval/violations/` 는 그 산출물을 나중에 **복사해 오는 목적지**다 — `collect_violations.py:2` 「`.dddjango/violations/*.jsonl` → `workspace/eval/violations/raw/`」, 그리고 같은 파일 7행 「**원본 무삭제** — 재수집 안전」.

**왜 문제인가**

**처분 제안**

$ python3 - (101파일 전수를 git cat-file -e 9334553:<path> 로 조회)

## 발견 12 — 판정이 최대 2발주의 중앙값에 얹혀 있고, «저분모» 플래그에는 처분 규칙이 없다

**심각도: major**
**분류: 설계**

**근거**

`t2-plan:36` 「판정 재료 = **밀착·혼합 층**의 유효 발주」 → O-7·O-4 **둘뿐**(O-5 는 비밀착 = 비열화 전용, `t2-plan:39`).
`t2-plan:38` 「유효 발주의 rate **중앙값** ≥ 15%(D9)면 운영 문턱 충족. … `V̄_B,o < 3`이면 «저분모» 플래그(**1→0=100% 잡음 자인**)」

**왜 문제인가**

n=2 발주의 중앙값은 산술평균이고, 한쪽이 uninformative(`V̄_B=0`)로 빠지면 **단일 값**이 된다. 그리고 저분모는 «플래그»일 뿐 배제도 가중도 아니다 — 즉 `V̄_B,O-7 = 1`, `V̄_C,O-7 = 0`, O-4 가 uninformative 인 조합이면 rate 중앙값 = 100% 로 **문턱을 통과**하고, 그 통과의 실체는 «한 발주에서 위반 하나가 사라졌다»다. 계획서가 그 잡음을 자인해 놓고 그것을 걸러낼 규칙은 등록하지 않았다.

거울상도 있다: 유효 발주 0건일 때의 판정이 정의돼 있지 않다(발견 1 참조). 사전 등록 규칙이 **입력 없음**과 **n=1 극단값** 양쪽에서 무정의다.

**처분 제안**
T2 게이트 전에 다음 세 줄을 사전 등록에 추가한다: ① 「유효 발주 < 2 이면 D9 문턱을 «충족»으로 읽지 않는다 — 판정은 자동 «조정»」 ② 「`V̄_B,o < 3` 인 발주는 rate 중앙값 계산에서 **제외**하고 별도 보고」(현행 «플래그만»에서 승격) ③ 「유효 발주 0건 = 판정 불가 — 원인 분류(수렴·팩 미적중·표본)를 리포트에 등재하고 계속/조정을 게이트로 재상정」. 이 셋은 산출물을 보기 전에 등록해야 의미가 있다.

## 발견 13 — C 프롬프트에 봉인 문면에 없는 지시 3문장과 `join` 필드가 실린다

**심각도: minor**
**분류: 드리프트**

**근거**

봉인·계획의 C암 기술은 일관되게 «번호·명칭»이다:
- manifest `arms.C.label` = `루프+그래프(SPARQL 선별 · <rules> 번호·명칭 동봉)`
- 설계 §3 표 = `<rules>`(번호·명칭) 추가
- `t2-plan:41` estimand = 「selector 축 + 선별 결과의 **번호·명칭 제시**」

실물 C stdout(발견 3 재현)은 그 밖에 `_RULES_NOTE` 3문장을 싣는다 — `regen_core.py:133-137`, 그중 「candidate 를 근거로 다른 코드를 고치지 않는다」는 **행동 지시**다. 그리고 각 항목에 `join` 필드가 붙는다(`regen_core.py:143` `RULE_FIELDS = ("rule","label","join")`) — 코드 주석 자신이 「`join` 은 **규범 내용이 아니라 조인 방식**이다」(139~140행)라고 «번호·명칭» 밖임을 인정한다.

```
$ grep -rn "candidate 를 근거로\|조인 방식" 설계·manifest·계획·발주  →  0건 (미공개)
```

계약 상수도 둘로 갈려 있다: `regen_core.py:143` = 3필드 / `rulepack.py:27` = 2필드, 양쪽 다 「이 집합이 **계약**이다」라고 적혀 있다.

**왜 문제인가**

`_RULES_NOTE` 자체는 필요하다(AS-04·AS-09 실측으로 도입). 문제는 **estimand 명명이 실물보다 좁다**는 것이다. C−B 를 「번호·명칭 효과」로 리포트하면, 실제로는 「번호·명칭 + 후보 억제 지시 + 조인 메타」의 효과를 그 이름으로 부르게 된다. 개정 8 은 「규범 본문은 양 암 미동봉」까지만 정했고 부가 지시문은 다루지 않았다.

**처분 제안**
`t2-plan:41` estimand 문면과 manifest `arms.C.label`·설계 §3 표를 실물에 맞춘다 — 「선별 결과의 번호·명칭 + 조인 표지(`join`) + 후보 오적용 억제 문장」. 그리고 `_RULES_NOTE` 원문(byte)과 `RULE_FIELDS` 값을 manifest 에 `c_arm_material` 로 **명시 등재**한다(현재 B암은 `b_arm_material` 로 본문 해시까지 봉인돼 있는데 C암은 대응물이 없다). `rulepack.RULE_FIELDS` 는 「팩이 내는 필드」로 주석을 정정해 «계약» 중복 선언을 없앤다.

## 발견 14 — 설치 cache 를 사전식 최댓값으로 고르고, 옛 2.11.0 트리가 아직 디스크에 남아 있다

**심각도: minor**
**분류: 봉인 공백**

**근거**

`manifest_seal.py:286-292`
```
hits = sorted(home.glob(pattern));  scripts = hits[-1]
```
패턴의 두 번째 `*` 가 버전 디렉터리다. 문자열 정렬이므로 `sorted(['2.11.0','2.13.0','2.2.0','2.9.0'])[-1] == '2.9.0'`.

현재 디스크:
```
$ ls -d ~/.claude/plugins/cache/changja88-dddjango/dddjango/*/
.../2.11.0/    .../2.13.0/          ← 옛 트리가 지워지지 않았다
```

런타임이 실제로 무엇을 로드하는지의 정본은 따로 있다:
```
$ ~/.claude/plugins/installed_plugins.json
"installPath": ".../dddjango/2.13.0", "version": "2.13.0",
"gitCommitSha": "c1c10dd02f8b59ab7fc68c5eae376012bc631e52"
```
manifest 는 이 정본을 **기록하지 않는다** — glob 으로 유도한 `cache-claude_path` 만 싣는다. 참고로 `sealed_commit`(9334553) ≠ 설치본 `gitCommitSha`(c1c10dd) 이며, manifest 는 그 차이를 적지 않는다.

**왜 문제인가**

지금은 `hits[-1]` 이 2.13.0 을 맞힌다 — 우연이다. 2.9.x·2.2.x 계열이 하나라도 캐시에 생기면 봉인 도구는 **런타임이 로드하지 않는 트리**를 해시하고 `--check` 가 green 을 낸다. 계획서 자신이 「plugin 은 설치 캐시에서 로드」를 hard blocker 로 격상해 놓고(`t2-plan:99`), 정작 «어느 캐시인가»의 정본을 안 읽는다. 남아 있는 2.11.0 은 `findings.py` 가 없는 판(같은 줄 실측)이라 오식별 시 파이프라인이 통째로 다르다.

부수적으로 `script_trees` 는 cache 측을 `scripts/` 만 덮는다 — `pipeline` 그룹이 봉인하는 절차 정본 2건(`commands/dddjango.md`·`skills/dddjango/SKILL.md`)의 **cache 사본은 대조되지 않는다**(오늘 실측으로는 source 와 sha256 일치이나, 도구가 그것을 검사하지는 않는다).

**처분 제안**
`install_trees()` 를 `installed_plugins.json` 의 `installPath`·`version`·`gitCommitSha` 를 읽는 방식으로 바꾸고 그 셋을 manifest 에 등재한다. glob 은 폴백으로만 쓰되 hits 가 2개 이상이면 `PENDING` 대신 **명시 실패**로 낸다. cache 측 해시 범위를 `scripts/` 에서 `pipeline` 그룹이 봉인한 파일 전체로 넓힌다. 실런 전 옛 캐시(2.11.0) 제거를 절차로 못 박는다.

- **설치본 4트리 동일성 주장은 오늘 실측으로 참**이다 — `commands/dddjango.md` 와 codex `SKILL.md` 의 source↔cache sha256 이 일치했고, `mirror_parity` 37파일 동일도 재현됐다.
- **안 본 것**: 부속서 `PENDING` 4항·`--self-test` 변이 커버리지·`--allocation` 출력과 rows 의 일치·`verify-runready` 차단 범위·O-5 인바운드 3 중화의 충분성·인수 기준 P8/P9 의 느슨함 — 전부 레인 AU 의 지정 과제라 손대지 않았다. 27종 검사기의 내부 정확성, 루브릭 34차원, 오탐 심의 절차 자체도 보지 않았다. 타깃 저장소는 접근 범위 밖이라 어떤 주장도 하지 않았다.
