# dddjango 플러그인 파이프라인 설계

작성일: 2026-05-26
상태: 확정 (사용자 리뷰 대기)

## 1. 목적

`/dddjango`는 개발자의 기존 Django 프로젝트 안에서 **하나의 기능을 DDD 방식으로 끝까지 빌드하는 오케스트레이터**다. 요구 정리 → 설계 → 구현(테스트 포함)까지를 단계별 게이트로 끌고 가며, 코드를 직접 생산한다.

지식은 10개 소스 코퍼스(`workspace/reference/<skill>/reference/final.md`)에서 재생성한 스킬로 공급한다. 런타임은 Claude 전용(Codex는 추후, 비범위).

## 2. 핵심 원칙

플러그인 전체가 **하나의 패턴**으로 통일된다:

> **응집된 작성(1명) + 독립적 전문 리뷰(여러 명)**

- **작성**은 한 주체가 응집해서 한다 — 흩어진 결정을 한 머릿속에서 통합.
- **검수**는 독립적인 전문가가 한다 — 작성자의 블라인드스팟·편향을 잡음.

이 원칙이 설계 단계와 구현 단계에 동일하게 적용된다.

| 단계 | 작성(응집) | 독립 검수 |
|---|---|---|
| 설계 | architect 1명이 통합 설계 명세 | ddd/api/db 리뷰어가 각자 독립 리뷰 |
| 구현 | 코더 1명이 단위 TDD | 인수테스트(독립 작성) + discipline 감수자 |

부수 원칙:
- **단계별 체크포인트 게이트** — 각 단계 산출물을 사용자가 승인해야 다음으로.
- **discipline = 규율(norm)** — cleancode·tdd는 고유 산출물이 없는 횡단 규율. 단계를 소유하지 않고, 코딩 역할 지침에 *주입*되고 감수자가 *독립 점검*한다.
- **한 주제 한 소유자** — 스킬 경계는 소유권으로 유지.

## 3. 파이프라인

```
사용자:  /dddjango "주문 취소 기능 추가"
          │
   ┌──────▼───────────────────────────────────────────────────┐
   │  COORDINATOR  (메인 스레드 = /dddjango 커맨드)               │
   │  단계 오케스트레이션 · 사용자 게이트 · subagent 호출 · 통합·보고 │
   └──────┬───────────────────────────────────────────────────┘
          │
 [Phase 0] 요구·스코프 정리   (Coordinator ↔ 사용자)
          │   무엇을 / 경계 / 제약 확인
          ▼ ───────────────────────── G0: 스코프 승인
 [Phase 1] 설계
          │   architect (architecture-ddd/api/db 스킬) ── 통합 설계 명세 초안
          │        ├─ ddd 리뷰어 ┐
          │        ├─ api 리뷰어 ├─ 각자 독립 리뷰·보강 노트 (병렬, 필요한 lens만)
          │        └─ db  리뷰어 ┘
          │   architect가 리뷰 반영·충돌 중재 → 최종 설계 명세
          ▼ ───────────────────────── G1: 설계 명세 승인 (코드 전 통째 승인)
 [Phase 2] 구현   (이중 루프 TDD)
          │   ① 인수테스트 agent → 명세에서 "실패하는 인수 테스트" 작성 (바깥 Red)
          │                        + 덮은 행위 명시 (독립·블랙박스)
          │   ② 메인 코더 agent  → 인수 통과 목표로 내부 단위 TDD
          │                        (Red→Green→Refactor 반복, 단위 테스트 자작)
          │   ③ 인수 테스트 Green = 구현 완료 조건 (자동 통과 아님)
          ▼ ───────────────────────── G2: 구현 승인 (사용자)
 [Phase 3] 마무리·검증 보고   (Coordinator)
          │   실행한 검증만 보고(테스트·마이그레이션·check), 미실행은 사유 명시
          ▼
         완료

 ═══════ discipline 감수자 (cleancode · tdd) — 체크포인트 단발 감사 ═══════
   주 무대 Phase 2(게이트 직전) / Phase 1은 testability·단순성 경량 점검
   TDD 준수 · 클린코드 · 테스트 행위중심 · 인수↔단위 중복/누락 점검
```

## 4. 구성요소

### Coordinator (`/dddjango` 커맨드, 메인 스레드)
- 단계 오케스트레이션, subagent 호출, 산출물 통합, 사용자 게이트.
- 기능 성격에 따라 **필요한 설계 lens만** 활성화(순수 도메인 변경엔 db/api 생략 가능).
- 진행 가시성 표시(§6)의 주체.

### 설계 architect (subagent)
- architecture-ddd/api/db 스킬을 로드해 통합 설계 명세를 작성.
- 리뷰 노트를 반영하고 리뷰어 간 충돌을 중재.

### 설계 리뷰어 ddd/api/db (subagent ×3, 읽기 전용)
- 각자 자기 관심사로 명세를 독립 리뷰: 애그리거트 경계·도메인 규칙(ddd), 계약 완전성·상태코드·멱등성(api), 인덱스·제약·트랜잭션·마이그레이션 안전(db).
- 보강 노트만 산출(명세를 직접 쓰지 않음). 병렬·필요한 lens만 호출.

### 인수테스트 agent (subagent)
- 승인된 설계 명세에서 외부 관찰 가능한 행위·계약을 **실패하는 인수 테스트**로 작성(바깥 루프 Red). 구현을 보지 않음 → 블랙박스·독립.
- 덮은 행위를 명시(중복/누락 점검 근거).

### 메인 코더 agent (subagent)
- 인수 테스트 통과를 목표로 내부 단위 TDD(Red→Green→Refactor). 단위 테스트는 코더가 직접 작성.
- implementation-* 로 코드 작성.

### discipline 감수자 (subagent, 읽기 전용)
- subagent는 단발 실행이라 "실시간 감시"가 아니라 **체크포인트에서 단발 감사**한다. 실시간 규율은 주입(§2·§5)이 담당.
- **주 무대는 Phase 2(구현)** — 코드·테스트의 TDD 준수, 클린코드, 테스트 행위중심, 인수↔단위 중복/누락 점검. Phase 1(설계)은 코드가 없어 testability·단순성 경량 점검만.
- **감사 결과 반영 시점 = 게이트 직전**: 감수자 감사 → 작성자(코더)가 지적 반영 → (필요시 재감사 수렴) → 게이트에 *감수·수정된 결과 + 감수 리포트*를 함께 제시. 즉 게이트 직전의 품질 관문.
- **감사 빈도 = 적응형**: 기본은 G2 직전 1회. 기능이 여러 슬라이스로 커지면 Coordinator가 슬라이스마다 경량 감사로 올리고 + 마지막에 홀리스틱 점검 1회. (슬라이스 정의는 §10)
- 고유 코드 산출물 없음 — 감수 리포트만.

### 스킬 10개 (지식)
- 각 agent가 필요에 따라 로드. final.md에서 재생성.

## 5. 역할 × 스킬 매핑

| 역할 (subagent) | 로드하는 스킬 | 산출 |
|---|---|---|
| Coordinator (`/dddjango`) | (오케스트레이션 워크플로) | 게이트·통합·보고 |
| 설계 architect | architecture-ddd + architecture-api + architecture-db | 통합 설계 명세 |
| 설계 리뷰어 ddd | architecture-ddd | 도메인 리뷰 노트 |
| 설계 리뷰어 api | architecture-api | 계약 리뷰 노트 |
| 설계 리뷰어 db | architecture-db | 데이터 리뷰 노트 |
| 인수테스트 | implementation-test + architecture-api·ddd + discipline-tdd | 실패 인수 테스트 |
| 메인 코더 | implementation-django/django-ninja/django-web/python + implementation-test + discipline-tdd·cleancode | 코드 + 단위 테스트 |
| discipline 감수자 | discipline-cleancode + discipline-tdd | 감수 리포트 |

discipline 2개는 단계 소유 subagent가 아니다 — 코딩 역할 지침에 주입 + 감수자(subagent)로 독립 점검. (주입 = 역할 프롬프트가 해당 규율 스킬을 로드하고 따르도록 명시하는 것; discipline 고유 산출물은 없음.)

## 6. 진행 가시성 (사용자 피드백)

사용자가 "지금 어느 단계인지"를 항상 확실히 알도록 Coordinator가 세 가지로 표시한다.

1. **단계 트래커 라인** — 매 전환·게이트마다 출력:
   ```
   dddjango  [✓ 스코프] → [▶ 설계] → [· 구현] → [· 마무리]
   ```
   (`✓`=완료, `▶`=진행중, `·`=대기)

2. **네이티브 task 리스트** — Coordinator가 단계+핵심 하위단계를 task로 만들어 상태 갱신(하니스가 렌더). 영속적 진행 표시.

3. **게이트 배너** — 각 게이트에서: *방금 끝낸 것 / 승인 대기 산출물 / 다음에 할 것*을 명확히 제시하고 승인을 요청.

구현 단계(이중 루프)에서는 안쪽 진행도 노출한다 — 어느 인수 테스트를 만족시키는 중인지, Red/Green 상태.

## 7. 수정 모드 (부분 수정)

전체 파이프라인을 다시 돌지 않고 국소 수정. 단 설계가 바뀌면 그 변경도 승인 게이트를 거친다:
```
G0(영향 범위만 빠르게 확인) → 영향받는 설계 lens 재실행 → G1'(바뀐 설계 부분만 승인)
   → 영향받는 인수/단위 테스트만 → G2(구현 승인)
```
"API 응답만 바꿔" 같은 변경에서 도메인·DB를 건드리지 않는다. 설계 변경이 없는 순수 구현 수정이면 G1'은 생략하고 G0 다음 바로 테스트→G2로 간다.

## 8. 데이터 흐름 (산출물)

```
스코프 메모 (G0)
   └→ 설계 명세 (architect 작성, 리뷰어 보강) (G1)
        └→ 인수 테스트 (인수테스트 agent)
        └→ 코드 + 단위 테스트 (코더) (G2)
   ── 감수 리포트 (감수자, 전 구간)
   └→ 검증 보고 (Coordinator, Phase 3)
```
설계 명세는 인수 테스트와 코드의 단일 근거(source of truth)다.

## 9. 오류·엣지 처리

아래는 확정 결정에서 파생한 운영 규칙(제안)이다. 구체 수치·정책은 빌드 계획에서 확정한다.

- **게이트 거부**: 사용자가 산출물을 반려하면 해당 단계를 피드백과 함께 재실행. 다음 단계로 넘어가지 않음.
- **리뷰어 충돌**(api↔db 등): architect가 중재해 명세에 결정을 명시. 미해결이면 G1에서 사용자에게 트레이드오프 제시.
- **인수 테스트가 계속 Red**: 코더가 정해진 시도 횟수 후에도 통과 못 하면 멈추고, 명세 가정이 틀렸는지(→설계로 반송) 구현 난점인지 보고.
- **잘못된 인수 테스트 발견**: 코더가 명세와 인수 테스트의 불일치를 발견하면 임의로 고치지 않고 보고 → 인수테스트 agent/설계로 반송.
- **검증 미실행**: 테스트·마이그레이션·check를 실행하지 않았으면 실행한 것처럼 보고하지 않고 미실행 사유를 명시(코퍼스 acceptance 규칙 준수).

## 10. 테스트 전략 (이중 루프 TDD)

- **슬라이스(slice)**: 외부에서 관찰되는 완결된 행위 하나(대개 인수 테스트 1개에 대응). 예) "유효 주문 생성→201", "재고 부족→409", "배송 후 취소→거부". 코더는 한 슬라이스를 통과시킬 만큼의 구현(모델·서비스·엔드포인트)을 단위 TDD로 채운다. **기능의 크기 = 슬라이스 수** → §4 적응형 감사 빈도의 기준.
- **바깥 루프(인수)**: 설계 명세 → 외부 관찰 가능 행위/계약을 검증. 독립 agent가 구현 전에 작성. 안정된 계약이라 리팩터 중에도 불변.
- **안쪽 루프(단위)**: 코더가 Red→Green→Refactor로 내부 협력·엣지를 검증.
- **경계 기준**: "바깥에서 관찰되는 행위·계약"=인수, "내부 구현 디테일"=단위.
- **독립성**: 인수 테스트의 독립 작성 + 감수자의 행위중심·과도mock·중복/누락 점검으로 확보.

## 12. 빌드 범위

1. **스킬 재생성** — 10개 `final.md` → `SKILL.md`(+필요 시 references 분리). 변환 정책은 빌드 계획 단계에서 구체화.
2. **커맨드** — `commands/dddjango.md`(Coordinator).
3. **subagent** — 위 7개 agent 정의.
4. **매니페스트** — `.claude-plugin/plugin.json`.
5. **AGENTS.md 재작성** — 현재 삭제된 plan/validator/Codex를 참조하는 스테일 상태. Claude 전용·신규 파이프라인 기준으로 재작성.

## 13. 비범위 / 추후

- **Codex 런타임** — 추후. 지금은 Claude 전용.
