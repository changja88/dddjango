# dddjango 속도 개선 — 에이전트 작업용 참고 자료

- 작성일: 2026-09-06
- 사용자용 문서: [속도 개선 진행 현황](2026-09-06-design-spec-delivery-targets.md). 사용자는 그 문서만 읽어도 진행상황과 결과를 알 수 있어야 한다.
- 용도: 에이전트가 참고할 근거, 후보, 검증 조건을 보존한다. §1–8은 2번 문제의 상세 메모이며, §9는 3번 문제의 기존 진단 요약이다.
- 상태: **기존 5종에 이어, 최신 요청으로 승인된 단일 추가 실험 ‘원문 전량 읽기’ 6회 실행·검증·기록 완료. 제품 반영·배포와 다른 후속 실험은 범위 밖.**
- 목적: 현재 만족스러운 설계·코드 품질을 유지하면서, 필요한 정보를 읽고 찾아 전달하는 과정의 불필요한 비용과 누락을 줄인다.
- 현재 결과: 기존 선정 실험 5종은 완료했고, 정상 모델 응답 18개·원 채점 17/18·별도 채점기 보정 후 18/18 통과다(§14). 수동 선별은 후속 후보에서 제외했다. 추가 전량 읽기 6회에서는 **읽기 단계 중앙값 21.70% 감소 / 실패 포함 실제 총시간 중앙값 23.89% 증가**를 관측했다. 전량 전달과 사후 내용 19개 검사는 모두 통과했지만 출력 형식 실패 5회로 사전 성공 단축률은 산출 불가다(§15). 전체 속도 개선책으로 채택하지 않는다. §13은 최초 배치의 차단 이력, §1–10은 계획 수립 전 메모로 보존한다. 플러그인·코퍼스·진행 중인 fortune/account 작업은 변경하지 않았다.

## 1. 범위

앞선 진단의 **2번 쟁점인 대형 설계 명세의 읽기·정보 전달 비용**만 다룬다. 그중 실제 읽기 실패와 승인 항목 전달 누락은 관찰됐고, 정보 구조를 어떻게 고칠지는 아직 검증 전이다.

다음은 2번 문제의 개선 검토에서 제외한다.

- 사용량 한도 및 한도 해제 대기.
- 3번 쟁점인 설계·규범·검사기 판단 불일치. `#456` 오탐, `#493` 예보 처분 오류 등은 별도 문제이며 진행판에서는 별도 항목으로 추적한다.
- 모델·추론 강도 하향, 독립 리뷰·TDD·테스트·품질 게이트 축소.
- 사용자 승인 또는 발주서가 명시한 단계별 게이트의 생략.
- dddjango-web 적용, Serena/graphify 도입·활성화, 실행 환경의 도구 설치 문제 수정.
- 발주 가이드 개정. 내부 정보 전달 비용을 사용자에게 더 복잡한 발주서 작성 의무로 넘기지 않는다.

주요 관찰 대상은 Claude의 fortune 실행이다. account는 대조 관찰 자료이지 A/B 대조군이 아니다. 두 실행은 모델·작업 범위·명세 규모 등이 달라 총 소요 시간을 직접 비교해 개선 효과를 계산할 수 없다. Codex에서 같은 문제가 같은 크기로 발생한다고도 아직 판정하지 않는다.

## 2. 확인된 근거와 해석 한계

### E1. 부분 읽기에서도 명세가 도구 한도를 넘었다

- fortune의 S3 G1 승인 명세 `6200984c:.dddjango/20260904-2109-fortune-house/design-spec.md`는 **929,704바이트·2,304줄**, 가장 긴 한 줄은 **8,565자**다.
- 기존 진단의 마감 시점인 **2026-09-06 02:50 KST**까지, fortune 메인·서브에이전트 로그 전체에서 `exceeds maximum allowed tokens` 오류 **121건**, 파일 크기 한도 오류 **1건**을 확인했다. 이는 실행 전체의 오류 수이며 전부 같은 명세에서 발생했다는 뜻은 아니다.
- 구체 사례: S2-2 규율 감사 에이전트 `a00bba06b10f4da03`의 로그 31·47·51행에 각각 70,589·129,176·48,893토큰을 읽으려다 25,000토큰 한도를 넘은 결과가 있다.

**확인 가능한 결론:** 줄 수를 제한한 부분 읽기만으로는 실패를 막지 못하는 문서가 존재한다. 원문을 손실 없이 읽을 수 있는 단위와 경로가 수정 검토 대상이다.

**아직 말할 수 없는 것:** 명세가 크다는 이유만으로 내용이 불필요하다고 할 수 없다. 읽기 호출 수에는 필요한 부분 읽기·개정 후 재확인이 포함된다. 실패 횟수를 시간으로 환산하거나, 모든 재독을 낭비로 분류하지 않는다.

### E2. 승인된 요구가 작업 배정에서 빠졌다

- fortune S2 G1′에서 승인된 `NoticeSpeechComposer`의 생산자 가드와 테스트 케이스 2개가 구현되지 않은 상태를 최종 홀리스틱 감사가 발견했다.
- 요구는 `{subject}`가 있는 템플릿에 `subject=None` 또는 공백이 오면 `InvalidSpeechSituation`을 던지고, `{subject}`가 없는 상황에서는 `None`을 허용하는 것이었다.
- 감사는 당시 명세 §3.6·§10 입장 행·§12.2 개정을 근거로 들었다. Coordinator도 G1′ 항목을 `s2-followups.md`의 후속 목록에 옮기지 않아 S2-4 브리프에서 빠졌다고 인정했다.
- 근거: fortune 메인 로그 4047·4069행, `s2-impl-audit-holistic.md`의 발견 1 및 감사 처분 이행 표.

**확인 가능한 결론:** 명세에 승인된 결정이 존재하는 것과 해당 작업에 빠짐없이 연결되는 것은 별개다. 승인 결정→배정→집행의 연결이 수정 검토 대상이다.

**아직 말할 수 없는 것:** 누락이 큰 파일이나 특정 검색 기술의 부재 때문에 발생했다고 인과를 확정하지 않는다. 파일 분할이나 SPARQL만으로 이 누락이 사라진다는 증거도 없다. 이를 발견한 감사는 품질을 지킨 장치이며 축소 대상이 아니다.

### E3. 공통 제약·개정 관계를 찾는 비용은 사례별 재구성이 필요하다

여러 슬라이스에 적용되는 계약, 예외, 테스트 의무, 이후 개정까지 함께 찾아야 한다는 요구는 있다. 그러나 **어떤 관계의 부재가 어떤 반복·누락을 일으켰는지에 대한 사례별 대응표는 아직 작성하지 않았다.** 아래 T2·T3은 이 확인을 거쳐야 수정 필요성과 범위를 확정할 수 있다.

## 3. 수정 대상 후보

| ID | 검토 대상 | 해결하려는 문제 | 현재 근거 수준 |
|---|---|---|---|
| T1 | 명세의 물리적 읽기 단위와 접근 경로 | 부분 읽기조차 한도를 넘어 재시도 | 읽기 실패 확인, 최적 방법 미확정 |
| T2 | 현행 결정·개정의 탐색 구조 | 필요한 결정과 현재 유효한 내용을 찾는 비용 | 사례별 비용·원인 분리 필요 |
| T3 | 슬라이스와 공통 제약·예외·테스트의 연결 | 일부만 찾아 읽을 때 관련 의무가 빠질 위험 | 연결 단위·누락 원인 검증 필요 |
| T4 | 승인 변경의 작업 배정·집행 연결 | 명세에는 있지만 브리프·후속 작업에서 누락 | 실제 누락 확인, 예방 방법 미확정 |

### T1. 명세의 물리적 읽기 단위와 접근 경로

- **살펴볼 지점:** architect가 만드는 명세의 긴 줄·표·절 구성, 각 소비 역할이 원문을 읽는 경로와 실패 후 재시도 방식.
- **최소 대안 후보:** 원문의 내용·의미·순서를 유지한 읽기 친화적 형식, 정확한 위치 안내, 도구 출력 한도를 고려한 분할 읽기. 물리적 파일 분리는 필수 결론이 아니다.
- **보존 조건:** 원문 잘림·중복 누락·표 해석 변화가 없어야 한다. 전체 확인이 필요한 역할은 끝까지 확인할 수 있어야 하며, 실제 역할에 허용된 도구로 동작해야 한다.
- **판정:** 읽기 실패 감소와 함께 탐색·수신 비용을 측정한다. 실패만 줄고 총 비용이 그대로면 접근 안정성 개선으로만 평가한다.

### T2. 현행 결정·개정의 탐색 구조

- **살펴볼 지점:** 결정 본문과 개정 이력의 배치, 원문 위치의 안정성, 어떤 내용이 현행인지 확인하는 방법.
- **최소 대안 후보:** 정확한 절 탐색, 안정적인 결정 ID, 원문 참조와 개정·대체 관계. ID를 도입할지는 실제 혼동·탐색 사례로 판단한다.
- **보존 조건:** 요약문이나 작업 브리프를 별도의 설계 정본으로 만들지 않는다. 과거 승인 당시 내용과 현재 승인 내용을 구별하고, 보조 색인이 있다면 원문 개정과의 불일치를 알 수 있어야 한다.
- **판정:** 당시 유효한 결정과 관련 개정을 정확히 찾는지, 이미 대체된 내용을 현행으로 쓰지 않는지 확인한다. 색인 작성·갱신 비용도 포함한다.

### T3. 슬라이스와 공통 제약·예외·테스트의 연결

- **살펴볼 지점:** 구현 대상과 그에 적용되는 공통 계약·불변식·예외·패키지 구조·테스트 입장 행·개정 사이의 연결.
- **최소 대안 후보:** 원문 내 명시적 참조, 결정 ID 간 관계, 같은 관계를 대상으로 한 구조화 조회. 역할별 문서 분할이나 관련 절만 읽기부터 강제하지 않는다.
- **보존 조건:** 역할별로 읽는 양을 줄이더라도 검토 책임과 필요한 전체 맥락을 줄이지 않는다. 관계가 기록되지 않았다는 사실을 ‘관련 없음’으로 처리하지 않는다. 연결의 완전성을 확인할 수 없으면 원문 확인 범위를 넓히거나 누락·불확실성을 보고할 수 있어야 한다.
- **판정:** 실제 작업 시점에 필요했던 정보 집합과 조회 결과를 대조한다. 관계 누락·잘못된 연결·개정 누락이 있을 때 조용히 불완전한 입력으로 진행하지 않는지도 확인한다.

### T4. 승인 변경의 작업 배정·집행 연결

- **살펴볼 지점:** G1/G1′ 승인 항목이 해당 슬라이스와 역할 입력에 연결되는 과정, 개정 뒤 후속 작업 갱신, 실행 결과와 승인 항목의 대조.
- **최소 대안 후보:** 승인 항목을 원문 참조로 배정에 연결하고 기존 입장 표·슬라이스 기록과 대조하는 방식. 별도 수기 장부를 추가하는 것을 기본 해법으로 삼지 않는다.
- **보존 조건:** Coordinator가 설계 의미를 다시 결정하지 않는다. 설계는 architect, 코드는 coder, 인수 테스트는 acceptance-tester가 소유하는 기존 경계를 유지한다. 테스트의 `reuse/retain/reject` 등을 새 테스트 작성으로 바꾸지 않는다.
- **판정:** E2의 생산자 가드가 당시 입력만으로 올바른 작업에 전달되는지 확인한다. 배정됐다는 표시만으로 구현 완료라고 판정하지 않고, 기존 감사와 테스트를 유지한다. 새 대조 절차의 비용도 계산한다.

## 4. 저장소에서 살펴볼 위치

| T1–T3 명세 작성 형식 | [design-architect](../../dddjango/agents/design-architect.md) | [agent-design-architect.ttl](../../ontology/rules/agent-design-architect.ttl), Codex `dddjango-design-architect/SKILL.md` |

| T1·T3·T4 구현·테스트 입력 | [coder](../../dddjango/agents/coder.md), [acceptance-tester](../../dddjango/agents/acceptance-tester.md) | `ontology/rules/agent-coder.ttl`, `agent-acceptance-tester.ttl` 및 각 Codex 역할 미러 |
| T1·T3 독립 검토에 필요한 입력 | `dddjango/agents/design-review-{ddd,api,db}.md`, [discipline-reviewer](../../dddjango/agents/discipline-reviewer.md) | 대응하는 `ontology/rules/agent-*.ttl` 및 각 Codex 역할 미러 |
| 형식 변경의 호환성 | [design_pregate.py](../../dddjango/scripts/design_pregate.py) 및 명세 소비 지점 | 실제 파싱·입력 계약 영향이 확인된 경우만 도구·픽스처와 byte 미러 변경 검토 |

graph-owned 절을 변경하게 되면 TTL 정본 수정→렌더→rulepack 재생성 절차를 따른다. 산문 절과 플랫폼별 미러의 처리는 [개발 가이드](../../docs/DEVELOPMENT.md)를 따른다. 이번 문서는 메인테이너용 검토 기록이며 런타임 규칙을 추가하지 않는다.

## 5. SPARQL은 수정 대상이 아니라 비교할 수단이다

현행 [ontology_rulepack.py](../tools/ontology_rulepack.py)는 코퍼스 그래프에 빌드타임 SPARQL을 사용해 구조·명칭 인덱스를 만들고, 설치본의 [rulepack.py](../../dddjango/scripts/rulepack.py)는 표준 라이브러리로 이를 읽는다. 이 팩은 규범 본문을 담지 않으며, 작업마다 생성되는 `design-spec.md`의 결정 관계를 자동으로 조회하는 장치가 아니다.

비교 후보는 다음과 같다. 이번 문서 작성으로 어느 것도 도입하지 않는다.

1. **원문 유지 + 정확한 탐색·한도 내 읽기:** T1과 단순 탐색 문제를 낮은 변경 비용으로 해결할 수 있는지 확인한다.
2. **안정 ID + 명시적 관계 + 경량 조회:** T2–T4에 필요한 관계를 파일/JSON 등의 구조와 조회 코드로 다룰 수 있는지 확인한다.
3. **RDF + SPARQL 조회:** 동일한 사실·관계 집합을 대상으로 복합 관계 조회와 갱신·검증의 이점을 평가한다.

2와 3의 비교에서는 한쪽에만 더 좋은 관계 모델이나 더 완전한 정보를 주지 않는다. 필요한 정보 단위와 연결 자체가 빠져 있다면 저장·질의 기술을 바꾸는 것만으로 해결됐다고 보지 않는다. 런타임 SPARQL을 후보로 구체화한다면 현재의 배포 의존성 경계와 명세 작성·갱신 비용부터 별도로 검토해야 한다.

## 6. 수정 확정 전에 필요한 확인

2번 문제에서 제안된 다음 단계는 **대표 사례 선정과 당시 필요한 정보의 재구성**이다. 아직 그 단계 전체를 실행하거나 실험 환경을 만들지는 않았다. 별도 요청을 받은 경우에 수행한다.

선정할 사례는 세 종류다.

1. 토큰 한도 때문에 읽기를 재시도한 작업 — E1 사례를 출발점으로 삼는다.
2. 여러 슬라이스에 걸친 공통 계약·예외를 함께 알아야 했던 작업 — 구체 사례와 적용 관계는 아직 선정·검증 전이다.
3. 승인된 생산자 가드가 배정에서 빠진 작업 — E2 사례를 출발점으로 삼는다.

각 사례의 결과는 다음 대응표로 정리한다.

> 당시 필요한 정보 → 실제 전달·열람 경로 → 반복·누락의 원인 → 그 원인을 해결할 최소 대안

- 해당 작업의 **배정 시점**에 존재한 명세·승인·역할 지시·참조 자료·도구 결과를 기준으로 삼는다. 현재 파일이나 이후 수정 내용을 당시 입력에 섞지 않는다.
- 읽기 실패, 위치 탐색의 어려움, 명세 자체의 관계 누락, 배정 누락, 입력은 충분했지만 집행에서 빠진 경우를 구별한다.
- E1의 S3 승인 명세 크기는 규모의 근거일 뿐, S2 배정 당시 명세의 대체 자료가 아니다.
- 소급 복원이 불가능한 입력은 불명으로 표시한다. 사후 코드·감사로 후보 의무를 찾더라도, 당시 승인 자료로 확인되지 않은 내용을 당시 필수 정보로 확정하지 않는다.

그 결과로 T1–T4 각각의 필요성, 최소 변경 범위와 평가할 대안을 정한 뒤에야 구현 계획으로 전환한다.

- 원문 순서의 앞부분이 예산을 차지해 최종 guard는 0/6, constructor는 1/6만 남았다. 총 18개 상위 seed 중 17개도 탈락했다.

- 사람이 지정한 원문 묶음은 이 실패한 확장 출력과 별개다. 묶음 작성 후 조회는 6/6이지만, 질의에 따라 자동 생성한 것이 아니며 수동 선정 시간은 미측정이다.

### 같은 관계의 엔진 비교

- 노드 1,676개·관계 16,143개·시작점 6개를 양쪽에 동일하게 주었다. 여섯 조회의 반환 ID 배열은 전부 같았다(각 1 / 581 / 581 / 1 / 581 / 580개).
- 준비된 **6개 조회 묶음 전체**를 30회씩 반복한 중앙값: JSON 인접 목록 1.372ms(1.282–1.459), RDFLib 7.6.0/SPARQL 203.891ms(200.186–218.726). 이 묶음의 차이는 약 202.52ms다.
- 메모리 생성·직렬화·파싱·질의 준비 합계: JSON 3.975ms, RDF 641.017ms. 프로세스 시작·import는 미측정이며 `module_call_wall_ms`를 시작 비용으로 쓰지 않는다.
- 직렬화 크기 485,796 / 903,594바이트는 관계 인덱스 크기다. 원문을 포함한 모델 전달량과는 다르다.
- 한 머신의 특정 구현 미세 측정이다. SPARQL 구현 전체의 우열이나 실제 에이전트 속도를 대표하지 않는다. 원문·관계를 정확하게 준비해야 하는 문제도 엔진 교체로 해결되지 않는다.

### 개정·결손

- 실제 06fa→9fe 개정에서 오래된 digest와 없는 간선 대상은 거부했다. 유효 간선 하나를 빼면 수용했다. 구조적으로 유효한 누락을 모른다는 반례다.
- 메모리에 있는 새 문면의 행·관계 재생성은 약 13.094ms, 새 인덱스의 각 행은 원문과 일치했다. 수동 의미 검토·파일 읽기·배포 등 운영 갱신 총비용은 아니다.
- 내용이 같은 ID 1,619개 중 374개는 행 번호가 이동했다. 제거/변경 ID 38, 신규/변경 ID 57. 이 ID는 행 내용과 출현 번호를 쓰며 절의 의미적 정체성이나 중복 행의 논리적 동일성을 증명하지 않는다.

첫 결과 검토자는 E3 작성자이기도 했으므로 그 검토만으로 코드의 독립 리뷰를 주장하지 않았다. 이후 별도 검토자가 E3 코드·자료 재생성·여섯 독립 도달 집합 계산을 직접 대조했고 모두 일치했다. 이 검토에서는 실험 단위 테스트 21/21, 고정 Git 자료·코드 추출·133조각도 확인했다. 파라미터 튜닝이나 결과 변경은 없었다.

채점기의 제한된 AST는 모든 의미상 유효 Python 표현을 수용하는 범용 실행기가 아니다. 검토자가 `isspace()` 사용의 표현상 거부 반례를 확인했다. 현재까지의 모델 구현에는 해당 표현이 없었으며, 모든 시행 종료 뒤 실제 실패가 있다면 계약 위반과 채점기 표현 제한을 구별한다. 허용 함수에서의 동작 검사 통과를 코드 품질 전체의 동등성으로 확대하지 않는다.

## 14. 계정 교체 후 남은 테스트 완료

### 원 채점 17/18과 보정 후 18/18의 구분

`3-guard-full`은 `line.replace("{subject}", subject)`를 사용했다. 기본 AST 검사기가 `strip/format/get`은 허용하지만 `replace`는 허용하지 않아 동작 10개 실행 전에 거부한 것이다. 과제 문면은 순수 문자열 연산을 허용하며 표현을 `format`으로 강제하지 않았다. 독립 검토자가 동결 계약·모델 코드·테스트를 직접 대조해 해당 리터럴 치환이 이번 과제에 유효함을 확인했다. 범용 포맷 문자열에서 두 연산이 언제나 같다는 주장이 아니다.

모델을 다시 호출하거나 원 코드·응답·채점을 고치지 않았다. 기본 채점의 동작을 유지한 채 opt-in `allow_replace=True`를 추가하고, **유효 가드 응답 9개 전부**에 같은 10개 동작 검사를 적용했다. 바뀐 판정은 이 1건뿐이다. 생성자 9개 응답은 기존 9개 판단 검사를 유지했다. [adjudications.json](../eval/design-spec-delivery/2026-09-06/adjudications.json)에 9개 가드의 원 파일·코드 해시·기본/보정 판정을 보존한다. `default_all_pass_count=17`, `reviewed_all_pass_count=18`을 함께 보고하며 사전 고정 채점의 첫 통과율을 18/18로 바꾸지 않는다.

### 남은 긴 행 Read 및 검증 범위

- 추가 대상 `frozen/chunks-6200984c/002.txt`는 16,000바이트이며 최장 물리 행은 8,254자다. Read 정확히 1회, 약 6.627초, 성공 반환에서 행 번호를 제거한 내용과 원문이 byte-exact 일치했다.
- 파일 분할·전량 재조립은 133조각 전체, 실제 도구 반환 대조는 분할 조각 3개다. 원본 1:250 한도 오류 재현도 유지한다. 도구가 모든 파일을 항상 무손실로 읽는다는 일반 보장은 아니다.
- 재시도 선택·기록 보존·중복 방지·집계 및 보정 채점의 테스트를 추가했고 Red→Green을 확인했다. 실험 단위 테스트는 29/29 통과했다. 요약 재생성은 모델 호출 없이 동결 원문·프롬프트 digest와 원 채점의 동일성을 다시 검사한다.
- 최종 집계: 원 시도 18개 + 재시도 6개 = 24개 호출 기록, 유효 모델 응답 18개, `all_registered_trials_valid=true`, `invalid_or_missing_trials=[]`, `pending_read_probes=[]`다. 429 거부 6개의 원 기록과 재개 전 집계는 삭제하지 않았다.
- **이번에 남은 모델·Read 실행은 모두 끝났다.** 불필요 원문량, 자동 원문 선정의 누락 방지, 사람의 선정·개정 비용, 새로운 과제의 재현성, 전체 설계·코드 품질·총 시간은 미검증이다. 이 탐색 실험만으로 2번 해결 또는 제품 채택을 선언하지 않는다. 3번은 대기, 플러그인·코퍼스·진행 중인 워크트리 변경과 커밋·배포는 범위 밖이다.

## 15. 추가 실험 — 원문 전량 읽기의 과제 완료 시간

사용자는 수동 원문 선별을 후속 후보에서 제외한 뒤, ‘같은 원문과 품질 검사를 유지하고 읽기 실패·재시도를 포함한 전체 시간을 비교’하는 단일 실험을 승인했다. 원자료·실험용 코드는 `../eval/design-spec-delivery/2026-09-06/full-read/`에 둔다. 이전 실험 결과·코드·채점기는 수정하지 않는다.

### 실행 전 고정 조건

- 입력은 기존 `9fe56c87` 승인 명세 **603,455바이트·1,779행 전량**이다. 검색·요약·필수 원문 선정은 하지 않는다. 기존 가드와 생성자 과제를 한 세션에서 모두 수행하고, 두 읽기 방식에 같은 코드 조각·작업 지시·guard 10개 및 constructor 9개 검사를 적용한다. guard의 `allow_replace=True`를 시작 전에 고정한다.
- 원본 방식: 처음부터 끝까지 250행 단위의 초기 범위를 준다(마지막 범위 29행). 실제 Read 크기 오류가 난 범위만 절반씩 나누어 재시도한다. 한 행까지 줄여도 반환되지 않으면 전달 실패다. 분할본으로 대체하거나 성공한 범위를 반복 읽지 않는다.
- 분할 방식: 같은 원문을 UTF-8 **16,000바이트 이하 38조각**으로 나누고 전부 읽는다. 매 시행 조각을 다시 생성·기록하는 비용도 포함한다. 원본 시작 행·바이트 위치·행 중간 시작 여부를 제공하되 원문 본문은 바꾸지 않는다.
- 두 조건 모두 최대 4개 Read 동시 진행, Read 외 도구 없음. 신규 격리 세션, Claude Code **2.1.261**, `claude-fable-5-1`, xhigh, fast off, 자동 compact 경계 1M. 실제 compact 이벤트가 나타나면 무요약 조건 미달로 기록한다. 이는 공급자 내부 문맥 처리 전체를 증명하는 것은 아니다.
- 실행 순서는 **원본1 → 분할1 → 분할2 → 원본2 → 원본3 → 분할3**, 총 6회다. 호출별 최대 1,200초·15달러 한도. 품질 실패를 새 응답으로 대체하지 않는다. 런타임 불가·429는 보존하고 추가 유료 호출을 멈추며 계정·결제·한도 설정은 바꾸지 않는다.
- 총시간은 매 시행 원문 로드·입력 생성/기록·Read 오류/재시도·모델 과제 수행·로컬 판정까지다. 준비 시간·CLI 벽시계·마지막 Read 반환까지·검증 시간을 구분해 기록한다. 프로토콜 준비·실험 도구 개발·사전 가용성 확인 비용은 모델 과제 시간에 합치지 않는다.
- 허용한 경로·초기 범위·실패 범위의 이분 자식·동시 진행 수·최종 응답 전 전량 수신을 실제 도구 기록으로 검사한다. 모델의 자기 보고만으로 완료를 인정하지 않는다. 누락·전략 이탈·compact·과제 실패는 짧게 끝나도 성공 시간으로 집계하지 않는다. 두 조건 모두 3/3 완료되어야 관측 감소율을 낸다.

### 사전 검토 및 도구 프레이밍 확인

독립 검토에서 compact, 조각 행 번호, 읽기 전략 준수, 순서·준비 시간 귀속을 명확히 했다. 실패 보존 검토에서는 stdin 쓰기가 timeout 밖에 있던 결함을 발견해 비차단 입출력으로 고쳤으며, 입력을 읽지 않고 종료/대기하는 실제 자식 프로세스 테스트로 Red→Green을 확인했다.

`preflight.json`의 실제 Read 1회(원본 1–4행)는 정상 실행됐다. 번호가 붙은 행 범위의 **마지막 개행 하나가 출력 프레이밍에서 빠짐**을 확인했다. 따라서 비교는 행 번호 제거 및 정확히 그 경계 LF 하나를 복원한 뒤 원문과 대조한다. 복원은 모든 행 번호가 요청 범위와 같고 나머지 바이트가 완전히 동일할 때만 허용하며, 복원 횟수를 별도 기록한다. 일반적인 잘림·공백 제거·내용 정규화는 허용하지 않는다. 원 도구 반환은 그대로 보존하며 ‘raw 반환 byte-exact’라고 부르지 않는다.

새 측정 코드의 사전 단위 테스트는 **19개 통과**했다. 최종 검토에서 일부 성공 후 API 오류 또는 보조 모델 사용량만 남은 경우에도 후속 유료 호출을 멈추도록 중단 조건을 보완했다(Red→Green). 본 시행 0회 상태에서 이전 등록본을 `protocol-before-runtime-stop-fix.json`으로 보존하고 사전 변경 사유와 새 코드 해시를 `protocol.json`에 고정했다. 과제·프롬프트·원문·순서·예산은 변경하지 않았다. 프롬프트·채점기·원문 변경은 기존 시행을 같은 실험으로 덮어쓰는 근거가 될 수 없다.

### 해석 제한

이번 시간은 **전체 명세를 읽고 두 제한된 과제를 완료하는 시간**이다. 기존 단일 과제 시간과 직접 비교하지 않는다. 새 6회 내부의 탐색 비교이며, dddjango 전체 G0/G1/G2 재실행·새 과제 일반화·전체 코드 품질의 비열등성 검증은 아니다. 출처 행 번호의 정확성은 기존 19개 채점기에 포함되지 않는다. 모든 자료가 도구로 전달됐다고 해서 모델이 모든 내용을 이해·집행했다는 보장도 아니다. 캐시·추론량·실행 시점 차이는 기록하되 통제 완료라고 표현하지 않는다.

### 실행 결과 — 등록 6회 종료

원본/분할 각각 3회, 등록 순서 그대로 실행했다. 미실행·API 실패·timeout·선택적 재실행은 없다. 아래 시간은 원 기록이며 사후 추출·독립 검토 시간은 포함하지 않는다.

- 전 6회 실제 도구 반환으로 **603,455바이트 전량**을 재조립했다. 원본은 시행당 크기 오류 11회·성공 범위 19개·경계 LF 복원 19회다. 분할은 시행당 38조각 전부 반환됐고 오류·LF 복원은 0회다. 독립 검토자가 기존 trace 함수 재호출에 그치지 않고 원 이벤트를 별도 순회해 원문 SHA-256 일치를 확인했다.
- 등록 읽기 전략·중복 없음·최종 응답 전 전량 전달·compact 이벤트 없음·실제 런타임을 전 6회 확인했다. 동시 호출 상한은 같지만 관측된 최대 in-flight는 원본 모두 1, 분할은 2·1·2였다. 실제 병렬성이 완전히 같은 실험으로 해석하지 않는다.

- **실패 포함 실제 시도 총시간** 중앙값은 **144.016→178.424초**, **23.892% 증가**다. 분할 준비 63–66ms(원본 5.7–6.2ms), 로컬 검사 약 16–28ms를 포함했다. 형식 실패를 수선하는 시간은 측정하지 않았으므로 성공 완료 시간으로 부르지 않는다.
- 본 시행 6회의 CLI 보고 비용은 **42.1018달러**다(원본 20.7042 / 분할 21.3976, 사전 확인 제외). 한도나 계정 설정은 변경하지 않았다. 입력 캐시·출력·추론 토큰 사용량은 원 기록과 `supplemental-audit.json`에 남겼으며, 총시간 증가의 원인을 분할 자체 하나로 단정하지 않는다.

### 형식 실패와 사후 내용 대조를 분리

`1-original`, `2-original`, `3-original`, `2-chunked`, `3-chunked`는 최종 JSON 앞에 전체 읽기 완료 설명을 붙였다. 사전 고정 파서가 이를 거부했으므로 **기본 성공은 원본 0/3·분할 1/3**이다. 기존 파서·19개 채점기·응답·기본 판정은 변경하지 않았다. 양쪽 모두 3/3 성공해야 한다는 사전 기준에 따라 `summary.json`의 **`reduction_percent=null`을 유지**한다.

다만 파서의 형식 실패를 곧 내용 오답으로 오해하지 않도록 모든 6응답에 동일한 사후 추출 규칙을 적용했다: 전체 응답이 JSON이면 그대로 사용하고, 아니면 **유일한 `json` 코드블록의 본문을 수정 없이 추출**한다. 같은 19개 검사를 적용하면 전 6회 통과한다. 이 대조는 `supplemental-audit.json`에 원 응답·판정·추출 결과 해시와 함께 분리했다. 독립 검토자도 전 6회 원 응답에 동일한 추출·채점을 다시 적용해 확인했다. 사후 내용 통과를 사전 성공으로 승격하지 않는다.

### 결론 및 보존

**전량 분할 읽기는 이번 자료에서 누락 없이 읽기 오류를 없애고 읽기 단계를 줄였지만, 총시간 단축 효과는 확보하지 못했다.** 전체 품질 보존·전체 dddjango 파이프라인의 속도 개선을 입증한 것이 아니므로 제품에 반영하지 않는다. 다른 선정·검색 방식이나 3번 쟁점으로 자동 진입하지 않는다.

현재 상태: 승인된 추가 실험 6회·사후 대조·독립 검산 완료, pending 없음. 원 실험 자료 193개와 기존 Git HEAD·추적 파일 변경은 보존했다. 이번 변경은 `full-read/` 실험 산출물과 기존 진행 현황·이 참고 문서뿐이며, 플러그인·코퍼스·fortune/account 작업·커밋·배포는 건드리지 않았다.
