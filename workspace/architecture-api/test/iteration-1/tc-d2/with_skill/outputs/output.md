# API 버전 전략 설계

## 현황 요약

| 항목 | 내용 |
|------|------|
| API 유형 | 퍼블릭 API (외부 파트너 50개사 연동) |
| 현재 버전 | v1 (2년 운영) |
| 예정 변경 | 사용자 모델 구조 변경, 결제 API 재설계 |
| 레거시 | 일부 엔드포인트 제거 예정 |

---

## 1. 버전 관리 전략

### 1-1. 채택 전략: URL Path + Header 하이브리드

외부 파트너 50개사가 연동 중인 퍼블릭 API이므로 **가시성과 명확성**이 최우선이다.

| 계층 | 방식 | 역할 | 예시 |
|------|------|------|------|
| 메이저 버전 | URL Path | 구조적 Breaking Change 구분 | `/api/v1/users`, `/api/v2/users` |
| 마이너 버전 | Custom Header | 세부 동작 조정 (선택적) | `API-Version: 2026-05-01` |

**URL Path를 기본으로 선택한 이유:**

- 외부 파트너가 즉시 어떤 버전을 호출하는지 식별 가능
- 서버 라우팅이 단순 (v1과 v2를 독립 배포 가능)
- 디버깅, 로깅, 모니터링에서 버전이 바로 드러남
- 50개사 파트너 중 다양한 기술 스택이 존재할 수 있으므로, 헤더 전용 방식은 통합 난이도를 높임

**Header를 보조로 사용하는 이유 (Stripe 패턴 차용):**

- 메이저 버전 내에서 필드 추가, 응답 포맷 미세 조정 등 Non-Breaking 변경이 누적될 때 날짜 기반 헤더로 관리
- 파트너가 명시적으로 헤더를 보내지 않으면 계정 생성 시점의 기본 버전에 고정
- 점진적 채택이 가능하므로 파트너별 마이그레이션 속도 차이를 수용

```
# 메이저 버전은 URL로
GET /api/v2/users/123

# 마이너 조정은 헤더로 (선택적)
API-Version: 2026-05-01
```

### 1-2. 새 메이저 버전을 만드는 기준

다음 중 하나라도 해당하면 메이저 버전을 올린다.

| Breaking Change 유형 | 해당 여부 | 이번 v2에서의 구체 사례 |
|---------------------|:---------:|----------------------|
| 필드 제거 | O | 사용자 모델에서 기존 필드 제거 |
| 필드 이름 변경 | O | 사용자 모델 구조 변경에 따른 필드명 변경 |
| 필드 타입 변경 | O | 사용자 모델 구조 변경에 따른 타입 변경 가능 |
| URL 경로 변경 | O | 결제 API 재설계로 경로 구조 변경 |
| 필수 파라미터 추가 | O | 재설계된 결제 API에서 새 필수 필드 |
| 에러 형식 변경 | O | 결제 API 에러 응답 구조 변경 가능 |

이번 변경 사항(사용자 모델 구조 변경 + 결제 API 재설계)은 명백한 Breaking Change이므로 **v2 생성이 필수**다.

반대로, 다음은 새 버전 없이 기존 버전에 추가 가능하다 (Non-Breaking):

- 응답에 새로운 선택적 필드 추가
- 요청에 새로운 선택적 파라미터 추가
- 새 엔드포인트 추가

## 2. v1에서 v2 마이그레이션 계획

### 2-1. 타임라인

```
2026-04       v2 설계 확정, 내부 리뷰
    |
2026-05       v2 출시 (v1과 병행 운영 시작)
    |         파트너에게 공식 마이그레이션 가이드 배포
    |
2026-05~06    얼리어답터 파트너 마이그레이션 지원 (5~10개사)
    |
2026-07       v1 Deprecation 공식 선언
    |         v1 응답에 Sunset 헤더 추가
    |
2026-07~12    전체 파트너 마이그레이션 기간 (6개월)
    |         월간 마이그레이션 현황 리포트
    |
2027-01       v1 제거 (최종 기한)
```

### 2-2. 마이그레이션 지원 도구

**A. 마이그레이션 가이드 문서**

각 Breaking Change에 대해 v1 -> v2 매핑표를 제공한다.

```
## 사용자 모델 변경

| v1 필드 | v2 필드 | 변경 내용 |
|---------|---------|----------|
| name    | full_name | 필드명 변경 |
| address | address.street, address.city | 단일 문자열 -> 구조화된 객체 |
| (없음)  | email_verified | 신규 필드 추가 |

## 결제 API 변경

| v1 엔드포인트 | v2 엔드포인트 | 변경 내용 |
|-------------|-------------|----------|
| POST /v1/payments/charge | POST /v2/payments | 리소스 기반 URL로 변경 |
| GET /v1/payments/list | GET /v2/payments | 리소스 기반 URL로 변경 |
```

**B. 호환성 어댑터 (Compatibility Layer)**

전환 기간 중 파트너 부담을 줄이기 위해 선택적 호환성 레이어를 제공한다.

```
# 파트너가 v1 요청을 보내면
GET /api/v1/users/123
→ 내부적으로 v2 로직 실행 후 v1 형식으로 변환하여 응답

# 이를 통해 서버 측은 v2 단일 코드베이스만 유지
```

**C. 파트너별 마이그레이션 대시보드**

- 각 파트너의 v1/v2 트래픽 비율을 실시간 모니터링
- 마이그레이션 미완료 파트너에게 자동 알림 (월 1회)

### 2-3. v2 설계 시 적용할 원칙

| 원칙 | 적용 방법 |
|------|----------|
| 리소스 기반 URL | 결제 API의 동사형 URL을 명사형으로 재설계 (`/payments/charge` -> `/payments`) |
| RFC 9457 에러 포맷 | v2의 모든 에러 응답을 Problem Details 형식으로 통일 |
| 커서 기반 페이지네이션 | 50개사 대량 데이터 조회 시 offset 방식에서 cursor 방식으로 전환 |
| Idempotency-Key | 결제 API의 POST 요청에 Idempotency-Key 헤더 필수 적용 |

## 3. v1 Deprecation 일정과 프로세스

### 3-1. Deprecation 단계

#### Phase 1: 공지 (v2 출시 시점 -- 2026-05)

- API 문서에 v1 Deprecation 예정 명시
- 변경 이력(Changelog)에 기록
- 파트너 전체에 이메일 공지 발송
- 개발자 포털에 배너 표시

#### Phase 2: Sunset 헤더 적용 (2026-07)

v1의 모든 응답에 Sunset 헤더를 포함한다.

```http
HTTP/1.1 200 OK
Sunset: Sat, 01 Jan 2027 00:00:00 GMT
Deprecation: true
Link: </api/v2/users>; rel="successor-version"
```

| 헤더 | 용도 |
|------|------|
| `Sunset` | v1 종료 예정 일자 |
| `Deprecation: true` | 현재 버전이 deprecated 상태임을 명시 |
| `Link` | 대체 버전 엔드포인트 안내 |

#### Phase 3: 경고 강화 (2026-10)

- v1 호출 시 응답 본문에 deprecation 경고 메시지 추가
- 미마이그레이션 파트너 대상 직접 연락 (담당자 지정)
- 마이그레이션 지원 오피스아워 운영

#### Phase 4: v1 제거 (2027-01)

- v1 엔드포인트 호출 시 `410 Gone` 응답 반환
- 응답 본문에 v2 엔드포인트 안내 포함

```json
{
  "type": "https://api.example.com/errors/version-sunset",
  "title": "API Version Removed",
  "status": 410,
  "detail": "API v1 has been removed as of 2027-01-01. Please migrate to v2.",
  "instance": "/api/v1/users/123",
  "migration_guide": "https://docs.example.com/migration/v1-to-v2"
}
```

### 3-2. 레거시 엔드포인트 제거

v1 전체 Deprecation과 별개로, 곧 제거 예정인 레거시 엔드포인트는 **독립적 일정**으로 관리한다.

```
2026-04    레거시 엔드포인트 목록 확정, 파트너 공지
2026-05    Sunset 헤더 적용 (기한: 2026-11)
2026-08    경고 강화, 미마이그레이션 파트너 직접 연락
2026-11    레거시 엔드포인트 제거 (410 Gone)
```

레거시 엔드포인트의 Deprecation 기간은 최소 6개월을 보장한다.

## 4. 하위 호환성 유지 규칙

### 4-1. 버전 내 허용/금지 변경 목록

#### 허용 (Non-Breaking -- 버전 변경 없이 가능)

| 변경 | 예시 |
|------|------|
| 응답 필드 추가 | `created_at` 필드 추가 |
| 선택적 요청 파라미터 추가 | `?filter=active` 파라미터 추가 |
| 새 엔드포인트 추가 | `GET /api/v1/notifications` 추가 |
| 새 HTTP 메서드 지원 | 기존 리소스에 PATCH 추가 |
| 에러 메시지 텍스트 변경 | `detail` 필드의 문구 수정 |
| 성능 개선 | 응답 시간 단축 |

#### 금지 (Breaking -- 새 버전 필수)

| 변경 | 왜 Breaking인가 |
|------|----------------|
| 필드 제거 | 파트너 코드가 해당 필드를 참조 중일 수 있음 |
| 필드명 변경 | 역직렬화 실패 유발 |
| 필드 타입 변경 | 파싱 에러 유발 |
| 필수 파라미터 추가 | 기존 요청이 실패함 |
| URL 경로 변경 | 기존 클라이언트의 호출이 404 |
| 상태 코드 변경 | 파트너의 에러 핸들링 로직 오작동 |
| 에러 응답 구조 변경 | 에러 처리 코드 깨짐 |
| 인증 방식 변경 | 기존 인증 토큰 사용 불가 |

### 4-2. 개발팀 준수 규칙

```
규칙 1: 추가는 자유, 제거는 금지
       버전 내에서는 오직 Additive Change만 허용한다.

규칙 2: Robustness Principle 적용
       "보내는 것은 엄격하게, 받는 것은 관대하게"
       → 클라이언트가 인식하지 못하는 필드는 무시하도록 설계
       → 서버는 알 수 없는 필드가 포함된 요청도 거부하지 않음

규칙 3: Breaking Change 감지 자동화
       CI/CD 파이프라인에 OpenAPI 스펙 비교 도구를 통합하여
       PR 단계에서 Breaking Change를 자동 감지한다.

규칙 4: 변경 이력 관리
       모든 API 변경은 Changelog에 기록하며,
       Breaking/Non-Breaking을 명시적으로 구분한다.

규칙 5: 최소 6개월 마이그레이션 기간
       Deprecation 공지 후 최소 6개월간 기존 버전을 유지한다.
       50개사 규모를 고려하면 6개월~1년이 적정하다.
```

### 4-3. Breaking Change 감지 체크리스트 (PR 리뷰용)

PR을 머지하기 전에 다음을 확인한다.

```
[ ] 기존 응답 필드를 제거하거나 이름을 바꾸지 않았는가?
[ ] 기존 필드의 타입을 변경하지 않았는가?
[ ] 새 필수 파라미터를 추가하지 않았는가?
[ ] URL 경로를 변경하지 않았는가?
[ ] 상태 코드를 변경하지 않았는가?
[ ] 에러 응답 구조를 변경하지 않았는가?
[ ] OpenAPI 스펙 diff에서 Breaking Change가 감지되지 않았는가?
```
