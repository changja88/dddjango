# dddjango 작업 요청 가이드

## 1. 새 기능

```text
/dddjango:dddjango <만들 기능>을 만들어 줘.
1. 필요한 동작
   1) <누가 무엇을 할 수 있어야 하는지>
   2) …
2. 특별 기술 요청 사항
   1) <사용자가 직접 정한 기술 조건>
```

- 명령은 요청 맨 앞에 직접 입력합니다. 한 요청에는 한 기능만 담습니다.
- Codex에서는 첫머리를 `dddjango를 사용해`로, 리팩토링(3장)은 `$dddjango-refactor`로 바꿉니다.
- **1번**은 누가 무엇을 할 수 있어야 하는지를 한 항목씩 적습니다. API가 아닌 일 — 다른 서버에 물어
  저장하기, 정해진 때 도는 작업, 기능 걷어 내기 — 도 같은 꼴로 적습니다.
  - 꼭 일어나야 하는 결과(성공하면 무엇이 남는지 · 실패하면 어떻게 되는지)는 정한 만큼 모두 적습니다. 적지 않은
    결과는 플러그인이 정해 설계 승인 때 보여 주고, 스스로 정할 수 없는 것만 묻습니다.
  - 이번에 하지 않을 것은 `제외: …` 항목으로 적습니다.
- **2번**은 사용자가 직접 정한 기술 조건과, 플러그인이 스스로 알 수 없는 사실(환경 · 다른 작업 · 바깥 자료)만
  적습니다. 없으면 비웁니다.
  - 예: 쓸 API 프레임워크 · 새 의존성을 들이지 않는다 · 정해 둔 API 주소나 필드 이름 · 실제 결제·발송을 하면 안
    되는 환경 · 플러그인이 찾을 수 없는 바깥 자료의 위치(다른 저장소의 계약 파일) · 문서에 없는 바깥 서버의 동작 ·
    커밋 · push 규칙 · 같은 파일을 함께 고치는 다른 작업 · 이 요청보다 먼저 끝나야 하는 작업 · 기능을 둘 업무 영역.
  - 다른 세션이 대신 쓰는 요청이면 첫 항목에 «대신 쓴 요청»이라고 밝히고, 사용자가 정한 미룸 · 승인에는 그 말이
    적힌 기록의 절대 경로 `파일:줄`과 시각을 붙입니다.

**좋은 예**

```text
/dddjango:dddjango 주문 취소 기능을 만들어 줘.
1. 필요한 동작
   1) 회원이 배송 시작 전 주문을 취소할 수 있다. 취소되면 재고가 돌아온다. 배송이 시작됐으면 거절하고 주문은 그대로다.
   2) 회원이 자기 주문의 취소 내역을 볼 수 있다.
2. 특별 기술 요청 사항
   1) 개발 · 테스트 환경에서는 실제 PG를 부르면 안 된다.
```

**나쁜 예 — 실제 요청에서(이름은 바꿈)**

```text
3. 허용 경로 application/member/** 만(도메인·응용·저장·마이그레이션·admin·API·테스트). 그 밖 BC · framework/** ·
   pyproject.toml · uv.lock … 무변
- 탈퇴: …/withdraw_member/withdraw_member_use_case.py(한 경계에서 회원 + 인증 번호 두 애그리거트를 다루는 선례)
- admin 선례: driven_layer/django_member/admin/member/panel.py(readonly_fields · 추가·삭제 권한 없음)
```

- 이렇게 적습니다: 경로 목록과 선례를 빼고 결과와 사실만 적습니다.

```text
/dddjango:dddjango 배송지 기능을 만들어 줘.
1. 필요한 동작
   1) 로그인한 회원이 배송지를 여러 곳 등록 · 조회 · 수정 · 삭제할 수 있다. 배송지는 받는 사람 · 별칭 · 메모와
      주문서와 같은 주소 칸을 가진다.
   2) 운영자는 관리 화면에서 그 회원의 배송지를 읽기만 한다.
2. 특별 기술 요청 사항
   1) 같은 저장소에서 다른 작업이 함께 돈다.
```

## 2. 만든 기능 고치기 · 이어서 하기

```text
/dddjango:dddjango <고칠 기능>을 고쳐 줘.
1. 바꿀 동작
   1) 지금: <지금 결과> → 바뀐 뒤: <원하는 결과>
2. 특별 기술 요청 사항
   1) …
```

- 꼭 지켜야 할 기존 동작은 1번에 `유지: …`, 이번에 하지 않을 것은 `제외: …` 항목으로 적습니다.
- 세션 밖에서 바뀐 것(다른 작업이 합쳐짐 · 바깥 서버가 바뀜)을 알면 2번에 적습니다.
- 이미 만든 기능이나 끝나지 않은 이전 작업이 있으면 플러그인이 그 폴더를 이어서 쓸지 새 기능으로 할지 묻습니다.
  만든 기능을 고칠 때는 그 기능의 폴더를 «이어서»로 고릅니다. 세션이 끊겼으면 같은 명령으로 다시 부르고
  «이어서»를 고르면, 마지막으로 승인한 단계 다음부터 이어 갑니다 — 끊긴 작업을 이어 갈 때는 이전 작업을 먼저
  계속하므로, 바꿀 동작은 그 작업을 끝낸 뒤 따로 요청합니다.

**좋은 예**

```text
/dddjango:dddjango 주문 취소 기능을 고쳐 줘.
1. 바꿀 동작
   1) 지금: 결제 완료 뒤에는 취소를 거절한다 → 바뀐 뒤: 결제 완료 뒤에도 배송 시작 전이면 취소할 수 있다.
   2) 유지: 배송 시작 뒤 취소 거절 · 주문 조회 응답.
2. 특별 기술 요청 사항
   1) 환불 서비스가 새 버전으로 바뀌었다.
```

**나쁜 예 — 실제 요청에서(이름은 바꿈)**

```text
③ 이미 로그인해 있던 회원 — 이용 정지가 걸려 있는 동안 그 회원으로 선 로그인을 든 요청은 모두 로그인하지 않은
   요청과 같다 … 이 «로그인 필요» · «로그인 안 됨» 답에는 … 까닭 값과 풀리는 때가 더해진다 — 정지가 걸려 있는
   동안 그 로그인을 든 모든 요청에서다(첫 요청 한 번이 아니다).
```

- 이렇게 적습니다: 사용자가 정하지 않은 결과(모든 답에 «풀리는 때»를 싣는다)는 넣지 않고, 정한 결과는 빠짐없이
  적습니다.

```text
/dddjango:dddjango 이용이 정지된 회원이 로그인하지 못하게 고쳐 줘.
1. 바꿀 동작
   1) 지금: 이용 정지 중에도 로그인된다 → 바뀐 뒤: 로그인되지 않는다. 답으로 정지임을 가를 수 있다.
   2) 이미 로그인해 있던 기기도 정지 동안에는 로그인이 풀린다. 정지가 끝나면 비밀번호를 다시 넣지 않아도 저절로
      이어진다.
   3) 유지: 한 가지 일만 막는 정지는 로그인을 막지 않는다.
2. 특별 기술 요청 사항
```

## 3. 기존 코드 정리 — 리팩토링

한 업무 영역의 기존 코드를 표준에 맞추고 싶을 때 씁니다. 표준에 맞추느라 동작이나 DB 구조가 바뀔 수 있어서,
운영 전인 서비스에서만 진행합니다.

```text
/dddjango:refactor <영역> <지금 불편한 점(있으면)>
```

- `<영역>`은 `application/` 아래 폴더 이름입니다(예: `order`). 영역 하나씩 부릅니다. 새 기능이 필요하면 1장으로
  따로 요청합니다.
- 운영 전인지는 처음에 묻고(운영 중이면 멈춥니다), 밖에서 보이는 동작을 바꿀지는 설계 승인 때 항목마다 플러그인이
  사용자에게 직접 묻습니다.
- 다른 세션이 대신 부르느라 이 입구를 직접 부를 수 없으면, `/dddjango:dddjango`에 요청 첫 줄을
  `리팩토링 모드(입구 /dddjango:refactor) · 대상: <영역> <불편한 점>`으로 적어 보냅니다(Codex에서는 요청 첫 줄을
  `리팩토링 모드(입구 $dddjango-refactor) · 대상: <영역> <불편한 점>`으로 시작합니다). 그 아래에는 이 실행을 두고
  «운영 전»이라고 한 사용자 말의 기록(절대 경로 `파일:줄`과 시각)을 붙입니다 — 없으면 첫 질문에서 멈춥니다.

**좋은 예**

```text
/dddjango:refactor order 규칙 하나를 고칠 때 여러 곳을 고쳐야 해.
```

**나쁜 예 — 실제 요청에서(이름은 바꿈)**

```text
/dddjango:dddjango 기존 Django 프로젝트의 member 에서 driven 어댑터 5개의 현재 동작은 그대로 유지하면서, 단일 파일
5개를 … 어댑터 고정 골격(패키지 · adapter/·command/·constant/·contract/·schema/ · 클래스 하나당 파일 하나)으로 옮겨 줘.
- 슬라이스: 어댑터 하나마다 «새 패키지 골격 생성 → 역할 파일 이동 → import 처 갱신 → 옛 파일 삭제» 를 한 커밋으로
- 그 밖 member 층(도메인·응용·포트·OHS·REST·persistence 어댑터)·다른 BC 무변.
```

- 정리를 기능 입구로 넣었습니다 — 지금은 `/dddjango:dddjango`에 정리만 요청하면 리팩토링 입구를 안내하고 멈춥니다.
- 옮길 자리 · 작업 순서 · 볼 범위를 요청이 정했습니다 — 리팩토링은 영역 전체를 표준에 비춰 보고, 찾은 것을 목록으로
  보여 준 뒤 묻습니다.
- 이렇게 적습니다: `/dddjango:refactor member 어댑터를 더할 때 옛 배치와 새 배치가 섞여.` — 리팩토링은 어댑터
  다섯만이 아니라 영역 전체를 보고, 동작이 바뀔 수 있어 운영 전에만 진행합니다.

## 4. 적지 않는 것

두 칸 밖의 내용은 적지 않습니다. 특히 아래는 플러그인의 설계를 묶어 버립니다.

- 진행 방식 · 단계 · 리뷰 구성
- 파일 · 클래스 · 함수의 이름과 위치, 고쳐도 되는 · 안 되는 경로 목록, «이 코드를 본떠라»
- 테스트 방식 · 개수, 재시도 · 잠금 같은 구현 수단 — 원하는 것이 있으면 1번에 결과로 적습니다(예: 같은 요청이 두 번
  와도 한 번만 처리된다)
- 사용자가 정하지 않은 기존 코드 정리 미룸, 조사 범위를 좁히라는 말, 검사 · 승인을 줄이거나 건너뛰라는 말,
  검사 기준 커밋(`--base`)을 정하거나 옮기라는 말
- 조사한 코드 목록, 요청 문서의 판 이력, 진행 절차 설명

기존 코드 정리를 먼저 할지, 기능을 어느 업무 영역에 둘지 같은 결정은 플러그인이 조사 결과와 대가를 보여 주고
묻습니다. 이미 정했으면 2번에 적습니다.
