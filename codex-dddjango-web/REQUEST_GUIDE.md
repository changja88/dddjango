# dddjango-web 작업 요청 가이드

설치된 플러그인 루트의 이 `REQUEST_GUIDE.md`가 해당 runtime(Claude Code·Codex)에 대한 권위 있는 가이드 사본입니다.
저장소에 공개된 같은 이름의 문서는 최신판을 찾는 길이고, 설치한 버전의 동작은 이 사본을 따릅니다.
이 가이드는 dddjango-web 2.0.1 기준입니다.

## 1. 무엇을 하는 플러그인인가

`dddjango-web`은 기존 Django 프로젝트에 **한 기능의 화면**을 만듭니다. 화면 코드는 프로젝트의 `web/` 앱에
Django 템플릿·HTMX·JavaScript로 짓고, 테스트는 `web_test/`에 둡니다. 새 화면은 범위 확인(G0) → 설계(G1) →
구현(G2) 세 단계마다 사용자의 승인을 받고 넘어갑니다. 이 플러그인으로 만든 화면을 설계 변경 없이 고칠 때는 지난번에
승인한 설계를 그대로 써서 설계 단계를 건너뛰고, 작은 수정은 한 번만 승인받습니다(6절).

- 화면은 **이 Django 프로젝트 안의 JSON API**를 같은 프로세스 안에서 불러 데이터를 얻습니다. API를 어떤
  도구로 만들었는지는 상관없습니다.
- 백엔드 코드(API·모델·업무 규칙)는 고치지 않습니다. 필요한 API가 없으면 그 모양을 가정해 화면을 짓고,
  실제 API는 `dddjango`로 따로 요청하라고 안내합니다.
- 한 요청에는 한 기능을 담습니다. 서로 관계없는 화면 여럿은 나눠서 요청합니다. 한 프로젝트에서는 한 번에
  한 작업만 돌립니다.

## 2. 꼭 줄 것 세 가지

요청은 아래 셋이면 됩니다. 나머지는 플러그인이 프로젝트를 조사하고, 사람이 정해야 하는 것만 묻습니다.

### ① 무엇을 만들지 — 기능 설명

만들 화면과 그 화면에서 되어야 할 일을 결과로 적습니다. 새 화면이면 «주문 목록 화면», 있는 화면을 고치면
«주문 목록 화면에 상태별 필터 추가»처럼 씁니다. 새로 만들지, 고칠지, 작은 수정인지는 플러그인이 조사해서
정하고 첫 단계에서 근거와 함께 보여 줍니다.

### ② API는 어디를 보면 되는지 — OpenAPI 문서 위치

이 프로젝트 API의 **OpenAPI 3 형식 JSON 문서**가 어디 있는지 알려 줍니다. YAML 문서나 Swagger 2.0 문서는 쓸 수
없습니다. 위치는 아래 세 가지 가운데 하나로 줍니다.

1. **이 프로젝트 안의 문서 경로 (추천)**: `/api/openapi.json`처럼 `/`로 시작하는 경로만 줍니다. 개발 서버에서
   `http://127.0.0.1:8000/api/openapi.json`으로 열리는 문서라면 `/api/openapi.json`입니다. 플러그인이 개발 서버를
   켜지 않고 이 Django 프로젝트 안에서 그 경로를 직접 열어 문서를 받으므로, 서버를 켜 둘 필요가 없습니다.
2. **문서 파일 경로**: 컴퓨터에 저장된 OpenAPI 문서 파일의 경로를 줍니다. 서버 프로젝트가 같은 컴퓨터의 다른
   폴더에 있으면 그 폴더 안의 파일이어도 됩니다.
3. **웹 주소**: `http://`나 `https://`로 시작하는 주소를 줍니다. 개발 서버 주소라면 첫 단계 동안 서버를 켜 둡니다.
   로그인해야 열리는 주소는 열지 못합니다.

- 플러그인은 첫 단계에서 이 문서를 받아 보관합니다. 준 값이 실제로 있는 파일이면 파일로 읽고, 파일이 아니면서
  `/`로 시작하면 이 프로젝트 안의 경로로 읽습니다.
- 프로젝트 안의 경로는 프로젝트의 기본 설정(`manage.py`가 쓰는 설정)으로 엽니다. 그 설정으로 프로젝트가 뜨지
  않으면(필요한 환경 변수가 없을 때 등) 첫 단계에서 어떤 설정으로 열지 묻습니다.
- 한 번 준 위치는 프로젝트 설정에 저장되므로 다음 요청부터는 빼도 됩니다.
- 요청에도 설정에도 위치가 없으면 플러그인이 한 번 묻습니다. 끝내 없거나 문서를 받지 못하면 첫 단계 보고에
  그 사실을 보이고, 기존 화면 코드가 쓰는 API를 참고하거나 API 모양을 가정해서 짓습니다. 가정한 내용은 설계
  단계에서 확인받고, 첫 줄기를 만든 뒤 한 번 더 확인합니다.

### ③ 디자인은 어디의 어떤 화면인지

Claude Code와 Codex가 다릅니다. 시안 내용을 요청에 옮겨 적을 필요는 없습니다.

**Claude Code — Claude Design 화면 주소**

- 구현할 화면이 든 Claude Design 프로젝트의 주소를 줍니다. 주소 끝에 `?file=<화면 파일>.dc.html`이 붙어
  있으면 그 화면이 바로 후보가 됩니다.
- 앱 화면 시안이 든 프로젝트는 플러그인이 보여 주는 목록에 나오지 않습니다. 시안대로 만들려면 주소를 꼭
  줍니다.
- 주소에 화면 파일이 없으면 화면 이름을 시안 파일 이름 그대로(예: `OrderList`) 적습니다. 이름이 맞지 않으면
  플러그인이 화면 목록을 보여 주고 고르게 합니다. 비슷한 화면을 임의로 고르지 않습니다.
- Claude Code가 Claude Design을 쓸 수 있는 claude.ai 계정으로 로그인돼 있어야 합니다.

**Codex — 내려받은 시안 폴더 경로**

- Codex는 보통 Claude Design을 직접 읽지 못합니다. 시안을 Claude Design에서 내려받아, 그 폴더의 경로와
  구현할 화면 이름(화면 파일 이름 그대로)을 줍니다. 이름이 맞지 않으면 화면 목록에서 고르게 합니다.
- 폴더는 이름과 구조를 바꾸지 않고 그대로 줍니다. 맨 위에 화면 파일(`.dc.html`)이 있고, 함께 내려받은
  `assets/`·`_ds/`·`screenshots/` 같은 파일이 그대로 들어 있어야 합니다.
- 플러그인은 이 폴더를 읽기만 하고 고치지 않습니다.

**시안이 없을 때 (두 판 공통)**

- 디자인을 빼면 첫 단계에서 묻습니다. 가지고 있는 이미지 파일의 경로를 주거나, 자체 설계(기존 화면의 관례와
  프로젝트 디자인 시스템을 따름)로 진행할 수 있습니다. Claude Code에서는 Claude Design의 디자인 시스템
  프로젝트 목록에서 고를 수도 있습니다.
- 이미지는 참고 그림으로 씁니다. Codex는 그림 파일을 읽지 못할 수 있습니다.

한 번 정한 시안 프로젝트나 폴더는 프로젝트 설정에 저장돼 다음 요청에서 다시 묻지 않습니다. 다음 기능부터는
화면 이름(또는 화면 주소)만 적으면 됩니다. 다른 시안으로 바꾸려면 첫 단계에서 디자인 출처 변경을 고릅니다.
주려던 시안을 열지 못하면 조용히 자체 설계로 넘어가지 않고 첫 단계 보고에 표시한 뒤 다시 묻습니다.

## 3. 요청 예시

**Claude Code**

```text
/dddjango-web:dddjango-web "주문 목록 화면. 디자인: <Claude Design 화면 주소>" /api/openapi.json
```

조금 더 정한 것이 있으면 따옴표 안에 이어 적습니다.

```text
/dddjango-web:dddjango-web "주문 목록 화면을 만들어 줘.
디자인: <Claude Design 프로젝트 주소> · 화면: OrderList
목록에서 주문을 누르면 주문 상세 화면으로 간다. 주문 취소는 이번에 뺀다." /api/openapi.json
```

- 기능 설명은 큰따옴표로 감쌉니다.
- 닫는 따옴표 뒤 자리는 OpenAPI 문서 위치(프로젝트 안 경로·파일 경로·웹 주소)만 받습니다. 띄어쓰기가 든 파일
  경로는 큰따옴표로 감쌉니다. Claude Design 주소를 그 자리에 두면 API 문서 위치로 읽히니, 디자인 주소는 따옴표
  안에 적거나 플러그인이 물을 때 줍니다.

**Codex**

```text
dddjango-web을 사용해 "주문 목록 화면"을 만들어 줘. /api/openapi.json
디자인: /Users/me/Downloads/쇼핑몰 웹 시안 (Claude Design에서 내려받은 폴더) · 화면: OrderList
```

- Codex는 요청에서 기능 설명 → OpenAPI 문서 위치 순서로 읽습니다. 기능 설명은 큰따옴표로 감쌉니다. 감싸지 않아
  띄어쓰기가 든 설명이나, 어느 쪽인지 애매한 값이 있으면 한 번 되묻습니다.

### 알려 주면 좋은 것 (선택)

이미 정한 것만 보탭니다. 모두 채울 필요는 없습니다.

- 화면에 보여야 할 것, 누르거나 입력한 뒤 보여야 할 결과(예: 재고가 0이면 구매 버튼이 꺼진다).
- 이번에 뺄 것, 있는 화면이면 그대로 둘 것.
- 꼭 써야 하는 API가 정해져 있으면 그 사실.
- 자동 새로고침처럼 따로 원하는 동작. 말하지 않으면 필요할 때 설계 단계에서 넣을지 묻습니다.

## 4. 요청에 적지 않을 것

아래는 플러그인 단계가 정하고, 첫 단계(G0)나 설계 단계(G1)에서 보여 주고 확인받습니다. 요청에 미리 적으면
설계를 묶어 버립니다.

- 진행 방식(전체·수정·작은 수정)이나 단계 건너뛰기 — 플러그인이 조사해 정하고 첫 단계에서 근거와 함께
  승인받습니다.
- 코드 배치: 층(domain·application·infra·presentation), 폴더·파일 경로, 파일·클래스 이름 — 설계 단계가
  표준 구조로 정하고 G1에서 확인받습니다.
- 화면 쪼개기, ViewModel·State 모양, 세션이나 공유 상태를 쓸지 — 설계 단계가 정하고 관점별 검토를
  거칩니다.
- API를 묶는 방식, 오류 처리 모양 — 설계 단계가 OpenAPI 문서를 보고 정합니다.
- 쓸 라이브러리·패키지와 버전 — 설계가 고르고, 버전은 실제로 설치된 판으로 고정합니다.
- 시안 HTML을 그대로 옮기라는 지시 — 플러그인은 시안의 색·크기·간격과 배치·정렬을 그대로 재현하되, 시안 HTML은
  복사하지 않고 Django 템플릿·CSS로 새로 짓습니다.
- 테스트 명령, 테스트 개수, 검사 통과 조건 — 첫 단계에서 테스트 명령을 정하고, 화면 동작마다 테스트를 만들고,
  정해진 검사를 돌립니다.
- 단계를 미리 승인해 두라는 지시 — 단계마다 사용자 승인 없이는 넘어가지 않습니다.
- 기능을 둘 업무 묶음(BC) — 기존 영역과 겹치면 첫 단계에서 묻습니다.
- 백엔드 수정 — 이 플러그인은 백엔드를 고치지 않습니다. `dddjango`로 따로 요청합니다.

## 5. 첫 실행 전에 알아 둘 것

첫 단계에서 플러그인이 프로젝트를 점검하고, 빠진 연결을 보고에 보여 준 뒤 승인받고 넣습니다.

- settings: `INSTALLED_APPS`에 `"web"`, `TEMPLATES`·`STATICFILES_DIRS`·`MIDDLEWARE` 연결 줄,
  `ALLOWED_HOSTS`에 `"testserver"`(화면이 같은 프로세스 안에서 API를 부르는 데 필요).
- 루트 urls: `web.urls` 연결과 404·500 처리 연결.
- htmx 2.0.10: 없으면 인터넷에서 받아 `web/static/htmx/`에 둡니다. 인터넷이 막혀 있으면 파일을 달라고 합니다.
  이미 설치된 htmx는 그대로 씁니다.
- 테스트 도구: pytest·pytest-django·beautifulsoup4(화면 JavaScript 동작을 시험하면 pytest-playwright도)가
  없으면 구현 중에 설치하고, 의존성 목록에 실제 설치 버전을 고정해 넣습니다.
- git: git 저장소가 아니면 `git init`과 첫 커밋을 제안합니다. 커밋하지 않은 변경이 있으면 먼저 커밋하거나
  치워 둘지, 그대로 갈지 묻습니다. 그대로 가면 중간에 멈췄을 때 되돌리기가 안 됩니다.
- ruff를 쓰면 생성 폴더가 검사에서 빠지는지 알려 줍니다. 호스트의 pytest·ruff 설정 파일은 고치지 않습니다.
- Django는 4.2 이상이어야 합니다.
- Codex에서는 하위 에이전트 기능(`multi_agent`, 기본으로 켜짐)이 켜져 있어야 합니다.

## 6. 진행 중에 할 일

- **G0 범위**: 정리한 범위, 진행 방식과 근거, 위 점검 결과, API·디자인 출처를 봅니다. Claude Design 앱 화면
  시안(`.dc.html`)이면 제목·문구와 미리보기 그림을 함께 보여 주며 «이 화면이 맞나요?»를 묻습니다(Codex는 그림 파일 경로를 알려 주니 직접 열어
  대조합니다). 기존 영역과 겹치면 기능을 둘 자리(새 묶음 / 기존 묶음 / 설계에 맡김)를, 지난 작업 폴더가
  있으면 이어서 할지 새로 할지를 함께 묻습니다.
- **G1 설계**(설계를 건너뛰는 수정이면 없음): 설계 문서 경로와 요지를 봅니다. 기본으로 빼 둔 항목을 넣을지, 설계가 혼자 정하지 못한 선택지,
  가정한 API가 있으면 그 목록을 확인합니다. 승인한 설계가 이후 코드의 유일한 근거가 됩니다.
- **가정한 API 확인**: API를 가정했을 때만, 첫 줄기를 만든 직후 가정이 맞는지 한 번 더 묻습니다.
- **G2 구현**: 화면 동작 목록(위험한 항목에 별표)과 시안(시안이 없으면 디자인 토큰)과의 비교를 봅니다.
  `python manage.py runserver`로 직접 띄워 브라우저에서 확인한 뒤 승인합니다.
- **끝**: 실제로 돌린 검증만 보고합니다. 깨끗한 상태에서 시작했으면 작업 중 만든 커밋을 하나의 스테이징된
  미커밋 변경으로 모아 두니, `git diff --staged`로 보고 직접 커밋합니다. 모을 수 없는 상황이면 명령만
  알려 줍니다.

Claude Code는 선택지로, Codex는 글로 묻습니다. Codex에서는 «승인»이라고 답하거나 바꿀 점을 적습니다.
새 파일 없이 기존 문구·색 같은 디자인 값·아이콘만 바꾸는 작은 수정은 한 번 승인받고 바로 고친 뒤 검사 결과를
보고합니다. 고치다 화면 구조(함수 모양·화면 상태·주소)를 건드려야 하면 멈추고 일반 수정으로 바꿔 다시 승인받습니다.
작업 기록(범위 메모·설계 문서·보관한 API 문서와 시안)은 `.dddjango-web/` 아래 기능별 폴더에 남고, 코드와 함께
커밋하는 것이 기본입니다.

## 7. 이어서 하기 · 고치기

- 같은 명령으로 다시 요청합니다. 지난 작업 폴더가 있으면 첫 단계에서 «이어서» 또는 «새 기능»을 고르게 합니다.
- «이어서»를 고르면 API 문서와 시안을 다시 받을지도 묻습니다. 서버 API나 시안이 바뀌었으면 다시 받습니다.
  Claude Design 앱 화면 시안과 내려받은 폴더는 바뀐 것을 스스로 알아채지 않으니, 바뀐 시안을 반영하려면
  «디자인 다시 적용»이라고 분명히 적습니다.
- 세션이 끊겼어도 같은 방법으로 멈춘 곳부터 이어 갑니다.
- 만든 화면을 고칠 때는 바꿀 결과만 적습니다. 영향 범위는 플러그인이 조사합니다.

## 8. 다른 세션이 대신 요청을 쓸 때

- 사용자가 정한 내용만 옮깁니다. 사용자가 정하지 않은 설계 선택을 대신 정해 적지 않습니다.
- 4절의 «요청에 적지 않을 것»은 대신 쓰는 요청에도 그대로 적용됩니다.
- 화면 확인과 단계 승인은 사용자의 결정을 따릅니다. 사용자의 결정이 없는 설계 선택이나 시안과 다른 결과를
  대신 승인하지 않습니다.
