# 설계 철학과 프로세스 레퍼런스

17장(설계 철학과 프로세스)에 대한 상세 규칙과 예시.
설계 방향을 결정하거나 개발 프로세스를 정할 때 참조한다.

---

## 1. 두 번 설계하라 (Design It Twice) [APoSD]

모든 주요 아키텍처/인터페이스 결정에 대해 최소 두 가지 근본적으로 다른
접근법을 비교하라. 첫 번째 생각이 최선의 설계를 내놓을 가능성은 낮다.

## 2. 빠르게 구현한 후 다듬어라 [CC] [OO]

1. 처음에는 길고 복잡해도 좋다
2. 다듬고 또 다듬는다
3. 다듬는 와중에도 항상 단위 테스트는 통과한다

## 3. 안정적인 구조 중심 설계 [OO]

기능이 아닌 도메인 모델을 중심으로 설계하라.
도메인 모델이 안정적인 이유는 사용자가 도메인의 본질적인 측면을 가장 잘 이해하고 있기 때문이다.

## 4. 책임 주도 설계 (RDD) [OO]

1. 시스템 책임을 파악한다
2. 더 작은 책임으로 분할한다
3. 적절한 객체에 할당한다
4. 객체 간 협력을 설계한다

## 5. 세 가지 관점으로 클래스를 바라보라 [OO]

- **개념적 관점** -- 도메인 안의 개념과 관계를 반영
- **명세 관점** -- 객체가 "무엇"을 할 수 있는가 (인터페이스)
- **구현 관점** -- 객체의 책임을 "어떻게" 수행할 것인가

## 6. YAGNI [PC]

미래의 요구사항을 예측하지 마라. 현재 요구사항을 잘 해결하고,
나중에 수정하기 쉽도록 작성하라.

## 7. 깨진 창문 이론 [PP]

나쁜 코드를 발견하면 즉시 수리하라.
시간이 없다면 최소한 표시해 두라 (TODO 주석, 예외 발생 등).
하나의 깨진 창문을 방치하면 전체 소프트웨어가 빠르게 퇴화한다.

## 8. 추적탄 (Tracer Bullets) [PP]

프로토타입과 달리, 추적탄 코드는 최종 시스템의 골격이 된다.
요구사항에서 시스템 끝까지 빠르고 가시적이며 반복적으로 도달하는 것이 목표다.

| 추적탄 (Tracer Bullet)    | 프로토타입 (Prototype)     |
|--------------------------|---------------------------|
| 최종 시스템의 일부가 된다   | 작성 후 버린다             |
| 가볍지만 완전하다          | 특정 측면만 탐구한다        |
| 실제 환경에서 동작한다     | 격리된 실험이다             |

## 9. 기타 핵심 팁 [PP]

| 팁                         | 설명                                       |
|----------------------------|--------------------------------------------|
| ETC (Easier to Change)     | 좋은 설계의 핵심 가치 -- 변경하기 쉬운 코드    |
| 작은 걸음으로               | 항상 작은 단위로 변경하고 확인하라              |
| 일찍 리팩토링하고 자주 리팩토링하라 | 문제를 발견하면 즉시 개선                |
| 묻지 말고 시켜라            | 결합을 최소화하라                             |
| 우연에 의한 프로그래밍을 피하라 | 코드가 왜 동작하는지 항상 이해하라            |

## 10. 패턴은 절대적 진리가 아니다 [IP]

패턴은 절대적인 진리가 아니므로 상황에 따라 패턴을 적절히 변화시켜 사용해야 한다.
원칙을 명확하게 알고 있다면 새로운 패턴을 만들 수도 있다.
